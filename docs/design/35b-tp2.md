# 35B tensor parallelism (tp=2): Qwen3.6-35B-A3B NVFP4, GDN + MoE

Status: lane G1b, 2026-10-21. Extends [ADR-0006](../decisions/0006-tensor-parallelism.md). Results:
[2026-10-21-35b-tp2-cuda.md](../results/2026-10-21-35b-tp2-cuda.md).

## Model facts that decide the split

- 40 layers: 30 GatedDeltaNet (GDN) layers and 10 gated full-attention layers. Every layer has an MoE FFN.
- Hidden 2048. Attention: 16 q heads, 2 KV heads, head_dim 256, with the output gate stored per head as `[q_h | gate_h]`.
- GDN: 16 k heads and 32 v heads (dk = dv = 128). v head `h` reads k head `h / 2`, the same mapping in the cpu reference
  and `kernels/cuda/gdn.cu`. `in_proj_qkv` rows and conv channels are laid out as `[q (16x128) | k (16x128) | v (32x128)]`.
- MoE: 256 experts, top-8, I = 512, plus one shared expert (I = 512) with a sigmoid gate.
- Formats:

  | weights | format |
  |---|---|
  | attention q/k/v/o; GDN in_qkv, in_z, out | FP8 E4M3, one scale per tensor |
  | experts, shared expert, lm_head | NVFP4 (16-element blocks) |
  | router, shared_expert_gate, in_a, in_b, conv, embedding | bf16 |

## Split per block

| block | split | collective |
|---|---|---|
| gated attention | by head: 8 q heads (with their gates) and 1 KV head per rank. q/k/v are row shards, o is a column shard. | 1 all-reduce, f32 partial |
| GDN | by k-head group: rank r holds k heads `[8r, 8r+8)` and v heads `[16r, 16r+16)`. in_qkv rows and conv channels are sliced per group (q, k, v separately, `ShardAxis::RowGroups`). in_z, in_a, in_b, A_log and dt_bias are row shards. The gated norm weight (`[dv]`) is replicated. out is a column shard. The recurrent state is sharded with the heads, so each rank holds half. | 1 all-reduce, f32 partial |
| MoE, routed | **tensor parallel inside each expert**: every rank holds all 256 experts at I/2 = 256. gate and up rows `[256r, 256r+256)` are sliced separately, and the down columns likewise. | shares one all-reduce with the shared expert |
| MoE, shared expert | same split (gate and up rows, down columns). | |
| router, shared_expert_gate | replicated. The residual stream is bitwise identical on every rank, so every rank routes identically. | none |
| embedding, norms | replicated | none |
| lm_head | rank 0 only (ADR-0006) | none |

**MoE: tensor parallel or expert parallel.** At batch 1 the comm is the same either way: one `[1, 2048]` all-reduce per MoE
layer. Load balance decides:

- Expert parallelism puts top-8 over 2 ranks. The busier rank runs 5.1 experts on average against 4, so expert time
  is about 27 % above an even split.
- Tensor parallelism inside each expert is balanced by construction.
- The CUDA kernels accept I = 256: the decode kernels need `n % 16`; the prefill MMA and w4a16 kernels need `n, k % 128`.
- The combine `out = routed + sigmoid(g) * shared` is linear in both partial sums, and `g` is replicated. So routed and
  shared partials go through **one** all-reduce.
- The MoE output kernels write the activation dtype, so the MoE reduce is a bf16 in-place sum: two roundings, as in
  vLLM. The attention and GDN reduces keep ADR-0006's f32 partials, rounded once.

**Fused ops.** `Model::fused_ok` already turns every fused op off when `tp.world > 1`. That stays: it is conservative, and
CUDA does not register the TP-sensitive folds (`MoeBlock`, `SharedDownCombine`, `SigmoidMulMatmulFp8`) anyway.

## Comm per decode step and over the Spark link

- **Calls per decode step:** 10 attention + 30 GDN + 40 MoE = **80 all-reduces**.
- **Bytes per decode step:** 40 × 8 KiB (f32) + 40 × 4 KiB (bf16) = 480 KiB per rank.
- **Measured NCCL between the Sparks** (2026-10-18, NCCL 2.29.7, unanimis bae817c8): 16-18 µs at 4 KiB, 22 GB/s busbw with
  both PCIe halves of one port.
- **Decode comm:** 80 × ~17 µs ≈ **1.4 ms per token**. The 22 µs of bandwidth time is noise.
- **Reference point:** the 8B on HIP P2P measured 17.6 µs per call, 72 calls, 1.27 ms per token.
- **Decode floor:**
  - tp=1 decodes at 83 tok/s (12 ms/step, CUDA graphs on).
  - At tp=2 rank 0 reads half the layers plus the replicated router, embedding row and the 286 MB lm_head: about 1.3 GB
    against about 2.2 GB at tp=1.
  - The weight-read floor then drops from about 8.5 ms to about 5 ms. Adding 1.4 ms of comm gives a ~6.5 ms floor.
- **Prefill comm:** a 2048-token chunk moves 40 × 16 MiB (f32) + 40 × 8 MiB (bf16) = 960 MiB, about 45 ms at 22 GB/s.
  tp=1 prefill at 16k is ~5300 tok/s, about 385 ms per chunk, so halved compute plus comm is ~240 ms per chunk.
- **Risks to the gain:**
  - CUDA graphs are off at `world > 1` (ADR-0006), so tp=2 decode runs eager. tp=1 eager vs graph is measured so the gap
    can be attributed.
  - lm_head stays whole on rank 0. A vocab-parallel head would save ~0.5 ms per step and is the first follow-up.

## Two hosts: process model and transport

ADR-0006 is one process, one thread per rank. The Sparks are two hosts with one GB10 each, so cross-host tp=2 adds:

- **A remote rank.** `intarsia tp-worker --listen ADDR` runs on spark2. It loads the rank-1 shard from load options sent by
  rank 0, then serves an ordered command stream over TCP:
  - `new_state`, `forward(ids)`, `truncate(len)`, `snapshot(keep)`, `drop`.
  - Rank 0 sends `forward` before running its own forward, and reads the worker's reply after it.
  - The other commands are fire-and-forget on the same ordered stream. Errors surface on the next reply.
  - The engine, server, accuracy and bench code still see one `Model`.
- **A device collective:** `NcclComm` in `intarsia-backend-cuda`.
  - libnccl is loaded with `dlopen` (`INTARSIA_NCCL_LIB`), so the build does not change.
  - The library comes from the vLLM container image on the boxes.
  - Stream-ordered `ncclAllReduce` sums in place. For f32 partials into a bf16 output, a convert follows.
  - Rank 0 makes the unique id and sends it in the hello. Both ranks init the comm before loading weights, with NCCL_IB_HCA
    set to both halves of the direct port. This mitigates spark2's `ibv_reg_mr` ENOMEM history.
- **Numerics.** A two-operand sum commutes. So the NCCL f32 and bf16 sums give the same bits as the host communicator
  (`f32(a) + f32(b)`, one rounding).
  - Gates run on one box with two ranks and the host comm are therefore the cross-host gates.
  - One greedy-ids diff, cross-host against one-box, confirms this before the numbers are reused.

## What each backend gets

- **Core (all backends):**
  - Sharded loading for FP8 and NVFP4 (rows, columns, row groups).
  - Sharded GDN and MoE.
  - Per-rank dims (`LinearDims` and `MoeConfig` halved).
  - The remote-rank protocol.
  - Any `Comm` plugs in.
- **CUDA:** `NcclComm`.
- **HIP (lane G2b):** the core sharding plus its existing P2P comm, in one process with two R9700s. No remote rank needed.
- **Metal:** none. tp=1 is unchanged: every path above is gated by `world > 1`.
