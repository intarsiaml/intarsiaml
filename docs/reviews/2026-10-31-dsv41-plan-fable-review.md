# Review: DSv4.1 Flash unpark plan (read-only)

## 1. Phase order and shortcuts

The order (0 → 1a → 1b → 2 → 3 → 4) is a correctness-first serial chain; the critical path to a TP=2 result is the CUDA kernel work in Phase 2, and nothing in Phase 1b feeds it except frozen op signatures. Changes I would make:

- **Start the EXL3 grouped-MoE lane now, not after 1b.** The Mia checkpoint is EXL3 in nearly every linear, not just experts: `wq_a/wq_b/wkv/wo_a.slice.0-7/wo_b`, compressor `wkv/wgate`, indexer `wk/wq_b`, `engram.wkv`, shared experts, head (6-bit), the whole MTP stack (4-bit). Only norms, `embed`, `ffn.gate` (f16 + f32 biases), `indexer.weights_proj` and `hc_*` are plain. So Phase 1b's "FP8 E8M0" op is nearly irrelevant for this checkpoint, and `MatmulExl3` (admitted on sm_121) plus a *missing* EXL3 grouped-expert kernel and *missing* EXL3 TP sharding (`docs/results/2026-10-21-m2-exl3.md`: "tensor parallelism EXL3 refused at load", "EXL3 routed experts / MoE not covered") are the real bottleneck. Neither needs a new `Op`: `MoeExperts`/`MoeBlock` with a new weight format, and `quant/moe.rs:205-226 load_shard` already shards intermediate width. The `dsv41-cuda-moe` worktree exists and is empty; brief it today.
- **Cut the Rust CPU full-model path.** Keep naive per-op `cpu-ref` implementations (admission needs them), but the oracle is the official torch code with dequantised weights (Lane 0). Run that oracle in `dtype="bf16"` mode: in fp8 mode it fp8-quantises `o` before `wo_a` (model.py:787) and fp4-quantises the indexer query (model.py:553), which neither the EXL3 weights nor TensorFold reproduce; fixtures from the fp8 path would fail a 1e-4 gate for the wrong reason.
- **Merge Phases 2 and 3.** No single Spark holds 202 GB, so the first full-model run is TP=2 anyway. Make every loader and kernel shard-aware from its first commit; "few-layer parity on one Spark" stays as the unit test.
- **Replicate, don't shard, the indexer and the `hc_*` tensors.** The reference all-reduces `index_score` (model.py:560), which at prefill is `[chunk, n_compressed]` fp32: 4096 × 64K × 4 B = 1 GiB per indexer layer per chunk over RoCE. TensorFold needed a patch (`0001-c7-indexer-split`) to survive that. Indexer weights are 0.05 GB; replicate and skip the collective entirely.
- **Shortcut assessment.** TensorFold's host is Zig, so the "family" is a spec, not reusable code; the local `miaai/repo` holds only a Dockerfile plus 34 patches (no `.cu`), and the kit is AOT fatbins with an internal launch convention. Calling those via a C ABI means reverse-engineering parameter structs with no upstream stability promise; the source-level port through the `ik` ABI (ADR-0002, already done for EXL3/NVFP4) is right. Do fetch `bertholomus/TensorFold@629c524` now so Lane 0's porting map works from the kernel sources, and port its four hard kernels (grouped EXL3 MoE, sparse gather attention with sink, indexer score+top-k, hc fused) as the *first* CUDA implementation rather than writing CPU-first versions.
- **Design DSpark hooks in 1a**, since Phase 4 depends on them: tap the mean-over-streams attention input of layers 37-39 (model.py:1269), and make every per-sequence state (window ring, compressed KV, `index_k`, candidates, compressor partial group, Engram token history) live under one `Truncate(len)`-able slot, which `tp_remote` already speaks.

## 2. Technical risks and cheap de-risks

1. **The official code has no chunked prefill and no multi-token decode.** `Compressor.forward` (model.py:466-482), `_window_kv` (701-710) and the indexer mask (564) branch on `start_pos == 0` and otherwise assume one token. Chunked prefill, verify blocks for spec decode, and prompt-cache resume all live outside the reference. De-risk in Lane 0: extend the torch code to arbitrary chunks and assert chunked == whole on one prompt (bitwise when chunk % ratio == 0), plus "prefill N" == "prefill N-3 + decode 3" on `compress_kv`, `kv_state`, `score_state`.
2. **Rounding points, not Sinkhorn.** `hc_split_sinkhorn` is a 4×4 fp32 loop with eps (kernel.py:426-458); low risk. The risk is where bf16 rounding happens: residual stream stored bf16, `hc_mixes` fp32 (954-957), `hc_post` rounds via `type_as(x)` (968), MoE combine fp32 (895), row-parallel all-reduce in fp32 (274). Fixture per sublayer boundary, not per layer.
3. **Sparse attention details** (kernel.py:355-385): `-1` indices skipped, `scores_max` init -1e30 so all-masked rows give 0, sink added only at the end, compressed indices offset by the 128-token window, output rope part counter-rotated (model.py:782), compressed KV on theta 160000 + YaRN with positions = compressed index, stored fp8 (761). Any of these silently shifts KL; a per-op fixture with a 4K prompt covers all.
4. **Top-k is discrete.** Indexer selection flips at score ties, so hidden-state parity breaks after the first flip in long contexts. Gate on selected-set Jaccard (≥0.98 vs TensorFold at 32K) rather than exact match.
5. **Engram slack is one layer.** Layer 1's rows are needed after ~0.4 ms of layer-0 compute. Run `fio randread 4k QD24` on spark2's 93 %-full disk today for p99/p99.9; if p99.9 > 0.4 ms, prefetch the top-4 candidate tokens' rows before sampling (4×48 reads, trivial IOPS) or rely on the DSpark block lookahead.
6. **Engram token map.** Must be bit-exact with the HF `tokenizers` normaliser chain (engram.py:29-39); MiaAI's `dsv41_token_map.json` is a ready fixture.
7. **EXL3 grouped MoE efficiency.** Per rank per token: 18 GEMVs of ~4 MB each with mixed per-tensor K. Microbench today on spark1 next to vLLM: 18 `MatmulExl3` launches at N=1152/K=5120 and N=5120/K=1152 vs the m2 doc's 198-230 GB/s; the gap is the grouped kernel's target. Also check that the Hadamard shard boundary (1152 = 9 × 128) is honoured for `wo_b`/`w2` row-parallel splits.
8. **NCCL over RoCE** is already proven at ~80 all-reduces per step on the 35B (`2026-10-29-tp2r-refresh.md`, 98 tok/s). DSv4.1 adds ~10 more; fine if the indexer is replicated (point 1 above).

## 3. Memory: ≤ 6 GiB non-weight per rank

Itemised: CUDA context + NCCL ~1.8 GiB (cap `NCCL_MAX_NCHANNELS`, small `NCCL_BUFFSIZE`); graphs ~0.3; KV at 128K ~0.5 (window KV trivial; compressed FP8 ~0.2, `index_k` ~0.05); hot tier 1.0; workspace ~0.8 at a 4096 chunk if the indexer is tiled (a naive `[chunk, 32 heads, n_compressed]` fp32 score tensor is 2 GiB per tile, logits for a full chunk 2.1 GiB: never materialise either); IO buffers 0.2. That is ~4.6 GiB **only if the Engram scales are not resident**: the scope doc's 3.07 GiB of resident E8M0 scales would push it to 7.7 GiB. Repack rows as 264 B (payload + scales) at 15 per 4 KiB page: zero resident scales, 3 % padding, 104.8 GB per rank shard, and the NVMe pays 4 KiB per row anyway (device IOPS, not bytes, is the budget). Also design in: O_DIRECT or `fadvise(DONTNEED)` weight loading so 99 GB of page cache does not sit in the unified pool; a per-rank pre-sharded weight cache on local NVMe (Mia does this). Flag disk: spark2 has 272 GB free and already holds Mia's 203 GB Engram copy; a repacked shard plus a rank cache does not fit beside it without deleting the reference engine's data.

## 4. Tuning toward ≥ 0.8x Mia

Dense bound at TP=2 on these weights is ~7.5-8 GB/token, ~4 GB per rank → ~55 tok/s ideal, 40-45 realistic; code at 71 tok/s is unreachable without drafts. Ranked by gain per effort:

1. **Multi-token verify path + n-gram/suffix drafts** (Metal-only `SpecMode::Ngram` exists). Zero model cost, works across hosts via `Forward(ids)` + `Truncate(len)`, and proves the verify path DSpark needs. Large gain on code, small on prose.
2. **DSpark at TP=2.** The blocker is protocol, not kernels: `load.rs:447` refuses cross-process MTP; the drafter must be sharded like the main MoE (replicating 3.7 GB breaks the memory budget). Mia's acceptance is ~2.3 tokens/round on random text, higher on code. This is the only route to the code target.
3. **Fusion**: hc_mixes + Sinkhorn + hc_pre + RMSNorm per sublayer (80/step), all-reduce + hc_post (`INTARSIA_TP_FUSION` gave +4.5 % on the 35B), Engram gate. 5-10 %.
4. **Graph segmentation at layers 1 and 14** so IO waits never sit inside a captured graph; three launches cost ~30 us.
5. **Prefill**: chunk ≥ 4096 (expert bytes are read once per chunk, so larger chunks approach the bandwidth ceiling), tiled indexer with online top-k. Mia's 2090 tok/s at 4K suggests it is indexer-bound.
6. **Expert placement**: lowest. Intermediate-width sharding is balanced by construction at batch 1; EP only helps batched serving.

## 5. Gates

- **"2x reference noise" may be zero.** TensorFold's docs call its variants "bit-identical"; if the Mia server is deterministic run-to-run, the gate is unsatisfiable. Define noise as the KL between two legitimate TensorFold configurations (prefill chunk size, `--graphs` on/off, `TF_DS_IDX_SPLIT`), with an absolute floor around 1e-3 (the m2 doc hit 4.4e-4 engine error on EXL3).
- **Long prompts are missing.** Candidates (layer 20, 2048 blocks × 8) only engage past 16K compressed positions; a 64 × 128 short-prompt set never exercises them, nor top-512 selection. Add ≥ 2 prompts of 32K-64K.
- Add: chunked == whole and verify == decode exactness (needed for lossless spec claims); indexer set Jaccard; DSpark acceptance vs Mia; MMLU 0.879 ± 0.01 via localeval as the end-to-end anchor.
- The endor Q8_K_XL anchor measures the 2.9 bpw format's loss (~0.1 KL), so use it as a sanity bound ("our KL to Q8 within 10 % of TensorFold's KL to Q8"), not a tight pass/fail.
