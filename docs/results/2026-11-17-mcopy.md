# mcopy: copy drafts beside the MTP head (CUDA, Qwen3.6-35B-A3B NVFP4)

Lane `mcopy`, branch `mcopy` from origin/main `a2d6be540`. Opt-in only: `INTARSIA_SPEC_COPY=<n>[,<len>]`, off by default.
Measured on spark1 (DGX Spark GB10) with vLLM up beside it (services flight, guidance, capcom; live traffic adds noise, so every
speed number is an ABBA over server restarts). Raw output: `docs/results/2026-11-17-mcopy/raw/`; scripts: `scripts/mcopy/`.

## Summary

- **What it does.** At each step of a greedy `--spec mtp` request on the single-sequence engine, if the last `n` tokens of
  prompt + output occurred earlier, the (up to `len`) tokens that followed that occurrence are verified as one chain by the
  ordinary verify pass, instead of the MTP head's `k = 2` drafts. Otherwise the step is the usual MTP step. No kernel change;
  the verify pass is the existing `Model::forward_verify` with `1 + len` rows.
- **Gate (a), greedy ids equal `--spec off`: passed, first attempt, no divergence anywhere.** `generate`: 10 prompts (`copy3k`, `json-xform`, `code-gen`,
  `reason`, `chat-short` and the cmtp `short-0`, `short-3`, `4k-0`, `4k-1`, `16k-0`; 256 to 2902 ids) x 1 to 6 copy arms
  (n = 4, 8, 12, 20; len = 7 and 15, i.e. 8-row and 16-row verify passes, the row cap), 41 of 41 comparisons identical. Served:
  every reply of every arm has the same sha as the base arm of its round (and the `--spec off` arm of the first A/B, 5 cells, equals base; `agent-batch` was never compared to `--spec off`) (15 replies per arm and
  round in the first A/B, 21 in the later ones). A cpu unit test (`copy_drafts_beside_the_mtp_head_keep_greedy_output_identical`)
  covers the same on the tiny model with 4 (n, len, k) configurations, `max_tokens` landing inside a chain, and a follow-up request.
- **Gate (b), speed, MTP k2 against MTP k2 + copy (`serve --max-batch 1`, ABBA, 3 rounds x 3 reps per cell):**

  Ratio to base (median of the 3 rounds, the rounds in brackets; base tok/s is the median decode speed). `n12`, `n20`:

## Design (the spec-path changes)

1. `crates/intarsia-core/src/spec.rs`: `CopyCfg { n, len }` and `copy_from_env()` (`INTARSIA_SPEC_COPY`, read once);
   `propose_copy(ctx, cfg)`, which scans `prompt + output` backwards for the newest earlier occurrence of the last `n` tokens
   that has `len` tokens after it (else the longest continuation, at least `COPY_MIN_CHAIN = 3`); `SpecConfig::verify_rows()`
   returns `1 + max(k, len)` for `--spec mtp` when the variable is set, so the model is loaded (plan dry-run, workspace,
   recurrent-state snapshot rows) for the longer pass. `len` is limited to 3..=15 (`1 + len <= Model::VERIFY_MAX_ROWS = 16`).
2. `crates/intarsia-core/src/engine.rs`:
   - `EngineMeta::spec_copy` (tests set it; `None` reads the variable) and `Shared::copy`; `Seq::new` (the single-sequence engine
     only; the batched scheduler builds its `Seq` with `Seq::build`, which leaves `copy` at `None`) sets `Seq::copy` for a greedy
     drafting request with one rank.
   - `Seq::plan_step`, MTP branch: after the same `k`, room and `min_tokens` tests as the head's draft, a chain from
     `propose_copy` returns `Next::Verify(chain)` (the existing variant the n-gram drafter uses) instead of `Next::Draft(k)`.
     `len` is cut by the room left in the context window and by `max_tokens`, exactly as `k` is.
   - `Seq::prepare_with`, `Next::Verify`: for a copy chain it drops a pipelined pre-draft, tells the cost gate a speculative pass
     starts, and catches the head up (`mtp_queue_room` / `mtp_catch_up`, as the `--spec auto` DFlash branch does) when the head's
     queue could overflow: a verify pass only queues the head's hidden rows (`mtp_after_forward`, `catch_up = false`) and the
     rejected ones are dropped by the rollback, the accepted ones are consumed by the next MTP draft, which catches the head up
     over all queued rows. Acceptance and rollback are `spec_accept` / `spec_cut` / `SequenceState::spec_rollback`, unchanged.
   - `Seq::account_verify`: a copy pass says nothing about the head, so neither the back-off gate (`SpecGate::record`) nor the
     adaptive depth sees it. Telemetry (`spec_step(proposed, accepted)`) does, and the trace line says `copy`.
3. `crates/intarsia-models/src/load.rs`: `INTARSIA_SPEC_COPY` with `--spec mtp` is refused at load unless the backend is CUDA (or
   the cpu reference), `--max-batch` is 1 and there is one rank. Ignored without `--spec mtp`.
4. `docs/tuning.md`: the `INTARSIA_SPEC_COPY` row. Tests: `crates/intarsia-core/src/spec.rs` (parse, `propose_copy`),
   `crates/intarsia-models/tests/mtp.rs` (identity with copy drafts).

Notes on the CUDA path that the numbers depend on:

- On the 35B the MTP step is a captured graph (`mtp graph step` in the trace: draft + verify of 3 rows, one replay). A copy
  chain is the eager `forward_verify`. Measured pass times (copy3k, n = 20, len = 7): a chain pass of 8 rows about 30 ms for
  8 tokens, an MTP graph step about 19.6 ms for 2.4 to 3 tokens, so a chain pays when it accepts 3 or more drafts
  (chains that accept fewer lose).
- The verify pass at 8 rows takes the fused GatedDeltaNet verify launch (`gdn_verify_rows_fused`, 2..=8 rows); 9 to 16 rows take
  the per-row loop. That is why the default `len` is 7. `len = 15` (16 rows) is exact too and faster still on text that copies
  all the way (table), but pays more for a miss.
- CUDA verify attention is one decode call per row for an MTP model (`Backend::prefer_verify_attn_per_row`), so the rows are
  bitwise the decode step at any position; this is what keeps 8 and 16 rows exact (16k-token prompt included).

## Gate (b): speed

`scripts/mcopy/ab.sh` (arms differ by environment only; same binary): `serve --backend cuda --max-batch 1 --max-seq 8192 --spec mtp
--spec-k 2 --mem-budget 40`, one server per arm and round, the arm order reversed on even rounds, 3 reps per cell
(`scripts/mcopy/cell.py`: streaming, greedy, thinking off, a per-round nonce in the first user message so no request hits the
prefix store; decode tok/s = (completion tokens - 1) / time after the first token). `scripts/mcopy/prompts.py` writes the cells:

| cell | what | max_tokens |
|---|---|---|
| copy3k | re-emit `scripts/ab35b/toolsmoke.py` (about 3K tokens) with one small edit | 3800 (2903 produced) |
| agent-edit | agent turn: the tool result holds a 6 KB file; emit an `edit_file` JSON call whose `old_string` is a whole function and `new_string` the renamed one | 1200 (about 300) |
| agent-batch | agent turn: the tool result holds a file with call sites; emit one `edit_file` JSON object per site | 1500 |
| json-xform | 34 JSON records in, the same records out with `status` changed where `region` is `eu` | 2600 (cap reached) |
| chat-short, reason, code-gen | controls: explanation, step-by-step arithmetic, new code with test boilerplate | 400, 500, 800 |

Cell values are medians of tok/s over every rep of every round, with [min-max]; the ratio is the median over rounds of the
ratio of the round's medians (base and arm of one round ran back to back), the per-round ratios in brackets. A round uses its own
nonce, so a cell's per-round ratios differ by content as well as noise (agent-edit most: 1.01 to 1.21).

## Findings

1. **Copy-heavy text is where it pays, and by a lot.** The 3K-token re-emit goes from 152 to 262 to 314 tok/s (n12, n20L15 at len 15), 2.9K tokens in 11 s (n12) or 9 s (n20L15) instead of 19 s. A chain of 7 accepts all 7 in 355 of 367 chain passes (7.7 tokens per verify pass against the MTP head's 2.4 to 3 on the same text). JSON transform 1.37 to 1.61x. The gain rises with n (acceptance 65 / 76 / 93 % at n = 8 / 12 / 20 on json-xform: a short suffix finds look-alike text and the chain then misses); n above 20 was not tried.
2. **Agent turns gain little here.** `agent-batch` +4 %, `agent-edit` +2 % (rounds 0.98 to 1.21): the copied part of those replies is 200 to 600 tokens and a chain needs 20 tokens of suffix before it fires. A reply that quotes a whole file (write_file, a long `old_string`) would sit between these cells and copy3k; not measured, there is no agent trace in the repo to replay.
3. **A flat 0.5 to 2 % cost on text that never copies.** `code-gen` has zero chain passes at n = 20 over all 800 tokens and still reads 0.986, 0.977 and 0.994x in the three runs that have it, `reason` 0.978 to 1.000x, `chat-short` 0.976 to 1.000x (n = 20, all runs). The chains are not the cause. The host scan (`propose_copy`, one comparison per context token per step) is a microsecond per step by arithmetic, not measured. The verify passes the model is prepared for go from 3 to 8 rows (`len` 3: 4 rows), which changes the load-time plan dry-run and the workspace; `n20L3` (4 rows) did not remove it, so the 8-row preparation is not obviously the cause either. Not isolated. This flat cost is what fails the 0.99x rule.
4. **n = 8 is too short**: `reason` 0.958x (12 false chains in 500 tokens), json 1.19x against 1.56x at n = 20. n = 12 is borderline (`reason` 0.986x in the main A/B, 0.994x in the first). n = 20 is the setting to try.
5. **len 15 against 7.** 16-row passes are exact (gate (a)) and 18 % faster on copy3k (2.07 against 1.74x), 3 % faster on json-xform, 1.5 % on agent-batch, and 0 to 1 % slower on the controls (not distinguishable from noise). The 9 to 16-row pass takes the per-row GatedDeltaNet loop instead of the fused launch, which the miss rate pays for; a chain pass is about 30 ms for 8 tokens, the MTP graph step about 19.6 ms for 2.4 to 3.
6. **Back-off.** A skip after a chain that accepts fewer than 3 drafts changed nothing at n = 20 and lost yield at n = 4 (above); removed.
7. **Not done / not verified.** The batching engine (`--max-batch` above 1; refused at load), tp > 1, HIP, Metal, sampled requests (greedy only), the thinking mode, speed cells at 16k context (gate (a) covers 16k prompts for ids, 256 tokens), real agent transcripts, n above 20.
