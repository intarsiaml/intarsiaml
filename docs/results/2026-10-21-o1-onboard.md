# 2026-10-21 lane O1: `intarsia onboard`

One command from finished weights to published quick numbers, then the in-depth numbers, resumable. Design, stage table
and flags: `docs/adding-a-model.md` section 0. Code: `crates/intarsia-cli/src/cmd/onboard.rs` (stage list `STAGES`,
runner `run_pipeline`, reports), small visibility changes in `cmd/qualify.rs` and `cmd/qualify/{proc,report}.rs`.

## What it is

`onboard` does not copy qualify, accuracy or bench logic. `quick` and `in-depth` run `intarsia qualify --resume` on
`<out>/qualify/` (first `--quick-only`, then the rest, which skips what qualify already finished); `recipe` calls
`recipe::analyse`; `smoke` runs `intarsia generate`. The six reports (`quick.*`, `in-depth.*`) are qualify's own
renderer on qualify's `state.json`, plus an onboard verdict banner and a stage timeline. Onboard's own state file
(`onboard-state.json`) holds one record per stage (verdict, start, end), is saved atomically after every stage, and
names the stage that was running when the process died.

## Notes and limits

- qualify (and so onboard) now forwards SIGTERM / SIGINT to the subprocess it is waiting for and to its bench server
  (`proc::forward_termination`; before, a plain kill left them running on macOS because they are in their own process
  group and `die_with_parent` is Linux-only). This changes qualify's behaviour on signals only.
- A SKIP inside qualify (for instance no golden) is final for onboard's `quick` stage; supply the golden and
  `--redo quick`. A different `--golden-from` between runs is refused by qualify's own key check.
- A stage that is resumed shows its last attempt in the timeline, with the first start as a note; the qualify rows show
  every sub-stage with the time it ran.
- Not run: spark1 CUDA with vLLM up (optional in the brief; spark1/spark2 were held by another lane's exclusive job).
