## 3. Changes

1. **M=1 MXFP4 GEMV with x in LDS** (`kernels/hip/mxfp4.hip`, `mxfp4_gemv1_lds_kernel`). The block stages x once (QDQ'd
   per 32-group when `act` = 1), component-major so lanes read consecutive 16-byte words (the first, group-major layout
   had a 16-way bank conflict); grid sized 4 blocks per CU with a grid-stride row loop; 8 groups per lane in flight;
   the first batch is loaded before the staging. K > 8192 (`down_proj`, 34 KB of x) keeps the pre-pass + plain GEMV:
   the LDS kernel lost 27 us per call there to occupancy. Per row the arithmetic is that of the old GEMV on a pre-passed
   x (same lane-to-group map, fma chain, warp sum; QDQ'd values are exact in bf16). Knob
   `INTARSIA_HIP_MXFP4_LDS=<blocks per CU>`, 0 = old path. Alone: +2.0 % (A/B x3 30.3 to 30.9, 29.8 to 30.4; window 7).
   Iterations that did not help (raw in `burst-logs.txt`): 8-row blocks (60.7 us avg, slower), the bank-conflicted
   layout, 1 / 8 / 16 / 64 blocks per CU, batching without the pre-staging prefetch.
2. **`Op::MatmulMxfp4Pair`** (core op, appended; CPU reference = two `MatmulMxfp4`, bitwise; HIP kernel
   `matmul_mxfp4_pair_gemv` = one LDS-kernel launch over the rows of both matrices, or the two single ops when M > 1 or
   K > 8192; CUDA / Metal do not implement it, so `try_fused` falls back to the unfused pair there). Wired at GDN
   in_qkv / in_z, in_b / in_a, attention k / v and FFN gate / up, only when both are MXFP4 with the same `act_quant`.
   Launches 855 to 743; together with change 1: +7.3 % / +7.0 %.

## 4. Gates (final window #3321, tree `34d31926` + scripts)

* **27B bitwise.** Self-golden written by the base build on the golden's 10 prompts: new vs base gives
  mean KL21 2.642356e-12 prefill / 2.288803e-10 decode, 0 flips, PASS; **base vs its own self-golden gives the same
  numbers to every printed digit** (`raw/acc/sg27-selfbase.log`), so the residual is the self-golden comparison's own
  floor and the new logits equal the base's. 256 greedy ids identical to base at short and 4k prompts (md5
  `2086b6a4`, `ef88d237`), also with `INTARSIA_HIP_MXFP4_LDS=0`.
* **HIP kernel-level bitwise tests** (`crates/intarsia-backend-hip/tests/mxfp4_decode.rs`, added after review):
  `mxfp4_gemv_lds_is_bitwise_prepass_gemv` (M = 1 LDS kernel vs every row of an M = 2 pre-pass + GEMV call on stacked x;
  the 27B shapes K = 5120 / 6144 / 17408 plus edges; act dynamic and none; bf16 and f32 out) and
  `matmul_mxfp4_pair_is_bitwise_two_gemvs` (pair vs two single GEMVs, M = 1 and 2, act dynamic and none): 2 passed
  (window #3507). Mutation check on a copy of the tree (#3510): QDQ dropped from the LDS staging, and the pair's second
  segment reading the first segment's scales: both tests FAIL (17125 of 17408 and 6131 of 6144 elements differ).
* **27B A2 reference-noise gate** (W4A4 golden, ref-noise sidecar): prefill KL21 1.799e-1, 0.913 x ref noise, **PASS**;
  decode 1.392 x ref noise, FAIL as on main (1.39), **not worse** (`raw/acc/acc27-final.log`).
* **35B (NVFP4) and 8B (bf16), HIP:** 256 greedy ids identical base vs new, short and 4k prompts (`IDS SAME` x4,
  `raw/ids/`). Neither model has MXFP4 tensors, so neither reaches the new code; the call sites only add an
  (MXFP4, MXFP4) arm.
* **`kernels test --backend hip --model <27B>`:** 55 kernels, 1090 cases, **0 FAIL**; `matmul_mxfp4_pair_gemv` 82 cases
  ADMITTED (`raw/kernels-test.log`).
* **CPU / Metal / CUDA crates (endor, by the worker):** core + cpu + models 269 passed; metal + cuda 135 passed; CLI
  builds; HIP crate lib tests 17 passed (tatooine). The CUDA and Metal no-op checks on their boxes are the coordinator's.
