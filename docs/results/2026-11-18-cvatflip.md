### HIP and Metal: not affected

- The variable is read in exactly one place: `verify_attn.rs:57` (`cuda_verify_attn_rows_env`), called from `model.rs:1812` with `b.name()`. `verify_attn.rs:52` returns `false` unless the backend name is `"cuda"` (CUDA `device.rs:256` = `"cuda"`, HIP `device.rs:791` = `"hip"`, Metal `lib.rs:973` = `"metal"`; the CPU backend is neither). A grep of `crates/` finds no other reader of `INTARSIA_CUDA_VERIFY_ATTN_ROWS`.
- The field `cuda_verify_attn_rows` is consulted only at `verify_attn.rs:116` (table registration, early return) and `verify_attn.rs:160` (captured launch, `Ok(false)` = the unchanged per-row launches); the batch-view `Model` hard-codes `false` (`model/batch.rs:1154`). So on HIP and Metal the field is `false` for every value of the variable and both sites take the old path.
- HIP keeps its own `INTARSIA_HIP_VERIFY_ATTN_ROWS` (eager passes, `model.rs:1878`, unchanged). Unit test `other_backends_never_read_it` and the three `cvat_*` process tests assert `hip` / `metal` / `cpu` stay `false` for unset, `0` and `1`.

### Table cap (1024 pairs): not reachable, no fix needed

- A "pair" is the `(K device address, V device address)` of one attention layer's cache in one `SequenceState` (`verify_attn.rs:VerifyCapTab.regions`, keyed by `device_address(kv.k), device_address(kv.v)`), registered from `capture_spec_step` (`spec_graph.rs:471`) for the sequence's caches and its MTP head's cache.
- States are allocated once per engine slot, not per request: `LocalEngine::new` calls `model.new_state()` once (`engine.rs:764`), the batched engine once per slot (`engine/batch.rs:1141`); a request `reset`s / truncates the state, the KV buffers (and so the pairs) stay. There is no code path that reallocates KV buffers while serving. So the table grows with the number of sequence states, never with requests.
- Size: the 35B has 10 full-attention layers + the MTP head's cache = 11 pairs per state, so 1024 pairs hold 93 states; `--max-batch` is at most 32 in the recipes (352 pairs). Past the cap it still degrades to the per-row launches with a stderr note (`captured: all table regions taken`), never to a wrong result.
- Served evidence (`scripts/cvatflip/churn.sh`, `raw/g-churn.log`, `raw/churn/serve.log`): `serve --max-batch 1 --spec mtp --spec-k 2`, 50 distinct sequential greedy requests (50 of 50 ok, 888 graph replays, 5 captures): all four registrations print `captured table regions 11 of 1024`; the count never moved. `--max-batch 8` (mb8 gate, 8 concurrent requests, `raw/mb8/serve-def.log`): 11 -> 22 -> 33 regions, one more 11 for each new slot state that first captured, still per state.
