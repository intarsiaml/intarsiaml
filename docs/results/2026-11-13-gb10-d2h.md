# gb10-d2h: is a pageable device-to-host copy exposed to the GB10 stale-page fault?

Date: 2026-11-13. Lane `gb10-d2h`, spark1 (GB10, driver 580.178.04). Result: **not exposed in 917,600 checked copies; no engine change.** The positive control (TensorFold's exact conditions) did not fail either, so this is "no evidence of exposure", not proof of absence. Raw logs: `docs/results/2026-11-13-gb10-d2h/raw/`. Repro: `scripts/gb10-d2h/`.

## The report

TensorFold issue #2102, fixed in #2103 (`a3962b45f`) and #2289 (`e9ee73834`): on a GB10 with driver 580.178.04 and `uvm_ats_mode=1`, a synchronous `cuMemcpyDtoH_v2` into pageable host memory returned `CUDA_SUCCESS` while some destination pages kept their old contents and the bytes landed on other pages of the process (an allocator's footer was overwritten). The downstream fork's rank-round test hit it 10 times in 60 runs. Its conditions: two host compare buffers from a Zig GPA that churns, 296 KiB logits-row downloads, a "larger allocation/comparison workload". `compute-sanitizer` was clean and both buffers were unregistered pageable host memory. Pinning the compare buffers gave 0/60; a pinned bounce gave 0/100. TensorFold itself has no small reproducer: 40,000 fresh-mapping downloads (C and Zig) and 200 runs of its own smoke test on the same driver never missed. Its fix stages every integrated-device download through a per-thread pinned buffer, at most 4 MiB a piece (cost on an idle GB10, direct against staged: 303,104 B 10.59 vs 20.97 us, 4 MiB 84.74 vs 212.36, 64 MiB 1,354.59 vs 4,095.36 us).

## Our path

`Backend::download` in `crates/intarsia-backend-cuda/src/device.rs` (`ik_rt_memcpy_d2h`) calls `cudaMemcpyAsync(D2H)` on the engine's stream and then `cudaStreamSynchronize` (`kernels/cuda/ik_runtime.cu:93`), straight into the caller's pageable `&mut [u8]` (the prefix store's `take_host_buf` Vecs, logits rows). It is the same class as TensorFold's `download`: no pinned bounce, pageable destination. Stream 0 is a non-blocking normal-priority stream; every other stream id is the high-priority decode lane.

## Method

`scripts/gb10-d2h/d2h_repro.cu`, built by `run.sh` with the engine's nvcc flags (`-O3 --std=c++17 -lineinfo --expt-relaxed-constexpr -arch=sm_121`) and linked against the real `kernels/cuda/ik_runtime.cu`, so the `ours` rows run the engine's exact function. Device buffers hold a position-dependent 64-bit hash pattern (written by a kernel). Each run: allocate a destination, copy, then check every byte against the pattern, check canary guard pages before and after the destination (misplaced bytes), and check a pool of live heap buffers (allocator churn: 48 buffers, 3 replaced every 4th run) for changed fingerprints.

| Method | Call |
|---|---|
| `ours` | `ik_rt_memcpy_d2h` on a non-blocking stream (the engine's path) |
| `ours_hp` | the same on a high-priority stream (decode lane) |
| `sync_rt` | `cudaMemcpy(D2H)` (TensorFold's condition, runtime API) |
| `sync_drv` | `cuMemcpyDtoH_v2` (TensorFold's exact call) |
| `bounce` | negative control and candidate fix: `ik_rt_memcpy_d2h` into a 4 MiB pinned buffer, `memcpy` on |
| `mut_noop`, `mut_skippage` | harness self-test: copy nothing; skip one page in the middle |

| Destination | State |
|---|---|
| `fresh` | new malloc/mmap per run (glibc mmaps the big ones), prefilled 0xAA like TensorFold's compare buffers |
| `cold` | new, pages never touched before the copy (the driver faults them in) |
| `reuse` | one long-lived buffer |
| `rand_off` | fresh, copy lands at a random unaligned offset (1..4093) |
| `thp` | 2 MiB aligned mmap with `MADV_HUGEPAGE`, prefilled |
| `pageout` | prefilled then `MADV_PAGEOUT`: 0.0 % of its pages in the process page table when the copy starts (`/proc/self/pagemap`), the copy faults them back in |

Environment: spark1, NVIDIA GB10, driver 580.178.04, CUDA 13.0 (runtime and driver API 13000), kernel 6.17.0-1032-nvidia, `uvm_ats_mode=1`, `integrated=1`, `pageableMemoryAccess=1`, THP `madvise`, vLLM (34 GB, flight/guidance/capcom) up and serving throughout, 121 GB, 82 GB available at start, swap 6 GB used. The one thing that differs from TensorFold's box is the kernel (theirs 7.0.0-1024-nvidia). Under fleetq `--quiet gpu`; nothing else on the box was touched.

Harness self-test (p8, 20 runs per cell): `mut_noop` and `mut_skippage` were flagged on 20 of 20 runs in every destination kind (a skipped page shows as 4,078..4,086 stale bytes in the page next to the first mismatch, still 0xAA on prefilled kinds), so a dropped page of the TensorFold kind would have been seen. Note that p6 ran before the `pagemap` presence check was added; the `pageout` code was the same, and the check run afterwards (p8, #9274) shows 0.0 % present for 296 KiB and 4 MiB destinations.

## Result

Not exposed in what we could run. 917,600 copies through our call sequence and TensorFold's, in the memory states the report names (fresh pageable mappings, allocator churn, 296 KiB rows) and several it does not (cold pages, unaligned destinations, huge pages, swapped-out pages, page-cache and fault/drop pressure, 8 concurrent threads, a competing GPU kernel stream, 4 KiB to 600 MiB), produced no stale byte, no misplaced byte and no CUDA error.

What this does not show: the positive control never failed either. TensorFold could not reproduce its own fault outside the fork's rank-round workload, and neither can this harness. So a clean `ours` result says our path is no worse than `cuMemcpyDtoH` on this box under these workloads; it does not say the driver fault is absent on spark1. The fault may need that workload (a Zig GPA with a large allocation and comparison pattern), or the kernel 7.0 their box ran (spark1 is on 6.17.0-1032). The engine's download buffers are heap `Vec`s (the prefix store's `take_host_buf`), the same destination class as TensorFold's compare buffers; this lane did not check serving or gate evidence for wrong restores.

## Cost of the fix, in case it is ever needed

The `bounce` rows are a measured candidate (4 MiB pinned chunks, one synchronous copy per chunk, `memcpy` on), medians in microseconds on the quiet box (p1, fresh destination), against the direct path:

| Bytes | Direct (`ours`) | Pinned bounce | x |
|---|---|---|---|
| 4 KiB | 6.6 | 6.6 | 1.0 |
| 64 KiB | 7.9 | 10.4 | 1.3 |
| 296 KiB (logits row) | 15.0 | 23.1 | 1.5 |
| 1 MiB | 27.7 | 60.2 | 2.2 |
| 4 MiB | 81.5 | 218.3 | 2.7 |
| 16 MiB | 295.5 | 866.8 | 2.9 |
| 64 MiB | 1,149 | 3,797 | 3.3 |

That matches TensorFold's own measurement (about 2x at a logits row, 3x at 64 MiB). A prefix-store capture of a few hundred MiB would cost several ms more per 64 MiB, which on a hot path is not free; so the fix is not applied pre-emptively. If a corrupt download is ever seen on a Spark: (1) put the staging in `ik_rt_memcpy_d2h` (a thread-local pinned buffer of at most 4 MiB, copy in pieces, `cudaMemcpyAsync` + sync into it, `memcpy` out), which covers every caller and costs the table above; or (2) cheaper for the big users, have the prefix store allocate its host buffers pinned (`cudaHostAlloc`) so the copy is direct into page-locked memory with no extra `memcpy`. (2) belongs in `crates/intarsia-core/src/prefix_store.rs`, which another session owns, so it is described here and not implemented.

## Left undone

- No engine change, so no backend tests were run (nothing in `crates/` or `kernels/` changed).
- The positive control stayed negative; a deterministic reproducer would need TensorFold's fork (zspark) rank-round test, which is not in `/opt/code/TensorFold`.
- Not tried: a kernel 7.0 box; a different `uvm_ats_mode`; the engine's real server under load with downloads checked end to end.
