## Recommendation (for the morning)

**Make the draft vocabulary 131072, not 65536.** The set `INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1 INTARSIA_VERIFY_TOPK=1 --mtp-draft-vocab 131072` has **no losing cell**
in the 16 cells measured (4 prompt sets x thinking on / off x 1 and 2 streams, ABBA against main's default, 16 / 16 seeded replies identical to the default's in every cell):

| cells (T = 1.0, seeded, 384 forced tokens) | 1 stream vs main default | 2 streams vs main default |
|---|---|---|
| English chat | +5.7 % (thinking) / +3.3 % (off) | +14.4 % / +21.3 % |
| code | +3.6 % / +4.9 % | +13.6 % / +26.8 % |
| Chinese prompts, thinking default (English think block, 4 % CJK) | +4.4 % | +10.1 % |
| Chinese (thinking off: the reply is Chinese) | **+2.8 %** | **+14.3 %** |
| mixed (en, zh, code, JSON pairs) | +5.1 % / +3.2 % | +14.5 % / +14.9 % |
| ~3k-token prompts | +4.0 % | +10.9 % |

Where it loses against the default: **nowhere**; the smallest gain is +2.8 % (Chinese, 1 stream), comparable to the visit-to-visit spread (up to ~3 % on this cell), so read it as flat. What it gives up
against 65536 is ~2-3 points on English / code at 2 streams (e.g. code 1.268 vs 1.304 with thinking off) in return for not losing 21-24 % on Chinese.
ITL p99 is at or below the default's (within 1 ms) in 15 of 18 cells. The three that are worse: code, 1 stream, thinking (171 vs 160 ms) and mixed with thinking off, a Chinese stream beside an English one,
at 1 stream (144 vs 130 ms) and at 2 streams (178 vs 156 ms, +14 %; every arm with batched verify is above the default in that cell: P0 171, P65536 204, P98304 173). 8 requests per cell, so the tail is a coarse number, but the mixed-language pair is the one
cell where the tail should be watched.

If the user flips defaults, in order of risk:
1. **`--mtp-draft-vocab 131072` alone** (recipe `[tuning.cuda] mtp_draft_vocab = 131072` in `recipes/qwen3_5_moe.toml`, the key exists): +3 to +6 % at 1 stream, about neutral at 2 streams (with `batched_mtp = 1` nothing drafts there; mtp2s's D arm measured +1 %), no loss anywhere,
   output unchanged (verify keeps the full head), no new code path. The 65536 of the mtp2s doc must **not** be the value.
2. **`batched_mtp = 2`** (same recipe table) **plus `INTARSIA_BATCHED_VERIFY=1` and `INTARSIA_VERIFY_TOPK=1`** (env only today, no recipe key: flipping them needs a small code change to make them recipe or on-by-default knobs): the 2-stream gain.
   With the full head instead of 131072 the 2-stream gain shrinks to +5 to +16 % (P0 rows), so step 1 is what makes step 2 worth it.
3. `--mtp-draft-vocab 65536` only for a deployment whose traffic is known to be Latin-script only.

## What the draft vocabulary is, and why 65536 fails on Chinese

- Rule (confirmed in code): `--mtp-draft-vocab N` is the **first N ids** of the lm_head (`Model::load`, `QTensor::row_prefix`; `model.rs:188`: "token ids 0..N"). Multiple of 8 (all values here are multiples of 128). The verify pass keeps the full head, so output never changes, only acceptance.
- Layout of the Qwen3.6-35B vocabulary (`scripts/dvocab/tokscan.py`, `raw/tokscan.txt`; 248044 tokens): ids 0-95723 are ASCII / Latin BPE; **the first Chinese token is id 95726** (`的`), Chinese runs from there in
  roughly descending frequency (the ~150 most common characters are ids 95726-96674, common words such as 我们, 可以, 因为 are 96050-97500); Chinese occupies ids 95726-147455 (51k of its 55k tokens); ids above 147456 (~100k tokens) are other scripts and symbols
  (Latin extensions, Cyrillic, Arabic, Hangul, kana, ...). Chinese tokens below N: 65536 -> **0**, 98304 -> 2275, 114688 -> 18640, **131072 -> 35024**, of 55328.
- So the reduced head with N = 65536 can **never propose a Chinese token**; with N = 98304 it proposes only the ~2300 most frequent; 131072 holds the 35k commonest Chinese tokens plus all of ASCII.
  The frequency ordering already exists in the vocabulary, so no reordering or new analysis is needed: a prefix is already "ASCII plus the frequent Chinese". Its price: head work ~ N / 248320 (0.53 for 131072 vs 0.26 for 65536).
- Why mtp2s saw only 0.71 -> 0.60 on "Chinese": with the thinking default the 35B answers a Chinese prompt with an **English think block** (CJK characters = 4 % of the 384 forced tokens' text; `speed.py` now records
  `cjk_share`), so that set measured mostly English. With thinking off the reply is Chinese (45 % CJK characters) and 65536 collapses (below).

## Method

`scripts/dvocab/` (copied from `scripts/mtp2s/`): `sweep.sh` / `sweep2.sh` (thinking default / off), `speed.py` (new sets, see below), `sweep_table.py`, `tokscan.py`. Binary: main 4a62a9743 (no code change; fleetq #9320 build).
Per visit a fresh `intarsia serve --backend cuda --max-seq 32768 --mem-budget 40 --max-batch 2` (35B NVFP4, spark2; vLLM `retro` up and idle, `vllm_busy` 0 before and after each visit), memwatch killing under 10 GB (never fired), then `speed.py` for each set
at 1 and 2 streams: **8 prompts, 384 forced tokens each, temperature 1.0 with top_k 20 / top_p 0.95 and a fixed seed per prompt**; 1 stream = the 8 prompts in turn, 2 streams = 4 consecutive pairs; combined tok/s = median over the pairs of the summed per-stream decode tok/s (localeval's definitions); a warm-up request first.
Arms: **A** main's default (MTP k = 2 for a lone stream, no drafting at 2 streams, full head); **P0 / P65536 / P98304 / P114688 / P131072** = `INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1 INTARSIA_VERIFY_TOPK=1 --spec mtp --spec-k 2 --mtp-draft-vocab N` (P0: N = 0, the full head).
Order per job (ABBA, mirrored): `A P0 P131072 P98304 P65536 P65536 P98304 P131072 P0 A`, so every arm has two visits, one early and one late (exceptions: P131072 has four visits in the thinking-off cells, two more from #9323, which bracketed P114688 against P131072 and not against A; A and P131072 have two visits in `long`). Each visit logs whether the server fell back to the full head (the `not applicable to this lm_head` line): 0 in every visit.

Prompt sets (8 prompts each, `speed.py`): **en** (lane mtp2s's: hash maps, a story, sieve, French Revolution, Rust merge, German translation, a train sum, an email), **code** (Python, Rust, SQL, TypeScript, bash, C++, Go, a refactor),
**cjk** (8 Chinese prompts, the first two mtp2s's), **mixed** (pairs `en+zh`, `code+JSON`, `en+code`, `zh+en`, so at 2 streams a Chinese and an English stream share a verify pass), **long** (mtp2s's ~3k-token prompts, 4 per visit).
Two thinking modes: server default (Qwen3.6: think block first; what mtp2s measured) and **`-nt` = thinking off** (the forced tokens are the answer; a Chinese prompt gives Chinese). Jobs: #9321 thinking default, #9322 thinking off,
#9323 P114688 against P131072 (thinking off; order P114688 P131072 P131072 P114688), #9324 long prompts (A P131072 P131072 A).
The 2-stream acceptance of A is not shown (it does not draft at 2 streams; the few passes in its counter are warm-up and tail effects).

## Not built, and why

- **An adaptive rule** (drop to plain batched decode when rolling acceptance falls under a threshold): not needed, there is a value with no losing cell. If a deployment mixes in languages that sit above id 147456 (Cyrillic, Arabic, Hangul, kana,
  Latin extensions: ~100k tokens, not measured here) a reduced head cannot draft them at all, and then `--mtp-draft-vocab 0` is the safe setting or a rolling-acceptance fallback is the next step.
- **A frequency-ordered subset** instead of a prefix (e.g. ids 0-65535 plus the first ~20k Chinese tokens, a head of ~87k rows): the ordering already exists (see above), but using it needs a row gather at load and an id remap after the argmax on every backend
  (the draft token feeds the next head step on device), i.e. new code in `model.rs` and the graph paths. Expected gain over 131072: the 2-3 points on English / code that 65536 has, at the cost of a tail of Chinese below 20k.
  Left for later; 131072 already has no losing cell.

## Leftovers

- **Tool calls** were proxied by one JSON-output prompt in `mixed`; no request used the `tools` parameter (thinking is usually off for them, so the `-nt` cells are the closest).
- **Tensor parallelism not measured** (TP = 1 only). With a vocab-parallel head at TP = 2 the 35B head shard on rank 0 is 124160 rows, so 131072 exceeds it: `row_prefix` on the shard fails and rank 0 loads a separate head and reduces it
  (`model.rs` ~1700, no fallback line printed). It should still work, but it is untested here; keep a recipe default for TP = 1 or test before a recipe-wide flip.
- **The 27B default (65536 on HIP and CUDA)** very likely has the same problem: its tokenizer has the identical id layout (`raw/tokscan-27b.txt`: first Chinese id 95726, 0 Chinese tokens below 65536), which fits the 27B CJK loss in the LOG (65.9 -> 51.4 %).
  Not measured and the 27B recipe untouched: a user decision.

- A real traffic sample would settle the language mix; Cyrillic, Arabic, Hangul and kana were not measured (they sit above id 147456 and no prefix up to 131072 contains them).
- ITL p99 per cell rests on 8 requests; a production-shaped run (many more requests) would tighten it.
- The greedy path was not re-measured (mtp2s: greedy gains are larger, same acceptance ordering).
- If the user flips `batched_mtp = 2` by default, `INTARSIA_BATCHED_VERIFY` / `INTARSIA_VERIFY_TOPK` need recipe keys (env-only today).
