## What the numbers say about TF's gate/up kernel

TF ships only a cubin (`bertholomus-tp2/kit/cubins/experts_cb.cubin`); what follows comes from its launch code
(`zig/src/families/dsv41/exl3_experts.zig`), `cuobjdump -res-usage` / `-sass` (raw/cubin) and the nsys trace (`prefill/raw/tf`).

- Launch: `grouped_mma_kernel<2,2,10,true,4>`, grid `(1, I/64 = 18, n_gu*2)`, 256 threads, 106 registers, 64-row work-list entries (`mma_rows_gu = 64`), K split 4
  (K splits folded in the program), per block 64 columns.
- SASS of that instance: 112 HMMA.16816, 46 LDGSTS (cp.async), 28 LDSM (ldmatrix), 52 BAR. So its A operand (the activation rows) is staged through shared
  memory and read with ldmatrix; ours was read word by word from global memory by every lane.
- Per layer, matched pass for pass (rank 0, chunk 2048, `raw/bench/layermatch.py`): gate/up ours 18.2-23.2 ms vs TF 11.9-14.2 ms (ratio 1.50-1.68); down ours
  6.3-7.8 vs TF 5.7-6.9 (ratio 1.05-1.10). Down is not the gap; the "MoE down 187 vs 97" of the brief includes kernels other than the down GEMM.

Microbench (`raw/bench/moe_bench.cu`, spark, next to vLLM): the repo's `grouped_rows_kernel` as baseline on synthetic experts (384 + 1 shared, 2048 rows, 6 routed
slots + shared, sigma 0.5 routing: 629 groups of 32 members), widths k2 = 6 (routed) / 8 (shared). **Calibration:** the baseline takes 21.4 ms against 21.2 ms
mean in the real trace (nsys, same grid 1668 on the 9 column blocks). Every variant is checked bitwise against the baseline's Z.

| variant (job 8049 slot, `raw/bench/moe_bench-1102-200204.log`) | median ms | vs base |
|---|---|---|
| base: repo kernel, 4 warps x (2 member tiles x 8 n tiles), 128 thr, 255 regs | 21.43 | 1.00 |
| **staged A, 256 thr = 4 K quarters x 2 column groups, 32 rows x 128 cols (shipped)** | **14.09** | **0.66** |
| same, 2 stages instead of 3 | 14.55 | 0.68 |
| same, 1 k tile of weights in flight instead of 2 | 15.03 | 0.70 |
| staged A on the base shape (128 thr, 8 n tiles) | 18.22 | 0.85 |
| no staging, 256 thr, 32 x 128 | 19.52 | 0.91 |
| no staging, 64 rows x 64 cols (TF's tile) | 25.37 | 1.18 |
| no staging, 48 rows x 64 cols | 24.16 | 1.13 |
| no staging, 16 rows x 64 cols | 38.10 | 1.78 |
| 64-row groups with 128 or 512 threads, register-capped | 68-79 | 3.2-3.7 (spills) |
| staged A with 64 rows: shared memory 110 KB > 99 KB per block | does not launch | |
| knockout: no A loads (timing only) | 11.08 | 0.52 |
| knockout: no weight decode | 18.64 | 0.87 |
| knockout: no mma | 13.67 | 0.64 |
| knockout: no A, no decode | 10.62 | 0.50 |

Reading: (1) 64-row grouping is not what makes TF fast. Without staging it is slower in every shape I could build; the groups-of-64 count (440 vs 629) is not the win it
looks like. (2) The A path was the cost: removing it halves the launch, decode alone is 13 %. (3) Staging A recovers 7.3 of the 10.8 ms the A knockout promises and lands
at 14.1 ms against TF's 13.4 ms in the same layers (TF mean over the 20 matched layers 13.4; ours before 21.2). The knockouts are upper bounds (they also drop the dependency
chain), so the 10.6 ms floor is not reachable.

**DRAM byte floor.** Gate+up weights of one layer on one rank: 1.628 GB (all 384 experts, 3 bpw routed mix {k2 4: 12.5 %, k2 6: 87.5 %}; `raw/bench/cachestats.txt`,
header + meta read from the rank cache). At the practical read rate measured on the same box (arena stream, 224-239 GB/s) that is 6.8-7.3 ms; at the 254 GB/s nominal
6.4 ms. Plus the activations, 2 x 147 MB written by `rot_in` and read once from L2/DRAM, about 1.3 ms. So: ours was 3.0x the weight floor, the staged kernel is 2.0x,
TF is 1.9x. The gap to TF is now 5 % (inside the layer-to-layer spread); the gap to the floor is 2x and is mma plus decode plus the 8-warp reduction, i.e. the next lever is
compute organisation, not bytes.

**Bench to real.** The brief warned that bench savings reach the real path at about 40 %. Here: router 2.55 ms per call saved in the bench x 80 calls (40 layers x 2 chunks
of 2048) = 0.20 s expected, 0.278 s measured (chunk 2048, router tile only); gate/up 7.34 ms x 80 = 0.59 s expected, 0.495 s measured (84 %). Both benches ran the repo's kernel on
the real shape with a calibrated baseline, which is why the ratio is high; the 40 % applies to benches whose baseline is not calibrated.

## Router gate (task 1), bench numbers

`raw/bench/router_bench-1102-191404.log` (spark1, M rows, N = 384, K = 5120, bf16 x, f16 w, f32 y; all rows bitwise equal to the one-row tile):

| M | R=16 (was) | R=8 (shipped) | R=4 | R=4 unroll 4 | R=2 |
|---|---|---|---|---|---|
| 512 | 0.635 ms | **0.347** | 0.377 | 0.394 | 0.578 |
| 1034 | 1.286 | **0.697** | 0.758 | 0.818 | 1.165 |
| 2048 | 4.251 | **1.696** | 1.841 | 1.594 | 2.302 |

A tensor-core version was not built. There is no mma with a bf16 A and an f16 B operand, so either side would be converted first and the f32 sums would no longer be
the decode kernel's; that would be an opt-in numerics change, and the bitwise tile already gets 2.5x. The knockout without activation loads is 0.46 ms at M = 2048: the
kernel is bound by re-reading x (R=8 is faster than R=16 in every row of the table; why, the registers at R=16 or the load pattern, I did not isolate). Further tuning (unroll, R=4, staged x) was not tried (the remaining
gain is under 3 % of the prefill). The `tile` micro-kernels of the first run (8x8, 16x4, 6x6) reported "not bitwise"; that was a bug in the bench's write-out (lanes
>= 32 never wrote), not numerics, and they were dropped.

## Combine, rot_in, epilogue (task 3): stopped

- `combine_kernel` (4.5 ms per launch in the nsys trace at 2048 rows, TF `down_combine` 1.7 ms): in the microbench the same kernel takes 1.47 ms (228 GB/s of a 254 GB/s
  floor of 1.32 ms), also right after a kernel that wrote all 293 MB of Z (1.52 ms), and a register-resident warp-per-item variant (bitwise equal) takes 1.46 ms.
  So the kernel is at the floor standing alone; the 3x in the real pass is not the kernel's design and a kernel rewrite cannot plausibly deliver it. What differs in
  situ I did not find (guess: memory-bound kernels run slower in the real pass because of CPU/GPU contention for the unified memory; the router is 1.36x slower in situ than in
  the bench for the same reason).
- Potential if the 2.9 ms per launch were recovered: 0.23 s of 4.5 s (5 %) at chunk 2048, 2 % at chunk 512 after the 40 % rule; unproven, so not attempted.
- `rot_in` (1.8 ms), `epilogue` (0.8 ms), `group_kernel`: TF's `gateup_epilogue` is 0.8 ms as well; no gap worth 3 %.

## Not checked

  window; the changed kernels run only for prompt chunks (T >= 64 rows) and, for the router, at M > 1 (the speculative verify windows use R=8 now instead of 16, bitwise; golden ran with the

  launch), the real model has only 4 and 6.
