[docs/design/35b-tp2.md](../design/35b-tp2.md). Branch `feat/35b-tp2` on origin/main `789511c`. Raw logs: `2026-10-21-35b-tp2-cuda/raw/`.

  - dev = `8a564d3` (one-box gates);
  - xdev = `240580e` (cross-host). It differs from the branch head only in comments and in the CLI same-device check.
  - All built on spark2 with spark1's Rust 1.90 toolchain (copied), CUDA 13.0.3.
- **NCCL:** 2.30.7+cuda13.3 (the library's own banner; torch in the same image reports the 2.29.7 it was compiled against), `libnccl.so.2` copied out of the vLLM container to `~/intarsia-nccl/` on both boxes.

## 2. tp=2 accuracy, cross-host (the real configuration)

Rank 0 runs on spark1 and rank 1 on spark2. They are joined by NCCL over ConnectX-7 port f1, both PCIe halves
(`NET/IB : Using [0]rocep1s0f1 [1]roceP2p1s0f1`, RoCE). vLLM was up during these runs; accuracy does not depend on it.

Binaries: the xdev build (`240580e`); S1 comes from the base build. Raw logs: `raw/x-gates2`, `raw/x-gates1`, `raw/x-smoke3`.

**Cross-host runs are deterministic.** The `self-short` stats in x-smoke3 and x-gates2 agree to every digit.

**Cross-host gives the same bits as the in-process group.** The protocol hands the remote rank exactly the in-process
rank's work.
- Mac: `tp_hybrid::hybrid_moe_tp2_remote_rank_is_bitwise_the_in_process_group`.
- GPU: 256 greedy ids at 1.5k and 16k tokens, cross-host vs one GB10 with two ranks: **identical**.
  - On one GB10 the ranks are joined by the host comm, and a two-operand sum commutes.
  - The long self-golden stats also agree to every digit.

**One-box tp=2 is racy, so it is not used for numbers.** Two ranks on one GPU share that device's cuBLAS handle and
workspace (`kernels/cuda/matmul.cu`, `g_dev[dev]`).
- The prefill GEMMs of the two ranks then race on two streams.
- One-box tp=2 self-short read 5.1e-3, 1.0e-2 and 4.7e-3 in three runs (`raw/gates2`).
- The CLI refuses a repeated `--devices` again; `INTARSIA_TP_SAME_DEVICE=1` overrides it for debugging.
- tp=2 on two GPUs in one process (HIP) does not share it: the state is per device.
- The tp=1 rows below are single-rank runs, so they are unaffected.

| configuration | 35b-short | 35b-long |
|---|---|---|
| base against its own dump | 2.7e-13 / 3.7e-11, 0 / 0 | 2.8e-13 / 1.1e-11, 0 / 0 |
| tp=1 SIMT attention (split-KV and flash disabled) | 4.0e-3 / 9.0e-3, 1.18 / 0.63 | 2.83e-2 / 1.00e-2, 4.36 / 2.5 |
| tp=1 fp8 GEMV disabled (decode only) | 0 / 3.8e-3, 0 / 1.88 | 0 / 2.6e-3, 0 / 3.75 |
| tp=1 nvfp4 GEMV disabled (decode only) | 0 / 4.9e-3, 0 / 0 | 0 / 2.9e-3, 0 / 2.5 |
| **tp=2 cross-host** | **3.7e-3 / 1.16e-2, 1.11 / 1.25** | **3.22e-2 / 8.4e-3, 4.64 / 3.75** |
| tp=2 cross-host, 1 % bug on rank 1 (`INTARSIA_TP_TEST_BUG=scale:1.01`) | 3.7e-3 / 7.3e-3, 0.97 / 1.25 | 2.97e-2 / 8.1e-3, 4.32 / 7.5 |

**Findings**

1. **tp=2 sits inside the 35B's own tp=1 reordering spread.** Swapping only the tp=1 attention kernels moves the 35B as
   far as tp=2 does:
   - short prefill: 4.0e-3 vs 3.7e-3;
   - long prefill: 2.83e-2 vs 3.22e-2, flips 4.36 % vs 4.64 %.
   - The greedy ids diverge in the same range (next table).
2. **The 8B-derived TP budget in docs/accuracy.md does not transfer to the 35B.** That budget (mean 1.2e-3, max position
   9.8e-2, flips 0.84 %) fails every tp=1 variant here as well.
   - The 35B is 4-bit with top-8 routing, so one routing flip moves a position far: max position KL is 27 for the SIMT
     variant.
   - On the long set, chat_reuse_4k dominates: mean KL 1.7e-1 over its 4631 prefill rows, against 3.0e-3 over its 16
     decode rows.
3. **The same derivation, done on the 35B, passes tp=2.** budget = max over the tp=1 variants × k = 2:

   | set | mean KL | max position KL | flips | tail | worst prompt |
   |---|---|---|---|---|---|
   | short | 1.8e-2 | 2.3 | 3.76 % | 2.8e-3 | 6.5 × |
   | long | 5.7e-2 | 54.6 | 8.7 % | 7.1e-3 | 5.9 × |

   tp=2 cross-host **passes** both (`raw/x-gates2`, `self-short` / `self-long` rc=0).
4. **That budget is too loose to catch a 1 % partial-scale bug, and so is any budget on these sets.** The bug passes the
   35B budget, and reads the same as clean tp=2. The 8B result was the same (docs/accuracy.md).
5. **The guard that catches the bug is the Mac f32 test** `tp_hybrid::hybrid_moe_tp2_catches_a_one_percent_partial_scale_bug`.
   - It runs the same core sharding code: GDN by k-head group, MoE inside each expert, the FP8 and NVFP4 slices.
   - Clean tp=2 against tp=1 gives a rel L2 of 3.4e-6; with the bug it gives 5.3e-1.
   - The mutants show each all-reduce and the q|k|v row-group split are load-bearing (section 5).
6. **Nothing is shipped from this.** The 35B TP budget is measured, not shipped, the same policy as for the 8B. Default
   budgets and the gate code are unchanged.

## 3. Cross-host plumbing

- **Two processes.**
  - spark1 runs any command with `--tp 2 --tp-remote 10.100.152.3:29555`.
  - spark2 runs `intarsia tp-worker --listen 10.100.152.3:29555` with the same model flags; `--serving` when rank 0
    is `serve`.
  - A handshake checks a fingerprint of the model, the recipe, the load options and the plan options, then agrees on
    the KV capacity (the smaller rank's).
- **NCCL env:** `NCCL_SOCKET_IFNAME=enp1s0f1np1 NCCL_IB_HCA=rocep1s0f1,roceP2p1s0f1 NCCL_IB_GID_INDEX=3`. NCCL used
  NET/IB (RoCE) on both HCAs, channels alternating between them.
- **Load:** cross-host `serve` loads in 8.2 s. Rank 0 holds 11.09 GB of weights, rank 1 10.80 GB.
- **Admission on plan shapes:** at serve, nothing was rejected on either rank.
  - Rank 0 checked 30 kernels with 508 cases.
  - Rank 1 checked 29 kernels with 491 cases. These are the per-rank shapes: experts at I = 256, 8 q heads and 1 KV
    head, 16 GDN v heads.
  - The rank-1 log line is new in `240580e`. The first xdev build was stale for that file, an rsync mtime issue; it was
    fixed by touching the file and rebuilding.

## 4. Speed, tp=2 vs tp=1, spark1

Window `raw/x-window1` (fleetq #2991, 11:34-11:42, both vLLMs down 509 s, `raw/downtime.log`). Binary xdev, rank 0
on spark1, rank 1 on spark2. `intarsia bench speed`, 2 reps + 1 warmup, gen 128, thinking off, `--prefill-chunk`
default (2048).

| arm | prefill 1k\* | 4k | 16k | decode 1k | 4k | 16k |
|---|---|---|---|---|---|---|
| tp=1, CUDA graphs (the shipped config) | 4566 | 5840 | 5392 | 82.3 | 80.0 | 72.2 |
| tp=1, eager (`--no-graphs`) | 4514 | 5862 | 5417 | 73.7 | 71.8 | 65.3 |
| **tp=2 cross-host** (eager: graphs are off at world > 1) | **5067** | **7107** | **6747** | **77.4** | **75.6** | **70.3** |
| tp=2 vs tp=1 graphs | +11 % | **+22 %** | **+25 %** | **−5.9 %** | **−5.5 %** | **−2.6 %** |
| tp=2 vs tp=1 eager | +12 % | +21 % | +25 % | +5.1 % | +5.3 % | +7.6 % |

\* The 1k prompts are under 1024 tokens, so that column is mostly TTFT overhead, not prefill throughput.
Decode spread within an arm is ≤ 0.8 tok/s. The eager arms include 16 profiled steps (per-op synchronised) out of
256, the graphs arm 2; the tp=2 vs graphs row therefore carries a small penalty for tp=2.

**Findings**

1. **Prefill gains 22-25 % at 4k/16k.** The design estimated ~240 ms per 2048-token chunk against ~385 ms (+60 %).
   Measured: 16k tp=2 is 2.47 s TTFT against 3.07 s. Comm (960 MiB per chunk, ~45 ms at 22 GB/s) and the replicated
   parts (lm_head, router, embedding, norms) take the rest.
2. **Decode is 3-6 % slower than tp=1 with graphs, and 5-8 % faster than tp=1 eager.** tp=2 runs eager because CUDA
   graphs are off at world > 1 (ADR-0006). The tp=1 graphs-vs-eager gap is 8.6-10.4 tok/s, larger than anything tp=2
   gains. A tp=2 step is 12.9 ms at 1k against the design's ~6.5 ms floor; the per-op split is in section 4a.
3. **So decode at tp=2 needs graphs under TP to pay off.** NCCL all-reduce is graph-capturable; the remote rank would
   need its forward to be a replay too. That is the first follow-up, ahead of the vocab-parallel lm_head.
