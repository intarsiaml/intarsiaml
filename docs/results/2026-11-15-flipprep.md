## 2. What the recipe change reaches (code reading, then measured)

- `batched_mtp_for` returns 0 for `world != 1` or a rank in another process (`load.rs`), and the MoE MTP head is not a recipe default at `world > 1` (`mtp_head_usable`). So `batched_mtp`, `batched_verify` and `verify_topk` never act at tp2: **at tp2 the only effect of the flip is `mtp_draft_vocab = 131072` for an explicit `--spec mtp`** (opt-in, lane mt2).
- The draft head is the first N rows of the lm_head (`Model::load`, `reduced`). With a vocab-parallel head, rank 0 holds rows `[0, V / world)` = 124160 rows; when N is not inside that share the loader loads a whole copy of the head on rank 0 for drafting and takes the prefix (the DFlash drafter's rule), so a 131072-row head needs no clamp and no fallback.

## 5b. Batched-verify row counts 2..=6 under admitted kernels only (coordinator gate, lane dv27's 27B finding)

Lane dv27: on the 27B the plan probes verify passes of `2..=verify_rows()` (3) and batched steps of `2..=batch_rows()` (2) rows, never the `sequences x (k + 1)` rows of a batched verify pass, so `matmul_mxfp4` at M = 5, 6 had no ADMITTED kernel under `serve`'s admitted-only rule (`no kernel for matmul_mxfp4 ... m=6 [admitted kernels only]`, an engine failure).
Does the 35B have the same hole? Two explicit checks:

1. **Static pin (new test, in this PR)** `crates/intarsia-backend-cuda/tests/rows_registry.rs::batched_verify_rows_2_to_6_select_an_admitted_kernel_for_every_35b_op`: builds the CUDA registry, marks admitted exactly what the plan's probes select (ordinary calls at every probed size, row-exact calls at 2..=3 rows), turns on `require_admitted`, and checks that every row count 2..=6 of every op the 35B runs
   (NVFP4 / fp8 / bf16 projections, the bf16 lm_head, MoE experts, the fp8 pair, the ops without a row-exact kernel) selects an admitted kernel. It passes. Why: the 35B's row-exact kernels are one kernel per op for M = 1..=16 (`ROWS_PINS`: `matmul_nvfp4_gemv_rows`, `matmul_bf16_gemv_rows`, `logits_bf16_gemv_rows`, `matmul_fp8_gemv_rows`, `moe_experts_decode_v2_rows_bf16`, `matmul_fp8_pair_gemv_rows`),
   so the kernel admitted at 2..=3 rows is the one selected at 4..=6. **Negative control:** with the 27B's `matmul_mxfp4` left in, the same test fails with dv27's message (`M = 5 would select matmul_mxfp4_gemv_rows, but under admitted kernels only: no kernel for matmul_mxfp4 on cuda/sm_121 ... [admitted kernels only] [row-exact verify kernels only]`): the test would have caught the 27B bug.
2. **Runtime histogram on the real 35B** (`rows.sh`, fleetq #9491, `raw/rows/`): flip-default servers (admission on, admitted kernels only) with `INTARSIA_CB_TRACE=1 INTARSIA_SPEC_TRACE=1`; the rows of a verify pass = sum of (drafted + 1) over the sequences verified between two decode phases (`rows_hist.py`); load ids.py (B = 1, 2, greedy + T = 1.0) and a 2-stream greedy code set.
