# mtp-store: MTP drafting on prefix-store requests

Lane `mtp-store`, branch `mtp-store` from origin/main `48c7e9f39`. Candidate 1 of
`docs/research/2026-11-13-tensorfold-1.2.8-review.md`. Before this lane the prefix store and `--spec mtp` excluded each
other three ways: on the single-sequence engine a drafting request bypassed the store (`engine.rs`, LOG 2026-10-23 12:10),
the batching engine refused the pair (`engine/batch.rs`), and a configured store skipped the recipe's MTP default
(LOG 2026-10-26 17:33, rule 2). So the production shape, `serve --max-batch 2 --prefix-store on` for the
Qwen3.6-35B-A3B NVFP4 on a DGX Spark, ran with no MTP at all.

## Design

The store restores the main model's state only (attention KV and GatedDeltaNet state). The MTP head keeps its own
attention cache (`MtpState::kv`, one row per position: the head's row for position `p` is computed from the main model's
final hidden state of `p` and the token of `p + 1`), and the engine required that cache to cover the whole sequence
(`kv.len + pending_rows == st.len`). After a restore to length `L` the hidden states of positions `0..L` do not exist, so
the head could not follow.

TensorFold's head context is a range `[begin, end)` over a ring (`zig/src/families/qwen3_5/cuda_mtp_absorb.zig`,
`absorbRole`): when the rows to absorb start past `end` ("a gap (a prompt restored from a cache): the context starts
here") it sets `begin` to the gap's end and goes on; the head then attends to what it has seen since. We do the same
without a ring and without a kernel change:

- `MtpState` gets `base`, the position of the head's cache row 0. The invariant becomes
  `base + kv.len + pending_rows == st.len`; the tokens paired with queued rows are read at `base + kv.len + 1 ..`.
- `SequenceState::mtp_restart` starts the head's context over at the current length: empty cache, empty queue,
  `base = st.len`, synced. The head's cache row `i` then holds position `base + i` at rope position `i`. RoPE scores
  depend on position differences only, so the attention over the rows the head holds is the one absolute positions give
  (up to rounding); no attention kernel learns about `base`. The captured step's device position table
  (`spec_graph.rs`, `POS_CATCH_UP` / `POS_CHAIN`) gets head-relative positions for the head's rows; the verify rows keep
  absolute positions.
- Single-sequence engine (`Seq::new`): a drafting request on a model with an MTP head now takes the store path like any
  request. After the restore (or the local reuse) the head is restarted at the resume point when it is not synced: the
  store wrote the state (`load_prefix` marks the head unsynced), or the previous request did not draft. A drafting store
  request therefore also keeps its reuse after a request that did not draft, where the store-off path starts from an
  empty sequence (unchanged).
- Batching engine: `BatchedEngine::new` accepts the store with `--spec mtp`. Batched MTP keeps slot reuse off
  (`cfg.prefix_reuse = false`, unchanged), so a request resumes from the store alone; `SeqAdapter::restore` restarts the
  slot's head context after a restore. Every request runs the store's chunk schedule, drafting or not. Other speculation
  modes stay refused with the store.
- `SequenceState::truncate` with a `base`: a cut inside the head's span behaves as before (snapshot of the same context,
  else the one zero row); a cut at or before `base` restarts the context at the cut; `truncate(0)` resets `base` to 0.
  Recurrent snapshots record the `base` they were taken under and are not used across a restart.
- Loader: where the switch is on, a configured store no longer skips the recipe's MTP default (`mtp_default_k`), and with
  `--max-batch` > 1 the recipe's `batched_mtp` applies as without a store.
- A DFlash draft (`--spec dflash`, `--spec auto`) bypasses the store as before.

What a restart costs: the head sees only the positions computed since the restore, so the first passes after a restore
draft from a short context. Drafts are verified (every emitted token is a verify row's argmax), so this can only move the
acceptance rate. Measured below.

Switch: `INTARSIA_MTP_STORE` (`docs/tuning.md`), `1` / `on` or `0` / `off`; unset is on for the CUDA backend and off
elsewhere. Off is the behaviour before the lane in all three places. `prefix_store.rs` is not touched.

Not done: giving the head more context after a restore (store the last hidden rows with an entry, or re-prefill a tail);
it would need a change to the store's entry layout. Sampled requests do not draft in the batching engine (lane
`mtp-sampled`).

### CUDA (spark1, Qwen3.6-35B-A3B NVFP4, vLLM up beside it)

New `crates/intarsia-models/tests/mtp_store_cuda.rs` (`mtp_on_store_requests_equals_mtp_off_cuda`): two chats through
the model's chat template (thinking on), three turns each, greedy, 160 tokens per reply, the chats alternating so every
later turn restores its history from the store. Build `590d9b97a` (`cargo test --release --locked -p intarsia-models
--test mtp_store_cuda`), `max_seq` 8192, bf16 KV, fleetq #9282 (`--quiet gpu --mem 45`, vLLM up): **1 passed, 0 failed**
(195 s). Raw: `2026-11-13-mtp-store/raw/gate.log`.

| arm | requests | ids = store-on MTP-off | cached tokens equal | decode tok/s median (min-max) | acceptance |
|---|---|---|---|---|---|
| single engine, store on, MTP off (reference) | 6 | - | - | 86.5 (85.7-87.7) | no drafts |
| single engine, store on, MTP default (k 2) | 6 | **6 of 6** | **6 of 6** | 128.5 (127.1-134.5) | first turns 79.9 % (195 / 244), restored turns **80.5 %** (391 / 486) |

| `--max-batch 2`, store on, MTP default (N 1), each round's 2 requests together | 6 | **6 of 6** | - | 65.3 per stream (62.7-69.9) | 9 passes, 18 / 18 (drafts only while one sequence decodes) |
| the same engine, every request once more alone (each restores all but 2 tokens, then drafts) | 6 | **6 of 6** | - | 111.0 (106.5-125.0) | **64.2 %** (534 / 832); per request 67.4, 62.9, 59.3, 59.3, 60.8, 77.4 % |

- Greedy ids with the store on are the same with MTP on and off on both engines (18 of 18 replies, 2880 tokens). The
  single-sequence engine also reports the same cached tokens (0, 19, 1871, 1168, 2641, 2175): a drafting request uses the
  store exactly as a request that does not draft. Store hits 4 of 6 lookups (single), 10 of 12 (batched).
- Acceptance after a restore depends on how many prompt tokens follow the restore point, because that is the head's
  whole prompt context after the restart. With a new user turn after it (182 to 1009 tokens prefilled after the restore)
  it is 80.5 %, the same as cold turns on the same engine (79.9 %) and as the head with its whole context (78.7 %, store
  off; not the same tokens, the store-off schedule gives other ids on CUDA). When everything but the last 2 tokens is
  restored (a repeated prompt, here the second pass on the batching engine) it is 64.2 %: the head then starts from two
  rows and only learns the reply as it is written. Still a net gain in that pass (111.0 tok/s against 86.5 tok/s plain on the
  single-sequence engine, not a paired number).
- TTFT of the restored turns is unchanged by drafting (single engine: 262 / 265 / 235 / 155 ms with MTP against
  275 / 263 / 232 / 155 ms without).
