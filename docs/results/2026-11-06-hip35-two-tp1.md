# hip35-two-tp1: Qwen3.6-35B as two tp1 servers (one per R9700) against one tp2 server

Lane `lane-dp/hip35-two-tp1` (branch off main `2abdc2475`), 2026-11-06. Qwen3.6-35B-A3B NVFP4, `serve --backend hip`, tatooine (2x AMD R9700, 32 GB each).
**Status: done.** Sections 1 to 5 (protocol, decision rule, caveats) were committed and pushed (commit `a62a98b6d`, pushed before any measurement) and are unchanged except this line; results are under "Results" and deviations from the protocol are listed there.

## 1. Request

User, 2026-11-06 (relayed in the lane brief): "test 35B as two tp1 servers".

Question: does the 35B serve more aggregate throughput as two tp1 servers (data-parallel, one per card) than as one tp2 server? Nothing in this lane changes a default or a serving config; the user decides.

## 2. Protocol (fixed before any data)

- **Arm T (tp2):** one server on both cards: `--tp 2 --devices 0,1`, `HIP_VISIBLE_DEVICES=0,1`, port 8300.
- **Arm D (2x tp1):** two servers, `HIP_VISIBLE_DEVICES=0` (port 8301) and `=1` (port 8302), started together. For N total streams, N/2 go to each server concurrently with distinct prompts. At 1 stream D uses one server (server 0; the other is up and idle).
- **Common serve flags (all arms and servers):** `serve --backend hip --model Qwen3.6-35B-A3B-NVFP4 --profile-every 0 --mem-budget 29 --max-seq 8192 --max-batch 16` (the 11-05 setup, `2026-11-05-hip-pack-default.md`), `GPU_MAX_HW_QUEUES=1`. Defaults are untouched: packed prefill on at tp1 (HIP default since 11-05; tp2 never packs), and the speculative setting is the build's default for this model on HIP, which is **off** at both tp1 and tp2 (the recipe's `mtp_default_k` is set for Metal and CUDA only, `mtp_default_tp_k` for the 27B only, and `--max-batch` above 1 keeps plain decode); the server's startup line is quoted in the results.
- **Load:** `scripts/dp/load.py`, one driver for both arms. Total streams **1, 8, 16, 32**. Each stream has its own ~1k-token prompt (`[N-burst-i]` nonce + the `scripts/hg/stall.py` filler, 45 sentences, seeded by (N, i): the same prompt set in every arm), 128 generated tokens, greedy (`temperature 0`, `ignore_eos`, `min_tokens` 128, thinking off). All streams of a burst start behind one barrier. Per stream count: one discarded warm-up burst, then 3 measured bursts.
- **Metrics:**
  - aggregate tok/s per server = completion tokens / that server's wall (barrier release to its last stream's end, prefill included: the definition of localeval's `aggregate_decode_tok_s`, so the 11-05 numbers are comparable); the arm's aggregate = the **sum** over servers; the combined figure (all tokens / longest wall) is recorded beside it;
  - per-stream decode tok/s = (tokens - 1) / (end - first token), median over streams and bursts;
  - TTFT p50 / p95 pooled over a visit's bursts;
  - the visit's value is the median of its 3 bursts.
- **Order:** ABAB = T1, D1, T2, D2, a fresh server or servers per visit.
- **Calibration:** T1's 1-stream and 16-stream aggregates are compared with 11-05 (tp2: 163.0 and 476.05 tok/s, localeval). A deviation above 8 % is flagged in the log and the doc; ratios are then read with that in mind.
- **CPU check (before trusting D):** the host has 24 hardware threads (Ryzen 9 9900X, 12 cores x 2, one NUMA node). During D1, before the sweep, 16 streams on server 0 alone give the per-server reference; the 32-stream dual run's per-server rates are compared with it (starvation if clearly below, say under 95 %), and `docker stats`, `ps` thread counts and `top` are sampled during a longer dual burst. `serve --help` is checked for a thread or affinity option; `docker --cpuset-cpus` pinning is used only if starvation shows, and then as a separate, labelled run.
- **Memory:** peak VRAM per card from `/sys/class/drm/card{0,1}/device/mem_info_vram_used` (the host has no `rocm-smi` / `amd-smi`), sampled once a second through every visit; card to HIP-device mapping from the PCI slots and confirmed by which card grows under which server. `--mem-budget 29` probably dominates the peak (the engine takes its pool up front), so the server log's KV capacity is quoted as well.
- **Context on one card:** one D-style server (card 0, the other card idle, `--max-batch 16`, `--mem-budget 29`) at `--max-seq 32768`, then 65536 once if that works; if 32768 fails, 24576, 20480, 18432. A max-seq counts only if the server loads and serves a ~16k-token prompt (usage `prompt_tokens` >= 15500, 32 tokens generated). Reported: the largest that did.
- **Identity:** 4 fixed prompts, greedy, run solo on each server and then all at once on every server of the visit. D servers are tp1 from main (build stamp recorded), so the claim checked is: same text sha256 on card 0, card 1, under dual load, and in D1 vs D2. tp1 text is **not** compared with tp2 (single-card output is expected to differ).
- **Fleet:** all of it in fleetq jobs on tatooine (a `--load cpu` build and dry run, one exclusive window that takes radiance down, `--mem 30`), queued behind #8712 and #8743. The window script restores radiance from an EXIT / HUP / INT / TERM trap on every path and confirms `:8080/v1/models` answers before the job is released. No deadman timers.

## 3. Decision rule (fixed before any data)

- **D is "better for throughput"** if D_k / T_k >= 1.3 at **16 total streams and at 32 total streams, for both visit pairs k = 1, 2** (T1 vs D1 and T2 vs D2): four ratios, all four required.
- The 1-stream latency cost of D against T (tok/s, TTFT p50 / p95) is reported separately and is not part of the rule.
- No default or serving config is changed by this lane.

## 4. Caveats stated up front

- **`--max-batch 16` at 32 streams.** The specified config has 16 slots per server: T at 32 total streams runs two waves (16 decode, 16 queued), D has 16 + 16 = 32 slots and no queue. The rule is applied to this specified config. The slot count is a real property of "two servers", but it also means a D win at 32 is partly a slot-count win. A single extra T visit at `--max-batch 32` (16 and 32 streams), if the window has time, is reported separately as a sensitivity check and is **outside the rule**.
- n = 2 visits per arm (medians of 3 bursts each): treat differences under about 3 % as noise. The 11-05 doc found 1-stream tatooine figures bimodal inside one server start.
- The tp2 server also has a host-side cost of two ranks in one process; D has two processes sharing 24 threads: the CPU check above is the only evidence on that.
- The binary is main `2abdc2475` built on tatooine (`scripts/dp/build.sh`); the 11-05 numbers came from the `a39404a79` branch build, so a small drift from them is possible.

## Results

Setup actually run: main `2abdc2475` code, built on tatooine from the tree at `f99ea4703` (main plus this lane's scripts and doc only; stamp `head=f99ea4703 branch=lane-dp/hip35-two-tp1`), `~/intarsiaml-dp/dp-intarsia`. Jobs: #8757 (cpu: build + `DRY=1` window check, radiance up), #8774 (cpu: DRY re-check after the timer guard), **#8775 (the window: radiance down 11:23 to 11:31, answered on :8080 after 15 s)**, #8780 (window 2, context ladder, radiance down 11:35 to 11:37), #8782 (window 3, context at max-batch 16, radiance down 11:41 to 11:43). Each window restored radiance and confirmed `/v1/models` before releasing. Raw data: `2026-11-06-hip35-two-tp1/raw/` (window 1), `raw-w2/`, `raw-w3/`; per run `*-load.json` (every stream: TTFT, decode rate, text hash), `*-ident.json`, `*-vram.tsv`, server logs, `steps.log`. Tables below are `python3 scripts/dp/table.py raw`.

**Speculative setting:** off, as predicted. Neither the tp2 server nor the tp1 servers log any MTP/spec line (`serve-*.log`: only the `continuous batching: up to 16 sequences (--max-batch), busy prefill chunk 4096` line), `--max-batch` above 1 keeps plain decode. Packed prefill: on at tp1 (HIP default since 11-05; the D servers ran 8 / 16 / 40 packed passes at 8 / 16 / 32 total streams), never at tp2 (0 passes). That is part of "D as served by default", not a separate variable.

**Calibration against 11-05 (localeval, tp2):** T1 1 stream 165.1 vs 163.0 tok/s (+1.3 %), 16 streams 484.5 vs 476.05 (+1.8 %). The driver agrees with localeval within 2 %. D1's one-server 1 stream (139.6) is +3.8 % over 11-05's tp1 134.5; one server at 16 streams (393.5) is -1.0 % against 397.5.

### Verdict

**By the pre-registered rule, D (two tp1 servers) is better for throughput: D/T = 1.40x and 1.40x at 16 total streams, 1.61x and 1.62x at 32, in both visit pairs; all four are above 1.3.** Also 1.24x at 8 streams. Visit-to-visit spread is under 1 %, so the ratios are not near the threshold at 16 and 32. The 1-stream cost of D is real: **-15.4 % / -14.2 % tok/s (139.6 vs 165.1; 140.2 vs 163.4), TTFT p50 +0.03 s (0.146 vs 0.114; 0.143 vs 0.116)**. Per-stream decode at low load is lower with D (1 stream 164.9 vs 192.0 tok/s); at 16 streams it is higher (52 vs 40 tok/s per stream), at 32 streams it is a little lower (31.0 vs 33.0) because T's second wave of 16 streams waits in the queue (T TTFT p50 3.0 s, p95 5.9 s, against D 1.04 / 1.71 s).

**Caveat on 32 streams (stated before the data, confirmed):** T's 32-stream figure is two waves of 16. The extra T visit at `--max-batch 32` could not be run: the engine refuses it (`unsupported: --max-batch 32 is not implemented yet (the engine decodes 16 sequence(s) at a time) ... use --max-batch 16`, `raw/serve-X1-dp-t.log`), so 16 is the ceiling per server and two servers are the only way to 32 slots today. The 16-stream cell has no such confound (both arms have a free slot per stream) and still shows 1.40x. Part of the D gain at 16 and 32 streams is the packed prefill that only runs at tp1 (TTFT p50 at 16 streams 0.55 s vs 0.96 s).

### Deviations from the protocol, and limits

- The max-seq probe as written (32768, then 65536; step down) answered "no" for every rung in window 1 because the limit is the server's clamped context, not max-seq; windows 2 and 3 (two extra radiance-down windows of 2 and 1.5 minutes, same standing approval) varied `--max-batch`, `--mem-budget` and `--kv-fraction` to find what does fit. No data was dropped.
- The extra `--max-batch 32` T visit could not run (above); the visit is logged as failed in `steps.log`.
- n = 2 visits per arm, 3 bursts each, one 1k-token prompt shape, 128 generated tokens, greedy; short prompts and short generations flatter prefill-heavy settings. Not tested: longer prompts, MTP, mixed lengths, a real request mix, the cost of running two processes in production (a router in front of the two ports, health handling), and radiance's own use of both cards (D would replace radiance's tp2 service on tatooine).
- The aggregate counts prefill time inside the wall (localeval's definition), so TTFT differences feed into it.
- No default or serving config was changed. The decision whether to serve the 35B as two tp1 servers is the user's.
