# kvq: speed verdict for `INTARSIA_METAL_ATTN_KV_ONCE` and default flip (2026-11-16)

Lane `kvq`, branch `kvq`, base `origin/main` 10cb85061. Follow-up of `docs/results/2026-11-15-mka-metal-kv-once.md` (PR #387), whose
end-to-end ABBA was run on a shared, hot box and could not separate the knob from noise.

## Verdict

**The knob is a speed win on both models at 32k and a tie everywhere else; the Metal default is flipped to on**
(`INTARSIA_METAL_ATTN_KV_ONCE=0` is the off switch). The null test is clean (35B `--spec off`, where the knob changes no launch:
0.999 and 0.995). No clean cell loses.

## Method

endor, one `fleetq run --quiet gpu,cpu` slot per cell group, one binary (`target/kvq-intarsia`, built `--features metal`),
arms A = knob unset, B = `INTARSIA_METAL_ATTN_KV_ONCE=1`. Order ABBA BAAB (4 visits per arm), a FRESH server per visit, 90 s idle
cooldown between visits, each visit covers 4k and 32k with `localeval speed --gen 256` (3 reps + warmup on the 35B, 2 on the 27B; so
8 to 12 measured reps per arm per cell). The server's own decode time (`intarsia_itl_seconds` sum / count, `intarsia_spec_steps_total`)
is scraped around each call: ms per token and ms per verify pass. A visit whose server step time is more than 10 % above its arm
median is rerun once (`scripts/kvq/ab.py`, `analyze.py`). Raw: `docs/results/2026-11-16-kvq/raw/ab-*`.

Notes on how reliable each row is:

* Null test: both 35B `--spec off` rows differ by <= 0.5 % (limit 3 %): the batch was quiet, so the other rows can be read.
* MTP rows are noisy by themselves (draft acceptance varies 0.62 to 0.85 per visit, spread 10 to 17 % inside one arm). The
  per-pass server time is not affected by acceptance and moves the same way as tok/s: 35B 32k -16 %, 27B 32k -7 %.
  Knob-on stays ahead of knob-off on both models at 32k, but the 35B 32k tok/s ratio (1.18) is wider than the null spread only
  because of the pass-time cut; read it as "about +10 to +18 %".
* 27B MTP 32k and 4k, the first job (#9685): visits 1 to 3 were disturbed (weights loading cold, 80 to 100 s server start,
  step time up to 40 % high) and were rerun once as the method says; the table uses the reruns (original means: 38.7 / 38.6 tok/s,
  on / off, inside noise). One rerun of an on-arm 4k visit stayed slow (52 ms per pass against 43), which made 4k look 4 % worse
  in that job (0.96); the 4k-only confirmation (#9699, 8 clean visits, step times 46 to 49 ms) gives 1.000, so 4k is a tie.
* Rules from the brief: the knob wins clearly (>= 3 %, beyond the null spread) at MTP 32k on both models (1.18 and 1.07), ties
  within noise in every other cell, and no clean cell loses by more than 2 %.

## Why the 27B's 9 to 10 % GPU-time cut did not show as tok/s in mka's run

It does show. With a quiet box and fresh, cooled servers the 27B verify pass takes 59.3 ms instead of 64.0 ms at 32k (-7 %), which is
+7 % tok/s (MTP) and +7 % (plain). mka's 27B rows (38.9 vs 39.0) were taken on a box shared with other lanes' CPU jobs and, as its
own null rows showed, were not readable. The per-dispatch gain in mka's trace (-9 to -10 % GPU busy per pass) is slightly larger than
the -7 % wall time per pass seen here; the difference (about 2 %) is host time per pass that the kernel change does not touch.
I did not capture a new per-dispatch trace pair: the old traces were deleted with the mka worktree, and the server-side step times
already reconcile with the GPU-busy figures, so no hidden CPU gap or sync point is needed to explain the numbers.

(`tests/kv_once.rs` forces the knob through `set_kv_once_for_test`).
