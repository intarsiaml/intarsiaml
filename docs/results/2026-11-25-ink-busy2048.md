# Inkling-2-Mini on Metal: busy prefill chunk 2048 (was 256)

User decision 2026-11-25: the Metal busy prefill chunk of Inkling-2-Mini (the chunk a prompt prefills in while other sequences decode,
`serve --max-batch` > 1) defaults to 2048. Lane ink-batch, branch `ink/busy2048` (tree `8f4c64105`), main `0b8fab600`.
Raw: `docs/results/2026-11-25-ink-busy2048/raw/` (scripts `gA.sh` `gB.sh` `gC.sh`, logs, per-arm `/metrics` snapshots, RSS samples, localeval logs).

## 1. The change

`recipes/inkling2.toml`, `[tuning.metal]`: `busy_chunk = 2048` (next to `prefill_chunk = 2048`). The loader already takes a recipe's
`busy_chunk` for any model (`crates/intarsia-models/src/load.rs`, after `--busy-chunk`, before the builtin 256 / recurrent-batch rule), so no
loader or engine code changes. Only Inkling-2 on Metal moves: cpu, cuda and hip keep 256, and every other recipe resolves as before (test
`crates/intarsia-models/tests/recipe_ink_busy_chunk.rs` pins the busy chunk of every shipped recipe on all four backends).
`--busy-chunk N` still wins. Revert: `--busy-chunk 256`, or delete the recipe line. No env var.
A lone prompt (nothing decoding) never runs a busy chunk: it takes the solo chunk, 2048 already.

Reading:
- **16 streams: 256 mean 133.6 tok/s (arms 1, 4), 2048 mean 172.1 (arms 2, 3): +28.8 %.** Arm 1 is not fully warm (its 1-stream cell, which a busy
  chunk cannot touch, ran 55.0 against 59.2 in the three warm arms), so it biases toward 2048. Against the one fully warm 256 arm (arm 4, 145.0) the
  two 2048 arms are +16.0 % (168.2) and +21.4 % (176.0). Both readings clear the +15 % bar; the honest warm-only figure is +16 to +21 %, one 256 sample.
  Section 48 measured +28 % (169.9 against 132.2).
- 4 streams: 256 84.6 / 101.6, 2048 101.6 / 118.4. Arm 3's 4-stream cell was flagged `spread` by localeval; the warm arms agree at 101.6 (2048 against 256).
- **1 stream: 59.2 tok/s in all warm arms (2048: arms 2, 3; 256: arm 4): no regression** (bar: 2 %). As expected, a lone prompt never runs a busy chunk.
- 16-stream TTFT p99: 256 11.3 / 9.6 s, 2048 5.6 / 5.4 s (a queued 1015-token prompt prefills in one chunk instead of four).
- Cost: server ITL p99 (whole arm, all stream counts) 440 / 242 ms at 256, 714 / 474 ms at 2048 (arm 0: 844); max bucket <= 250-500 ms at 256 against <= 1000 ms at
  2048. A 2048-row prefill pass is about 0.9 s on the decoding rows (P1 measurement in section 48 of `2026-11-21-inkling2-batch.md` on `ink/batch`: 893 ms). This is the accepted trade-off.
- Memory: peak RSS 24.11-24.12 GiB and box-wide device memory in use 40.0 GiB in every arm, so 2048 adds no memory (`ps rss` may leave out
  Metal allocations; the device figure is the stronger evidence).

**Status of the bar.** The brief asked for all arms warm; arm 1 (256) was not (its 1-stream cell is the tell), so the +28.8 % headline
leans on it. The gain against the only fully warm 256 arm is +16.0 % (arm 2) and +21.4 % (arm 3), mean +18.7 %: the bar is cleared on **one** warm 256
sample, the low end one point above +15 %. A confirmation A/B (two discarded warm-up arms, then 256 / 2048 / 2048 / 256) is queued; its result is
added to this document when it lands. Until then the gate is "passes, n = 1 warm 256".

Bar: 16-stream aggregate gain >= +15 % holds on that sample; 1-stream regression 0 % (<= 2 %). Not measured: other prompt-length mixes, the ITL effect on a chat
workload with long prompts arriving constantly (the A/B closed loop has one 1k prompt per request).
