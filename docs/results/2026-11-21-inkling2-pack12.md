## Format (`crates/intarsia-core/src/quant/p12.rs`)

A bf16 weight `[N, K]` (K % 8 == 0) becomes `codes` u8 `[N, 3K/2]` + `aux` i32 (u32 bits) `[N + 1 + E]`:

- Each row has a base exponent `b` (the 16-exponent window `[b, b+15]` that holds the most elements of the row). An element
  whose exponent is in the window is stored in place as 12 bits: sign, 4-bit offset, 7-bit mantissa. Any other element (an
  escape: zeros, subnormals, outliers) stores 0 in place and its exact bf16 bits go to the side list.
- Layout per 8-element chunk `c`: two u32 words at row bytes `[8c, 8c+8)` (plane A) and one at `[K + 4c, K + 4c + 4)`
  (plane B). Each pair word holds two 16-bit halves `s | o << 7 | m`; the fourth pair's 2 x 12 bits fill the free bits
  11-14 / 27-30 of the other three. Decode is `Q_j = W_j & 0x87FF87FF`, a few shifts for `Q3`, then `+ b * 0x00800080` per
  pair word: about 2 ALU ops per element, and the result is the uint4 a bf16 kernel would have loaded. Rows stay 8-byte
  aligned for K = 2304 / 3072 and every lane read is coalesced.
- `aux[n] = start_n << 8 | b_n`, `aux[N] = E << 8`, then the escapes `col << 16 | bf16 bits`, columns ascending per row.
- **Pack at load time, not a sidecar.** The 177 tensors pack in about 2.5 s of wall time on 20 cores. Parallel rows give the
  same bytes for any thread count (unit test). A sidecar would save those seconds but add a cache-invalidation path for no
  real gain.

### The 9..16-row calls

Ordinary decode runs P12 only where its bf16 twin GEMV runs: in_proj at 1..8 rows, wo and the unembed at 1 row. Above
that the call runs the bf16 NAX GEMM, so batched decode at 9..16 sequences is unchanged. The `_rows` (rows-exact) kernels
also run inside speculative verify passes (`Model::forward_verify`), and at 16 rows they are slower than bf16 (table above).
The bf16 weights stay resident anyway, so the model can pick per row count at no memory cost. The rows sweep picks the
crossover, and the model then routes larger calls to bf16 (bitwise the same output either way).

### Forced `=1` on a backend without P12 kernels (coordinator check, commit 6f9fcd1ae)

Before 6f9fcd1ae, `=1` packed on any backend, and only the per-call guards (`self.registry.select(&c).is_ok()`, then the bf16

reference registers `MatmulP12` and an `InkInProj` that takes u8 codes. On a backend without them (CUDA, HIP), memory would
be spent on copies that are never used, and an `InkInProj` kernel that declares no weight dtypes could take the u8 call.
This branch has no Inkling-2 kernels on CUDA or HIP at all (the load already refuses there, naming the op), but the
ink-cuda lanes are adding them. So it is fixed at load now:

Registered row ranges (7ceadd726): each plain P12 kernel takes exactly its bf16 twin's ordinary rows (Matmul / Logits:
1 row; InkInProj: 1..=8, `PROJ_GEMV_ORDINARY_MAX`), and each `_rows` kernel takes every `exact_rows` call of 1..=16 rows.
So with the flag on, a call runs a P12 kernel exactly where the flag-off call runs the twin GEMV. An ordinary 2..16-row call,
which runs the NAX GEMM in bf16, is refused for P12, and the model keeps the bf16 weight for it. The kernel choice per call
is therefore unchanged, and the output is bitwise unchanged wherever tests/p12.rs holds.

stay as zero-copy mmap views).
