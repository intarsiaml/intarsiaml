## 1. Verdict

**Ships opt-in; FIFO stays the default.** Gates (a) and (b) pass, so per the brief it ships; the numbers below are for the default decision.

* `INTARSIA_PREFILL_ORDER=shortest` (default `fifo`) gives the next prefill chunk to the prefilling sequence with the fewest prompt tokens left; `INTARSIA_PREFILL_AGE` (default 8)
  is the aging cap. Only the order between requests changes.
* A ~1K-token prompt that arrives 2 s into a ~40K-token prefill: **TTFT 6.14 -> 0.64 s (-90 %)**; the 40K prompt's own TTFT is unchanged (7.89 -> 7.93 s).
* A burst of 4 long (~16K) + 8 short (~1K) prompts at `--max-batch 4`: TTFT p50 of all 12 **8.81 -> 5.26 s (-40 %)**, the 8 short ones' p50 **9.07 -> 5.21 s**; the price is on the long
  ones (their p50 8.81 -> 10.36 s, +17 %), the p99 (the last long prompt) is unchanged (12.33 -> 12.56 s), the total time is unchanged (13.11 -> 13.16 s).
* Steady decode (4 streams, nothing prefilling) is unchanged: 204.3 -> 206.6 tok/s aggregate (+1.1 %, inside the run spread of about 3 %).
* Served greedy ids are bit for bit each request's solo ids: **180 / 180 cells identical** (fifo, shortest, shortest with `INTARSIA_PACK_PREFILL=0`), packed passes and reordering both engaged.

## 2. What changed

* `crates/intarsia-core/src/scheduler.rs`: `PrefillOrder { Fifo, Shortest }`, `SchedulerConfig::{prefill_order, prefill_age}`. One helper (`prefill_ranking` / `pick_prefill`) now names the
  prefilling sequence in all three places step 4 picks it (the per-iteration chunk loop, the overlap predicate, the overlap branch), and `prefill_packed` takes the rest of a pass in the
  same order. Admission (step 2) stays FIFO: a request still needs a free slot, in arrival order. `BatchMetrics::reordered_chunks` counts decisions that went to a sequence other than the
  oldest prefilling one (always 0 under fifo; `intarsia_batch_prefill_reordered_total`).
* `crates/intarsia-core/src/engine/batch.rs`: `INTARSIA_PREFILL_ORDER` (`fifo` | `shortest`, unknown value: warning and fifo) and `INTARSIA_PREFILL_AGE` (>= 1) into `BatchedOptions` and the
  scheduler config. No `serve` flag (an env var needs no CLI to loader plumbing; the brief allowed either). Two rows in `docs/tuning.md`.
* Shortest ranking: a sequence passed over `prefill_age` decisions in a row first (the one passed over longest, then the oldest); then the fewest tokens left (`plen - pos`), ties to the oldest.
  A "decision" is one chunk or one packed pass, counted per sequence from the decision after its last chunk (`Active::last_turn`). Chunk counts, not milliseconds, so the cpu tests are
  deterministic; at 2048-row chunks of the Spark 35B a decision is about 0.25 s, so the default 8 is about 2 s.
* **The aging bound is `prefill_age + max_batch - 1` decisions, not `prefill_age + 1`**: a long prompt that has aged queues behind other aged prompts (passed-over longest first), and there
  are at most `max_batch - 1` of them. Found by the aging test (age 1 gave a gap of 2 with 4 slots); the doc comment and the tuning row say so.

How it meets the other scheduler features (none of them changes; each request's chunk schedule is what it was):

* packed prefill (`INTARSIA_PACK_PREFILL`, CUDA default on): a pass is headed by the ranking's first sequence and filled in ranking order, so several short whole prompts that wait behind a long
  prefill now pack together (a long prompt mid-prompt never packs on CUDA, `pack_whole_prompts`, so it is skipped and ends the pass). Grouping only; gate (b) ran with packing on and off.
* macro prefill (`INTARSIA_PREFILL_MACRO`): only while one sequence prefills and nothing decodes, as before. A short prompt that arrives during a macro pass is admitted after the pass
  (documented behaviour); from then on two sequences prefill, so single chunks, and the short one goes first.
* prefill pause/park (`INTARSIA_PREFILL_PAUSE_ROWS`): a parked chunk is whichever chunk was picked; the park's decode phase is unchanged. Tested on cpu (pause 100).
* prefix store / idle-slot reuse: `pos` starts at the restored length, so "remaining" is `plen - cached`; a store request on its own chunk schedule is ranked the same way.
* busy chunk: the first chunk of a sequence still picks solo or busy size by whether anything decodes at that moment and keeps it. On the CUDA 35B busy = solo (2048), so the choice does not
  depend on timing. **Where busy != solo (Metal 35B, HIP's recipes) the order can change which size a request gets**; fifo already had that dependence on arrival timing. One more
  consequence, in any config: a long prompt that began in a quiet engine keeps its solo-size chunk, and after a short prompt overtook it and started decoding, the long one's next chunk runs
  beside that stream (fifo never does this, the long prompt always finished first). The cpu trace check allows it under shortest; on CUDA 35B with `INTARSIA_PREFILL_PAUSE_ROWS` 768 (default) such a chunk parks.

* prefix herd (lane herd, `INTARSIA_PREFIX_HERD`, PR #424): the pick is now `Scheduler::prefill_pick` and requests with `herd_held(i) == true` (followers waiting on a leader's shared
  prefix) must stay out of it. The shortest-first ranking lives inside it: `prefill_pick` walks `prefill_ranking()` (fifo: oldest first; shortest: aged, then fewest tokens left) instead of
  the active list, passes every held request over exactly as before and does the follower's store lookup (`herd_resume`) when one is released. The overlap path, which cannot
  do a lookup before planning its chunk, uses the side-effect-free `pick_prefill`, which also skips held requests; a packed pass fills from the ranking without held ones. cpu test
  `herd_followers_stay_held_under_shortest` (tests/herd.rs): a follower with 2 tokens left against a 240-token leader is still held under shortest and prefills only its own tokens
  (negative control: without the exclusion it prefills 66 rows and the test fails). The hardware gates (b) and (c) ran on a build before this merge (herd off, as it is by default);
  the pick under `INTARSIA_PREFIX_HERD=0` is the same ranking.

## 3. Gate (a): cpu scheduler tests

* `shortest_lets_a_short_prompt_overtake_a_long_prefill`: 6000-token prompt, one step, then a 100-token prompt. Fifo: long finishes prefill first (and 0 reordered decisions). Shortest: the short
  prompt takes the second chunk and finishes first, the long prompt still completes, both keep the plain chunk schedule and the same tokens as under fifo.
* `shortest_aging_bounds_the_wait_of_a_long_prefill`: a 20000-token prompt and a new 60-token prompt every iteration for 80 iterations, `max_batch 4`: for age 1, 3 and 8 the long prompt runs
  all its 10 chunks, no gap between two of its chunks reaches `age + 4`, and aging did force a chunk. Negative control: age 100000, the long prompt waits for more than 8 other chunks.
* `batched_equals_solo_randomized_with_shortest_prefill`: every request equals its solo reference under shortest for plain, 3 chunks per iteration, packed passes, paused chunks and overlap,
  `max_batch` 2 / 4 / 8, age 2 / 8, both `avoid_single_row` settings (3556 exact cells, 840 reordered decisions).
* `prefill_order_knob_parse`. `check_trace`'s "prefill start in submit order" assertion is now fifo only (admission stays FIFO and is still asserted); its per-iteration prefill budget allows a solo chunk under shortest.

`cargo test -p intarsia-core -p intarsia-server` all green (212 lib tests, 50 scheduler tests, the server tests), `docs_env_vars` green.

Reading it:

* The pair result is the clean one: the 40K prompt is done at the same time either way, and the short prompt no longer waits for it. 0.64 s is consistent with the short prompt waiting for
  the macro pass in flight (the scheduler runs one pass per iteration) and then taking the next chunk (not separately timed); the 2 s arrival is the same in every run.
* In the burst the first four slots take L S S L (fifo and shortest alike, admission is FIFO). Under fifo the shorts behind each long prompt wait for it (S1 2.9 s, S4 6.0 s, S7 9.1 s ...);
  under shortest the first shorts finish in about 1.4 s and the longs finish later (L3 6.7 s vs 5.7 s, L6 10.4 s vs 8.8 s), the p99 and the total are unchanged because the same tokens are prefilled.
  The burst is slot-limited: shorts that are still queued for a slot cannot overtake anything, which is why the gain is 40 % and not 90 %. Ordering admission too (shortest request first
  when a slot frees) was not tried: it is a different change (it would reorder the queue, not the prefill chunks) and was out of the brief.
* Decode: nothing prefills in that scenario, so the order cannot matter and does not (spread between runs of one arm is about 3 %).
* The aging cap's effect on hardware is not measured (the cpu tests carry it).
* Packed passes with shortest: 7-9 per server in both arms (the same prompts), so shorts waiting together still pack.

## 6. Not verified / limits

* Aging at a non-default `INTARSIA_PREFILL_AGE` on hardware, and a longer sustained stream of short prompts against one long one (the cpu test does it with a mock model).
* Other backends (HIP, Metal): the scheduler change is backend independent and the cpu tests cover it; no hardware run. Metal / HIP configs with busy chunk != solo chunk can give a request a
  different chunk size under shortest than under fifo (section 2); not measured.
* `--tp 2`, batched MTP with the store, DFlash: not run with shortest. Batched MTP does not enter the choice of which sequence prefills (by construction, not measured).
* Shorter-than-prefill decode stalls: a long prompt's chunk that runs beside a freshly decoding short stream (section 2) was not measured as ITL.
* Admission order (shortest request first when a slot frees) is untouched, FIFO.

## 7. Default decision and revert

Opt-in only. To try it: `INTARSIA_PREFILL_ORDER=shortest` (and `INTARSIA_PREFILL_AGE=<decisions>`, default 8) in the server's environment. To go back: unset it (the default is `fifo`, the 2026-10-15
decision). Flipping the default is the user's call: it trades the long prompts' latency (+17 % p50 in the burst, 0 % for a lone long prompt) for the short ones' (-40 to -90 %).
