# storeids: why store on and store off give different greedy ids (CUDA, 35B NVFP4)

Lane `storeids`, branch `storeids` from origin/main `d6c2d0928`. Raw output: `docs/results/2026-11-17-storeids/raw/` (`ids.jsonl` has every reply's ids, `tables.md`, the 11 serve logs and metrics, `run.log`).
Scripts: `scripts/storeids/` (`run.sh`, `ids_bench.py`, `table.py`, `memwatch.sh`). Measurement and docs only: no engine code and no default changed.

## 1. Verdict

**Expected and already decided; docs-only PR.** The difference is the prefix store's chunk schedule, not packed prefill, macro prefill, MTP or batching:

* With the store off, a recurrent (GatedDeltaNet) model prefills the prompt body in chunks and runs the **last prompt token as its own 1-row pass**; with the store on the final chunk runs **whole**
  (`engine.rs:1841-1845` and `:1885-1893`, `engine/batch.rs:257-298` against `engine.rs:1837-1839` and `batch.rs:264`). A prompt of `k * 2048` tokens (8192) is `2048, 2048, 2048, 2047, 1` off and
  `2048 x 4` on, so the last pass differs and the output bits differ. A prompt of `k * 2048 + 1` tokens (8193) is `2048 x 4, 1` in both, and the ids are equal 16 of 16.
* The project decided this on 2026-10-23: LOG row "Prefix store (PR #113) merges opt-in, default off ... Store on vs off is not bitwise for the 35B hybrid" (status in force), and
  `docs/results/2026-10-22-pc-prefix-store.md` section 3 (b): CUDA 35B "not bitwise from step 0 (CUDA prefill is chunk-sensitive)", "ids equal" on its chat test. The `INTARSIA_PREFIX_STORE` row of
  `docs/tuning.md` says the same ("yes (on a chunk-sensitive backend, CUDA / Metal, the boundary-cut schedule changes prefill bits vs the store off)").
* What the old docs did not say (added to the tuning.md row): the schedule differs **with no message boundary at all** (token-id prompts, `/v1/completions`), because of the last-token pass, and
  random-id prompts have flat logits (top-1 probability about 0.4 %), so a small numerical change flips greedy ids in 14 of 16 prompts where a chat prompt did not.

Neither arm is "the right one" in an absolute sense: both are bf16 / NVFP4 approximations and no fp32 oracle was run. Each arm equals its **own** single-sequence engine (store off = `serve` without `--max-batch`, store on = `serve --prefix-store on`),
bit for bit in every cell. flipev's 14 of 16 reproduces exactly (14 of 16 at 8192 tokens here, same seeds 71 / 72).

## 2. Method

spark1 (GB10, CUDA), `Qwen3.6-35B-A3B-NVFP4`, one binary built from origin/main `d6c2d0928` (fleetq #9951, `--quiet gpu,cpu --mem 62`, 32 min including the 5 min build; vLLM stayed up, earlyoom active,
lowest MemAvailable 44.9 GB, nothing killed). One server visit per config, `--max-seq 16384 --mem-budget 40`. Prompts are token ids (random ids in [1000, 100000) from a seed, as flipev's `herd_bench.py`; seeds 71 / 72 at 8192 tokens are flipev's
pack-phase prompts), `/v1/completions`, temperature 0, `ignore_eos`, 48 tokens. Sets: **8192** (seeds 71, 72: 16 prompts, the flipev case) and **8193** (seeds 81, 82: 16 prompts, the control where the two schedules coincide).
Every compared prompt is cold (`cached_tokens` 0 in all 352 streamed replies, every reply 48 tokens, 0 errors in all 392 requests including the 40 `lp` ones; no prompt is sent twice to one server). `burst` = the 8 prompts of a seed released together (flipev's cell); `seq` = one at a time (the single-sequence engine).

`generate` takes only a text prompt, so the single-sequence reference is `serve` without `--max-batch` (the same `LocalEngine` that `generate` runs). The brief's "chunk size matched to the store's chunking" has no knob (the store's schedule is not
a chunk size; `INTARSIA_PREFILL_TAIL_MERGE` and `--prefill-chunk` do not remove the lone last-token pass), so the matched-schedule experiment is the prompt length: 8193 makes both schedules identical.

## 3. Bisect: ids equal to the single-sequence store-off reference (x / 16)

Reference = `s_spec0` (single-sequence engine, `--spec off`); `s_def` (default, MTP k2) is identical to it in every cell, so the table does not repeat it.

| config | env / flags | 8192 tokens | 8193 tokens |
|---|---|---|---|
| `s_def` solo, store off | default (MTP k2, macro 8192) | 16 / 16 | 16 / 16 |
| `s_spec0` solo, store off | `--spec off` | 16 / 16 (the reference) | 16 / 16 (the reference) |
| `s_spec0_nomacro` | `--spec off`, `INTARSIA_PREFILL_MACRO=0` | 16 / 16 | 16 / 16 |
| `b_off` `--max-batch 8` burst, store off | default (batched MTP N=2 ran: 173 accepted drafts in `b_off`, 0 with `--spec off`; macro and pack at their defaults) | 16 / 16 | 16 / 16 |
| `b_off_spec0` | `--spec off` | 16 / 16 | 16 / 16 |
| `b_off_nomacro` | `INTARSIA_PREFILL_MACRO=0` | 16 / 16 | 16 / 16 |
| `b_off_plain` | `INTARSIA_PREFILL_MACRO=0 INTARSIA_PACK_PREFILL=0 --spec off` | 16 / 16 | 16 / 16 |
| `s_store` solo, store on | `--prefix-store on` (MTP k2 stays on, `INTARSIA_MTP_STORE`) | **2 / 16** | 16 / 16 |
| `s_store_spec0` | `--prefix-store on --spec off` | **2 / 16** | 16 / 16 |
| `b_store` `--max-batch 8` burst, store on | `--prefix-store on` (macro and pack turned off by `store_combinations`) | **2 / 16** | 16 / 16 |
| `b_store_spec0` | `--prefix-store on --spec off` | **2 / 16** | 16 / 16 |

Every store-on config equals every other store-on config (16 / 16 at both lengths): `b_store` = `s_store`, `b_store_spec0` = `s_store_spec0`, and MTP on / off does not matter. Every store-off config equals every other store-off config.
The full matrix (each config against `s_def`, `s_spec0`, `s_store`, `s_store_spec0`, and burst against burst) is `raw/tables.md`.

Which knob flips the ids: only `--prefix-store on`, and only where its schedule differs from the plain one:

| knob | flips the ids? |
|---|---|
| macro prefill on / off (solo and `--max-batch 8`) | no (16 / 16 both lengths; confirms the l7m / sk claim that a macro pass is bitwise the plain schedule, here at the ids level on 8K prompts) |
| packed prefill on / off | no (and it never engaged: `intarsia_batch_pack_passes_total` 0 in every visit, as flipev found) |
| MTP k2 vs `--spec off` (solo and batched, store off and on) | no |
| batching (`--max-batch 8` burst vs one at a time) | no, within either arm |
| `--prefix-store on`, prompt `k * 2048` tokens | **yes** (14 of 16 differ; first differing token index 0, 0, 3, 4, 4, 4, 5, 6, 7, 10, 12, 22, 40, 46) |
| `--prefix-store on`, prompt `k * 2048 + 1` tokens (schedules coincide) | no (16 / 16 in every config) |

First differing token: index 0 in 2 prompts (the prefill's last-row logits already pick another token), later in the rest; in every case the store-on arm's decode, MTP verify and batching are bitwise the store-off arm's whenever the prefill is.
That puts the first diverging pass in prefill chunk 4 of the 8192 prompt (the first three 2048-row chunks are the same in both schedules).

Logprob side measurement (`lp` cells: 4 prompts per set, top-5 logprobs of the first token, `raw/tables.md`): at 8192 tokens the first token's top-1 logprob is higher with the store on in all four prompts, by 0.100, 0.082, 0.040 and 0.096 nats
(-5.470 -> -5.370, -5.322 -> -5.240, -5.419 -> -5.379, -5.387 -> -5.291); at 8193 tokens it is bitwise equal (delta 0). The common sign is an observation on four prompts, not a mechanism. Margins of top-1 over top-2 at token 0 are 0.4 to 0.6 nats and fall under 0.1 later, which is
where the ids flip.

## 4. Where the chunk counts come from (flipev's 66 vs 60)

flipev read the 66 vs 60 prefill chunks as the store aligning chunks. It is not the alignment. Matched comparisons only (the visits ran different request mixes: `b_off` and `b_store` also ran 8 `lp` prompts, the others burst only; `intarsia_batch_prefill_chunks_total`):

| visit (burst only, 32 prompts) | macro | chunks |
|---|---|---|
| `b_off_spec0` | on (default) | 132 |
| `b_off_nomacro` | off | 146 |
| `b_off_plain` (macro off, pack off, `--spec off`) | off | 146 |
| `b_store_spec0` (store on) | off (`store_combinations`) | 146 |

With macro prefill off, store off and store on run the same number of scheduler chunks (146): the lone last token and the 2047-row chunk sit inside one scheduler chunk, so the schedule difference is invisible in the count. The gap in flipev is the **macro prefill**, which the store turns off under
`--max-batch > 1` (`store_combinations`, `batch.rs:1280`): 14 chunks fewer here. MTP and packing do not move the count (`b_off_nomacro` = `b_off_plain` = 146). The `lp` prompts explain the rest: `b_store` 182 against `b_store_spec0` 146 is 4 prompts of 8192 tokens at 4 chunks plus 4 of 8193 at 5 chunks = 36
(so an 8193-token store-on prompt runs 5 passes, the 1-row one included), and `b_off` 140 against 132 is the same 8 prompts in macro passes.

## 5. What it means for the herd flip

* `INTARSIA_PREFIX_HERD=1` needs the store (`docs/results/2026-11-17-herd.md`), so a herd default-on only acts when the store is on. Herd does not change the ids relative to store on: a follower restores the leader's stored state, and a restore is bit-identical to a cold prefill **with the store on**
  (`tuning.md` `INTARSIA_PREFIX_STORE` row; flipev: 672 / 672 herd replies equal their store-on solo reply). Here `b_store` = `s_store` 16 / 16 at both lengths, the same statement without herd.
* So the id difference belongs to the store default, not to herd: anyone who turns the store on moves from the store-off bits to the store-on bits for prompts whose last chunk differs (about every prompt, not all of them: 8193-token prompts are equal), exactly as documented since 2026-10-23.
  Herd on top changes nothing further.
* The store also costs 12 to 14 % on a burst of unrelated 8K prompts (flipev section 6): not through packing (never engaged) and, per section 4, partly the macro prefill it turns off. That too is a store-default question.

## 6. Not verified

* Which of the two schedule differences causes the bits: the last body chunk of 2047 rows instead of 2048, or the lone 1-row last pass. Lengths 8194 (`2048 x 4, 1, 1` against `2048 x 4, 2`) and 8200 would separate them; a follow-up job (fleetq #9958) was queued behind the mcdiag jobs
  (61 min estimate) and cancelled, so neither was run. No numerics fix was attempted (out of scope).
* Real chat prompts: not run here. The 2026-10-22 pc lane measured ids equal on its chat test; random-id prompts are the worst case (flat logits).
* No fp32 / oracle reference, so no statement that either arm is more accurate; the KL of the two arms was not measured (only first-token logprob deltas on 4 prompts per length).
* One model, one GPU (spark1), one chunk size (2048), one run per config (flipev found both arms deterministic; here each arm's burst replies equal its solo replies).
* Not covered: HIP, Metal (the tuning.md row already says CUDA / Metal are chunk-sensitive), `--max-batch 16`.
