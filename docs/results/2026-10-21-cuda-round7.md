# CUDA round 7: opt-in e4m3 tensor-core projection GEMMs (cuBLASLt), 35B prefill +10-13 %, +20 % with chunk 4096 (2026-10-21)

Target: spark1 (DGX Spark GB10, sm_121, CUDA 13.0), Qwen3.6-35B-A3B-NVFP4. Lane G1 of
`docs/plans/2026-10-21-quota-burn-plan.md`; the user's 2026-10-19 decision was "2 yes opt-in" (unanimis 11031a99).
Branch `perf/cuda-round7`. Raw logs are in `docs/results/2026-10-21-cuda-round7/raw/`.

## 1. Headline

- **New opt-in kernel `matmul_fp8_gemm_lt`, switched on by `INTARSIA_CUDA_FP8_GEMM_LT=1`.** It runs the 35B fp8 W8A8
  projection GEMMs on cuBLASLt's native e4m3 tensor-core path. The default is unchanged and bitwise: the same greedy ids
  as `origin/main` on the 1497- and 16026-token prompts, the same KL21 digits, the same 8B plan.
- **The activation numerics are the same as vLLM's, and they already were.** Both engines quantise the activations
  statically per tensor: e4m3 of `x / input_scale`, with the checkpoint's `input_scale`.
  - vLLM: `scaled_fp8_quant` + `cutlass_scaled_mm`.
  - Ours: the default path already multiplies e4m3-valued activations (round 4, §4.2).
  - So the only numeric change is the accumulation. cuBLAS, like vLLM's CUTLASS sm120 kernel, accumulates the whole K
    inside the tensor core's fp32 accumulator. The default bf16 GEMM adds each k-step's result with a separate fp32
    add instead.
- **Kernel speed at M = 2048:** 99-135 TFLOPS, quantiser included, against 36-71 for the default `gemm_reg`. The fp8
  projections of one 2048-token chunk take 41.2 ms instead of 81.1 ms.
- **End to end, in-engine A/B ×3, `--at-most` on both sides** (gains are paired per round):

  | change in prefill | 1k | 4k | 16k |
  |---|---|---|---|
  | lt | **+10.2 %** | **+12.9 %** | **+12.1 %** |
  | lt + `--prefill-chunk 4096` | +8.8 % | **+20.2 %** | **+19.6 %** |

  Decode is unchanged in both arms (−0.6 to +0.3 %).
- **localeval against vLLM, same day.**
  - Prefill: lt 4689\* / 6378 / 5964, lt + chunk 4096 4671\* / 6845 / 6354, vLLM 5171\* / 6353 / 6275 tok/s.
  - At 16k, lt is −5.0 % and lt + chunk 4096 is **+1.3 %**. Round 6's default was −15.3 %.
  - Decode: lt is 82.4 / 79.9 / 72.3 tok/s against vLLM's 77.9 / 76.6 / 73.6.
  - \* The 1k prompts are under 1024 tokens, so that column is TTFT overhead, not prefill throughput.
- **Accuracy: vLLM's own run-to-run KL is the yardstick.** Same method throughout: every candidate truncated to top-20,
  the M3 tool `scripts/m3-accuracy/setkl.py`.

  | 35b-long, system/user-turn rows excluded (M3's proposed floor metric, option (a); not yet decided) | KL21 |
  |---|---|
  | vLLM re-run vs its own stored golden | 8.42e-3 |
  | default vs golden | 1.420e-2 |
  | **lt vs golden** | **1.355e-2** (closer than default) |
  | lt vs default (the size of the change) | 7.61e-3 (below vLLM's own) |

  - 35b-short: lt is further from the golden than default, 6.55e-3 against 5.32e-3. That is +23 % on all rows, +17 % on
    the excluded rows.
  - The size of the change on short is 3.36e-3, 1.06x vLLM's own 3.16e-3.
- **Gate verdict.** Neither our default nor lt is within vLLM's own KL against vLLM's golden: default is 1.7x on both
  sets. So, read literally, the gate cannot be met by any intarsia build.
  - What lt does meet: on M3's proposed 35b-long metric it is closer to vLLM than default is. The change it makes is below
    vLLM's run-to-run noise on long and at that noise level on short (+6 %).
- **One gate fails: `chat_reuse_4k` continue, 3/32 (default 32/32), so the prefix-reuse gate fails.** It is a near-tie,
  not a reuse bug:
  - warm-vs-cold logit KL is 4.96e-3 for lt against 4.90e-3 for default (default even has 2 argmax flips there);
  - chunk 2048 vs 1024 alone gives 4.85e-3;
  - the first divergence is at a token where the cold run's margin is 0.067 nats.

  Restore and aligned stay 32/32.

## 4. What was built

- **`kernels/cuda/fp8_gemm_lt.cu`.** The quantiser `lt_actq8_kernel` writes e4m3 bytes, with the same rounding as the
  default's `fp8_actq_kernel`. Then `cublasLtMatmul` runs in TN layout:
  - A = weights [N,K] with weight_scale as the A scale pointer;
  - B = xq [M,K] with input_scale as the B scale pointer;
  - D bf16 or f32; fp32 compute.

  The scales stay on the device, with no host synchronisation. Descriptors are initialised on the stack.
- **The algorithm pin.** One algorithm per (N, K, output dtype), from the heuristic at M = 2048. It must need no
  workspace, split-K is pinned to 1 with no reduction, and it is checked with `cublasLtMatmulAlgoCheck`. It is cached
  per device.
- **The W8A16 fallback** (input_scale ≤ 0) is the same as `gemm_f8`'s: the bf16 weight-only kernel runs after cuBLAS
  and overwrites the output when the scale is not positive.
- **Registration** (`quantmoe.rs`): every M ≥ 5, K % 128 = 0, N % 16 = 0. Priority 25 when `INTARSIA_CUDA_FP8_GEMM_LT=1`
  (`kernels::fp8_gemm_lt`), −10 otherwise. Declared in `kernels/cuda/ik_cuda_abi.h`. `build.rs` links `cublasLt`.
- **Debug switches:** `INTARSIA_LT_DEBUG=1` prints the chosen algorithm. `INTARSIA_LT_FAST_ACCUM=1` is an A/B knob only,
  with no effect on sm_121.
- **`tools/golden_vllm.py --ids-from GOLDEN`** re-scores an existing golden's ids on the server, giving a second
  reference sample on identical positions.
- **Scripts in `scripts/cuda-round7/`:**
  - `window.sh`: one `fleetq run --takes-down guidance` per window, with a trap restore and optional localeval;
  - `acc.sh`, `acc2.sh`, `wAB.sh`, `dev.sh`, `probe.sh`, `prep.sh`, `build-base.sh`, `mut.sh`, `mutate.py`,
    `kl-table.sh`, `vllm-self.sh`, `fetch.sh`, `memcheck.sh`, `goldens.sh`.

  Also a race-targets line for the lt test.

## 5. Notes and caveats

- **A base build pitfall (caught and fixed).** The first r7-base build was the dev binary: `git archive` gives old
  mtimes, and the target dir copied from r7-dev looked fresh to cargo. Window 1's "base" gens therefore ran dev
  defaults. Window 2 re-ran them on a clean base: 0 round-7 symbols, checked by `build-base.sh`. The ids were identical
  to window 1's dev defaults on both prompts.
- **The base export is 4be7b7d4.** `origin/main` has since moved to 789511c2 with HIP-only and server-metrics changes;
  no CUDA engine code differs.
- **spark1 memory.** vLLM now holds about 81 GB (EngineCore), not the 64 GB fleetq books for it, so about 25 GB is
  free. No 35B process ran beside vLLM: all 35B runs were inside the downtime windows. The windows requested
  `--mem 85`, because `--mem 100` would never start (fleetq computes 100 − 64 = 36 GB needed, while the box shows 24).
- **localeval's unanimis auto-capture of the vLLM run failed** with an ssh mux error. The run itself is saved:
  `results/20261021-105608-spark-guidance-vllm-cuda-round7`.

## 8. Decisions for the user

1. **Make e4m3 (lt) the CUDA default?** Not recommended yet; it stays opt-in.
   - **For:**
     - +10-13 % prefill, +20 % with chunk 4096;
     - vLLM parity at 16k with chunk 4096 in localeval;
     - the gated 35b-long metric is closer to vLLM than default;
     - the change is no bigger than vLLM's own run-to-run noise on long.
   - **Against:**
     - the prefix-reuse gate fails on the `chat_reuse_4k` continue row, a near-tie (§3.3);
     - 35b-short is 23 % further from vLLM;
     - greedy ids change at token 32 / 41.
   - **Options:**
     - (a) keep it opt-in (current state);
     - (b) default after a near-tie-aware continue gate or a second continue prompt, so one coin flip cannot decide it;
     - (c) default now, accepting the continue-row FAIL.
   - **Unmeasured for default use:** batched decode at 5-32 concurrent streams. The kernel bench (§2.1b) shows lt
     2.5 % slower at M = 8. No end-to-end concurrent-serving A/B ran.
   - **Precedent:** the user made HIP's `matmul_fp8_mma_f8` default at 35b-short KL21 7.07e-3 to 7.42e-3 ("f8 on",
     2026-10-18; LOG.md O2). lt's tool-exact 35b-short KL21 is 6.648e-3, below that. The difference: HIP had no failing
     reuse row.
2. **Chunk 4096 with lt** (`--prefill-chunk 4096`, already a flag) adds another +7 % at 4k and 16k on top of lt. Its
