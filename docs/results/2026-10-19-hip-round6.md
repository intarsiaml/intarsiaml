### MoE gate_up (item 2): what bounds it

Resources (`prof/isa-moe.txt`, `-Rpass-analysis=kernel-resource-usage`, gfx1201): round-5 gate_up<64> 235 VGPRs, 34880 B
LDS, 6 waves/SIMD, no spills. The k-block loop (one 64-element k block, ISA in the CPU-slot dump) issues 16 WMMAs against
~150 VALU ops (fp4 nibble extract `v_and`/`v_lshrrev`, scale `v_mul`, bf16 pack `v_perm`, moves) and 48 LDS reads (32
`ds_load_b32` fp4 table lookups, 16 `ds_load_b128` activation fragments). The epilogue already fuses silu(gate) * up
(`moe_wmma.h`, gate waves read the up accumulators from LDS), so there is no separate silu pass to fuse.

Achieved rate: measured microbench (`bench_prefill_shapes`, W1, round-5 kernel): whole `moe_experts` (gate_up + down)
at T = 4096, 64 pairs: 5032 us = 41.0 TFLOPS (the bench's own flop count, 6 * 2048 * 512 per pair). Derived from the profile,
not a counter (assumes the 64-pair launches are a 4096-token chunk, which the microbench's flop count is consistent with):
gate_up<64> 2.63 ms per launch = 52 TFLOPS with the round-5 kernel, 2.41 ms = 57 TFLOPS with variant 5; weight bytes read
(256 experts x 1024 rows x 2048 x 0.5 B + e4m3 scales, re-read per pair tile, ~2 tiles per expert) ~0.6 GB per launch =
~0.25 TB/s, well under the card's DRAM bandwidth. So it is not memory-bound; it is issue/latency-bound on the in-register
dequant (VALU + LDS table reads per WMMA) at an occupancy of 6 waves. The two levers that held:

* **kMwSkip**: the last pair tile of an expert usually holds fewer than 64 pairs; its empty 16-pair fragments still ran their
  LDS reads and WMMAs. Skipping them (block-uniform `jn`, compile-time fragment count) cut gate_up<64> 105.1 -> 99.1 ms.
* **kMwOcc**: gate_up's up accumulators (16 KB) alias the activation double buffer (free after the k loop; the loop's last
  barrier orders it), LDS 34880 -> 18496 B, and `amdgpu_waves_per_eu(8)` caps VGPRs at 186: 8 waves/SIMD instead of 6.
  With kMwSkip: 99.1 -> 96.6 ms. Same for down (no aliasing needed there, occupancy only): 53.3 -> 51.9 ms.

Dense f8 GEMM comparison: `f8_gemm_kernel<4,2,2,4,bf16>` averages 268 us per launch (260 launches, 69.8 ms), 147 VGPRs, 40960
B LDS, 6 waves, no spills. Its per-launch shapes are not in the trace table and the f8 lines of `bench_prefill_shapes` were
filtered out of the W1 log, so **its TFLOPS were not measured this round**; I do not quote one.

### GDN v2 (item 3)

`gdn_delta_rows_v2_kernel<128,2,2>`: 90 launches, 100-102 ms. Grid 8 x 32 one-wave blocks = 256 waves for 128 SIMDs (2
waves per SIMD): every head and every row block already runs concurrently, so there is no cross-head overlap left to take;
each wave walks the T tokens in order (the state recurrence). The token loop of the PD 2 kernel is dependency-bound: 1171
instructions, 182 of them `s_delay_alu` stalls (counted from the `isa.sh` dump; resources in `prof/isa-gdn.txt`, which was
taken from the build that still had the pipelined kernel). Built and measured a bitwise two-token register
pipeline (`gdn_delta_rows_v2p_kernel`: token t's update + output dot interleaved with token t+1's decay + kv dot in one pass
over the state, one LDS sync per token instead of two). It is bitwise (`gdn_v2_is_bitwise_the_rows_kernel`, 19 shapes,
`logs/w1-gpu1.log`) but bought only 100.61 -> 99.27 ms (-1.3 %, W1 `prof/pipe1.txt` vs `prof/mw0.txt`), 187 VGPRs. Dropped
(see below).

### f8 GEMM (item 4)

Spill check only: every `f8_gemm_kernel` instantiation has 0 B scratch (`prof/isa-fp8.txt`). No change.

## What I tried and dropped

* **Byte-indexed fp4 table** (`kMwByte`, 256 float2 entries: one LDS read per two weights instead of one per weight):
  gate_up<64> 99.1 -> 116.7 ms with kMwSkip (`prof/mw3.txt`), 115.7 ms with all bits (`prof/mw7.txt`). Removed from the code.
  Cause not profiled further.
* **Token-pipelined GDN** (above): bitwise, -1.3 % of GDN time. Not worth a second kernel. Removed from the code.
* Not tried (dead ends from earlier rounds, per the brief): 128-pair MoE tile, LDS-staged GDN, more lanes per GDN row,
  chunked/WY GDN, fp4 activations, XSTAGE.

## Caveats and env vars

* The 32-pair tile stays on the round-5 kernel. Within W1, variant 5 there was 1.2 ms (gate_up) + 0.7 ms (down) faster than
  mw0, but all W1 32-pair numbers were ~4 ms slower than in round 5 and W2 for reasons not found, and there was no window left
  to A/B it on its own. A candidate for round 7 (flip `kMwDefault32`, rerun `moe_pairs`, the pin, and an A/B).
* The flash HPB A/B (W1) and the W2 A/B used other base trees (see top). Only W3 is used for the bars.
* `bench_prefill_shapes`' variant sweep did not run in W1 (its switch was not `INTARSIA_HIP_*`, so `dev.sh` did not pass it);
  renamed to `INTARSIA_HIP_MW_SWEEP`, not re-run. The variant decision rests on the same-window profiles.
* The derived MoE TFLOPS / bandwidth are shape arithmetic over measured times, not hardware counters; the dense f8 TFLOPS was
  not measured.
* Env vars: `INTARSIA_HIP_FLASH_HPB=1|2|4` (default 4; 2 is the round-5 behaviour), `INTARSIA_HIP_MOE_MW=0|1|4|5` (default 5
  at 64 pairs, 0 at 32; `0` restores the round-5 MoE prefill kernels exactly). Both in `ENV_KNOBS`. Unchanged from round 5:
  `INTARSIA_HIP_FP8_F8=0` (f8 kill switch), `INTARSIA_HIP_MOE_V3=1` (opt-in decode MoE).
