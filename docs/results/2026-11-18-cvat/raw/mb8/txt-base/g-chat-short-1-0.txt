When two different keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In chaining, each bucket in the array contains a linked list (or another dynamic structure) of entries that hash to that index. When a collision happens, the new entry is simply appended to the list. In open addressing, all entries are stored directly in the array itself. If a collision occurs, the algorithm probes for the next available slot using a specific sequence, such as linear probing (checking the next index sequentially) or quadratic probing, until an empty spot is found.

The load factor, defined as the ratio of the number of stored elements to the total number of buckets in the hash table, is critical because it directly influences the frequency of collisions. A low load factor means there are many empty buckets relative to the number of items, which significantly reduces the probability that two keys will hash to the same index. Conversely, a high load factor indicates that the table is nearly full, increasing the likelihood of collisions and forcing the hash table to perform more work to resolve them.

This relationship between the load factor and lookup time is fundamental to the efficiency of hash tables. In an ideal scenario with a low load factor and a good hash function, lookups, insertions, and deletions occur in constant time, $O(1)$. However, as the load factor increases, the average length of chains in chaining or the number of probes in open addressing grows, causing lookup times to degrade toward linear time, $O(n)$, in the worst case. Therefore, most hash table implementations automatically resize (rehash) the table when the load factor exceeds a certain threshold, typically around 0.75, to maintain optimal performance.
