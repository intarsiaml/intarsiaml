# Lane mfp8split: a 9..=12-row split plan for the row-exact fp8 GEMV (2026-11-17)

Branch `mfp8split` from `origin/main` `b9e400f20`. Raw data in `docs/results/2026-11-17-mfp8split/raw/`, scripts in `scripts/mfp8split/`. Machine: endor (M5 Max); every Metal
build, test, timing and served run went through fleetq on endor (`--quiet gpu,cpu` for timing and served runs).

## 0. Coordinator go-aheads / plan changes

(none)

## 1. Verdict

**Ships default-on; `INTARSIA_METAL_FP8_ROWS_SPLIT=0` takes it back.** `matmul_fp8_gemv_rows` calls of 9..=12 rows run as 9 = 7+2, 10 = 8+2, 11 = 8+3, 12 = 8+4 (`FP8_ROWS_PLAN`) instead of
the halves 5+4 / 5+5 / 6+5 / 6+6. Every other row count (2..=8 one launch, 13..=16 halves) and every other kernel dispatch exactly what main does.

* **Bitwise: all gates pass** (section 4): `tests/rows_exact.rs` (every row equal to the one-row call, plan and halves, both fp8 forms, f32 and bf16 out, plus a wrong-slice control and the
  kernel `NEGCTL` controls), served greedy ids 66 / 66 cells equal solo `generate` in every one of 5 arms on each model, the arms equal each other, the default MTP engine's ids equal main's.
* **Speed (ABBA, same binary, env switch, `serve --max-batch 16`)**: on the 35B the fp8 kernel's saving shows up as the server step, **-4.4 % / -5.1 % / -2.5 % at 10 / 11 / 12 streams, -2.6 % at 9**
  (pooled over 10 to 14 visits per arm), and as aggregate tok/s **+1.8 / +5.1 / +3.5 % (means), +2.7 / +4.1 / +4.9 % (medians) at 10 / 11 / 12 streams**; 9 streams is **-1.0 % (mean) / +2.1 % (median)**,
  inside the noise of this Mac (the null cell s8, whose dispatch is identical in both arms, reads -1.5 % / -3.8 % on the same statistics). The 27B (head only) is neutral: +/-4 %, inside its noise (a ~1-2 % effect
  is the prediction). Ship rule of the brief (a)-(c) pass and 9..12 streams gain >= 2 % on the 35B at 10, 11 and 12 with no cell regressing beyond noise: met. The gain is modest, as mchunkx's estimate said.
* Nothing else changes: `--max-batch` unset is still 1; at `--max-batch 8` or less no call has 9 rows, so the dispatch is main's byte for byte (plans diff empty, ids equal main).

## 2. The change

`crates/intarsia-backend-metal/src/lib.rs`: `FP8_ROWS_PLAN` (rows -> launch sizes, empty = the old rule), `fp8_rows_split_enabled()` (`INTARSIA_METAL_FP8_ROWS_SPLIT`, `0` = off, unset or anything else =
on), the test hook `with_fp8_rows_split`, and one branch in `chunk_sizes` (`kernel == matmul_fp8_gemv_rows && knob on && the plan has an entry`). `row_chunks` slices the row tensors per chunk exactly as for the
MXFP4 plan; the shared weights, scales and the `_xd` scratch are reused by the chunks (stream order), and every row of a row-exact kernel is bitwise the one-row launch, so any split is bitwise the same.
`docs/tuning.md` has the row; lib unit tests pin the plan (`fp8_plan_is_a_valid_split_and_only_9_to_12`, and `chunk_sizes_by_kernel_and_knob` no longer lists fp8 among the kernels that keep halves).

## 4. Gates

(a) **Bitwise, `tests/rows_exact.rs`** (`raw/test-rows.log`: 11 passed, 4 ignored timing tests; lib `chunk` tests 4 passed). New `fp8_row_splits_are_bitwise_the_one_row_gemv`: every fp8 shape of the file
(35B projections, odd shapes, K = 5120), both weight layouts (second with NaN codes), M = 9..=16, input scale 0 and 0.37, f32 and bf16 out, aligned and unaligned x, plan on and off, both forms of the kernel
(`fp8_case`: staged where K allows and `_xd` with the scratch): each row of the M-row call equals the one-row `matmul_fp8_gemv` launch. Controls: a plan whose tail chunk reads the wrong rows must differ from the
one-row launches (asserted), and `INTARSIA_METAL_NEGCTL=fp8_xd` / `fp8_mmt` (a kernel form with one association changed) make the new test FAIL while it passes with the env unset (`raw/negctl.log`).

(b) **Served greedy ids** (`scripts/mfp8split/gates.sh`, `served_ids.py`; `raw/gates-27b`, `raw/gates-35b`): `generate --spec off --show-ids`, 256 greedy tokens on each of 16 prompts (even about 100 tokens, odd about
4700) is the reference; `serve` arms `new-mb16` (`INTARSIA_METAL_FP8_ROWS_SPLIT=1`), `new-mb16-off` (`INTARSIA_METAL_FP8_ROWS_SPLIT=0`), `base-mb16` (main `b9e400f20`), `new-mb8`, `base-mb8` serve 1 / 4 / 6 / 8 / 9 / 10 / 12 / 16 concurrent
streams. **Both models, all five arms: 66 / 66 cells equal the stream's solo ids** (`vs solo generate: SAME`).

(c) **No-op**: `base-mb16` vs `new-mb16`, `base-mb8` vs `new-mb8` and `new-mb16-off` vs `new-mb16`: SAME 66 / 66 cells each, both models (so 1..8 streams are main's ids). Served plan JSONs: base-mb8 vs new-mb8 0 differing
lines; base-mb16 vs new-mb16 and new-mb16 vs new-mb16-off 0 differing lines on both models (the 8 lines that differ between mb8 and mb16 are the scratch sizes that follow `max_batch`). Default MTP engine (`generate`, no `--spec off`), 256 tokens, prompt 0 (99 tokens) and 1 (about 4.7k): ids md5
equal between main and the branch on both models (`mtp p0 / p1 ... SAME`). Routing (kernel-mode profile, 24 tokens, short prompts, `--max-batch 16`; `matmul_fp8_gemv_rows` launches by rows):
35B 10 streams on: 8-row launches 2080, 2-row 2340 (plan 8+2; with the other tail sizes of the ragged steps); off: 5-row 4160 (halves 5+5); 12 streams on: 8-row 2340, 4-row 1820 (8+4); off: 6-row 3640, 5-row 1300;
8 streams on: 8-row 2080 only (one launch). 27B 10 streams on 8-row 16 / 2-row 18, off 5-row 32; 12 streams on 8-row 18 / 4-row 14, off 6-row 28 / 5-row 10 (`raw/gates-*.log`, lines `route ...`). The knob does what it says. **Shipped default (variable unset)**, 35B, 10 streams, same trace (`raw/routedef-35b.log`, job #9901): 8-row launches 2080, 2-row 2340, no 5-row launches: the plan applies with no env set (the ids cannot change either way). Not repeated on the 27B (same code path).

## 5. Speed: ABBA

`scripts/mfp8split/abba.sh`: one binary (`.base/bin-new`), `serve --max-batch 16`, arm A = `INTARSIA_METAL_FP8_ROWS_SPLIT=0` (the old halves), arm B = `INTARSIA_METAL_FP8_ROWS_SPLIT=1` (the plan; the env var is set explicitly in every arm, and the shipped default, the variable unset, is checked separately in section 4). Fresh server per visit, warm-up, then cells of N closed-loop streams
x 2 short requests (about 115 prompt tokens), 256 greedy tokens each, `INTARSIA_CB_TRACE=1`; the thermal level is waited to 0 (up to 120 s) before every cell. s8 (one 8-row launch) and s16 (halves 8+8) are null cells:
both arms dispatch the same. **This Mac is noisy**: whole visits and single cells land 15-30 % slow in either arm (A2 s12 / s16, B3 s8 / s9 / s16 in run 1), so the table pools every visit. The cause was not found: the other fleetq jobs of the window (mcopy, #9885 / #9892) ran on spark1, not endor, and the thermal level was waited to 0 before each cell, so it is load outside the queue or thermal state.

## 6. Revert

`INTARSIA_METAL_FP8_ROWS_SPLIT=0` in the server's environment: the old chunking (one launch up to 8 rows, halves 9..=16) for `matmul_fp8_gemv_rows`, bitwise the same ids. To remove the code: delete `FP8_ROWS_PLAN`,
`fp8_rows_split_enabled`, `with_fp8_rows_split` and the `chunk_sizes` branch in `crates/intarsia-backend-metal/src/lib.rs`. To default it off without removing it: `DEFAULT_FP8_ROWS_SPLIT = false` there.

## 7. Not verified / limits

* The aggregate-rate gain at 9 streams is not demonstrated (mean -1.0 %, median +2.1 %, inside the null cell's -1.5 % / -3.8 %); the step time (-2.6 %) says it is real but small. The 10..12-stream gain is 2-5 %, with the
  noise described above; a quieter machine would tighten it; in run 2 the B arm's step time was bimodal (24.1 ms and 26-27 ms visits) where A's was flat, which is not explained (cell-specific, not visit-specific). The 27B has 2 visits per arm.
* Timing of the kernel is in isolation (a warm queue of launches); the ABBA is the in-situ check. TTFT and the 4k-prompt prefill path are not touched (prefill is a different kernel) and were not re-measured.
* `serve --max-batch 16` is still opt-in; the default cap (1) and the 8-stream ship rule are untouched. Only Metal is affected; the HIP and CUDA row kernels are not.
* Machine noise: the thermal level was waited to 0 before every cell (`cooled` lines in each visit's `cells.txt`); some cells still ran at level 1-2.
