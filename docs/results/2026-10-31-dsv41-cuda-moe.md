# DSv4.1 lane cuda-moe: EXL3 TP sharding and grouped EXL3 routed experts on CUDA (2026-10-31)

Lane `dsv41/cuda-moe` of `docs/plans/2026-10-31-dsv41-unpark.md` ("EXL3 grouped MoE + EXL3 TP sharding start now";
review `docs/reviews/2026-10-31-dsv41-plan-fable-review.md` sections 1 and 2.7). No new `Op` variant: the routed experts
are an EXL3 encoding of the existing `Op::MoeExperts` (coordinator decision, 2026-10-31).

## Headline

- **EXL3 linears shard at load** (`QuantLoadOpts::shard`, previously refused): column-parallel (`ShardAxis::Rows`, the
  checkpoint's N) and row-parallel (`ShardAxis::Cols`, K). The rule is the 128-point Hadamard grid: each rank's share
  must be a multiple of 128, anything else is refused naming the tensor and the rule. Every DSv4.1 EXL3 tensor splits at
  TP=2 on both axes (checked over `quantization_config.json`); `w2` row-parallel is 2 x 1152 = 2 x 9 x 128.
  CPU parity: column slices side by side are bitwise the whole output; row-parallel partials summed are within 4.8e-7 of
  it (f32 outputs, |y| up to 5.6) at the DSv4.1 expert shapes.
- **EXL3 routed experts in `Op::MoeExperts`** (`quant::exl3_moe`): input 3 an i16 trellis arena selects the encoding;
  per-matrix widths and 16-byte offsets in an `[E, 8]` table, per-expert scales `[E, 3H+3I]`, the SwiGLU clamp as input 7.
  CPU reference (f64), loader with the TP=2 intermediate-width split (rank 0 + rank 1 = whole to 1.2e-7).
- **CUDA `moe_experts_exl3`**, ported from TensorFold's DeepSeek-V4.1 fork (Apache-2.0): decode windows (< 64 rows) run
  the grouped GEMV (`grouped_cp_kernel`), prompt slices (512 rows) the grouped prompt kernel (`grouped_rows_kernel`);
  six launches a slice. Deterministic (no atomics), and a row's bits depend on neither its batch nor the path.
- Real Mia experts (layer 3: 3-bit routed + 5-bit shared; layer 20: 2-bit routed + 4-bit shared), T = 1 and 4, whole and
  TP=2 ranks: cuda vs cpu rel_l2 3.3e-4 .. 3.7e-4 (inside tolerance); rank 0 + rank 1 vs whole 4.5e-7 (cuda), 4.4e-8 (cpu);
  64-row prompt slices bitwise equal to the decode kernel row by row.
- Decode per TP=2 rank (6 routed + shared, real experts): **257 us/token at 199 GB/s** in one call, against 784 us at
  65 GB/s for 21 separate `matmul_exl3_gemv` launches (3.0x); routed only 213 us vs 675 us (3.2x).

Reading the table:

- The separate-launch baseline is far below m2's 198-230 GB/s because the per-rank expert matrices are small: a gate / up
  GEMV at TP=2 has N = 1152, only 9 blocks of 128 columns for the GB10's 48 SMs, and every `matmul_exl3_gemv` launch is
  two kernels (input rotation + GEMV), so 36-42 launches a token. The grouped kernel runs one grid over every
  (expert, column block, K split) and reaches the m2 GEMV's bandwidth on matrices 4-10x smaller.
- 40 MoE layers x 257 us = 10.3 ms a token a rank for the routed + shared experts, a ~97 tok/s ceiling from the MoE alone
  (attention, router, all-reduce excluded).
- Prefill is optimistic: the 64-expert pool gives 48 / 192 rows per routed expert, where real routing over 384 experts
  gives about 8 at T = 512 and 32 at T = 2048 (fewer rows per decoded tile, closer to the decode kernel's cost per row).
  A `BENCH_POOL=384` rerun needs a fresh tensor extraction (the subset holds 64 + 6 layer-3 experts). The prompt kernel is
  decode-bound (trellis decode per 16x16 tile shared by 2 member tiles), not bandwidth-bound.

## Sharding rules (EXL3 at load)

`W = diag(suh) H_K W_q H_N diag(svh)` with `H` block-diagonal in 128-point blocks and every 16x16 tile of `W_q` its own bit
stream, so a cut of K or N at a multiple of 128 cuts nothing else: the slice is again an EXL3 layer (its trellis tiles and
its part of suh / svh). `exl3::shard_ranges` / `Exl3::load`:

| Axis | Splits | Legal when | DSv4.1 at TP=2 |
|---|---|---|---|
| `ShardAxis::Rows` (column-parallel, outputs) | checkpoint N | N / world is a multiple of 128 | w1 / w3: 2304 -> 2 x 1152 = 2 x 9 x 128 |
| `ShardAxis::Cols` (row-parallel, inputs; partial sums) | checkpoint K | K / world is a multiple of 128 | w2: 2304 -> 2 x 1152 |
| `ShardAxis::RowGroups` | | refused (no EXL3 checkpoint fuses projections into one trellis) | |

Everything else is refused with the tensor's name, its [K, N], the axis and the rule. Every EXL3 tensor of the Mia
checkpoint passes on both axes at TP=2 (checked over `quantization_config.json`). Experts: `exl3_moe::load` keeps rank
r's intermediate columns of every expert (w1 / w3 by N, w2 by K), so each rank's MoE output is a partial sum for the
row-parallel all-reduce.

CPU parity (`raw/endor-cpu-shard-parity.log`): column slices side by side are bitwise the whole output; row-parallel
partials summed are within 4.8e-7 (|y| <= 5.6) at the DSv4.1 expert shapes, 7.6e-6 at |y| = 86; f64 shard reassembly
(`exl3::tests::shards_reassemble_the_whole_layer`, TP 2 / 3 / 6) within 1e-12 relative.

TensorFold's grouped EXL3 expert kernels as BertholomusAI's DeepSeek-V4.1 fork extends them:
`https://github.com/bertholomus/TensorFold`, branch `deepseek-v41-tp2` @ `af26d42b1f618e9e653903a6c043448b52729c64`,
`src/tensorfold/cuda/exl3/{experts_grouped.cuh, experts.cu}` (Apache-2.0). The pinned family branch `deepseek-v41-zig` @
`629c524a` launches the cubin built from those sources (`zig/src/families/dsv41/exl3_experts.zig`) and holds no copy of
them; its documented launch sequence is the one ported. The local MIT tree (`/opt/code/TensorFold/src/tensorfold/cuda/exl3/`,
fork of `jkuepker/TensorFold`) predates the DSv4.1 grouped decode kernel. Notice: `kernels/cuda/NOTICE-tensorfold` (with
the fork's NOTICE verbatim) and `LICENSES/Apache-2.0-TensorFold.txt`; changes listed in the header of
`kernels/cuda/exl3_moe.cuh` (torch-free ik ABI, arena + offset table instead of pointer arrays, device-side codebook and
width dispatch, NaN instead of `__trap`, no PDL / readiness flags / L2 discards, bf16 / f16 / f32 output).

## What the DSv4.1 graph needs to call

The kernel serves `Op::MoeExperts` with an i16 arena at input 3 (`quant::exl3_moe`):

```text
let ex = quant::exl3_moe::load(backend, src, &names, 5120, 2304, rank, world, cfg.swiglu_limit)?;
// names: [layers.{l}.ffn.experts.{x}.{w1,w3,w2}] for x in 0..384, then [layers.{l}.ffn.shared_experts.{w1,w3,w2}]
inputs = [x [T,5120], ids [T,7] i32 (6 routed ids from MoeRoute + 384 for the shared slot), weights [T,7] f32
          (route weights incl. routed_scaling_factor, then 1.0), ex.gate_up_w, ex.gate_up_s, ex.down_w, ex.down_s, ex.gscales]
OpCall::new(Op::MoeExperts, inputs, [out [T,5120]], OpAttrs { top_k: 7, .. })   // selects moe_experts_exl3 on CUDA
```

The merged skeleton (`dsv41/plan`, `crates/intarsia-core/src/dsv41/graph.rs` `moe_routed`) instead emits
`Op::MoeExpertsExl3` (13 inputs, stacked per projection, cpu stub) and runs the shared expert as `MatmulExl3` +
`SiluGluClamp` + `MatmulExl3`. Two ways to connect:

- (a) recommended: the graph emits `MoeExperts` as above. One launch for routed + shared: the shared slot adds 44 us
  (257 vs 213 us), where its three separate GEMVs add 108 us (783.7 vs 675.1) plus the `SiluGluClamp` launch, so about
  65-75 us more a layer, 2.6-3 ms a token over 40 layers. The shared
  expert is clamped at `swiglu_limit` like the routed ones (`graph.rs:539`), so one clamp a call is exact; its weight is
  1.0 (not scaled by `routed_scaling_factor`). The NVFP4 fusion chain (`fusion.rs`: `MoeTopk, MoeExperts, MatmulNvfp4Glu,
  SharedDownCombine`) cannot match this graph (it uses `MoeRoute` and `MatmulExl3`).
- (b) bind the kernel to `Op::MoeExpertsExl3`: the stacked inputs map onto the kernel with a per-projection descriptor
  instead of the arena table (an adapter was drafted in this lane, uncommitted, at
  `/opt/code/intarsiaml/.worktrees/dsv41-cuda-moe/.scratch/moe-experts-exl3-op-attempt.patch`; it needs the CUDA tests
  reworked and every GPU gate rerun).
