# Lane hsjf: why the short prompt waits with `herd` + `sjf` both on (2026-11-17)

Branch `hsjf` from `origin/main` `cc7c8026c`. Verdict: **not a scheduler gap, no engine code changed, nothing default-on.** The short prompt in mflip's cell 1 had no KV slot, not a bad
rank. Two cpu tests pin both halves (the mechanism, and that with a free slot sjf does overtake the herd leader).

## 1. The mechanism

mflip cell 1 (docs/results/2026-11-17-mflip.md, PR #430): `--max-batch 8`, 8 herd prompts at t=0 plus one 1000-token prompt at +2 s. That is **9 requests for 8 slots**.

* Admission is FIFO and takes a free slot or everybody waits (`Scheduler::step`, phase 2, crates/intarsia-core/src/scheduler.rs:1203-1206, `pick_slot` of the queue head). Nothing is preempted. The
  eight herd requests (admitted at t=0) hold all eight slots, so the short prompt sits in `waiting` and is never an `Active`, so `prefill_ranking` (scheduler.rs:1695) and `prefill_pick`
  (scheduler.rs:1734) never see it.
* It is admitted when the first herd request finishes decoding (48 tokens, `burst.py --max-tokens` default), then prefills its 1000 tokens at once: sjf ranks it first (fewest tokens left,
  scheduler.rs:1696-1706) and herd does not hold it (its prompt shares no `min_tokens` prefix with anyone, so `herd_held`, scheduler.rs:1777-1790, is false).
* Evidence from mflip's own raw (`docs/results/2026-11-17-hsjf/raw/mflip-mix-admission-check.txt`, from `mix-35b-off-mb8/results.jsonl`), absolute seconds from t=0: in all 8 on-arm bursts the
  short prompt's first token comes **0.38 to 0.41 s after the first herd request ended** (e.g. B1 seed 1: first herd end 6.22, short first token 6.61; B3 seed 1: 5.94 / 6.32), which is the
  1K prefill time, and **after** every herd first token (herd TTFTs 3.5 to 5.7 s). With no free slot before 5.9 s there was no way to run earlier.
* The "4.7 s equals the herd leader's 4.8 s" match is a coincidence of units: the short prompt's TTFT is counted from its own submit at +2 s, so 4.7 s is 6.7 s absolute; the herd's last TTFT
  4.8 s is absolute from t=0. The 2 s stagger is about the 48-token decode that frees the first slot. Ruled out: a herd-leader priority (none in `prefill_ranking`/`prefill_pick`; `herd_held`
  only passes over followers, and only holds a request that shares a prefix with an older one), leader remaining-length ranking, follower counting, store chunking (one chunk per iteration
  with both on; the ranking still chooses it), `intarsia_batch_prefill_reordered_total` was 0 in both arms because the short prompt never co-prefilled with another request.
* Off arm: the short prompt is admitted at the first free slot too (10.7 to 13.0 s) but then prefills last under fifo (youngest), so 24-28 s.

sjf-alone cell (mherd): 40K + 1K at `--max-batch 4`: two requests, slots free, so the short prompt is an `Active` at once and is ranked first (0.75-1.6 s). Same code path, different slot situation.

## 2. cpu tests (`crates/intarsia-core/tests/herd.rs`, mock model, 4 herd prompts of 320 shared + 8 own tokens, short 20-token unrelated prompt submitted at iteration 6)

First-token iteration per request (short last):

| slots | herd | order | herd requests | short |
|---|---|---|---|---|
| 5 | on | fifo | see test (leader first at 40) | after the leader (asserted `>`) |
| 5 | on | shortest | 46 / 43 / 44 / 45 | **8** (before the leader's first token, asserted `<`; within `short_at + 6`) |
| 4 | on | shortest | 43 / 40 / 41 / 42 | **47** (after the first herd request ended at 44; asserted) |

* `herd_and_shortest_short_prompt_overtakes_the_leader`: with a free slot, both on: the short prompt overtakes the herd leader (first token 8 vs 46); herd + fifo leaves it behind the
  leader; every reply equals the herd-off fifo reply.
* `herd_and_shortest_short_prompt_waits_for_a_slot_when_the_herd_fills_them`: slots = herd size: the short prompt's first token follows the first herd request's last token and the leader's first
  token; the same run with one more slot overtakes; the two runs' replies are equal.
* Existing guarantees untouched (no code changed): `herd_followers_stay_held_under_shortest`, the aging-bound and randomized ids tests in tests/scheduler.rs.

## 3. Gates

* cpu: `cargo test -p intarsia-core --test herd`: 11 / 11 pass (9 existing + 2 new). No `crates/` source changed, so with both env vars unset behaviour is unchanged by construction.
* Hardware: **not run.** The brief asks for it only if code changed. It would be one mflip cell 1 repeat at `--max-batch 16` (expected: short TTFT about 0.4 to 1.6 s, as sjf alone); not queued (fleet busy: lanes mcopym and flipev, spark2 `quiet gpu,cpu` job overdue).

## 4. What to do about it (not done)

* Operational: run with `--max-batch` above the expected concurrent herd size plus the short-prompt traffic. That is the existing slot capacity limit, not herd/sjf specific.
* A real change would be preempting a decoding or prefilling request for a short arrival, or letting a held follower give up its slot. Both are large (state swap, ids risk) and out of scope; not proposed here.

Revert: nothing to revert (tests and docs only).
