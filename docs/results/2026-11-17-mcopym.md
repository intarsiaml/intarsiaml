# mcopym: copy drafts beside the MTP head on Metal (Qwen3.6-35B-A3B NVFP4, endor)

Lane `mcopym`, branch `mcopym` from the mcopy2 head (`205b11506`, PR #429). Opt-in only: `INTARSIA_SPEC_COPY=<n>[,<len>]`, off by default, nothing new is default-on.
Measured on endor (Apple M5 Max, macOS 27.0), `Qwen3.6-35B-A3B-NVFP4`, tp 1, `--spec mtp --spec-k 2` (the Metal default), every run in a `fleetq` slot
(`--quiet gpu,cpu`). Raw output: `docs/results/2026-11-17-mcopym/raw/`; scripts: `scripts/mcopym/` (the cells and the table script are mcopy's, `scripts/mcopy/`).

## Summary

- **Does it run on Metal as is? No, one refusal, then yes.** `crates/intarsia-models/src/load.rs:1032-1039` refused `INTARSIA_SPEC_COPY` on any backend but CUDA / cpu. That is the only
  CUDA-only piece: with `metal` let through (the whole code change, 3 lines), the engine paths (`propose_copy`, `Seq::plan_step`, `copy_pass`, `copy_backoff`, `copy_behind`) run unchanged, the chains fire and the
  verify rows are bitwise the decode steps.
- **Length cap on Metal: `len` 7 (8-row verify passes) is the maximum, and it is the default (`COPY_LEN_DEFAULT = 7`), so CUDA's `n20` and `n20,7` are the same arm here.**
  `INTARSIA_SPEC_COPY=20,15` fails the load of the plan dry-run: `no kernel for attn_prefill on metal/applegpu_g17s (m=9 ...) [row-exact verify kernels only] ... needed by Verify t=10 ... t=16`
  (`raw/plan/new-n20L15.err`). The cause is `ROWS_MAX = 8` of the rows-exact verify attention (`crates/intarsia-backend-metal/src/attn.rs:429`, used by `rows_ok` at :433, `rows_scratch` at :438 and
  `launch_attn_rows` at :463). Everything else the verify pass needs takes 16 rows (`CHUNK_ROWS_MAX = 16`, the multi-row GEMVs, `lib.rs:239`; the MoE expert-grouped kernels take 8 and chunk above, `moe.rs:82`). See "What 9 to 16 rows would take".
- **Gate (a), greedy ids equal `--spec off`: PASS, 25 of 25** (`generate`, 5 cells x arms mtp / n20 / n20,7 / n12 / n4; `raw/ids-gate.txt`). Served replies of every copy arm have the same sha as the base arm's in every A/B and diagnostic round (no `IDS DIFFER`).
- **Gate (b), knob unset = main: PASS.** `plan show --json` (Metal, 35B, `--spec mtp --spec-k 2`, `--max-seq 8192`) of the base build (`205b11506`) and this branch: 13188 bytes, byte-identical (sha a3bb4203...), the base twice also identical. Greedy `mtp` ids of this branch equal `--spec off` (same gate, arm `mtp`).
- **Gate (c), speed: the copy-heavy cells gain more than on CUDA in relative terms and the controls are flat.** n20 (4 ABBA rounds x 3 reps): copy3k **1.747x**, json-xform **1.537x**, agent-edit **1.195x**, agent-batch **1.050x**,
  chat-short 1.006x, reason 0.984x, code-gen 0.983x. The two low control cells are one bad round each (below) plus a clean diagnostic that finds no cost of the knob.
- **code-gen: no persistent post-chain slowdown on Metal.** In the diagnostic, fresh servers, n20 (which fires 3 to 7 chain passes in its code-gen / reason / chat-short run) is 1.012x of base and n256 (the knob on, no chain ever fires) 0.991x:
  indistinguishable from each other and from base. The 0.2 to 0.3 ms per MTP step (+1.2 to 1.8 %) that CUDA pays after its first chain pass is not there to the resolution of this run (about 1 %). A clue for the CUDA cause: Metal's MTP step is not a captured graph
  (eager, the pipelined step of lane mmtp, `Backend::supports_graphs` is the default `false` for Metal), CUDA's is. That fits suspects (a) and (b) of mcopy2 (graph-specific state after the rollback of a chain pass) and not a cost in `propose_copy`, the
  back-off or the accounting, which Metal shares. Not proven: no CUDA run with graphs off here.

## What changed

1. `crates/intarsia-models/src/load.rs`: the `INTARSIA_SPEC_COPY` load check accepts `metal` (message: "on the cuda or metal backend"). Still refused with `--max-batch` above 1 and at tp > 1.
2. `docs/tuning.md`: the `INTARSIA_SPEC_COPY` row says Metal works, `len` at most 7, and why.
3. `scripts/mcopym/`: `build.sh` (base from `git archive` and this tree, one target dir), `plan.sh`, `ids.sh`, `ab.sh`, `lib.sh` (Metal versions of mcopy's scripts, thermal level logged per cell).

No engine, spec or kernel change. The 8-row verify on Metal was already exact: `Registry::select` gives the verify pass the rows-exact kernels up to 8 rows (`multirow.rs`, `kernels.rs`).

## Method

- Binaries: `target/intarsia-base` (`git archive 205b11506`, with the knob refused on Metal) and `target/intarsia-new` (this tree), `cargo build --release -p intarsia-cli --features metal`. (First build of `new` reused a stale `intarsia-models` artifact because the target dir was cloned from another worktree; caught by the missing message string, cleaned and rebuilt: `raw/build3.log`.)
- Gate (a): `scripts/mcopym/ids.sh`, `generate --chat --no-think --temperature 0 --show-ids` against `--spec off`; cells with a single user message (copy3k 2902 ids, json-xform 2600, code-gen 500, reason 500, chat-short 389), arms `mtp` (knob unset), `copy=20`, `copy=20,7`, `copy=12`, `copy=4` (`INTARSIA_SPEC_TRACE=1` to count chains). The agent cells are multi-message, so only the served sha check covers them.
- Gate (c): `scripts/mcopym/ab.sh`, `serve --max-batch 1 --max-seq 8192 --spec mtp --spec-k 2`, one fresh server per arm and round, the arm order reversed on even rounds, 3 reps per cell, the seven cells of mcopy2 (`scripts/mcopy/prompts.py`, `cell.py`: streaming, greedy, per-round nonce in the first user message, decode tok/s = (completion tokens - 1) / time after the first token), a warm-up request per server, `notifyutil` thermal level before and after each cell (`raw/ab-run-r*.log`), cooling to level 0 (at most 120 s) before every server start.
  Arms: `base` (knob unset), `n20` (`INTARSIA_SPEC_COPY=20`, len 7), `n12`. Ratio = median over rounds of the round's median tok/s ratio. Thermal levels were 0 to 2 (never above), the base arm ran as warm as the others (it reached level 2 in every round, n20 and n12 in most; `raw/ab-run-r*.log`).
  The diagnostic (`raw/diag/`): fresh servers, cells `code-gen reason chat-short` only, 5 reps, 3 rounds, arms base / n256 / n20.

## What 9 to 16 rows would take (not done: step 4, no new kernels)

`len` 15 on CUDA gives +18 % over len 7 on copy3k (2.06x against 1.75x). On Metal the 8 to 15 token chains fail at load because `rows_ok` (`attn.rs:433`) returns false above 8 rows, so the plan has no `attn_prefill` kernel for `Verify t=10..16`.
Two ways, neither measured here:
- **Smallest, no kernel:** accept 9..=16 rows in `rows_ok` and let `launch_attn_rows` fall through to its existing path for a row count it cannot take (`attn.rs:463-480`), which already runs one `AttnDecode` launch per row (bitwise by construction, as HIP's `verify_attn_per_row`). Costs `rows` attention launches per full-attention layer (10 layers of the 35B) for the 9..16-row passes only. Roughly 10 lines plus the scratch rule (`rows_scratch` clamps at `ROWS_MAX`); the MoE side chunks above 8 rows already (`moe.rs:76-82`). Needs a `tests/rows_exact.rs`-style bitwise check at 9..16 rows and the ids gate again.
- **Proper:** raise `ROWS_MAX` to 16 for the multi-row kernel `attn_rows_splitkv_t` (`kernels/metal/attention_splitkv.metal:342`). Its row count is a runtime argument (`p.s0`), so this may be a constant, the scratch slabs (`R x N x max_split x (D + 2)` floats) and a bitwise test, but the register / threadgroup budget at 16 rows was not looked at. Unknown size until built.
Neither changes anything with the knob unset. The speed benefit at 16 rows on Metal is unmeasured; CUDA's came partly from the per-row GatedDeltaNet loop being exact at 9 to 16 rows, which was not examined on Metal.

## Not done / unverified

- `len` above 7 (refused at load, above). Sampled requests, thinking mode, the batching engine (`--max-batch` above 1: refused at load), tp > 1, 16k-context speed cells, real agent transcripts, n above 20. `--prefix-store on` with copy drafts was never exercised (as on CUDA).
- Gate (a) through `serve` was checked by reply sha against the base arm, not against a served `--spec off` arm (no `off` arm in the Metal A/B); the `--spec off` comparison is the `generate` gate.
- The agent cells have no `generate` ids check (multi-message cells).
- The `INTARSIA_SPEC_COPY` unit tests are cpu-only and unchanged; `raw/cargo-test.log` has the run of the docs drift test and the cpu copy identity test on this tree.
- endor ran lane `mflip` beside the first part of this lane's queue, not during the runs (`--quiet gpu,cpu`); the standing services (kev, tensorfold) were up.
- Commits are signed `Co-Authored-By: Claude Sonnet 5.5` (the model that did the work), not the `Opus 5.5` line in `scan/lane-rules.md`.
