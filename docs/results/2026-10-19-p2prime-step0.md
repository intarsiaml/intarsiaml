# P2' step 0: a v3 consumer with no ordering is killed on hardware, 2026-10-19

Branch `perf/p2prime-step0` on origin/main `d416f53b`, not pushed. HIP only (tatooine, 2x R9700 gfx1201). No default changed:
v3 stays opt-in (`INTARSIA_HIP_MOE_V3=1`), and P2' is not built.

## Headline: outcome A

**`v3-noorder` is killed.** It removes the fence and every other consumer-side acquire.

- **Runs:** 9 of 9 full `moe_v3` runs fail. Both sentinel stress tests fail in each run.
- **Where:** all three `PRE` instances (`INTARSIA_HIP_MOE_PRE` 4 / 1 / 2) and both GPUs.
- **Occupancy settings:** with and without the side stream.
- **What fails:** 2755 / 8640 launches of `v3_sentinel_stress`, the existing test, unchanged, and 5541 / 12960 of the new
  `v3_sentinel_stress_narrow`.
- **Stale reads:** every differing launch carries NaN outputs. With the h scratch poisoned before every launch, that means the
  sentinel was read.

**Gate:** the kill is enough for P2' to proceed, and for v3-as-default to be reconsidered. Both are decisions for the user, and
nothing here changes either.

**The unmutated v3 passes:** 16 of 16 full runs, 0 differing launches:

| test | launches |
|---|---|
| `v3_sentinel_stress` | 15 360 |
| `v3_sentinel_stress_narrow` | 23 040 |

**What the test proves, and what it doesn't.** On gfx1201, the sentinel stress tests see a stale h read whenever no wave of the
consumer block invalidates its near cache after the wait. That is the case for `noorder` and `nobaracq`: every run fails, with
NaN. They see none while any per-wave invalidate is left: `nofence`, `nospinacq`, `fenceonly` and the base all pass. So the test
detects a missing per-wave acquire. It does **not** show:

- that the agent-scope fence is needed on this ISA. `v3-nofence` still survives, and is equivalent here (section 1).
- that the remaining ordering is enough at every occupancy. In particular, at T = 2 even `noorder` was never caught (section 4).

## 1. ISA evidence (`raw/isa/`, `hipcc -O3 --offload-arch=gfx1201 -S` of `kernels/hip/moe.hip`)

The down role's wait in `moe_experts_p1_v3_kernel<4>` (the default `PRE`), from the base tree (`raw/isa/base_wait_excerpt.s`):

```
	global_load_b32 v45, v44, s[28:29] scope:SCOPE_DEV     ; thread 0: acquire load of sync[0], first try
	s_wait_loadcnt 0x0
	global_inv scope:SCOPE_DEV                             ; (a) the spin's acquire: thread 0's wave only
	...
.LBB_138:                                                  ; spin
	s_sleep 1
	global_load_b32 v45, v44, s[28:29] scope:SCOPE_DEV
	s_wait_loadcnt 0x0
	global_inv scope:SCOPE_DEV                             ; (a) after every load, so also after the one that sees NG
	...
	s_wait_loadcnt_dscnt 0x0                               ; __syncthreads() release half (LDS lut, pre-reads complete)
	s_barrier_signal -1
	s_barrier_wait -1
	global_inv scope:SCOPE_SE                              ; (b) __syncthreads() acquire half: every wave
	s_wait_loadcnt 0x0
	global_inv scope:SCOPE_DEV                             ; (c) __builtin_amdgcn_fence(acquire, "agent"): every wave
	...                                                    ; then the h reads: plain global_load_b128 ... off (default scope)
```

Three instructions on the consumer side order the h reads after the producers' stores:

- **(a)** the spin load's acquire. It runs in thread 0's wave only, after each load of the counter.
- **(b)** the barrier's workgroup acquire. It runs in every wave.
- **(c)** the fence. It runs in every wave.

The pre-read seam (`PREREAD`) loads the same h lines with the same plain `global_load_b128` before the wait. Its loads sit at
lines 1136 to 1232 of the base `<4>` body (`raw/isa/base.k4.s`), and the real reads come after the barrier, from line 1314
(line 1311 in `v3-noorder.k4.s`).

**Mutants and their ISA diffs** (`raw/isa/<mutant>.k{1,2,4}.diff`; labels renumbered, so the diffs show only the real changes):

| mutant | source change (`scripts/hip-decode/mutate.py`) | instructions removed in `<4>` | `<1>` / `<2>` |
|---|---|---|---|
| `v3-nofence` (existing) | fence line dropped | (c): `s_wait_loadcnt 0x0; global_inv scope:SCOPE_DEV` | same |
| **`v3-noorder`** | spin load `RELAXED`; `__syncthreads()` + fence replaced by a workgroup release fence, `s_barrier`, and a compiler-only `asm volatile("" ::: "memory")` | (a) both `global_inv scope:SCOPE_DEV`, (b) `global_inv scope:SCOPE_SE`, (c) both instructions | same |
| `v3-nobaracq` | `__syncthreads()` + fence replaced as above, spin kept | (b), (c) | same |
| `v3-nospinacq` | spin `RELAXED`, fence dropped, `__syncthreads()` kept | (a), (c) | same |
| `v3-fenceonly` (control) | spin `RELAXED`, barrier without acquire, fence kept | (a), (b); (c)'s `global_inv scope:SCOPE_DEV` stays | same |

`v3-noorder`'s wait after the change (`raw/isa/noorder_wait_excerpt.s`):

```
	global_load_b32 v45, v44, s[28:29] scope:SCOPE_DEV
	s_wait_loadcnt 0x0
	...                                                    ; spin: s_sleep 1, the load, s_wait_loadcnt, no global_inv
	s_wait_loadcnt_dscnt 0x0
	s_barrier_signal -1
	s_barrier_wait -1
	;;#ASMSTART                                            ; compiler-only fence
	;;#ASMEND
	...                                                    ; h reads, still below the barrier
```

- The barrier is still there in every mutant (`s_barrier_signal/wait`), and so is the release-side `s_wait_loadcnt_dscnt`. The
  LDS `lut` therefore stays race-free.
- The compiler-only fence keeps the h reads below the barrier. So a stale value is the hardware's L0 / near cache, not
  instruction reordering.
- The only `global_inv` left in `noorder`'s down path before the h reads is the ticket barrier's `global_inv scope:SCOPE_SE`
  (line 51). It runs before the pre-read.

**Each mutant's patterns match exactly once.** `noorder`, `nospinacq` and `fenceonly` edit two adjacent statements of the same
wait: the spin line and the barrier/fence pair. All 138 `mutate.py` mutations apply on this tree (134 before, plus 4 new),
checked on the Mac.

**Why `v3-nofence` cannot be killed here** (the explanation from phase 1, now confirmed by the 2 x 2 below): removing (c)
leaves (b). Every wave still runs `global_inv scope:SCOPE_SE` after the barrier, and on hardware that refresh is enough.

**Other blocks' invalidates (caveat).** The producer side is unchanged in every mutant (`raw/isa/base_producer_excerpt.s`). After
its h store (`global_store_b16`), a gate_up role runs:

1. `__threadfence()`: `s_wait_storecnt 0; global_inv scope:SCOPE_DEV`;
2. its barrier: `global_inv scope:SCOPE_SE`;
3. the release add.

Those invalidates act on the caches of the CU the gate_up role runs on. So a down block that shares that CU is refreshed by
someone else's instructions. This is one plausible reason why T = 2 grids never show the stale read (section 4). It is inferred,
not measured.

- **Which tests fail.** In every killed run exactly the two stress tests fail: "4 passed; 2 failed", with panics at
  `moe_v3.rs:244` and `:269`. The bitwise, counter-reset, last-role-late and graph-replay tests pass even for `noorder`. Without
  the `PREREAD` seam and the sentinel, the stale read was not observed.
- **Reading the 2 x 2** (fence gone in all four rows): a per-wave invalidate after the wait is what matters on this hardware.
  - Either (b) or (c) alone is enough (`nospinacq`, `fenceonly`).
  - (a) alone is not (`nobaracq`). It runs in thread 0's wave only.
  - **Do not read this as "per wave" proof.** (a) invalidates the caches of thread 0's CU. With 8 waves per block, in WGP mode,
    some waves may sit on the WGP's other CU. So `nobaracq` can fail for those waves only. The data does not say which waves read
    stale.
- The earlier verdict "`v3-nofence` survives" (phase 1, 0 / 4800) carries over: 0 / 7200 stress launches here.

## 3. Test changes (`crates/intarsia-backend-hip/tests/moe_v3.rs`)

- **`v3_sentinel_stress` itself is unchanged in behaviour:**
  - same seed (55), same draws, same launch order;
  - `SKEW_ALL` with skew 0 / 2 / 6, plus the side instance on stream 1.
- **Shared helper.** Its body moved into a helper, `sentinel_stress(be, &Stress, rounds)`. The helper now prints one tally line
  per shape: per skew, the launches that differ and how many of them carry NaN.
- **New: `v3_sentinel_stress_narrow`.** Only the last gate_up role is late (`SKEW` without `SKEW_ALL`, at 0 / 20 / 40, up to about
  0.15 ms). So one store lands late, and only one CU gets the producer's invalidates afterwards. It runs in two occupancy
  settings:
  - without the side stream (seed 56);
  - with it (seed 57).

  Same `PREREAD`, the same sentinel before every launch, and every launch compared bitwise with v2.
- **No kernel change.** The test uses the existing default-off seams (`INTARSIA_HIP_MOE_V3_SKEW`, `_SKEW_ALL`, `_PREREAD`).
- **Deterministic:** fixed seeds, and bitwise comparison with v2. The base passes 16 / 16 runs.

On this hardware the existing test already kills `noorder`. The narrow test adds the "no side stream" setting and kills it in
the same shapes. Neither test kills `v3-nofence`.

## 4. Where the kill happens (occupancy settings; `raw/logs/w1-summary.txt`, `w2-summary-pre{1,2}.txt`)

Per shape, for `noorder` (and `nobaracq`, which behaves the same), each cell is 120 launches per run:

| shape (t, e, k, h, i) | blocks (NG + ND) | `all-late` skew 2 / 6 | `last-late` skew 20 / 40 (side and no side) | skew 0 |
|---|---|---|---|---|
| 1, 256, 8, 2048, 512 (35B, T = 1) | 512 + 256 | 120 / 120 every run | 120 / 120 every run | 1 to 17 at PRE 4, 120 at PRE 1 and 2 |
| 1, 64, 8, 1024, 256 | 256 + 128 | 120 / 120 | 120 / 120 | 0 to 12 |
| 1, 16, 2, 256, 16 | 4 + 32 | 120 / 120 | 120 / 120 | 81 to 120 |
| 2, 256, 8, 2048, 512 (35B, T = 2) | 1024 + 512 | **0** | **0** | 0 |
| stream 1 side instance (T = 2) | 1024 + 512 | 0 | 0 | 0 |

**Every T = 1 launch with a skew is caught, and no T = 2 launch is caught.**

- A T = 2 grid (1536 blocks) is probably more than the part holds at once. So down blocks wait beside still-running gate_up blocks,
  whose invalidates (section 1) refresh shared CUs.
- That is a hypothesis. It was not measured: no occupancy counters, no per-wave data.

**Consequence for P2'.** P2' has more edges, including at T > 1 in verify. Its test must cover the T = 1-like case, where the
consumers wait alone, for every edge: it cannot rely on large grids to expose a missing acquire.

## 7. Caveats

- **Seams make the kill possible.** The kill relies on the default-off seams: `PREREAD`, which puts the h lines in the consumer's
  caches before the wait, and skew. Without them, `noorder` passed the other four `moe_v3` tests. So "killed" means the test
  harness can make the stale read happen. It does not mean the production decode would show it at a measurable rate.
- **Hardware facts are inferred.** The cache-level statements (which cache `SCOPE_SE` / `SCOPE_DEV` invalidate, waves split across
  the CUs of a WGP) come from the ISA and the LLVM AMDGPU memory model, not from an AMD hardware document.
- **Only the consumer side was mutated.** Producer-side ordering (`__threadfence()`, the release add) was not mutated in this task.
- **Run counts.** 3 runs per mutant and setting, 16 for the base. The kills are not marginal: every T = 1 skewed cell fails 120 /
  120 in every run. Survival is 0 differing launches over 7200 per surviving mutant.
- **Mac checks** on this branch (`raw/logs/mac-checks.log`):
  - `cargo test --workspace`: 103 test binaries, all `ok`, exit 0;
  - `cargo check --workspace --features hip`: exit 0. On the Mac `ik_hip` is off, so the HIP test file compiles only on tatooine,
    where it built.
