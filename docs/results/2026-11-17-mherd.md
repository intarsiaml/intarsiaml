# Lane mherd: do `herd` and `sjf` work on Metal? (2026-11-17)

Branch `mherd` from `origin/main` `36f21e2ea` (contains #424 herd and #425 sjf). Validation lane: **no engine code changed**. Machine: endor (M5 Max, Metal), every build and served run through fleetq on
endor (`--quiet gpu,cpu`; jobs #9912 probe, #9913/#9916 herd, #9918 sjf, #9920 27B). Raw output `docs/results/2026-11-17-mherd/raw/`, scripts `scripts/mherd/` (`lib.sh`, `herd.sh`, `sjf.sh`, `ids27.sh`,
`sjf_pair.py`, `analyze.py`; the herd client is `scripts/herd/herd_bench.py`). Nothing becomes default-on; both stay opt-in.

## 1. Verdict

**Both work on Metal, with no code change, and give the same kind of gain as on CUDA; every generated id equals the reference.**

* **herd** (`INTARSIA_PREFIX_HERD=1`), Qwen3.6-35B-A3B-NVFP4, 8 requests behind a barrier, one new 16448-token shared prefix + 200 own tokens each (the CUDA gate's full size): TTFT sum **121.7 -> 32.1 s (-74 %)**,
  last TTFT **27.0 -> 4.5 s (-83 %)**, wall **27.6 -> 6.2 s (-78 %)**; n = 8 cells per arm, 8 visits in ABBA ABBA order, every cell inside +/-12 % of its arm's mean. CUDA on a Spark: 108.3 -> 27.3 s, 24.0 -> 3.97 s.
  Ids: **256 / 256 replies equal** the store-on solo reply of the same prompt (0 errors). No-regression cell (8 unrelated 8192-token prompts): 65.8 vs 62.0 s TTFT sum, inside the cell-to-cell spread (60.0-71.5 s).
* **sjf** (`INTARSIA_PREFILL_ORDER=shortest`), 35B, a 1000-token prompt arriving 2 s into a 40000-token prefill (`--max-batch 4`): short TTFT **9.97 -> 1.64 s (-84 %)**, long TTFT 11.72 -> 11.97 s (**+0.25 s, +2.1 %**,
  inside this Mac's run noise; see 4.2). Ids: **64 / 64 replies equal** (pair and solo cells, both arms, vs the fifo-arm solo reply; shortest pair cells equal the fifo pair cells 4 / 4).
* 27B (ids only, scaled, section 5): herd 32 / 32 replies equal (on: TTFT sum 121.8 -> 63.2 s, one cell per arm); sjf 8 / 8 replies equal (short TTFT 13.6 -> 3.4 s, one cell per arm).
* Metal difference worth knowing: sjf's short prompt gets its first token in 1.6 s, not the 0.24 s it takes alone (4.2), and its remaining 47 tokens still decode beside the long prompt's chunks, so the short's *end-to-end* time
  improves only about 0.5 s (10.6 -> 10.1 s mean) while its TTFT improves 8 s. On CUDA the short's TTFT was 0.64 s.

## 2. Reachability: both features run on the Metal `serve` path (code read, no code change needed)

Metal `serve --max-batch N` builds the same `BatchedEngine` as CUDA / HIP; the scheduler and the prefix store are backend-neutral Rust in `intarsia-core`. Nothing in the herd / sjf path is gated on a backend.

* Same engine and scheduler: `crates/intarsia-models/src/load.rs:1188` (`BatchedEngine::new`) for every backend with `--max-batch > 1` (Metal 2..=16, 35B recipe cap 8); the batched engine drives `intarsia_core::scheduler::Scheduler`
  (`crates/intarsia-core/src/scheduler.rs:914`). No `cfg(feature = "cuda"/"metal")` anywhere in `scheduler.rs`, `engine/batch.rs` or `prefix_store.rs` (the only `cfg` in the scheduler is `fault-inject`, `scheduler.rs:942-984, 1555`).
* **sjf**: env read in `engine/batch.rs:153` (`INTARSIA_PREFILL_ORDER`), `:195` (`INTARSIA_PREFILL_AGE`); config `scheduler.rs:422-451`; the choice is `prefill_ranking` / `pick_prefill` (`scheduler.rs:1694, 1715`) at step 4
  of `step` (`scheduler.rs:1312`). Pure ordering over the `Phase::Prefilling` list: backend independent.
* **herd**: env read `engine/batch.rs:209` (`INTARSIA_PREFIX_HERD`), announce `:1199-1205`; `prefill_pick` / `herd_held` (`scheduler.rs:1734, 1777`); the follower's second store lookup is `BatchSeq::herd_resume`
  (`engine/batch.rs:822`), which calls the same `SeqStore::restore` as admission. The store is `prefix_store.rs` (the Metal 35B served it before: `INTARSIA_MTP_STORE` defaults on for `metal`, `spec.rs:258`).
* What gates the **combination** on any backend (`store_combinations`, `engine/batch.rs:1280-1300`): the store with `--max-batch > 1` refuses overlap, `INTARSIA_PACK_PREFILL=1` and `INTARSIA_PREFILL_MACRO`, and turns the recipe's macro
  prefill off. Metal's packed prefill is off by default (`backend.rs:271`, `pack_prefill_default` false except CUDA / HIP), so Metal has none of those. Explicit `--spec` with the store at `--max-batch > 1` is refused
  (`engine/batch.rs:1108-1116`): the runs here use `--spec off`, as the mfp8split gates did. Herd needs `--prefix-store` (`:1205` prints "no effect without --prefix-store").
* Hardware facts seen in the served logs: busy prefill chunk 2048 on the 35B (`load.rs:1172-1185`), `chunk-invariant backend: false` for the store (restores happen at the schedule points, as the 16384 cached tokens show).
* Cost to make either work on Metal: 0 h. Not run on Metal in the CUDA lanes (their docs say "CPU tests only"); this lane is the Metal serve run.

## 3. Method

* Binary: `target/release/intarsia` of this worktree (`cargo build --release -p intarsia-cli --features metal`), identical to origin/main `36f21e2ea` (no source change). One server per visit (the env var is read at startup),
  fresh prefix store per visit, `INTARSIA_CB_NO_REUSE=1` in every arm (no idle-slot prefix reuse, as the sjf ident gate), `--spec off --profile-every 0 --no-supervisor --no-ui`, the thermal level waited to 0 (up to 90 s) before every visit.
* Model `~/models/Qwen3.6-35B-A3B-NVFP4`; 27B `~/models/Qwen3.8-27B-Quark-AWQ-MXFP4`. fleetq `--mem 50` (35B RSS 35-40 GB measured: 34.9 GB without store, 40.4 GB with the store and 17408-token context), `--quiet gpu,cpu`;
  endor-kev and endor-tensorfold stayed up.
* Clients: token-id prompts on `/v1/completions` (the shared prefix is exactly the same ids; the length is exact), temperature 0, `ignore_eos`, 48 tokens, TTFT = client time from the barrier (herd) or from each request's own
  submit (sjf) to the first streamed token.
* **herd gate** (`scripts/mherd/herd.sh`): `serve --max-seq 17408 --max-batch 8 --prefix-store on`, A = herd off, B = `INTARSIA_PREFIX_HERD=1`, visits A1 B1 B2 A2 B3 A3 A4 B4 (ABBA twice). Per visit: warm-up, `herd8` seeds 1 and 2
  (8 at once, a new 16448-token shared prefix + 200 own tokens), `distinct` (8 unrelated 8192-token prompts), `solo` seeds 1 and 2 (the same 8 prompts one at a time, each restoring from the store: 16384 cached).
* **sjf gate** (`scripts/mherd/sjf.sh`): `serve --max-seq 41024 --max-batch 4`, A = fifo, B = `INTARSIA_PREFILL_ORDER=shortest`, the same ABBA ABBA visits. Per visit: warm-up, `pair` seeds 1 and 2 (a 40000-token prompt at t = 0 and a
  1000-token prompt at t = 2 s), then `solo` seeds 1 and 2 (the same two prompts, one after the other).
* **Scaled**: herd and sjf at the full CUDA size on the 35B (Metal prefills the 35B at about 5.3k tokens/s at 8k, so 8 x 16K takes 27 s off and the 40K prefill 11.6 s); nothing scaled there, except 2 seeds per visit instead of 3 and
  no `max-batch 16`. The 27B is far slower (about 0.9-1.3k tokens/s), so its ids-only runs are scaled to 8 x 4160 shared tokens (herd) and 12000 + 1000 tokens (sjf), one seed, one visit per arm (A1 B1, not ABBA).

## 6. Not verified

* 27B: one cell per arm, not ABBA; no 16K-class prompt (scaled to 4K / 12K); timings there are indicative only.
* `--max-batch 16` (27B recipe) with herd or sjf; staggered herd arrivals; herd and sjf together; prefix sizes other than 16448; MTP (`--spec mtp`) with the store plus herd on Metal (every run used `--spec off`, so the
  shipped Metal default engine with the store was not exercised: the store disables the recipe's MTP default, and an explicit `--spec` with the store is refused at `--max-batch > 1`).
* The `herd_*` scheduler counters were not read (the metrics endpoint does not print them in the captured files); herd's effect is shown by cached tokens (16384) and TTFT.
* Busy != solo chunking on Metal (sjf doc, section on other backends) did not show up: shortest and fifo ids equal solo here, at one 40000 + 1000 geometry and 2 seeds.

## 7. Revert

Nothing to revert: no code or default changed. The features stay off unless `INTARSIA_PREFIX_HERD=1` / `INTARSIA_PREFILL_ORDER=shortest` is set.
