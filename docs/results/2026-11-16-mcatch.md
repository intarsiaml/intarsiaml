# mcatch (2026-11-16): the MTP head's catch-up passes of a batched draft, batched across sequences? Stop rule at task 1: findings only

Lane `mcatch`, branch `mcatch`, worktree `.worktrees/mcatch`, from main c60d26caf (#415 mhead merged). Follows `docs/results/2026-11-16-mhead.md` (chained one-row passes batched; the catch-ups left per sequence) and `docs/results/2026-11-16-mdraft.md`.

## Verdict

**No code change. The stop rule of task 1 fires: the all-n = 1 catch-up, the only catch-up shape that can be batched bitwise, is 3.5 % of the 2-stream iterations, so batching it is worth at most 0.014 ms per iteration (bound 0.04 ms even if a whole head pass disappeared; bar 0.15 ms to continue, 0.2 ms to ship). `INTARSIA_BATCHED_CATCHUP` was not added, `docs/tuning.md` is untouched, nothing was built or run on spark2.**
The shapes that carry the iterations are the 2-3-row catch-ups (65.8 %), which cannot be batched with the row-exact twins (below); they are the only follow-up with a ceiling worth a lane, and its device test is named at the end.

## Task 1: the catch-up shapes at 2 streams

A drafting step runs, per sequence, a catch-up pass of the head over the n rows its verify pass left queued, n = accepted + 1 (the drafted ids are the head's own greedy chain: `state.rs:723`, after the verify rollback `pending_rows = keep - pos`; `mtp_draft_batch` then calls `mtp_run_pending(st, n, Some(next), ...)` once per sequence). The Emit line of lane mhead's CB trace lists `(sequence, emitted)` per iteration, and emitted = accepted + 1, so the catch-up shapes of iteration i + 1 are the emitted counts of iteration i. No new device run was needed: `scripts/mcatch/shapes.py` reads the server logs lane mhead kept (`docs/results/2026-11-16-mhead/raw/abba/serve-{F.a,F.b,B.a,B.b}.log.gz`, 10 two-stream cells x 2 rounds per visit, the mhead prompt mix, spark2 / 35B NVFP4 / `--max-batch 2`; and the gate logs `raw/gates/serve-ids-{n1,n0,base}.log`) and counts the 2-sequence iterations that follow a 2-sequence iteration of the same two sequences. The B visits (main's binary) and the F visits draft the same ids, so their shapes agree.

Result, `docs/results/2026-11-16-mcatch/raw/shapes.txt` (50 030 two-sequence iterations, 49 621 counted; 409 skipped: a request's first draft after its prefill, or a sequence joining or leaving):

Per visit the all-n = 1 share is 3.42-3.52 % (four 12 170-iteration visits); the 313-iteration gate logs read 5.5-5.8 %, a small sample of mostly two 4k prompts. Any n = 1: 34.3 %. No n = 1 (both catch-ups are 2-3 rows): 65.8 %.

### The ceiling

A batched all-n = 1 catch-up is one 2-row pass in place of two one-row passes, the same transformation lane mhead measured on the chained pass: 0.39 ms saved per batched pass. So

- ceiling = 0.0351 x 0.39 ms = **0.014 ms per iteration** (the bar to continue is 0.15 ms, to ship 0.2 ms);
- even if a whole one-row head pass disappeared (mtp2s nsys: 1.13 ms for 35 kernels at 1 row; 1.34 ms for 39 kernels at 2-3 rows, `docs/results/2026-11-16-mtp2s.md`): 0.0351 x 1.13 = 0.040 ms;
- even if the whole draft (mean `prepare` 3.6 ms) disappeared on those iterations: 0.127 ms, still under 0.15 ms.

To matter, all-n = 1 would have to be about 38 % of the iterations for the 0.15 ms bar at 0.39 ms saved; it is 3.5 %. The shape is rare because two sequences must both reject their first draft in the same iteration (per-draft acceptance on this mix is about 62 %, `docs/results/2026-11-16-mhead.md`); that is also why (3, 3), both accepted both drafts, is the most common shape.

What was not measured: the time one catch-up pass takes per shape on the current binary. A fresh spark2 measurement was not taken: spark2 was held exclusively by another lane's job (fleetq #9780, a two-Spark TP2 bench, overdue) for the whole session, and the verdict does not depend on it: the ceiling is bounded by the share, and the pass times are in the nsys figures above. `prepare_us` by shape in `raw/shapes.txt` is NOT a catch-up cost (the (1, 1) iterations read slower than (3, 3), backwards for the row count, so it is confounded by which prompt, position and cell the iterations come from); it is printed only for the absurd bound. The logs come from lane mhead's binary (main 914267d89 + mhead); #416 (msmallm), the only change on main since, is Metal-only, and the CUDA draft path is the code the F visits ran.

## Task 2: the all-n = 1 batched catch-up: not built

It is a small change (gather each sequence's one queued row from `MtpState::pending` into the staging rows, one `mtp_layer_batch` over them with `ids = next`, scatter the head-cache K/V by committing each sequence's token, `pending_rows = 0`), and bitwise by the same argument as the chained pass (a one-row catch-up is the same one-row pass: `mtp_layer` with t = 1 sets no `head_rows_attn`, picks `moe_experts_decode_v2_bf16`, `matmul_bf16_gemv`). It was not built because of the stop rule: at 3.5 % of the iterations it cannot reach the 0.2 ms ship bar (ceiling 0.014 ms), and it would add a code path and a knob for a gain below measurement noise (lane mhead's ABBA resolves 0.3 ms). The change is described here so it can be built if the all-n = 1 share ever rises (for example with k = 1 serving, no chained pass, or a drafter with much lower acceptance).

## Task 3: the mixed and the 2-3-row catch-ups: why they are not batched (on paper; not tested on a device)

These are 96.5 % of the iterations, the part that would matter. Not tested, because the stop rule ends the lane at task 1; what is known from the code and the kernel registry:

- The solo pass picks its kernels by row count. At n = 1 the head's MoE runs `moe_experts_decode_v2_bf16`; at n = 2..31 `moe_experts_bf16` (`crates/intarsia-backend-cuda/tests/rows_registry.rs:154`, `kernels.rs` `MOE_BLOCK_PINS`: `35b m=1 experts: moe_experts_decode_v2_bf16`, `35b m=2 experts: moe_experts_bf16`). A row-exact batched pass (`exact_rows`) picks `moe_experts_decode_v2_rows_bf16`, which is bitwise the n = 1 kernel per row (`rows_exact.rs`), not `moe_experts_bf16`. So a sequence with n >= 2 cannot join a row-exact pass bitwise, and a batch that contains an n = 1 sequence cannot use one MoE launch for both kinds of rows: the (1, 2), (1, 3) shapes (30.7 %) are out unless the MoE is split by group, which gives back the saving.
- The remaining candidates are (2, 2), (2, 3), (3, 3) (65.8 %): 4-6 rows, each sequence's rows computed by the ordinary kernels as solo. That needs the ordinary kernels to give every row the same bits whatever the other rows of the launch are and whatever the total row count is: (a) `moe_experts_bf16` at 4-6 rows equal per row to its 2-3-row calls (it is the warp-per-row kernel, expected, but no test covers a row group of this shape); (b) the bf16 projections: the ordinary pick is `matmul_bf16_gemv` for M <= 4 and `matmul_bf16` above (`kernels.rs:1010`), so the (2, 3) and (3, 3) groups (5 and 6 rows) would switch to `matmul_bf16`, a different kernel from the 2-3-row solo calls: not bitwise unless it is shown to be, and pinning the gemv at M = 5-6 needs a new registration; (c) the per-row attention of a multi-row catch-up (`head_rows_attn`, a multi-row path of its own) would have to be run per sequence on its own cache with n rows, which `attn_block_batch` (one row per sequence) does not do.
- Each of (a) and (b) is a device test of the `rows_exact.rs` kind; neither exists.

**Follow-up, unverified:** a `mcatch2` lane for the (2, 2), (2, 3), (3, 3) shapes. Rough ceiling: the shared part of the two catch-up passes is what mhead saved on the chained pass (0.39 ms, only the projections are shared; the MoE experts of two sequences are mostly distinct), so 0.658 x about 0.4-0.5 ms = 0.26-0.33 ms per iteration if the kernels turn out row-independent, nothing if not. That is a guess from mhead's number, not a measurement; it would clear the 0.2 ms bar only barely and it needs the two device tests above first.
