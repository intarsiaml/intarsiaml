# HIP round 8: Qwen3.6-35B-A3B NVFP4 on one R9700 (gfx1201): sub-millisecond launch pieces against the ~275 us post-dispatch stall, vectorised MoE reduce, batched split-KV combine, 2026-10-19

Branch `perf/hip-round8` on origin/main `13cde333` (PR #28: P2' MoeBlock on by default). Not pushed. Every GPU window ran the
branch build against base = `13cde333` built in its own tree and cargo volume on tatooine (`~/intarsiaml-r8base`,
`intarsia-cargo-target-r8base`).

Everything in this round is bitwise. Greedy ids, KL21 and prefix reuse are identical to base. Each new path has a kill switch,
and its test compares it against the path it replaces, bit for bit.

## Headline

* **35B prefill +4.8 % at 4096 tokens and +3.7 % at 16384** (interleaved A/B x3 vs base `13cde333`, W7, `--at-most` on both
  sides): 9003 -> 9433 tok/s and 7686 -> 7968 tok/s. The 4408-token prefill goes **538 -> 517 ms** (unprofiled, W2 base vs
  W5 branch). The per-lever on/off pairs inside one window add up to the same: -12 ms from launch pieces, -9.5 ms from the
  reduce.
* **35B decode +0.9 % at 4096 and +1.5 % at 16384** (157.3 -> 158.8, 145.0 -> 147.2 tok/s), from the batched split-KV
  combine. 128 and 1024 are unchanged (164.8 / 164.2), as are 8B prefill and decode (within -0.8 to +0.3 %, overlapping
  ranges).
* The biggest headroom left in the prefill was not a kernel. **Every dispatch of 1 ms or more is followed by ~275 us in which
  the GPU starts nothing**, although the next dispatch has been queued for 10+ ms. That cost 32.4 ms (about 6 %) of the base
  4408-token prefill. MoE down and the GDN delta rule now run as pieces of < ~0.6 ms each, bitwise. gate_up keeps the stall
  (10.7 ms): its pieces would cost more than the stall.
* `moe_reduce_v8_kernel`: the MoE weighted expert sum 20.9 -> 10.6 ms, bitwise.
* All bitwise to base: KL21 digits, prefix reuse, 256 greedy ids and 8B goldens identical; 14/14 mutants killed; admission
  0 REJECT / 0 FAIL. No new resident memory. Nothing outside the HIP crate, `kernels/hip`, scripts and docs.

**Where the idle goes** (`raw/prof/base-pf4408-gaps.txt`, `-gap-by-duration.txt`, `-apigaps.txt`):

* Inside the prefill proper (`gaps.py`, launches up to the first argmax: 2649 kernels, span 533.0 ms, idle 44.7 ms), 119
  boundaries hold 32.4 ms. By pair: gate_up<64> -> down 10.7 ms, down<64> -> reduce 10.7 ms, GDN delta -> gated_rmsnorm
  8.0 ms, flash -> sigmoid_mul 2.7 ms. These gaps average 274 to 276 us each.
* The cause is how long the dispatch before the gap ran. 119 of the 123 dispatches of 1.00 ms or more are followed by a
  266 to 495 us gap, typically ~275 us, in which the GPU starts nothing. None of the 519 dispatches between 100 and 999 us
  is. The threshold is sharp.
* The host is not the cause. The API trace shows the next kernel's `hipLaunchKernel` returned 10 to 16 ms before the
  previous kernel ended. The queue already holds the next dispatch when the GPU stalls.
* Four runtime knobs did not move it: `HSA_ENABLE_INTERRUPT=0`, `ROC_ACTIVE_WAIT_TIMEOUT=5000`, `GPU_MAX_HW_QUEUES=4`, and a
  no-op control. All four sat within 8158 to 8195 tok/s (W2).
* The rest of the 44.7 ms: 2436 boundaries under 5 us (7.7 ms, about 3 us each; the known per-boundary cost), 92 of 5 to
  20 us (1.1 ms), and one 3.5 ms gap between the chunks. The chunk gap is a `copyBuffer` followed by the second chunk's embedding, host
  side; see Caveats.

## What I built

Levers were picked by measured share and by headroom that a bitwise change can reach. The headroom estimate was written down
before each lever was built.

### 1. Sub-millisecond launch pieces (`ik_split_pieces`, `INTARSIA_HIP_SPLIT_US`, default 600 us)

*Headroom estimate before building:* the 32.4 ms of long-dispatch stalls (about 6 % of the prefill span). If the pieces cost
nothing, all of it could go. I expected 15 to 20 ms, because every piece pays its own ramp and tail.

* `kernels/hip/ik_hip.h` `ik_split_pieces(est_us, max_pieces)`: the number of pieces is `ceil(est / budget)`, capped. The
  launcher estimates each launch's time from its size, using rates measured in this profile.
* **MoE down** (`moe.hip` `moe_wmma_launch_p`): pieces over consecutive feature tiles (grid y). All three kernel families
  (`moe_wmma_kernel`, `_v`, `_r7`) take a new `y0` argument, and `n0 = (blockIdx.y + y0) * FEAT`. Each block of a piece is
  the single launch's block for that feature tile; no kernel reads `gridDim.y`. The 4096-token chunk runs as 2 pieces of
  ~600 us. The 312-token chunk stays one launch.
* **GDN delta rule** (`gdn.hip` `ik_gdn_delta_rule_bf16_v2`): pieces over consecutive token ranges. Each piece offsets its
  qkv / a / b / output pointers to its first token. It continues the in-place f32 state the previous piece stored, which is
  exact because the state round-trips through memory in f32 between launches either way. The recurrence sees the same tokens
  in the same order. 4096 tokens run as 6 pieces.
* **gate_up is never split** (`GATEUP ? 1 :`). Split v1 cut it into 4 pieces, and the pieces took **114.1 ms against
  85.7 ms** for one launch. A hot expert has more pair tiles than the grid's z covers, so it sets each piece's length and
  every piece pays that tail. The 4408-token prefill got 3.3 % slower in W3 (556 to 560 ms against 537 to 541).
* **Measured** (W4, same window, interleaved, on vs `SPLIT_US=0`): 4408-token prefill **526 / 526 / 527 / 529 ms vs
  538 / 540 / 539 / 541 ms (-12 ms, -2.2 %)**.
* **Profile** (W4/W6):
  * down 45.5 -> 48.6 ms (+3.0) and GDN 101.0 -> 104.4 ms (+3.4); the pieces cost 6.4 ms.
  * The down -> reduce (10.7 ms) and GDN -> norm (8.0 ms) stalls are gone, 18.7 ms removed.
  * gate_up -> down (10.7 ms) and flash (2.7 ms) remain.
* Bitwise: `tests/moe_pairs.rs` runs `SPLIT_US=1` (one feature tile per launch) and `150` (uneven pieces) for every kernel
  family at both tiles, against one launch. `tests/gdn_v2.rs` runs `SPLIT_US=1` (one token per launch), `7` and `40`
  (ranges that are no multiple of the prefetch depth or of the 32-token gate batch) on all 19 shapes, output rows and final
  state.

### 2. `moe_reduce_v8_kernel` (`INTARSIA_HIP_MOE_REDUCE=0` = the scalar kernel)

*Headroom estimate before building:* the scalar `moe_reduce_kernel` read 2 bytes per thread per expert row. It moves
~151 MB per 4096-token chunk in 0.49 ms, about 308 GB/s. At ~550 GB/s the 20.9 ms would drop to about 11 ms, so roughly
10 ms of headroom.

* Each thread owns 8 consecutive features. It loads the token's K (<= 8) expert rows as 16-byte vectors before any arithmetic,
  then sums `round_bf16(y * w)` over k = 0, 1, .. in order, skips the same invalid ids, and stores with the same bf16
  conversion. The bits are the scalar kernel's. It needs H % 8 == 0 and 16-byte-aligned y / out, otherwise the scalar kernel
  runs.
* **Measured** (W5, interleaved, on vs off): **516 / 516 / 517 / 518 ms vs 525 / 525 / 527 / 528 ms (-9.5 ms, -1.8 %)**.
  Kernel 20.85 -> 10.56 ms (132 us per 4096-token launch). That is ~1.1 TB/s effective, above DRAM bandwidth, so part of y
  likely comes from the 64 MB last-level cache that down has just written it into (not profiled).
* Bitwise: `tests/moe_pairs.rs` compares it with `INTARSIA_HIP_MOE_REDUCE=0` on every case: K = 4 and 8; H = 256, 320
  and 2048; the hot-expert, scale-byte and NaN cases.

### 3. Batched split-KV combine (`combine_kernel<D, 16>`, `INTARSIA_HIP_SPLITKV_R8=0` = one split at a time)

*Headroom estimate before building:* 136 us/step at 17.6k context. The 64 dependent loads of 1 MB each wait on one another,
so the kernel is latency-bound. At bandwidth it would take a few us, so ~110 us/step of headroom, about 1.5 % of decode at
16k. At short context it is 16 us/step, nothing to win.

* The max pass and the weighted-sum pass each load 16 splits' (m, l) and acc into registers before the arithmetic. They then
  fold over s = 0, 1, .. in order with the same operations. The padded slots of the last batch are skipped exactly where the
  old loop stopped.
* **Measured**:
  * Profile 13.6 -> 7.0 us per launch (W4), 66 us/step.
  * Unprofiled 17.6k decode (W4, interleaved): **144.52 / 144.48 / 144.41 / 144.21 vs 143.62 / 143.46 tok/s (+0.6 %)**.
    That is within reach of noise, so the x3 A/B below is the judge.
* Bitwise: `tests/splitkv_r8.rs` (new):
  * 130 cases of decode and of the 2..16-row verify path.
  * GQA groups 1..8, head dims 32..256.
  * Split counts 1 to 64: last batch full, partial and alone.
  * Peaky and flat softmax.

## What I tried and dropped

* **gate_up<64> as launch pieces** (split v1, above): 4 pieces cost 28 ms against the ~11 ms of stall they would remove. Two
  pieces would still pay most of one extra tail; I did not build that.
* **Split-KV stage 1 with a register double buffer** (next step's K/V loaded before this step's arithmetic), bitwise:
  * Built, tested bitwise (W4 `splitkv_r8`).
  * Measured 92.8 us against 90.3 us per launch at 17.6k: no gain. I did not find out why (no ISA or occupancy look).
  * Reverted to the original loop. Stage 1 is still 64 % of peak bandwidth; finding the limit needs an occupancy and ISA
    look, which I did not do this round.
* **flash attention as pieces over query tiles**: not built. The headroom is 2.7 ms (10 launches x 275 us, 0.5 %), and
  causal tiles are uneven, so pieces risk the same tail as gate_up.
* **Runtime knobs against the stall** (W2): `HSA_ENABLE_INTERRUPT=0`, `ROC_ACTIVE_WAIT_TIMEOUT`, `GPU_MAX_HW_QUEUES`. No
  effect (above).
* **MoE gate_up<32> (round-5 kernel)**: not built. It runs only in the sub-4096 tail chunk. 30.2 ms over 40 launches is
  ~0.75 ms per layer. My estimate is ~300 MB of gate_up weights per layer (256 experts x 2 x 512 x 2048 fp4 + scales), so
  about 64 % of bandwidth. The headroom is at most ~11 ms, and only when
  the prompt's tail chunk is large; it is zero for prompts at the chunk size.
* **MoE gate_up<64> dequant path**: not attempted. Round 7 took it from 98.9 to 87.7 ms (VALU 8.04 and LDS reads 1.00 per
  WMMA). In my judgement the next step needs a different tile design, more WMMAs per dequantised fragment. That
  is bigger than this round's budget; the idle stalls were cheaper headroom.
* **GDN prefill compute**: the angle this round was the launch shape, not the recurrence (all heads already run at once, and
  a two-token register pipeline gave -1.3 % before). The pieces raise the kernel's time by 3.4 % (0.76 -> 0.79 us per
  token, 30 layers x 4408 tokens), but 8.0 ms of stall goes.
* **Decode launch overhead**: 0.88 ms/step of 3.3 us boundaries, the known graph-replay cost; not attempted again.

## Caveats and env vars

* `INTARSIA_HIP_SPLIT_US=n` (default 600; 0 = one launch per kernel), `INTARSIA_HIP_MOE_REDUCE=0`, `INTARSIA_HIP_SPLITKV_R8=0`.
  Every value is bitwise; all three are read at every launch.
* The split's rate constants (`kMwMacPerUs64/32`, 0.77 us per GDN token at 256 waves) are calibrated on the R9700 with the
  35B. On other shapes or GPUs the piece count changes, never the bits.
* The ~275 us stall after a >= 1 ms dispatch is characterised, not explained: it is not host-side, and the knobs tried do not
  touch it. Its cause (CP / firmware / driver) is open, and a fix there would also cover gate_up and flash. Worth a ROCm issue
  with `raw/prof/base-pf4408-gap-by-duration.txt` as the repro data.
* There is a 3.4 ms gap between the 4096-token and the 312-token chunk. A `copyBuffer` runs, then the second chunk's
  embedding starts 3.4 ms later. It recurs at every chunk boundary, so a 16k prompt has three of them. It is host side, most
  likely in the core prefill loop, so I left it: a candidate for a later round, and it touches shared code.
* The default split also cuts GDN / down launches estimated at 600 us to ~1 ms (chunks of roughly 780 to 1300 tokens), which
  would not have stalled. W8 measured no cost at 1024 tokens. A trigger at the ~1 ms stall line, with pieces still sized near
  600 us, would be cleaner; it is a candidate for round 9.
* In W5 the unprofiled 17.6k decode with the combine on (`d16env:X=0`) printed no `finish=` line. The stage output is
  grep-filtered, so the cause cannot be recovered from the log. The same build then ran the 16k A/B in W7 with 0 errors, and
  W4 ran the same combine code without a problem.
* Profiles in different windows (W2 base, W6 branch) differ by up to ~1 % in kernel time from run to run. The per-lever
  numbers above therefore come from on/off runs in the same window.
