# HIP tp=2: decode graphs and fusion under TP, and the short-set KL (lane H1, 2026-10-21)

Qwen3.6-35B-A3B NVFP4 at tp=2 on tatooine's two R9700s (one process, a thread per rank, the HIP P2P all-reduce), following
G2b (`origin/feat/35b-tp2-hip`, `docs/results/2026-10-21-35b-tp2-hip.md` there) and the CUDA port in PR #52
([2026-10-21-tp2-cuda-graphs.md](2026-10-21-tp2-cuda-graphs.md)). Branch `lane-h1/tp2-hip-graphs` on origin/main `0294b778`.
Raw logs: `2026-10-21-h1-tp2-hip/raw/w1..w4` (accuracy dumps not committed; `tatooine:~/h1/out/<window>/`). Scripts:
`scripts/h1-tp2-hip/`.

## Headline

- **tp=2 now decodes faster than tp=1, with fusion on.** tp=2 with graphs and row-local fusion (`INTARSIA_TP_FUSION=1`) beats tp=1 by
  +14.7 / +17.6 / +22.2 % at 1k / 4k / 16k. With graphs alone (the new default) it stays 5-12 % behind tp=1.
- **Graphs and fusion change no bits.** Every comparison below is identical: 256 greedy ids, accuracy dumps on both sets,
  and the self-golden against the eager dump at the 1e-13 floor. Rank 1 replays in lockstep; its counters are printed.
- **The short-set KL is reduction order, not a bug and not the all-reduce.**
  - The P2P all-reduce gives bitwise the same dump as the host communicator's f32 sum.
  - Against the vLLM golden the noise was measured on, tp=1 and tp=2 are equally far: 5.831e-3 and 5.843e-3 (scored rows).
  - Two equally correct tp=1 kernel variants move the short set by the same amount as tp=2 (1.52x and 1.08x of vLLM's
    run-to-run, against tp=2's 1.65x), and land just as close to the golden.
  - The engine-vs-golden gate with the reference noise passes on both sets. The change-vs-base form (`--self-vs-ref-noise`,
    tp=2 against tp=1) fails at 1.66x short and 1.31x long, as would the tp=1 MoE variant. That is a decision for the user (section 5).

**The golden.** tatooine holds two vLLM runs of the short golden: `qwen36-35b-a3b-nvfp4-vllm-top20.safetensors` (fnv b58845c3, the

refuses the first with the sidecar, so this lane gates on the `-meta` file. The two runs are 2.309e-3 apart (scored).

**Reading it.**
- **Not the communicator.** The P2P kernel's f32 add with one rounding gives exactly what the host's rank-order f32 sum gives,
  on every row. There is no RCCL in this path.
- **Not a bias.** A bug adds an error that tp=1 does not have, so tp=2 would sit further from the golden than tp=1. It sits at
  1.002x of tp=1's distance. Per prompt it goes both ways: `science` is 1.304e-2 for tp=1 and 7.085e-3 for tp=2.
- **The size of a reordering on HIP.**
  - Changing only the MoE GEMMs' accumulation order at tp=1 moves the short set by 4.57e-3. That is 92 % of tp=2's 4.97e-3, and
    those GEMMs are exactly what tp=2 re-shapes (expert width halved).
  - HIP's own distance to vLLM is 1.9x vLLM's run-to-run (5.83e-3 against 3.01e-3), so any reordering on HIP moves the short set
    more than vLLM's run-to-run.
  - CUDA's 1.06x for the same core sharding fits this: CUDA tp=1 sits closer to vLLM (1.51x of the noise in A2's table).
- **Coarser partials land closer by chance.** bf16 partials round twice, yet sit 4.86e-3 from the golden, closer than tp=1.
  The rows move by about +-1e-3 between equally valid runs. The default stays f32: it is the documented one-rounding contract.
- **Where it is not.** The trace of tp=1 and tp=2 (`INTARSIA_HIP_TRACE=1`) shows the same prefill kernels; only the decode
  fusions differ. Kernels against the reference at the tp=2 shard shapes pass (`kernels test`, and the HIP crate's tests with the
  new shard-shape cases, section 3).
- The MoE block's tp=2 partial is the bf16 output of the MoE kernels (`model.rs`, "summed in place in the activation dtype"), so it
  rounds twice, where o_proj and the GDN out-projection round once. That is core behaviour on both backends and is not changed
  here; a f32 MoE partial would need new HIP and CUDA MoE output variants.

## 4. What changed

- `P2pComm::capture_safe` = true (`crates/intarsia-backend-hip/src/comm.rs`). A collective is kernel launches on the caller's stream
  with no host synchronisation, event or allocation. Everything the kernel keeps between calls lives on the device:
  - per-block counters, which pick the scratch parity and the flag value at run time, so replays and eager calls interleave;
  - the flags;
  - the fixed scratch slots.

  The partials are the model's workspace, so nothing needs `Comm::reserve`. Core graph and lockstep logic (#52) is unchanged:
  the in-process peer already took rank 0's decision (`run_peer`).
- `HipBackend::fusion_under_tp` = true (opt-in through `INTARSIA_TP_FUSION=1`, as on CUDA). The fused kernels take every dim from
  the call; their admission holds at the shard shapes (8 q / 1 kv heads, GDN 8 / 16 heads, MoE and shared widths 256).
- Rank 0 prints each in-process peer's graph counters when the model is dropped (`graph_step.rs`), as `tp-worker` does for a remote
  rank.
- Tests:
  - `comm::collectives_captured_into_a_graph_replay_exactly_and_interleave_with_eager_ones`: 200 rounds of replays with new data,
    every fifth round eager;
  - the 35B tp=2 shard shapes in the fused and unfused kernel tests (`fusion_p2`, `fused_decode`, `moe_block`, `moe_v3`,
    `decode_v2`, `gdn_v2`, `flash_v2`, `attention`, `splitkv_r8`);
  - the comm tests now hold one group at a time. With `GPU_MAX_HW_QUEUES=1` two parallel test groups can deadlock across the
    two devices' single queues. Window 3 hit this: the bounded wait trapped. The engine runs one group per process.
- **Effect per backend:** HIP tp=2 decode graphs by default (bitwise to eager), fusion opt-in; HIP tp=1 bitwise unchanged; CUDA,
  Metal and CPU: only the core `Drop` print (in-process TP only).

## 5. Decisions for the user

1. **Make `INTARSIA_TP_FUSION=1` the HIP tp=2 default?**
   - For: it is the step that makes tp=2 beat tp=1 (+15 % to +22 % decode; graphs alone stay 5 % to 12 % behind). It is
     bitwise to unfused on every gate here (ids short and 4k, short dump), and the out-projection fold mutant is killed.
   - Against: the long set and prefix reuse were not run with fusion on.
   - The lane rules keep a changed default opt-in until you say so. The flip is one line.
2. **The change-vs-base form of the reference-noise gate for HIP tp=2** fails at 1.66x short and 1.31x long. An equally correct
   tp=1 kernel variant fails it too (1.51x). Options:
   - accept tp=2 on the engine-vs-golden gate, which it passes;
   - or calibrate a HIP factor from tp=1 variants (the MoE WMMA and FP8 F8 runs give 1.08x to 1.52x).
3. **The deleted G2b record.** The T1 merge (`6712b10c`, `f7f0b0ea`) removed `docs/results/2026-10-21-35b-tp2-hip*` and
   `scripts/35b-tp2-hip/`, which had reached main through the T1 branch. They live on `origin/feat/35b-tp2-hip`. This PR does not
   restore them. That is for the coordinator.
