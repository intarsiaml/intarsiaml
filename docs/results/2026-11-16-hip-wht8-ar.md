# HIP tp2 prefill: the wht8 lossy all-reduce wire (lane wht6-8b), 2026-11-16

Question (from the review of `docs/results/2026-11-14-hip-wht6-ar.md`): does the same wire with 8-bit symbols keep most of the
prefill gain of wht6 and pass the change-vs-base KL rule? Opt-in only; `exact` stays the default; no default was flipped.

## Summary

- Built `INTARSIA_HIP_AR_WIRE=wht8`: the wht6 kernel with the symbol width as a template parameter (`kernels/hip/allreduce_wht6.hip`,
  `ik_ar2_wht8`). 8.25 bits per element (3.9x fewer bytes than an f32 partial, 1.9x fewer than bf16). The wire error is 4.1x smaller
  (rms 0.41 % of the reduced partial against 1.66 %).
- Kernel gate: PASS (both ranks bit-identical, worst rotated error 0.993 of the codec's bound, delayed-rank stress test clean,
  negative control sees 123 wrong results). wht6 reproduces the 11-14 numbers bit for bit (same worst-error and rms per size).
- Speed (35B NVFP4 tp2, same build, 6 interleaved rounds x 3 reps): prefill **+9.8 % / +18.8 % / +15.8 %** at 1k / 4k / 16k against
  exact, against wht6's +11.7 % / +22.0 % / +18.0 %. wht8 **keeps 84-88 % of wht6's prefill gain** (0.97-0.98 x wht6's prefill
  speed). Decode unchanged (0.993-0.998 x).
- Accuracy: **wht8 does NOT pass the change-vs-base KL rule**. Short golden: mean KL21 5.56e-3 = 1.76 x the reference noise (limit
  1x), `code` and `chat_system` over 3 x their own noise. Long golden: 3.24e-2 = 1.46 x. Same build, wht6: 1.51 x and 1.42 x. The
  4x smaller wire error did not lower the KL. Top-1 flips: 18 (1.25 %) short, 1683 (4.56 %) long; greedy ids leave the exact wire's
  at id 28 (24-token prompt) and id 82 (4.4k prompt). The vLLM-golden gates all pass.
- Recommendation: wht8 buys nothing over wht6 on the gate that matters (both fail it by a similar margin) and gives up 12-16 % of
  the gain. Do not offer it as a serving profile; keep it as an experimental opt-in knob next to wht6, or do not merge the PR.

### The 8-bit code

Everything but the symbol width is wht6's. Per group of 64 consecutive elements: orthonormal 64-point Walsh-Hadamard rotation (in
f32, f32 partials are encoded from f32), scale `s = bf16_nearest_even(amax(rotated group) / 127)` (1.0 for an all-zero group), symbol
`q = clamp(rint(v / s), -128, 127) + 128` stored as one byte, dequantised as `(q - 128) * s`, reduced in f32 on both ranks with
FMA contraction off (bit-identical outputs), rotated back and rounded once to the output dtype.

- Why these choices: the scale and rounding scheme are kept identical to wht6 so the two widths differ in one parameter only and the
  comparison is clean. Round to nearest even is the minimum-error uniform quantiser. The bf16 scale keeps the per-group side
  information at 0.25 bit per element; at 8 bits an f32 scale would cost 0.5 bit more for a change of at most 0.4 % in the step
  size. The scale is rounded to nearest, so it can round down by up to 2^-8; the extreme symbol then clamps, which adds at most
  amax / 256 of error on that element, still inside the half-step bound (amax / 254) the test checks (with 0.4 % slack).
- Layout: a wave still owns a chunk of 32 groups = 2048 elements; a lane holds 8 elements of a group (8 lanes span a group, 4
  groups per wave-iteration, 8 iterations), so a lane emits 64 symbols = 16 dwords = four 16-byte words (wht6: 12 dwords, three words).
  Lane L's u-th word lands at `chunk * 128 + u * 32 + L`, one coalesced 512-byte store per wave and word. A chunk is 2048 bytes
  (wht6: 1536); symbols are byte-aligned, so the pack and unpack code has no word-straddling case.
- Capacity: a 20 MiB wide slot carries 19.66 M elements per launch at 8 bits (26.2 M at 6 bits): a 4096-row f32 chunk of hidden 2048
  or the 2048 x 5120 chunk of a 27B is still one launch. Local pack buffer: 20.3 MiB per rank as before (+ the f32 scales).
- Messages, floor (`INTARSIA_HIP_AR_WIRE_MIN_KB`, 128), the fused `ar_norm` path, the GEMM pre-push and the 1-row decode behave as
  for wht6 (section 1 of the 11-14 doc).

## 2. Gate 1: kernel tests (both R9700s) - PASS

`scripts/wht6-8b/kernels-window.sh` (`raw/kern1/`): `cargo test --release -p intarsia-backend-hip --test ar_wht6 -- --test-threads=1`:
8 passed, 1 ignored (rate). The existing suites with the wire unset (`--test comm --test ar_push --test ar_norm`): 13 + 4 + 4 passed.
`intarsia kernels test --backend hip` (single device, 91 kernels, 2219 cases, no failure; it does **not** exercise the two-rank wire,
`tests/ar_wht6.rs` is the gate for that).

| wire | worst rotated error / codec bound | rms error / rms of the sum | ranks bit-identical | stress, delayed rank | negative control (no wait) |
|---|---:|---:|---|---|---:|
| wht6 | 0.996 | 1.5-2.0 % (1.66 % at prefill sizes) | yes, every size and dtype pair | 0 wrong of 30 rounds | 123 wrong |

f32 partial holding the same values; the f32 -> bf16 output is the f32 result rounded once.

| 256 x 2048 | f32 2 MiB | 106.7 | 60.9 | 65.3 | 1.63 | 0.90 |

### Why the 4x smaller wire error does not lower the KL

The wire error went down 4.1x (kernel gate) and the change-vs-base KL did not follow: wht8 is 5.56e-3 against wht6's 4.79e-3 on the
short golden, 3.24e-2 against 3.14e-2 on the long one, and the per-prompt tables of the two are of the same size prompt by prompt
(for example `count` 1.97e-3 / 3.42e-3, `long_prose_700` 5.73e-3 / 4.32e-3, with the worst prompt different in each). Checked
against a shared systematic deviation of the lossy path: wht8 against the wht6 dump (`cross` step, `raw/acc2/cross-8v6.out`) gives
6.81e-3 and the reverse 7.03e-3, **larger** than either wire against the exact one. Two wires that shared a deviation would be close
to each other; they are not, so each run decorrelates from the exact run on its own and the two are further apart than either is
from the base. Reading: for this model any change of the all-reduce numerics beyond bf16 rounding sends the logits to a floor of
about 1.5 x the vLLM re-run noise on mean KL, with a handful of near-tie positions (MoE routing, a few top-1 flips) carrying much
of the mean; the quantiser error of 6 or 8 bits is below what that floor resolves. This is an interpretation of the cross result and
the per-prompt tables, not a proven mechanism: a 12- or 16-bit probe of the same kernel (the template takes any even width) would
show where the KL starts to fall below the floor, and was not run.

For scale, the chunked GDN delta rule (#378), a reordering of exact arithmetic, measured a prefill mean KL21 of 3.455e-3 on the same rule (LOG 2026-11-15 12:05).

## 5. Not done, not verified

- 27B MXFP4: not measured (the checkpoint is not on tatooine, as in the 11-14 lane). Its GEMM pre-push interplay is unmeasured.
- A wire of more than 8 bits (the floor probe above) and a floor sweep (`INTARSIA_HIP_AR_WIRE_MIN_KB`): the wht6 doc's floor result
  (a higher floor only moves which prompts are lossy) is assumed to carry over.
- Batched decode above 16 rows per step with the wire on: not exercised.
- Fleet: one kernel window, four accuracy windows (the first on the dirty stamp) and two speed windows, each a few minutes, with the a4k-restore lane's windows in
  between; every window restored radiance (it answered after each). The tatooine tree and the docker volume
  `intarsia-cargo-target-wht6-8b` are removed. `raw/` holds the `.out` / `.err` / step logs, not the `.safetensors` dumps.
- The first accuracy window ran on a dirty-stamped build and its self-golden steps were refused by the provenance check; the build
  was redone from a clean commit and the whole accuracy set rerun (`raw/acc2/`). Nothing from the refused run is used.

## 6. Recommendation

8 bits are cleaner on the wire (0.41 % rms against 1.66 %) and keep 84-88 % of wht6's prefill gain (+10 / +19 / +16 % at 1k / 4k /
16k against exact), but neither wire passes the project's change-vs-base KL rule on the 35B (wht8 1.76 x / 1.46 x the reference
noise on the short / long golden, wht6 1.51 x / 1.42 x), and greedy output still leaves the exact wire's within 28 to 82 tokens.
The reviewer's expectation that 8 bits would pass does not hold on this model. Leave `exact` the default, do not offer wht8 as a
serving profile, and keep it, if at all, as an experimental opt-in beside wht6 (a LOSSY line is printed at start). If the prefill
gain is wanted, the user decision is the same as for wht6: accept a measured change-vs-base failure for 10-19 % prefill, as was done
for the GDN chunk kernel (LOG 2026-11-15 12:05); wht8 is then the safer of the two on the wire and costs 2 % of prefill speed against
wht6, but the measured KL does not show it to be safer on the model.
