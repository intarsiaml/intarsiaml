# Metal 35B prefill chunk 256 -> 2048 (gc2)

**Update 2026-10-23:** with the 4k-golden continue oracles (docs/results/2026-10-22-gc2-4k-continue-oracles.md, committed on #104) Metal 35B `qualify` PASSES on this branch at chunk 2048 (exit 0), and also on #104 alone at chunk 256. The chunk change is therefore not needed for the verdict; it remains an optional +26 % prefill. The statement below that it "does not fix" the failure was true without the oracles.

**Result: the change does NOT clear `qualify`'s `long_docs_4k` `continue` failure on the 4k golden.** It does give +26 % prefill at 4k.
Do not merge it as the fix for PR #104.

Change: `[tuning.metal] prefill_chunk = 2048` in `recipes/qwen3_5_moe.toml` (user-delegated 2026-10-22 19:41), plus the Metal 35B
baselines, noise envelope and CPU-oracle self-golden re-recorded at 2048 (they were recorded at 256 and are chunk-tied:
`accuracy/baseline.rs`, `qualify.rs recorded_baseline`). Tests: `cargo test --release -p intarsia-models -p intarsia-core -p intarsia-cli`

Old chunk-256 baselines moved aside (`raw/old-baselines/`), q-0 recorded new ones at 2048 and they were installed in
`golden/baselines/`; q-1 ran against them.

| stage | q-0 (record) | q-1 (verdict) |
|---|---|---|
| doctor, recipe, plan | PASS | PASS |
| kernels, gate | not run | PASS, PASS |
| acc-short | MISSING-BASELINE (recorded) | PASS (prefill top-1 98.33 %, KL 7.04e-3; decode top-1 98.75 %, KL 1.11e-2) |
| acc-oracle | MISSING-BASELINE (dump recorded) | PASS (prefill top-1 96.26 %, KL 1.09e-2) |

`acc-4k` prefix reuse, `long_docs_4k` `continue`, is still the only failing case. Everything else (`restore`, `aligned` bit-identical,
all `long_code_4k` and `chat_reuse_4k` cases) passes:

| run | chunk | split | result |
|---|---|---|---|
| gc2 acc-4k, reuse mode | 2048 | 3072 (cached 3087) | FAIL, streams diverge at token 8 (warm took 11, cold 333); shared rows differ by 0.175 nats, KL up to 1.5e-2; limit 0.25 nats / 1e-2; warm margin 0.211, cold margin 0.133 |
| gc2 acc-4k-reuse (qualify's capped run) | 1024 | 2000 (cached 2015) | FAIL, diverge at token 8 (warm 333, cold 11); 0.252 nats, KL up to 2.9e-2; warm margin 0.346, cold margin 0.132 |
| gc main (gc-gate-coverage doc) | 256 | 2000 | FAIL, diverge at token 8; 0.252 nats, KL up to 2.9e-2 |

So the divergence is not chunk-dependent: it is a near-tie (cold margin 0.13 nats) that the two paths resolve differently. The committed
`continue` oracles in `golden/oracle/` cannot judge it: they were made for another golden's prompt ids ("the golden's prompt token ids differ
from the ones it was made for") and are frozen at splits 2000 and 3072. Likely real fixes: make `continue` oracles for the 4k golden's ids,
or exclude the near-tie case from the 4k golden; neither is done here.

QUALIFY's reuse gate runs at min(plan chunk, 1024) (`REUSE_CHUNK_CAP`), so with this change it judges at 1024 (split 2000) while
`accuracy --mode all` judges at the plan's 2048.
