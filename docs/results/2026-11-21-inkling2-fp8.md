# Inkling-2-Mini: opt-in reduced-precision dense weights (lane ink-fp8, 2026-11-21)

Status: in progress. Default stays native bf16 (exact vs vLLM); every mode here is opt-in.

## Briefs received

1. 2026-11-21 (coordinator), go-ahead for extending `InkInProj` (73) for e4m3 weights, additive only:
   1. bf16 calls stay exactly as they are (2 inputs, no dummy `[0]`). The 3rd input `scales [3] f32` exists only when w is e4m3
      (W8A16); validation rejects e4m3 without scales and bf16 with scales.
   2. Keep the no-contract-change path (3 `MatmulFp8` calls) as the fallback; the loader picks the fused op only when the
      backend reports support for the e4m3 variant (every other backend, including the CUDA lanes, gets the fallback). A bf16
      kernel must never be handed e4m3 bytes.
   3. CPU reference first, then the Metal kernel; e4m3 admission sweep cases at real shapes and rows 1/4/16/2048, rows-exact;
      update the op-list entry in the spec doc on this branch.
   4. 4-bit in_proj: 3 `MatmulMxfp4` calls, no contract change.
   5. Fix the bypassed `INTARSIA_LMHEAD_QUANT` hook in the Inkling loader; stays off by default.
   Order: the accuracy x speed table on the fallback path first (it decides whether fp8 is worth having), then the fused kernel
   and a re-time. Everything opt-in.
2. 2026-11-21 (coordinator, from Fable's decode review `.worktrees/ink-fable/decode-profile-review.md`):
   1. New lane ink-pack12 (`.worktrees/ink-pack12`) owns lossless 12-bit packing of in_proj, wo and the unembed (review 0.3,

      this lane keeps the lossy e4m3 / mxfp4 modes. Both keep the w-dtype dispatch in the loader and the validator as ONE match
      over {bf16, e4m3 + scales, p12 + side}; whoever lands second merges onto the other; this branch has priority on the op-73
      validation code.
   2. Added scope, after the accuracy table: item 6, the unembed as an exact screen for greedy and top-k / top-p (a 4-bit or fp8
      copy with a per-row error bound picks the candidates, only those get exact bf16 rows; est. 0.6-1.0 ms/token, exact, so it
      can be default-on once proven). Start with a CPU script on the golden logits (candidates per token within the bound). New
      ops for it take discriminants 88-91.
   3. Measure decode with `--profile-every 0` (the default 16 adds about 4 ms/token of fake gap; the real bf16 step is
      15.76 ms = 63.4 tok/s, unembed 1.58 ms, in_proj + wo 4.78 ms).
