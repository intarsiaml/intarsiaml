# Inkling-2-Mini: opt-in reduced-precision dense weights (lane ink-fp8, 2026-11-21)

Status: accuracy (cpu) and full-model decode speed (Metal, endor M5 Max) measured for every mode; fp8 recommended as the opt-in
fast mode, 4-bit rejected. Default unchanged (native bf16, exact vs vLLM) for Inkling and every other model. Branch `ink/fp8`
(merged `ink/metal` up to a0751f302; not pushed, not merged into main).

Reading the table:
- **fp8 stays inside vLLM's own noise.** Against vLLM, fp8 / fp8 is no worse than our bf16 (8.96e-3 vs 9.06e-3 short, 1.28e-2 vs
  1.41e-2 long: the differences are noise of the same size as vLLM's batch / chunk noise, about 1e-2); no confident-row miss.
  Against the W4A16 oracle (G2, a tighter reference than vLLM) fp8 adds about 1.4e-3 (short 4.39e-3 is just above the bf16-port G2 bound of
  4e-3, long 5.30e-3 is under 6e-3). G2 bounds were set for the exact port, so fp8 is not "G2-exact", which is expected for a lossy mode.
- The fp8 head alone is almost free in accuracy (KL 1.6e-4 against our bf16) and worth +6 %; fp8 attention is where the KL goes
  (4.6e-3 against our bf16) and where most of the speed is.
- **mxfp4 attention fails**: 2 confident-row misses on the short set (allowance 1), top-1 94.7 %, KL 2.05e-2 against vLLM (twice
  the bf16 port's, above the 1.05e-2 G3 bound). The q / k L2 clip and the 16-dim relative projection (Fable's risk note) do not
  survive 4-bit weights with plain per-32 e8m0 scales. Not recommended; finer 4-bit (NVFP4 per-16 with e4m3 scales, or keeping
  `wr_du` / `wq_du` at fp8) is the only variant worth a later try.
- Fused e4m3 `InkInProj` vs three `MatmulFp8` packs: +4.7 tok/s (fp8 / bf16) and +5.7 tok/s (fp8 / fp8); the existing `MatmulFp8`
  GEMV reaches only ~330 GB/s at these shapes (below), so the contract extension was worth it.
- Greedy text diverges from bf16 within the first ~10 tokens in every quantised mode (expected for changed numerics); fused and
  packs diverge from each other later (accumulation order).

Per token (48 visits) the e4m3 in-projection saves 48 x (72.1 - 38.6) us = 1.6 ms; fp8 `wo` on the existing GEMV saves only
0.1 ms (295 GB/s), so `wo` and the fp8 head are the remaining headroom: a `MatmulFp8` GEMV at the e4m3 `InkInProj`'s ~515 GB/s
would save about 0.45 ms (wo) + HEAD_SAVE ms (head) more per token. That is a `MatmulFp8` kernel variant (no new op), but it would
change the kernel every other fp8 model selects on Metal, so it needs to be opt-in or shape-gated; not built here.

## Recommendation

- Keep bf16 the default (exact).
- Offer **fp8 attention + fp8 unembed** (`INTARSIA_INK_ATTN_QUANT=fp8 INTARSIA_LMHEAD_QUANT=fp8`, or the recipe keys
  `[tuning.metal] ink_attn_quant = "fp8"`, `lm_head_quant = "fp8"`) as the opt-in fast mode: 64.2 -> 77.7 tok/s (+21 %) on endor,
  G3 short / long inside the bounds and no worse than our bf16 against vLLM, no confident-row misses; it costs about 5e-3 KL against
  the exact port. If only the head is wanted, the fp8 head alone is +6 % for 2e-4 KL.
- Do not offer mxfp4 dense (fails G3: confident misses, KL 2e-2).
- The user decides on any default.

## Unembed as an exact screen (item 6, brief 2.2)

Script `tools/inkling2_unembed_screen.py` over the oracle's final normed hidden states `h` of the 569 short-golden
positions (`tools/inkling2_dump_hidden.py`, the W4A16 oracle `tools/inkling2_ref.py`, spark1 cpu, fleetq #10831). For each unembed row n,
`|h.W_n - h.Wq_n| <= ||h||_2 e_n` with `e_n = ||W_n - Wq_n||_2` precomputed (Cauchy-Schwarz; also a per-32-column block form,
`sum_b ||h_b|| e_{n,b}`, 72 bound values per row). Greedy: candidates `{n : a_n + b_n >= max_m (a_m - b_m)}`, top-k: the k-th
largest lower bound. The script asserts that the true top-k is always inside the candidates (it was, every position).

| Copy | Bound | greedy candidates mean / p50 / p99 / max | top-20 mean / p99 | top-50 mean / p99 |
|---|---|---|---|---|
| fp8 (per tensor, 0.46 GB) | row | 12.1 / 1 / 470 / 565 | 1109 / 6677 | 3321 / 12148 |
| fp8 | 32-col block | 8.6 / 1 / 328 / 358 | 852 / 4812 | 2595 / 9998 |
| mxfp4 (0.245 GB) | row | 34243 / 2622 / 200058 / 200058 | ~all | ~all |
| mxfp4 | block | 24894 / 802 / 200058 / 200058 | ~all | ~all |

The true error is 0.11 of the row bound (median; max 0.14), so Cauchy-Schwarz is about 9x loose but still enough for fp8: an fp8
screen plus at most a few hundred exact bf16 rows (mean 12 rows = 0.06 MB) gives the exact greedy token while reading 0.46 GB instead
of 0.92 GB (about -0.8 ms / token at 560 GB/s, the brief's 0.6-1.0 ms). Top-20 needs about 1100 exact rows (5 MB) on average,
6700 (31 MB) at p99: still a large saving. A 4-bit copy is useless with these bounds (most rows stay candidates). Open points before
ops 88-91: (1) the bound needs slack for the fp32 accumulation difference between the screen GEMV and the exact rows (about 1e-6
relative; add `||h|| * ||W_n|| * 2^-20`); (2) top-p / temperature sampling needs the full softmax normaliser, which the screen
does not give exactly (bounding the tail mass of non-candidates is possible but not exact); exact greedy and exact top-k are
straightforward; (3) the candidate count has a long tail (max 565 greedy), so the exact pass needs a variable-length gather.
Only the short set (569 positions) was run.
