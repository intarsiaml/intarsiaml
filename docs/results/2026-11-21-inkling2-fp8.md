## Recommendation

- Keep bf16 the default (exact).
- Offer **fp8 attention + fp8 unembed** (`INTARSIA_INK_ATTN_QUANT=fp8 INTARSIA_LMHEAD_QUANT=fp8`, or the recipe keys
  `[tuning.metal] ink_attn_quant = "fp8"`, `lm_head_quant = "fp8"`) as the opt-in fast mode: 64.2 -> 77.7 tok/s (+21 %) on endor,
  G3 short / long inside the bounds; on cpu no worse than our bf16 against vLLM with no confident-row miss, on Metal +1.3e-3 / +1.7e-3
  KL and one confident-row miss per set (short: exactly at the allowance of 1; long: under 2). Decode-mode KL rises more
(+3.4e-3) than prefill. It costs about 5e-3 KL against the exact port. If only the head is wanted, the fp8 head alone is +6 % for 2e-4 KL.
- Do not offer mxfp4 dense (fails G3: confident misses, KL 2e-2).
- The user decides on any default.

## Unembed as an exact screen (item 6, brief 2.2)

Script `tools/inkling2_unembed_screen.py` over the oracle's final normed hidden states `h` of the 569 short-golden
positions (`tools/inkling2_dump_hidden.py`, the W4A16 oracle `tools/inkling2_ref.py`, spark1 cpu, fleetq #10831). For each unembed row n,
`|h.W_n - h.Wq_n| <= ||h||_2 e_n` with `e_n = ||W_n - Wq_n||_2` precomputed (Cauchy-Schwarz; also a per-32-column block form,
`sum_b ||h_b|| e_{n,b}`, 72 bound values per row). Greedy: candidates `{n : a_n + b_n >= max_m (a_m - b_m)}`, top-k: the k-th
largest lower bound. The script asserts that the true top-k is always inside the candidates (it was, every position).

Fallback share (positions above a candidate cap): cap 16: 6.2 %, 32: 3.2 %, 64 / 128: 2.8 %, 256: 1.4 %, 512: 0.7 %. The
distribution is bimodal: almost every position has at most 64 candidates, and a 2.8 % tail has 129-565 (flat top logits).

The true error is 0.11 of the row bound (median; max 0.14), so Cauchy-Schwarz is about 9x loose but still enough for fp8: an fp8
screen plus at most a few hundred exact bf16 rows (mean 12 rows = 0.06 MB) gives the exact greedy token while reading 0.46 GB instead
of 0.92 GB (about -0.8 ms / token at 560 GB/s, the brief's 0.6-1.0 ms). Top-20 needs about 1100 exact rows (5 MB) on average,
6700 (31 MB) at p99: still a large saving. A 4-bit copy is useless with these bounds (most rows stay candidates). Open points before
ops 88-91: (1) the bound needs slack for the fp32 accumulation difference between the screen GEMV and the exact rows (about 1e-6
relative; add `||h|| * ||W_n|| * 2^-20`); (2) top-p / temperature sampling needs the full softmax normaliser, which the screen
does not give exactly (bounding the tail mass of non-candidates is possible but not exact); exact greedy and exact top-k are
straightforward; (3) the candidate count has a long tail (max 565 greedy), so the exact pass needs a variable-length gather.
Only the short set (569 positions) was run.
