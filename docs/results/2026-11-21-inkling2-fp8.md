Reading the table:
- **Acceptance (the brief's bar: vLLM's batch / chunk noise, about 1e-2): fp8 / fp8 passes.** Its KL against our own bf16 is
  4.9e-3 (short) / 5.6e-3 (long), about half of that noise, with no confident-row miss; against vLLM it is no worse than our bf16
  (8.96e-3 vs 9.06e-3 short, 1.28e-2 vs 1.41e-2 long) and inside the G3 bounds.
- **fp8 fails G2 short**, as expected for a lossy mode: 4.39e-3 against the 4e-3 bound set for the exact port (G2 long 5.30e-3
  passes 6e-3). G2 is the exact-port gate; it is not the acceptance bar for an opt-in lossy mode.
- The fp8 head alone is almost free in accuracy (KL 1.6e-4 against our bf16) and worth +6 %; fp8 attention is where the KL goes
  (4.6e-3 against our bf16) and where most of the speed is.
- **mxfp4 attention fails**: 2 confident-row misses on the short set (allowance 1), top-1 94.7 %, KL 2.05e-2 against vLLM (twice
  the bf16 port's, above the 1.05e-2 G3 bound). The q / k L2 clip and the 16-dim relative projection (Fable's risk note) do not
  survive 4-bit weights with plain per-32 e8m0 scales (long set: 5 confident misses against vLLM, allowance 2; KL 2.98e-2). Not recommended; finer 4-bit (NVFP4 per-16 with e4m3 scales, or keeping
  `wr_du` / `wq_du` at fp8) is the only variant worth a later try.
- Fused e4m3 `InkInProj` vs three `MatmulFp8` packs: +4.7 tok/s (fp8 / bf16) and +5.7 tok/s (fp8 / fp8); the existing `MatmulFp8`
  GEMV reaches only ~330 GB/s at these shapes (below), so the contract extension was worth it.
- The tiny tests (`tests/inkling2.rs`) under `INTARSIA_INK_ATTN_QUANT` fail 3 of 8, as expected: g1a / g1b compare against bf16 /
  f64 oracles, and `no_kernel_refusal_names_the_op` expects a load without the `InkInProj` kernel to fail, which a quantised load
  no longer needs (packs). The default path passes 8 / 8 on cpu and Metal. Separately, `tests/inkling2.rs` does not compile on

- Greedy text diverges from bf16 within the first ~10 tokens in every quantised mode (expected for changed numerics); fused and

- Keep bf16 the default (exact).
- Offer **fp8 attention + fp8 unembed** (`INTARSIA_INK_ATTN_QUANT=fp8 INTARSIA_LMHEAD_QUANT=fp8`, or the recipe keys

### Is the screen's bound rigorous? (brief 13, answer only; nothing flipped)

**Short answer: the fp8 side is rigorous; the claim "screen on == screen off, bitwise" rests on one assumption that is tested,
not proved: that `LogitsGather` rounds exactly as the head kernel does.** Greedy output is exact by construction only if that
assumption holds, so the screen is a default *candidate* once that gap is closed (or accepted) and the longer B16 ABAB passes.

**What is proved.** Let `x_n` be the logit the bf16 head would compute on the device, `a_n` the screen's fp8 GEMV output, `h` the
bf16 activation row (`D = 2304`), `u = 2^-24`, `g = (D+2)u/(1-(D+2)u)`.

1. *The screen GEMV's inputs are exact.* The screen copy is weight-only fp8 (`quantize_host(HeadQuant::Fp8, ..)`, input
   scale 0, `act_quant: false`), so `fp8_xprep_bf16` passes `h` through unrounded (`is > 0 ? q(x) : x`), and the kernel reads it
   as f32 (exact from bf16). e4m3 codes decode through half as value / 256, exact; the 256 is folded into the power-of-two
   part of the scale. Every product `q_nk h_k` and `W_nk h_k` (bf16 x bf16) is exact in f32.
2. *Any summation order is covered.* Both kernels (`fp8_dot16` 16-term fma chains, per-lane adds, `simd_sum`; the bf16 head's
   `dot8` and `simd_sum`) evaluate a tree of correctly rounded f32 adds and fmas of depth at most `D + 1`, plus one scale
   multiply. For any such tree `|computed - exact| <= g * sum |terms| <= g ||h|| ||row||` (Higham, Lemma 3.1 and eq. 4.4). The
   proof does not depend on the order the compiler or `simd_sum` chooses, and contraction of `a*b + c` into an fma only removes
   roundings. So `|x_n - h.W_n| <= g ||h|| ||W_n||` and `|a_n - s h.q_n| <= g ||h|| s ||q_n||`.
3. *The margin covers the quantization error and both rounding errors.* `beta_n = (||W_n - s q_n|| + g(||W_n|| + s||q_n||)) *
   (1 + 2^-20)`, computed in f64 from the weights at load. Its own f64 rounding (about 1e-16 relative) is about 1e10 times below
   the `2^-20` pad; the pad is not directed rounding, but it covers it by that factor. With Cauchy-Schwarz,
   `|x_n - a_n| <= ||h|| beta_n`.
4. *`hn >= ||h||`.* `ss` is an f32 sum of `D` squares with relative error at most `g_D` (about 1.4e-4 at D = 2304); `sqrt` adds
   `u`; `hn = fma(sqrt(ss), 1 + 2^-11, 2^-50)` and `2^-11` (4.9e-4) exceeds `g_D / 2 + u` for every `D` up to about 16 000. That
   limit on `D` is not asserted in code: a gap for other models, not for Inkling-2 (2304).
5. *The interval formulas round safely.* `lo / hi = a_n -/+ (hn beta_n + 2^-20 m_n + 2^-96)`; the `2^-20 m_n` term (16 u of the
   magnitude) covers the three or four roundings of these fmas.
6. *Flush to zero and overflow* (0dd775105): a flushed operand or result moves a sum by at most `2^-126` per entry; with row
   norms below `2^20` (checked at load, else the screen stays off) that stays below `2^-99`, inside the `2^-96` term; flushed
   squares lower `||h||` by less than `2^-57`, inside the `2^-50` floor. A row with `m_n > 2^90` (or any non-finite value)
   takes the full head, so no partial sum can overflow.
7. *Selection.* With `lo_n <= x_n <= hi_n` for all n and `L = max lo`, every maximiser of `x` has `hi >= x* >= L`, so it is a
   candidate. Above the cap (64), on non-finite values, or for non-bf16 rows, the full head runs. Ties go to the lowest index,
   as in the head's argmax.

So **the true argmax of the head's device logits is always among the candidates.** This part is rigorous.

**The gap: the gathered values must be the head's bits.** The token is the argmax of the candidates' values as `LogitsGather`
computes them. It equals the full head's token if those values are bitwise the head kernel's `x_n`, which no inequality gives.
`logits_gather_f32o_v` repeats `gemv_f32o_v`'s per-row code (same `dot8` blocks, same lane order, same `simd_sum`), and the
build uses `-O3 -fno-fast-math`. But identical source in two kernels is not a formal guarantee of identical rounding: the
compiler may contract or schedule differently in each. This is covered by tests, not proof:
- Metal admission of `logits_gather_f32o_v`, bitwise against the cpu reference;
- `tests/screen.rs` `gather_is_bitwise_the_head_logits` (bitwise against the real head kernel);
- md5 off == on across 12 x 256 + 5k (#11180), every #11189 / #11248 rep, the merged-tree scope runs (#11247) and the forced
  fallbacks (#11338).

If the bits ever differed, the damage would be bounded: the chosen token would still be a candidate whose logit is within about
one ulp of the head's maximum, so only near-exact ties could flip.

Two smaller dependencies:
- With P12 default on, the unscreened head runs the P12 kernel (`head_p12`). Screen on == off then also needs P12's head to be
  bitwise `logits_bf16_gemv`, which is P12's own claim (`quant/p12.rs`: "bitwise their bf16 twins"), checked by that lane.
- The first-use check selects the screen by kernel name (`logits_bf16_gemv` / `_rows`). A new head kernel turns the screen off
  rather than breaking it.

**Ways to close the gap** (none done; each is a decision for the coordinator):
- (a) Run the gather through the head's own kernel: a `gemv_f32o_v` launch over the candidate rows (row-index indirection in
  the same function), so both paths execute one compiled body.
- (b) Accept the tested equality as the gate, as the repo does for other "bitwise twin" kernels (P12, rows-exact), adding a
  load-time self-check: gather vs head on a few random rows, screen off on any mismatch.
- (c) Add the `D < 16 000` assertion (item 4) before the screen serves another model.
