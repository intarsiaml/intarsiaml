# postchain2: one event at the real chain's position, 3-row vs 8-row chains, and nsys (CUDA, Qwen3.6-35B-A3B NVFP4, spark1)

Lane `postchain2`, branch `postchain2` from origin/postchain (PR #442 head `10b99f7af`), for the PR squashed onto origin/main `6542ed9eb`
(the binaries measured are named under "Change of plan"). Follows `docs/results/2026-11-18-postchain.md` ("next measurement").
spark1 (DGX Spark GB10) with vLLM up beside it; fleetq `--quiet gpu,cpu` for timing, `--load cpu` for the build; CARGO_BUILD_JOBS=3 MAX_JOBS=3
FLASHINFER_NVCC_THREADS=1, fleetq `--mem 55`, free-memory watchdog `scripts/postchain2/wd.sh` (kill below 15 GB available) on every build and serve.
Raw output: `docs/results/2026-11-18-postchain2/raw/`; scripts: `scripts/postchain2/`. Nothing default-on.

**Result: the post-chain offset is named and an opt-in fix removes it in the trace.** After ANY eager decode / verify pass that uses the real
side stream (a copy chain's verify, a bogus or accepted probe chain, even one eager 3-row MTP step), the captured MTP step's graph replays run in a
slow mode for the next ~25-200 replays (0.5-4 s): the graph's kernels are not slower, but every dependent node starts ~0.4 us later after its
predecessor ends (median gap 0.480 us vs 0.096 us), about 650 node boundaries per replay, so +0.25 ms of idle per replay (0.32 vs 0.07 ms).
The mode then ends by itself, mid-request. That is the "+0.17..0.28 ms in the next request, fading two requests later". Base servers most likely
run it too (not traced): every server ends most 300-token requests with an eager 1-draft MTP step, the same kind of pass. New opt-in `INTARSIA_SIDE_EAGER=0` (forks onto the side stream only inside graph
captures; eager passes run on one stream) leaves 0-1 slow replays where the controls have 69-116.

- Step 1 (one event at the real chain's position 828, no-event null `nc` in every round, 3 rounds instead of 5): every single event raises MID1
  against `nc`: `e` (one eager MTP step, no chain) +0.317 (SE 0.033, 3/3), `L2` +0.306 (0.022, 3/3), `L7` +0.238 (0.042, 3/3), `a7` +0.155
  (0.064, 3/3); `n20` +0.186 (0.105, 2/3). So neither a chain nor acceptance nor 8 rows is needed: one eager pass is enough (reading "`e` +").
- Step 2 (3-row vs 8-row): `L2` (3-row bogus chain) is as high as `L7`; `c3` (`INTARSIA_SPEC_COPY=20,3`, 4-row passes) +0.199 (0.117, 2/3), not
  lower than `n20`. Row count is not the trigger.
- Step 3 (nsys, graphs traced per node, MID1 of each server): per-kernel durations do not grow (the per-name differences are inside the
  base-vs-base null, and slightly negative); what grows is idle time inside the replay, bimodal per replay (0.069 ms or 0.32 ms), in runs that
  start at the beginning of the request after the event (or right after an in-request chain) and stop by themselves. Base servers: 0 slow
  replays of 267 in MID1 (3 of 3); event servers: 26-185 slow.
- Step 4 (fix): `INTARSIA_SIDE_EAGER=0` (opt-in, new): `e` controls 98 and 69 slow replays in MID1, `e` + knob 0 and 0, n20 + knob 0 and 1
  (and no eager kernel on a second stream). Code-gen ABBA (4 rounds): n20 / base 0.9869, nx / base **0.9968**, nx / bx 1.0016 (lifted by one slow
  bx server; 0.9961 without it); the graph-step offset of n20 (+0.159 ms) is -0.007 ms with the knob. Gates pass.

## Step 3: nsys over MID1 (`raw/ns1/`, `raw/ns1-*.txt`; `scripts/postchain2/nsys.sh`, `nsys_an.py`, `nsys_cmp.py`, `nsys_ovl.py`, `nsys_mode.py`)

in the order b1 e1 n1 b2 n2 e2 b3 (`b` base, `e` one eager MTP step at g = 754 in MID0 (`ONCE=1`), `n` `INTARSIA_SPEC_COPY=20`: its chains at 828 in
MID0 and 665 in MID1). Tracing costs about 0.1 ms per step (median replay span 17.5-17.7 ms, untraced step 17.4 ms). The captured MTP step is one
graph of 1006 nodes (~265 replays per MID1; a 1004-node variant 22 times), on two branches: 715 nodes on the main stream, 285 on the side stream
(the shared-expert and k / v / z / b / a projections of `INTARSIA_MOE_SHARED_STREAM` / `INTARSIA_SIDE_PROJ`) overlapping it by ~5 ms per replay.

1. **Kernel durations do not grow.** Per kernel name, summed over its nodes, n - b and e - b are inside the null (b2 - b1, e2 - e1, n2 - n1) and

2. **Idle time inside the replay grows, and it is bimodal.** Per replay: span (first node start to last node end), union (time at least one node

## Change of plan at 04:27 EST (after rounds 1-3 and the first nsys run)

Rounds 1-2 and the first nsys run (`raw/ns1/`, below) named the mechanism: after any eager decode / verify pass, the captured MTP step's graph
replays run in a slow mode for the next ~25-200 replays, every dependent graph node starting ~0.4 us later. So the batch was stopped after round 3
(rounds 4-5 not run; the 4-of-5 bar of the design above cannot be met, results are reported as n of 3 with SE) and the time went to a fix.

Fix candidate (opt-in, new): `INTARSIA_SIDE_EAGER=0`: the side-stream forks of `INTARSIA_SIDE_PROJ` / `INTARSIA_MOE_SHARED_STREAM` (default on) are
taken only inside a graph capture; an eager pass runs its side launches in order on its own stream. Rationale: the eager passes are the only place where
the process launches on the real side stream (a high-priority stream, `ik_rt_stream_create_high_priority`); in ns1 every MID1 with an eager pass before
it shows eager kernels on that stream and then slow replays.

Builds from here on: origin/main `8b994f55b` (with #442, #443) as `intarsia-main`, and this branch merged with it as `intarsia`. Rounds 1-3 and ns1
used the pre-merge build of `10b99f7af` + the scripts (no engine change).

Fix test, decided before it runs (`raw/ns2/`, nsys over MID1 as in ns1, REF 500 tokens, probes with `ONCE=1`): arms in order `e1 ex1 nx1 ex2 nx2 e2`;
`e` = one eager MTP step at g = 754 in MID0, `ex` = `e` + `INTARSIA_SIDE_EAGER=0`, `nx` = `INTARSIA_SPEC_COPY=20` + `INTARSIA_SIDE_EAGER=0`. Readout:

**Works:** `ex` and `nx` about 0 slow launches (also none after `nx`'s own MID1 chain at 665) while both `e` controls show slow launches, and no
eager kernel of `ex` / `nx` on a second stream. **Does not work** (slow launches in `ex`): the trigger is eager launches in general, not the side
stream; then no ABBA, write-up only.

ABBA, decided before it runs (only if the fix test works; `scripts/postchain2/ab.sh`, as cpupin's test 1: code-gen 800 tokens, 8 reps per server
after 2 warm-ups, 4 rounds, order reversed on even rounds): arms `base`, `n20` (`INTARSIA_SPEC_COPY=20`), `bx` (`INTARSIA_SIDE_EAGER=0`), `nx`

## Verdict and revert

The CUDA post-chain slowdown is the slow graph-replay mode that an eager pass on the side stream starts. `INTARSIA_SIDE_EAGER=0` (new, opt-in,
off by default) keeps eager passes on one stream: in the trace it leaves 0-1 slow replays where the controls have 69-116, it removes n20's
