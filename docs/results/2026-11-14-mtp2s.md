## Step 1: where a 2-sequence verify iteration goes

### Method

`scripts/mtp2s/prof.sh` (fleetq #9296, spark2, binary at main df26332d2 + scripts): a fresh `intarsia serve --max-batch 2 --mem-budget 40
--max-seq 8192` per arm under `nsys launch -t cuda,osrt --cuda-graph-trace=node`, two warm-up rounds (graph captures), then a traced window of
2 greedy streams x 256 tokens (`gen2.py`, natural English prompts, thinking off). `seg.py` cuts the trace into passes at every device-to-host
copy (each pass ends with its token download), groups them by (captured, kernel count) and sums kernel time per op class over all streams.
Arms: **P1** 1 stream, no drafting (`INTARSIA_BATCHED_MTP=0`); **P2** 2 streams, main default (`batched_mtp = 1`: no drafting at 2);
**S1** 1 stream, main default (the captured solo spec step, k = 2); **V2** 2 streams, `INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1`, k = 2;
**V2k1** the same at `--spec-k 1`. Raw: `raw/prof/seg-*.txt` (tables and top kernels), `gen-*.txt`, `metrics{0,1}-*.txt`, `serve-*.log`.

| P1 plain decode, 1 row | graph | 3.13 | 0.23 | 0.42 | 0.29 | 1.28 | 6.83 | 0.65 | 11.69 | 0.07 | 11.75 | 0.28 |

Kernel names per class: `raw/prof/seg-*.txt` (`--names` section).

### One V2 iteration (2 streams, k = 2), against two plain steps

- 101 batched verify passes and 406 head passes in the window: **4.0 head passes per iteration** (per sequence: the catch-up pass that
  yields draft 1, and the chained pass for draft 2). Each is a separate eager pass with its own token download.
- Iteration = verify 26.8 + 4 x 1.88 (drafts) + gaps = **~34.5 ms** profiled (unprofiled `intarsia_batch_step_ewma_ms` of that server:
  32.8 ms). Acceptance in the window 286 / 445 = 64.3 %, so 2.28 tokens per sequence per pass, **4.56 tokens per iteration**:
  4.56 / 34.5 ms = 132 tok/s (measured 134.7 in the window).
- Plain: 15.05 + 0.42 = 15.47 ms per 2 tokens (128.1 tok/s measured). **Break-even** iteration = 2.28 x 15.47 = 35.3 ms;
  **+8 % needs <= 32.7 ms**, i.e. about 2 ms (profiled: ~1.8 ms more) must go.
- Where the 34.5 ms goes: verify MoE experts 11.1, verify projections ~6.8 on the main chain (9.8 summed with the overlapped shared
  expert), verify GDN 2.1 (the 180 row-by-row launches of `gdn_delta_dec` / `gdn_conv` / `gdn_conv_state`, 0.55 ms in the 2-row step),
  verify lm_head 1.35, attention 0.6, **eager idle 3.9** (CUPTI inflates eager launches; the unprofiled ewma says ~1.7 ms of the profiled
  iteration is tracing overhead), and **drafts 7.5, of which 5.0 is the head's full-vocabulary lm_head** (4 x 1.25 ms).
- k = 1 (V2k1): 4 verify rows (22.2 ms) + 2 head passes (3.7 ms) = ~25.9 ms for 2 x 1.77 = 3.54 tokens (acceptance 77 %): 136.7 tok/s
  (measured 135.8), the same place as k = 2.

### The hypothesis "MoE expert bytes scale with the distinct experts touched"

MoE expert time by rows: 1 row 3.13 ms, 2 rows of two sequences 6.00 (1.92x: two sequences share almost no experts), 4 rows (2 seqs x 2)
8.76, 6 rows (2 seqs x 3) 11.14 (1.86x the 2-row step for 3x the rows; gate/up 7.41 vs 3.87, down 3.72 vs 2.13). So consecutive rows of
one sequence do share experts (or L2 lines), and the decode MoE kernel already gets that reuse without a dedup pass. A uniform
distinct-experts model would predict ~2.8x; the measured 1.86x leaves an expert-grouped verify kernel little headroom (at most a few ms
of the 11.1, with bitwise risk). The **whole** verify pass costs 1.53x a 2-row step in GPU busy time (22.9 vs 15.0) and 1.78x in span
(eager): not the 2-3x the hypothesis predicted. The pass cost is not the main problem; the draft passes around it are.

### Graph or eager

The plain 2-row step and the solo spec step replay captured graphs. The batched verify (`Model::forward_verify_batch`) runs eagerly
(1464 launches), and so does every head pass of the deferred-verify path (`Seq::prepare_with(.., defer_verify)` calls `Model::mtp_draft`,
one pass and one download per draft position per sequence).

### Levers, by size (ms per V2 iteration, profiled)

| lever | saves | code | risk |
|---|---|---|---|
| reduced draft head, `--mtp-draft-vocab 65536` (exists; verify keeps the full head, so ids are unchanged) | ~3.6 (4 x (1.25 - ~0.33)), also ~1.8 per solo pass at 1 stream | none | acceptance on text outside the first 64k ids (the LOG: CJK on the 27B HIP 65.9 -> 51.4 %) |
| graph-capture the batched verify | up to the eager idle, ~2 unprofiled | large (ragged rows, per-sequence state and save buffers) | medium |
| one 2-row head pass for both sequences per draft position | ~1.25 lm_head + ~0.4 head layer per position, x2 | medium (`mtp.rs`, engine; #371 edits nearby) | low (drafts only propose) |

| expert-grouped verify MoE | < 2-3 | large (kernel) | bitwise |

## Step 2: what was built

**`INTARSIA_VERIFY_TOPK=1` (opt-in, off by default).** In a batched verify pass, a sampled (keyed) sequence's rows come back as the
device-side top-k of each row (`HeadMode::LastTopK(k)`, the candidates a plain batched decode step already asks for under device-side
sampling, R3b) instead of whole logits rows, when the request's sampler takes the top-k in a plain step for every row of the pass
(`Seq::topk_for`: `1 <= top_k <= 64`, no stop-id mask, logit trace or constraint). One `topk_rows` call covers every row of the pass; a
row holding a NaN comes back as logits, as in batched decode. The draw goes through `Seq::token_from` as before, which already takes a
`TopK` row (`Sampler::sample_topk`, exact against the full-row draw); so a seeded request's tokens are unchanged.

Code (small, in the files #371 also touches):
- `model.rs`: `forward_verify_batch_run` takes a head mode per sequence (`None` / `LastLogits` / `LastTopK(k)`) and returns `StepOut`
  rows; new `Model::forward_verify_batch_rows`; `forward_verify_batch_logits` keeps its signature (the CPU test uses it).
- `model/batch.rs`: `batch_topk` is `pub(super)`.
- `engine/batch.rs`: `BatchedOptions::verify_topk` (env `INTARSIA_VERIFY_TOPK`, only with batched verify); the deferred verify of a keyed
  sequence asks for `LastTopK(k)` when `Seq::verify_topk(rows)` gives one `k` for all its rows; `verify_step` accepts `LastTopK`
  and hands the rows through unchanged; a startup line names the setting.
- `engine/keyed.rs`: the keyed acceptance takes `StepOut` rows; `Seq::verify_topk`.
- `docs/tuning.md`: the knob's row.
