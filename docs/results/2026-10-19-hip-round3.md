## 1. Result

* 35B prefill, interleaved A/B, 3 rounds, same windows: **1024 / 4096 / 16384 tokens 3181 / 3726 / 3135 to 4743 / 5681 / 4450
  tok/s (+49 / +52 / +42 %)**; 128 tokens 1219 to 1681 (+38 %). Decode unchanged (140.3 / 140.1 tok/s at 128 tokens).
* Every output is **bit-identical** to base: the new kernels are bitwise the kernels they replace (kernel tests), and the 35B
  short golden, the 35B long golden with the prefix-reuse gate, both 8B fp32 goldens and 256 greedy ids after a 4408-token
  prompt all equal base to the last printed digit.
* Lever 1, `matmul_fp8_mma_v2`: the W8A8 dense GEMM quantised the activations again in every block along N (64 times at N = 8192)
  and decoded the fp8 weights in software. Now the activations are quantised once per call into the existing workspace, and the
  gfx12 conversion instruction decodes the fp8: 21.8 to 70.7 TFLOPS (qkv, M = 4096), 516 to 143 ms per 4408-token prefill.
* Lever 2, 64-pair MoE tile: each dequantised NVFP4 weight fragment feeds four WMMAs instead of two when the experts are busy:
  MoE experts 32.7 to 40.3 TFLOPS at T = 4096, 227 to 197 ms per 4408-token prefill.
* Resident memory: unchanged, workspace 167 905 792 B in both plans (the MoE scratch is the largest).
* Radiance downtime 13.5 min over 4 windows (cap 60).

## 3. Choice of levers

Both need no weight layout change and no new resident memory, and both keep the products and the order of the f32 additions
exactly, so they can be bitwise:

1. The fp8 GEMM was 44 % of prefill at 11 % of the bf16 WMMA peak. The microbench (`pfb`, hot caches) splits that cost: the same
   kernel on weight-only activations ran 2.3x faster than on W8A8 (50.3 against 21.8 TFLOPS at qkv, M = 4096), so most of the
   time was `Fp8Policy::xprep` (`__fdiv_rn`, software `ik_f_to_e4m3` and decode per element, per block). `f8_actq_kernel` (the
   opt-in f8 path's quantiser) already produces exactly xprep's rounding as e4m3 bytes, once per call. The weight decode was the
   rest (v2 runs weight-only at 67.8 against 50.3 TFLOPS).
2. The HIP MoE kernel already has what the CUDA W4A16 change built (weights dequantised into registers, each wave owns distinct
   rows, only the activation tile in LDS; resource dump: 160 VGPRs, 9 waves/SIMD, no spills). Its remaining cost is the decode
   of each weight fragment (8 LDS table reads, 8 multiplies, 4 permutes, a scale decode) for only two WMMAs. A 64-pair tile gives
   it four. The tile size does not touch any pair's arithmetic.

Not taken: the GDN delta rule (now 31 % of prefill) needs a chunked formulation that changes the summation order (its own
accuracy campaign, not bitwise); splitting state rows over more lanes was a dead end in round 2.

## 4. What was built

1. `matmul_fp8_mma_v2` (`kernels/hip/fp8.hip`, `Fp8PolicyQ`; ABI in `kernels/hip/ik_hip_abi.h`, HIP-only). The launcher runs
   `f8_actq_kernel` (exits for weight-only activations) into scratch, then the `dq_gemm` tile loop of `matmul_fp8_mma` with a
   policy that loads the e4m3 activation bytes (8 per chunk, half the bytes) and decodes them to bf16 when the tile is stored, and
   decodes the weight chunk with `v_cvt_pk_f32_fp8` + one byte permute per pair (`ik_e4m3x8_to_bf16` in `ik_quant.h`; every e4m3
   value is exact in f32 and in bf16, so the bf16 is the top half of the f32). Same LDS tiles, same WMMA sequence: bitwise
   `matmul_fp8_mma`. Weight-only activations are read as bf16 as before. `ik_dq_gemm.h` gained an optional `xload` policy hook
   (`dq_xload`; the other policies keep the bf16 load) and a `DqArgs::xq` field.
   Registration (`quantmoe.rs`): op `MatmulFp8`, same predicate as `matmul_fp8_mma` (`K % 16 == 0`), priority 1 (above
   `matmul_fp8_mma` 0, below the GEMVs 10 / 20 and the opt-in `matmul_fp8_mma_f8` 5), scratch `M * K + 16` bytes, deterministic,
   same tolerances. `matmul_fp8_mma` stays registered (admission, and the bitwise reference of the tests).
2. `moe_wmma_kernel<GATEUP, PAIRS>` (`kernels/hip/moe_wmma.h`) with PAIRS 32 or 64, and `moe_wmma_launch<PAIRS>` in `moe.hip`.
   `INTARSIA_HIP_MOE_PAIRS` = 32 | 64 | unset/0 (auto: 64 when the average expert has >= 32 pairs, i.e. T >= 1024 at the 35B's
   256 experts, top-8). Measured (`pfb`): T = 312 32-pair 11.8 / 64-pair 10.8 TFLOPS, T = 1024 22.9 / 29.2, 2048 27.2 / 34.5,
   4096 32.7 / 40.3. 64-pair: 235 VGPRs, 6 waves/SIMD, 34.9 KB LDS (gate/up), no spills.
3. Tests: `tests/fp8_mma_v2.rs` (new), `tests/moe_pairs.rs` (new), registry tests in `src/quantmoe.rs`, `bench_prefill_shapes`
   gained the v2 column, a weight-only row and both pair tiles. Scripts as listed above.

## 9. Memory

No new resident memory. The v2 scratch (M * K + 16 B: 16 MB at a 4096-token chunk with K = 4096) lives in the one plan workspace,
whose size is the largest scratch of any kernel: the MoE experts' 167.9 MB at chunk 4096. Measured: 167 905 792 B in both plans.
The unit test `fp8_v2_scratch_stays_below_the_moe_workspace` pins that ordering for chunks 5 to 8192. The 64-pair tile only uses
more LDS per block (34.9 against 17.5 KB) and registers. A model with fp8 dense layers and no MoE would get a workspace of
M * K bytes it did not have before (none is served on HIP today).

## 10. Uncertain or not done

* The fp8 GEMM is at 70 TFLOPS (37 % of the 191 bf16 peak). Next on that kernel: weights straight from global into A fragments
  in the existing k-slot map (lane half h reads bytes h*8..+7 and 16+h*8..+7 of each 32; no re-layout), a WM = 1 tile; not tried.
* GDN delta rule, 31 % of prefill now: needs a chunked, non-bitwise formulation (own accuracy campaign).
* Decode: 22 % of each step is launch gaps; only fusion (fewer of the 578 launches) addresses it.
* `INTARSIA_HIP_MOE_PAIRS` is read with `getenv` at every MoE launch (so one test process can compare the tiles); the cost is
  negligible next to a ~2 ms launch, but it differs from the read-once style of the other knobs.
* The auto threshold (32 average pairs) is set from hot-cache microbench points at T = 312 and 1024; T between them was not measured.
* The v2 128x128 kernel spills 12 bytes per lane (two 8-byte values, outside the WMMA chain per the ISA dump); not investigated.
