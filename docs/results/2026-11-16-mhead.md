# mhead (2026-11-16): the chained one-row MTP head passes of a batched draft as one pass (2-stream 35B NVFP4, spark2)

Lane `mhead`, branch `mhead`, worktree `.worktrees/mhead`, from main 914267d89 (#413). Follows `docs/results/2026-11-16-mdraft.md` (which batched only the draft lm_head and its argmax) and `docs/results/2026-11-16-mtp2s.md`.

## Verdict

**Ship, default-on for CUDA (`INTARSIA_BATCHED_HEAD=0` off), bitwise, but it clears the stop rule narrowly: 2-stream iteration 28.18 -> 27.86 ms (-0.32 ms; bar 0.3), draft (`prepare`) 3.79 -> 3.40 ms (-0.39 ms), 2-stream tok/s 1.0091x (1.007-1.011x on the 10 cells; bar 1.008x), 1 stream unchanged.**
mdraft estimated about 0.5 ms; the head layer pass is launch- and weight-read-bound, but only the projections are shared between the rows: the MoE experts of the two sequences are mostly distinct and the attention is per row, so 0.39 ms is what the batching removes. Two of the ten cells are at 1.007x, under the bar on their own; the geomean and the iteration saving are over it. Bitwise-neutral and default-on is the brief's rule for this case; a reviewer who reads 0.32 ms / 1.009x as noise can set the default off by flipping `batched_head` in `crates/intarsia-backend-cuda/src/device.rs` (one line).

## What it does

A drafting step is, per sequence: a catch-up pass of the head layer over its n queued rows (n = 1-3), the lm_head + argmax of the last row = draft 1, then k - 1 chained ONE-row passes, each followed by lm_head + argmax. mdraft batched the lm_heads; at k = 2 each sequence still ran its own chained pass (2 per iteration). Now `Model::mtp_draft_batch` runs the chained pass of all b sequences as one b-row pass (`Model::mtp_layer_batch`, `crates/intarsia-core/src/model/mtp.rs`):

- every projection and the MoE run on the backend's row-exact multi-row kernels (`exact_rows`): the bf16 GEMVs (`matmul_bf16_gemv` -> `matmul_bf16_gemv_rows`), and the head's routed experts, which are NVFP4 (`routed experts quantised to nvfp4` in the serve log; the `_bf16` in the kernel names is the activation dtype, the weights are `U8`): `moe_experts_decode_v2_bf16` (M = 1) -> `moe_experts_decode_v2_rows_bf16` (M = 1..16, picked under `exact_rows`). Each rows twin is bitwise the one-row kernel per row by `crates/intarsia-backend-cuda/tests/rows_exact.rs` (`moe_decode_rows_are_bitwise_the_one_token_kernel` at the 35B expert shape). The M = 1 fused pair (`matmul_pair_bf16_gemv`, router + shared-expert gate) has no kernel at M >= 2 and runs as the two single GEMVs, which `fused_decode.rs::matmul_pair_is_bitwise_two_gemvs` proves bitwise the pair. This is the argument of batched decode of the main model; the in-situ device check below is the evidence for the head's own shapes;
- the row-parallel ops (embedding, rmsnorm, add) have no row-count dependence;
- the attention is per row: `attn_block_batch` with `tabs = false` (new parameter) runs each row's q-norm / rope / KV append / decode attention as the solo one-row calls on that sequence's own head cache at its own position. `tabs = false` keeps it off the row tables (`row_tab` holds the main model's slots; a head cache is not one);
- the cache is not advanced by the pass; the caller commits each row's token as before and truncates to the committed length after the draft, so #406's prefix-store state handling (cache length / queue / sync) is untouched (asserted by the unit test).

The 1-3-row catch-up passes stay per sequence (a 2-3-row catch-up picks `moe_experts_bf16`, a row-exact batched pass would pick a different kernel: not bitwise). Falls back exactly as mdraft's batched draft does (1 or more than 8 sequences, different adaptive depths, subset head, TP, ...); `Backend::batched_head` (default false: Metal, HIP, CPU unchanged) adds the CUDA claim, `INTARSIA_BATCHED_HEAD=0` per `docs/tuning.md`. k = 1 has no chained pass, nothing changes.

Coverage limit of the device check: at k = 2 a chained pass's K/V row is truncated right after the draft, and the check mode then overwrites it with the serial pass, so the check compares the output rows (which attend over the row the pass appended) but not the K/V bytes a second chained pass would read at k >= 3. k >= 3 is covered by the CPU unit test only.

Dev check `INTARSIA_BATCHED_HEAD_CHECK=1` (docs/tuning.md): after every batched chained pass the per-sequence passes run on the same inputs too, the draft continues from those, and the two sets of output rows are compared bit for bit on the device's real weights (the CPU unit test cannot see CUDA numerics; the ids gate cannot see draft drift, because verify fixes the output).
Trace: `INTARSIA_SPEC_TRACE` verify lines now end with the drafted ids (`drafts [a, b]`), so the gate compares drafts, not only accept counts.

## Not built / follow-ups

- The catch-up passes (1-3 rows) are not batched. The all-n = 1 case (both sequences accepted nothing) would be a one-row pass and batchable bitwise; it was not built: it needs the rows of the two sequences' queues gathered first, and the gain is the same ~0.4 ms on a minority of iterations.
- k >= 3 batches every chained pass; only k = 2 was measured.
- The MoE experts (mostly distinct per sequence) and the per-row attention are not shared, so the saving is bounded by the shared projections.
- Only spark2 / 35B NVFP4 measured.
