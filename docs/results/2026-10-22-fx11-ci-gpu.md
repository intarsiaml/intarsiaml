## 2. CI change: type-check the GPU crates with the real-GPU cfgs

Two options were open: install nvcc / ROCm in CI, or add a build.rs switch that skips kernel compilation.
Chosen: the switch. `INTARSIA_CUDA_CHECK_ONLY=1` (cuda `build.rs`) and `INTARSIA_HIP_CHECK_ONLY=1` (hip `build.rs`) emit the
cfgs a real toolkit build emits (`ik_cuda`, `ik_sm120a`, `ik_hip`) and return before compiling or linking anything.
`cargo check` never reads kernel output, so it then type-checks the full GPU Rust code, including the `#![cfg(ik_cuda)]`
test files, which the stub build compiles out.

Why not the toolkit: a CUDA or ROCm install on a hosted runner is gigabytes and minutes, needs a third-party action or
image to pin and trust, and still would not give a sm_121 / gfx1201 device, so it buys no test coverage; a type check does
not need it. What the switch does NOT check: that `kernels/cuda/*.cu` and `kernels/hip/*.hip` compile, and linking. Those
stay on the fleet builds. A check-only artifact cannot link or run; the variable is set on the CI check steps only and
documented in `docs/tuning.md` (the drift test `docs_env_vars` requires a row).

New jobs in `.github/workflows/ci.yml`:

* `check-cuda`: `cargo check --locked -p intarsia-backend-cuda --all-targets`, `cargo check --locked -p intarsia-cli --features cuda`
* `check-hip`: the same for `intarsia-backend-hip` and `--features hip`

Local run (macOS, `CARGO_TARGET_DIR` private): all four commands finish with no errors (the existing warnings in those
tests are unchanged). Before this change the same commands type-checked none of that code.

## 5. `INTARSIA_CUDA_FAST_PREFILL`: docs, code and the finding

* Code: `crates/intarsia-backend-cuda/src/kernels.rs:95`, `is_ok_and(|v| v == "1")`: only the exact value `1` enables.
* `docs/tuning.md:88`: "off (only exactly "1" enables)". Agrees with the code.
* The finding says the parse "changed from any value to `== "1"` in 9aa73f1b". It did not. `git log -S` shows the variable
  was introduced in 2a0dd539 (2026-10-13) already as `== "1"`; 9aa73f1b only deleted the neighbouring `opt_in_priority`
  helper (the diff line the review likely read). No earlier "any value" or "0 enables" form exists in history, and no
  script in `scripts/` sets it to `0` (the two uses are `=1` and `unset`, `scripts/prefill-cuda/ab-ours.sh`).
* Docs, code and ADR-0008 / LOG.md agree: opt-in, numerics-affecting, off by default. No docs change needed and no engine
  change made.
