## What the cut does, and how ours maps to TensorFold's

Layers 20-39 all read layer 20's compressed KV and index keys (`kv_source_layers = [2, 8, 14, 20]`, test `shared_sources_follow_layer_order_and_ratio`: `kv[20..40] == Some(20)`; the other index sources 24, 28, 32, 36 only re-run the indexer's queries against layer 20's keys). So for a row below `floor = prompt length - 128`, the decoder half produces nothing another row consumes except the layer's own sliding-window keys, which the replay drops. The decoder layers of the replayed rows (positions `floor..`) therefore see no window key before `floor`, fewer than 128 keys for the first rows. That is the approximation; it is TensorFold's, not the reference model's (our copy of the official code, `.worktrees/dsv41-official/model.py`, has no replay).

| TensorFold (`families/dsv41/`) | ours |
|---|---|
| `model.zig fillChunk`: at `li == layers / 2` call `prompt.replayCut`, `replay = prompt length - window` | `replay::cut_layer` (`n_layers / 2` = 20), `replay::floor`, `replay::classify`; the runtime picks the graph per chunk (`Dsv41Runtime::pass_replay`) |
| `replayCut`: layer 20's `attnMixes` and `kvSourceUpdate` over every row of the chunk | encoder part's last stage: the layer's `hc_attn` sublayer and `kv_source_update` (`graph.rs`: the compressor block of `attention`, moved out unchanged) |
| the chunk is cut to the rows at positions `>= replay`: `h[first:]`, `pre[first:]` copied down, `start += first`, `pos += first` | no copy: the decoder part is a second graph built for `t - first` rows at `pos0 + first`, whose first inputs are the encoder part's streams `x0` and last FFN pre-mix `hc_ffn.pre` read in place from row `first` (`name@row` workspace views) |
| "an encoder-only chunk (no row at or past `replay`) ends here", no head, no synchronize | encoder part graph without a head, `Want::Nothing` |
| layer 20's `attnMixes` run again on the cut rows | the decoder part recomputes layer 20's `hc_attn` on the kept rows (same) |
| `attention(.., floor, kv_done)`: no window key before `floor`; layer 20's update skipped | `AttnReplay { floor, skip_kv_update }`; the decoder layers' sparse attention is built at `pos0 - floor`, which turns the kernel's window test `pos0 + row >= window` into "position >= floor" (below) |
| `TF_DS_REPLAY_FLOOR=1` (off by default: ring mode of small chunks reads the slot's previous request's keys below the floor) | always masked, which is TensorFold's `TF_DS_REPLAY_FLOOR=1` behaviour; no stale key is ever read |
| DSpark taps absorbed for the cut rows | the decoder part's `dspark absorb` stage, at the kept rows' positions |
| `engramApply` on the cut rows | refused when an Engram layer lies at or after the cut (the model's are 1 and 14) |

How the window is dropped: both `attn_sparse` kernels in `kernels/cuda/dsv41_attn.cu` use the host `pos0` only in the window validity test (`ok = (p0 + row >= W)`, lines 122 and 311; `attn_eff` returns `pos0` unchanged in host mode, and `nsplit` is computed from the shapes), and `dsv41_ref.rs` tests the same expression. Building the call at `pos0 - floor` (never negative: the decoder part starts at `floor`, a whole chunk past it starts at or above it) moves that test to the floor. `WindowKv`, the ropes and the ring writes keep the true position. No kernel was changed. The option is refused at load on any backend but CUDA (the CPU reference matches the formula but `fast.rs` was not read, and no CPU run is planned).

## How both TP ranks make the same cut and run the same collectives

A rank's plan is a function of `(st.len, ids.len(), window)` and the chunk size only: `floor = st.len + ids.len() - window` is computed once at the start of `Dsv41Runtime::forward`, then each chunk is classified from `(floor, pos0, t)`. The two ranks have identical inputs:

- the primary calls `Worker::forward(ids)`: `r.start_forward(ids, false)` then `self.rt.forward(&mut self.st, ids, logits)` (`dsv41_engine.rs`); the only caller with more than one row is `generate`, with the whole prompt remainder `req.prompt[keep..]`; the other callers pass `[tok]` (decode) or `[bos]` (two warm-up rows, one row each). Nothing splits the prompt before `forward`;
- `RemoteSeq::start_forward` (`tp_remote.rs`) puts all the ids into one `T_FORWARD` message; the other rank's loop reads them all (`b[16..].chunks_exact(4)`) and calls `model.forward_rank(st, &ids, ..)`, which is `Dsv41Runtime::forward(st, ids, false)` (the `RankModel` impl in `runtime.rs`);
- `truncate(keep)` goes to both ranks (`Worker::truncate`), so `st.len` agrees; the chunk size and the replay flag are part of the handshake fingerprint (`dsv41_engine.rs: fingerprint`), so a mismatch refuses to start;
- the head's all-gather is part of every graph that has a head: both ranks build the same graph for a chunk, so an encoder-only chunk (no head) is encoder-only on both.

What the graphs contribute is checked by `dsv41_replay.rs` on the real shapes: on rank 0 of the Mia world-2 cache (headers only), the encoder part has **42** collectives (20 layers x 2 all-reduces + the 2 Engram gathers) and the decoder part **41** (20 x 2 + the head's gather), and the whole extras sequence of each is equal, in order, to the corresponding stages of the plain graph (embed + layers 0-19; layers 20-39 + head). 42 + 41 = 83, the plain pass's collective count. The kv-source update has none (replicated weights). Rank 1's cache was not built against (the structure comes from the config, not the shards).

## The cases

| case | what happens |
|---|---|
| encoder-only chunk (`pos0 + t <= floor`) | `Encoder` graph: embedding, layers 0-19, layer 20's mixes and kv update, no head; `Want::Nothing`; Engram rows for the chunk are issued as always |
| chunk that crosses the floor | `Encoder` graph on all `t` rows, then `Decoder` graph on `t - (floor - pos0)` rows at `floor` (no token ids, no Engram), with the head; the 4106-token example at chunk 2048 is 2048 + (1930 + 118) + 10, so 118 decoder rows in the middle chunk and 10 in the tail |
| chunk at or past the floor | the plain graph with the decoder layers' sparse attention built at `pos0 - floor` (so the window keys before `floor` are not read) |
| prompt of at most 128 tokens | `floor = 0`: `forward` takes the plain `pass` path exactly as without the option, so ids are bit-identical to off by construction (the script's step 1 checks it) |
| chunk 512 and 2048, prompt lengths on chunk boundaries | `replay::classify` is pure and unit-tested for chunks 1, 7, 16, 128, 512, 2048 and totals 1 to 32768 including 127, 128, 129, 511-513, 1023-1025, 2047-2049, 4096: decoder rows always sum to `min(total, 128)`, at most one chunk crosses, order is encoder / cross / whole, and the chunk holding the last row is never encoder-only (`a_prefill_sends_exactly_the_last_window_rows_through_the_decoder_half`). A chunk ending exactly on the floor is encoder-only; one starting on it is whole; one row past the floor gives a one-row decoder part |
| Engram layers (1, 14) | in the encoder half, run on every row as always. An Engram layer at or after the cut is refused at load and by the graph builder |
| DSpark taps (37, 38, 39) | in the decoder half. The absorb stage runs in the decoder part (and in whole chunks) for the kept rows only, at their positions. The drafter's window is the last 128 positions, `floor..`, so the first draft after a prefill reads only rows that were absorbed. A tap at or before the cut is refused |
| decode window ring, first 128 decode tokens | no special handling: decode token `k` reads positions from `total + k - 127`, all `>= floor = total - 128`, all written by the decoder part or a whole chunk. Verify passes and rollback inside a request stay `>= total`. The 128 replayed rows are exactly the ring's content |
| prefix reuse | see below |
| decode, verify, draft, one-row forwards | untouched (`replay_floor` returns none for fewer than 2 rows; a one-row forward's window never reaches below the floor) |

**Prefix reuse.** Rows below a replay's floor skipped the decoder layers, so the state holds valid decoder-layer window keys only from `SequenceState::replay_from` (the floor of the replay that built it; 0 when nothing was skipped). A resumed prefill of a prompt with floor `F` from `keep` cached tokens reads decoder windows back to `F`, so it is safe iff `keep <= F` (nothing below is read) or `replay_from <= F` (the rows `F..keep` were written). `replay::reuse_ok` is that rule. The engine applies it right after `restorable_len` (`replay_keep`): otherwise it prefills from scratch (keep 0), and `Dsv41Runtime::forward` itself returns an error rather than read skipped keys. A chat turn that extends the previous prompt past 128 new tokens reuses it (keep <= F); a turn of fewer new tokens reuses it when the previous floor is not above the new one, which is the usual case. The result depends on the cache history in one respect: the kept rows `F..keep` were computed under the earlier floor (longer windows), not under `F`; a cold run of the same prompt would give slightly different decoder-layer keys for them. The encoder half and the layer-20 compressed KV are bit-identical to off in every case (same ops, same shapes, same chunk schedule). The tracker `replay_from` is per sequence state and identical on both ranks (same ops).

## How a replay chunk runs (read against `pass` / `run_graph`, not run)

`pass_replay` calls `run_graph` like `pass` does. Checked by reading: (1) nothing in `pass`, `pass_replay` or `run_graph` commits; `forward` calls `st.commit` once per chunk after the chunk's graphs, so a crossing chunk (two graphs) advances `st.len` by exactly its `t` rows; `forward` also checks `st.len == start + rows` and `tokens.len() == len` after a replay prefill and errors (resetting the sequence) otherwise. (2) The fifth argument (`host`) is `&[]` in `pass` too; Engram rows are hashed and issued inside `run_graph` from `ids`, so the encoder and whole graphs get theirs, and the decoder part (`ids` empty, no Engram layer) correctly gets none. (3) Absorb stages in a pass read no host input (`dspark.mh` belongs to the separate `build_absorb`); the test now asserts the decoder part with absorb on reads neither `token_ids` nor `host.pos`. (4) Positions come from each step's `pos0` attribute: `host.pos` is uploaded only when a step has `pos` set, which only device-position graphs do, and replay graphs refuse that. The `INTARSIA_DSV41_DUMP_POS` row selection used `st.len` as the graph's first row, which is still the chunk start during a crossing chunk, so a decoder part's rows were selected and named wrongly; fixed (`Exec::row0`, `run_graph_at`, `replay::decoder_pos0` / `dump_hits`, unit test `position_dumps_of_a_crossing_chunk_use_each_parts_own_first_row`). The fix itself has only the pure-arithmetic test: the dump hook has not run.

## Step 7: recent-window items, and how to read them (rule committed 2026-11-04 11:49 EST in 904011f3f, before any item set or model data exists)

**Why.** Step 6's items put every answer-bearing fact far from the prompt end, so they cannot show a defect in the rows the replay actually recomputes (see "What step 6 cannot catch"). Step 7 plants one fact per prompt at a measured token distance from the end of the prompt the server prefills, so that the window and its edge are the thing under test. Replay stays opt-in whatever step 7 says; a result changes what is known, not the default.

**The item.** A log of repo prose with many lines of the form `Vault <Name> code: XX-9999-XX.` (the same form for the target and for the decoys, different names and codes); the question at the end asks for the code of one named vault and says to reply with only the code. The reply is scored by the last code-shaped string in it (`score_code` in `replay-test-lib.py`): exact, no judge, no partial credit, an empty reply is a failed call and never a wrong answer. A blind guess of the code has a chance of about 1 in 3 billion; the realistic wrong answer is another vault's code, which the analysis counts separately (5 or 23 decoy lines per item).

**The distance.** The server prefills `BOS <User> text <Assistant> </think>`, 4 template tokens more than the text (chunk32k-2: `prompt_tokens` minus the manifest's text count was exactly 4 on all 540 calls, `cached_tokens` 0 on all). The replay floor is `total - 128` over that whole sequence (`replay::floor(st.len + rows, window)`, window = `sliding_window` = 128, independent of the chunk size), so the distance of a fact is measured in that sequence: **d = number of tokens from the first token of the fact line to the end of the prompt, template tokens included**. Rows at or past the floor are the 128 rows the decoder half runs on, so a line with `d <= 128` is replayed whole. A line whose first token is below the floor and whose last token is above it is not used (no item straddles the floor).

| bucket | d (tokens from the fact line's first token to the end) | what it is |
|---|---|---|
| 1 | up to 64 | inside the replayed rows, with the question next to it |
| 2 | 65 to 128 | inside the replayed rows, up to the first replayed row |
| 3 | 129 to 256 | the whole line below the floor: the first rows the decoder half skips |
| 4 | 257 to 1024 | below the floor, near |
| 5 | 1025 to 4096 (at 4K prompts: up to half the prompt) | below the floor, mid |
| 6 | at least half the prompt away | far control |

**Sample size.** 12 items per bucket per length, 4K and 32K prompts (144 items), run at chunk 2048 by default (chunk 512 for the 4K items only if the time allows; see the script). Off and on answer the same item. Per chunk size, the rule reads each bucket **pooled over the two lengths: 24 pairs per bucket**, 72 pairs in buckets 1 to 3 together. The per-length rows (12 pairs) are printed but decide nothing.

**Reading rule.** b = pairs where off is right and on is wrong, c = pairs where on is right and off is wrong (concordant pairs do not enter). Per chunk size, the replay counts as DEFECTIVE when any of these holds:

1. In bucket 1, 2 or 3 (pooled, 24 pairs): **b >= 4 and b - c >= 4**.
2. In bucket 4, 5 or 6 (pooled, 24 pairs): **b >= 5 and b - c >= 5**. A loss in the far control means the damage is not specific to the recent window.
3. Buckets 1 to 3 together (72 pairs): the exact one-sided sign test on b against c has **p <= 0.01** (for example b = 9, c = 0 spread as 3 + 3 + 3, which rule 1 alone misses).

Nothing else counts: c larger than b is never a defect (a gain of 4 or more is printed as "on better, review"), and a cell where off itself is right on fewer than two thirds of the pairs is printed as uninformative. The measurement itself is invalid, and the step FAILS, when any call errored or returned an empty reply, a `prompt_tokens` differs from the manifest (then the distances are not the manifest's), `cached_tokens` is above 0 (a prefix hit moves the chunk schedule and the floor), an item is missing in an arm, or the dataset's sha256 differs from the frozen one. A DEFECT does not stop the later steps; it is the step's reported status.

**What the rule can see.** Rounding alone moved 13 of 180 answers (7 %) between two layouts in chunk32k-2, roughly half each way, so a bucket of 24 pairs expects about 2 discordant pairs, split. A Monte Carlo of the rule with that noise (`replay-test-lib.py rulepower 24 0.07`, 40000 runs per row, seeded; the true loss q is the share of pairs where on loses an answer off gets right, equal in buckets 1 to 3, noise only elsewhere):

| true loss q in buckets 1-3 | 0 | 0.05 | 0.10 | 0.15 | 0.20 | 0.30 |
|---|---:|---:|---:|---:|---:|---:|
| P(rule fires) | 0.016 | 0.244 | 0.632 | 0.885 | 0.974 | 1.000 |

So a false DEFECT happens about once in 60 runs at one chunk size, a loss of 10 % of the items in the recent buckets is found about 6 times in 10, and one of 20 % or more almost always. A loss of 5 % or less is mostly invisible: a clean step 7 does not show that the replay is as good as off.

**What this set cannot detect.**
- Anything beyond copying one verbatim code out of a log: reasoning over several facts, paraphrase, summarising, code and maths in the recent rows. A defect that only shows where the answer needs composition stays hidden (step 6's items are the multi-fact ones, and they are far from the end).
- Small losses (see the table), and any loss that off and on share (off wrong on the same items); an off arm that is itself wrong on many items of a cell makes the cell uninformative.
- Effects on the answer's own tokens after the first one: replies are short (`max_tokens` 40), so the decode window ring is exercised for a few steps only (step 5 (b) is the 160-token tripwire).
- Prompt lengths other than about 4K and 32K, thinking mode (these are thinking-off requests), sampled decoding, prompts whose question is not last, resumed prefills (every item has a unique first line, so the prefix cache cannot hit), and chunk sizes not run. At chunk 2048 the 4K prompts have the floor in the last chunk of 2 or 3, never the many-small-chunks schedule of chunk 512; the encoder-only chunk case is exercised only at 32K.
- The numbers above assume the noise rate of that one chunk32k-2 comparison; a noisier model on these items would raise the false rate.
