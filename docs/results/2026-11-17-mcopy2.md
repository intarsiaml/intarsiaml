# mcopy2: copy drafts beside the MTP head, review fixes (CUDA, Qwen3.6-35B-A3B NVFP4)

Lane `mcopy2`, branch `mcopy2` from origin/main `36f21e2ea` (PR #427, `mcopy`). Opt-in only: `INTARSIA_SPEC_COPY=<n>[,<len>]`, off by default,
nothing new is default-on. Measured on spark1 (DGX Spark GB10) with vLLM (flight, guidance, capcom) up beside it, every speed number an ABBA
over server restarts, `fleetq` slots for every run on the Spark. Raw output: `docs/results/2026-11-17-mcopy2/raw/`; scripts: `scripts/mcopy/`
(the lane's `build.sh` now builds a git ref too, `plan.sh` is new, `ids.sh` prints graph / eager step counts and host gaps from the trace).

## Summary

- **Verdict: stays opt-in, not a default-flip candidate.** The two flip conditions were no cell below 0.995x and agent cells >= 1.03x
  against MTP k2. Final build (back-off v2, lazy catch-up), ABBA, 3 rounds x 3 reps, n20 / n20L15 (`INTARSIA_SPEC_COPY=20` / `=20,15`): lowest cell
  **0.981x / 0.982x** (`code-gen`, a cell where no chain fires; 0.976 to 0.991 over the rounds), `reason` 0.999 / 0.995, `chat-short` 1.000 / 0.995;
  agent cells `agent-batch` 1.033 / 1.044 but `agent-edit` **1.007 / 1.005** (rounds 0.997, 1.167, 1.007: the nonce changes the reply, and
  the short, about 300-token reply gains only when its quoted function is long enough to start a chain). Both conditions fail. The `code-gen` gap is the flat
  cost mcopy found; the fixes here do not move it (the old code, `old20`, reads 0.988x in the same run). Copy-heavy text keeps its gain: `copy3k`
  1.756 / 2.058x, `json-xform` 1.555 / 1.607x. Whether to recommend the knob for copy-heavy workloads is still the user's call.
- **Review items 1, 2, 3 fixed, nits 4 and 6 fixed, nit 5 not** (below). Gates (a) and (b) pass: greedy ids equal `--spec off` and main's, the
  knob-unset `plan show --json` is byte-identical to main's, the cpu tests pass.
- **The flat cost is located, not fixed:** it is not a cost of the knob being on (n256: knob on, nothing fires: 1.000x) but a persistent +0.2 to 0.3 ms
  (+1.2 to 1.8 %) on every MTP graph step after the first chain pass of a request, even a missed one (`serve` trace, "Where the flat cost is not"). It is not
  host work, graph-vs-eager, the widened passes, kernel selection or the scan. Cause in the rollback / graph-state path, not found.

## What changed

| # | review item | change |
|---|---|---|
| 1 | no back-off for missed chains; `n = 1` accepted | `spec::CopyBackoff` (per request, `Seq::copy_backoff`): after `m` consecutive chains that each accepted fewer than 3 drafts the next `2^(m-1)` steps (at most 64) propose no chain and skip the scan; a chain that accepts 3 or more resets it. `CopyCfg::parse` needs `n >= 4` (`COPY_MIN_N`; the engine API itself does not check, the cpu test uses n = 1, 2). First version skipped 4, 8, ... 64 steps after every miss: see "Back-off". |
| 2 | copy passes feed the MTP measured-cost gate | `cost_mark` carries a `CostKind` (`Spec`, `Plain`, `Copy`); a chain pass starts a `Copy` interval (the pass and the emission of its tokens, up to the next step that calls `cost_begin`) that the gate never samples. Chain passes also leave `intarsia_spec_*` telemetry: new `intarsia_spec_copy_{steps,proposed_tokens,accepted_tokens}_total` (and `spec_copy_*` in the snapshot and in `generate`'s summary line). Tokens per verify pass in `intarsia_spec_*` therefore no longer include chain passes and are not comparable with mcopy's table. |
| 3 | per-row recurrent save buffers outside the plan | `SpecConfig::save_rows()` = `max(k, len)` for `--spec mtp` with the knob set, else `k`; the loader passes it as `LoadOptions::mtp_k`, so the memory plan reserves and every sequence allocates the buffers up front (`Model::load` clamps `mtp_k` to `DFLASH_K_MAX`, 15, instead of `SPEC_K_MAX`, 6; unchanged for values <= 6). `prepare_spec_rows`' lazy allocation stays as the fallback. |
| 4 | a chain makes the next MTP step eager | `Seq::copy_behind`: after a chain the head is caught up (`mtp_catch_up`) just before the next step that drafts with the head, so that step finds one queued row and replays its captured graph. Lazy on purpose: chain after chain leaves the rows queued, as before. |
| 5 | `SpecConfig::verify_rows()` reads the env | **not changed.** It reads `copy_from_env()`, a `OnceLock` read once per process, not the environment per call; `SpecConfig` is built as a struct literal in about 40 places (tests), so carrying the copy config in it is not cheap. |
| 6 | chain passes counted in MTP telemetry | split (item 2). |

Tests: `spec::tests::copy_backoff_doubles_over_consecutive_misses_and_resets_on_a_hit`, `copy_cfg_parses_n_and_len` (n < 4 refused), cpu engine tests
`copy_drafts_beside_the_mtp_head_keep_greedy_output_identical` (now also asserts the chains are counted apart and the MTP counters hold only head passes;

## Back-off and catch-up, what the numbers say

- **A skip window after every miss costs yield where misses sit among hits.** v1 lost 1.4 % of json-xform's gain at n20 and about 4.5 % at n20L15 (1.538x against
  mcopy's 1.611x and this run's 1.607x), and cut the chains at n = 4 on json-xform from 517 (no back-off) to 247. A miss costs about one hit's gain by the
  pass times (a chain pass is ~30 ms, an MTP graph step ~19.6 ms for 2.4 to 3 tokens; an estimate, not a fit), so the second version waits only
  after consecutive misses (1, 2, 4, ... 64 steps): chains at n = 4 are 406 on json-xform and 389 on copy3k (v1: 247 / 308), at n = 20 the same as with no
  back-off (323 and 183 chains on json-xform at len 7 and 15, mcopy without back-off: 327 / 176). What it buys is a bound on the look-alike case, not speed on these
  cells: the lane has no text where chains keep missing (mcopy's n = 4 runs fired 8 chains on code-gen and 36 on reason in 500 tokens), so the back-off is a guard that
  is not measured to pay here. `n < 4` is refused because below it every look-alike matches.
- **Nit 4, eager step after a chain.** With the knob on every head pass of the final build is a captured-graph replay (`intarsia_graph_replays_total` 3008 against
  2982 head passes in `n20` round 1, no eager head pass; the trace of the ids runs: `eager_steps=0` in every arm). Main's code ran about 2 % of its head
  passes eagerly after a chain (`old20`: 2897 replays for about 2955 head passes, computed from the n20 chain count). The speed effect is within the noise
  (copy3k n20 1.756x against 1.751x, json 1.555x against 1.565x), so it is not the flat cost and not worth more than the one flag it costs. The catch-up
  is lazy because an eager one after every chain made copy3k n20 1.732x against 1.741x for old (the 8-row head pass per chain, 360 of them, when most chains are followed by another chain).

## Where the flat cost is, and is not (code-gen 0.98x, reason / chat-short 0.99x)

Found, not fixed: **the cost starts when the first chain pass has run, and stays for the rest of the request.** Evidence, in the order it was gathered
(all 35B NVFP4 on spark1; `raw/ids-gate*.txt` for `generate`, `raw/diag1/` for `serve`):

1. `generate`, 500-token code-gen and reason, greedy, `INTARSIA_SPEC_TRACE=1` (the trace prints each captured-graph step's time and the host gap before it): with the knob
   on and no chain firing (n20, n256, n20L3: copy_passes 0) the run is the base run: the same 180 of 180 (code-gen) and 173 of 173 (reason) head passes are graph
   steps, no eager step, host gap 4 us in every arm (the plan_step scan is inside it, so the scan is under a microsecond), mean graph step 18.11 to 18.21 ms
   (base 18.13 / 18.14) on code-gen and 18.47 to 18.54 (base 18.57) on reason: differences of +-0.5 %, no trend with the verify rows (4, 8 rows). `plan show` differs
   in `scratch_bytes` only, so no kernel selection changes. So: not host work, not graph-vs-eager, not the widened passes, not kernel selection.
2. `serve --max-batch 1`, code-gen, trace on, 2 rounds x 3 reps (`raw/diag1`, ABBA): **n256** (knob on, 8-row passes, scan on, no chain ever fires) is **1.000x**
   (0.998, 1.002) of base; **n20** is **0.989x** (0.990, 0.989). The difference between n20 and n256 is that n20 fires a few chains in a serve run on this
   cell (2 and 4 chain passes in the two n20 logs, accepted 2 of 7 and 1 of 7 in the two on round 1), where `generate`'s 500 tokens fire none; mcopy's "no chain fires on code-gen at n = 20" was
   true of `generate` and not of the served cell (a nonce-prefixed prompt, 3 reps in one server).
3. The graph-step times of the same logs split at the first chain pass (first chain at graph step 587 of 1170 in round 1, 539 of 1167 in round 2): n20 steps before it
   18.158 / 18.085 ms, after it 18.373 / 18.406 ms (**+0.22 / +0.32 ms, +1.2 / +1.8 %**); over the same step ranges base moves +0.05 / +0.04 ms and n256
   +0.04 / +0.01 ms (drift of the run). Before the first chain the n20 server is the base server. A step that follows a missed chain (a pass that accepted 1 or 2
   drafts) is slower for the rest of the request, with the catch-up in front of the next draft (this build) as well as without it (the old code reads 0.988x in the same A/B).

So the flat cost is a **persistent slowdown of the MTP graph step after a chain pass has run**, about 0.2 to 0.3 ms per step, not a cost of the knob being set. It
accounts for the whole A/B gap on code-gen (1.2 to 1.8 % per step against 1.1 to 1.9 % in the A/B), and fits `reason` / `chat-short` sitting closer to 1.0 (fewer chains in the served runs; not
counted). It does not obviously depend on `len`: mcopy's `n20L3` read 0.995x and `n20` 0.994x (5 reps) against `n20L15` 0.986x, here all three-round cells are 0.98x. **Cause not found.** Suspects, none tested: (a) the rollback
after a chain pass leaves the recurrent state in a different device buffer than the one the captured graph was recorded against, and each later graph step pays a
state copy; (b) the chain's `spec_rows` / position-table state makes the graph's `spec_step_ok` / replay path do per-step host or device work that a head-only
request never does (host gap says no host work; a device-side copy would not show in it); (c) memory placement after the 8-row pass's allocations (the save
buffers are allocated up front in this build, so not those). The next measurement is an `nsys` capture of one graph step before and after a chain, or the
same trace with `INTARSIA_SPEC_GRAPH=0` (eager head steps: if the slowdown disappears there it is graph-specific). Until then a flip would need the chain-fired cost gone, and the
copy-heavy gains (1.55 to 2.06x) are measured with it included.


## Not done / unverified

- **Nit 5** (`verify_rows()` reads the env): not changed, above.
- Three A/B rounds for the final build; the 0.995x floor on a 1 to 2 % cost is measured against a restart noise of about 0.5 to 1 %, so
  `code-gen` (below 0.995x in every round of every run it appears in, here and in mcopy, except one round of `old20`) is solid and `reason` / `chat-short` (0.99 to 1.00) are not.
- The batching engine, tp > 1, HIP, Metal, sampled requests, thinking mode, 16k-context speed cells, real agent transcripts, n above 20: unchanged from mcopy
  (refused at load or not run). `--prefix-store on` with copy drafts was never exercised.
- spark1 ran vLLM beside every run; its traffic was not logged. The earlier build's binary (back-off v1) is gone (rebuilt), its numbers are the `ab1` raw files.

## Revert

Unset `INTARSIA_SPEC_COPY`: nothing else changes by default (gate (b)). Reverting the PR restores mcopy's behaviour: no back-off, chain passes in the MTP cost
gate and counters, save buffers allocated lazily outside the plan, `n >= 1` accepted.
