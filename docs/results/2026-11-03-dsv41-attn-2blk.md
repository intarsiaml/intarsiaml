# DSv4.1 CUDA prefill `attn_sparse_mma`: two blocks per SM and four barriers per tile (bench only)

Date 2026-11-03, branch `dsv41/attn-2blk` (carries [the attention-fusion doc](2026-11-03-dsv41-attn-fusion.md)). Follows its section 4 "next attempt (a)". Raw logs, bench and patch: `2026-11-03-dsv41-attn-fusion/raw/bench/` (`attn-2blk.patch`, `attn_ab_bench.cu`, `occ_probe.inc`, `ab-build.sh`, `ab-run.sh`, `ab-run-1.log`, `ab-build-8207.txt`).

## Result

**Negative: nothing lands, nothing is wired into the engine.** The variant really runs two blocks per SM (occupancy API: 2, against 1) and is bit-identical, but at CSA T=2048 it is **0.4 % slower** (5.055 ms against 5.037 ms), and 8.7 % slower at T=512. The gain needed was 15 % of the kernel at T=2048 (about 3 % of a 4K prefill); the measured gain is -0.4 %. Per the stop rule I tried no other variation. `kernels/cuda` is untouched on the branch; the variant is the patch `raw/bench/attn-2blk.patch` (`-DATTN_2BLK`, applied to a copy of `dsv41_attn.cu` in the bench only).

## 1. What limits the kernel to one block per SM

Device query on spark2 (GB10, sm_121; probe in `occ_probe.inc`, printed by every bench process): 48 SMs, shared memory per SM **102400 B**, reserved **1024 B per block**, default per-block limit 49152 B, opt-in per-block limit 101376 B, 1536 threads per SM, 65536 registers per SM.

Unmodified kernel (`attn_sparse_mma`, D = 512, 32 heads, 32-key tiles, 256 threads): dynamic shared memory 73344 B (Q 33280 + key tile 33280 + S 4224 + P 2560) plus 768 B static, 107 registers per thread. Two blocks would need 2 x (74112 + 1024) = 150 KB against 100 KB, so shared memory is the limit (threads: 6 blocks, registers: 2 blocks by 107 x 256 = 27.4 K each). Two blocks fit only if a block stays under about 49 KB. Q (32 heads x 512, 32 KB) and the key tile (32 keys x 512, 32 KB) are each as large as the whole budget, and neither can shrink bit-identically: a smaller key tile changes the softmax tile boundaries, 16 heads per block still leaves 54 KB, and the Q fragments for a warp's 16 rows over D = 512 would take 128 registers per thread. The one structure that can leave shared memory without changing any arithmetic is Q.

Barriers in the unmodified loop: 5 per tile (top / meta written / keys gathered / S written / P and alpha written), plus one before the epilogue.

## 2. The variant (`-DATTN_2BLK`)

1. **Q from global.** The mma A fragments of Q are read with `__ldg` (4 bytes per load, same fragment layout and same `k0` order as before) instead of `lds32` from a Qs tile in shared memory. Shared memory per block: 40064 B dynamic + 1152 B static = 41216 B; 2 x (41216 + 1024) = 84.5 KB fits.
2. **`__launch_bounds__(256, 2)`**: 128 registers per thread, no spills (cuobjdump `LOCAL:0`; `raw/bench/ab-build-8207.txt`).
3. **Metadata one tile ahead.** `valid` / `srcrow` are double buffered; the `idx` load for the next tile is issued before the gather and its shared stores come after it, so the "top" and "meta written" barriers merge: **4 barriers per tile**, and the `idx` global-load latency is no longer on the tile's critical path.

All arithmetic and its order are unchanged (the mma `k0` loop, the softmax rows, the PV loop).

Calibration: the unmodified kernel reproduces the recorded 1.30 ms (1.304), 5.04 ms (5.037) and the three recorded hashes of `bench-vec0.txt` (`4ee9a847...`, `aa254a57...`, `90ad1d7f...`), so the bench is the one the earlier lane used. Occupancy API: unmodified 1 active block per SM, variant 2. Hashes were identical in all 6 pairs at all five shapes. One variant rep at T=2048 in pair 6 hit 6.1 and 6.4 ms (a transient on a box shared with vLLM; included in the "max" of `ab-run-1.log`, not in the median).

Reading, as inference and not measured: the variant is flat at T=2048 where two blocks per SM are resident for most of the run, and 41 % slower at T=37, where there are fewer blocks than SMs (37 against 48), so no SM holds two. The T=37 case shows that Q-from-global plus the merged barrier cost more per tile when a block runs alone; at T=2048 the second block's overlap buys that back and nothing more. I did not split the variant into its parts (no `ncu`, and the stop rule says no second variation), so how much of the cost is the Q loads (128 4-byte global loads per thread per tile, each warp load touching 8 rows) and how much is the 128-register cap is not known.

## Not checked

- The three changes separately (Q from global alone, the merged barrier alone, `launch_bounds` alone): not built, by the stop rule.
- Anything in the engine: wiring, golden, plandiff, in-situ prefill timing. Not wired. For the record, wiring would need only `attn_mma_smem` (40064 B), `__launch_bounds__(256, 2)` and the kernel body; the grid (`nsplit`, `Tn`, `H/32` blocks), scratch layout and the merge kernel are unchanged, and the `cudaFuncSetAttribute` call already takes `attn_mma_smem(kMaxD)`. The decode / verify path (T <= 16, split > 1) hashes equal at T=11 (bench only).
- A stall breakdown (`ncu` is not available on these boxes), TensorFold's kernel, other shapes (D other than 512, H = 16 per block, `dpos` device-position calls with `pos` non-null), the F16 / F32 / SIMT kernels.
- Other Q-load schemes (16-byte loads with a quad transpose, staging Q through a small shared buffer) that might make the 2-block form cheaper: not tried.
- Timings are on a shared box (vLLM resident, idle); no in-situ run.
