When two distinct keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In **chaining**, each bucket in the array contains a linked list (or another dynamic structure) of entries. When a collision happens, the new entry is simply appended to the list at that index. Lookup time then depends on the length of the list, requiring a linear scan through the colliding elements. In **open addressing**, all entries are stored directly in the array itself. When a collision occurs, the algorithm probes for the next available slot using a specific sequence (such as linear probing, quadratic probing, or double hashing) until an empty slot is found.

The **load factor** ($\alpha$), defined as the ratio of the number of stored elements ($n$) to the total number of slots in the table ($m$), is critical because it directly influences the probability of collisions. As the load factor increases, the hash table becomes more crowded, significantly raising the likelihood that new insertions will collide with existing entries. In chaining, a higher load factor means longer linked lists, which degrades lookup time from $O(1)$ toward $O(n)$. In open addressing, a high load factor causes "clustering," where consecutive occupied slots force the probing sequence to traverse many elements before finding an empty spot, again slowing down lookups and insertions.

Therefore, maintaining a low load factor is essential for preserving the hash table’s efficiency. Most implementations dynamically resize the table—typically by doubling its capacity and rehashing all elements—when the load factor exceeds a certain threshold (often around 0.75). This resizing ensures that the average number of collisions per bucket remains small, thereby guaranteeing that the expected time complexity for lookups, insertions, and deletions remains constant, or $O(1)$ on average.
