When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another data structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the table using methods like linear probing or double hashing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements ($n$) to the number of buckets ($m$), i.e., $\alpha = n/m$, is critical because it directly influences the frequency of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This degradation in performance is why hash tables typically trigger a **rehashing** operation (resizing the table and redistributing elements) when the load factor exceeds a certain threshold, often around 0.75.

The load factor matters for lookup time because it determines the average length of the collision resolution structure. In a well-tuned hash table with a low load factor, the average number of elements per bucket is small, allowing lookups to approach **$O(1)$** constant time complexity. However, if the load factor becomes too high, the average chain length or probe sequence grows, causing lookup time to degrade toward **$O(n)$** in the worst case. Therefore, managing the load factor ensures that the hash table maintains its primary advantage: fast, constant-time access to data.
