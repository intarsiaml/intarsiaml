When two distinct keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In **chaining**, each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision happens, the new entry is simply appended to the list at that index. Lookup involves hashing the key to find the bucket and then traversing the list to find the matching key. In **open addressing**, all entries are stored directly in the array itself. When a collision occurs, the algorithm probes for the next available slot using a specific sequence (such as linear probing, quadratic probing, or double hashing) until an empty slot is found.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets ($n / m$), is critical because it directly influences the probability of collisions and the length of chains or probe sequences. As the load factor increases, the hash table becomes more crowded, leading to a higher frequency of collisions. In chaining, a higher load factor means longer linked lists, which increases the time required to traverse them. In open addressing, a higher load factor results in longer probe sequences to find an empty slot or the target element, and if the load factor approaches 1, the table may become nearly full, causing significant clustering and degraded performance.

Consequently, the load factor determines the efficiency of lookup, insertion, and deletion operations. Ideally, hash tables maintain a low load factor (often capped at 0.7 or 0.75) to ensure that the average-case time complexity remains $O(1)$ for these operations. If the load factor exceeds a certain threshold, the hash table typically triggers a **rehashing** operation: it creates a new, larger array and redistributes all existing elements into it. This reduces the load factor and restores efficient performance
