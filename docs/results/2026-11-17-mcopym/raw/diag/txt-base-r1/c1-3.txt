When two distinct keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In **chaining**, each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision happens, the new entry is simply appended to the list at that index. In **open addressing**, all entries are stored directly in the table itself. If a collision occurs, the algorithm probes for the next available slot using a specific sequence, such as linear probing (checking the next index sequentially) or quadratic probing. Both methods ensure that every key can be stored, but they differ in how they manage memory and access patterns.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets ($n / m$), is critical because it directly influences the probability of collisions. As the load factor increases, the hash table becomes more crowded, making it statistically more likely that new insertions will collide with existing entries. In chaining, a higher load factor means longer linked lists, which increases the time required to traverse the list to find a specific key. In open addressing, a higher load factor leads to longer probe sequences, as the algorithm must skip over more occupied slots to find an empty one.

Consequently, the load factor determines the efficiency of lookup operations. Ideally, a hash table maintains a low load factor (often kept below 0.75) to ensure that the average time complexity for lookups, insertions, and deletions remains close to $O(1)$, or constant time. If the load factor grows too large, the performance degrades significantly, approaching $O(n)$ in the worst case, where the hash table effectively behaves like a linear search through a list.
