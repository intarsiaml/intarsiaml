When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the table using methods like linear probing or double hashing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements to the number of buckets ($n / m$), is critical because it directly influences the probability and severity of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This degradation in performance is why hash tables are designed to maintain a low load factor, typically by resizing the table (rehashing) when $\alpha$ exceeds a certain threshold (e.g., 0.75).

Consequently, the load factor determines the average lookup time. In an ideal scenario with a low load factor and a good hash function, collisions are rare, and lookups occur in **$O(1)$ constant time**. However, as the load factor approaches 1, the likelihood of collisions increases significantly, causing the average lookup time to degrade toward **$O(n)$** in the worst case (where all keys collide into a single bucket). Therefore, managing the load factor through dynamic resizing is essential to preserving the hash table’s efficiency.
