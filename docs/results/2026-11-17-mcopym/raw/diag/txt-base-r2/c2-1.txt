When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision occurs, the new key-value pair is simply appended to the list at that index. Alternatively, **open addressing** methods like linear probing or quadratic probing search for the next available empty slot in the table by incrementing the index according to a specific sequence. In both cases, the goal is to ensure that every key has a unique location for storage, even if their initial hash values collide.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets in the table, is critical because it directly influences the frequency of collisions and the length of the chains or probe sequences. As the load factor increases, the probability that two keys will hash to the same index rises significantly. In chaining, a higher load factor means longer linked lists, which increases the time required to traverse the list during a lookup. In open addressing, a higher load factor leads to longer probe sequences as the table becomes more crowded, increasing the number of memory accesses needed to find an empty slot or the target key.

Consequently, the load factor determines the efficiency of lookup operations. Ideally, a hash table maintains a low load factor (typically kept below 0.75) to ensure that the average case for lookup, insertion, and deletion remains $O(1)$, or constant time. If the load factor grows too large, the performance degrades toward $O(n)$ in the worst case, resembling a linear search through a list.
