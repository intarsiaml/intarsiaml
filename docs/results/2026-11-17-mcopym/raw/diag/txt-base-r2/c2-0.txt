When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision occurs, the new key-value pair is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the array using methods like linear probing (checking the next index sequentially) or quadratic probing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements ($n$) to the number of buckets ($m$), is critical because it directly influences the probability of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. For example, if the load factor approaches 1, nearly every bucket is occupied, causing lookups to degrade from $O(1)$ average time to $O(n)$ worst-case time, effectively turning the hash table into a linked list.

Therefore, the load factor matters for lookup time because it determines the average length of the collision resolution structure. To maintain efficient $O(1)$ average-case performance, hash tables typically resize (rehash) when the load factor exceeds a certain threshold (often 0.75). By keeping the load factor low, the probability of collisions remains minimal, ensuring that lookups, insertions, and deletions remain fast and scalable as the dataset grows.
