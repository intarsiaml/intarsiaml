When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another data structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** methods like linear probing or quadratic probing search for the next available empty slot in the array by incrementing the index until a free space is found. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets in the table, is critical because it directly influences the frequency of collisions. As the load factor increases, the buckets become more crowded, making it statistically more likely that new insertions will collide with existing entries. In chaining, a higher load factor results in longer linked lists, which increases the time required to traverse the list during a lookup. In open addressing, a higher load factor leads to longer sequences of probes as the algorithm searches for the next empty slot.

Consequently, the load factor determines the average time complexity of lookup operations. Ideally, a hash table maintains a low load factor (typically kept below 0.75) to ensure that the average number of collisions per bucket remains small, preserving the $O(1)$ constant-time lookup performance. If the load factor grows too large, the performance degrades toward $O(n)$ in the worst case, as the table behaves more like a linear list. To mitigate this, hash tables often implement **rehashing**, where the table size is increased and all elements are redistributed when the load factor exceeds a certain threshold, thereby restoring efficient lookup times.
