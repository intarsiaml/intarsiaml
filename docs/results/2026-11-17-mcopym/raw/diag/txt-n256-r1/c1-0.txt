When two distinct keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In **chaining**, each bucket in the hash table contains a linked list (or another dynamic data structure) of entries. When a collision happens, the new entry is simply appended to the list at that index. In **open addressing**, all entries are stored directly in the table itself. If a collision occurs, the algorithm probes for the next available slot using a specific sequence, such as linear probing (checking the next index sequentially), quadratic probing, or double hashing.

The **load factor** ($\alpha$) is defined as the ratio of the number of stored elements ($n$) to the total number of buckets ($m$) in the hash table ($\alpha = n/m$). It is a critical metric because it directly influences the probability of collisions. As the load factor increases, the buckets become more crowded, making it statistically more likely that new insertions will collide with existing entries. In chaining, a higher load factor means longer linked lists, which increases the time required to traverse them. In open addressing, a higher load factor leads to longer probe sequences as the algorithm searches for the next empty slot.

Consequently, the load factor significantly impacts lookup time. Ideally, a hash table maintains a low load factor (often kept below 0.75) to ensure that the average-case time complexity for lookups, insertions, and deletions remains $O(1)$. If the load factor grows too large, the performance degrades toward $O(n)$ in the worst case, as the hash table begins to behave more like a linear list. To mitigate this, hash tables often implement dynamic resizing: when the load factor exceeds a certain threshold, the table is rehashed into a larger array, thereby reducing the load factor and restoring efficient $O(1)$ average
