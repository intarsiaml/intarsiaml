When two distinct keys hash to the same index in a hash table, a collision occurs. To handle this, hash tables typically employ one of two primary strategies: chaining or open addressing. In **chaining**, each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision happens, the new entry is simply appended to the list at that index. In **open addressing**, all entries are stored directly in the table itself. If the target slot is occupied, the algorithm probes for the next available slot using a specific sequence, such as linear probing (checking the next slot sequentially), quadratic probing, or double hashing.

The **load factor** ($\alpha$) is defined as the ratio of the number of stored elements ($n$) to the total number of slots in the table ($m$), i.e., $\alpha = n/m$. The load factor is critical because it directly influences the probability of collisions. As the load factor increases, the table becomes more crowded, leading to a higher frequency of collisions. In chaining, a higher load factor means longer linked lists, which increases the time required to traverse them. In open addressing, a higher load factor increases the number of probes needed to find an empty slot or the desired key, significantly slowing down insertions and lookups.

Consequently, the load factor determines the efficiency of lookup operations. Ideally, hash tables maintain a low load factor (often capped at 0.75 or similar thresholds) to ensure that the average time complexity for lookups, insertions, and deletions remains close to $O(1)$, or constant time. If the load factor grows too large, the performance degrades toward $O(n)$ in the worst case, effectively turning the hash table into a linear search structure. Therefore, most hash table implementations automatically resize (rehash) the table when the load factor exceeds a certain threshold to restore optimal performance.
