When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the underlying array contains a linked list (or another dynamic structure) of entries. When a collision occurs, the new key-value pair is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the array using methods like linear probing or double hashing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements to the number of buckets ($n / m$), is critical because it directly influences the probability of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This degradation in performance is why hash tables are designed to maintain a low load factor. For instance, in chaining, the average time to find an element is $O(1 + \alpha)$, meaning that as $\alpha$ grows, the lookup time approaches $O(n)$ in the worst case, effectively degrading to that of a linked list.

Therefore, to preserve the $O(1)$ average-case lookup time, hash tables dynamically resize when the load factor exceeds a certain threshold (commonly 0.75). Resizing involves creating a new, larger array and rehashing all existing elements into it. This process redistributes the keys more sparsely, reducing the load factor and minimizing collisions. Consequently, keeping the load factor low ensures that the hash table remains efficient, allowing lookups, insertions, and deletions to remain constant time on average rather than linear time.
