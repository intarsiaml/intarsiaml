When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the underlying array contains a linked list (or another data structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the array using methods like linear probing or double hashing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements to the number of buckets ($n / m$), is critical because it directly influences the probability of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This increases the average number of comparisons required to find, insert, or delete an element. For example, in chaining, the average time to search becomes proportional to $1 + \alpha$, meaning performance degrades linearly as the table fills up.

Consequently, the load factor determines the **lookup time complexity**. A hash table is designed to offer $O(1)$ average-case time complexity only when the load factor is kept low (typically below 0.75). If the load factor grows too large, the hash table begins to behave like a linear search structure, degrading to $O(n)$ worst-case time complexity. To maintain efficiency, hash tables often trigger a **rehashing** operation—creating a larger array and redistributing all elements—when the load factor exceeds a certain threshold, thereby resetting the collision probability and restoring constant-time performance.
