When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another dynamic structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** methods like linear probing or quadratic probing search for the next available empty slot in the array by incrementing the index based on a specific sequence. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets ($n / m$), is critical because it directly influences the probability of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This degradation in performance is why hash tables are designed to maintain a low load factor, typically by resizing the table (doubling the number of buckets) and rehashing all elements whenever the load factor exceeds a certain threshold (often 0.75).

Consequently, the load factor determines the **average-case lookup time**. When the load factor is kept low and constant (e.g., $\alpha < 1$), the average number of elements per bucket remains small, allowing lookups, insertions, and deletions to occur in **$O(1)$ amortized time**. However, if the load factor grows large (approaching or exceeding 1), the average chain length or probe sequence increases linearly with the number of elements, causing the lookup time to degrade to **$O(n)$** in the worst case, effectively turning the hash table into a slow linear search structure.
