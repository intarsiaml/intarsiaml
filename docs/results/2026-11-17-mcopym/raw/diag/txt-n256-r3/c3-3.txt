When a hash table encounters a collision—meaning two different keys hash to the same index—it must employ a strategy to store both values without overwriting one another. The most common approach is **chaining**, where each bucket in the hash table contains a linked list (or another data structure) of entries. When a collision occurs, the new entry is simply appended to the list at that index. Alternatively, **open addressing** probes for the next available slot in the table using methods like linear probing (checking the next index sequentially) or quadratic probing. In both cases, the goal is to ensure that every key has a unique location while maintaining the efficiency of direct access.

The **load factor** ($\alpha$), defined as the ratio of the number of elements stored to the total number of buckets ($n / m$), is critical because it directly influences the probability and severity of collisions. As the load factor increases, the buckets become more crowded, leading to longer chains in chaining or longer probe sequences in open addressing. This increases the average number of comparisons required to find, insert, or delete an element. For example, in chaining, the average time to find an element is proportional to $1 + \alpha$, meaning performance degrades linearly as the table fills up.

Consequently, the load factor determines the balance between space efficiency and lookup speed. A low load factor (e.g., $\alpha < 0.75$) ensures that collisions are rare, allowing for near-constant time $O(1)$ lookups. However, if the load factor becomes too high, the hash table behaves more like a linked list, degrading lookup time to $O(n)$ in the worst case. To maintain optimal performance, hash table implementations typically trigger a **rehashing** operation—creating a larger table and redistributing all elements—when the load factor exceeds a certain threshold, thereby resetting the collision rate and preserving efficient lookup times.
