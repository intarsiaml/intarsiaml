## Item 2: GSM8K accuracy after a store restore (window #9319, 2026-11-14 01:17 to 01:33)

### Method (same driver and inputs as `docs/results/2026-11-13-restore-acc.md`)

- Inputs: `raw/gsm8k-inputs.json` is that lane's frozen set (the 200 pinned GSM8K test questions `gsm8k-00000` to `gsm8k-00199` with their golds, and the first 32 train worked solutions). `scripts/soak/gsm8k_prefix.py` sends chat messages: one fixed system prompt, 32 worked few-shot turns (user `**Problem**: ...`, assistant the worked solution ending `#### n`), then the test question as the last user message, so every request shares a 6904-token prefix that the store cuts at a message boundary, and the question is decoded after that restore. Thinking off, temperature 0, 512 max tokens, concurrency 1 (at concurrency 1 every decode drafts, so a restored request always has MTP running after the restore), flexible-v1 scoring.
- **Arm W**: `serve --max-batch 2 --prefix-store on` (default 8 GiB), MTP default. The first request is cold and captures; every later request should restore the prefix. **Arm O**: `serve --max-batch 2` (no store), MTP default: every request prefills in full. Both arms ran on a fresh server (empty store).
- Pairing: the brief names `scripts/soak/paired_gsm8k.py`, which reads localeval `result.json`; this driver writes jsonl, so the paired test is `scripts/soak/gsm8k_prefix_cmp.py` (exact two-sided McNemar on the discordant pairs, plus reply-text and token-id identity). Same statistic, different input format.

So a restore followed by MTP drafting (today's binary, MTP head restarted at the resume point) produces the same bits as a cold store-on prefill without MTP, for all 199 restored requests.
- **Why W and O differ in text on 116 of 200 questions.** 84 of 200 replies are identical between W and O (token ids too); 116 differ, with a median first diverging token at index 29 and 18 of them within the first two tokens. This is **not** a restore or MTP effect: O differs in exactly the same 116 questions from the previous lane's cold store-on arm C (`raw/O-vs-restoreacc-C.json`: 84 identical, 116 non-identical, the same counts). It is the known difference between the store's prefill schedule (chunks cut at message boundaries) and the store-off schedule (2048-row chunks), which changes the bits of the prompt state, and with it greedy ties, as in the cutover soak's Ba against B-specoff (73 of 200 differing, accuracy unchanged). Accuracy is the same either way.
- No warnings in either serve log; MemAvailable lowest 47.3 GB (W) and 54.7 GB (O); no request was rejected.

## Limits

- Greedy accuracy only. Sampled-request accuracy after a restore was not measured (sampled drafting is seed-exact by construction in the mtp-sampled lane's gates, and the restore is exact in the greedy case, so a bit difference is not expected, but this lane did not test it).
- GSM8K was at concurrency 1, where every decode drafts; at the production K=2 MTP is mostly idle (see MTP), so the accuracy arms exercise MTP after a restore harder than production does. One restored prefix shape (6.9k tokens cut at a message boundary, 199 restores of the same entry); the soak's multi-turn restores up to 28k tokens have no reference bits (all-greedy replies of the two soaks were not compared bit for bit between binaries).
- One soak, one seed set (61 to 78), one window. MTP counters are not split by request class in the soak (only in the K=1 probe, 12 requests per class). The "spec steps plus accepted drafts" share is derived from the counters (each spec step emits one token plus its accepted drafts); I did not verify that definition in the engine code.
- The spark1 box carried 6.3 GB of swap (not ours, constant) and vLLM at 34 GB; MemAvailable numbers are specific to that.
- No real missioncntrl traffic (agent tool calls, long sessions) was replayed; no thinking-on requests; no `--kv-dtype fp8`.
- The earlier rows in the comparison come from different binaries and a different box; differences of a few percent between them are not evidence of anything.
