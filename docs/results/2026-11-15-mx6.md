# mx6: the plan covers batched-verify row counts (`no kernel for matmul_mxfp4 ... m=6`)

Lane `mx6`, 2026-11-15. Branch `mx6`, worktree `.worktrees/mx6`.

## Brief + progress (kept at the top so it survives compaction)

**Brief (from the coordinator).** On CUDA (DGX Spark, sm_121) the Qwen3.8-27B Quark MXFP4 checkpoint served with
`INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1 --max-batch 2 --spec mtp --spec-k 2` fails its first request:
`no kernel for matmul_mxfp4 on cuda/sm_121 (m=6 ...) [admitted kernels only] [row-exact verify kernels only]`, and the watchdog exits the
server (`docs/results/2026-11-15-dv27.md`, section "The 27B `--max-batch 2` + batched MTP failure"). Diagnosis there: a kernel for m = 6
exists (`matmul_mxfp4_gemv_rows`, 5..=4096) but the plan admission probe covers only verify row counts `2..=verify_rows()` and batch row
counts `2..=batch_rows()` (`crates/intarsia-core/src/plan.rs`), never sequences x (k + 1), so it is never admitted and `require_admitted`
(`registry.rs`) skips it. Shipped defaults cannot reach it (it needs `INTARSIA_BATCHED_VERIFY`), but lane `flipprep` is about to make
batched verify (`batched_mtp = 2`, `batched_verify = true`) the default for the 35B on CUDA (user-approved), and any model or backend whose
batched-verify shapes are not admitted would crash the same way.

Fix: (1) the plan covers batched-verify row counts (up to `batched_mtp_n x (k + 1)` and every intermediate count that can occur; MoE and
lm_head too), admission tests those kernels; with batched verify off `plan show --json` is byte-identical to origin/main, with it on the
plan grows (show the diff). (2) Defence in depth: a missing admitted kernel must not crash mid-serve (refuse at load with the shape named, or
fall back to per-sequence verify bitwise; pick the simpler correct one and say why). (3) Gates: CPU tests of the touched crates including a
test that would have caught this; `plan show` identity with the knobs off on the 35B and 27B (CUDA); the 27B on CUDA with the failing env
serves and greedy plus seeded sampled ids equal `--spec off` at B = 1 and 2; the 35B on CUDA with the same opt-in set still has identical
ids (no regression for flipprep's flip); HIP and Metal read for the same probe gap (code only, tatooine off limits).

## Root cause (confirmed)

The coordinator's reading is right, and one level wider. Three facts:

1. **The kernel exists, nothing admitted it.** The CUDA row-exact MXFP4 table is split by row count (`crates/intarsia-backend-cuda/tests/rows_registry.rs`
   pins: `1..=1 matmul_mxfp4_gemv_rows`, `2..=4 matmul_mxfp4_gemv_mr_rows`, `5..=4096 matmul_mxfp4_gemv_rows`). Admission tests the kernels the plan's
   probes select, on the probes' shapes. The probes had verify runs of `2..=k+1` rows (2 and 3 for k = 2) and batched decode of `2..=max_batch`
   rows, so only `_mr_rows` (and the one-row kernel) were ever tested; `_gemv_rows` at m >= 5 stayed `Untested`, and `Registry::select` with
   `require_admitted` skips untested kernels.
2. **A batched verify pass has more rows than any probe.** `Model::forward_verify_batch` runs the projections, the MoE and the head ONCE over
   the rows of all drafting sequences: `n` sequences of `2..=k+1` rows each is `2n..=n(k+1)` rows (6 for two sequences at k = 2), at the `exact_rows`
   mark, so it asks for row-exact kernels at row counts the plan never looked at. Attention and the GatedDeltaNet recurrence run per segment, so
   they only ever see the solo verify shapes, which the plan already covered.
3. **The failure is an engine failure.** It happens inside `verify_step` at the first request, which the scheduler treats as fatal
   (`fail_all`): the watchdog marks the engine failed and the server exits for restart. It is not a per-request error.

Any model whose kernel table changes between `k + 1` and `n(k + 1)` rows (a different kernel, a kernel the probes never selected) hits it
the moment batched verify runs; where one kernel serves every row count (the case on most tables) the shapes were merely untested, and
admission's clamped case labels hid it.

## The fix

**Plan (`crates/intarsia-core/src/plan.rs`, `model.rs`).**

- `Model::enable_verify_batch(max_seqs)` (after `enable_verify`, before `configure_plan`) declares that batched verify passes of up to
  `max_seqs` sequences may run. The plan then probes a new phase, `Phase::VerifyBatch`: the real ragged pass (`Seqs::Packed` over phantom
  sequences, then the verify head over all rows) for every row count `n` sequences of `2..=verify_rows` rows can have, `2n..=n x verify_rows`
  for `n` in `2..=max_seqs` capped at the pass's logits rows (`VERIFY_MAX_ROWS` = 16), at the start and at the end of the context, like the
  other verify probes. The projections (every format), the MoE, the norms and the lm_head are in that pass, so all of them are probed at the
  larger row counts; admission tests the kernels picked for them as it does for the other verify shapes (against the reference, at the
  plan's clamped cases). Attention and GatedDeltaNet segments stay the solo verify shapes.
- Nothing is added when batched verify is not planned: no probe, no call, no op in the plan, so `plan show --json` is unchanged.
- `intarsia-models` `load.rs`: `batched_verify_for` (today `INTARSIA_BATCHED_VERIFY=1`) and `batched_verify_seqs_for` (`min(batched_mtp, spec_off_at - 1,
  --max-batch)`) decide, once, before `configure_plan`; the same resolved value then goes into `BatchedOptions::batched_verify`, so the plan
  covers exactly the passes the engine may run. **Merge order with lane flipprep:** flipprep resolves `batched_verify` from the recipe
  after the plan (`bo.batched_verify = recipe.resolve_batched_verify(..)`); with both merged, `batched_verify_for` must do what that block does
  (the env var wins both ways, else the recipe) and that block must go, or the 35B flip would plan nothing for batched verify and the engine
  would fall back to per-sequence verify (see defence below; it logs `batched verify off: the model's plan does not cover its row counts`).

**Defence in depth: fall back to per-sequence verify, never crash.** Picked over refusing the load because per-sequence verify is the
engine's existing, bitwise-equal path (`forward_verify` per drafting sequence, what a server without `INTARSIA_BATCHED_VERIFY` runs), so a
gap costs speed, not availability, and a refusal would turn a missing kernel for an optimisation into a server that does not start. Three
layers, each independently sufficient for the failing case:

1. **At load**: a `VerifyBatch` probe that finds no admitted row-exact kernel (or errors) does not fail the load; the plan switches batched
   verify off (`Model::verify_batch_seqs()` reads 0), keeps none of its calls, and logs
   `intarsia: batched verify off for this model: no admitted row-exact kernel for <op> (<shape>) in a <t>-row pass; verify passes run per sequence`.
2. **In the engine**: `BatchedEngine::new` runs batched verify only where the model's plan covers it (`verify_batch_seqs() >= 2`); `verify_step` splits a
   step into passes of at most the planned rows and sequences (`verify_batch_rows()`, `verify_batch_seqs()`), so no pass has a row count the plan
   did not probe.
3. **In the model**: `forward_verify_batch` on a planned model, given a pass the plan did not cover (more sequences or rows), runs one solo
   verify pass per sequence, which leaves every state exactly as the batched pass would (the pass's own contract).

**Metrics.** `intarsia_batch_verify_passes_total{seqs="n"}` and `intarsia_batch_verify_rows_total` (additive, emitted only once a batched
verify pass has run) so a gate can show the pass ran; the scheduler already counted them.

## Tests (CPU)

- `crates/intarsia-models/tests/plan.rs`:
  - `batched_verify_runs_on_a_kernel_only_the_plan_admission_of_its_row_counts_admits`: the failure itself on the cpu backend. The row-exact
    `Matmul` table is split like CUDA's MXFP4 one (a kernel for 2..=4 rows, another for 5 and up, both running the cpu matmul), plan admission
    on (`admit` + `require_admitted`). Unplanned (what main does), a batched verify pass of 2 sequences x 4 rows fails with
    `[admitted kernels only] [row-exact verify kernels only]`; planned, admission tests the 5+ kernel at the pass's row counts and the pass equals
    each sequence's solo verify pass.
  - `batched_verify_row_counts_are_planned_and_a_gap_switches_it_off_at_load`: a kernel that reaches 6 rows keeps batched verify on (the
    plan holds its calls), one that stops at 5 switches it off at load with no load failure and no batched-verify call left in the plan, and a plan
    that never asked for batched verify is the same plan as the switched-off one.
- `crates/intarsia-models/tests/mtp.rs`: `planned_batched_verify_pass_equals_each_sequences_solo_verify` (the hybrid GatedDeltaNet + MoE fixture:
  a planned pass of two sequences and the fallback for three are bitwise the solo verify rows and states); the existing batched-verify engine tests
  now plan it (`enable_verify_batch`), as the engine only runs it where planned.
- Mutation check (probes removed, everything else kept): the admission test's planned arm then fails with `NoKernel("matmul on cpu/any (m=8 ...) [admitted kernels only] [row-exact verify kernels only]")`, the server's failure; the gap test fails at its assertion that the plan holds the batched-verify calls.
