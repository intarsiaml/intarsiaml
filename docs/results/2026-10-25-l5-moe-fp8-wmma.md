* **Where the gain comes from.** `kMf8ZFast` (grid = pair tile, feature tile, expert slot, so one expert's pair tiles run next to each other and share its weights from the L2) is worth 1.3x by itself for the fp8 kernel

  no numerics change. Without that reorder the fp8 kernel is *slower* than r7 (0.93x). The plan's "62 TFLOP/s dequant-bound" for r7 is partly an L2 launch-order effect (53 TFLOP/s measured here in the engine order, 65 reordered).
* **Why the fp8 kernel stays at about 70 TFLOP/s** (hp's register-only 360.7 TFLOP/s does not carry over). Ablations at T = 4096 (fp8 sz+bar, TFLOP/s of the two projections): full 71; no weight loads 80; no scale FMAs 90; no LDS activation reads 69;

## 1. Scope note (as written before the measurements)

### 1.1 What is replaced

The routed expert projections of `moe_experts_impl` (`kernels/hip/moe.hip`) for prefill-sized calls: today `moe_wmma_kernel_r7` (bf16 WMMA, weights
dequantised in registers, 8 VALU per WMMA, about 62 TFLOP/s). Qwen3.6-35B-A3B: H = 2048, I = 512, E = 256, top-8. gate_up is K = 2048, N = 2 x 512;
down is K = 512, N = 2048. At a 4096-token chunk that is 8.2 TFLOP per forward (40 layers), 137.6 ms of the 420 ms 4k prefill (33 %), and
561 of 1784 ms at 16k (31 %). Decode, rows-exact (batched decode) and calls under the token threshold keep the bf16 kernels untouched.

### 1.2 Design

* **Orientation.** Weights are the WMMA B operand (columns = output features), activations the A operand (rows = pairs). In the gfx12 C layout a lane then
  holds one feature column and 8 pairs, so the per-(feature, k16) NVFP4 block scale is a single scalar per lane, the same one it loaded with its weights.
  (With weights as A, a lane holds 8 features and would need 8 scales per k16.)
* **One NVFP4 block = one k16.** `moe_wmma.h` permutes k so that a WMMA step covers two different scale blocks (lane halves read elements `s*8` and `32+s*8`).
  That layout cannot take a per-k16 scale. The new kernel uses the natural order: step t of a 64-k block = block t, lane half h takes elements
  `16t + 8h .. +7` (4 bytes of the row's 32-byte block: dwords `2t + h`). A lane still issues one 16-byte load per row and block (dwords 4h .. 4h+3 of the row's 8 dwords);
  two `v_permlanex16` (swap the two 16-lane rows) plus 6 `v_cndmask` then hand each lane the dwords {h, 2+h, 4+h, 6+h} it needs (8 VALU per row and 64-k block, 2 per k16).
* **Decode.** `ik_fp4x8_to_e4m3` of `moe_wmma_r7.h` (7 integer ops per 8 weights) gives the exact e4m3 bytes of the e2m1 values times 2^-6; the even elements land in
  one dword and the odd ones in the other, and that pair of dwords is the B fragment as is. The k slots inside a lane are therefore ordered (0, 2, 4, 6, 1, 3, 5, 7); the
  activation quantiser writes its bytes in the same order, so no byte permute is needed in the kernel. Radiance's `kMagU`/`Wref` table (exponent fold for e8m0 scales) does not
  port: NVFP4 scales are e4m3 and cannot be folded into e4m3 weights exactly. Only the lossless e2m1 -> e4m3 byte map transfers (`libr4d/r4d_mxfp4.h:20-58`).
* **Scale.** `part = wmma_fp8(x_frag, w_frag, 0)` per k16, then `acc[8] += part[8] * e4m3_to_f(scale)` as 8 `v_fma_f32` (hp priced one fp8 WMMA + 8 FMA at 360.7 TFLOP/s
  register-only, against 372.0 for fp8 alone: the FMAs co-issue; `2026-10-22-hp-hip-prefill-roofline.md` section 7). The 2^6 from the 2^-6 byte values is applied once in the epilogue.
* **Activation quantisation: per token (row), not per block.** `scale = max(amax / 448, tiny)`, `q = cvt_fp8(clamp(x / scale, -448, 448))` (RNE), one scale per row.
  gate_up input: T rows once (shared by the top-8 pairs of a token); down input: the P = 8T rows of `h`. The row scale is applied in the epilogue
  (`acc * (64 * a_row) * gscale`), then the existing bf16 rounding points (g, u, silu(g), the product) are kept, so the e4m3 activations are the only numeric change.
  Per-block (k16) activation scales were rejected: the row scale would have to enter the per-k16 FMA, 8 more multiplies per k16 per lane (the lane holds 8 different rows).
  Expected error: radiance measured 0.040 relative Frobenius per expert layer against 0.003 for a16w4 (all from the two e4m3 roundings of the activations), and an unchanged GSM8K.
* **Accumulation order.** A pair's output is the same fixed-order sum over k whatever else is in the tile, so the result is independent of the grouping, like the bf16 kernels
  (deterministic run to run; batched == solo as long as both sides take the same path).
* **Path choice.** The fp8 path is taken when `INTARSIA_HIP_MOE_FP8_WMMA=1` and the call has at least `INTARSIA_HIP_MOE_FP8_MIN` tokens (default: the crossover measured in
  step 2, radiance: 1025). Below that the bf16 r7 kernels run (they win at small M: weight-streaming-bound, the fp8 path re-reads weights per 64-pair tile just the same). The
  test-only lower threshold lets the short goldens and GSM8K (prompts under 1025 tokens) exercise the kernel at all, and each gate records the threshold it ran at.
* **Scratch.** `moe_experts_scratch` is core (CUDA and Metal use it): untouched. The HIP registry gets its own scratch function that adds `T*H + 4T + P*I + 4P` bytes (rounded to 256)
  only when the knob is on; with the knob off the number is the core one, byte for byte.
* **Files.** New `kernels/hip/moe_wmma_fp8.h` (quant kernels, `moe_fp8_kernel`); `moe.hip` (dispatch, scratch layout); `crates/intarsia-backend-hip/src/{kernels.rs,quantmoe.rs}`
  (fingerprint list, scratch fn); `docs/tuning.md`; `kernels/hip/NOTICE-radiance` (the e2m1 -> e4m3 map and the quantiser structure come from radiance, Apache-2.0).
  `scripts/l5/` holds the standalone harness and window scripts.

### 1.3 Expected time and the stop line

* Today: 8.2 TFLOP / 62 TFLOP/s = 133 ms (measured 137.6 ms at 4k).
* Target: an effective 100-110 TFLOP/s for the two projections (radiance's hand kernel: 134 TFLOP/s w13, 100 w2; our extra cost is the per-k16 FMA fold and the
  tile-restricted decode) = 75-82 ms, plus the two quantisation passes (about 0.14 ms per layer at 4k, 5-6 ms per chunk) = 81-88 ms.
* Saving 50-55 ms of 420 ms = **12-13 % served prefill at 4k** (plan: +10-20 %). [Superseded by section 0: the harness's own r7 figure is 3.86 ms/layer (155 ms per 4096 chunk), and the fp8 kernel measured 2.96 ms with both quantiser passes, 69.6 TFLOP/s, not 100-110.] 16k: experts 561 ms of 1784 ms, the same ratio, about 12 %. 1k unchanged (bf16 path).
* **Stop line.** saving = 137.6 x (1 - 1/s) - quant_ms, with s the speed-up of the expert projections over r7 at M = 4096 and quant_ms about 6. Under 5 % served (21 ms of 420) needs
  s < 1.25 including the quantisation passes. Step 2 (the standalone harness, same binary for r7 and fp8) is therefore a pass/fail: below s = 1.25 at M = 4096 I stop and report.

### 1.4 Gates (step 4) and traps recorded up front

* The short goldens and GSM8K never reach the fp8 path at the default threshold (prompts under 1025 tokens): they run with the test-only threshold lowered (`INTARSIA_HIP_MOE_FP8_MIN=16`); 35b-long (up to 4064
  tokens, chunk 4096 on HIP) runs at the default.
* The k = 2 envelope and the 3.0e-2 floor are not loosened. If 35b-long fails with the knob on, the result is reported as such (the knob stays off by default either way).
* The threshold applies per chunk; G-C batched == solo needs both sides to chunk identically, which the HIP recipe (chunk 4096, prefill chunk-invariant) gives.
