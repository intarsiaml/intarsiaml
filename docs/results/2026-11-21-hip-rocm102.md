## Verdict (first trial, before the fix)

- **Builds and runs:** this needed two changes to the image and none to the code (section 1).
- **Every kernel, unit and batch-equivalence test passes:** the HIP GPU suite, the real-35B batched / macro tests, and all
  2219 kernel cases (81 kernels admitted, 0 rejected, with per-kernel max_abs / rel_l2 identical to 7.2.4 at the printed 4
  digits). `qualify` does not pass; see the next point.
- **The 35B logits move:** 10.2 fails `qualify`'s "same as the recorded build" gates (acc-short baseline, acc-oracle
  self-golden, tp2 self-golden): mean KL21 8.6e-3 against a 1e-4 limit. 7.2.4 from the same tree passes all of them and
  reproduces the recorded baseline exactly. Against the vLLM golden, 10.2 is as accurate as 7.2.4, in a different place:
  tp1 prefill KL 5.71e-3 vs 6.00e-3, decode 1.13e-2 vs 1.11e-2 (section 2).
- **Speed:** prefill +5 % at 4k (tp1 and tp2) and +1.6 % at 16k; decode between -0.7 % and -1.7 % at 4k / 16k / tp2, which
  is about the run noise (section 3).

Recommendation at the time (superseded by the update above): no switch for now. +5 % prefill would be worth having, but switching means re-recording every HIP baseline (35B
acc-short, envelope, oracle tp1 / tp2 dumps; the 27B ones are already stale). It also means accepting a logit shift whose
cause has not been found. A follow-up that splits compiler from runtime (section 4) should come first. The user decides
whether to switch; until then the 10.2 image stays opt-in.

## 1. What the image needed

1. **No ROCm lib dir in the loader config.** The 7.2.4 image registers `/opt/rocm-7.2.4/lib` in `/etc/ld.so.conf.d`; the
   10.2 image registers nothing. The `intarsia` binary has no ROCm rpath: build.rs's `-Wl,-rpath` is a `rustc-link-arg`,
   and that reaches only the targets of `intarsia-backend-hip` itself, not the CLI that depends on it. So the first smoke test
   died at once with `libamdhip64.so.7: cannot open shared object file` (`raw/win1/smoke-doctor-first-attempt.err`; radiance
   was back 15 s later). The trial Dockerfile now writes `/opt/rocm/lib` to `/etc/ld.so.conf.d/rocm.conf` and runs `ldconfig`.
   The rpath gap is real on main too; the 7.2.4 image just hides it. Checked with `readelf -d`: the CLI has no RPATH or RUNPATH,
   and the HIP crate's own test binary (`device_pos`) has RUNPATH `/opt/rocm/core-10.2/lib:/opt/rocm/lib`.
2. **The version stamp moved.** ROCm 10 (TheRock layout) keeps it at `/opt/rocm/core-10.2/.info/version`, but `intarsia doctor`
   (and so every run stamp) reads `/opt/rocm/.info/version`. The image links `/opt/rocm/.info` to `core-10.2/.info`.
   build.rs already found the right file, because it resolves hipcc's real path to `/opt/rocm/core-10.2/bin/hipcc`.

The `-full` image also ships hipBLASLt, rocWMMA and the profilers (since 7.14 there is no slim tag). The HIP backend links
none of them (build.rs compiles `kernels/hip` with hipcc only), so the A/B measures the compiler and the HIP runtime only.
Build time: CLI 118 s on 10.2 vs 96 s on 7.2.4 (cold volumes). No new hipcc warnings; the extra Rust warnings in
`raw/build-r10.log` come from the test binaries, which only the r10 arm built.

**10.2 is deterministic across processes.** A second 10.2 `qualify` in its own window (#10528, `raw/win3/`) gave every printed
number again: acc-oracle KL21 8.5756e-3 / max 3.4393e-1 / 228 flips, tp2 8.5879e-3 / 205 flips, and the same four vLLM rows. So
the shift is a fixed change in numerics, not a race or uninitialised memory.

So 7.2.4 on this tree matches the 11-15 recording exactly, and the whole difference is the toolchain. The 10.2 build is a
different numerics point, about as far from vLLM as 7.2.4 (prefill a little better on tp1, decode a little worse on tp2).
It is much further from 7.2.4 than the gates allow. Mean KL21 8.6e-3 between the builds is the same size as each build's
distance from the reference. MoE routing and the GDN recurrence amplify small per-op differences, so this size of change
is plausible from contraction or math-library changes. It was not localised (section 4).

`scripts/rocm102/speed-window.sh` (#10527; `raw/speed-1314/`). Qwen3.6-35B-A3B NVFP4, `localeval speed`, a fresh server per

|---|---:|---:|---:|---:|---:|---:|---:|

| tp1 | 4k | 11858 | 12471 | **+5.2 %** | 160.9 | 159.4 | -0.9 % |

Per-round values are in `raw/speed-1314/summary.txt`:
- **tp2 4k prefill:** the ranges don't overlap (7.2.4 14527-14715, 10.2 15328-15462).
- **tp1 4k prefill:** two of the three 10.2 rounds are at 12471-12543 against 7.2.4's 11804-11911; the third is 10560.
- **16k:** the ranges don't overlap (10592-10717 vs 10793-10829).
- **1k:** TTFT overhead dominates both prefill and decode (7.2.4 6331-8274, 10.2 8097-8942), so the 1k row is not a speed result.

Decode differences at 4k and tp2 are inside the round-to-round spread. At 16k, 10.2's rounds (143.8-144.3) sit just below

## 4. Not done / follow-ups

- **Where the logits move.** Link a kernel archive compiled by 7.2.4's hipcc into a 10.2-runtime binary, and the reverse.
  That splits the compiler from the runtime. Then rebuild one kernel group at a time to find the code that changes the bits.
  The 10 kernels the sweep does not cover are also candidates.
- **Re-recording the baselines** if the user switches: 35B acc-short + envelope + the oracle tp1 / tp2 dumps (as in
  `scripts/gdn-default/stages.sh` `rec` / `chk`), and the 27B baselines, which need the 27B checkpoint on tatooine.
- **rpath:** a library build script cannot put a link-arg on the CLI binary. A ROCm install without a loader entry fails
  at the first run. Either the CLI's own build script gets the rpath, or the images keep the loader entry; this trial keeps
  the loader entry.
- **Not measured:** acc-long, acc-4k (known FAIL on main), the 27B, speculative / MTP decode, multi-stream throughput.
  rocprofv3 and the new 10.2 profiling features were not tried (the prof image is 7.2.4 only).
