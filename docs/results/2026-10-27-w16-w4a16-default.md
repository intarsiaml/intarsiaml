# Qwen3.8-27B MXFP4: W4A16 is the default (lane W16)

User decision 2026-10-26 20:24 EDT: "2 + 1. be cautious of tonights downtime and you can fan out the work before and after the downtime"
(option 1 = make 16-bit activations the default for the 27B MXFP4; option 2 = a separate W4A8 lane). Evidence for option 1:
`2026-10-27-act27-27b-w4a16-mmlu.md` and `2026-10-27-mmlu27-27b-quality.md` (full MMLU n=1425: W4A4 0.802, W4A16 0.822, Radiance 0.830;
cost at tp2: prefill -30%, 2121 -> 1479 tok/s at 4k, decode -13..-19%).

## Change

* New recipe key `[defaults] mxfp4_act = "dynamic" | "none"` (`intarsia-core/src/recipe.rs`). Precedence, in `quant::mxfp4::effective_act`:
  `--mxfp4-act`, then the recipe key, then what the checkpoint declares (Quark: `dynamic`), then W4A16.
* `recipes/qwen3_5_vl.toml` (`Qwen3_5ForConditionalGeneration`, the Qwen3.8-27B) sets `none`. No other built-in recipe sets it (test
  `the_27b_recipe_defaults_to_w4a16_and_no_other_recipe_sets_the_key`). The key is read only for MXFP4 projections, so a bf16 checkpoint
  of the same architecture is unchanged and prints no `mxfp4 activations` line.
* Load log: `mxfp4 activations: none (recipe qwen3_5_vl [defaults] mxfp4_act)`; the deviation note (`scheme.rs mxfp4_act_note`) says the
  recipe chose it for accuracy (MMLU 0.822 vs 0.802) and that `--mxfp4-act dynamic` runs the declared scheme. `intarsia recipe` text
  (`cmd/recipe.rs`) says a scaffolded recipe does not set the key.
* `qualify` gate: goldens are a property of the activation mode (docs/results/2026-10-25-ac-27b-accuracy-gate.md: a W4A16 golden against a
  W4A4 run is 0.14 KL21 away). `qualify` (1) computes the model's effective mode (recipe key, else checkpoint), and when it finds a golden by
  model name prefers the `-w4a16` one for `none` and never takes it for `dynamic` (`facts::find_golden_act`); (2) runs `intarsia accuracy`
  with `--mxfp4-act` set to the mode the golden was made with (`facts::golden_act`: `activations dynamic|none` in the golden's
  `engine_version` metadata, which `tools/golden_quark_mxfp4.py` writes, else `-w4a16` in the file name; unknown: no flag). So the default
  W4A16 path is gated against the W4A16 golden and its recorded baseline (`golden/baselines/...-w4a16-top20.hip.*`), and a W4A4 golden
  still gates W4A4 (the opt-out). No golden was re-recorded. Limit: the 27B goldens are named `qwen3.8-27b-mxfp4-hfquark-*` and the
  model directory `Qwen3.8-27B-Quark-AWQ-MXFP4`, so they are not found by name today; they are given with `--golden`, and (2) then
  applies. (1) matters once `--model-name` or a golden directory uses the matching name.

## CPU checks

`cargo test --release -p intarsia-core -p intarsia-models -p intarsia-cli`: all pass, including the precedence matrix
(`act_precedence_is_cli_then_recipe_then_checkpoint`: CLI dynamic / CLI none / recipe none / recipe dynamic / no key -> checkpoint W4A4 /
checkpoint W4A16 / nothing declared), the real 27B `config.json` selecting `builtin:qwen3_5_vl` (no flags: `none`; `--mxfp4-act dynamic`:
`dynamic`), `every_schema_key_is_documented`, and the qualify golden tests (`mxfp4_golden_follows_the_activation_mode`).

G0 for other models: not run as `plan show` byte-identity. It is a valid check only for models whose recipe changed or whose loader path
changed; here the only code path that reads the new key is MXFP4 activation resolution, `effective_act(cli, None, declared)` is the old
function, and the test above asserts that no recipe other than `qwen3_5_vl` carries the key. The 8B and 35B checkpoints are not complete
in this Mac's Hugging Face cache, and there is no origin/main binary of the same date to diff against, so a `plan show` diff was not made.
