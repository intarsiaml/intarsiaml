Median of 3 reps after 1 warmup, 128 forced output tokens, 2 m 14 s total:

|---:|---:|---:|---:|---:|

| 4122 | 8.088 | 510 | 11.0 | 81.7 |

The "floor" is 221 GB/s / 16.38 GB = 13.5 tok/s, the figure in the task. It overstates what a decode token reads: the
input embedding table (1.24 GB) is a one-row gather, so a token reads about 15.1 GB, a floor of about 14.6 tok/s.
By that measure 14.6 tok/s at short context is about 100% of the floor, and about 92% of the 242.2 GB/s device copy
bandwidth that `intarsia doctor` measures on this box (about 224 GB/s effective read rate). Decode loses ground as
context grows (14.6, 13.7, 11.0 tok/s) because the decode attention kernel runs one block per head and walks the KV
serially. Prefill at 4k drops to 510 tok/s (from 1246), probably the simple prefill attention kernel.
Server-side, `/metrics` after the 20-token curl requests showed last decode 14.86 tok/s; its last prefill figure
(55.5 tok/s) is just the fixed per-step cost on a tiny prompt.

## 5. Honest gaps

Correctness and gates
* The Mac 0.6B bf16-golden run fails the default 1e-3 mean-KL gate (1.247e-3). See 2.2 for the evidence and the decision needed.
* The golden sets are small (8 prompts, 434 positions), not the ~64 prompts the plan describes. Top-1 99.08% on the 0.6B is a margin of a few positions.
* Admission uses 0.6B shapes. The 8B's K=12288 down projection and the K=4096 full-vocab logits are covered only by the end-to-end accuracy run, not by the sweep.
* No runtime admission hook: `generate` and `serve` do not run admission at load. Determinism of the `Deterministic` kernels is checked on a 40-case repeat only.
* `--kv-dtype fp8_e4m3` loads on CUDA and then fails with NoKernel at the first attention call, because the attention kernels need bf16 KV. Load should reject it.
* Sampling has no device kernel (host sampling only). No sampling-quality test was run.

Performance
* Decode attention (one block per head, 32 blocks on 48 SMs, serial KV walk) costs 25% of decode speed at 4k context (14.6 to 11.0 tok/s). A split-KV kernel needs a scratch buffer, which the launcher ABI does not allow yet.
* Prefill falls from 1246 to 510 tok/s at 4k; there is no flash-style prefill attention.
* Weights are held twice on the GB10 (page cache and the cudaMalloc copy); loading takes 32 to 57 s. Zero-copy is a follow-up.
* The live profile (`intarsia top`) shows `embedding` at about 34% of kernel time and 54 ms per call. That is almost certainly queue wait absorbed by the first profiled op, not real embedding cost. **Resolved 2026-10-12 (fixcore):** the profiler now synchronises before starting an op's timer (Opus review finding 10); with `--profile-every 1` on spark1, Qwen3-8B, 2 requests of 600 prompt tokens + 24 decode tokens, `embedding` totals 0.54 ms over 50 calls (about 11 us each) and `matmul` is 3.13 s of the 3.65 s profiled.
* Batch size 1 and contiguous KV only: no concurrency measurement (`bench speed --concurrency` not run), no paged KV, no graphs.
* One run per configuration, on a box with a vLLM neighbour; run-to-run variance across sessions is unknown (within a run, reps agreed within 1%).

API and server
* No reasoning-content splitting: Qwen3's `<think>` text arrives in `content` (visible in the Anthropic stream). No tool-call parsing, logprobs, n>1, batched prompts, images, auth or CORS.
* Anthropic `stop_reason` is only `end_turn` or `max_tokens`; `stop_sequence` is always null.
* The ITL histogram is a per-request mean weighted by token count, not true per-token latency.
* `/health` field `last_step_ms` is an epoch timestamp in milliseconds, not a duration. The name misleads (same field in the telemetry snapshot).
* localeval warned that it could not verify the server was idle: it looks for vLLM-style in-flight counters, and `/metrics` exposes `intarsia_requests_running` instead.
* `intarsia top` was checked against the live `/events` stream through a pty, not on a real terminal.
* No process supervisor or step watchdog yet (plan section 4); a wedged CUDA context would not be restarted.
* `info().free_mem` from `cudaMemGetInfo` ignores reclaimable page cache on GB10 and under-reports (38.7 GB vs 55.8 GB available).

Process
* Everything under `crates/`, `kernels/`, `recipes/`, `deploy/`, `docs/` and `tools/` is still untracked; `Cargo.lock` and `tools/uv.lock` should be committed.
* Goldens (130 MB each) are git-ignored. The 8B golden lives only on spark1 at `~/intarsiaml-golden/qwen3-8b.safetensors`, the Mac goldens only in `golden/`. Repo syncs to spark1 must exclude `golden`.
* The Grafana dashboard JSON parses but was not loaded into Grafana. Disk on spark1 is 95% full (about 200 GB free); I deleted `~/intarsiaml/target/foundation` (1.6 GB), and `~/intarsiaml/target` is now 1.5 GB.

## 0. What integration changed

The pieces from the six workstreams compiled together; the one thing missing was the join in the decoder
(`crates/intarsia-core/src/model.rs`). Everything below is that join, nothing else:

| Change | Why |
|---|---|
| `Block::Moe` arm in `Model::load` / `run_chunk`, reading `[layer.moe]` (`kind`, `prefix`) from the recipe and the MoE sizes from `ModelDims.moe` | the quantmoe agent built `MoeWeights::load/forward` but nothing called them |
| `ModelDims.moe: Option<MoeConfig>`, filled by `from_hf_config` when the config has MoE keys (a MoE config missing a key is now an error, test updated) | `Model::load` gets dims, not the raw config |
| One shared `MoeScratch` in the workspace (not one per layer), counted in the memory plan; `ExecRunner` implements `OpRunner` over `Model::exec`, so MoE ops get profiling, plan recording and kernel scratch like every other op | the plan resolver sees MoE shapes; admission runs on them |
| `lm_head` is a `QTensor`; head matmuls go through `proj` (`Op::Logits` for bf16, `Op::MatmulNvfp4` with f32 output for the quantised head) | the checkpoint's `lm_head` is NVFP4 (`weight`, `weight_scale`, `weight_scale_2`, `input_scale`); the recipe's `tied_to` is only a fallback |
| `LoadOptions.fp8_act` and `--fp8-act static|none` on every model command (default: the recipe's `[defaults] fp8_act`, i.e. `static` = W8A8) | lets the FP8 W8A8 vs W8A16 question be measured (section 3.2) |

client (forced 128 tokens, thinking off). vLLM's prefill TTFT at 1k-4k tokens is 5-7x faster than ours.

Where our time goes (`generate --profile-every 1`, which synchronises per op and so lowers decode to 56 tok/s):
- Prefill, 1610-token prompt: `moe_experts` 1447 of 2289 ms (63%) at chunk 256, 1370 of 1915 ms at chunk 1024; then
  bf16 `matmul` (router, gates) 398 ms, `matmul_fp8` 235 ms, `gdn_delta_rule` 64 ms. Per call `moe_experts` costs
  about 4 ms at 256 rows and 8.5 ms at 1024: the kernel is a CUDA-core dequantising grouped matmul, not a tensor-core
  one, and re-reads the expert weights each chunk.
- Decode: 844 kernel launches per token (sum of `calls_per_decode_step` in `/v1/intarsia/plan`: 140 bf16 gemv for
  routers/gates/in_a/in_b, 130 FP8 gemv, 121 NVFP4 gemv, 80 rmsnorm_add, 70 silu_glu, 40 each topk/experts/combine,
  ...). Bytes read per token, counted from the checkpoint layout (not measured): FP8 GDN projections 30 x 33.5 MB =
  1.0 GB, gated-attention FP8 10 x 27 MB = 0.27 GB, active NVFP4 experts 8 x 1.67 MB x 40 = 0.53 GB, shared experts
  0.07 GB, NVFP4 `lm_head` 0.29 GB, routers 0.04 GB: about 2.2 GB, a floor near 10 ms (about 100 tok/s) at
  221 GB/s. Against that floor vLLM (13 ms/token) is at about 78% and we (15.5 ms) at about 64%. 844 launches in
  15.5 ms is 18 us each, so launch and latency overhead is the likely limit; CUDA graphs and a fused MoE block are
  the candidates, and neither exists yet (hypothesis, not tested).

## 3. What was built

1. **HIP graph capture and replay of the decode step** (`crates/intarsia-backend-hip/src/device.rs`, `kernels/hip/ik_runtime.{h,hip}`):
   `supports_graphs()`, `graph_capture` (`hipStreamBeginCapture` thread-local mode, `hipStreamEndCapture`, `hipGraphInstantiate`)
   and `graph_replay` (`hipGraphLaunch`), driven by the existing `crates/intarsia-core/src/model/graph_step.rs` and the device `pos` tensor
   the HIP launchers already took. `INTARSIA_HIP_TRACE` stream events are skipped while a capture runs.
2. **v2 decode kernels**, registered next to their v1 kernels (`matmul_nvfp4_gemv_v2`, `matmul_fp8_gemv_v2`, `moe_topk_bf16_v2`,
   `moe_experts_bf16_v2`; the registry prefers them by priority; all four are ADMITTED, errors 0 against the cpu reference, see
   `intarsia kernels test`). They compute the same arithmetic in the same order as v1 and are **bitwise equal** to it:
   * nvfp4 gemv and the MoE p1 gate_up/down kernels request the first lane-iterations' weights, scales and activations *before* the
     shared-table barrier (the barrier used to precede every load), so the table fill overlaps the memory latency.
   * fp8 gemv stages the activations eight per thread, converts to e4m3 with the gfx12 hardware instruction
     (`v_cvt_pk_fp8_f32`, after an explicit clamp, scale a power of two), and uses two rows per warp at every N
     (`INTARSIA_HIP_FP8_Q=1|2|3`, `INTARSIA_HIP_FP8_ROWS`; default Q=2).
   * moe top-k packs each candidate into a 32-bit key so a warp argmax round is one shuffle and one max.
3. **Fusions inside existing launchers** (no new op, 50 fewer launches per step): the single-tile `gdn_conv_bf16` writes its own new
   state (`gdn_conv_state` only runs for T > 32), and the partial-rotary `rope_bf16` copies the un-rotated tail itself
   (`rope_pass` only runs for rotary_dim 0).
4. Knobs (all in the admission fingerprint, `kernels.rs::ENV_KNOBS`): `INTARSIA_HIP_FP8_Q`, `INTARSIA_HIP_MOE_PRE`
   (lane-iterations in flight before the barrier, default 4), `INTARSIA_HIP_XSTAGE` (activations through shared memory,
   default off: measured slower for the MoE kernels, 42.8 us against 37.6 us).

### Tried, no gain

* Shared-memory staging of the activations for nvfp4 gemv and the MoE p1 kernels: no change for nvfp4, 14 % slower for MoE.
* Warps per block for the MoE v2 kernels (2, 4, 8): 37.7 us in every setting. Prefetch depth 1 / 2 / 4: 45.7 / 43.0 / 37.8 us;
  4 already covers all lane-iterations of H = 2048, so more cannot help. The MoE kernels are limited by their dependent phases
  (ids -> weights -> reduce -> second kernel), not by occupancy or by request depth.
* The CLR environment knobs listed in section 2.
* Reusing a stream after an *invalidated* graph capture: two attempts (an empty failing body, and a synchronous copy inside the
  capture) both left the device returning `hipErrorStreamCaptureInvalidated` (901) for later calls; the wrong assumption was that
  `hipStreamEndCapture` + `hipGetLastError` + `hipStreamSynchronize` clears the capture error. Stopped. Consequence: a capture
  that fails would leave the HIP backend unusable although `graph_step.rs` would switch graphs off. Neither the 35B nor the 8B
  fails one (1 capture, 1920 and 1905 replays), and the test for it was dropped (documented in `tests/device_pos.rs`).

### Scope notes

* **Tensor parallel is not affected**: `GraphState::new(opts.graphs && tp.world == 1)` (`crates/intarsia-core/src/model.rs`) keeps graphs
  off for TP models, so the TP=2 path never reaches `graph_capture` (the unrecoverable invalidated-capture case above cannot be
  hit there). No TP run was made on this branch.
* Radiance port plan (`docs/research/radiance-port-plan.md`) decode techniques *not* tried, and why: the fused GDN decode block op
  (conv update + recurrent update + gated rmsnorm in one kernel, section 3.5) would remove ~3 launches per GDN layer (~90 per
  step) but is a new block-scope op across the CPU / CUDA backends; gate/up weight fusion at load (section 3.3, halves the shared
  expert GEMV launches and feeds `silu_mul` one row) needs a loader / recipe change; `qk_norm + rope(+gate)` fusion touches 10
  layers only; per-shape tune tables (section 7.4) were replaced by the knob sweeps above; the fused all-reduce kernels are TP.
  These are the next candidates: with a ~1.5 us boundary per launch and ~900 launches, every 100 launches removed is ~0.15 ms
  (~2 %).

### Not done

* Fusions that need a new op or a graph change: gate_split + sigmoid_mul (not adjacent in the dataflow), topk + combine (the
  routed experts sit between them), rmsnorm + residual (already one kernel, `rmsnorm_kernel<true,true>`), the GDN small GEMVs
  (a, b, router and shared-expert gate: 140 launches of ~2 us plus their boundaries; a two-weight GEMV or running them on a forked
  capture stream would remove ~0.2 to 0.4 ms), `shared gate/up + silu_glu`. Each is an op-level change across the CPU and CUDA
  backends; with a ~1.5 us boundary per launch they are worth ~1 to 2 % each.
* fp8 and MoE are at 77 % and 62 % of DRAM bandwidth in the step (cold microbenchmarks: 86 % for the big fp8 shapes); the
  remaining headroom is ~0.35 ms (fp8) and ~0.5 ms (MoE) per step if the dependent-phase latency of the MoE pair could be hidden.
* The full (non-quick) `intarsia kernels test --model <35B>` panics in the cpu reference (`reference.rs:120`, `chunk_size must not
  be zero`, a Matmul case with n = 0). **Pre-existing**: it reproduces on `63b0f72` built in `~/intarsiaml-base` (0 `_v2`
  kernels registered, same panic). It makes the `kernels` stage of `qualify` ERROR for the 35B (the other six quick stages
  pass). Not touched; `kernels test --quick` on the 35B passes.

## Method

`kernels/cuda_checks/decode_replica.cu` launches the kernel sequence of `Model::run_chunk` (with `ik_moe_experts_bf16`,
not the engine's `ik_moe_experts_decode_bf16`, see the correction above) for one
Qwen3.6-35B-A3B token (T = 1): 40 layers (30 GatedDeltaNet, 10 gated attention), every layer followed by the MoE
block (router, top-8 of 256, routed experts, shared expert, combine), then final norm, NVFP4 `lm_head`, argmax.
Shapes are the real ones (hidden 2048, 16/2 heads of 256, GDN 16 key / 32 value heads of 128, conv width 8192,
experts 512 wide). Weights are random bytes and the routed experts of all 40 layers share one set; per-layer
dense weights are separate, so L2 does not hide the 2.2 GB read per token. It links the real `kernels/cuda/*.cu`.

- Machine: spark2 (GB10 sm_121, CUDA 13.0.88, nsys 2025.3.2), fleetq jobs #1435 to #1438, `--mem 4..8`.
- Context 1024, 200 to 300 timed steps after 5 warmup, token id copied in and token copied out every step.
- nsys: `nsys profile -t cuda` (eager) and `--cuda-graph-trace=node` (graph), 30 steps each, `cuda_gpu_kern_sum`.

## Step time

| Variant | median ms/step | tok/s |
|---|---:|---:|
| eager: one launch per kernel, host position | 15.27 to 15.30 | 65.3 to 65.5 |
| CUDA graph, device-side position | 13.14 to 13.17 | 75.9 to 76.1 |
| graph + second stream for independent branches (shared expert, GDN z/b/a projections) | 12.58 | 79.5 |

The eager replica matches the engine (63 to 65 tok/s in `2026-10-12-phase1a.md`), so the replica is a fair model
of the launch pattern. GPU busy time per step is 13.5 ms eager and 13.3 ms graph (nsys kernel sums). So the
eager step wastes about 1.8 ms (12%) on host launch gaps, which graph replay removes. After that the step is
bound by kernel time, not launches.

|---|---|---:|---:|---:|---:|

## What this says about the 10.6 ms floor

- The FP8 GEMVs read 1.27 GB per token (30 x 33.5 MB GDN, 10 x 27 MB attention). At 221 GB/s that is 5.7 ms; they
  take 6.1 ms, so they run at about 93% of the copy bandwidth. Little to win there.
- The routed experts read 0.53 GB (2.4 ms at 221 GB/s) and take 2.9 ms in gate_up + down: about 82%.
- The `lm_head` reads 0.29 GB (1.3 ms) and takes 1.29 ms: at the floor.
- Together these three are 8.6 ms of the 13.3 ms and sit near their byte floors. The floor is 10.6 ms because it
  adds the other bytes; the step cannot reach it while the 4.7 ms of small kernels stay serial.
- The small kernels (bf16 gemv 0.53, shared-expert gemv 0.51, norms 0.25, silu 0.12, GDN core 0.86, attention
  0.32, MoE routing 0.32) are 3.0 ms, latency bound at 1 to 4 us each, with a dependent chain between them.
- Running independent branches concurrently (second stream inside the capture) took the replica from 13.15 to
  12.58 ms: 0.57 ms, 4%. A fusion that removes launches inside a graph saves the kernel's ramp and tail
  (about 1 to 2 us each), not a host gap, so the ceiling for fusing norms, silu and GDN glue is roughly 0.3 to
  0.5 ms.
- `gdn_delta_rows_kernel` is the largest single non-GEMV kernel (24 us x 30). It reads and writes the f32
  recurrent state (32 x 128 x 128 x 4 B = 2.1 MB read plus written per layer, 63 MB per token, 0.29 ms at 221
  GB/s), so it takes 2.5x the state traffic. That is the best fusion target after graphs (conv + gating +
  recurrence + gated norm in one kernel).

Projection: graph replay alone is worth about 2.1 ms (65 to 76 tok/s in the replica); streams add about 0.6 ms.
vLLM measures 76 to 78 tok/s on the same checkpoint, so graph replay by itself could reach vLLM's level in the
engine, if the engine's decode MoE kernel (not the replica's) costs the same inside a captured graph: unmeasured. The remaining gap to 94 tok/s (10.6 ms) is mostly kernel efficiency, not launch overhead.

## What changed in the code (checks per item in the table below; the CUDA Rust path has never linked or run)

- Device-side position: `OpCall::pos` (an `i32 [1]` tensor) for `Rope`, `KvAppend`, `AttnDecode`. The launchers
  `ik_rope_bf16`, `ik_kv_append_bf16`, `ik_attn_decode_bf16`, `ik_attn_decode_bf16_splitkv` take an optional
  `const ik_tensor* pos` before `stream` (ABI header updated). The split-KV decode launches its grid at the
  length-independent maximum and the blocks past the active split count exit; the partition is unchanged.
- `Backend::{supports_graphs, graph_capture, graph_replay}`; CUDA implementation over
  `ik_rt_graph_begin/end/launch/destroy` (thread-local capture mode). cpu backend resolves the device position
  at launch.
- `Model` captures the whole T = 1 step once per `SequenceState` (token and position are device scalars) and
  replays it; profiled steps, a failed capture, `--no-graphs` and backends without graphs run the eager path.
  A new state (new id) gets its own recording; `reserve_scratch` and re-resolution drop it.
  `ResolvedPlan::decode_position_stable` is true only when the plan selects the same kernels at the first and
  last context position. Telemetry: `graph_replays`, `graph_captures`.
- KV layout is unchanged (contiguous `[Nkv, cap, D]`); no paged KV.

## Open risks (read from code, not run)

- Ordering and parity of the graph path were checked by reading `Model::forward_inner`: the `st.len + ids.len() <= st.cap`
  check runs before the graph branch (a device-position append cannot bounds-check), and the branch does the same
  `st.commit` and `telemetry.step` as the eager loop. Split-KV scratch is already a kv_len-independent bound in
  `kernels.rs::splitkv_scratch` (`splitkv_parts(usize::MAX/2, ..)`), equal to the maximum the new decode launcher uses.
- `decode_position_stable` compares plan probes at position 0 and cap-1. If a decode kernel's `when` looked at
  `kv_len`, graphs would switch off without a message. Not seen in the registrations, never run on the real plan.
- The first capture happens inside the first graph decode step. `StreamId 0` is a stream from `cudaStreamCreate`
  (not the legacy default stream), so capture should be legal; unverified on a GPU through Rust.
- The MoE block under capture: `moe.rs` has no per-step upload/download/sync by reading, but it never ran under
  a capture guard (the cpu fixture has no MoE). A violation shows as one stderr line and an eager fallback.
- ABI: `ik_rope_bf16`, `ik_kv_append_bf16`, `ik_attn_decode_bf16(_splitkv)` gained a `pos` argument. The HIP
  worktree (`phase2a/hip`) must take the same signature; not touched here.

## 8. Accuracy bisect (2026-10-13, spark1, measured)

### 8.4 The defect in `moe_experts_mma_bf16` and its fix

What was compared. Real layer shape (H=2048, I=512, 64 experts, top-8), outputs against the CPU reference `ref_moe_experts` (which matches the old kernel to 0.01 to 0.1 % of elements), bf16 elements that are not equal to the reference:

| | old `moe_experts_bf16` | `moe_experts_mma_bf16` before | after |
|---|---:|---:|---:|
| T=40 | 0.01 % (rel_l2 3.9e-5) | 1.01 % (3.5e-4) | 0.19 % (1.6e-4) |
| T=128 | 0.14 % (1.4e-4) | 0.74 % (3.2e-4) | 0.13 % (1.3e-4) |
| T=512 | 0.12 % (1.3e-4) | 0.60 % (2.8e-4) | 0.13 % (1.3e-4) |

(first run of a throw-away diagnostic, random case seed 5; the committed test uses other data, see 8.5.) The kernel-admission worst `rel_l2` of `moe_experts_mma_bf16` fell from 3.377e-4 (7.2) to 1.245e-4 (`final-gate/logs/kernels.log`).

Cause. `moe_mma_kernel` called `ik_mma_bf16_16816(acc[i][j], ...)` with the running fp32 sum as the C operand for all 32 (gate/up) or 8 (down) k steps of 64. The tensor core's accumulate step aligns the operands to the larger exponent and drops low bits (its fp32 accumulation is not an IEEE add), so the error of a long dot product grows with the number of steps; the warp-per-row kernel sums in ordinary fp32 and does not have it. The weights are dequantised exactly and the bf16 rounding points of the epilogue were already the reference ones, so accumulation was the only precision difference left. The mechanism is inferred from the effect of the fix (5x fewer off-by-one outputs); the SASS was not inspected. The signed mean error against the reference is small and of mixed sign (|gain| below 2e-6 before and after), so this was extra noise, not a bias.

Fix (`kernels/cuda/moe_grouped.cu`, mainloop): every k16 `mma` starts from a zero fragment and its result is added to the accumulator with a normal fp32 add (`float t[4] = {0}; mma(t, ...); acc += t`). Cost on the kernel (A/B in one lease, original and fixed kernel alternated twice, `bench_real_shapes`, microseconds): T=16 918 -> 931, T=64 2020 -> 1995, T=128 2275 -> 2309, T=256 2446 -> 2419, T=1024 3019 -> 3112 (+3.1 %), T=4096 6743 -> 7002 (+3.8 %). Prefill tok/s of the whole engine is unchanged (8.6). The dense `matmul_*_gemm` / `matmul_*_mma` kernels use the same in-mma accumulation; they are unchanged against the old build (8.2), so they are not part of this regression and were left alone.
