# fp8kv: the opt-in fp8 (e4m3) KV cache on the batched path, measured for 35B serving

Lane fp8kv, 2026-10-29, branch `lane-fp8kv/opt-in` from `main` 867b97145, merged with 7aebefb83 (#250, HIP only). spark2
(spark-fa00, GB10 sm_121), `nvidia/Qwen3.6-35B-A3B-NVFP4`. CUDA only. Raw: `docs/results/2026-10-29-fp8kv-opt-in/raw/`.

**Status: PR, opt-in.** The bf16 default is unchanged: its bitwise gates hold and the SASS of every bf16 attention kernel is
unchanged. `--kv-dtype fp8` (or `kv_dtype = "fp8_e4m3"` in a recipe) now runs the B = 16 batched step and the MTP verify on one
row-table launch per layer with CUDA graphs. It changes outputs. On the short quality evals the change is inside noise.

## Result

- **What was missing.** CUDA had fp8-cache kernels for solo decode, verify / short prefill and flash prefill (round 5,
  `docs/results/2026-10-19-cuda-round5.md`), but no fp8 twin of the row-table attention `attn_decode_bf16_splitkv_rows` (#246).
  Under an fp8 cache:
  - **Batched decode fell back.** `attn_batch_rows` (`crates/intarsia-core/src/model/batch.rs`) found no kernel for the rows
    `AttnDecode` call, so it ran per-row launches. That marks the step state-bound, and `batch_graph_prepare` then turns the
    batched CUDA graph off ("batched steps run eagerly").
  - **MTP verify fell back too.** `verify_attn_rows` made the same rows call and also fell back to one `AttnDecode` per row.
  - **Everything else already handled fp8.** That covers the KV append (also the rows twin), prefix store sizes (`size_bytes`
    of the slot dtype), packed prefill (per segment `attn_rows` on the slot's view), the drafter caches and solo graphs.
  - This fallback was found by reading the code. Its cost on main was not measured.
- **The fix.** One kernel, `attn_decode_f8kv_splitkv_rows`:
  - `splitkv_rows_persist_kernel` (the B = 16 path of #246) and the full `splitkv_kernel<ROWS>` grid are templated on the cache
    type. The e4m3 instantiation uses 8-byte streaming loads and the e4m3 unpack `splitkv_step` already had.
  - KB stays 2 for the 35B's group of 8 heads, as in the solo f8kv decode kernel, so row r is bitwise
    `attn_decode_f8kv_splitkv` on row r alone. That is the batch-invariance argument, and tests/row_tables.rs checks it.
  - It is registered as a row-table twin with `.weights([Fp8E4m3])`, so only an fp8 cache selects it.
  - The bf16 instantiations compile to the same SASS. All 62 kernels of `attention_splitkv.cu` match main, and the 4 bf16
    persist kernels match once the new template argument is stripped from their names (`raw/sass.txt`).
- **Scale.** Scale 1.0, a saturating cast (`__NV_SATFINITE`) of the bf16 K / V in `kv_append`. This is unchanged and it is what
  vLLM does here.
  - The checkpoint declares `kv_cache_quant_algo: FP8` (`hf_quant_config.json`) but ships no `k_scale` / `v_scale` tensors:
    the index has only `weight_scale` and `input_scale`, 30971 each. vLLM then uses 1.0.
  - Static checkpoint scales could be folded in for free: k_scale into the attention `scale` attribute, v_scale into the
    combine. That is left for a checkpoint that has them.
  - A computed scale (per tensor, or per token and head as TensorFold did, unanimis 0b34c5f6) costs work on every append and
    load. e4m3's error is relative (3 mantissa bits), so a scale would only help values in e4m3's subnormal range, below 2^-6.
- **Accuracy (the gate).** Same server build, bf16 vs fp8 KV, thinking off, greedy, localeval 0.4.0 (`raw/w3/`):

  | measure | bf16 KV | fp8 KV | Δ | noise (2·SE) | verdict |
  |---|---:|---:|---:|---:|---|
  | MMLU, 10 per task (n = 570) | 0.846 | 0.851 | +0.005 | ±0.043 | noise |
  | GSM8K, flexible (n = 100, bare answer, ~8 output tokens) | 0.500 | 0.500 | 0.000 | ±0.141 | noise |
  | MMLU predictions that differ | | | 12 / 570 (2.1 %): 6 now right, 3 now wrong | | |
  | GSM8K predictions that differ | | | 22 / 100: 2 now right, 2 now wrong | | |
  | greedy, 256 tokens: first differing token, 1k / 4k / 16k (2 prompts each) | | | 14, 55 / 22, 27 / 2, 17 | | see below |

  - **Greedy divergence.** It is early at every length: 2 to 55 tokens. For scale, the prefix-store test's chunk-schedule
    change (store on vs store off, `raw/w1/prefix.txt`) moved logits bits but kept all 48 greedy ids. The fp8 cache is a larger
    perturbation than a chunk change.
  - **The evals are coarse.** These short evals see no loss. They cannot resolve a sub-point loss, and GSM8K ran without
    chain-of-thought. Round 5 found the fp8 cache's KL inside the bf16 same-window range on the 35b-short golden.
  - **Verdict.** MMLU and GSM8K are inside noise. The greedy divergence (2 to 55 tokens; at token 2 on one 16k prompt) has
    no same-window noise reference, so it is reported here, not cleared.
  - **localeval run ids:** 20261029-125916-adhoc-fp8kv-bf16-mmlu, -130646-...-fp8-mmlu, -130444-...-bf16-gsm8k and
    -131210-...-fp8-gsm8k. unanimis 748ebc90, 3126a7fb, 53099691, 7f3bd420.
- **Speed.**

  | measurement | bf16 KV | fp8 KV | Δ |
  |---|---:|---:|---:|
  | decode-attention bucket, B = 16 step, ~1.1k context, nsys (stage 1 + KV append per step) | 1.785 ms | 1.114 ms | **-0.67 ms (-38 %)** |
  | attention rows kernel alone, B = 16, 10 layers' own caches from DRAM, 1.1k / 4k / 16k keys | 187 / 638 / 2295 us | 112 / 373 / 1196 us | -40 / -42 / -48 % |
  | attention rows kernel alone, B = 8, 1.1k / 4k / 16k keys | 97 / 317 / 1144 us | 66 / 191 / 603 us | -32 / -40 / -47 % |
  | step B = 16, prompt 1024, graphs, 2 interleaved rounds x 3 runs (ms) | 43.0 / 44.9 / 44.2 | 42.5 / 44.6 / 44.4 | about -0.2 ms, inside run-to-run spread |
  | step B = 8, same (ms) | 28.9 / 29.2 / 29.1 | 28.3 / 30.7 / 30.7 | see note |
  | serve burst (1k prompts, 256 gen, `--max-batch 16`), 3 interleaved rounds: 1 / 4 / 8 / 16 streams tok/s | 79.6 / 175.7 / 230.2 / 300.8 | 79.3 / 175.5 / 236.7 / 305.0 | -0.4 / -0.1 / +2.8 / +1.4 % |
  | single stream, MTP default, 3 rounds: decode tok/s at 1k / 4k / 16k | 110.8 / 113.2 / 86.9 | 107.5 / 110.0 / 95.5 | -2.9 / -2.9 / **+9.9 %** |
  | single stream: prefill tok/s at 1k / 4k / 16k | 5253 / 6925 / 6584 | 5254 / 6851 / 6409 | 0.0 / -1.1 / -2.7 % |
  | single stream: TTFT at 16k | 2.53 s | 2.60 s | +0.07 s |
  | KV bytes per token | 2x | 1x | half (MemAvailable with the server up: +1.3 GB at `--max-seq 8192`) |

  - **The step and burst barely move.** At the served ~1k context, attention is about 1.8 ms of a ~44 ms B = 16 step. Halving
    its bytes saves 0.67 ms of kernel time, about 1.5 % of the step, which is what the 16-stream burst shows (+1.4 %, inside
    the ±5 % decode noise).
  - **The win grows with context.** The kernel saving is 1.9x at 16k, and single-stream 16k decode gains +9.9 %. Round 5
    measured +4.9 % at 16k without MTP.
  - **Single-stream decode is confounded by MTP.** Acceptance depends on the tokens, and fp8 changes the tokens, so the 1k /
    4k -2.9 % is the same kind of noise. The 16k gain matches the kernel numbers.
  - **Prefill is slightly slower.** -2.7 % at 16k. This is the round-5 flash f8kv kernel (-1.3 % then), whose staging
    converts every tile. That kernel is not touched here.
  - **Step note.** The B = 8 fp8 runs 2 and 3 were 1.5 ms slower than bf16, while the attention kernel is 32 % faster. The
    decoded tokens differ between the two caches, so the MoE routing differs too. The step test's wall time is therefore not
    a controlled A/B under a numerics change. The nsys bucket and the kernel timing are.

Batch invariance holds for the fp8 cache exactly as for bf16. So prefix reuse keeps its warm == cold property under fp8, and
the batch composition never changes a row's bits.

## How to use it

- **Turn it on.** `intarsia serve ... --kv-dtype fp8` (also `fp8_e4m3`, `float8_e4m3fn`), or `kv_dtype = "fp8_e4m3"` in
  `[defaults]` of a copy of the recipe passed with `--recipe`. `/metrics` reports it in `intarsia_info`.
- **When to use it:**
  - Long contexts (16k: +10 % single-stream decode).
  - KV memory is the limit: it halves KV bytes per token. How many more tokens the planner then admits was not measured
    here (`plan show` prints no capacity line for this case).
  - Matching vLLM's served numerics: vLLM serves this checkpoint with `--kv-cache-dtype fp8`.
- **Not worth it** at ~1k-token bursts (+1.4 % at 16 streams), or where outputs must be bitwise the bf16 gates'.

## Not done

- **Main's fp8 fallback cost.** The per-row fallback plus eager batched step on main was not measured.
- **Prefill.** The fp8 flash prefill kernel's 1 to 3 % loss is untouched.
- **Stronger accuracy measures.** No CoT GSM8K, KL golden or long-context needle eval for fp8 in this lane; round 5 has the
  KL figure.
- **The combine kernel** is not in the nsys bucket (name filter). It is the same kernel for both caches, so the delta stands.
