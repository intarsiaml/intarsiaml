## 7. Gaps and what to do next

*Tree: 4963b43 + uncommitted worktree (dirty), later committed as a7da13b; exact tree not recorded.*

1. **Prefill** (2.0-4.4k tok/s): GEMM at 48-81 TFLOPS is about 25-42% of peak and flash attention at 22-27 TFLOPS about 13%. Next: a double-buffered K loop with direct-to-LDS loads or
   `ds_read_tr`, 256-row tiles for N = 12288, a K/V-prefetching flash kernel (the 4k prefill is attention-bound: 3068 vs 3386 tok/s at 1k), and a hipBLASLt route (`Fast`) for comparison.
2. **k/v GEMV** at 58%: fuse the k and v projections (one launch, N = 2048) in the model block; HIP graphs for the decode step.
3. **lm_head GEMV** at 89.6%: every variant gives 562 GB/s, so it is not the loop shape; page-table reach on the 1.2 GB matrix is a suspect (unverified), try a 2 MB-aligned allocation.
4. **Decode attention at 4k+**: 33 us per layer against a 27 us byte floor (16.8 MB of K+V per layer at 627 GB/s); the split-count policy is shared with the CUDA backend and has not been tuned for this card.
5. TP=2 over both cards, quantised weights (MXFP4 x FP8), GDN and MoE: radiance ports (`docs/research/radiance-port-plan.md`).

### 9.1 Kernels

*Tree: 4963b43 + uncommitted worktree (dirty), later committed as a7da13b; exact tree not recorded.*

| Op (launchers) | Implementation | Notes |
|---|---|---|
| `matmul_fp8_gemv` (M<=4) | warp owns 2 rows (N>=6144) or 1; loads in flight before x staging; W8A8 path decodes e4m3 to fp16 with 3 ALU ops/pair and `v_dot2_f32_f16` | Deterministic. W8A8 and W8A16 selected on the device from `input_scale`. |
| `matmul_fp8_mma` | bf16 WMMA, e4m3 dequantised to bf16 tiles in LDS (exact), tile by M | Deterministic. The gfx12 fp8 x fp8 WMMA was NOT used (see gaps). |
| `matmul_nvfp4_gemv` (M<=8) | warp per row, e2m1 16-entry LDS table, e4m3 block scale by integer arithmetic, f32 global scale last | Deterministic; f32 output for lm_head. |
| `matmul_nvfp4_mma` | same tile GEMM as fp8 with the NVFP4 policy | |
| `moe_topk` | ported (warp per token, ties lowest index, bf16-rounded softmax weights) | The CUDA kernel returns early for out-of-range warps and synchronises with `__syncwarp()` (`kernels/cuda/moe.cu:92`), which is correct. The HIP port uses a block barrier (`__syncthreads`) and so has no early return (a `live` flag instead): a deliberate difference, not a fix of a CUDA bug (the first version of this note said it was). |
| `moe_experts` | T*K<=16: ungrouped gate/up kernel plus a down kernel fused with the weighted reduction (decode = topk + 2 launches); T>=16: counting-sort grouping, then grouped bf16-WMMA projections with the e2m1 x e4m3 values expanded straight into A fragments in registers (no weight tile in LDS); T<16 multi-token: GEMV-style grouped kernels | Never dequantises more than the touched experts. The ungrouped and grouped GEMV-style kernels use the same lane and accumulation order; the WMMA path accumulates in a different order, so it matches the others only within the admission tolerance. |
| `moe_combine`, `gate_split`, `sigmoid_mul` | ported | |
| `gdn_conv`, `gdn_delta_rule` | ported; the delta rule keeps state rows in registers: dk 32/64 one thread per row, dk 128 two lanes per row (xor-shuffle reductions) because 128 f32 per lane spilled on gfx12 | Deterministic. 9.7 us per launch at T=1, 36.8 us at T=16. |

### 9.6 Gaps and next steps

*Tree: 4963b43 + uncommitted worktree (dirty), later committed as a7da13b; exact tree not recorded.*

1. **Decode launch overhead** (about 4 of 10.4 ms): fuse rmsnorm+add+gate/router GEMV, k+v, q/k norm+rope, or capture the decode step as a HIP graph. The graph route is a core change (model.rs), not a kernel change.
2. **fp8 GEMV** at 47-75% of 627 GB/s DRAM-cold (the first version said 56-71%, cache-hot; section 10.3) on the 8192/4096-row shapes; 2-row-per-warp helped, a split-K variant for N<=4096 would raise occupancy.
3. **Prefill**: fp8/nvfp4 `mma` dequantise through LDS; the NVFP4 lm_head reaches about 60 TFLOPS but the fp8 qkv case only 7.5 TFLOPS at M=256 (each weight tile is re-dequantised by every token block, and N=8192 gives few blocks); the gfx12 `v_wmma_f32_16x16x16_fp8_fp8` would take the e4m3 weights and e4m3-quantised activations directly (W8A8 is already exact in fp8) and skip the dequant. Not tried this round; admission would need the saturating-activation case checked against the reference.
4. **GDN prefill** is sequential over tokens (400 us per layer call at T=256); a chunked form (as in radiance `r4d_gdn_recurrent_update` / fla chunk kernels) would cut this 10% share.
5. **moe_experts** T=1 reaches 51% of bandwidth DRAM-cold (the first version said 37%; 8 expert rows x 2 projections, small launches); T>=64 reaches 54-59% (section 10.3; the old figures were hot and used a different routing / byte count). Tile table (64 features x 32 pairs, 8 waves) was tuned on this card only at T=64 and T=256.
6. No radiance kernel was ported this round (its paged interleaved layout differs from our contiguous K/V; the GDN update kernel was not adopted because our own port already passes admission).
