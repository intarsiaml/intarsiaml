# M2: EXL3 as a first-class quant format (2026-10-21)

Lane M2 of `docs/plans/2026-10-21-quota-burn-plan.md` (requirement 1, modular quant support; ABI id `IK_QUANT_EXL3 = 5`).
Branch `m2/exl3` from origin/main `92f9043f`. Shared crates change, so it is not merged here (see Files).

## Headline

EXL3 (ExLlamaV3's trellis / QTIP-style format) now loads and runs through the same plugin path as NVFP4 / FP8:
`QuantFormat` `exl3`, `Op::MatmulExl3`, a CPU reference, the `quant_method = "exl3"` scheme, the recipe tool, and
CUDA kernels admitted on spark1: a decode GEMV and, from 33 rows, a prefill GEMM.

- **CPU reference vs exllamav3's own reconstruction on real tensors: W_q bitwise (0 of 14 x 32768 values differ).** The
  14 cases are 4 slices of two published GLM-5.3-Flash EXL3 checkpoints (4-bit MCG) and 10 tensors quantised by
  exllamav3 1.6.0 itself on spark1, covering every width and codebook (1 MUL1, 2 3INST, 3 MCG, 4 3INST, 5 MCG, 6 MUL1,
  8 3INST, 1.5 / 2.5 / 3.5 MUL1).
- Full weight and forward against exllamav3: W rel_l2 4.1e-4 (exllamav3's `get_weight_tensor` rounds to fp16 after each
  step), y rel_l2 4.2e-4 to 5.3e-4 and max_abs at most 8.8e-4 for |y| up to 1.4, which is one fp16 ulp of exllamav3's
  fp16 GEMV.
- Against TensorFold's independent numpy decoder at every width and codebook (27 cases): W_q bitwise, W and y rel_l2
  below 1e-7.
- A Qwen3-shaped model with EXL3 attention and an EXL3 lm_head, loaded through `recipes/qwen3.toml`, matches the same
  model with the dequantised weights to rel_l2 7.3e-7 on the CPU backend. With every linear EXL3, FFN included, the
  rel_l2 is 7.1e-7; that variant needs M1's quantised dense FFN, so the test runs on `m2/exl3-on-m1`.
- CUDA decode GEMV on GB10: 198-230 GB/s on the large Qwen3-8B shapes, 3.3-3.8x faster than the bf16 GEMV.
- The prefill GEMM is bitwise equal to the GEMV and gives prefill of 3582 tok/s at 1024 tokens; the GEMV alone gave
  1195.
- Every admission case passes.
- **Real model end to end** (turboderp/Qwen3-8B-exl3 @ 4.0bpw on spark1, CUDA):
  - The output is coherent, and decode runs at 47 tok/s against 15.6 for bf16 Qwen3-8B.
  - **Engine error vs exllamav3 on the same weights: KL 4.4e-4** (top-1 98.6%).
  - The format's own loss vs bf16 is KL 2.28e-2 in exllamav3 and 2.32e-2 in intarsia.
  - **Quick tier on the PR branch: 7/7 PASS.** On current main the KL gate scores only assistant-side rows (PR #40):
    decode KL 2.59e-2 on those rows.
  - Before PR #40 the same run failed acc-short: decode KL 3.26e-2 over all 128 rows, against a 3.0e-2 limit.
    exllamav3 itself scores 3.51e-2 on those rows, so that was 4-bit quantisation loss, not an engine bug. No gate
    was changed by M2.

## Format (what the decoder implements)

`{p}.trellis` i16 `[K/16, N/16, 16*bits]`, `{p}.suh` f16 `[K]`, `{p}.svh` f16 `[N]` (or packed signs `su` / `sv`),
optional `{p}.mcg` / `{p}.mul1` i32 marker (none = 3INST). `W [K,N] = diag(suh) H W_q H diag(svh)` with 128-point
Sylvester Hadamards / sqrt(128). Each 16x16 tile is a ring of `4*k2` 32-bit words (k2 = 2 x bits); value p is the
16-bit window ending at bit E(p), mapped through a multiply-based codebook to fp16 (one rounding), placed at the
mma.m16n8k16 B-fragment position. Engine layout: `QTensor [n, k]` with parts `[trellis i16, suh f16, svh f16,
codebook i32 [1]]`. The codebook is device data: the kernel reads it once and branches uniformly, so launches never
synchronise. `k2` comes from the trellis shape and is a template parameter.

### CUDA

`matmul_exl3_gemv` (`kernels/cuda/exl3.cu`, ported from TensorFold's MIT `linear.cu` / `decode.cuh`;
`crates/intarsia-backend-cuda/src/exl3.rs`). spark1 GB10 (sm_121), non-exclusive fleetq slots #2955 / #2962 / #2964 /
#2966 with spark1-vllm up. Raw logs: `raw/cuda-*.log`.

- **Design.** `rot_in` computes `xh = H (x * suh)`, rounded to fp16, into scratch. Then `linear<K2, WK=8>` runs one
  block per 128 output columns with 8 warps splitting K; partial sums are added in warp order, so results are
  deterministic. Each warp decodes 16x16 tiles straight into mma.m16n8k16 B fragments, followed by the output
  Hadamard and `svh`.
- **Codebook dispatch.** The codebook is read from the device at kernel entry and dispatched with one uniform branch;
  half-integer widths compile MUL1 only. An unusable codebook value writes NaN, since the host cannot see it.
- **Rows.** Any M runs as 128-row slices on one stream, with no sync and no allocation. Split-K is off: TensorFold's
  split-K counters need zeroed memory.
- **Admission** (`intarsia kernels test --backend cuda --op matmul_exl3`): quick 81/81, full 242/242 ADMITTED. The
  full sweep covers every width x codebook; M = 1, 3, 5, 8, 17, 40, 256, 300; the Qwen3-8B projection shapes; and
  the 151936-wide head. Worst rel_l2 is 1.68e-3 for bf16 out and 2.4e-4 for f32 out.
- **Tolerance.** EXL3 has its own measured tolerances: bf16 `Tol::new(1.5e-2, 3.5e-3)`, f32 `Tol::new(1e-3, 5e-4)`,
  about 2x the worst measured. The shared quant TOL (rel_l2 1e-3 / 2e-4) is unchanged. The gap is the fp16 rounding
  of `xh` before the tensor-core multiply, which exllamav3 does too. Against a reference that also rounds `xh` to
  fp16, f32 outputs agree to 1e-7..3e-5.
- **Other checks.** `cargo test --test exl3` passes (5 tests, 323 cases): a 300-row call agrees with partial calls
  across slice edges, and f16 in/out and the NaN codebook case are covered. `--test quantmoe` and `--test admission`
  pass. `compute-sanitizer racecheck` on one test reports 0 hazards.

| N x K | EXL3 4-bit us | GB/s | bf16 GEMV us | NVFP4 GEMV us | EXL3 speed-up vs bf16 |
|---|---|---|---|---|---|
| 4096 x 4096 | 42.3 | 198 | 139.2 | 38.2 | 3.3x |
| 1024 x 4096 | 36.1 | 58 | 36.7 | 10.0 | 1.0x |
| 12288 x 4096 | 109.3 | 230 | 418.8 | 116.6 | 3.8x |
| 4096 x 12288 | 116.2 | 217 | 419.7 | 122.3 | 3.6x |

At 4096 x 4096: 2 bit 26.6 us, 2.5 MUL1 35.9, 3 bit 39.0, 3.5 MUL1 40.9, 5 bit 49.4, 8 bit 73.4; 4-bit MCG 42.4
and MUL1 41.5 (the three codebooks cost the same). Time is flat up to M=16 (43.9 us); it is 70 us at M=32 and 448 us

- **Weak spot, small N.** 1024 x 4096 (the k/v projections) reaches only 58 GB/s: 8 blocks on 48 SMs. The fix is
  split-K with counters zeroed by a `cudaMemsetAsync` in the launcher.

#### Prefill GEMM: `matmul_exl3_gemm` (M >= 33)

- **Layout.** Each block owns 128 output columns and 64 or 128 rows. Each of its 8 warps decodes one 16-column
  weight tile once per k step and runs all the block's row groups against it (`ldmatrix` + mma). The rotated input
  and the trellis words are staged with `cp.async` in a 3-stage ring. The decode of the next k tile overlaps the
  current mma; `clock64` phase timing showed the first version serialising decode, issue and mma, which this fixed.
- **Bitwise equal to the GEMV.** It keeps the same per-128-K mma chains, added in the same order, then the same
  epilogue. So which kernel runs never changes a row's bits; tested on 68 cases, plus 600 rows across the 512-row
  slice edge.
- **Rows and crossover.** Rows run in slices of 512. The crossover at 33 rows was measured: the GEMV is 2x faster at
  M=16, and the GEMM takes 0.51-0.57x of the GEMV's time at M=48.
- **Admission.** Quick sweep (now with M=40): GEMV 108/108, GEMM 27/27. Full sweep: GEMV 242/242, GEMM 81/81. Worst
  GEMM bf16 rel_l2 is 9.5e-4, within the same EXL3 tolerances. racecheck and memcheck are clean on both block sizes.
- **Speed.** 4-bit, M=1024: 587 / 195 / 1598 / 1731 us on the four Qwen3-8B shapes. That is 58-65 TFLOP/s against
  91-103 for the bf16 GEMM. Against the GEMV it is 2.2-8.7x faster at M >= 128. Full table:
  `raw/cuda-gemm-prefill.log`. spark1 was shared, so these are the fastest of 15 replays.

## Effort estimate: HIP and Metal ports

Both ports reuse everything above the kernel: the format plugin, `Op::MatmulExl3`, the scheme, the recipe hook, the
cpu reference and the admission sweep (`quant::exl3::sweep`, every width x codebook) are backend-independent. The
work is the kernel, its `KernelImpl` entry and the measured tolerance.

| Port | Decode GEMV | Prefill GEMM | Why |
|---|---|---|---|
| HIP (R9700, RDNA4, wave32) | 6-10 h | +4-6 h | The decode itself is portable: exllamav3 already builds `codebook.cuh` for ROCm (`USE_ROCM`, a C form of the lop3). The CUDA kernel's value placement follows the mma.m16n8k16 B fragment, which RDNA4 WMMA does not share. A scalar-FMA GEMV that decodes into registers and reduces over K is enough for decode, since it is bandwidth-bound. The 128-point Hadamard maps to wave32 shuffles as on CUDA. Prefill: dequantise tiles to bf16 in LDS and reuse `kernels/hip/ik_dq_gemm.h`. |
| Metal (M5 Max) | 8-12 h | +4-6 h | On main Metal has no quantised-weight kernels (`crates/intarsia-backend-metal/src/kernels.rs`: no fp8/nvfp4/MoE). M1's MXFP4 Metal GEMV (`92794701`, on its branch) brings the first quant host plumbing; with it merged, EXL3 adds binding 5 inputs including the device i32 codebook, plus scratch for the rotated input. Without M1, add 2-3 h. The simdgroup is 32 wide, so the GEMV structure ports directly. Unknown: the cost of the 32-bit multiply-based codebook on Apple GPUs. Prefill: dequantise to bf16 and use `gemm_bf16.metal`. |

The estimates assume the CUDA kernel as the template and one person-equivalent agent lane each. They include the
`kernels test` admission run and a microbench, but not an end-to-end qualify (+1-2 h per backend once a model is on the box).

## Decisions for the user

1. **Merge**: M1 is on main (PR #42); merge `m2/exl3-pr`, which already resolves the M1 conflicts.
2. **Third-party quant formats against a bf16 golden.** With PR #40's scored-row KL, EXL3 4.0 bpw passes, with a
   margin of 2.59e-2 against 3.0e-2. On all rows it would fail (3.26e-2), and so would exllamav3 itself (3.51e-2).
   - The margin is thin and comes from the format, not the engine.
   - Option: add an optional "format reference" golden to qualify: `tools/golden_exl3.py`, the format's own
     implementation on the same ids. With it, qualify would gate engine error directly; here that is KL 4.4e-4, and
     a gate of about 2e-3 would fit.
   - Recommendation: do this before qualifying lower-bpw EXL3 models (2-3 bpw). Their format loss will exceed any
     bf16-relative gate while the engine is still correct.
3. **Next CUDA work** (not done):
   - split-K for small N, with zeroed counters: k/v projections reach 58 GB/s in decode; about 2 h;
   - GEMM to bf16 speed: 58-65 TFLOP/s against 91-103 at M=1024; larger tiles; about 3-4 h.

Notes:
- `IK_QUANT_EXL3 = 5` already existed in the ABI. No launcher reads `ik_quant`: the parts go in as separate tensors,
  as for NVFP4.
- The plan-time admission label leaves out the codebook, which is device data, so plan-time grades one codebook per
  shape and width. The sweep grades all three.
- Not covered: tensor parallelism for EXL3 (refused at load), EXL3 routed experts / MoE, EXL3 biases (refused).
- `--act-dtype` is not a CLI flag (`common.rs` sets `None`), hence the conversion tool. A flag would make it
  unnecessary.
