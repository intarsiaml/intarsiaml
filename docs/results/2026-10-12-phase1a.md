# Phase 1a results, 2026-10-13

Gate (ARCHITECTURE.md 13, Phase 1a): the hybrid GatedDeltaNet + sparse-MoE model Qwen3.6-35B-A3B (NVFP4 routed
experts, FP8 projections) loads from its checkpoint, answers correctly, tracks the vLLM server on spark1 on
`prompt_logprobs`, and is served through the same APIs and UI as the dense models. Qwen3-8B must not regress.

Verdict: the model loads and answers (first run, no debugging needed), passes the 4-bit accuracy gate against vLLM
(top-1 98.4% prefill / 98.8% decode, mean KL 6.5e-3 / 1.0e-2), and decodes at 63-65 tok/s against vLLM's 77-78 tok/s
(80-85%). Prefill is the gap: 700-890 tok/s against 4800-6100 tok/s (14-18% at 1k-4k tokens), 63% of it in one
kernel (`moe_experts`). Qwen3-8B has no regression except one gate margin (section 2.2).

Machines. Mac: Apple M5 Max (cargo build and test only). spark1: DGX Spark GB10 (sm_121), CUDA 13, cargo 1.90.0
(MSRV). All GPU work ran in one fleetq lease (#1374, 40 GB, `--uses guidance`, "intarsiaml phase1a integration"),
released at the end; the servers were stopped before release. Raw bench JSON next to this file

## 0. What integration changed

The pieces from the six workstreams compiled together; the one thing missing was the join in the decoder
(`crates/intarsia-core/src/model.rs`). Everything below is that join, nothing else:

| Change | Why |
|---|---|
| `Block::Moe` arm in `Model::load` / `run_chunk`, reading `[layer.moe]` (`kind`, `prefix`) from the recipe and the MoE sizes from `ModelDims.moe` | the quantmoe agent built `MoeWeights::load/forward` but nothing called them |
| `ModelDims.moe: Option<MoeConfig>`, filled by `from_hf_config` when the config has MoE keys (a MoE config missing a key is now an error, test updated) | `Model::load` gets dims, not the raw config |
| One shared `MoeScratch` in the workspace (not one per layer), counted in the memory plan; `ExecRunner` implements `OpRunner` over `Model::exec`, so MoE ops get profiling, plan recording and kernel scratch like every other op | the plan resolver sees MoE shapes; admission runs on them |
| `lm_head` is a `QTensor`; head matmuls go through `proj` (`Op::Logits` for bf16, `Op::MatmulNvfp4` with f32 output for the quantised head) | the checkpoint's `lm_head` is NVFP4 (`weight`, `weight_scale`, `weight_scale_2`, `input_scale`); the recipe's `tied_to` is only a fallback |
| `LoadOptions.fp8_act` and `--fp8-act static|none` on every model command (default: the recipe's `[defaults] fp8_act`, i.e. `static` = W8A8) | lets the FP8 W8A8 vs W8A16 question be measured (section 3.2) |

## 2. Qwen3-8B regression (bf16, CUDA)

### 2.1 Kernels

`$B kernels test --backend cuda`: 30 kernels, 471 cases, all ADMITTED, 15.1 s. Worst: `attn_prefill_bf16_flash`
rel_l2 2.4e-3, `matmul_bf16` 1.8e-4, `matmul_fp8_mma` 1.9e-4, `moe_experts_bf16` 1.4e-4.

### 2.2 Golden logits (HF bf16 reference, strict top-1)

`$B accuracy --backend cuda --model $S1_8B --mem-budget 36 --max-seq 4096 --golden ~/intarsiaml-golden/<g>.safetensors --mode both`

| Golden | Mode | Positions | Top-1 | Mean KL | Max KL | Gate (top-1 >= 99.5, KL <= 1e-3) |
|---|---|---:|---:|---:|---:|---|
| qwen3-8b (8 prompts) | prefill | 434 | 100.00% | 6.38e-4 | 1.97e-2 | PASS |
| qwen3-8b (8 prompts) | decode, teacher-forced | 128 | 100.00% | 1.115e-3 | 1.51e-2 | FAIL on KL by 1.2e-4 |
| qwen3-8b-long (10 prompts, 2 cross a chunk) | prefill | 1434 | 99.58% | 8.57e-4 | 1.11e-1 | PASS |
| qwen3-8b-long | decode, teacher-forced | 160 | 100.00% | 9.81e-4 | 1.51e-2 | PASS |

Quick gate (`--quick`): PASS. The short-golden decode result is a FAIL against the 1e-3 gate (128 positions, mean KL
1.115e-3); the larger 160-position set passes at 9.8e-4. This is reported as a failure, not a margin. Cause not
determined: no baseline decode run exists for the short golden (Phase 0 had no decode mode), and the attribution to
HF bf16 reference noise in the cudaperf and fixcore reports comes from the long golden, so it is unproven here.
What is shown: integration did not change the 8B path by construction. `QTensor::call` for a bf16 head with f32
output emits `Op::Logits` with inputs `[x, w]` and default attrs, as the old direct call did, and the 8B plan
still selects `logits_bf16_gemv` (decode) and `matmul_bf16_gemv`. Not loosened.

### 3.2 Accuracy against vLLM `prompt_logprobs`

`$B accuracy --backend cuda --model $S1_35B --mem-budget 36 --max-seq 4096 --golden ~/intarsiaml-golden/qwen36-35b-a3b-nvfp4-vllm-top20.safetensors --mode both [--fp8-act none]`

Golden: 10 prompts, 1441 prefill positions (2 prompts cross a 256-token chunk boundary), top-20 log-probs from the
live vLLM server; KL is over the reference top-20 support, both sides renormalised (so it is not comparable to the
8B full-vocabulary KL). Gate class 4-bit: mean KL <= 3e-2, top-1 reported, not gated.

| FP8 activations | Mode | Positions | Top-1 | Mean KL | Max KL | Top-5 | Gate |
|---|---|---:|---:|---:|---:|---:|---|
| `static` W8A8 (recipe default) | prefill | 1441 | 98.40% | 6.50e-3 | 8.18e-1 | 91.49% | PASS |
| `static` W8A8 | decode, teacher-forced | 160 | 98.75% | 1.04e-2 | 5.67e-1 | 93.62% | PASS |
| `none` W8A16 | prefill | 1441 | 98.33% | 5.95e-3 | 6.05e-1 | 92.01% | PASS |
| `none` W8A16 | decode, teacher-forced | 160 | 98.12% | 6.82e-3 | 1.21e-1 | 93.00% | PASS |

Zero non-finite rows. Worst prompts: `chat_system` (prefill top-1 90.6%, KL 2.4e-2), `chat_reasoning` (93.3%),
`long_prose_700` decode (KL 3.6e-2 W8A8). Greedy-match before first divergence: 27% (prefill positions), 89% of the
16 decode positions per prompt. W8A8 and W8A16 are indistinguishable on top-1; W8A16 has lower mean KL (-8% prefill,
-35% decode) and a much lower max KL in decode, on a small sample. The recipe default stays `static` (the declared
checkpoint scheme and what vLLM runs) until a larger golden decides; `--fp8-act none` is the switch.
This is not an exactness claim: two NVFP4 implementations of the same checkpoint differ in accumulation order and
where bf16 rounding lands; 98.4% top-1 and KL 6.5e-3 say they are the same model, not that they are bit-close.

### 3.3 Speed, ours against vLLM

Same client (`$B bench speed ... --sizes 128,1024,4096 --gen 128 --reps 3 --thinking off`, concurrency 1, median of 3,
1 warmup), both run on spark1 one after the other (our server idle while vLLM was measured and vice versa). vLLM:
`http://100.120.88.104:8000/v1`, model `guidance`, inside the lease's `--uses guidance`. vLLM in-flight count
(`vllm:num_requests_running`): 0 before, 0 after, sampled each second during the run: 1 only while the bench's own
request ran (16 samples at 1, 8 at 0, waiting always 0). So vLLM was not shared with anyone for these numbers.
Our server: `--max-seq 8192 --mem-budget 38`, prefill chunk 256 (default) and 1024.

| Prompt tokens | | TTFT s | Prefill tok/s | Decode tok/s |
|---:|---|---:|---:|---:|
| 128 | vLLM | 0.121 | 1094 | 76.5 |
| 128 | ours, chunk 256 | 0.183 | 695 | 65.0 |
| 128 | ours, chunk 1024 | 0.184 | 705 | 65.0 |
| 1024 | vLLM | 0.203 | 4824 | 76.7 |
| 1024 | ours, chunk 256 | 1.107 | 873 | 64.7 |
| 1024 | ours, chunk 1024 | 1.049 | 946 | 64.8 |
| 4096 | vLLM | 0.669 | 6135 | 78.2 |
| 4096 | ours, chunk 256 | 4.581 | 887 | 62.7 |
| 4096 | ours, chunk 1024 | 4.203 | 952 | 62.9 |

Decode is 80-85% of vLLM. The task's "86-90 tok/s" bar was not reproduced: vLLM measured 76-78 here under this
client (forced 128 tokens, thinking off). vLLM's prefill TTFT at 1k-4k tokens is 5-7x faster than ours.

Where our time goes (`generate --profile-every 1`, which synchronises per op and so lowers decode to 56 tok/s):
- Prefill, 1610-token prompt: `moe_experts` 1447 of 2289 ms (63%) at chunk 256, 1370 of 1915 ms at chunk 1024; then
  bf16 `matmul` (router, gates) 398 ms, `matmul_fp8` 235 ms, `gdn_delta_rule` 64 ms. Per call `moe_experts` costs
  about 4 ms at 256 rows and 8.5 ms at 1024: the kernel is a CUDA-core dequantising grouped matmul, not a tensor-core
  one, and re-reads the expert weights each chunk.
- Decode: 844 kernel launches per token (sum of `calls_per_decode_step` in `/v1/intarsia/plan`: 140 bf16 gemv for
  routers/gates/in_a/in_b, 130 FP8 gemv, 121 NVFP4 gemv, 80 rmsnorm_add, 70 silu_glu, 40 each topk/experts/combine,
  ...). Bytes read per token, counted from the checkpoint layout (not measured): FP8 GDN projections 30 x 33.5 MB =
  1.0 GB, gated-attention FP8 10 x 27 MB = 0.27 GB, active NVFP4 experts 8 x 1.67 MB x 40 = 0.53 GB, shared experts
  0.07 GB, NVFP4 `lm_head` 0.29 GB, routers 0.04 GB: about 2.2 GB, a floor near 10 ms (about 100 tok/s) at
  221 GB/s. Against that floor vLLM (13 ms/token) is at about 78% and we (15.5 ms) at about 64%. 844 launches in
  15.5 ms is 18 us each, so launch and latency overhead is the likely limit; CUDA graphs and a fused MoE block are
  the candidates, and neither exists yet (hypothesis, not tested).

## 4. Honest gaps

- Prefill is 5-7x slower than vLLM at 1k-4k tokens: the `moe_experts` kernel (63% of prefill) needs a tensor-core
  grouped GEMM (fp4 MMA on sm_121 or dequantise-once + cuBLAS), and FP8/NVFP4 `*_mma` kernels re-dequantise per
  M-tile. Decode is at 80-85% of vLLM, about 64% of the byte-count floor, with 844 launches per token (no CUDA graph, about 9 launches per MoE layer unfused).
- Accuracy is gated only at the 4-bit class (KL <= 3e-2); top-1 is not gated for quantised models by design. The
  golden is 10 prompts; W8A8 vs W8A16 differences are inside its noise. No fp32/bf16 HF reference for the 35B exists
  (the checkpoint is NVFP4; the reference is vLLM running the same checkpoint).
- The MoE block wiring has no Mac-side model-level test (the block itself is tested against HF in
  `intarsia-backend-cpu/tests/quant_hf.rs`; the join is verified by the real-checkpoint accuracy run only). A tiny
  random MoE model against HF on cpu is the missing test.
- FAIL: 8B decode on the short golden (128 positions) is above the 1e-3 KL gate (1.115e-3); cause undetermined (section 2.2).
- Bench client bug: when a request fails with a context-length HTTP 400, `intarsia bench speed` prints "server rejected parameters, dropped: ignore_eos, min_tokens, stream_options" and counts it as a parameter rejection; the warning appeared in the 8B run even though forced length worked at the other sizes. Not fixed (bench is not in the integration area).
- The MTP head and vision tower are ignored.
- Only one GPU run per configuration; 3 reps, medians, no confidence intervals. vLLM's number depends on its own
  config (MTP/speculation may be on in other runs; the 86-90 tok/s bar was not seen).
- The 35B UI/architecture map has not been looked at in a browser with the hybrid plan (the plan JSON is verified, the
  rendering of 40 mixed layers is not); `serve` was run with `--no-supervisor` for the benchmarks.
- Cold load is 66 s (weights mmap'd from a 95%-full disk); the second load 36 s.
