**Decisions after review (coordinator, end of round):**

* **f8 default stands.** Provenance: the user said "f8 on" on 2026-10-18 at 23:35 EDT (relayed by the coordinator); commit
  `8624fec1` implements it. `INTARSIA_HIP_FP8_F8=0` remains the kill switch.
* **`moe_experts_bf16_v3` is opt-in (`INTARSIA_HIP_MOE_V3=1`, default off).** The default decode path is v2, i.e. the round-4
  decode path already measured (the "base" decode column of every table below). Reason: the mutant `v3-nofence` (acquire fence
  before the h reads dropped) survives, so the mutation bar is not met, and a missed acquire in a cross-block spin-wait risks a
  hang or a stale read for only +0.8 % decode. v3 stays opt-in until a test kills `v3-nofence`. Suggested test (not built):
  a stress run where the gate_up roles delay their h stores (skew per role, not only the last one), the h scratch is
  pre-filled with a sentinel (NaN / 0x7fc0 bf16) before every launch, and the down roles' inputs are checked for the sentinel
  (any NaN in the output = a read before the store became visible); run it over many launches and several CU-occupancy
  settings so a down role's CU has the h lines cached from a previous launch.
* **flash v2 is the default** (bitwise v1, the prefill gain below).

The W4 35B A/B was taken with v3 on in the branch arm. Prefill there is v3-independent (v3 serves only the decode path, T * K
<= 16, and hands every prefill chunk to v2's grouped path unchanged), so the prefill deltas are the default build's. The branch
decode column is the opt-in v3 number; the default decode is the base column. The 8B is dense (no MoE), so its numbers are the
default build's.

## What I built

1. **f8 default** (`8624fec1`, `crates/intarsia-backend-hip/src/quantmoe.rs`, `docs/backends/hip.md`): `matmul_fp8_mma_f8` is
   the default fp8 prefill GEMM; `INTARSIA_HIP_FP8_F8=0` is the kill switch (`fp8_f8_from`: unset or any value but "0" = on).
   Registry pin `fp8_selection_is_pinned` (f8 above v2 by default, below under the kill switch) and `fp8_f8_is_the_default`.
   Verified on hardware: acc35 base KL21 7.417e-3 (f8), `acc35f8off` 7.071e-3 (v2) - the round-4 numbers exactly (W2).
2. **`moe_experts_bf16_v3`, OPT-IN** (`INTARSIA_HIP_MOE_V3=1`; `moe_v3_enabled` / `moe_v3_from` in `quantmoe.rs`, priority
   20 when on, -10 (below v1 and v2) when off; pins `moe_v3_is_opt_in`, `moe_experts_selection_is_pinned`; Mac mutants
   `v3-default`, `v3-prio` killed) (`kernels/hip/moe.hip`, `moe_experts_p1_v3_kernel`): the v2 decode pair (gate_up, then down +
   per-token reduce) as one grid of NG + ND blocks. Roles come from an atomic ticket (not blockIdx), so a down role exists
   only once every gate_up role is held by a running block and the wait cannot deadlock whatever the dispatch order. Down
   roles issue their weight and scale loads (all of them at I = 512), then thread 0 spins on a per-stream counter
   (acquire, agent scope, `s_sleep`); gate_up roles fence and add 1 after their h store. The last down role resets the three
   counters. Counters: a module-scope `__device__` array, one 64-byte slot per (device, stream), 16 slots (1 KB); a 17th stream
   falls back to the two v2 launches. Same expressions in the same order as v2: bitwise. Prefill shapes run v2's grouped
   path unchanged. Same `when`, same scratch as v2.
3. **`attn_prefill_bf16_flash_v2`** (`kernels/hip/attention_flash.hip`, `flash_hpb_kernel`): `flash_kernel` with HPB query
   heads of one kv head per block (`INTARSIA_HIP_FLASH_HPB` 1 / 2 / 4, default 2, capped to divide the GQA group): K / V tiles
   staged once per HPB heads, HPB times the waves for the same LDS. Each wave runs v1's instructions for its 16 rows (diffed
   kernel bodies: only the head / row / stride indexing differ), so bitwise. Priority 20 over v1.
4. Tests: `tests/moe_v3.rs` (bitwise v2 on 11 shapes plus duplicate / invalid ids; 200 back-to-back launches of two shapes on
   one scratch with changing activations; 20 graph replays; `v3_waits_for_every_gate_up_role` with the
   `INTARSIA_HIP_MOE_V3_SKEW` test seam that starts the last gate_up role ~0.1 ms late), `tests/flash_v2.rs` (51 shapes incl.
   two 4096-row 35B chunks, bitwise v1, run at HPB 1, 2, 4), flash v2 added to both sweeps of `tests/attention.rs`
   (cpu reference, causal-edge poisoning, exact chunk edges). Registry pins `moe_experts_selection_is_pinned`,
   `round5_attention_selection_is_pinned`.
5. Scripts: `remote.sh` stages `pf8o`, `pf8x`, `profenv`, `pfprofenv`, `r5test`, `acc35f8off`, `plan8`, `plan35f`,
   `mutbuild5` / `mutrun5`; `mutrun` now has a per-mutant timeout; `ids4k` copies the base ids next to this tree's (W3
   compared against a stale default path and printed DIFFER; the files themselves were identical, checked with `cmp`).

### Core-op proposals (not implemented: they touch shared code)

Checked: HIP registers a kernel for every core op except `Op::Sample` (`kernels.rs` `UNIMPLEMENTED`), and every fused op
the model tries first resolves to a HIP fused kernel at the 35B decode shapes, by matching each `run_fused` / `try_fused`
call in `crates/intarsia-core/src/{model.rs,model/gdn_block.rs,quant/moe.rs}` to the decode trace
(`raw/prof/decode128-r5.txt`): `RmsNormAddMatmulPair` -> `rmsnorm_add_pair_kernel` 69 / step (29 GDN in_b/in_a + 40 MoE
router / shared-gate logit), `MatmulFp8Pair` -> `fp8_gemv_pair_kernel` 40, `GatedRmsnormMatmulFp8` -> `fp8_gemv_gated_kernel`
30, `MatmulNvfp4Glu` -> `nvfp4_glu_kernel` 40, `QkNormRopeKv` -> `qk_norm_rope_kv_kernel` 10. No fused op falls back to its
unfused ops, so there is no CUDA / Metal fused op left to port. The attention layers' input norm (`norm_in`, model.rs
~1303) is a plain RmsNorm / RmsNormAdd with no fused op to try; it is proposal P5 below. Every remaining decode launch is
one core op = one launch. A launch boundary costs ~3 us inside the replay
(p50 3.0 us, `raw/prof/decode128-r5.txt`), so each launch removed is worth ~3 us of a 7.62 ms step. Estimates below are that
gap only (kernel time assumed unchanged):

| proposal | ops fused | launches / step | est. saving |
|---|---|---|---|
| P1 `MoeRouted` | MoeTopk into MoeExperts (each v3 role recomputes the 256-logit top-k, or role 0 publishes it) | -40 | ~120 us (1.6 %) |
| P2 `SharedExpert` | MatmulNvfp4Glu + shared-down MatmulNvfp4 + MoeCombine (one-launch, v3-style ticket wait) | -80 | ~240 us (3.1 %) |
| P2' `MoeBlock` | P1 + P2 in the v3 grid (shared expert as a 9th, sigmoid-gated expert) | -160 | ~480 us (6 %) |
| P3 `GdnConvDelta` | GdnConv into GdnDeltaRule (conv output only feeds the delta rows) | -30 | ~90 us (1.2 %) |
| P4 attention gating | GateSplit into QkNormRopeKv; SigmoidMul into the o_proj GEMV's input load | -20 | ~60 us (0.8 %) |
| P5 attention input norm | RmsNormAdd into the attention qkv MatmulFp8Pair (the fp8 twin of RmsNormAddMatmulPair) | -10 | ~30 us (0.4 %) |

All of P2', P3, P4, P5: about -220 launches, ~0.66 ms per step (~8.5 % decode), bitwise if each fused kernel keeps the unfused
expressions (as v3 does).

## What I tried and dropped

* **128-pair MoE prefill tile** (`moe_wmma_kernel<.., 128>`, LDS of the up accumulators aliased onto the activation tiles):
  bitwise (moe_pairs test, 32 / 64 / 128 / auto) but 5-7x slower: bench_prefill_shapes T=1024 64 pairs 1802 us vs 128 pairs
  11216 us, T=3072 4157 vs 15484 us (W3 `pfb`); 35B prefill at 4408 tokens 598 ms (64) vs 1204 ms (128). Likely register
  spills (J = 8 accumulators) or 1 block per CU; not investigated further. Reverted.
* **One-launch split-KV decode by "last block combines"** (`attn_decode_bf16_splitkv_v2`, ticket counter per (row, kv head),
  the last split block runs combine_kernel's loop): bitwise v1 (144 cases, host and device position, counter reuse, graph
  replay; 3 of 4 mutants killed), launches 488 -> 478 and idle -18 us per step, but the split kernel went 123 -> 173 us per
  step (one block now merges 8 heads serially) and decode 146.61 (v3 only, W2 `prof`, one unprofiled run) -> 146.26 (W3, same stage). Net loss: reverted. A combine
  that spreads the G heads over the block's threads might win ~30 us; not tried.
* `INTARSIA_HIP_XSTAGE=1` (existing knob) on decode: 141.78 vs 145.69 tok/s (W1). Off stays.
* Not attempted, per the brief: fp8 dense prefill GEMM (now f8 by default), one-launch split-KV in the slow form, LDS-staged
  or lane-split GDN, chunked GDN, fp8 / fp4 activations.

## Mutations

Each mutant is applied to a copy of the tree by `scripts/hip-decode/mutate.py`, built in a CPU slot (`raw/logs/mutbuild.log`),
run in a GPU window. **Which build:** the W3 kills ran on the intermediate tree (round-5 kernels plus the since-dropped 128-pair
tile and split-KV v2, before the skew test existed); `v3-early` and `v3-ticket` were rebuilt and rerun on the final tree in
W4. The flash code is unchanged since W3, the v3 kernel changed only by the skew test seam (off unless the env var is set), and every pattern in `R5MUT` plus the three f8
ones still applies exactly once to it (checked on the Mac with the mutate script); a full GPU rerun on the final build did
not fit in the downtime cap.

* f8 selection (Mac, `cargo test -p intarsia-backend-hip --lib`, `raw/logs/mut-f8-lib.log`): `f8-optin`, `f8-nokill`,
  `f8-prio`, and the v3 opt-in `v3-default`, `v3-prio` - 5 / 5 killed.
* moe v3 (`raw/logs/w3-mutrun-gpu1.log`, `w4-gpu1.log`): `v3-noreset`, `v3-nowait`, `v3-hrow`, `v3-gurow` killed (W3);
  `v3-early` (wait ends one gate_up role early) **survived in W3**, killed in W4 by the new `v3_waits_for_every_gate_up_role`;
  `v3-ticket` (ticket counter not reset) hangs the kernel: killed by the timeout (exit 137 under `timeout -s KILL 40`, W4;
  GPU 1 ran the real tests clean afterwards). `v3-nofence` (acquire fence before the h reads dropped) **survives and is not
  equivalent**: without the fence the HIP memory model allows a down role to read stale h. No test here makes the stale read
  happen; this mutant is unkilled and the mutation bar is not fully met for v3. (A test would need an h line cached on the
  down role's CU before the wait; not found.)
* flash v2: `fl2-head`, `fl2-kvh`, `fl2-row`, `fl2-stride` - 4 / 4 killed (W3).
* dropped kernels, for the record (W3): 128-pair `p128-xr`, `p128-sred` killed, `p128-sync` aborted (exit 134);
  split-KV v2 `skv-noreset`, `skv-first`, `skv-group` killed, `skv-nofence` survived (unkilled, like `v3-nofence`).

## Caveats and env vars

* 8B branch arm has 2 rounds, not 3: W5's `BURST_CAP=500` cut `pf8x:B3` to keep total downtime under 45 min. Both branch
  rounds are above all three base rounds at 4160 and 16384, and inside base's spread at 1024 / decode.
* f8 default is not bitwise round 4 (by design, decided on round 4's numbers); everything else in this round is bitwise.
* `INTARSIA_HIP_FP8_F8=0`: v2 dense prefill GEMM (kill switch). `INTARSIA_HIP_FLASH_HPB=1|2|4` (default 2; 4 measured faster
  in one profile, not A/B'd). `INTARSIA_HIP_MOE_V3=1`: opt-in one-launch MoE decode (default off). `INTARSIA_HIP_MOE_V3_SKEW=<n>`: test seam only (delays the last gate_up role), never set in
  production. Rollback: `INTARSIA_HIP_DISABLE=attn_prefill_bf16_flash_v2` (v1 stays registered; v2 MoE is the default, v3 and
  v1 stay registered). All four new knobs are in `ENV_KNOBS` (part of the backend fingerprint).
* v3's counters are per (device, stream) with 16 slots; more streams fall back to v2 (correct, slower).
* Long context (item 3): only the A/B at 16k (decode +0.6 %, from v3); no 16k decode profile was taken and no attention
  decode change survived.
