# mtp-snap: inner chunk-end snapshots with an MTP state attached; GPU batched-slot snapshots (analysis)

Lane `mtp-snap`, branch `mtp-snap` from origin/main `5e49b2bc8`. Follow-up to #382 (`docs/results/2026-11-16-hip-a4k-restore.md`), whose
review left two limits: (1) with an MTP (or DFlash) drafter state a macro prefill pass kept only its end snapshot
(`SequenceState::inner_snapshot_bufs` returned no buffers when `self.mtp.is_some() || self.dflash.is_some()`); (2) GPU
`BatchedEngine` slots keep no recurrent snapshots at all (`Model::batch_snapshots` is 0 off the cpu reference).

## Part 1: what an MTP snapshot holds and why the inner one can be exact

The MTP head trails the sequence (`state.rs` `MtpState`): position `p`'s head row reads the main model's final normed hidden row of `p` and the
token of `p + 1`, so between passes `base + kv.len + pending_rows == st.len`. A snapshot's MTP part (`MtpSnap`) is `(base, kv_len, rows, buf)`:
the head's cache length and a copy of its queued hidden rows. `SequenceState::truncate` to a snapshot length cuts the head's cache to `kv_len`
(an attention cache: a cut is just a length, the rows below stay) and copies the queued rows back (`state.rs` truncate, the `ms.base == m.base &&
ms.base + ms.kv_len + ms.rows == len` branch). Without a payload a restore falls back to cutting the cache at `len - 1` and queueing a **zero**
row (drafts only, so tokens are unchanged, but the first draft after the restore differs from the plain schedule's).

What the plain schedule leaves at a chunk end `L` (one `forward` per chunk, `mtp_after_forward(.., catch_up = true)` after each): the head has
caught up over every queued row whose next token is known, i.e. all but the newest, so `kv_len = L - 1 - base`, `pending_rows = 1`, and the
queued row is the hidden row of `L - 1` from that chunk's pass.

What a macro pass has: the head runs only after the whole pass (`mtp_after_forward(st, &hn, total, true)`, lane mpf), catching up over all its
rows in workspace-sized pieces. So mid-pass the head's state at `L` does not exist yet, but both of its parts are available **after** the pass
without recomputation:

- the queued row: `hn` holds every row of the pass, and the macro pass's hidden rows are bitwise the plain schedule's (the property #162 / lane
  l7m ships on: `real_35b_macro_prefill_is_bitwise_the_plain_schedule`, and on cpu `mtp_model_takes_the_macro_prefill_pass_and_the_head_follows`
  asserts equal logits). Row `L - 1 - pass_start` is copied out of `hn` right after the pass, before the head output and the head ingest reuse
  the workspace;
- the cache: after the pass's catch-up the head's cache covers positions up to `pass_end - 2`, so it covers `L - 2`; cutting it to
  `L - 1 - base` rows (what restore does) gives the rows the macro catch-up wrote. They equal the plain schedule's rows when the head's K / V
  ingest gives the same bits in either piece shape (macro: pieces of `ws.max_tokens` from the pass start; plain: one catch-up per chunk, the
  first `C - 1` rows, then `C` per chunk). On cpu that holds and is already asserted for the pass-end state (`mtp_model_takes_the_macro...`,
  "the macro schedule leaves the head's K / V as the chunked schedule's"); the new test asserts it at the inner cuts.

So the inner snapshot is `MtpSnap { base, kv_len: L - 1 - base, rows: 1, buf: row L - 1 }`, filed **after** the head's catch-up and only while
the head is active and in sync with its cache covering `L - 1` (a non-drafting request, a failed head pass or an out-of-sync head gets no MTP
payload, as there is nothing consistent to restore). It is valid for as long as the existing pass-end snapshot is: the head's cache rows below
`kv_len` are only rewritten after a truncate below `L`, which drops the snapshot (`drop_snapshots_above`), and `mtp_restart` clears every
snapshot's MTP part.

### Scope of the exactness claim

- **Main-model state** (recurrent slots, KV): unchanged from #382, bitwise the plain schedule on every backend where the macro pass is.
- **Head's queued row**: the macro pass's own `hn` row, so bitwise the plain schedule's wherever the macro pass is (cpu, HIP, CUDA per the
  existing macro gates).
- **Head's cache rows**: bitwise the plain schedule's on cpu (tested). On a GPU they are whatever the macro catch-up wrote; they equal the plain
  schedule's only if the head's K / V ingest is piece-shape invariant on that backend. That condition is lane mpf's (the pass-end state has
  had it since #162), not new here, and no output token depends on it: drafts only propose.

### Code (`crates/intarsia-core/src/state.rs`, `model.rs`)

- `inner_snapshot_bufs`: no longer refuses an MTP state (DFlash guard kept, unreachable).
- `inner_mtp_rows` (new): per kept inner length, a one-row device buffer with the pass's hidden row of `len - 1` (`None` without an
  active, synced head).
- `push_inner_snapshots(.., mtp_rows, ok)`: attaches the `MtpSnap` when the head is still in sync after its catch-up.
- `Model::forward_inner` macro branch: copies the rows right after the pass, runs the head output and the head catch-up, then files the
  snapshots (previously filed before the catch-up). A failed head output now returns the snapshot buffers to the free pool instead of dropping them.

Cost: per kept inner chunk end, one `hidden x act` bytes device allocation and copy (10 KiB on the 27B / 4 KiB on the 35B in bf16). This is
the same kind of allocation the pass-end snapshot already makes for its MTP rows (`SequenceState::snapshot`); #382's "no allocation beyond the
memory plan" still holds for the recurrent part. The copy uses stream 0, as `mtp_queue`'s copy of the same rows does (deliberate: it must be
ordered with the head's queue copy, not the model stream's macro snapshot copies). At most `RECURRENT_SNAPSHOTS - 1` = 3 per prefill call.

## What a GPU run should check (not run in this lane)

`intarsia accuracy --mode reuse` (the acc-4k gate) runs no drafter, so it does not exercise this path. A GPU check needs `--spec mtp`:

1. CUDA (Spark, 35B, recipe defaults: chunk 2048, macro 8192, MTP k = 2 by default) or HIP 35B with `--spec mtp`: `intarsia serve`, request A =
   a ~4.5k-token prompt, then request B sharing A's first ~2.1k tokens (more than one chunk) with a different tail. Check: B's
   `cached_tokens` = 2048 (before: 0), B's ids equal a cold run of B on a fresh server, B's MTP acceptance close to the cold run's.
2. `batch_recurrent` macro tests with `INTARSIA_BATCH_TEST_BACKEND=hip` / cuda: no regressions expected (no MTP there; the non-MTP path
   changed only in where the snapshots are filed). The `mtp.rs` tests build `CpuBackend` themselves, so running them on a GPU box tests
   the cpu path again; item 1 is the GPU check.
3. Prefill tok/s at 4k / 16k with `--spec mtp`, main vs branch: expect no change (one row copy and one small allocation per inner snapshot).
4. Do not misattribute `engine_hybrid_reuse_equals_cold` on HIP: it fails on main too (#382 window 2; lane hip-reuse).

## Part 2: snapshots for GPU batched slots (investigation only)

### Why it is 0 today

`Model::batch_snapshots` (`model/batch.rs`) cites decision **2026-10-23 06:41**: "MTP (`--spec mtp`) and the prefix store stay at batch 1 for
hybrid models" (reason recorded: per-row hidden outputs and k x 63 MB spec rows per sequence for MTP). Its sources, rb design doc section 7 and
the Fable review (`docs/results/2026-10-23-rb-recurrent-batching/fable-review.md`), give the snapshot-specific reasons:

- **Memory (m4)**: live 63 MB + 4 snapshots per slot is 4.9 GiB at N = 16 on the 35B, allocated lazily inside the scheduler thread (cudaMalloc
  while serving). The design doc wanted the per-slot count configurable (2 at N >= 8) "until the prefix store takes over snapshot storage".
- **Exactness (M5)**: batched prefill picks its chunk by load (`busy_chunk`, default 256; `solo_chunk` 2048 / 4096), so snapshot positions
  and the passes that wrote them depend on what else runs. On GPUs prefill is chunk-dependent (decision 2026-10-23 06:41, second row:
  "busy-chunk prefill vs solo-chunk prefill is KL-gated, not bitwise").
- **Eviction (m5)**: keep = 4 holds the last four chunk ends only, so a long shared system prompt is evicted anyway.

### Memory, with numbers

Per-sequence recurrent state: 35B 62.8 MiB (30 GDN layers x (96 KiB conv + 2 MiB delta)), 27B 149 MiB (plan note,
`docs/results/2026-10-25-mr-hip-27b-batch-profile.md`). KV per token: 35B 20 KiB, 27B 64 KiB. KV budgets from committed plan dumps: 35B on one
R9700 11.9 GB, 27B on one R9700 14.3 GB, 35B on a GB10 62.1 GB. Context per slot after the recurrent reservation (live + s snapshots):

| model / device | N | s = 0 | s = 1 | s = 2 | s = 4 |
|---|---:|---:|---:|---:|---:|
| 35B, R9700 | 8 | 69.7k tok | 66.5k (-5 %) | 63.3k (-9 %) | 56.8k (-18 %) |
| 35B, R9700 | 16 | 33.2k | 30.0k (-10 %) | 26.8k (-19 %) | 20.4k (-39 %) |
| 27B, R9700 | 8 | 24.9k | 22.5k (-10 %) | 20.1k (-19 %) | 15.3k (-38 %) |
| 27B, R9700 | 16 | 11.2k | 8.9k (-21 %) | 6.5k (-42 %) | **1.7k (-85 %)** |
| 35B, GB10 | 16 | 186k | 183k (-2 %) | 180k (-3 %) | 173k (-7 %) |

Restore cost is a device copy of one state: 63 MB at ~194 GB/s is 0.33 ms on a GB10 (rb doc: 0.65 ms measured on an earlier path), 149 MiB
on an R9700 about 0.3 ms: negligible next to the prefill it saves. Snapshot cost per chunk end is the same copy.

### Exactness

With the default reuse rule a recurrent slot resumes at any snapshot (`Model::reuse_len` -> `restorable_len`). On a GPU a resumed request
then runs the remainder from the cut with its own chunk schedule, which a cold run does not, and a busy-chunk prefill wrote the snapshot with
256-row passes that a solo cold run (2048 / 4096) never runs. CUDA and HIP set `prefix_reuse_any_cut = false` for dense models for exactly this
reason, and the HIP solo engine already fails `engine_hybrid_reuse_equals_cold` at a `plen - 1` cut (lane hip-reuse). The opt-in
`INTARSIA_PREFIX_REUSE=exact` rule (`recurrent_schedule_cuts`: resume only at the prompt's own cold-schedule cuts) is the only bitwise rule,
and it needs the snapshot to have been written by solo-chunk passes. A batched slot that prefilled under `busy_chunk` writes other bits at
those positions, so even an exact-cut snapshot would be inexact unless the slot also prefilled with the solo chunk.

### Recommendation

1. **Keep 0 snapshots on GPU batched slots by default** (no change). The binding reason on CUDA is exactness (memory costs only 2-7 % of
   context there); on HIP memory also binds (27B at N = 16: s = 1 costs 21 % of context, s = 4 leaves 1.7k tokens per slot).
2. If batched multi-turn reuse is wanted (the real win: a chat continuation or edited last message re-prefills the whole history today),
   the cheapest exact design is **s = 1 per slot at the request's last solo cold-schedule cut at or below `plen - 1`**, taken only when the
   slot prefilled with the solo chunk (no busy prefill), restored only under the `exact` cuts rule. Memory: 35B R9700 N = 8 -5 %, N = 16
   -10 %; 27B N = 8 -10 %; GB10 -2 %. Gate it per backend/model with the qualify acc-4k reuse rows run through `serve --max-batch` and
   a busy-prefill case. Preallocate in `enable_batch` (already counted by the plan: `per_state x (1 + batch_snapshots)`).
3. Longer-lived shared prefixes (system prompts) belong in the prefix store, not per-slot snapshots (rb design section 7); lifting the
   "prefix store at batch 1" decision is the larger, better-targeted change and needs its own decision.
