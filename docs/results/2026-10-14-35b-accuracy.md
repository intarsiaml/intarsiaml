# 35B accuracy: defect or noise (2026-10-14, spark1 CUDA, tatooine HIP, Mac CPU)

Model `nvidia/Qwen3.6-35B-A3B-NVFP4`, goldens `qwen36-35b-a3b-nvfp4-vllm-top20` (`35b-short`, 10 prompts) and
`...-long-top20` (`35b-long`, 5 prompts), both vLLM (bf16 activations, NVFP4 experts, fp8 KV cache). Starting point:
`docs/results/2026-10-13-phase1b.md` sections 7 to 10 (verdict there: `35b-short` FAIL on the decode aggregates,
`chat_multiturn` decode KL 8.66e-2 with one position at KL 1.33; `35b-long` baseline PASS, floor FAIL as on the old build).

## 0. Approach (written before any GPU work)

The vLLM golden is itself a bf16 / NVFP4 / fp8-KV implementation, so "CUDA disagrees with vLLM" proves nothing. The
judge is agreement between independent implementations of the **same weights** in this engine:

| implementation | where | numerics |
|---|---|---|
| CUDA (HEAD) | spark1 GB10 | bf16 activations, tensor-core GEMMs, grouped MoE mma kernel for T >= 32 |
| CUDA, `INTARSIA_CUDA_DISABLE=moe_experts_mma_bf16` ("oldmoe") | spark1 | as HEAD, warp-per-row MoE for every T (the old numerics, bitwise per phase1b 8.2) |
| CUDA, SIMT attention | spark1 | as HEAD, SIMT instead of flash / split-KV attention |
| HIP (HEAD) | tatooine R9700 | separate kernel set, bf16 activations |
| CPU (HEAD, `--backend cpu`) | Mac | f32 accumulation; NVFP4 / MoE / GDN ops through the f64 reference math, outputs rounded to bf16 at the same points as the GPUs. The closest thing to an fp32 reference the repo has: `tools/golden.py` cannot load the NVFP4 checkpoint (phase1b 9.9) |

Every run dumps the top-64 log-probs of every compared position (`--write-self-golden`), the baseline JSON (all
aggregates and per-prompt stats against the vLLM golden) and the per-position TSV (`INTARSIA_ACC_POS_DUMP`).
`scripts/acc35b/xcompare.py` compares any two dumps per position with the accuracy tool's 21-way KL (validated first by
reproducing the tool's own CUDA-vs-vLLM numbers).

Decision rule per item, fixed now:

* **Outlier position.** At a position p, CUDA is the outlier if KL21(CPU || CUDA) > X and KL21(HIP || CUDA) > X while
  KL21(CPU || HIP) < X / 5, with X = 0.1 nats (an order of magnitude above the mean cross-implementation KL measured
  on short prompts, 3e-3 to 1e-2, phase1b 8.7 and 10.4). The vLLM golden is reported but not a vote. The reference's
  top-2 margin at p is reported so a near-tie can be named: a near-tie is p1 - p2 < 0.2 in every implementation.
* **Reference-free check.** The `--mode both` dump holds the prefill row and the decode row of the same 16 positions
  (same tokens; decode = prefill of n - 16 tokens, then T = 1 steps). Within one implementation the two rows differ only
  by kernel path. If CUDA's prefill and decode rows disagree at p (KL > X) while HIP's and CPU's agree, it is a CUDA path
  defect without any reference.
* **Defect** = CUDA is the outlier by the rule above at the failing positions. Then bisect with
  `INTARSIA_CUDA_DISABLE` (kernel families) to one kernel, fix, add a kernel-level test that fails on the pre-fix code.
* **Noise** = the implementations scatter around each other with CUDA not separated from them (CPU lands as far from HIP
  as from CUDA, or CUDA sits with one of the others). Then the gate gets an envelope for the aggregates derived from the
  measured spread between implementations on the same weights (CUDA variants, HIP; CPU where it covers the full set),
  with the derivation written here, and it must still fail a known-bad perturbation.
* **Lead to check first** (not a conclusion): `chat_multiturn` is the shortest prompt whose decode-mode prefill
  (58 - 16 = 42 tokens) reaches the grouped MoE kernel (T >= 32); phase1b 8.4 shows that kernel at T = 40 still at
  0.19 % of outputs off the reference against 0.01 % for the old kernel, and the committed test covers only T = 128, 512
  with a 0.1 % floor. W1 runs a small-T sweep (`moe_experts_mma_small_t_sweep`).
* Two failed attempts on one line of investigation stop it; the wrong assumption is recorded.

Windows: spark1 vLLM down at most 20 min per window and 60 min in total (`scripts/acc35b/window.sh`, a copy of
`scripts/prefill-cuda-window.sh` with a 17-minute script cap and `FLEETQ_JOB` on every ssh, cleanup included);
tatooine at most 2 bursts of 10 min (`scripts/hip-decode/burst.sh` pattern, `--takes-down radiance`). Builds and the CPU
runs do not stop anything (`fleetq run --mem 0`, CPU runs on the Mac).

## 1. Findings that changed the plan before the comparison

* **The HIP numbers of item 5 were measured against a different golden.** tatooine's
  `/models/golden/qwen36-35b-a3b-nvfp4-vllm-top20.safetensors` is sha256 `89d650a8...`, an earlier vLLM run without
  metadata; the golden every CUDA number is measured against (repo `golden/`, spark1 `~/intarsiaml-golden/`) is
  `b6b51e1b...` (tatooine has it as `...-top20-meta.safetensors`). Token ids are identical; the log-probs are not. So
  "HIP decode top-1 99.38 %, KL 9.96e-3" (`2026-10-13-hip-decode.md` section 5) is not comparable with the CUDA numbers.
  All HIP numbers below are recomputed against `b6b51e1b` from the HIP dump.
* **The reference has run-to-run noise of its own.** The two vLLM goldens (same model, same server role, different
  runs) differ by mean KL21 2.6e-3, max 0.24 at one position, 8 top-1 flips over 1441 positions
  (`scripts/acc35b/xcompare.py vnew=... vold=...`).
* **CPU backend on the Mac.** `sysinfo::available_memory()` reports 1.8 GB on this macOS 27 machine (128 GB, ~70 GB
  unused), which leaves no KV budget for the 35B. Added `INTARSIA_CPU_FREE_MEM_GB` (cpu backend only, overrides the
  measured free memory; off by default). The CPU run of the whole `35b-short` set (both modes) takes about 17 minutes
  at 38 GB RSS.

## 2. Gate rule, fixed before the CPU and corrected-HIP aggregates were seen (written 18:33)

Written after W1 and the HIP burst (the CUDA variants' numbers and the HIP dump were known; the HIP and CPU aggregates
against the correct golden and the CPU-vs-CUDA ranking were not). **This is a post-hoc gate change**: the `35b-short`
decode aggregates failed first, and the "path" perturbation below was chosen after seeing W1's data (section 3). It
decides the verdict, so it is named here before the numbers that use it exist.

* The aggregate checks (top-1, mean KL, tail-bucket KL, top-5, |tail excess|, mean |tail diff|, max KL(21-way)) get the
  same treatment the per-prompt checks got in phase1b 10.1: `limit = baseline -/+ max(fixed margin, k x delta)`,
  k = 2 (`DEFAULT_K`, not tuned), delta = the largest |difference of the aggregate against the vLLM golden| between the
  baseline build and an equally correct perturbation of it, over the perturbations in the envelope.
* Perturbations of the `35b-short` envelope: the two already recorded on the old build (SIMT attention, chunk 64), plus
  * `backend:hip` (HEAD on the R9700) and `backend:cpu` (HEAD on the Mac CPU): an independent implementation of the
    same weights, measured as baseline JSON against the same golden. The MoE-kernel swap is **not** a perturbation: it is
    the change under test.
  * `path:prefill-rows`: the baseline-equivalent build's (oldmoe, whose decode numbers equal the recorded baseline to
    the digit, phase1b 8.2) prefill-mode rows at the 160 decode positions, scored as a decode run. Same build, same
    tokens, same weights, a different but equally valid kernel path: exactly the perturbation observed at
    `chat_multiturn` position 55.
* Max KL(21-way) over 160 positions is an extreme statistic; with these deltas its limit will be near 2 nats, so it is
  effectively blind on this model. Stated now, not after the result.
* Leave-one-out: HIP and SIMT, each judged with an envelope that excludes itself, must PASS; a CPU run with attention
  output scaled x1.01 (`INTARSIA_CPU_MUTATE=attn_prefill,attn_decode:scale=1.01`), judged against the CPU's own
  baseline with the full envelope, **must FAIL**. If it passes, the envelope is too wide and the change is rejected.

### 2.1 Outcome of the section 2 rule: rejected (18:45)

The kill criterion fired. The CPU run with attention output x1.01 (`INTARSIA_CPU_MUTATE=attn_prefill,attn_decode:scale=1.01`,
a deliberate bug) is **closer** to the vLLM golden than the correct CPU run: decode tail-bucket KL 1.037e-2 -> 8.39e-3,
mean KL 1.030e-2 -> 8.33e-3, top-1 98.12 -> 98.75 %; prefill KL21 6.54e-3 -> 6.23e-3, top-1 98.27 -> 97.99 % (-0.28 pt
against the fixed 0.3 pt margin). It passes the old fixed margins as well, so no envelope could make the vLLM-relative
aggregate gate fail it: **the vLLM-relative gate has no resolution at the x1.01 scale on this model, with or without an
envelope.** As written in section 2, the aggregate-envelope change is rejected and not implemented. The `35b-short`
baseline gate against the vLLM golden stays as it is (verdict in section 5).

### 2.2 Same-weights CPU-reference gate, fixed before any mutant dump existed (18:50)

The comparison that can resolve small errors is the one against an independent implementation of the same weights.
It needs no new code: the CUDA build runs `intarsia accuracy --self-golden cpu.dump.safetensors` (the CPU backend's
top-64 dump of `35b-short`, both modes) with `--allow-config-mismatch` (backend), `--allow-same-code` and
`--allow-unstamped` (the Mac CPU dump is unstamped; it was built from commit 55ea0bc + the `INTARSIA_CPU_FREE_MEM_GB`
change, which does not touch numerics).

* Envelope: the self-golden statistics of the correct implementations other than the build under test against the CPU
  dump, X in {oldmoe (= the old build's numerics), SIMT attention, HIP}: mean KL21, largest single-position KL21, flip %,
  mean |tail diff|, worst prompt's mean KL21. Budget per statistic = k x max over X, k = 2 (`DEFAULT_K`). HIP stays in
  (section 2 named `backend:hip` before its numbers were known).
* Known before writing this: KL21(cpu || X) means, decode 5.5e-3 (oldmoe), 5.2e-3 (SIMT), 1.03e-2 (HIP), 6.65e-3
  (HEAD); prefill 4.1e-3, 4.3e-3, 4.8e-3, 4.9e-3 (HEAD). HEAD would fail a k = 1 budget without HIP; the choice of k and
  of HIP carries the verdict, and the reader should weigh it that way.
* Kill criterion: the CPU run with attention output x1.05 must FAIL this gate. If it passes, there is no gate change and
  the conclusion is "no gate available on the 35B resolves this". The x1.01 attention and x1.01 MoE-output mutants are
  reported as the measured resolution, not gated.
* Limits: CPU and CUDA run the same model graph code, so this gate checks kernels, not graph code (the vLLM floor still
  guards the graph); it covers `35b-short` only (the CPU takes ~17 min for it; the long set is out of reach).

### 3.4 Kernel level: the grouped MoE kernel at small T (W2, `moe_experts_mma_small_t_sweep`, 16 seeds x 12 T in 32..64)

Off-reference fraction of bf16 outputs (against `ref_moe_experts`): median 0.105 % (mma) against 0.052 % (old

(The first sweep's seed 11 / T = 33 at 0.85 % was one of these, not a special shape.)

bug. Measured, it is not: a 5 % attention-output error moves the same-weights distance by about 1.4x the spread between
CPU, HIP and the CUDA variants, and moves the distance to vLLM the wrong way. What the evidence does settle is that the
`35b-short` FAIL is not a CUDA defect; what it does not give is a gate that would catch a 5 % bug and pass HEAD at the
same time. Options for whoever takes it up (not done): many more positions per mode (the mean's spread is dominated by
a few fragile positions, e.g. `chat_multiturn@55`), a statistic that drops near-tie positions, or k chosen from a
calibrated false-pass rate over several known-bad mutants.
