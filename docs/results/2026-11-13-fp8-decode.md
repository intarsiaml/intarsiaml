# fp8-decode: the 64k fp8-KV "bimodality" (most likely host page faults on the sampler path) and a fix (2026-11-13, spark1)

Lane fp8-decode (fable-plan Item 3). Qwen3.6-35B-A3B-NVFP4, `intarsia serve --backend cuda --max-seq 131072 --mem-budget 40
--max-batch 2 --profile-every 0` (+ `--kv-dtype fp8` for the fp8 arms) on port 8291 of spark1, each run in its own fleetq
slot. spark1's vLLM (flight / guidance / capcom) was up and untouched, and took no traffic during any rep (scraped per rep).
Builds: `intarsia-base` = main 0e9dd325b (PR #351), `intarsia-fix` = this branch's 3ecde86ce.

Driver: `scripts/fp8-decode/reps.py`. It uses localeval's streaming client with the timing definitions of
`scripts/ab35b/sampled.py`: T 0.7, top_p 0.95, 256 tokens forced with `ignore_eos` + `min_tokens`, nonce-prefixed fresh
prompts. It also records per-rep ITL p50 / p99, the box's vLLM traffic and a hash of the generated text.
`scripts/fp8-decode/serve-run.sh` runs it. Every server ran with `INTARSIA_HOST_PROFILE=1`; the `decode-only` lines give the
mean per-step wall, `step-setup` (the decode step plus the logits download) and `accept` (the host sampler) over 256 steps,
about one request. `memguard.sh` logs MemAvailable, SM clock, power and the server's cumulative minor page faults every 2 s.
Raw files are in `2026-11-13-fp8-decode/raw/`.

## 1. What the bimodality was

ab35c (spark2, `docs/results/2026-11-13-ab35c-tools-store-sampled.md`) saw 64k fp8 decode at 62.8, then 58.3 and 58.2 tok/s.
That fast request was not a fresh server's first: it was the 6th (2 calibration requests and 3 x 32k came before it). The
slow requests were the 2nd and 3rd at the new, larger size.

**fp8 on spark1, base build:** 18 sequential 64k requests over three server lifetimes all landed in 62.6 - 65.8 tok/s, ab35c's
fast level. The runs were r1 (an exact replay of ab35c's sequence: 63.9, 63.9, 62.9), r2 (a fresh server, 64k only, prompt
order swapped: 63.5, 64.0, 64.7, 63.9, 64.1, 62.6, 63.2, 62.8) and r3 (5 x 4k, 5 x 32k, then 5 x 64k). The step wall stayed
flat at 15.57 - 15.68 ms with `accept` at 0.38 ms. Each slot ran several requests (pick_slot's LRU tie-break alternates the
two slots on nonce prompts). This rules out a KV, slot or graph-state degradation.

**The same pattern with bf16, base build, r3:** decode at 32k was 67.3, then 65.1, 65.5, 65.0, 65.1; at 64k it was 54.6, then
52.1, 53.6, 52.6, 52.4. At 64k the host profile puts the loss in `accept`, the host sampler span, which went from 0.40 ms per
step on the first request to 1.09 - 1.14 ms on the next four. The device span stayed at 17.9 ms. From 32k rep 2 on,
`step-setup` was also 0.35 ms higher than in later clean runs (14.96 vs 14.60; it holds the 1 MB logits download). Together
that is ~1.1 ms a step, the size of ab35c's gap (1/58.25 - 1/62.8 = 1.24 ms). The pattern is stochastic: identical later
sequences (r4, r5) ran clean.

**Mechanism, confirmed by forcing it.** The benchmark forces `min_tokens = 256`. The stop-id mask that comes with it turns off
device top-k (`Seq::topk_for`), so every sampled step of these runs takes the full-logits host path. Each step allocated
about 5 MB afresh:
- the 1 MB download buffer (`model/batch.rs`, `vec![0u8; v * 4]`);
- the 1 MB f32 row;
- the sampler's 2 MB key array, plus its candidates and probabilities (`sampler::sample_row`).

glibc serves chunks of this size by `mmap` while its dynamic mmap threshold is low, and that threshold moves with the heap's
history. When the allocations are mmapped, every step touches new pages: the sampler's faults show up as `accept` and the
device download into new pages as `step-setup`. main's prefault commit 368346b24 measured that download at ~170 MB/s on GB10.
- **Arm A** (r6a): `GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072` pins the bad state on the base build. Decode fell from
  81 to 39.9 tok/s at 4k and from 56 to 35.1 at 64k. `accept` went to 1.18 - 1.27 ms (the r3 slow reps' 1.1), `step-setup`
  rose by 11 ms, and the server took ~27k minor faults a second during decode, against ~0 in the clean runs.
- **Arm B** (r6b): mmap off (`mmap_threshold=32 MiB`, `trim_threshold=1 GiB`) stayed flat: 81.2 / 55.7 tok/s, `accept` 0.38 ms.

So the honest numbers are the fast ones. The slow mode is most likely a host allocator state that any request sequence can
fall into, with either KV dtype. Arm A shows that state is enough to produce it (`accept` 1.2 ms against r3's slow reps' 1.13),
and the size matches ab35c's gap (~1.1 vs 1.24 ms a step). But the natural occurrence was not observed directly: r3's slow
reps ran before page faults were logged, r4 and r5 did not reproduce it, and ab35c ran without a host profile.

**Fix** (commit 3ecde86ce, exact):
- The batched and graph decode paths download into a per-thread byte buffer that grows and never shrinks.
- They hand out logits rows from a per-thread pool. `Seq::token_from` returns each row to the pool after sampling (`model.rs`
  `logits_row` / `recycle_logits` / `with_logits_bytes`).
- `Sampler` keeps a `SampleScratch` (`sample_row_in`) across its steps.

The tokens are the same: `sampler::scratch_reuse_is_sample_row` compares it with `sample_row` across lengths, top-k, top-p
and greedy. Under arm A's forced-mmap setting the fix build runs 80.8 tok/s at 4k and 55.0 at 64k (r7a; base 39.9 / 35.1),
with `accept` at 0.39 - 0.40 ms. The per-step large allocations are gone.

The same stress on the single-sequence engine: `--max-batch 1`, `INTARSIA_SPEC_SAMPLED=0` so sampled requests run the plain
graph decode, forced mmap, 4k x 3, one `--quiet gpu,cpu` slot. Base runs 60.5, 53.0, 52.9 tok/s; the fix (b8686b754) runs
82.1, 82.0, 82.0 (raw `run-ss-mmap-*.log`).

Which requests take this path:
- **Single-sequence engine** (`--max-batch 1`, the recipe default): device top-k (`HeadMode::LastTopK`) is batched-decode only,
  so every sampled step takes the host full-logits path. Graph steps go through `graph_decode_step`, eager ones through
  `head_logits`; the fix covers both (commit b8686b754 for `head_logits`).
- **Batched engine:** only rows that need the whole row: stop-id masking under `min_tokens`, `top_k = 0` or > 64,
  constrained decoding and logit traces.

vLLM applies
`min_tokens` on the device, so these sampled benchmarks also carry ~0.38 ms a step of host sampling (~2.4 % at 64k) that vLLM
does not.

## 2. The fp8 split-KV decode kernel is not the bottleneck

The fable plan read "fp8 ~135 GB/s effective, so kernel-limited" from end-to-end per-token slopes. Measured directly with
`row_tables.rs` `timing_attn_rows` on spark1: the batched-decode launch `attn_decode_*_splitkv_rows`
(`splitkv_rows_persist_kernel` + combine), 10 layers' caches cycled from DRAM, at the 35B shape of 16 q and 2 kv heads of 256:

| kv len | bf16 M=1 | fp8 M=1 | bf16 M=2 | fp8 M=2 |
|---|---|---|---|---|
| 4096 | 52.4 us (160 GB/s) | 38.4 us (109 GB/s) | 84.8 us (199) | 55.5 us (152) |
| 32768 | 300.9 us (223 GB/s) | 170.6 us (197 GB/s) | 597.7 us (225) | 330.6 us (203) |
| 65536 | 583.0 us (230 GB/s) | 309.7 us (217 GB/s) | 1156.9 us (232) | 624.4 us (215) |

At 64k the fp8 kernel already streams 217 GB/s against bf16's 230: it takes 0.53x the bf16 time and is bandwidth-bound.

**Tried and reverted:** `INTARSIA_ATTN_F8_PF=2` loaded two iterations' K / V per step in the e4m3 persistent rows kernel. That
doubles the bytes in flight per warp; the steps and their order are unchanged, so the result was bitwise PF = 1. It was slower
at every length: 309.7 -> 322.7 us at 64k, 170.6 -> 179.8 at 32k, 38.4 -> 42.9 at 4k (raw `timing-attn-rows.log`, from the
build of that commit). It is not in the branch.

**Headroom left:** at most ~13 % of the attention time at 64k (217 -> ~250 GB/s), about 0.4 ms of a 15.7 ms step or ~2.5 %
end to end. The obvious lever is more splits at long context: today 64 splits x 2 kv heads make 128 items on a 48-SM grid.
That changes the split policy bf16 and fp8 share, and with it the fp8 = bf16-on-upcast-cache bitwise property
(tests/attn_f8kv.rs), so it was not tried without a decision.

The fp8 step grows by 3.52 ms from 4k to 64k (12.14 -> 15.66 ms). The attention kernel accounts for 2.72 ms of that
(10 layers x (309.7 - 38.4) us); the other ~0.8 ms is unattributed.

## 3. Numbers: base vs fix, same box, same window, 5 reps, sampled T 0.7

One fleetq slot with `--quiet gpu,cpu` (nothing else on spark1's CPU or GPU), arms run in the order below, each on a fresh
server. tok/s median (min - max); step = host-profile decode-only wall, ms, mean of the 5 requests:

| arm | 4k | 32k | 64k | step 4k / 32k / 64k |
|---|---|---|---|---|
| fp8, base | 81.7 (81.6-81.9) | 71.5 (70.5-72.8) | 63.5 (63.4-63.9) | 12.24 / 13.98 / 15.76 |
| fp8, fix | 82.4 (82.4-82.5) | 72.1 (71.9-73.6) | 64.1 (64.0-64.8) | 12.13 / 13.88 / 15.62 |
| bf16, base | 81.5 (81.0-83.8) | 67.0 (66.8-67.3) | 55.7 (55.7-57.1) | 12.31 / 14.97 / 17.95 |
| bf16, fix | 81.0 (80.9-81.1) | 66.7 (66.6-66.9) | 55.5 (55.2-55.7) | 12.35 / 14.99 / 18.01 |

All four ran in the good allocator state (`accept` 0.38 - 0.41 ms everywhere). There the fix is neutral within run-to-run
noise: fp8 +0.9 % (-0.1 ms a step), bf16 -0.3 to -0.6 % (+0.03 - 0.06 ms). What it removes is the bad state: under forced mmap
the base build runs 39.9 / 35.1 tok/s at 4k / 64k bf16 and the fix 80.8 / 55.0 (r6a vs r7a); r3's natural slow mode cost
2 - 4 %, and ab35c's ~7 %.

fp8 against bf16 (fix build): +1.7 % at 4k, +8.1 % at 32k, +15.5 % at 64k.

Reference (ab35b, spark2, vLLM): 75.1 / 69.2 / 62.7 tok/s at 4k / 32k / 64k. fp8 with the fix is ahead of it by +9.7 % /
+4.2 % / +2.2 %. vLLM on spark1 was not measured because it is a
live service. Earlier spark1 runs of the base build (r1 - r5, `--quiet gpu` only, so a CPU build of another lane could run
alongside) are in raw/ and agree within ~1 %.

## 5. Remaining

- **Benchmark caveat.** `scripts/ab35b/sampled.py` (and this lane's driver) force `min_tokens`, which puts every sampled step
  on the host full-row sampler. A device-side stop-id mask (device top-k over k + |stop ids|, filtered on the host) would
  remove that ~0.38 ms a step for `min_tokens` requests. It is not done here.
- **Unattributed slope.** ~0.8 ms of the 4k -> 64k step slope is not explained by the attention kernel.
- **Bursty streaming.** Streamed ITL p99 is ~80 ms at every size (cv ~0.85) although a step takes 12 - 16 ms: tokens reach the
  client in bursts. Decode tok/s is unaffected. Not in this lane's scope.
- **Natural slow mode not caught in the act.** It was not seen with page-fault logging on (see section 1), and ab35c's
  spark2 window has no host profile. A run that catches it naturally with `minflt` rising would close this.
