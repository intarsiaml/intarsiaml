# fp8-decode: the 64k fp8-KV bimodality and the fp8 decode attention kernel (2026-11-13, spark1)

Lane fp8-decode (fable-plan Item 3). Qwen3.6-35B-A3B-NVFP4, `intarsia serve --backend cuda --max-seq 131072 --mem-budget 40
--max-batch 2 --profile-every 0` (+ `--kv-dtype fp8` for the fp8 arm), port 8291 on spark1, every run in its own fleetq slot
(`--quiet gpu`), spark1's vLLM (flight / guidance / capcom) up and untouched. Build: main 0e9dd325b (PR #351), the code of
this branch (no engine change ships). Driver: `scripts/fp8-decode/reps.py` (localeval's streaming client, the timing
definitions of `scripts/ab35b/sampled.py`: T 0.7, top_p 0.95, 256 forced tokens, nonce-prefixed fresh prompts, plus per-rep
ITL p50 / p99, the vLLM traffic of the box during the rep, and the generated text's hash), run by `scripts/fp8-decode/serve-run.sh`
(server log with `INTARSIA_HOST_PROFILE=1`, MemAvailable / SM clock / power / temperature every 2 s). Raw: `2026-11-13-fp8-decode/raw/`.

## 1. Bimodality: not reproduced; the first request's number is the honest one

ab35c (spark2, ab35b build, `docs/results/2026-11-13-ab35c-tools-store-sampled.md`) saw 64k fp8 decode 62.8, 58.3, 58.2 tok/s.
Correction to the premise: that 62.8 was not a fresh server's first request; it was the 6th request (2 calibrations, 3 x 32k,
then 64k rep 1). Runs on spark1:

| run | sequence | 64k decode tok/s, each rep | 64k median |
|---|---|---|---|
| r1 exact replay of ab35c | calibrate, 32k p0 p1 p2, 64k p0 p1 p2 | 63.9, 63.9, 62.9 | 63.9 |
| r2 fresh server, 64k only, order swapped | 64k p2 p1 p0 p0 p1 p2 p3 p4 | 63.5, 64.0, 64.7, 63.9, 64.1, 62.6, 63.2, 62.8 | 63.7 |
| r3 fresh server, 4k / 32k / 64k x 5 | 64k after 5 x 4k and 5 x 32k | 65.8, 63.9, 63.8, 63.9, 64.3 | 63.9 |

(p*i* = filler prompt *i*, i.e. sampled.py's rep *i* prompt.) 18 sequential 64k fp8 requests over three server lifetimes, every
one within 62.6 - 65.8 tok/s, i.e. all at ab35c's "fast" level; none at 58. The host profile's decode-only step wall
(mean per 256 steps) is flat across requests: 15.57 - 15.68 ms at 64k (r2, 8 requests), 15.65 - 15.68 (r3), so there is no
degradation after request 1, from slot alternation (pick_slot's LRU tie-break alternates the two slots on nonce prompts; r2
ran 4 requests on each slot), KV reuse, stale state or re-capture. The step time does not depend on the prompt (p0 is not
faster wherever it lands), the SM clock stayed 2.33 - 2.46 GHz throughout, and spark1's vLLM took no traffic during any rep.

WIP: the mechanism of ab35c's slow reps is being pinned down (section 1b): bf16 r3 on spark1 showed the same "first
request at a new size fast, later ones slow" pattern in the host profile's `accept` span (0.40 -> 1.13 ms per step).

## 2. The fp8 split-KV decode kernel is not the bottleneck

The fable plan inferred "fp8 ~135 GB/s effective -> kernel-limited" from end-to-end per-token slopes. The kernel itself
(`row_tables.rs` `timing_attn_rows`: the batched-decode launch `attn_decode_*_splitkv_rows` = `splitkv_rows_persist_kernel` +
combine, 10 layers' caches cycled from DRAM, the 35B shape 16 q / 2 kv heads of 256), spark1:

| kv len | bf16 M=1 | fp8 M=1 | bf16 M=2 | fp8 M=2 |
|---|---|---|---|---|
| 4096 | 52.4 us (160 GB/s) | 38.4 us (109 GB/s) | 84.8 us (199) | 55.5 us (152) |
| 32768 | 300.9 us (223 GB/s) | 170.6 us (197 GB/s) | 597.7 us (225) | 330.6 us (203) |
| 65536 | 583.0 us (230 GB/s) | 309.7 us (217 GB/s) | 1156.9 us (232) | 624.4 us (215) |

At 64k the fp8 kernel already streams 217 GB/s (bf16 230), 0.53x the bf16 time: it is bandwidth-bound, not latency-bound.

Tried and reverted (commit cef962800, reverted in the next commit): `INTARSIA_ATTN_F8_PF=2`, loading two iterations' K / V
per step in the e4m3 persistent rows kernel (twice the bytes in flight per warp, the same steps in the same order, so
bitwise the PF = 1 partials). It was slower everywhere: 64k 309.7 -> 322.7 us, 32k 170.6 -> 179.8, 4k 38.4 -> 42.9 (raw
`timing-attn-rows.log`, `pf=2` vs `pf=1` lines; the extra registers cost occupancy). Not shipped.

Headroom left in the kernel: at most ~13 % of the attention time at 64k (217 -> ~250 GB/s), ~0.4 ms of a 15.66 ms step
(~2.5 % e2e). The obvious lever, more splits at long context (64 splits x 2 kv heads = 128 items on a 48-SM grid), changes
the split policy shared by bf16 and fp8 (and the fp8 = bf16-on-upcast-cache bitwise property, tests/attn_f8kv.rs), so it was
not tried without a decision.

the other ~0.8 ms is unattributed (nsys of a 64k serve step would split it; not done).
