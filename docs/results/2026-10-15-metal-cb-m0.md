# Metal continuous batching, M0: per-sequence state machine (refactor only)

Date 2026-10-15. Branch `metal-cb-m0` off `spike/metal` 56ec2d5 (G0, G0b and G1 merged). Machine endor (Apple M5 Max),
Qwen3-8B BF16. Plan: `docs/research/continuous-batching-design.md`, milestone M0 (sections 2.3 and 7), operator decisions in
section 8.1 (exact-only batching, cap 8, prefill chunk 256 while others decode: those matter from M1, not here).

**Verdict: M0 gates met.** The request token loop is now a per-sequence state machine, `Seq`, that
`generate_one` drives for one sequence. No behavior change: stdout, `--show-ids` ids, finish reason, completion count and the
speculative-decoding trace lines are byte-identical to the 56ec2d5 binary on 29 + 8 `generate` cases (spec off and
`--spec ngram`) and on a serve check (two-turn prefix reuse after a stop, seeded sampling, client disconnect,
counters). Decode speed is within 0.7 percent of base (new is not slower) at 128, 1k and 4k. `--max-batch N` exists
(default 1); N > 1 is rejected with "not implemented yet". No kernel or backend crate was touched; `model.rs`, `Model::new_state`,
`SequenceState` and KV allocation are untouched.

Commits (all on `metal-cb-m0`): `1071f3a` code, then the raw scripts and this document.

## 1. What moved where

Only `crates/intarsia-core/src/engine.rs` (the engine loop) and `crates/intarsia-cli/src/common.rs` (the flag) changed.

| Before (`engine.rs` at 56ec2d5) | After |
|---|---|
| `generate_one(sh, g, &req, &tx)`: validation, prefix reuse, `pick` closure, prefill loop, per-token loop, spec state, tail flush, all in one function | `Seq` (`pub(crate)`) holds the per-request state: sampler, stop ids, `IncrementalDecoder`, `StopMatcher`, `generated`, `min_tokens` switch, spec state (`pending`, `plain_next`, `ctx`, `SpecGate`). `generate_one` is a 15-line driver. |
| `pick` closure (`need_logits` decision, `min_tokens` mask, sampler) | `Seq::head_mode(k)` picks `LastLogits` or `LastArgmax`; `Seq::token_from(out, k)` applies trace, mask and sampler. The split is what a batched step needs: one forward for many rows, then per-row sampling. |
| prompt chunk loop with cancel checks | `Seq::prefill_step`, one chunk per call |
| top of the token loop (stop id, detokenise, stop strings, send, `max_tokens`, cancel) | `Seq::on_token` |
| pending queue pop, draft proposal, `spec_verify` call, telemetry, trace line, plain step | `Seq::plan_step` (what is needed next), `Seq::verify`, `Seq::advance` (single-sequence plan + run + sample) |
| spec KV rollback, held-back text flush, `Outcome` | `Seq::finish` |
| `run_job(sh, job)` borrowed `job.req` / `job.tx` | moves `req` into `Seq`, keeps a `tx` clone for `Done` / `Error`; telemetry calls unchanged |

Unchanged on purpose: `spec_verify` (free function, now called from `Seq::verify`), `LocalEngine`, the worker thread, the
`Inner` mutex, `run_job` telemetry (`request_started`, `request_finished`, `set_kv`), `debug_hooks`, the panic path.

Per-sequence API (what M1's `BatchEngine` drives):

```rust
pub(crate) struct Seq { req, tx, codec, telemetry, sampler, stop_ids, dec, stops, generated, spec state, .. }
Seq::new(sh, model, st, req, tx) -> Result<Seq>             // validate, reuse + truncate the KV prefix held in `st`
seq.prefill_step(model, st) -> Result<PrefillStep>          // Chunk | Started (first token in seq.tok) | Finished(Outcome)
seq.on_token() -> Result<bool>                              // account for seq.tok; true = finished
seq.plan_step(st) -> Next                                   // Emit(tok) | Verify(drafts) | Plain
seq.verify(model, st, &drafts) -> Result<()>                // speculative verify pass; verified tokens queue up
seq.head_mode(k) -> HeadMode; seq.token_from(out, k) -> Result<u32>   // plain step head / sampling (batchable halves)
seq.advance(model, st) -> Result<()>                        // single-sequence: plan + forward + sample
seq.finish(model, st) -> Result<Outcome>                    // spec KV rollback, tail flush, report
```

`--max-batch N` (`ModelArgs`, so on every command that loads a model, `serve` included): default 1; 0 is an error;
N > 1 fails with `--max-batch N is not implemented yet (continuous batching is milestone M1); use --max-batch 1`.
The check sits in `ModelArgs::engine_options`, before any weights are read.

Timing points kept as they were: `prefill` ends after the first sampled token, `decode` starts then, `t0` is taken after the
prefix truncate (now at the end of `Seq::new`). The cancel flag is checked at the start of every prefill call and after
each streamed token, as before. `GateParams::from_env` is read in `Seq::new` instead of after prefill (same value, nothing
reads it in between).

## 7. Limits and what M1 inherits

* Still one `Seq` at a time on one `SequenceState`; `--max-batch > 1` is an error. M1 adds the scheduler, N states and the
  `BatchEngine`; `Seq` keeps its `req`/`tx` and is not tied to the `Inner` mutex.
* `prefill_step` runs one model-chunk per call and checks cancel before each; M2's 256-token interleave will need a way to
  pass a smaller chunk size (today it reads `model.prefill_chunk()`).
* `Seq::new` does the prefix reuse against the single state; M1's slot choice (design section 3.5) has to happen before it.
* The `generate_one` path still holds the engine mutex for the whole request, as before.
* Speed figures are from one machine state (other sessions' jobs ran between my slots, each slot was exclusive).
* Sampled requests are compared with fixed seeds; the sampler stream per seed is unchanged because `Sampler::new` and the
  call order of `sample` are the same.
