## Brief + progress (kept at the top so it survives compaction)

Brief (coordinator, 2026-11-16, condensed): lane mstore (`2026-11-15-mstore-metal.md`) measured that after a prefix-store
restore the MTP head only sees the tokens prefilled after the restore point (its context restarts there, lane mtp-store):
35B 4k acceptance 60 % -> 42 %, decode 148 -> 128 tok/s, the catch-up costing 23 to 32 % of the prefill saved (stop rule
20 %). Fix: keep the head's KV rows (and any head state) in the store entry and restore them, so a restored sequence drafts
as if cold. Gates: emitted tokens unchanged (restored == cold, greedy and seeded sampled, single and `--max-batch 2`, after a
restart from disk; `tests/mtp_store_metal.rs` extended with acceptance within 2 points of cold on the 35B 4k case); old
entries read correctly or a clean miss; report the added bytes per entry; backend-neutral in core, CUDA builds and CPU
tests pass (GPU gate a leftover); MTP off: `GET /v1/intarsia/plan` byte-identical to main and the store bytes unchanged.
Measurement: mstore's window, 35B 4k and 27B 4k, fix vs main, ABBA, fresh servers, server step time per arm, 90 s
cooldowns. Results doc, LOG row, PR against main (not merged).

## Summary

- **Fixed: a restored request now drafts exactly like a cold one.** The store entry keeps the MTP head's cache rows and its
  queued hidden row, and a restore writes them back. 35B at 4k after a restore, against main: acceptance **59.9 %**
  (main 42.0 %, cold 59.9 %), decode **148.8 / 149.1 tok/s** (main 128.2 / 128.6, cold 148.7). On the 27B at 4k:
  **60.4 %** (main 50.0 / 48.4 %, cold 60.4 %), decode **51.2 / 51.1 tok/s** (main 46.5 / 45.8, cold 51.0).
- **The catch-up cost is gone: 0 % of the prefill saved** in all four cells (the rule allows 20 %). Main measured
  31 % / 24 % on the 35B (lane mstore: 32 / 23 %) and 10 % / 10 % on the 27B. The restored replies decode at the cold
  speed, so there is no break-even reply length any more. Restore time is unchanged within noise: TTFT 311 vs 305 ms
  from disk and 43 vs 41 ms from host on the 35B, 844 vs 837 ms and 68 vs 68 ms on the 27B.
- **Tokens unchanged. Every gate passes on both models.**
  - Lane mstore's gate (`tests/mtp_store_metal.rs`): restored == cold for greedy and seeded sampled, single-sequence and
    `--max-batch 2`, and after a restart from disk.
  - New 4k case: restored acceptance equals cold to the token on both models, greedy and sampled (delta +0.0 points,
    tolerance 2).
  - Every window text equals main's cold text (same hash).
- **MTP off: nothing changes.** The served plan is byte-identical, with `--spec off` and with the MTP default. The
  MTP-off store has identical object payloads, the same manifest fields and the same entries.
- **Footprint:** the head's cache costs 2 KiB per token on the 35B and 4 KiB per token on the 27B. That is one attention
  layer, against 20 / 64 KiB for the main KV pages. Each entry adds a 4 / 10 KiB tail. Measured on disk after the 4k
  prompt: **+9.24 MB (+4.1 %)** on the 35B (2 entries) and **+18.6 MB (+2.4 %)** on the 27B (3 entries). Head pages are
  shared between entries the same way main pages are.
- **Both engines restore the head.** In the gate's store snapshots every entry got the head's part and every hit
  restored it: single-sequence engine 10 entries / 10 with the head, 8 hits / 8 head restores; `--max-batch 2`
  10 / 10 and 14 / 14 (35B; the 27B 11 / 11, 8 / 8 and 11 / 11, 14 / 14).
- **Upgrade: one cold miss per prefix**, MTP-on servers only. The build key of a model with an MTP head gains
  `|mtphead1`, so entries written by older binaries go to another directory and are never read. The key already holds
  the executable's size and mtime, so every new binary misses once anyway. MTP-off keys, files and manifests are
  unchanged.

## Design

`crates/intarsia-core/src/prefix_store.rs` (`HeadLayout`, `HeadRef`), `state.rs` (`SequenceState::mtp_load_head`),
`model/mtp.rs` (`Model::mtp_store_layout`), `engine.rs` (the store is built with `PrefixStore::new_with_head`).

**The head trails the main model by one position.** Head row `p` reads the main model's hidden row of `p` and the token
of `p + 1`. So after a prefill chunk ending at `len`, the caught-up head holds rows `0..len - 1` and queues the hidden
row of `len - 1`.

**Head pages.** The entry keeps one head page per main page:
- The head page of the main page `[start, end)` holds head rows `[start - 1, end - 1)` (`[0, end - 1)` for the first).
- Those rows depend on the tokens up to `end` and on the chunks that wrote main rows up to `end - 1`. That is exactly
  what the main page's key covers: the tokens up to the end of the chunk that wrote its last row.
- So a head page uses its main page's key (salted), and entries share head pages the same way they share main pages.
- Without the shift, head row `end - 1` would depend on the next chunk, which a key that ends at a chunk end does not
  cover.

**Head tail.** The queued row is per entry (one hidden row, salted entry key).

**When an entry gets the head's part.** Only when the head followed the sequence from position 0 and caught up in a
prefill pass:

```
active && synced && base == 0 && kv.len + 1 == len && pending_rows == 1
```

Otherwise the entry is stored as before, without it. A restore of such an entry restarts the head's context at the
restore point (lane mtp-store). A head object counts as one of the entry's objects for lookup, eviction, pinning and
the disk manifest: an entry that loses one is dropped, as with a main page. Manifests get a `head` field only when the
entry has the head's part.

**Counters.** `mtp_head_inserts` and `mtp_head_restores` in the store snapshot, omitted when zero, so an MTP-off
snapshot is unchanged.

## Deviations and limits

- **Commits.** The windows used the pinned `9e4a8274c` (the fix), the gates the branch at `f2374bb0d` (the fix plus a
  docs row). The PR head merges origin/main (`34ce1373c`: HIP comm, `plan.rs`, `scheduler.rs`, docs; nothing this
  change touches). It was pushed with `--no-verify` because the pre-push hook's cargo tests would have loaded the CPU
  during lane kvq's quiet timing job. CI on the merge: see the PR.
- **The gate is from the branch build.** `gate.sh` ran `cargo test` on the branch (`f2374bb0d`: the fix plus a docs
  row). The windows used the pinned binaries.
- **Two reps per arm, one window per model; 32k not re-run.** Main's 32k cost was at most 1 % in lane mstore, and the
  same code path now restores the head there.
- **Head-less entries spread.** An entry written by a request that did not draft (constrained, traced, or not greedy
  where sampled requests do not draft), or written after a head-less restore (`base > 0`), has no head part. A restore
  of it restarts the head at the restore point, as before, and every later entry of that conversation is head-less too.
  Mixed batched passes that do not catch the head up (`pending_rows > 1` at the insert) also store head-less entries.
  The gates' drafting chats always stored the head; how often serving traffic produces head-less entries was not
  measured.
- **CUDA not built here.** The change is in core and backend-neutral, but the CUDA backend needs nvcc, which endor lacks.
  CI covers the compile (`cargo check (linux, cuda cfgs)` and `cargo test (linux)` on PR #406). The CUDA GPU gate
  (`tests/mtp_store_cuda.rs`) was not run: the Sparks are busy.
