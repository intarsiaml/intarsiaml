# kvonce: CUDA verify attention reads KV once per sequence (2026-11-20)

## Brief

Lane `kvonce`: add a CUDA verify-attention mode that reads each sequence's K/V once per verify pass for all of its rows. It must be opt-in and bit-identical to the current kernel. Worktree `/opt/code/intarsiaml/.worktrees/kvonce` (branch `kvonce`, from origin/main 2f989e0b). All scratch and build dirs inside it.

### Why
Lane samp64 (PR #471, `docs/results/2026-11-20-samp64.md`) measured the 35B NVFP4 on spark2 (GB10), bf16 KV, MTP k=2. At 64k context the verify-attention kernel `attn_decode_bf16_splitkv_rows` takes 18.6 of 36.2 GPU-busy ms per verify pass, against 1.3 ms at 4k. It streams the KV cache once per ROW, so a 3-row pass reads about 3x the 1.4 GB a plain decode step reads. That is why drafting loses to `--spec off` above ~56k (cutover blocker 5: sampled 64k is x0.81 of vLLM). samp64 shipped only an opt-in draft-length schedule (`INTARSIA_SPEC_SAMPLED_CTX_K`). The real fix is one KV read per sequence.

### Prior art (port it)
Metal: `INTARSIA_METAL_ATTN_KV_ONCE` (default-on, bit-identical; packed threadgroups: rows and head groups of a kv head share a threadgroup, each keeps its own softmax streams). Read `docs/results/2026-11-15-mka-metal-kv-once.md`, `docs/results/2026-11-16-kvq.md`, `crates/intarsia-backend-metal/src/attn.rs` (`pack_plan`), `kernels/metal/attention_splitkv.metal` ("Packed threadgroups"), `crates/intarsia-backend-metal/tests/kv_once.rs`. CUDA side: `crates/intarsia-backend-cuda/src/device.rs`, `tests/verify_attn_rows.rs`, `tests/row_tables.rs`, `tests/attention.rs`, CUDA kernel sources, the verify row-table launch (`INTARSIA_CUDA_VERIFY_ATTN_ROWS`, default-on since PR #464, lane cvat).

  - Why not Metal's packed threadgroups: bitwise needs each (row, head) stream to keep the canonical decomposition (8 key lanes x 32 threads, 8 dims per thread, KB=2). Accumulator state alone for 3 rows x 8 heads = 24 x 256 x 8 floats = 49K registers per (kv head, split): it does not fit one SM (64K regs) next to qr / prefetch / working registers. (Metal's own verdict for the 35B shape: packing did not pay.) Register count to be confirmed with cuobjdump on the first build.
  - PLAN (advisor-agreed): schedule-only change inside the persist kernel, template flag ONCE. Items renumbered (group, kv head, split, row-in-group), group = run of consecutive table rows with identical K and V pointers and the same split count and chunk, built on the device in the shared-memory preamble (graph-safe, fixed grid). Consecutive items go to concurrently running blocks, so the rows of one sequence stream the same K / V lines at the same time: one DRAM fetch, L2 serves the siblings. Loads `__ldg` instead of `__ldcs` (evict-first fights the reuse). Each item's arithmetic, range and partial slot are unchanged -> bitwise by construction. Fallback if the microbench shows too little: shared-memory staged tile (zero K/V past each row's end, skip iterations past end).
  - Knob: `INTARSIA_CUDA_ATTN_KV_ONCE=1` read once per process (like `rows_persist()`), plus extern "C" test setters (override, planted fault = group leader's end applied to every row).
  - Measurement plan: extend `verify_attn_rows.rs::timing_captured_attention_layers` (cap 65536+, t=3, knob off/on) on spark2 first, then served ABBA.
