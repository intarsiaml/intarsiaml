# kvonce: opt-in CUDA verify attention reads the KV cache once per sequence (2026-11-20)

Lane `kvonce`, branch `kvonce` from origin/main `2f989e0b`, spark2 (GB10), fleetq owner `claude-kvonce`. Qwen3.6-35B-A3B NVFP4, bf16 KV, MTP k=2, the shipping `serve` command line of samp64 / ab35d (`--max-seq 131072 --mem-budget 40 --max-batch 2 --prefix-store on`), production vLLM (`retro`) up beside it and untouched.

## Summary

1. **`INTARSIA_CUDA_ATTN_KV_ONCE=1` (opt-in, default off): the verify pass's rows of one sequence now share one DRAM read of the KV cache.** The persistent row-table attention kernel numbers its work items so that the 3 rows of a verify pass process the same (kv head, split) on neighbouring blocks at the same time; the L2 serves the repeat reads. Each item's arithmetic is untouched, so the output is bitwise the default launch.
2. **Kernel time per verify pass (nsys, 10 full-attention layers): 64k 17.2 -> 6.4 ms, 32k 8.4 -> 3.4 ms, 4k 1.2 -> 0.75 ms.** A 3-row pass at 64k now costs 1.09x a one-row decode step's attention (microbench, shipped `=1`: 5.90 ms against 5.41 ms for 10 layers; it was 2.96x).
3. **Served (ABBA BAAB, 12 reps per arm per cell, all windows clock-clean): sampled 64k 52.8 -> 75.5 tok/s (x1.43), 32k x1.22, 4k x1.05; greedy 64k 60.5 -> 88.2 (x1.46), 32k x1.27, 4k x1.02.** No cell is worse.
4. **Identity: seeded sampled (T=0.7) and greedy replies of 700 tokens at 4k / 32k / 64k prompts byte-identical knob on vs off (reply text and completion-token counts); bitwise test PASS (35B, 27B, 35B fp8 KV; M 1..=16, mixed tables, captured graphs; planted fault caught 7 of 7 per shape).**
5. **Cutover blocker 5 closes with the knob on:** sampled 64k 75.5 tok/s against vLLM's 65.3 (ab35d) = **x1.16** (was x0.81). With the knob on, MTP k=2 beats `--spec off` at 64k (75.5 against 57.2 sampled, 88.2 against 58.7 greedy), and k=2 also beats k=1 with the knob (64k 74.1 against 69.7, 32k 86.0 against 80.4): samp64's schedule (`INTARSIA_SPEC_SAMPLED_CTX_K`) is not needed with the knob, and its gated value `28000:1,56000:0` would now cost about 6 % (k=1 region) and 24 % (plain-step region) at 64k. **Do not combine `INTARSIA_SPEC_SAMPLED_CTX_K=...,56000:0` (or any k < 2 entry) with `INTARSIA_CUDA_ATTN_KV_ONCE=1`.**
6. No default flip: that is the user's call. Recommendation: default-on candidate for CUDA (it is a pure work reordering, bitwise by construction and by test).

## Brief

Lane `kvonce`: add a CUDA verify-attention mode that reads each sequence's K/V once per verify pass for all of its rows. It must be opt-in and bit-identical to the current kernel. Worktree `/opt/code/intarsiaml/.worktrees/kvonce` (branch `kvonce`, from origin/main 2f989e0b). All scratch and build dirs inside it.

### Why
Lane samp64 (PR #471, `docs/results/2026-11-20-samp64.md`) measured the 35B NVFP4 on spark2 (GB10), bf16 KV, MTP k=2. At 64k context the verify-attention kernel `attn_decode_bf16_splitkv_rows` takes 18.6 of 36.2 GPU-busy ms per verify pass, against 1.3 ms at 4k. It streams the KV cache once per ROW, so a 3-row pass reads about 3x the 1.4 GB a plain decode step reads. That is why drafting loses to `--spec off` above ~56k (cutover blocker 5: sampled 64k is x0.81 of vLLM). samp64 shipped only an opt-in draft-length schedule (`INTARSIA_SPEC_SAMPLED_CTX_K`). The real fix is one KV read per sequence.

## Design (what was built)

- **Where the time went.** The shipping verify pass (captured `spec_step` graph, cvat's row-table launch, and the eager verify passes) runs each full-attention layer's k + 1 = 3 rows as ONE `attn_decode_bf16_splitkv_rows` launch, which for the 35B (G = 8 query heads per kv head) and the 27B (G = 6) is `splitkv_rows_persist_kernel`: a fixed grid of SMs x resident blocks (48 x 1 on GB10) that deals the (row, kv head, split) items round robin, numbered row by row. So row 0 streams the whole 64k cache, then row 1 does again, then row 2: three DRAM reads of 134 MB per layer (samp64 nsys: 1.72 ms per launch, ~235 GB/s).
- **Why not Metal's packed threadgroups.** Bitwise identity fixes each (row, head) stream's decomposition (8 key lanes x 32 threads, 8 dims per thread, 2 keys per step, own online softmax per lane). The kernel already uses 251 registers per thread at one 256-thread block per SM; a block cannot hold a second row's accumulators (3 rows x 8 heads x 256 threads x 8 floats = 49K registers of accumulators alone per kv head and split).
- **What ONCE does instead (`INTARSIA_CUDA_ATTN_KV_ONCE=1`).** The same items, numbered differently: a *group* is a run of consecutive table rows with the same K and V cache addresses, the same split count and the same chunk (a verify pass; built on the device in the kernel's shared-memory preamble, so a captured graph stays valid at every position); a group's items are numbered kv head, then split, then row. The rows of one (kv head, split) are therefore consecutive items, dealt to neighbouring blocks in the same round, and they stream the same K / V lines at the same time: one DRAM fetch, the other rows hit L2. The loads stay streaming (`__ldcs`); plain loads (`=2`, diagnostic) measured 1-3 % slower. Every item computes exactly what it computes without the knob (row, kv head, split, key range, q, accumulation order, partial slot) and the combine is untouched, so the output is bitwise the default launch's by construction. Rows whose split count or chunk differs (a pass straddling a split-count change below 4096 keys or a chunk change every 4096 keys above) simply form separate groups.
- **Coverage.** Every caller of the row-table attention with the persistent kernel: the captured MTP verify graph and the eager verify passes at tp 1 (the shipping `serve --spec mtp`), the head's catch-up rows, batched decode (one-row groups: same work, different preamble), and the fp8_e4m3-cache twin. At tp 2 the same launcher takes the knob too (per-rank 12/2/256, G = 6): bitwise by the same construction, not measured served. The full-grid fallback (`INTARSIA_ATTN_ROWS_PERSIST=0`) and groups of <= 4 heads (the 8B, no persistent kernel) never read the knob. No Rust model change; `plan show` cannot change (the knob is read inside the kernel launcher).
