## 1. Where the 27B issues small-M MXFP4 matmuls (task 1)

Method: `INTARSIA_METAL_PROFILE=cb` + `INTARSIA_METAL_COMMIT_EVERY=1` (one record per dispatch, `t` = rows), histogram of
the `matmul_mxfp4_*` calls by M (`scripts/msmallm/mhist.py`). Job #9764, `raw/window.txt`, traces in `raw/window/`.

| path | MXFP4 calls by M (kernel) |
|---|---|
| `generate`, 6-token prompt, MTP default | prefill M = 6 (GEMV); decode M = 1; MTP verify M = 3 (GEMV) |
| `generate`, 6-token prompt, `--spec off` | prefill M = 6 (GEMV); decode M = 1 |
| `generate`, about 2.3k-token prompt, `--spec off` | prefill 2048 + **267** (NAX); decode M = 1 |
| `generate`, 4k prompt, MTP default | prefill 2047 + 2048 (NAX); decode M = 1, verify M = 2 / 3 (GEMV) |
| `serve --max-batch 16 --spec off` | **refused at load**: "a 9-row batched step runs matmul_mxfp4 on matmul_mxfp4_nax, which is not a row-exact (`rows_exact`) kernel and not the solo step's (matmul_mxfp4_gemv)" |
| `serve --max-batch 8 --spec off`, 9 concurrent chat requests | prefill **M = 62** per request (NAX, 496 calls each); batched decode M = 1..8 (GEMV); startup probes M = 9..16, 31, 32 (8 calls each, all before the first request) |
| `serve` default (MTP, max-batch 1), 4 concurrent chat requests | prefill **M = 62** per request (NAX); decode M = 1, verify M = 2 / 3 (GEMV) |

Readings:

* The NAX path starts at M = 9 (`mxfp4::nax_ok`: M > `GEMV_MB` = 8); M <= 8 is the GEMV (`matmul_mxfp4_gemv`, the M-row shaders
  at 2..8). That lower edge is not touched by this lane.
* **Decode never reaches `matmul_mxfp4_nax` on Metal.** Solo decode is M = 1, MTP verify M = 2 / 3, batched decode at most 8 rows
  (Metal's `--max-batch` cap; the plan check `check_batch_ops` refuses 9+ rows for the 27B because the NAX kernel is neither
  row-exact nor the solo step's). So the brief's "batched decode above 8 streams" produces no small-M calls today, and making
  the in-kernel form serve it would need a row-exact kernel bitwise the solo GEMV: a numerics-class change, not this lane's.
* The in-window traffic is **prefill only**: every short prompt (a chat-templated one-line request is M = 62), the remainder
  of a prompt chunked at 2048 (`len mod 2048`), and the tails of busy chunks (`--busy-chunk`, default 256) beside decoding
  streams.
* In the gates and the speed runs, "9 / 16 streams" therefore means 9 / 16 concurrent requests on `serve --max-batch 8`
  (Metal's cap; the extra requests queue and prefill as slots free up, beside the running decoders).

**Decision metric (fixed before the ABBA):** the change can only move prefill of in-window prompts. localeval's decode tok/s
excludes TTFT, so it is flat by construction. The stop rule is judged on the **wall-clock aggregate**: total completion tokens
over the time from the first request sent to the last token received, on short prompts, per stream count. Also reported:
short-prompt TTFT, server step ms, and 4k TTFT as the null cell (4k prompts never enter the window).

## 2. Crossover and routing (task 2)

`examples/naxd_bench.rs` (lane mprefill's microbench), job #9764, `raw/bench-smallm.txt`: per `matmul_mxfp4_nax` call, the
scratch path (activation pre-pass + `mxfp4_w_to_bf16` + the NAX GEMM) against each in-kernel decode form, 5 interleaved rounds,
a 1 GiB pool of distinct weights, W4A16. Quiet box (thermal 0 at the start; tight min-max ranges). Ratio = scratch time / form
time for form 0 (64 x 64, BK 64, 4 simdgroups, the fastest form at every M <= 128); bold = at least 1.05x. Output hashes equal
across all arms in all 54 cells.

The step at M = 96 is the second 64-row tile: the form re-decodes the weights once per 64 output rows, while the scratch
path decodes them once per call. The crossover is one 64-row tile pair: **M <= 128 wins on every shape (1.24x to 3.49x)**;
at M = 160 the GDN z projection loses (0.94x) and the others gain only 1.07 to 1.27x. A per-shape limit up to 192 would add a
little on five shapes; the single limit keeps the rule simple and was not refined.

Routing (`crates/intarsia-backend-metal/src/mxfp4.rs`):

* `INTARSIA_METAL_MXFP4_NAXD` unset = `NaxdKnob::Auto`: a `matmul_mxfp4_nax` call with M <= `NAXD_SMALL_MAX_M` (128) runs
  form `NAXD_SMALL` (0); larger calls keep the scratch path. The op itself only takes M > 8 (`nax_ok`), so the window is
  M = 9..128. `0` = the scratch path at every M (the build before this lane); `1` / `f<i>` force a form at every M as before.
* The kernel class is unchanged (the same registered `matmul_mxfp4_nax`, the same scratch size, the same M > 8 boundary to
  the GEMV), and the form is bitwise the scratch path (lane mprefill's `naxd_forms_are_bitwise_the_scratch_path`, and the new
  `small_m_routing_is_bitwise_the_scratch_path` at M = 9, 62, 128, 129 through the unset knob). So **default on**, per the brief.
* docs/tuning.md row updated (default "on for M = 9..128 (set 0 to disable)").

## 4. Speed (task 3)

`scripts/msmallm/abba.sh` (raw in `raw/abba/<visit>-<server>/`, tables by `scripts/msmallm/analyze.py`): same binary, A =
`INTARSIA_METAL_MXFP4_NAXD=0` (the scratch path at every M = main's behaviour), B = unset (this PR's default). Fresh servers per
visit. Per visit, server 1 = the default engine (MTP k2, max-batch 1): `s1` = 1 stream x 4 requests, then the null cell
`null4k` = 2 requests of 4716 prompt tokens (2048 + 2048 + 620: no in-window call) and 32 output tokens. Server 2 =
`--max-batch 8` (Metal's cap; no MTP there) with `INTARSIA_CB_TRACE=1`: `s4` / `s9` / `s16` = 4 / 9 / 16 closed-loop streams
x 2 requests. Every request: a distinct 430-character slice of the 16k prompt text (113 to 115 prompt tokens, so its prefill
is one in-window call per projection), 256 forced greedy tokens, streamed. Aggregate tok/s = all completion tokens / (last
token - first request sent): the decision metric fixed in section 1.

Round 1 (#9773, A1 B1 B2 A2) ran with the box at thermal pressure 2 for most cells: A visits disagreed by 4.9 % on s1 and
3.5 % on the null cell (over the 3 % bar). Round 2 (#9777, B3 A3 A4 B4) waited up to 180 s for thermal pressure 0 before
every server start and cell; it is the result. All eight visits are in `raw/abba-analysis-all.md` (same direction, noisier).

**Round 2 (cooled), mean of 2 visits per arm** (`raw/abba-analysis-round2.md`):

| cell | A agg tok/s | B agg tok/s | **B / A** | A TTFT p50 s | B TTFT p50 s | TTFT B / A | decode tok/s p50 per request A -> B | spread between visits A / B |
|---|---:|---:|---:|---:|---:|---:|---|---|
| 1 stream (MTP, default engine) | 62.83 | 64.82 | **1.032** | 0.339 | 0.217 | 0.639 | 71.52 -> 71.47 | 0.2 / 0.2 % |
| null: 4k TTFT (no in-window call) | | | | 5.289 | 5.253 | **0.993** | 62.25 -> 62.47 | 0.4 / 0.0 % |
| 4 streams (`--max-batch 8`) | 85.19 | 89.68 | **1.053** | 0.945 | 0.637 | 0.674 | 23.08 -> 23.71 | 0.7 / 1.0 % |
| 9 streams | 80.08 | 81.64 | **1.019** | 1.187 | 0.862 | 0.727 | 11.26 -> 11.09 | 1.3 / 0.4 % |
| 16 streams (8 decode, 8 queued) | 82.12 | 87.99 | **1.071** | 25.52 | 23.82 | 0.933 | 10.61 -> 11.22 | 1.7 / 0.3 % |

Server step ms (`--max-batch 8`, from the `cb-trace-us` Emit / PrefillIter lines inside each cell's window):

| cell | decode iteration ms p50 A -> B | mean gap between Emits A -> B (incl. prefill stalls) | prefill iteration ms A -> B (per visit) |
|---|---|---|---|
| 4 streams | 41.3 -> 40.4 | 46.0 -> 43.9 | 350.4 -> 226.3 (8) |
| 9 streams | 79.7 -> 81.9 | 74.5 -> 73.3 | 340.5 -> 227.2 (18) |
| 16 streams | 87.0 -> 82.3 | 96.6 -> 90.2 | 352.7 -> 224.2 (32) |

1-stream step: the default engine prints no per-step trace; its per-request decode rate (71.5 tok/s, about 14.0 ms per token
with MTP k2) is the same in both arms, as it must be (decode is the GEMV, untouched).

Readings:

* The whole effect is the prefill of a short prompt: **350 -> 226 ms per 115-row prefill** (-35 %; 1 stream TTFT 339 -> 217
  ms), from 496 MXFP4 calls each saving the flat weight decode (the 4-stream / 16-stream prefill iterations agree).
* End to end that is +3.2 % at 1 stream (a 4 s request loses 0.12 s of TTFT), +5.3 % at 4 streams (each prefill stalls the
  other decoders, so the saving counts once per decoding stream), +1.9 % at 9 and +7.1 % at 16 streams. The 9 / 16 ordering
  is not monotonic and the pure decode iteration (untouched kernels) moved by +2.8 % / -5.4 % between the arms at 9 / 16
  streams, so those two cells carry a few percent of noise; 1 and 4 streams have flat decode iterations and spreads under 1 %.
* **Stop rule not hit**: 1, 4 and 16 streams gain at least 2 % end to end. The null cell (4k TTFT, routing never applies)
  is 0.993 with a 0.4 % spread.
* Long prompts do not change: chunks are 2048 rows, so only a remainder of 9..128 rows enters the window (one call per
  projection per prompt; not timed separately).
* Prompt length matters: the cells use 115-token prompts, near the top of the window where the per-call gain is smallest
  (1.2 to 1.9x at M = 96..128 in section 2); a chat-templated one-line request (62 rows) is at 1.8 to 3.1x per call. Not
  measured end to end.

## 5. Leftovers

* A per-shape limit (up to 192 rows on five of the six shapes, 1.07 to 1.27x there) would add a little; not done.
* Batched decode above 8 rows on Metal (the brief's premise) would need a row-exact kernel bitwise the solo GEMV, a
  numerics-class change outside this lane; the in-kernel form here is bitwise the NAX scratch path, not the GEMV.
* The 9 / 16-stream cells carry a few percent of noise (their pure decode iterations moved between arms); a third cooled
  round would tighten them.
* The 35B (NVFP4 / fp8 NAX) has no in-kernel form; untouched.
