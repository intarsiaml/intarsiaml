# Lane mprefill: Metal prefill attribution and in-kernel weight decode for the NAX prefill GEMM (Mac roadmap idea #6, 2026-11-16)

Status: **findings only, stop rule hit at task 2; nothing wired in.** Engine sources in this PR are identical to the base.

* Prefill attribution (section 1): weight decode to bf16 scratch is 5.2 % / 4.4 % of 27B prefill at 4k / 32k (136 ms per
  2048-row pass, not 200) and 1.2 % / 0.7 % on the 35B; with the activation copy into scratch, 7.2 % / 6.1 % and 3.3 % / 2.0 %.
  The 35B's prefill is MoE, GDN and (at 32k) attention, not weight decode.
* An in-kernel decode form of `matmul_mxfp4_nax` was built (4 tile forms) and is **bitwise the scratch path** (W4A16 and W4A4,
  bf16 and f32 out, M / N tails), but it is **slower at M >= 512 on every 27B shape (0.58 to 0.92x) and ties at M = 256**,
  which is the brief's stop rule. It is **2.1 to 3.1x faster at M = 16 to 64 and 1.4 to 1.7x at M = 128**: a bitwise
  small-M win left for a follow-up (section 3).
* Kernel, knob (`INTARSIA_METAL_MXFP4_NAXD`), bitwise test, microbench and the profile split helper are on side branch
  `mprefill-naxd` (`4cb1b8448`), not in this PR.

## 1. Where prefill time goes (task 1)

Method: `generate --spec off`, 2 forced tokens, `INTARSIA_METAL_PROFILE=cb:<file>` + `INTARSIA_METAL_COMMIT_EVERY=1` (one
command buffer per dispatch; the NAX matmul's dispatches split by `with_encoder_parts`), exclusive GPU time per buffer,
prefill phase only (`scripts/mprefill/pf.py`). Job #9741, `raw/pf-split/*.table.txt` (the unsplit run #9739 in
`raw/pf-main/` agrees on totals). Shares are of GPU busy time; the trace's idle time is the one-buffer-per-dispatch
overhead, not engine idle. 35B prefill chunk 4096, 27B 2048 (recipe defaults).

| class | 35B 4k | 35B 32k | 27B 4k | 27B 32k |
|---|---:|---:|---:|---:|
| GPU busy (ms) | 735 | 10217 | 5194 | 49991 |
| NAX GEMM on quantised weights (fp8 / NVFP4 / MXFP4) | 32.1 % | 20.0 % | 79.1 % | 65.6 % |
| **weight decode -> bf16 scratch** | **1.2 %** | **0.7 %** | **5.2 %** | **4.4 %** |
| activation prep (x QDQ / copy to scratch) | 2.1 % | 1.3 % | 2.0 % | 1.7 % |
| attention | 6.3 % | 38.4 % | 2.8 % | 19.4 % |
| GDN (conv, delta rule, gates) | 20.2 % | 13.5 % | 7.5 % | 6.3 % |
| MoE (router, experts, combine) | 33.2 % | 23.0 % | | |
| norms, rope, kv append, silu, copies, embed | 4.9 % | 3.1 % | 3.2 % | 2.7 % |
| **decode + scratch (decode + activation prep)** | **3.3 %** | **2.0 %** | **7.2 %** | **6.1 %** |

Per weight shape (27B 4k, 2 passes of 2048 rows; 32k is 16 passes with the same per-call shares):

| matmul (role inferred from shape and calls per pass) | N x K | calls | x prep ms | w decode ms | GEMM ms | decode / call | GEMM TFLOPS |
|---|---|---:|---:|---:|---:|---:|---:|
| FFN gate, up (2 per layer) | 17408 x 5120 | 256 | 17.7 | 128.8 | 1885 | 0.50 ms | 49.6 |
| FFN down | 5120 x 17408 | 128 | 38.6 | 57.9 | 974 | 0.45 ms | 48.0 |
| GDN in-proj (48 layers) | 10240 x 5120 | 96 | 7.2 | 28.4 | 428 | 0.30 ms | 48.2 |
| o / GDN out (64 layers) | 5120 x 6144 | 128 | 10.1 | 21.7 | 348 | 0.17 ms | 47.4 |
| GDN z (48 layers) | 6144 x 5120 | 96 | 17.5 | 21.7 | 255 | 0.23 ms | 48.6 |
| attention q + gate (16 layers) | 12288 x 5120 | 32 | 2.4 | 11.3 | 169 | 0.35 ms | 48.8 |

35B: the fp8 projections decode in 3 to 4 % of their own call time and their GEMM runs at 39 to 57 TFLOPS; the NVFP4 shared
expert decodes in 3 % of its call, but its GEMM runs at 37 to 51 TFLOPS (512 x 2048, 2048 x 512; 25.5 / 23.3 with the packed K
the trace reports). Neither is a weight-decode problem.

Readings:

* The 27B weight decode is **136 ms per 2048-row pass** (272 ms over 2 passes), not the roadmap's 200 ms (that number was
  the step from the GEMV to the NAX path and included the GEMM reading 4x the bytes). It is 5.2 % of a 4k prefill and
  4.4 % at 32k, where attention grows. Removing it entirely (and the activation copy for the W4A16 calls) bounds the
  solo-prefill win at **about 5 to 7 % on the 27B and 2 to 3 % on the 35B**.
* The decode cost is flat in M, the GEMM is linear, so the share grows as chunks shrink: at a 256-row busy chunk (beside
  decoding streams) the 27B pays 136 ms of decode against about 257 ms of GEMM (35 %).
* The GEMM itself runs at 48 to 50 TFLOPS on the 27B at M = 2048 (lane mgemm's quiet-box figure), so an in-kernel decode
  must hold that rate to win anything at M = 2048.

## 2. In-kernel weight decode for `matmul_mxfp4_nax` (task 2; branch `mprefill-naxd`)

**Build** (`kernels/metal/mxfp4_naxd.metal`, launcher `mxfp4.rs::launch_mxfp4_naxd` on the side branch). A threadgroup owns a
BM x BN output tile and walks K in steps of BK. Per step its threads decode the BN x BK weights (the exact bf16 values
`mxfp4_w_to_bf16` writes) into one of two threadgroup buffers, then the NSG simdgroups run `matmul2d`
(multiply-accumulate) with A read from device memory (the same activation pre-pass as the scratch path, no A staging) and B
from that buffer. Two buffers give one barrier per K step, and the next step's weight words are fetched before the
accelerator runs. The epilogue matches `gemm_nax_fp8_t`. Forms: 64x64 BK 64 on 4 or 2 simdgroups, 128x64 BK 64 / 4,
128x128 BK 32 / 8. Opt-in `INTARSIA_METAL_MXFP4_NAXD=1|f<i>`, default off; test hook `mxfp4::with_naxd`.

**Bits.** `tests/mxfp4_nax.rs::naxd_forms_are_bitwise_the_scratch_path` (#9745 / #9746, `raw/test-naxd1.log`, 5 of 5 tests
pass): every form equals the scratch path bit for bit on 7 shapes (M = 9..300 with tails, N up to 6144, K up to 17408, a
3-row input offset, an unaligned output offset), W4A16 and W4A4, bf16 and f32 out. The microbench's output hashes agree
across all arms in every cell at the 27B shapes. So the accelerator's K order depends on neither the tile nor whether B
comes from device or threadgroup memory. This matches lane mgemm's K-split result (bitwise) and lane mnr's (bits
independent of the K step).

**Speed.** `examples/naxd_bench.rs` (side branch), per `matmul_mxfp4_nax` call: the scratch path (3 dispatches) against
each form. Interleaved rounds with the order rotated per round, a 1 GiB pool of distinct weights, W4A16. Ratios are
scratch time / form time, so above 1 means the form is faster. Run #9749 (`raw/bench1.txt`, M >= 256) was noisy: the
scratch arm ran at 26 to 37 TFLOPS against about 48 in the engine, with wide min-max ranges. Read ratios only, not absolute
TFLOPS. Run #9754 (`raw/bench2-smallm.txt`, M <= 256) was quiet, with tight ranges.

| shape (N x K) | M = 16 | 64 | 128 | 256 | 512 | 1024 | 2048 |
|---|---:|---:|---:|---:|---:|---:|---:|
| gate / up 17408 x 5120, best form | **3.14** | **2.75** | **1.37** | 1.02 to 1.07 | 0.88 | 0.92 | 0.80 |
| down 5120 x 17408, best form | **2.48** | **2.11** | **1.74** | 1.01 to 1.11 | 0.90 | 0.78 | 0.82 |
| GDN in-proj 10240 x 5120, best form | | | | 0.88 | 0.81 | 0.92 | 0.83 |
| o / out 5120 x 6144, best form | | | | 0.88 | 0.79 | 0.83 | 0.83 |

(best of the four forms per cell; at M <= 128 the best is always 64x64 BK 64 on 4 simdgroups; the two M = 256 values per row
are #9749 / #9754.)

**Stop rule hit:** slower than the scratch path at M >= 256 (from M = 512 on every shape, and at 256 on two of four).

**Why it loses at large M.** All four forms, spanning BM 64..128, BN 64..128, BK 32..64 and 2..8 simdgroups, land at about
20 to 30 TFLOPS from M = 512 in the same window where the scratch path's GEMM runs higher. The in-tree staged NVFP4 MoE kernel
(`moe_nax.metal`) runs at about 38 (gate / up) and 32 (down) TFLOPS in the 35B trace. The limit is `matmul2d` taking its B
operand from threadgroup memory behind a barrier per K step, not the tile shape. The shipped GEMM reaches 48 to 50 TFLOPS
only because the primitive streams both operands from device memory itself. At M = 2048 on gate / up the form saves about
0.5 ms of decode and adds about 3 ms of GEMM. A different BK or swizzle does not change that ratio, so no further forms
were built.

**Why it wins at small M.** The scratch decode is flat in M (about 0.5 ms per gate / up call), so below about 200 rows it
dominates each call. The in-kernel form pays decode once per BM rows of output, so it is cheap there.

## 3. What this means for roadmap idea #6, and the small-M case

Corrections to the roadmap's section 2 row 6 and note 6:

* Weight decode costs **136 ms per 2048-row 27B pass**, not 200 ms. The 200 was the GEMV-to-NAX step and includes the GEMM
  reading 4x the bytes. Solo-prefill upside is at most 5 to 7 % (27B) and 2 to 3 % (35B), and the staged form cannot
  collect it at chunk-sized M.
* At a 256-row busy chunk, decode is about 25 to 35 % of a gate / up call, not "most of it", and the in-kernel form only
  ties there. So "about 1.7x beside decoding streams" does not hold for 256-row chunks.
* A form that is bitwise the scratch path keeps prefill in the NAX numerics class and M = 1 on the GEMV. It does not merge
  the classes and does **not** retire `prefill_peel`.

The open case is the bitwise **small-M** win (M = 9..~200, 1.4 to 3.1x per call). Which 27B paths make `matmul_mxfp4_nax`
calls in that range (`mxfp4::nax_ok`: M > 8): batched decode or verify passes of 9 or more rows (`--max-batch` above 8
streams, so every step pays the full-weight decode today), prefill tails (the last chunk's remainder), and busy chunks below
256 rows. Because the form is bitwise the scratch path, routing calls with M < 256 to it changes no output bits and needs no
numerics decision. It still needs the usual served gates and an end-to-end measurement of the 9..16-stream decode step,
which this lane did not run (out of scope; the stop rule ended the build).
