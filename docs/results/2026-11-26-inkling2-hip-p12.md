## Step 0 (no GPU)

- **No prior HIP P12 attempt.** `git log --all -i --grep=p12` and the results docs of every `ink/*` / `archive/*` branch: the only
  HIP hit is `bb5f2407b` ("hip / cuda: list MatmulP12 as not implemented there"); the HIP docs list P12 as "not built"
  (`2026-11-25-inkling2-hip.md:22`, `-hip-mix.md:48`). `ink/hip-batch`'s doc mentions P12 only as the batched plan that drops the
  P12 copies (`model/batch.rs:drop_p12_for_batch`), so batched decode is untouched by this lane.
- **The consultant's claim holds, for the GEMV form.** `kernels/hip/ink_proj.hip:in_proj_gemv_kernel<M>` is a port of CUDA's
  `in_proj_gemv_kernel<M, false>` (`kernels/cuda/inkling2_p12.cu`, the bf16 arm of the GEMV-form twin pair): one wave per weight row,
  lane L sums chunks L, L + 32, ... ascending (8 fmas each in element order), then `ik_warp_sum`. The P12 twin to port is CUDA's
  `in_proj_gemv_kernel<M, true>` arm, not `p12_in_proj_kernel` (the mma form).
- **CUDA's "in_proj P12 off" note is about the mma form.** `quant/p12.rs:pack_in_proj` returns true on CUDA whenever
  `in_proj_gemv("cuda")` is, and that is CUDA's default since brief 31; so CUDA packs and runs the GEMV-form P12 in_proj by default.
  The "unset: off on CUDA ... ALU bound" text of `INTARSIA_INK_P12_IN_PROJ` (`docs/tuning.md:216`) describes the mma-form decision
  (spark1 #11157). That lowers this lane's main risk (the GEMV form's unpack per byte is the same on both). Row not edited here.
- **Every HIP bf16 twin has the same per-output order.** The bf16 GEMVs Inkling-2 decode / verify reaches on HIP are
  `gemv_kernel<1,1,8>` (one row, `INTARSIA_HIP_GEMV` default; the unembed in 3 pieces under dec3 bit 4), `gemv_kernel<M,2,4>`
  (M = 2..8, and 9..16 for wo), `gemv_rows_wide_kernel<M>` (the unembed's rows twin at M >= 9) and `in_proj_gemv_kernel<M>`. In all
  of them a (weight row, activation row) sum is lane L's fma chain over chunks L, L + 32, ... then `ik_warp_sum`; R, U, the block and
  the piece only change scheduling (the masked tail iterations add `0 * 0` to an accumulator that started at +0 and so is never -0).
  One P12 body therefore serves every row count bitwise, and its R / U / grid are free knobs.
- Dispatch stall (dec3): a launch of >= ~1 ms is followed by ~260 us idle. The P12 unembed is 200058 x 3456 B = 691 MB, ~1.10 ms at
  627 GB/s: still over the 950 us trigger, so it is split too (2 pieces). Its `aux` side list is indexed with the global N, so a
  piece passes the global N plus a row offset (not a sliced `aux`).
- Floors today (dec3 window 1 profile, per decode token): in_proj 48 x 63.8 us = 3.06 ms, wo 48 x 23.8 us = 1.14 ms, unembed
  1.44 ms (3 x 481 us after dec3). At 0.75 of the bytes and the same GB/s: -0.77, -0.29, -0.36 ms of a ~13.0 ms step.
