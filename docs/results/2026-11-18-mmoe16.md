# mmoe16: a cheaper 16-row MoE verify pass on Metal (Qwen3.6-35B-A3B NVFP4, endor)

Lane `mmoe16`, branch `mmoe16` from origin/main `7cfe3d885`. Opt-in only: `INTARSIA_METAL_VERIFY16=1`, off by default. Nothing is default-on.
Measured on endor (Apple M5 Max, macOS 27.0), `Qwen3.6-35B-A3B-NVFP4`, tp 1. Every GPU run had its own `fleetq` slot (`--quiet gpu,cpu`); builds used `--load cpu`.
Raw output: `docs/results/2026-11-18-mmoe16/raw/`. Scripts: `scripts/mmoe16/`, adapted from mgdnv's; the cells and table script are mcopy's.

## Verdict

- **Exact: yes.** A 9..=16-token `moe_experts_bf16_rows` call with the knob on is bitwise equal to the T one-token calls and to the knob-off call. This holds for 224 cases / 2800 token rows, including bf16 subnormal, near-2^-126 and near-2^100 activations.
  - Greedy ids: knob on = knob off = `--spec off` in 8 of 8 (copy3k and json-xform, `INTARSIA_SPEC_COPY=20,15`, with GDN verify fuse off and on).
  - `plan show --json` is byte-identical to origin/main with the knob unset and with it set.
  - The whole Metal crate passes: 38 test binaries.
- **Faster: yes, at 16 rows.**
  - Per MoE layer at T = 16, the routed experts take 320 -> 289 us (1.107x, micro, about 61 distinct experts like the real pass).
  - Served speed at `INTARSIA_SPEC_COPY=20,15`, knob on against off (4 ABBA rounds x 3 reps): **copy3k 1.060x, json-xform 1.031x**.
- **len 15 against len 7 on json-xform: a tie, not a clear win.**
  - With the knob (and fused GDN rows in both arms), len 15 is **1.006x** of len 7 on json-xform; the round ratios are 1.039, 0.973, 1.017 and 0.996. Without the knob it is 0.976x.
  - On copy3k, len 15 is 1.138x with the knob, against 1.074x without it.
  - So the knob takes json-xform from a loss to parity. It does not make len 15 a measurable win there.
- **Default-on and the chain-length default stay the user's call.** Neither was changed here.

## What changed

1. `kernels/metal/moe.metal`: `moe_dec_gu_a` / `moe_dec_dn_a` ("9..=16-row calls, arithmetic e2m1 decode" section).
   - These are the fat row kernels `moe_dec_gu_p` / `moe_dec_dn_p`: same grid, threadgroups, rows per simdgroup (2), per-pair work, scale fmas, `simd_sum`s and roundings.
   - Two changes:
     - Each e2m1 code is decoded by bit arithmetic into a half (`nvfp4.metal`'s `nv_x2` trick: code / 2^14), not by a lookup in the `moe_fp4` constant table.
     - The activation block is scaled by 2^14 once and shared by the 4 (gate+up) / 2 (down) weight rows.
   - Why this is exact: (code / 2^14) * (x * 2^14) is the same real number as code * x. So every fma of `moe_blk_dot`'s 16-term chain gets the same exact product and the same addend, and rounds to the same float.
   - The one assumption is that x * 2^14 does not overflow, i.e. |x| < 2^114. The test covers |x| up to about 2^100 and subnormals.
2. `crates/intarsia-backend-metal/src/lib.rs`: `verify16_enabled()` (`INTARSIA_METAL_VERIFY16` equal to `1`, read once) and a test hook `with_verify16`.
   - `src/moe.rs`: the rows branch picks the `_a` kernels when the knob is on and T is 9..=16. Every other call is unchanged: 1 token, 2..=8 tokens, and the grouped prefill path.
3. `docs/tuning.md`: the `INTARSIA_METAL_VERIFY16` row. It states the side scope: a `--max-batch` decode step of 9..=16 sequences uses the same kernel, still bitwise. With the knob set, `INTARSIA_METAL_NEGCTL=moe_*` and `INTARSIA_METAL_MOE_ROWS_FAT=0` no longer reach 9..=16-token calls.
4. `crates/intarsia-backend-metal/tests/moe_verify16.rs`: the bitwise test, the negative control and the `--ignored` timing test.

Not a registered op or kernel: the knob only switches shaders inside the existing `moe_experts_bf16_rows` launcher, so the plan is the same.

## Why the MoE experts, and why this change

After mgdnv's fused GDN rows, the largest share of the extra cost of a 16-row pass is the routed experts (28.8 % of the extra in mrows16k's profile).

Earlier findings:
- The routed experts already run 16 rows in one launch.
- Lane mm found that grouping pairs by expert (reading each expert once) is slower than one threadgroup per pair (`docs/results/2026-10-25-mm-metal-moe-grouped.md`). Even with identical routing it was 216 vs 157 us at T = 8.

So the cost is per-pair arithmetic, not weight traffic.

The per-pair inner loop does a constant-table lookup per weight element. The nvfp4 GEMV kernels decode the same format by bit arithmetic and get about 1.5x the per-element throughput. Removing the lookup is exact and cuts the per-pair cost. That cost grows with the pair count, which doubles at 16 rows.

Variants tried and dropped (`raw/timing-run2-pairmajor.log`, `raw/timing-run3-3arm.log`, `raw/timing-run4-pr.log`):
- A pair-major grid, which puts the pairs that share an expert next to each other in dispatch order: 1.05x at T = 16 against 1.11x for the plain grid.
- 4 weight rows per simdgroup for gate+up and/or down: 1.04 to 1.05x, worse than 2.

The R = 2 fp8 tile of mrows16k was not repeated.

## Gates

**(a) Bitwise unit test** (`cargo test --release -p intarsia-backend-metal --test moe_verify16`, `raw/moe_verify16-final.log`): `MMOE16 bitwise: 224 cases, 2800 token rows equal (knob on == knob off == one-token calls)`.

What it covers:
- T 9..=16.
- Seven routings:
  - random;
  - identical (16 pairs per expert);
  - overlap;
  - invalid ids (-1, E, i32::MIN);
  - a token with no valid expert;
  - duplicates (8 pairs of one expert per token);
  - a 72-expert pool (about 61 distinct experts, like the real pass).
- bf16 and f32 output.
- Weights at offset 0 and 8.
- Activations:
  - normal;
  - tokens scaled by 1e-6 and by 3e4;
  - one token of raw bf16 bit patterns: subnormals (0x0001..0x007F, 0x8001..0x807F), just above 2^-126, around +-2^99..2^100, and signed zeros.
- Every output byte, guards included.

**Negative control** (`verify16_negative_control`): one activation of the last token is changed in the reference (T = 9, 12, 16). About 1890 bytes differ, and only from the last token's first byte on, so the compare is live.

The existing `tests/rows_exact.rs` MoE gate (knob off, 1..=16 rows) still passes as part of (e).

**(b) Greedy ids** (`scripts/mmoe16/ids.sh`, `generate --chat --no-think --temperature 0 --show-ids`, `raw/ids-gate.txt`): **8 of 8 PASS, `ids fails=0` twice.**
- Cells: copy3k (2902 ids) and json-xform (2600 ids).
- Arms: `copy=20,15` and `copy=20,15+on` against `--spec off`, and `+on` against its knob-off twin.
- Run once with `INTARSIA_METAL_GDN_VERIFY_FUSE` unset (`raw/ids-gdnoff`) and once set (`raw/ids-gdnon`).
- The 16-row chain passes are inside the compared ids: 180 chain passes on copy3k and 183 on json-xform, most accepting 15.

**(c) `plan show --json`** (`scripts/mmoe16/plan.sh`, `raw/plan-gate.txt`): **byte-identical.**
- The base binary was built from `git archive 7cfe3d885` in its own target dir and run twice. The new binary was run with the knob unset and with it set.
- All four outputs are 13188 bytes, sha a3bb4203...
- The `INTARSIA_SPEC_COPY` arms differ in `scratch_bytes` only, as on main.

**(d) `cargo test --release -p intarsia-cli --test docs_env_vars`**: pass (`raw/docs-env-vars.txt`).

## Speed

### Per layer: routed experts at 9..=16 tokens (micro)

Test: `timing_moe_verify16` (`raw/moe_verify16-final.log`).

Method:
- 35B shapes: E 256, top 8, H 2048, I 512.
- 24 routings cycled over 4 weight sets (1.7 GB), so most expert reads are uncached.
- Each `time_us` block is 48 calls, best of 3.
- 6 rounds with the arm order alternating; the table shows the median of the 6 per arm.
- "x40" is one pass's routed-expert time.
- T = 8 is the noise floor: the knob does not touch 2..=8-token calls.

| T | routing (distinct experts) | knob off | knob on | ratio | x 40 layers |
|---:|---|---:|---:|---:|---|
| 8 | pool72 (43.3) | 174.0 us | 172.8 us | 1.007x | noise floor |
| 8 | random (57.6) | 200.7 | 200.0 | 1.003x | noise floor |
| 9 | pool72 (47.2) | 192.9 | 182.4 | 1.058x | 7.71 -> 7.29 ms |
| 9 | random (63.0) | 219.9 | 212.9 | 1.033x | |
| 12 | pool72 (53.8) | 244.7 | 226.5 | 1.080x | 9.79 -> 9.06 ms |
| 12 | random (82.0) | 286.3 | 276.0 | 1.037x | |
| **16** | **pool72 (61.1)** | **320.1** | **289.3** | **1.107x** | **12.81 -> 11.57 ms** |
| 16 | random (101.9) | 361.5 | 346.3 | 1.044x | |

Notes:
- The knob-off 40-layer time at T = 16 (12.8 ms) is close to the profile's 13.6 ms of routed experts per real 16-row pass (mrows16k), so the micro is representative.
- The saving, about 1.2 ms per 16-row pass, is consistent with the served gains below.
- Earlier runs of the same micro scatter by up to 30 % in absolute time (`raw/timing-run1.log` .. `run4`, endor's standing services share the GPU). The on/off ratio at T = 16 pool72 was 1.11 to 1.14 in every run that compared the same arms.

### Served: knob off against on, and against len 7

Setup (`scripts/mmoe16/round.sh`, `run-ab.sh`, raw `raw/ab`, `raw/ab-run-r*.log`):
- `serve --max-batch 1 --spec mtp --spec-k 2`, one binary; the arms differ by env only.
- A fresh server per arm and round.
- 4 rounds, each in its own fleetq slot, with the arm order reversed on even rounds (ABBA). 3 reps per cell.
- Greedy, thinking off.
- Every arm has `INTARSIA_METAL_GDN_VERIFY_FUSE=1` (mgdnv's fused GDN rows, opt-in on main), so the comparison is the best available 16-row stack.

Arms:
- `c7` = `INTARSIA_SPEC_COPY=20,7`
- `c15off` = `20,15`
- `c15on` = `20,15` + `INTARSIA_METAL_VERIFY16=1`

Reading the tables:
- Values are decode tok/s medians over 12 reps [min-max].
- The ratio is the median of the per-round ratios of the round medians; the four round ratios are in brackets.
- Reply shas are equal between arms in every round: no `IDS DIFFER`.

Thermal level (`notifyutil`, before -> after each cell): 15 of 24 cell runs ended at 0 and 9 ended at 1 or 2, in every arm.
- json-xform (the second cell) ended at 1 or 2 in 8 of 12 runs: c7 4, c15off 2, c15on 2.

- The 16-row pass is still about 1.8x an 8-row pass. A pass that emits fewer than ~15 tokens on json-xform (mixed acceptance: 138 of 183 chain passes accept 15) still pays for 16 rows.

## Not done / unverified

- **No counter for the path in the served runs.** The `_a` kernels are selected by a two-line condition in the launcher. The unit test runs them through the same `launch` call, and the served speed difference only appears in the knob arm. A debug counter build like mgdnv's was not made.
- The knob covers only the routed experts. Dense fp8, lm_head, shared expert and attention still run as before at 16 rows.
  - The same exact decode would also speed up the 1..=8-token MoE calls (normal decode and the 8-row chain). That was out of scope (opt-in for 9..=16 only), so it was not enabled or measured there.
- Exactness depends on |x| < 2^114 for every activation entering the routed experts. A larger value gives inf where the table path gives a finite product. This is stated in `docs/tuning.md`.
- One machine, one model, greedy only. The 27B has no NVFP4 routed experts, so the knob does nothing there.
  - `--max-batch` 9..=16 decode with the knob was not run. It is the same kernel and bitwise per the unit test.
- Speed: 4 rounds on a shared Mac with standing services. Single cell-rounds scatter by several percent, as noted above.
- `cargo fmt` / clippy were not run (CI does not run them).
- Commits are signed `Co-Authored-By: Claude Opus 5.5` as `scan/lane-rules.md` asks.

## Revert

Unset `INTARSIA_METAL_VERIFY16` (the default): the existing kernels run exactly as before (gate (c), and the knob-off arm of (a)). Reverting the PR removes the two shaders, the knob and the test.
