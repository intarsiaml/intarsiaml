# CUDA round 5: long-context decode, the bf16 split-KV ceiling, and an opt-in fp8 KV cache (2026-10-19)

Target: spark1 (DGX Spark GB10, sm_121, CUDA 13.0), Qwen3.6-35B-A3B-NVFP4. Measured against `origin/main` 916217a4
(round 4 merged, 15c32e9c is an ancestor); rebased at the end onto 49973a51 (HIP and docs only since 916217a4, see
section 13). Raw logs: `docs/results/2026-10-19-cuda-round5/raw/`.

## 1. Headline

- **No default-path speed change ships.** I found no bitwise lever that speeds up the bf16 split-KV decode kernel. The
  default bf16 kernels compile to the same SASS as on main, and their greedy ids and KL21 match main to every digit.
- **vLLM runs an fp8 KV cache.** The flags are `--kv-dtype fp8` (e4m3, scale 1.0; the checkpoint ships no k/v scales)
  and FlashInfer with its own split-KV planning. Per decode step at 16k it reads half the KV bytes we read.
- **Prototype, opt-in only: `--kv-dtype fp8_e4m3`.** This adds three fp8-KV attention kernels.
  - 16k decode: **+4.9 %** in the same-window A/B (72.1 → 75.6 tok/s). localeval gives 75.7, against vLLM's 73.7.
  - 16k prefill: -1.3 %.
  - KL21 stays inside the same-window base range on all four gate runs.
  - **It fails the prefix-reuse gate:** `long_docs_12k continue` scores 8/32 (bf16: 32/32). `chat_reuse_4k` stays 32/32.
  - It is not default-on. Making it default would need a recipe (shared) change and a ruling on that gate. That is
    the decision in section 14.
- **Also done:**
  - compute-sanitizer racecheck now runs in the CUDA test path (`gpu-test.sh`) and in the mutation harness. Round 4's
    surviving `no-loop-sync` mutant is now killed by racecheck (100 hazards).
  - `kernels test --quick` no longer exits 1 when the only problem is kernels without cases.

## 4. Part 2: bf16 split-KV bandwidth (bitwise bar)

**Probe.** `kernels/cuda_checks/kv_stream.cu` (new) reads ten 35B-shaped layer caches in rotation, 335 MB at 16k,
far above L2. Logs: `raw/dev/02-dev-baseline.out`, `05-probe-rand.out`.

| cap | plain stream, 16 B loads | the split-KV kernel's own grid and loads, no math |
|---|---|---|
| 4k | 228.4 GB/s | 244.9 GB/s |
| 16k | 231.6 (memset) / 234.5 (hashed data) GB/s | 235.7 / 231.9 GB/s |
| 32k | 237.7 / 233.9 GB/s | 236.8 / 235.1 GB/s |

- The box reads about **232–238 GB/s**, roughly 85–87 % of the spec figure.
- The split-KV access pattern alone reaches the same rate, so the access pattern is not the limit.
- The data values do not matter: memset and hashed data agree within 1.3 %.

**The kernel, cold** (ten rotating caches, `splitkv_timing` / `f8kv_timing`):

- At 16,026 keys: 166–170 µs per layer, **193–197 GB/s, 83–85 % of the measured rate**.
- At 32k: 314–322 µs per layer, 208–214 GB/s (88–91 %).
- In-engine at 16k it takes 184.5 µs (178 GB/s).
- The 35B instantiation `splitkv_kernel<8,32,2>` uses **255 registers**: one 256-thread block per SM, 128 blocks on 48
  SMs, 2.67 waves.

**Levers tried.** All of the following were bitwise against base (533 cases each) and then dropped. The code is kept on
local branch `perf/cuda-round5-dropped-pipe-hs`.

| lever | result at 16k / 32k (µs per layer, base in the same run) | verdict |
|---|---|---|
| cp.async ring, 2 / 3 / 4 stages (loads 1–3 steps ahead of the math) | 164–170 vs 166–170 / 313–323 vs 314–322 | noise; dropped |
| head-split: 2 × 256 threads, each half holds 4 of the 8 heads (123 registers, 16 warps per SM) | 162.5 / 166.5 vs 166.5 / 167.2; 312 vs 314 / 317 | ≤ 2.4 %, inside the noise; dropped |
| 16-byte vector loads | already used: one `uint4` per thread per key row | n/a |
| fewer combine passes | combine is 6.5 µs of 191 µs per layer (3.4 %) | ceiling 0.06 ms per step; not attempted |
| more splits at long context | changes the partition and with it the fp32 summation order | outside the bitwise bar; not attempted |

**Conclusion.** Cold, the kernel sits at 83–91 % of the measured read rate. The prefetch and occupancy levers did not
move it. The rest is mostly wave quantisation (128 blocks on 48 SMs) and the in-engine overhead (184.5 vs ~168 µs), and
neither can be removed without a new partition. The bitwise ceiling on bf16 is about 1.84 → 1.43 ms per step at 16k;
fp8 moves the floor to 0.72 ms.

## 5. Part 3: fp8 KV cache prototype (opt-in, NOT default)

**What it is.** Three kernels: `attn_decode_f8kv_splitkv`, `attn_prefill_f8kv_splitkv` and `attn_prefill_f8kv_flash`.

- They are the split-KV and flash kernels, templated on the cache element.
- e4m3 K / V are converted exactly to f32 / bf16 on load. Every e4m3 value is a bf16 value, and the arithmetic after the
  load is the bf16 kernels' code.
- So on an fp8 cache the output is **bitwise the bf16 kernels' output on the cache upcast to bf16**.
- The flash path streams the fp8 bytes with cp.async into the upper BK × D bytes of the bf16 tile they become. Where the
  bf16 kernel waits for that tile, each thread reads its own bytes into registers, a barrier follows, and each thread
  writes the bf16 values. This needs no extra shared memory.
- A first version used a separate staging area. It cost +29 % on prefill chunks because occupancy dropped from 3 to 2
  blocks. A synchronous-load version cost +49 %.
- The bf16 instantiations keep their SASS (`sass-diff.sh`: every bf16 kernel in `attention_splitkv.o` and
  `attention_flash.o` hash-identical to main, `raw/dev/08-f8kv-intile.out`).
- The kernels are registered only for an `fp8_e4m3` cache, so the default selection is unchanged. They are selected by
  the existing `--kv-dtype fp8_e4m3` flag, which the KV append already supported.

**Isolated timing** (ten rotating caches, `raw/dev/08-f8kv-intile.out`):

| shape | bf16 | f8 |
|---|---|---|
| 35B decode, 1,034 keys | 17.9 µs | 16.2 µs |
| 35B decode, 4,096 keys | 59.7 µs | 45.4 µs |
| 35B decode, 16,026 keys | 167.1 µs | **112.3 µs (-33 %)** |
| 35B decode, 32,768 keys | 318.8 µs | 208.6 µs (-35 %) |
| 35B chunk, T 2048, 2,048 keys | 611 µs | 675 µs (+10 %) |
| 35B chunk, T 2048, 16,384 keys | 7993 µs | 8895 µs (+11 %) |
| 8B decode, 16,384 keys | 301.7 µs | 159.0 µs |

In-engine, the 16k prefill's flash kernel took 378.2 ms with f8 and 384.5 ms with bf16. At 4k it took 29.3 vs 25.6 ms
(section 8).

**Shared code this touches.** No shared file is modified for fp8 KV; my diff is in `crates/intarsia-backend-cuda`,
`kernels/cuda` and scripts. The opt-in does run these existing shared paths with an fp8 cache:

- the KV slot allocation (`crates/intarsia-core/src/plan.rs`, `SlotSpec::AttnKv` dtype);
- the KV dtype resolution (`crates/intarsia-core/src/model.rs`, `opts.kv_dtype` / `recipe.kv_dtype`);
- the prefix-cache and reuse paths (`intarsia-core` engine), which is where the reuse-gate failure below shows up;
- the CUDA `kv_append` fp8 store (`kernels/cuda/elementwise.cu`, unchanged).

Making fp8 the default would mean changing the recipe's KV dtype for this model, a shared change. So this stops at a
proposal.

| greedy ids, 1,497-token prompt, 256 tokens | reference | identical (graph and eager) | differ at token 25 (graph = eager) |
| `chat_reuse_4k` (continue / restore / aligned) | 32/32, 32/32, 32/32 | 32/32 ×3 | 32/32 ×3 |
| prefix-reuse gate (`long_docs_12k`, `long_code_12k`) | PASS | PASS | **FAIL** |
| 8B fp32 short, dev default | | prefill KL 2.897e-4, decode PASS | |
| 8B fp32 long, dev default | | prefill KL 4.004e-4, decode PASS | |

- **35b-long exits 1 in every arm, base included.** As in rounds 2–4, it fails the class floor of 3.0e-2. The bar is the
  same-window base range, and base matches round 4 to every digit.
- **The f8 reuse failure** is `long_docs_12k continue`: 8/32 tokens equal. The gate's diagnosis, from `raw/r5A/reuse-f8.log`:
  - the streams diverge beyond rounding at token 8;
  - the warm run's margin is 0.005 nats, the cold run's 0.242;
  - the shared rows differ by 0.684 / 0.232 nats.

  The likely mechanism: the warm prefix was prefilled with other chunk boundaries than the cold run. The bf16 K / V
  values then differ in the last bits, and rounding to e4m3 can turn that into a 1-ulp e4m3 step (about 6 %). This is
  inferred, not traced. vLLM has the same exposure with prefix caching on.
- f8's greedy ids are not bitwise against base, as expected for a dtype change. The ids bar applies to bitwise changes.

**Pick: `moe_w4a16_kernel`.** It is a third of prefill at every length, and a bitwise change there can only reorder
loads or tiles, not the per-expert sums. I did not analyse it this round, so I have no number for its headroom. The first
step is a roofline check: bytes and FLOPs per call against its 1.84 ms average.

The second candidate is cheaper and certainly bitwise: fold `fp8_actq` (2.2 %) into the rmsnorm that feeds it, keeping
the bf16 rounding before quantisation. Its ceiling is about 2 %.
