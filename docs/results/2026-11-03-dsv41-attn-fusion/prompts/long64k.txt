# c8k: should the 35B CUDA recipe raise `prefill_chunk` from 2048 to 8192?

Lane c8k, 2026-10-24. Evidence for one user decision; the recipe default is not changed in this PR (`recipes/qwen3_5_moe.toml`
untouched). Follows #125 (fp8-lt default-on, merged `6189466f`); every number below is main `6189466f` (fp8-lt default), CUDA,
Qwen3.6-35B-A3B-NVFP4, GB10 (spark1 and spark2).

## Result

**Recommendation: adopt 8192 for the solo chunk, as a package, not as the one-line recipe edit.** The prefill gain is real and no
accuracy gate moves. But the one-line edit (a) turns `qualify` acc-4k red on CUDA for a structural reason, and (b) makes the batching
engine's busy chunk 8192 too, which lengthens the worst decode pause 1.75x (4k prompts) to 3.3x (16k). Both have a small, measured fix
that this PR does not make (the brief says to change nothing):

1. recipe `[tuning.cuda] prefill_chunk = 8192` (and the explanatory comment above it);
2. `qualify` acc-4k: run its in-run reuse at `min(plan chunk, 1024)` like the separate capped run already does, or drop reuse from that
   `--mode all` run (today: "nothing ran: no prompt can cross a chunk boundary at prefill chunk 8192 ... not a pass", exit 1);
3. busy chunk default `min(solo, 2048)` for the 35B on CUDA (today `--busy-chunk 2048` does this per deployment; measured below);
4. re-record the acc-short baseline at 8192 in the same change (identical numbers, see "Baseline").

If the user prefers not to touch qualify and batching now, the evidence also supports leaving 2048 as it is: the gain is 6-11 % on
prompts of 4k and longer and nothing below 2k changes.

| | chunk 2048 (main) | chunk 8192 |
|---|---|---|
| Solo prefill, 4k / 16k tok/s | 6598 / 6059 | 7023 / 6733 (**+6.4 % / +11.1 %**) |
| Solo prefill vs vLLM, 1k / 4k / 16k | -9.3 % / +2.2 % / -4.8 % | -9.0 % / +8.9 % / +5.8 % |
| Accuracy and reuse gates run by hand (thresholds unchanged) | 1 FAIL in the new 12k s6000 control (below) | **0 FAIL** (table below) |
| `qualify` acc-short / acc-long / acc-4k, real stages | PASS / PASS / PASS (exit 0) | PASS / PASS / **FAIL** (exit 1, structural) |
| Decode stall when a prompt arrives beside 3 decoding streams, 4k prompt (max ITL) | 336 ms | **590 ms** |
| same, 16k prompt | 383 ms | **1264 ms** |
| 4-stream aggregate decode | 96 / 112 tok/s (4k burst / stagger) | 99 / 112 tok/s (no change) |
| Stall with `--busy-chunk 2048` on top of 8192 | | 337 ms (4k), 382 ms (16k): the 2048 values |

What the decision turns on:

1. **Prefill gain is real and reproduces the lt numbers** (+8.9 % / +5.8 % vs vLLM at 4k / 16k here, +8.6 % / +6.4 % in the brief; 3
   interleaved rounds, per-round spread about 1 point). 1k is unchanged (a 1k prompt is one chunk either way).
2. **No accuracy gate moves.** KL goldens, acc-short against main's baseline, acc-4k accuracy and the prefix-reuse gate all pass at 8192
   with no threshold touched. Thinner than the 2048 evidence, stated plainly: the reuse gate at 8192 can only be judged on the two 12k
   prompts (a 4k prompt cannot cross an 8192 boundary), and `long_code_12k` continue has warm/cold 1.71x (limit 1.5x + 3e-3, passes at 71 %
   of the limit).
3. **The qualify acc-4k problem is structural, not numeric.** Its `--mode all` run on the 4k golden (prompts of 4064, 4064 and 4631 tokens)
   needs at least one prompt that crosses a chunk boundary; at 8192 none can, so the gate reports FAIL with "nothing ran". The accuracy
   part of that stage passes (floor PASS). The HIP recipe has the same shape at 4096 and survives only because `chat_reuse_4k` (4631)
   still crosses it.
4. **The cost is the decode stall under batching** (`--max-batch`, opt-in), not decode throughput. Steady-state ITL (p50 21-27 ms) and
   aggregate decode are the same at both chunks. What changes is the worst single gap each time a new prompt is prefilled while others
   decode: one chunk's worth of GEMMs, 336 ms -> 590 ms for a 4k prompt and 383 ms -> 1264 ms for 16k (vLLM, same window, 4k: max ITL
   313-654 ms). The stalls are fewer and longer: total stalled time is about equal (see the ITL section). `--busy-chunk 2048` removes the
   growth in full and keeps the solo prefill gain.
5. **Not covered:** `--busy-chunk 2048` under solo 8192 is not KL-gated (the existing `real_35b_busy_chunk_prefill_kl_gate` hard-codes
   solo 2048 and asserts it); it is by design not bitwise to the solo run, like the shipped 1024 busy chunk. Reuse at 8192 is judged on
   two prompts. The 12k s6000 oracles (below) make a main-side gate look bad at chunk 2048 in a hand-run arm; qualify does not exercise
   it (`q2048` passes).

### Finding: the 2048 s6000 control (a FAIL that is not an 8192 result)

`long_docs_12k` continue at its default split 6000 against the new s6000 oracle fails at chunk 2048 (`ru2/reuse-L2048.log`): the cold run
is 3.7e-3 from the oracle, the warm (prefix-restored) run 7.9e-2, 21x, limit 8.6e-3. Without an oracle for that split the gate judged the
same case by greedy agreement only (`32/32 ok`), so this was not visible before the new oracles. `reuse-diag` on the same prompt
(`raw/gates/rd`) says it is not a restore defect:

| Run (long_docs_12k, split 6000) | mean KL(oracle \|\| cold) | mean KL(oracle \|\| warm) | Rule |
|---|---:|---:|---|
| chunk 2048 | 3.74e-3 | **7.93e-2** | FAIL (limit 8.60e-3) |
| chunk 1024 (what `qualify` uses) | **8.48e-2** | 6.20e-3 | PASS (limit 1.30e-1) |
| chunk 2048, `long_code_12k` | 2.46e-3 | 1.97e-3 | PASS |

At chunk 2048 the engine's own diagnostics for these 32 rows: cold chunk 2048 vs cold chunk 1024 mean KL 4.2e-2 (max 1.22, one argmax
flip); warm vs cold at the same chunk 4.5e-2; cold 2048 vs cold 2047 4.4e-3; cold 2048 vs cold 4096 bitwise identical; each run
repeated is bitwise identical (deterministic). So for this prompt the logits of the 32 rows move by about the oracle distance when only
the chunk schedule changes: whichever run lands on the far side of an unstable position is the one "far" from the oracle (cold at 1024,
warm at 2048). The oracle-relative rule (warm <= 1.5 x cold + 3e-3) passes when cold is the far one and fails when warm is. That is my
reading of the diagnostics, not proven by a bisect of the unstable position. It is the same class as the long_docs_4k near-tie of gc2,
at 12k. Not touched: the rule, its factors, the oracle.

Consequence for this PR: `golden/oracle` now holds a reference that a hand-run reuse at chunk 2048 and default split fails. `qualify`
on main's tree passes with it present (`q2048`, exit 0: its reuse runs are capped at 1024), so nothing on main's gates turns red, but
anyone running `accuracy --mode reuse --prefill-chunk 2048` on the long golden with this directory will see that FAIL. The s6000 files are
in their own commit (`c8k: continue oracles s6000 ...`) so the user can drop them with one revert; I did not.

## Decode stall under batching (ITL, 4 streams)

`scripts/c8k/itl-window.sh`, spark2, `--max-batch 4`, no vLLM, retro up and idle (0 running requests recorded before each visit),
3 interleaved rounds. localeval's `--concurrency` reports aggregate and per-stream decode only (no ITL), so `scripts/c8k/itl4.py` reuses
its client and prompt method and keeps every inter-token interval. Two scenarios, 4 streams of ~4k (and ~16k) tokens:
**burst** (all four start together: three prompts prefill beside the first stream's decode) and **stagger** (A decodes; B, C, D arrive 1.5 s
(4k) / 4 s (16k) apart, each prefilling beside the decoders). ITL = gap between streamed tokens, pooled over all streams.

## 2. What changed

**(a) Row tables (HIP kernels in `kernels/hip`).** One launch per layer and op for all rows of a step, instead of one per row. The kernels take
the table of device addresses of `OpCall::rows` (`u8 [rows, stride, 8]`, the same contract as CUDA's) and, where the row's position matters,
the positions of all rows on the device (`pos`, `i32 [rows]`):

| kernel (`row_table` in the registry) | twin of | grid |
|---|---|---|
| `gdn_conv_bf16_rows` | `gdn_conv_bf16` (T = 1: conv and state update in one kernel) | `.y` = row |
| `gdn_delta_rule_bf16_v2_rows` | `gdn_delta_rule_bf16_v2` (T = 1), state at table entry plus byte offset | `.z` = row |
| `kv_append_bf16_rows` | `kv_append_bf16` | one thread per (row, head, vector) |
| `attn_decode_bf16_splitkv_rows` | `attn_decode_bf16_splitkv` with a device position (the one-row decode grid) | `.z` = row, scratch for `rows` rows |
| `rope_bf16`, position per token | `rope_bf16` | `pos` of numel T > 1: token t at `pos[t]` |

Each is the one-row kernel's code with the row's pointers taken from the table, so row r is the one-row launch on sequence r alone
(`tests/row_tables.rs`, section 5). The solo step runs the fused `gdn_conv_delta_bf16` and `gate_split_qk_norm_rope_kv_bf16`; the batched step runs
the chains of those folds with the row-table kernels, which the fusion table proves equal (`crate::fusion` gets HIP entries for
`GateSplitQkNormRopeKv`, `QkNormRopeKv` and `GdnConvDelta`, each naming its existing bitwise test; `QkNorm` and `Rope` join the row-parallel ops of
the batch-consistency check; `GateSplit` may run once over all rows or once per row). `model/batch.rs` does not use the per-sequence fold when
row tables run (a launch bound to one sequence's cache cannot be in a batched graph).

**(b) HIP graphs per batch size.** No new code: `Backend::supports_graphs` is already true on HIP, and the generic batched-graph path of rb3
(`graph_step.rs`, one graph per row count, row tables rewritten before each replay) engages as soon as the step has no per-row launches left.
The A/B above is the measurement. The `moe_block` kernel's sync counters are reset by the kernel itself, so replaying it in a graph is safe
(`moe_block_graph_replay_is_bitwise_eager`, an existing test, passes).

**(c) `moe_block_bf16_rows`.** `moe_block` fuses top-k, routed experts, shared expert and combine in one launch, but only at `T * K <= 16`, i.e.
T <= 2 at top-8: steps of 3 or more rows ran the unfused chain (about 7 launches per layer). Every role of the kernel already works on one
token, so lifting the bound to T <= 16 (`ik_moe_block_bf16_rows`, registered `rows_exact`, same kernel code, only the shape check differs) keeps
each token bitwise the T = 1 launch on it alone: `moe_block_rows_are_the_solo_block_per_token` compares 1,252 tokens over 168 launches (T = 1..16,
six shapes including the 35B's top-8 of 256, norm on and off, with routing ties) with T = 1 blocks, plus a negative control per launch.
The batched step could not take it before: the block is only tried when the shared-gate logit was already computed by the router pair, and the pair
is a one-row kernel. In `quant/moe.rs` a batched pass now computes the gate logit with its own GEMV (the second half of the pair, a registered
equivalent) first, when a row-exact `MoeBlock` is selectable (`OpRunner::fused_available`, asked only with batching on and a row-exact pass, so
nothing changes with batching off, section 5). **The model takes it for 3 and 4 rows only** (`MOE_BLOCK_ROWS_MAX` in `quantmoe.rs`): past
that it is slower than the unfused chain (section 4). The kernel itself stays row-exact for 1..16.

**(d) Multi-row fp8/nvfp4 GEMVs: not touched.** hb measured them ALU-bound past 4 rows; the profile below says why they are the next lever and what
they cost (section 4), and no change was made.

**Device sampling** stays opt-in (`INTARSIA_DEVICE_SAMPLING=1`, user decision 2026-10-23 17:57) and is not ported: HIP has no `topk_rows`
(`supports_topk` is false), and the speed matrix is greedy, where it changes nothing.

**Shared crates.** `plan.rs`: `admit` leaves row-table kernels to their base's admission (they cannot be graded with table-less cases) and queues
the base kernel of a twin that no planned call uses, to be tested by its sweep (section 6); `GateSplit` joins `WIDE_OR_PER_ROW_OPS`, `QkNorm` and
`Rope` join `ROW_PARALLEL_OPS`; unit test `batch_check_accepts_hip_folds_per_row_or_as_row_table_chains`. `fusion.rs`: the three HIP entries.
`model.rs` and `quant/moe.rs`: `OpRunner::fused_available` and the gate-logit-first path above. `model/batch.rs`: eight lines. All inert on CUDA
and Metal (no `MoeBlock` kernel there; section 5).

## 3. Method

* Speed: `intarsia serve --backend hip --model Qwen3.6-35B-A3B-NVFP4 --max-seq 8192 --max-batch 16` in the dev container on card 0, then
  `localeval speed --url http://tatooine:8294/v1 --model intarsia --thinking off --sizes 1024 --gen 128 --reps 3 --concurrency 4,16` (and
  `--sizes 4096 --concurrency 4`), inside the fleetq job (`--takes-down radiance --quiet gpu,cpu`). Main and branch are built by the same
  command into separate cargo target volumes and served one after the other in the same job, so there is no drift between them; every arm is a

  sources, and the serve binary's op list was checked from the model-loop test (`OPLIST`).

## 4. Why the numbers are what they are

Step profile of the final tree (`real_35b_batch_step_profile`, each op synchronised, so the wall is longer than the real step; ms per step):

| B = 16 (op time sum 54.95 ms) | calls | ms | share |
|---|---|---|---|
| matmul_fp8 (attention and GDN projections) | 130 | 14.17 | 25.8% |
| moe_experts (unfused chain, rows kernel) | 40 | 13.76 | 25.0% |
| matmul_nvfp4 (shared expert and lm head) | 121 | 7.61 | 13.9% |
| matmul (bf16: router, gate logit) | 140 | 6.03 | 11.0% |
| gdn_delta_rule | 30 | 3.90 | 7.1% |
| rmsnorm_add | 80 | 1.79 | 3.3% |
| attn_decode, gdn_conv (now one launch per layer) | 10, 30 | 1.41, 1.05 | 4.5% |
| moe_topk, silu_glu, moe_combine, gated_rmsnorm, rope, qk_norm, the rest | | 5.2 | 9.5% |

At B = 4 (wall 23.9 ms profiled): moe_block 6.8, matmul_fp8 5.6, matmul 3.2, rmsnorm_add 1.8, gdn_delta_rule 1.7, nvfp4 0.7, the per-row ops 2.2.

* **Row tables** remove the per-row launches of five ops: before, B = 16 meant 16 launches of each of conv, delta rule, append, rope, qk_norm and
  attention per layer; now one. The remaining cost of these ops is 8.7% of the B = 16 step.
* **The fused MoE block is slower past 4 rows.** Uncapped (all rows 3 to 16 through `moe_block_bf16_rows`) the model-loop step was 23.73 ms at 8 rows
  (22.21 ms without) and 47.57 ms at 16 rows (41.75 ms without, window 7), +7% and +14%: the fused block reads each token's experts separately, while the
  unfused `moe_experts_bf16_rows` shares an expert's weights between the rows routed to it (about half the expert reads at 16 rows). At 3 and 4 rows
  the fused block still wins (12.11 to 11.63 ms, 13.83 to 13.61 ms; 4 streams +4.5% served), so the cap is 4. Raw logs for both runs are in `raw/`.
* **(d) is the next lever.** At B = 16 the fp8, nvfp4 and bf16 GEMVs plus the expert chain are 76% of the profiled step; the fp8 GEMV alone is 25.8%
  (109 us per call). hb found these kernels ALU-bound past 4 rows (they decode the weights once per row-tile), which the profile does not
  contradict (the fp8 time grows 2.5x from B = 4 to B = 16 while the bytes read stay the same). A tensor-core (WMMA) multi-row fp8 kernel that is also
  bitwise the one-row GEMV is a different kind of change (the accumulation order is part of the contract) and was not attempted here.
* **Served vs model loop.** At 4 streams the model loop does 13.6 ms per step (294 tok/s aggregate) but serve delivers 213 tok/s, i.e. 18.8 ms per
  step; at 16 streams 41.6 ms against 62 ms. So 5 to 20 ms per step is not in the model-loop step. Where it goes (scheduler and engine thread, per-row events and SSE, detokenising,
  the host side of the batched step, prompt prefills of staggered streams inside the burst) was not profiled here, so it is an open point, not a finding.

## 6. Things found on the way

* **The tests run without admission; `serve` does not.** The first `serve` of the branch failed at load with `no kernel for kv_append ... [admitted
  kernels only]` while every G-B and G-C test was green: a row-table twin takes the admission of the kernel it twins
  (`Registry::effective_admission`), and on HIP the plan never selects the base (the solo step runs the fused op), so the base stayed untested.
  Same trap as rb3's first lesson. Fixed in `plan::admit` (queue the base, test it by its sweep). The load line then reported the row-table kernels
  as `REJECTED` (the plan-shape admission graded them with calls that carry no table); it now skips them like the sweep does, and the load line has
  no `REJECTED` (39 kernels checked, 636 cases).
* **`INTARSIA_ROW_TABLES=0` failed to load on HIP** once the fusion table had the `GateSplitQkNormRopeKv` entry: the per-sequence fold, expanded to
  its chain, counted `gate_split` B times where the rule wanted once. Fixed (`GateSplit` in `WIDE_OR_PER_ROW_OPS`) with a unit test for both forms.
* **The HIP attention tests iterate every kernel of an op** and so called the row-table attention kernel without a table (`IK_ERR_INVALID_ARG`);
  they skip `row_table` kernels now, as CUDA's do. Found by the full-suite run, not by the targeted ones.
* **A batched step with the fused MoE block changed `plan show` with batching off** (a `moe_block` scratch of 18,432 B instead of 9,216 B): the new
  gate-logit-first path was also taken by solo steps of two rows (prefill tails, `fused_ok` accepts `T * K <= 16`). Restricted to batched passes
  (`batch_rows >= 2` and row-exact); the no-op gate is what caught it.
* **Pre-existing failure on `origin/main`:** `cargo test --release -p intarsia-backend-cuda --test rows_registry` fails two tests on the Mac
  (`ordinary_calls_pick_what_they_picked_before_the_rows_kernels` at `rows_registry.rs:178`, `exact_rows_calls_pick_the_rows_kernels_only` at `:186`).
  This branch has no diff in `crates/intarsia-backend-cuda` or `kernels/cuda`, and `origin/main` has not moved since the branch point, so the
  test binary is main's. The pin tables show why: they still expect `matmul_fp8_gemm_reg` / `matmul_fp8_pair_gemm_reg` where main now selects
  `matmul_fp8_gemm_lt` and no pair kernel (the fp8 cuBLASLt default of #125). Not touched here.

## 5. Is the engine's decode path wrong?

All offline, on the three engine dumps. The dumps hold the engine's top-64 only, so this estimator reads lower than the gate's
(decode scored 0.2915 here against 0.3397 in the gate); every comparison below uses the same estimator on both sides.

| quantity (118 scored decode rows) | mean | bootstrap 95 % |
|---|---:|---|
| engine decode vs bf16 golden | 0.2915 | [0.113, 0.534] |
| engine prefill vs bf16 golden, same rows | 0.2192 | [0.093, 0.416] |
| HF bf16 vs f32, same rows | 0.2527 | [0.120, 0.430] |
| engine decode vs engine prefill, same rows | 0.1619 (median 0.007) | [0.082, 0.263] |
| paired: engine decode minus HF noise | +0.039 | [-0.059, +0.166] |
| paired: engine decode minus engine prefill | +0.072 | [-0.012, +0.178] |

* **Not distinguishable from the reference's own spread at this sample size.** Dropping `chat_multiturn` (5 rows) gives 0.2155
  against noise 0.1974 (1.09x). Dropping it and `long_prose_700` gives 0.1135 against 0.0681 (1.67x) on 97 rows of small absolute
  size; engine prefill on those rows is 0.0518. So the engine's decode rows sit above its prefill rows and above one HF spread
  draw on the ordinary rows too. One draw of a heavy-tailed spread cannot say more than that.
* **The decode path itself is right in W4A16.** Same engine, same GDN recurrence, attention, KV cache and state: decode KL
  8.3e-4 against the W4A16 golden (M1) and 6.0e-4 (T2). Only the W4A4 activation rounding is added.
* **Why decode and prefill differ in W4A4:** under W4A4 every MXFP4 product is exact (T2 section 3), so the engine's two paths differ only in
  how the non-MXFP4 ops (norms, attention, GDN step) round to bf16. Rounding activations to fp4 turns a one-ulp difference at an
  e2m1 near-tie into a whole step (M1 section 5). Engine decode against engine prefill is 0.16 mean with a median of 0.007: a few
  rows flip, the rest agree. That is the same mechanism, at the same size, as HF bf16 against HF f32.
* The W4A4 noise envelope of section 6 (chunk 256 -> 64) moves the decode mean by 5e-3 relative: the engine is near-deterministic under that perturbation, so it does not measure the activation-rounding sensitivity of section 5; the decisive control for "engine noise class" stays the engine-vs-engine row above (0.16, median 0.007).

## 1. DFlash in one page

Target Qwen3-8B (36 layers, H=4096, 32 q heads, 8 kv heads, head_dim 128). Draft: 5 dense Qwen3 layers (same shapes,
`intermediate_size` 12288, qk-norm, rope theta 1e6 neox), all `full_attention`, **non-causal**, plus `fc` and `hidden_norm`.

**Features from the target.** `target_layer_ids = [0, 8, 16, 24, 32]` are 0-based layer indices. The tap is the *output* of
layer i, i.e. the full residual stream after that layer (attention and MLP adds both applied), before any final norm.
(z-lab: `_LayerHook` stores the layer output; vLLM's `eagle_aux_hidden_state_layer_ids = [1, 9, 17, 25, 33]` is the same
five tensors seen as the input of layer i+1.) For every target position t, `feat_t = concat(out_0, out_8, out_16, out_24, out_32)`
in that order, 20480 values. Prefill positions and every verified position produce features.

**Context projection (shared by all 5 draft layers).**
`h_ctx = hidden_norm(fc(feat))`, `fc` is [4096, 20480] no bias, `hidden_norm` an RMSNorm.
For draft layer l: `K_ctx = rope(k_norm(k_proj_l(h_ctx)), pos)`, `V_ctx = v_proj_l(h_ctx)`, at the target's absolute
positions. Note the context rows do **not** pass through the layer's `input_layernorm`, only the shared `hidden_norm`.
These K/V persist in the draft's own KV cache (5 layers x 8 kv heads x 128 x 2 x bf16 = 20 KiB per token).

**Block decode (one forward per round). Corrected after the MLX reference run (section 10.3).**
Let P be the number of context rows, equal to the position of the anchor token `b` (the last committed token, which the
target has not yet been fed). The query block is `[b, MASK x 14]` (`mask_token_id` 151669), **15 rows** (`dflash_config.block_size
= 15`) at positions P..P+14. Per layer: `x = embed(tokens)`; `x += o_proj(attn(input_layernorm(x)))`; `x += mlp(post_attention_layernorm(x))`;
the query rows' own K/V (same projections, qk-norm, rope at P..P+14) are appended **after** the context K/V and attended
with **no causal mask** (every query row sees all context and all block rows). Final `norm`, then `lm_head` on **all 15
rows, the anchor row included** (`sample_from_anchor: true`): row r predicts the token at position P+r+1, so row 0 (the
anchor) drafts the token right after the anchor. **15 drafts, 16 verify rows.** (The z-lab convention of taking rows 1..15
gives tau 1.04 with this checkpoint: it is the wrong layout here.) The block K/V are scratch: the next round overwrites
positions P'.. with real context K/V.

**Verify (unchanged from MTP/ngram).** Target forward on `[b, d1..d15]` (16 rows = `LOGIT_ROWS`), longest-prefix greedy
match, commit accepted + 1 bonus, roll the target KV back. The next round's context is the features of the rows the verify
produced for the committed positions (anchor row plus the accepted rows).

Geometry note: `block_size = 15` is the number of query rows and of drafted slots; `sample_from_anchor: true` means the
anchor row is sampled too; `causal: false` is the non-causal block attention. (Whether the query block has 15 or 16 rows
(one extra unused mask row) is a statistical tie on the reference, tau 3.298 vs 3.261; we use 15, which is also cheaper.)

## 3. Corrector math (from the paper, section 4.2-4.3 and App. A, G)

Per drafted slot i = 1..B (B = 15): hidden state `h_i` (4096), top-K draft candidates `c_ik` and their draft logits
`l_i(k)`, K = 16. Let E be the (frozen) token embedding, `LN` a non-affine LayerNorm, `LN_gb` an affine one, r = 128.

```text
b_ik = LN(W_cand E[c_ik])                     W_cand  [r, d]        = dcoco.cand_proj
g_i  = LN(W_ctx  h_i)                         W_ctx   [r, d]        = dcoco.ctx_h_proj
z_ik = LN_gb(W_fuse [b_ik ; g_i])             W_fuse  [r, 2r]       = dcoco.cand_ctx_proj, ctx_out_norm
s_p  = W_pair [h_p ; h_{p+1}]                 W_pair  [r, 2d]       = dcoco.pair_proj        (p = 1..B-1, once per slot pair)
S_p(a,b) = l_{p+1}(b) + MLP([s_p ; z_pa ; z_{p+1,b} ; l_p(a) ; l_{p+1}(b)])      MLP: 386 -> 256, GELU, 256 -> 1
```

The MLP's output layer was zero-initialised in training, so at initialisation S_p(a,b) = l_{p+1}(b) and the selection below
reproduces DFlash's argmax. Selection (prefix-first greedy, eq. 7): `k_1 = argmax_k l_1(k)`, then
`k_{p+1} = argmax_b S_p(k_p, b)`. The draft block is `c_{p,k_p}`. Complexity: (B-1) K^2 = 3584 scores in the paper's
batched pass, O(B K) for the walk. Verify is the unchanged linear verify.

Implementation plan, no extra drafter pass:
- The walk only ever needs row `a = k_p` of S_p, so it can be run lazily: 14 steps x 16 candidates = 224 MLP evaluations
  instead of 3584. cpu-ref and the first CUDA version do exactly that.
- MLP layer 1 is linear in its concatenated input, so split `W0 = [Ws | Wa | Wb | w_la | w_lb]` (128, 128, 128, 1, 1
  columns; **column order is an assumption**, section 8): `pre = Ws s_p + Wa z_pa + Wb z_{p+1,b} + w_la l_p(a) + w_lb l_{p+1}(b) + bias`.
  The three 128->256 projections are done once per slot or per candidate (Matmul), the pair grid is a broadcast add, so the
  per-transition work is a 256-wide GELU and a dot. This reuses existing ops; no new GEMM kernel is needed.
- Greedy exactness: the corrector only changes *which* tokens are proposed. Verify is the target's own greedy argmax, so
  the committed ids are the target's regardless of the corrector's numerics (the paper's lossless claim, and the same
  argument as MTP). Stochastic (App. G): the proposal is a point mass `p_j = 1[v = y_j]`, accept with probability
  `q_j(y_j)` (min(1, q/p) with p = 1), on rejection resample from `q` restricted to `v != y_j` and renormalised. We only
  ship greedy, so this stays out of scope until the engine has stochastic spec.
- Paper numbers to compare against (Qwen3-8B, B200, vLLM, T=0, thinking off, ten-suite average, concurrency 1): vanilla
  265.6 tok/s, DFlash 783.1 (2.95x, tau 3.913), DCOCO 959.7 (3.62x, tau 4.985); gain +18-23% at batch 1, narrowing with
  concurrency. tau there = accepted drafts + 1.

## 4. Mapping onto this repo

Grounded in `crates/intarsia-core` at origin/main cf84efa43 (read in this phase; line numbers will drift).

| piece | existing seam | what is new |
|---|---|---|
| mode | `spec.rs` `SpecMode {Off,Ngram,Mtp}`, `SpecConfig::parse`, `SPEC_K_MAX = 6` | `SpecMode::Dflash`. `SPEC_K_MAX` is 6 because of the 8-row GEMV cliff; DFlash needs k up to 15 (16 verify rows = `LOGIT_ROWS`, `VERIFY_MAX_ROWS = 16`). Dflash gets its own `DFLASH_K_MAX = 15`, others unchanged |
| drafter | `model/mtp.rs` (`mtp_draft`, own `MtpState` with a pending queue and its own KV) | `model/dflash.rs`: loads the draft, owns a 5-slot draft `SequenceState`, ingest queue, block forward |
| verify, accept, rollback | `Model::forward_verify`, `engine.rs` `spec_verify / spec_accept / spec_cut`, `st.truncate` for attention-only models | **unchanged** |
| gate / back-off | `SpecGate`, `CostGate` (`spec.rs`) | the tap must keep recording on back-off (plain decode) steps; ingest is lazy (queued features), so a back-off step costs one 40 KB/token copy and the context never has holes |
| target tap | `Model::run_layers` loop (`model.rs`, two ping-pong residual buffers, pending-add, fused norms) | copy the post-layer residual (pending add included) of layers 0, 8, 16, 24, 32 into a `[rows, 20480]` staging buffer. | attention | `AttnPrefill/AttnDecode`, contract "causal GQA" (`ops.rs`), `OpAttrs` has `window` only | new attr `causal: bool` (default true, not printed by `plan show` when true) so the default plan is byte-identical; non-causal variant for q_len = 16 over kv_len = P + 16 on cpu-ref and CUDA |
| draft layers | no generic small-transformer runner (`mtp.rs` is a bespoke MoE layer) | dense Qwen3 `Block::Attn + Block::Dense` already loads via `recipes/qwen3.toml`; reuse those blocks with weights from the draft dir, plus `fc`, `hidden_norm`, and the K/V-from-`h_ctx` projection (existing Matmul + QkNorm + Rope + KvAppend ops) |
| lm_head / top-K | `Logits`, `Argmax` ops | phase 2 needs `Argmax` on 15 rows; phase 3 needs top-16 values and ids per row (new op, cpu-ref + CUDA) |
| corrector | none | `dcoco.*` weights, host-side lazy walk first, GPU later only if profiling asks for it |
| batched | `--spec mtp` is refused with `--max-batch > 1` (LOG 2026-10-25 12:57) | same refusal for dflash; "4 streams" needs a decision (section 9) |

Costs and risks specific to the engine:
- **16-row verify exactness on CUDA.** The MTP doc's bitwise result covered at most 4 rows, and the `SPEC_K_MAX` comment
  records an 8-row GEMV cliff. The exactness gate (dflash ids == spec-off ids) is only as good as 16-row verify
  == 1-row decode, bit for bit. First step of phase 2 is a probe (below), before any drafter code.
- **Tap off-by-one is silent.** A wrong layer index or a pre-add tap still passes exactness and just lowers acceptance. Gate:
  per-slot argmax and tau against an independent reference.
- **Prefix reuse and reset.** Draft KV is per sequence; any prefix-cache hit, truncate or sequence reset must reset or
  truncate the draft KV to the same position (MTP has the same obligation in `MtpState`).
- **Chunked prefill.** Features of each prefill chunk are ingested as the chunk finishes (never stored for the whole prompt:
  8k tokens x 40 KB = 320 MB).

### 10.1 G1: 16-row CUDA verify probe (Qwen3-8B BF16, spark1 GB10, fleetq #5441, #5447)

`Model::verify_check` runs each id window through q single-row decode steps and through one `forward_verify`, from the
same state, and compares the f32 logits. Windows: q = 2..16 at contexts 17, 130, 513, 1024, 1900, 3000 (random ids) plus 24
windows of 16 ids that are the model's own greedy continuation (all accepted case). 1194 rows in all.

| config | windows with a logit difference | worst abs logit diff | argmax mismatches | verify16 / decode1 (len 1024, 12 passes, probe timing only) |
|---|---|---|---|---|
| default (multi-row `AttnPrefill` in verify) | 78 of 120 | 3.79 | 3 (random ids) | 79.3 / 66.9 ms = 1.19 |
| `INTARSIA_CUDA_VERIFY_ATTN_PER_ROW=1` (one `AttnDecode` call per row) | **0** | **0** | 0 | 88.7 / 67.0 ms = 1.32 |

(`raw/g1-verify16-probe.log`, `raw/g1-verify16-probe-perrow-attn.log`.) Finding: on the dense 8B the CUDA multi-row verify
attention is **not** bitwise the decode step from about 100 context tokens on (exact up to length 17 for every q, and at 130
for every q except 16; from 513 even q = 2 differs), while the `_rows` GEMV kernels are exact (all differences vanish when
only attention is changed). So the existing CUDA `--spec ngram` on the dense 8B can in principle flip a greedy id at a
near-tie; this is a pre-existing property, the 35B MTP gate did not see it. The fix is the existing HIP mechanism
(`Backend::verify_attn_per_row`: one decode call per row, exact by construction). CUDA now answers it from an opt-in
env var (default off, so nothing changes for the existing modes); DFlash will switch it on for its own verify through a
Model-level flag, so the ~8 h row-exact-kernel contingency is not needed. Cost: verify16 is 1.32x a decode step instead of
1.19x, so the break-even tau rises from about 1.4 to about 1.55 (draft included); G5's threshold (tau >= 2.5) is unchanged.

### 10.5 `--spec ngram` on CUDA (coordinator question: is it exact on the dense 8B?)

Not reachable: `--spec ngram` is refused on CUDA at load ("--spec Ngram needs the Metal backend without tensor parallelism
(backend cuda, tp 1)", `crates/intarsia-models/src/load.rs`; 18 of 18 runs of the 16 prompts plus the short and 4k prompts
exited with that error, `raw/ngram-k4-ids.log`). So no CUDA user can hit the multi-row verify attention through ngram, and

The finding of section 10.1 does matter for the other speculative mode that is allowed on CUDA, `--spec mtp`: its verify

128 and 1024 context; a model with more attention layers or longer contexts is the case the dense 8B probe says can flip a
near-tie argmax. Not measured here (no dense MTP checkpoint on spark1 besides the 27B, which belongs to another lane). Cheap
mitigation if wanted: switch `Backend::verify_attn_per_row` on for CUDA when `--spec mtp` is on (cost measured in section 10.1:

## Why lane hb saw "no output"

The gate prints nothing until it ends, and on HIP it runs every N from 2 to 16. That is 135 rows x 130 steps = 17,550 solo reference
steps of the dense 8B. Each one streams the 16.4 GB of bf16 weights at about 26 ms (about 630 GB/s, the card's bandwidth), so the solo
reference alone takes about 460 s. The batched steps take another 110 s. Lane hb stopped the test at 8 minutes (480 s, fleetq #4592),
before it could end. The 188% CPU it reported fits a host that is busy launching and waiting on the GPU, not a stuck host loop. For comparison, the
hybrid 35B gate, with the same pair count, finishes in 205 s: about 3B active parameters in NVFP4 make its solo step several times
cheaper.

Control run, so that the result does not depend on later HIP work (row tables, batch graphs, new rows kernels). The tree the guard
was added to (f3b9f19e5, the parent of 1ff822ac9, no guard yet) ran the same test unchanged, with a 25-minute cap (fleetq #5363):

progress lines only; no assertion changed.

# hg: the served-vs-in-process decode gap on HIP (2026-10-25)

Lane hg, Qwen3.6-35B-A3B NVFP4 on one R9700 (tatooine, `serve --backend hip --max-batch 16`, base `origin/main` 73ac1bbf for the measurements, 2c2d9941 for the gates). Follows [hr3](2026-10-24-hr3-hip-batching-r3.md) (PR #127). Branch `lane-hg/hip-serve-gap`, PR #133.

Machine-readable trace: [trace.json](2026-10-25-hg-hip-serve-gap/trace.json). Raw logs and scripts: `2026-10-25-hg-hip-serve-gap/raw/`, `scripts/hg/`.

## 1. Result

**There is no host-overhead gap to close.** hr3 left 212.6 / 257.1 tok/s served at 4 / 16 streams against 294 / 385 in the in-process step test and put the difference down to "5-20 ms per step outside the model step". Measured with a per-phase host timeline of the serving scheduler, that is wrong:

| 16 streams decoding, 35B | served | in-process step test |
|---|---|---|
| decode-only iteration | **42.2 ms** (256-iteration window) | 41.6 ms |
| steady aggregate decode | **375.6 tok/s** (15 streams: 378-389) | 385 tok/s |
| GPU idle between two decode steps | **0.025-0.030 ms** | |
| host work outside the model step (prepare, accept, detokenize, SSE send, metrics) | **about 0.07 ms** per step (0.2%) | |

The remaining 2.4% between 375.6 and 385 is within the 15-stream run-to-run spread (378.1 / 382.3 / 387.5 / 389.4 on four server starts) and 16 against 15 rows.

The gap is the metric. `localeval speed --concurrency` divides all generated tokens by the wall time of the whole burst (`speed.py:133`), and that wall contains the prefill of every prompt. With the hr3 doc's own numbers (991-token prompts at about 6.1k tok/s prefill, 128 decode steps of 41.6 ms at 16 rows and 13.6 ms at 4 rows):

| streams | prefill (N x 991 / 6.1k tok/s) | decode (128 x step) | predicted wall | predicted tok/s | served (hr3) |
|---|---|---|---|---|---|
| 4 | 0.65 s | 1.74 s | 2.39 s | 214.3 | 212.6 |
| 16 | 2.59 s | 5.33 s | 7.92 s | 258.6 | 257.1 |

Both within 1%. The 16-stream burst spends 2.6 of 7.9 s in prefill, one prompt at a time.

The radiance lead (native 1.11.0, device-side speculative acceptance, cb5a69a) was not inspected at the commit; it targets speculative acceptance, and intarsiaml's greedy batched path has no per-step host sampling to move (argmax runs on the device, 64 bytes come back) and only 0.07 ms of host work per step. What exists on HIP: nothing of either. `INTARSIA_DEVICE_SAMPLING=1` (`model/batch.rs:159`) needs `Backend::supports_topk`, which only the CUDA backend overrides (`intarsia-backend-cuda/src/device.rs:295`; default false at `backend.rs:319`), so it is a no-op on HIP; `INTARSIA_OVERLAP` (`engine/batch.rs:59-61`) is documented CUDA only. Neither affects this greedy benchmark (argmax runs on the device) and neither was changed.

## 0. Scope note (written before any code)

### What the model runs at 5 to 16 rows today

`MOE_BLOCK_ROWS_MAX = 4` (`crates/intarsia-backend-hip/src/quantmoe.rs`), so from 5 rows the model takes the unfused chain of
`crates/intarsia-core/src/quant/moe.rs` `forward_folded`. Counted from the source and the hr3 OPLIST (`w7-step-profile.log`, `batch16`):

| op (per layer) | kernel | launches at 16 rows (8 rows) |
|---|---|---|
| router, shared-gate logit | `matmul_bf16_gemv_rows` x2 | 2 (2) |
| `moe_topk` | `moe_topk_bf16_v2` | 1 (1) |
| `moe_experts` | `moe_experts_bf16_rows`: `moe_group_kernel`, `moe_gate_up_kernel`, `moe_down_kernel`, `moe_reduce_v8_kernel` (P = T*K > 16, so the grouped path, 8 pairs per weight pass) | 4 (4) |
| shared gate, shared up | `matmul_nvfp4_gemv_rows`, rows in groups of at most 4 (`kRowsGroup`, `nvfp4.hip`), each group re-reads and re-decodes the weights | 8 (4) |
| `silu_glu` | `silu_glu_bf16` (the fused `nvfp4_glu_kernel` is M = 1 only) | 1 (1) |
| shared down | `matmul_nvfp4_gemv_rows` | 4 (2) |
| `moe_combine` | `moe_combine_bf16` (`SharedDownCombine` is M = 1 only) | 1 (1) |
| total | | **21 (15)** |

The fused `moe_block_bf16_rows` (`moe_block.hip`) replaces everything after the two logit GEMVs with one launch, but it reads every
token's 8 experts separately (no sharing between tokens that pick the same expert) and runs the shared expert once per token. hr3 s4: it
wins up to 4 rows and loses past that (23.73 vs 22.21 ms at 8 rows, 47.57 vs 41.75 ms at 16).

The unfused `moe_experts_bf16_rows` is **already grouped by expert** (the counting sort in `moe_group_kernel`, weights read once per expert and
chunk of 8 pairs, per-pair arithmetic independent of the grouping, so token-exact). The plan's "block that groups tokens by expert" is
therefore mostly there for the routed part. What is not grouped is everything around it.

### Where the ms are (hr3 `real_35b_batch_step_profile`, B = 16, every op synchronised, 54.95 ms op sum, 41.6 ms unprofiled step)

| piece | profiled ms/step | note |
|---|---|---|
| `moe_experts` (routed, 4 launches x 40) | 13.76 | bandwidth floor: about 100 distinct experts x 1.77 MB (gate_up 1.125 MB + down 0.56 MB incl. scales) x 40 = 7.1 GB; at the 585-627 GB/s measured read peak (`2026-10-13-hip-decode.md`) 11.3-12.1 ms, so at most about 1.1-1.5 ms is left in the kernels themselves |
| shared expert: `matmul_nvfp4` 120 of 121 calls | about 4.6 (the 121st, the lm head, is about 3.0 at 16 rows per the `nvfp4.hip` comment) | 38 us per op profiled; a 0.5 MB weight is 1 us of traffic, so this is launch, tail and the 4x re-decode, not bandwidth |
| `moe_topk`, `silu_glu`, `moe_combine` | 0.99 + 0.79 + 0.77 | mostly the per-op sync price (about 17 us per op: (55.6 - 41.6 ms) / 814 launches) |

Not claimed: the profile syncs every op, so the sum overstates what graph replay pays. The plan's own bound for the routed part was about 4 ms; the
kernel-only part of that is smaller (about 1.1-1.5 ms) if the 100-distinct-experts figure holds for real routing, which the profile does not record.

### What I will change

One new kernel entry, `moe_block_bf16_grouped`, registered for `Op::MoeBlock` for 5..16 rows (`rows_exact`), so the model's existing
"gate logit first, then MoeBlock" path in `quant/moe.rs` takes it with no model change. Inside, a short chain of launches instead of a
ticketed megakernel (no cross-block spin synchronisation to prove deadlock-free):

1. `topk + group`: one block computes every token's top-k (`wave_topk`, the arithmetic of `moe_topk_v2_kernel`) and builds the expert-sorted pair
   table (`moe_group_kernel`'s output), writing ids and weights.
2. shared gate + up + silu for all rows in one pass over the weights (weights decoded once, one accumulator set per row, the lane order, the
   16-element fma chain and the warp sum of `nvfp4_gemv_v2_kernel` per row, then `nvfp4_glu_kernel`'s epilogue rounding).
3. routed gate_up and down (the existing grouped kernels, unchanged arithmetic) and `moe_reduce_v8`.
4. shared down + combine epilogue for all rows in one pass (`shared_down_combine_kernel<1>`'s arithmetic per row).

21 launches (15 at 8 rows) become about 8 including the two logit GEMVs. Every token's accumulation order is the order of the T = 1 block (each piece
copies an already row-exact kernel's arithmetic), so it stays bitwise; `tests/moe_block.rs` is extended to compare 5..16 rows against the T = 1
block, with a negative control. The fused `moe_block_bf16_rows` stays for 1..4 rows (it wins there).

### Expected gain (central estimate, to be replaced by the microbench)

What a removed launch is worth is not known well. Two data points disagree: `2026-10-19-p2prime-moeblock.md` s3 measured 3.9 us for a tiny
1-block launch inside a graph replay (T = 1), while hr3's fused block at 3 and 4 rows (12.11 to 11.63 and 13.83 to 13.61 ms) removes about 9 launches
per layer (360 per step) for a net 0.5 and 0.2 ms, i.e. only 0.6-1.3 us net per removed launch (the fused kernel has costs of its own).

| lever | ms per step at 16 rows (8 rows) |
|---|---|
| 13 fewer launches x 40 layers, at 0.6-1.3 us net each | 0.3-0.7 (0.2-0.4) |
| shared expert: one weight pass instead of 4 (2); 120 `matmul_nvfp4` ops at about 21 us real each (38 us profiled less the sync price) | 1.0-1.5 (0.4-0.8) |
| routed kernels: not targeted in this phase (bound 1.1-1.5 ms) | 0 |
| **total** | **about 1.3-2.2 ms of 41.6 = 3-5% model loop (8 rows: 0.6-1.2 of 22.2 = 3-5%)** |

The bar is served tok/s, not the model-loop step: hr3 s4 has 62 ms served against 41.6 ms in the model loop at 16 streams (the served burst includes
the prefills). 3% of served tok/s at 16 streams is about 1.9 ms per step (8.1 s burst wall x 3% / 128 steps), so the **go line is 1.9 ms
of model-loop saving at 16 rows**, and the central estimate above straddles it. The first GPU window is therefore a microbench, with existing kernels only
(`moe_rows_timing` in `tests/moe_block.rs`, T = 5, 8, 12, 16, graph replay, 16 layers): (a) the unfused chain as the model runs it, (b) topk + experts,
(c) the shared pieces + combine, (d) one `matmul_nvfp4_gemv_v2` launch at M = 4 per shared matrix as an optimistic floor for a single 16-row weight pass,
(e) a tiny launch, (f) the fused rows block, plus the distinct experts per layer. Available saving is about (c) - 3 x (d) plus the launch delta. **Build
only if that reaches about 1.9 ms at 16 rows; otherwise the lane stops there and reports.**

### Constraints for the build

* The shared-expert arithmetic is copied from `moe_block.hip`'s own copies of the `nvfp4_glu_kernel` and `shared_down_combine_kernel<1>` epilogues, not
  from `gemv_rows` + `silu_glu` + `moe_combine` (lane 1 option B may move those). The new op is tested against the T = 1 block and the unfused chain.

### 0.1 The kernel today

`f8_gemm_kernel<WN, WM, TN, TM, OutT>` (`kernels/hip/ik_f8_gemm.h`, called from `matmul_fp8_mma_f8` in `fp8.hip`; row-major weights
by default, the `frag` layout is opt-in `INTARSIA_HIP_FP8_FRAG`). W is the A operand (output features), the pre-quantised e4m3
activations the B operand.

| M, N | tile (weights x tokens) | block | wave tile | LDS (static) | used by (35B, M = 4096) |
|---|---|---|---|---|---|
| M >= 2048, N >= 8192 | 256 x 128 `<4,4,4,2>` | 16 waves (512 threads) | 64 x 32 | 2 x (256 + 128) x 80 B = 61,440 B | qkv / q+gate |
| M >= 2048, N < 8192, >= one block per CU | 128 x 256 `<4,4,2,4>` | 16 waves | 32 x 64 | 61,440 B | z, out_proj, k / v |

| M <= 64 | 128 x 16 / 32 / 64 | 4 waves | | small | not prefill |

Pipeline: 64 k bytes per stage, one `__syncthreads` per stage, global -> registers (issued at the start of the stage) -> LDS (at its
end), LDS double buffer, one 16 B `ds_read_b128` feeds two WMMAs. Resources from the compile (`raw/w0/f8bench-res.log`,

|---|---:|---:|---:|
| 256 x 128 `<4,4,4,2>` | 150 | 8 | 61,440 B |
| 128 x 256 `<4,4,2,4>` | 148 | 8 | 61,440 B |
| 128 x 128 `<4,2,2,4>` | 153 | 6 | 40,960 B |

The stage loop of the 256 x 128 kernel (`raw/w0/ref-4442-loop-tail.s`) already issues the WMMAs lo-all / hi-all with both 32-k groups'
fragment reads hoisted, and ends every stage with `s_wait_loadcnt 0x0`, `s_barrier_signal`, `s_barrier_wait`, `global_inv scope:SCOPE_SE`.

### 0.2 What a bitwise change can and cannot touch

One output element is a chain of `v_wmma_f32_16x16x16_fp8_fp8` on one accumulator, in increasing k, where each WMMA sums the 16 products of the 8 + 8 k bytes the two lane halves hold (per 32-k group, lo WMMA = bytes
0..7 and 16..23, hi WMMA = bytes 8..15 and 24..31), then one multiplication by `weight_scale * input_scale`.

* Cannot change: which k enter which WMMA, the order of the WMMAs on one accumulator, a second accumulator per output (split-k or a
  partial-sum tree), the epilogue arithmetic, the activation quantisation (`f8_actq_kernel`), hipBLASLt itself (its internal order
  is not ours; it is a different set of bits, so it is out).
* Can change: block / wave tile, how many waves, the LDS layout (swizzle instead of padding, stage size), the global-load distance
  and register / LDS staging, the order in which *independent* accumulators are issued, `s_barrier` placement, instruction
  scheduling, the epilogue's store pattern. Tile changes were already shown bitwise by hp (21 tiles x 11 shapes, partial M too).

| kernel (tile weights x tokens, waves) | qkv 4096x8192x2048 | z 4096x4096x2048 | o 4096x2048x4096 | kv 4096x512x2048 |

What moved the number (w1, w2, w4):

* Two stages of global loads in flight (a second register set; stage k + 2 is loaded while stage k is consumed): +6..13 %. Three or
  four stages: no further gain (4 stages equal 2; 3 is worse, an odd count makes the LDS buffer index dynamic).
* LDS-only barrier (`fence(workgroup, "local")` + `s_barrier`, the pattern radiance's `lds_barrier()` uses) instead of
  `__syncthreads()`: +1..5 % with two stages in flight, 0 with one. The reference loop ends each 64-k stage with
  `s_wait_loadcnt 0; s_barrier_signal; s_barrier_wait; global_inv scope:SCOPE_SE` (`raw/w0`, ISA of the 256x128 kernel): every
  stage drains the load queue and invalidates the L0 / L1 lines. This is the cause of "pf1 gets nothing, pf2 gets it".
* The XOR-swizzled 64 B LDS row (no padding) with the swizzle matched to 32 LDS banks (`(row >> 1) & 3`): neutral to +3 % and
  saves 20 % of the LDS (49 KB instead of 61 KB at 256x128, so 256x256 fits in 64 KB). My first swizzle assumed 64 banks and was
  15 % slower than padding (`raw/w1`), which is how the bank count was found.
* The 256x256 tile: +0..12 % over 256x128 on o / z / kv, but at M = 1024 N = 512 it is 2-3x slower (too few blocks); it would need
  a dispatch rule like hp's.
* Issue order of independent accumulators (lo-all then hi-all) and reading both 32-k groups up front: 0 (the compiler already
  emits the lo-all / hi-all order, `raw/w0`).
* Clamped, unpredicated global loads (radiance's trick to keep loads in flight across merges): **slower** (162 vs 194 at qkv),
  because the compiler spilled the load ring to scratch (`raw/w4/f8bench-res.log`, 48..208 B/lane). One attempt, not pursued
  (see the two-attempt rule; the assumption that might be wrong is that the compiler keeps the multi-stage ring in registers
  without scratch once the predicates are gone).

## 2. Side finding (outside this lane): `__syncthreads()` is expensive in gfx12 main loops

On gfx12 `__syncthreads()` is a workgroup acquire / release fence over all address spaces: the ISA shows `s_wait_loadcnt 0`
before and `global_inv scope:SCOPE_SE` after every barrier (only the 256x128 fp8 kernel's ISA was checked: `raw/w0/ref-4442-loop-tail.s`).
Other software-pipelined HIP kernels in `kernels/hip/` with one barrier per k-stage (the WMMA GEMMs, the MoE kernels, flash attention)
likely pay it too (check each one's ISA), and it limits any global-load distance greater than one stage. The fix is a local-scope fence plus
`__builtin_amdgcn_s_barrier()` (see `bar()` in `scripts/l8/f8v.h`), valid wherever the barrier only orders LDS traffic.
This lane measured +1..5 % on the fp8 GEMM from it alone; the MoE GEMM (36-46 % of hipBLASLt) has not been tried.

fp8 rows gate fail. Batching off is byte-identical to main (no-op below): `matmul_fp8_gemv_rows` is selected only for

## What changed

`matmul_fp8_gemv_rows` (the fp8 projections of the batched step: attention q/k/v/o, GDN in/out projections, about 30%
of the B = 8 step after step 1) at **5..=8 rows** now runs on 8x8 float simdgroup matrices (`fp8_rows_mmt_{bf16,f32}`,
`kernels/metal/fp8.metal`), after a pre-pass `fp8_xprep_t` that writes q(x) of all rows block-transposed (`xt[u][k][m]`,
bf16, zero-padded to 8 rows) into the call's scratch.

Why it is row-exact. Two facts measured on endor (`raw/probe/probe*.swift`, 262144 and 4 x 131072 elements):

1. `simdgroup_multiply_accumulate` on float 8x8 equals, bit for bit, the per-element chain `c = fma(a[i][k], b[k][j], c)`
   for k = 0..7 from c: all elements equal on wide-range, subnormal-producing, inf/NaN/-0 and cancellation data (NaN
   positions identical). Reversed k order or `c + chain(0)` do not match (141813 / 191569 of 262144).
2. `simd_sum` equals the xor butterfly 1, 2, 4, 8, 16 (4096 / 4096), i.e. the pairwise tree over lanes 0..31 in index order
   (the 16..1 butterfly matches 1581 / 4096, a sequential sum 1275).

The one-row kernel's value for (row m, output n) is: lane l sums the 16-term fma chains of blocks u = l, l + 32, ... in
that order (`fp8_dot16`, NaN when the block holds a NaN code), then `simd_sum`, then the scale. The new kernel computes
block u's chain for 8 outputs x 8 rows as two MMAs from 0 (k = 0..7, then 8..15; fma commutes in its multiplicands, so
`W x q(x)^T` gives the same chain per element), sets a block whose weight row holds a NaN code to NaN, and adds it to the
accumulator of class u mod 32. The 8 simdgroups of a threadgroup take classes 4s..4s+3 and fold them ((0+1)+(2+3)), the
threadgroup folds the 8 results ((0+1)+(2+3))+((4+5)+(6+7)): the same pairwise tree. Same scale expression and rounding.

Operand layout (measured): a lane's two elements of an 8x8 matrix are row `(lane & 16 ? 4 : 0) + ((lane >> 1) & 3)`,
columns `((lane >> 3) & 1) * 4 + (lane & 1) * 2` and `+ 1`. With weights as the left operand a lane's weight bytes are two
adjacent bytes of one row (one ushort load), its activations two adjacent rows of one k (one uint load).

Selection: the kernel is padded to 8 rows, so it costs the same at M = 2 as at 8, while `_xd` adds a 4-row tile at M = 5.
It takes M >= 5. `INTARSIA_METAL_FP8_ROWS_MMT=0` turns it off, `=N` (2..=8) moves the threshold (the gate runs it at 2).
`INTARSIA_METAL_NEGCTL=fp8_mmt` swaps the two MMAs of a block (k = 8..15 first): the gate must fail.

Scratch of `matmul_fp8_gemv_rows`: `max(M, 8) * K * 2 + 16` bytes (was `M * K * 2 + 16`).

|---|---:|---:|---:|---:|---:|
| 8192 x 2048 | 50.8 | 52.6 | 62.3 | 52.5 | -16% |
| 4096 x 2048 | 34.1 | 28.8 | 34.5 | 28.9 | -16% |
| 512 x 2048 | 10.4 | 8.9 | 10.5 | 8.9 | -15% |
| 2048 x 4096 | 36.4 | 32.2 | 36.1 | 32.2 | -11% |

For scale, the one-row kernel at M = 1 reads 8192 x 2048 in 27 us (about 620 GB/s), so the new kernel is still about 2x
the weight-streaming floor at 8 rows.

## What changed

Three row-exact kernels for the batched step (`forward_batch`, 2..8 rows), each keeping every row's arithmetic, order and
roundings of the one-row kernel:

1. **fp8 `matmul_fp8_gemv_rows`, `_xd` form** (`kernels/metal/fp8.metal`, `fp8_gemv_{bf16,f32}_m4_xd`). The staged form
   had every threadgroup re-quantize all 8 activation rows into 32 KB of threadgroup memory (`q(x)` of 8 x K per threadgroup,
   and the 32 KB capped the threadgroups per core). Now `fp8_xprep_bf16` writes `q(x)` of all rows once into the call's
   scratch, and the GEMV reads it straight from device memory with a 4-row tile (4 measured faster than 8 or 2 at every 35B
   shape). Same expression, same fma chain per row. `INTARSIA_METAL_FP8_ROWS_XD=0` takes the staged form back.
2. **MoE `moe_experts_bf16_rows`, fat threadgroups** (`kernels/metal/moe.metal`, `moe_dec_gu_p` / `moe_dec_dn_p`). One
   threadgroup row per (token, slot) pair, a simdgroup covers 2 weight rows of the pair's expert (was 1), the activation
   block is loaded once for both. `INTARSIA_METAL_MOE_ROWS_FAT=0` takes back mb's kernels.
3. **nvfp4 `matmul_nvfp4_gemv_rows`, narrow matrices** (`crates/intarsia-backend-metal/src/nvfp4.rs`). Matrices of at
   most 4096 rows (the shared experts, 512 / 2048 rows) run the one-row shader over a grid of M threadgroup rows; the 8-row
   shader gave them only 32 / 128 threadgroups. `INTARSIA_METAL_NV_ROWS_SPLIT=0` keeps the 8-row shader.

Profiling: `INTARSIA_METAL_PROFILE=kernel` now labels every dispatch of a multi-dispatch launch (`<kernel>#n`) and gives
the fp8 / nvfp4 weight shape and the MoE routing (distinct experts, pairs). New test `real_35b_batch_step_real_traffic`
(`crates/intarsia-models/tests/batch_metal_real.rs`, ignored) and analyzer `scripts/mm/kprof.py`.

## Why not "read each expert once"

The brief asked for an expert-grouped kernel, so each expert's weights are read once per step. mb's `_x` kernels already
do that: a leader pair serves up to 8 pairs of its expert (`moe_lead`, `MOE_XR = 8`). Ablation of the same fat kernel
(gate-up 2, down 4 rows per simdgroup) with 8 / 4 / 2 / 1 pairs per leader (`raw/logs/micro2.log`, `timing_rows`, T = 8,
us per call, mean of 2 reps):

| pairs per threadgroup row | random | identical routing | overlap |
|---|---:|---:|---:|
| mb `_x` (1 row / simdgroup, 8 pairs) | 357 | 235 | 308 |
| fat, 8 pairs | 243 | 216 | 234 |
| fat, 4 pairs | 215 | 194 | 200 |
| fat, 2 pairs | 207 | 181 | 190 |
| fat, 1 pair | 212 | 157 | 168 |
| fat, 1 pair, 2 / 2 rows (shipped, `micro3.log`) | 199 | 161 | 167 |

With random routing 1, 2 and 4 pairs are within the spread; with shared experts 1 pair wins clearly. Grouping saves little
DRAM traffic here (only 27% of pairs share an expert, and the second read of a block comes from the
cache when the pairs run at about the same time), and it serializes the pairs of an expert in one threadgroup. In the
real step, 1 pair per threadgroup row was 0.6 ms faster at B = 8 than 8 pairs (23.8 vs 24.4 ms, `raw/logs/step2.log`).
The win came from fatter threadgroups (2 rows per simdgroup: fewer threadgroups and leader scans, more loads in flight),
not from grouping. 2 rows beat 1 / 4 / 8 rows for both gate-up and down (`raw/logs/micro3.log`).

## Hypotheses

* **GatedDeltaNet recurrent per-seq loop: killed.** `gdn_delta_rule` is one row-table launch per layer for all sequences (48 calls/step), 8.8 ms at 16
  rows = 0.55 ms per sequence. The recurrent state is 149 MiB per sequence (plan note), read and written once per step: 0.31 GB per sequence
  at the ~600 GB/s the card streams = 0.52 ms. So it sits at the byte floor; the only lever is the state size/precision, not the loop. `gdn_conv`
  is 1.4 ms and flat.
* **Attention rows: killed (small).** `attn_decode` 3.6 ms at 16 rows = 0.23 ms per sequence for ~64 MB of KV each (65,536 B/token, 1k tokens): 2x the
  byte floor of 0.11 ms, 3 % of the step. Would matter at long context, not here.
* **lm_head rows: confirmed, and it is a cliff, not a slope.** micro-timing of `logits_bf16_gemv_rows` (248320x5120 bf16, raw/micro.log): M=1 4.24 ms
  (599 GB/s), 2 4.26, 4 4.34, 5 4.43, 6 4.45, 8 4.50, **12 7.85, 16 16.70 ms (152 GB/s)**. The same shape as the MXFP4 GEMV before #145: a kernel
  that is fine to 8 rows and loses its register budget above. Ideal at 16 rows is ~4.5-5 ms.
* **Pair launcher's two launches: killed.** At M >= 2 `matmul_mxfp4_pair_gemv_rows` is two launches of the rows kernel (the M=1 LDS fusion does not apply). The
  step has 176 pair calls; two launches instead of one at graph-replay gaps of at most 2-3 us bounds the effect at 0.5 ms of a 59-111 ms step
  (<1 %, an estimate). The pair op's time is the GEMV time of its two members (gate/up 17408x5120 twice: 2 x 272 us at M=16 in the micro-timing).

## MXFP4 GEMV at 8-16 rows: ALU estimate (not confirmed)

Rows kernel micro-timing (17408x5120, raw/micro.log): 80.4 us at M=1, 156.4 at M=8, 274.6 at M=16, i.e. 12.3-14.7 us per extra row, while the weights
(45 MB) are read once. 89.1 M weight elements per row in 12.5 us is 7.1 T fma/s; add the bf16 unpack shared by two weight rows (about half an op per fma)
and it is ~10.7 T VALU lane-ops/s. A single-issue R9700 lane rate is about 4096 lanes x ~2.9 GHz = 11.9 T/s (clock is an assumption; the advertised TFLOPS
counts dual issue). So the kernel would be running at roughly 90 % of single-issue VALU, and more rows then cost proportionally. This arithmetic is an
estimate; the check that would confirm it (instruction mix in the ISA, VOPD dual-issue use, or counters) was queued (fleetq #5260, cpu-only) but not run
because tatooine was held exclusively by another job; `scripts/mr/isa.sh` is in the branch for whoever runs it.

Row-exactness limits the options: the per-row summation order (one sequential fma chain per 32-element group, then a fixed warp-sum) must stay, which rules
out WMMA/dot-instruction accumulation unless the M=1 path changes with it (that changes bits against main: a user decision, not made here).

## Ranked levers (nothing implemented, per the brief)

1. **`logits_bf16_gemv_rows` above 8 rows** (bf16 lm_head, kernels/hip/matmul.hip `gemv_dispatch<M>`): the same cliff #145 fixed for MXFP4. Micro: 4.5 ms at M=8, 7.8 at 12, 16.7 at 16 (ideal ~4.6). Profiled
   step: 15.0 ms at B=16 against ~4.5 achievable, so about 10 ms of the 111 ms step (~9 %: 144 -> ~158 tok/s aggregate at 16 rows) and ~3 ms of the 83 ms step at 12 rows.
   Cheapest fix on the list: the register-shape pattern from #145, row-exactness is the same argument (per-row lane order unchanged), one launcher, one test case in `rows_exact`. Whether the cause is a spill
   should be checked first with `scripts/mr/isa.sh` (its second half prints VGPR/spill per `gemv_dispatch` M; not run). This is lane wg's file family (bf16 small-row), so coordinate before touching it.
2. **MXFP4 GEMV ALU cost** (69 % of the step): needs fewer VALU ops per fma without changing the summation order. Candidates, each to be checked in the ISA first: packed/dual-issue use on gfx12,
   cheaper fp4 -> f32 decode (the LUT/convert shared by 2 rows already), sharing the bf16 unpack across 4 weight rows for M <= 4 only (4 rows spilled above 6 in #145, so only a per-M choice helps).
   Upside is bounded by the ALU floor; a 15 % GEMV gain is ~10 % of the step. Larger gains need the numerics decision above.

Everything else: GatedDeltaNet and attention sit at their byte floors (killed above), the flat tail is 8 % of the step.

## Served vs bare step

localeval at `--max-batch 8` (PR #145 doc): 61.5 tok/s aggregate and 11.6 tok/s per stream at 8 streams. The bare 8-row step is 59.5 ms = 16.8 tok/s per
stream, 134.5 aggregate. localeval's figure includes the streams' 1k-token prefills (~1 s each at ~980 tok/s, serialised) and scheduling between
steps, so about half the served gap to the step is outside the model step. That is a serve-loop question (lane hg's serve-gap work), not
an MXFP4 kernel one, and sets the ceiling for what step-time fixes can show in the served numbers: a 15 % faster step moves a prefill-diluted
benchmark far less than 15 %.
