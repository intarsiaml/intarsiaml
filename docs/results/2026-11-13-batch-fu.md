# batch-fu: follow-ups of the batched prefix store (#353)

Lane `batch-fu`, branch `batch-store-followups` on `origin/main` `10b235785`. Brief, as given:

> PR #353 (merged) added prefix-store restore/capture to the 2-slot batched engine (`--max-batch 2 --prefix-store on`). Follow-ups:
> 1. Macro workspace stays reserved: the store turned macro prefill off after the workspace was allocated (1537 MiB against 537 MiB
>    with `INTARSIA_PREFILL_MACRO=0`). Decide it before allocation.
> 2. Restore runs before validation: a bad token id or a structured-output error was still looked up and restored before `admit`
>    refused it. Validate first.
> 3. The speculation refusal (explicit `--spec` + store + `--max-batch` > 1) fires only after the model loads. Refuse before the load.
> 4. Stale `serve.rs:73` comment ("as before").
> 5. The `INTARSIA_PREFIX_STORE_DEBUG` row of `docs/tuning.md` lacks the `admission` settle site.
> 6. `PrefillStart` reports the busy chunk while a store request runs the model chunk.
>
> Not touched: settle placement (`fail_active`, cancel-while-queued, settle off the scheduler thread: lane `interleave`) and
> `crates/intarsia-core/src/prefix_store.rs` (branch `store-writer-bound`, which also owns the "confirms them. every restore"
> capital in `docs/tuning.md`).

## Changes

1. **Macro off before allocation** (`crates/intarsia-models/src/load.rs`, `load_engine_group`): with `--max-batch` > 1 and a store
   configured, `LoadOptions::prefill_macro` is set to `Some(0)` before `Model::load`, so the workspace is planned for the model's
   chunk. An explicit `INTARSIA_PREFILL_MACRO` (which `store_combinations` still refuses above 0) or a caller's
   `LoadOptions::prefill_macro` is left alone. One stderr line says the recipe's macro prefill is off. `store_combinations` keeps
   its `set_macro_rows(0)` for a model loaded another way; its workspace line is unchanged.
2. **Validate before restore** (`scheduler.rs`, `engine.rs`, `engine/batch.rs`): new `BatchSeq::validate` (default `Ok`), asked
   before `restore`; the adapter checks the token ids and the structured-output constraint (`Seq::check_constraint`, which `Seq::admit`
   now shares). A request that fails it skips the lookup and the restore and is rejected by `admit` as before (same `Rejected` trace
   and metric). In the engine a bad token id is already refused by `submit`; the structured-output error was the reachable case.
3. **Early speculation refusal** (`crates/intarsia-cli/src/cmd/serve.rs`, `run`): `--max-batch` > 1 with an explicit `--spec` other
   than `off` and a store (the flag, or `INTARSIA_PREFIX_STORE`) bails before the supervisor and the model load, like
   `--prefix-store-pin`. `BatchedEngine::new` keeps its check for library callers.
4. The `serve.rs` doc comment on `--prefix-store` now says the refusal (at `--max-batch` > 1, before the load) and that
   `--max-batch 1` serves it as before.
5. `docs/tuning.md`: the `INTARSIA_PREFIX_STORE_DEBUG` row lists `admission` (the batched engine's backstop). The `prefill start`
   site is called the single-sequence engine's. The store row is untouched.
6. **`PrefillStart` chunk**: new `BatchSeq::own_chunk` (default `None`; the adapter returns the store schedule's chunk); the
   scheduler reports it in the event (the adapter's own `chunk` was already right).
