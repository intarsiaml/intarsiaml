Facts the script fixes that the old section left open:

* **Which code produced "before" (finding 1).** Both binaries are built with `INTARSIA_BUILD_STAMP` (head, code-tree hash, dirty,
  overlay). The gate refuses a baseline whose head is neither `--pre-change 4963b43` nor an ancestor of the build under test
  (`--revlist`), whose tree is dirty beyond the declared harness files, or whose code tree equals the build under test. A
  baseline recorded with `INTARSIA_CUDA_DISABLE` set is refused; names in that variable that match no kernel are an error.
* **Same-weights gate (finding 2).** `--write-self-golden` / `--self-golden` compares the new build with the logits of the
  pre-change build directly. Budgets and how they were chosen: `docs/accuracy.md`, "Choosing the self-golden budgets".
* **Replays visible (finding 4).** `/metrics` and the bench JSON carry graph replays, captures, eager and profiled decode steps;
  `bench speed --require-graphs` and the verdict stage fail on zero replays. The plan also prints a WARNING when graphs are
  disabled because decode kernels differ between positions.
* **Profiling and variance (findings 5, 6).** `--profile-every 0` on every arm; interleaved rounds, warmup, per-rep spread, a
  decision rule in the script header. `docs/benchmarking.md`.
* **vLLM down, memory guard (finding 7).** See `docs/benchmarking.md`. The build moved out of the exclusive lease. The lease
  `--mem` is 100 GB (`MEM_LEASE_GB`) because nothing else may use the box; peak RSS of the 16k accuracy run has still not been
  measured, so this is a budget, not a measurement.

Gate rule once the numbers exist: PASS only if the verdict stage says `PHASE 1 SPEED GATE: PASS` (all three sizes PASS in every
valid round against vLLM measured in the same lease) and every accuracy stage passed against the recorded baselines.
`NOT DECIDED` is reported as such.

- The old-vs-new difference on the 35B (mean KL 3.6e-3 short, 3.4e-2 long) is about the same size as the difference between flash and SIMT attention on the same old build (3.2e-3, 2.9e-2).
  That is a build-against-build KL. The baseline gate's margin (x1.15 on KL) applies to each build's KL against the vLLM golden, which is a different quantity, so whether the
  margin is tighter than this noise is an inference that was not measured.
- A max position KL of 19.7 (35b-long noise run, teacher-forced prefill) is hard to call reordering noise. The run cannot tell "the 35B amplifies a numerically equivalent
  reordering" apart from "one attention path is inaccurate at long context". The test that would separate them is to gate the SIMT-attention old build against the same golden with

- The noise-derived self-golden budgets for the 35B are loose (they admit a max position KL of 1.2 short and 59 long), so the self-golden PASS there is weak evidence.

## 8. Accuracy bisect (2026-10-13, spark1, measured)

Question: what made the 35B per-prompt gate fail in section 7 (`long_code_4k` top-1 96.9 % -> 92.2 %, `code` prefill KL 9.0e-4 -> 1.8e-3, four per-prompt limits on the short golden)?

Answer in four lines:
1. The whole old-vs-new difference on the 35B comes from one kernel, `moe_experts_mma_bf16` (`kernels/cuda/moe_grouped.cu`). With it disabled the new build reproduces the old build's logits to mean KL 3e-12 (bit-identical); every other Phase 1b change is neutral on accuracy.

Fixed (k16 partial sums added in fp32); kernel test added and mutation-checked.
3. The symptom is not fixed, and the 4.7-point `long_code_4k` drop is inside the noise of this gate: the old build with nothing changed but flash replaced by SIMT attention drops `long_docs_12k` 96.9 -> 92.2 % (the same 4.7 points) and fails the old build's own recorded baseline gate (8.3). On the 35B any change of the last bits re-rolls the per-prompt metrics; the per-prompt limits of the baseline gate are inside that noise. Both 35B baseline gates therefore still FAIL, with a different set of prompts (7).
4. Speed is unchanged (decode 72.7 / 72.2 / 69.9 tok/s against 72.3 / 71.8 / 69.6; MoE kernel +2 to 4 % at T >= 1024, nothing visible in prefill tok/s).

### 8.4 The defect in `moe_experts_mma_bf16` and its fix

What was compared. Real layer shape (H=2048, I=512, 64 experts, top-8), outputs against the CPU reference `ref_moe_experts` (which matches the old kernel to 0.01 to 0.1 % of elements), bf16 elements that are not equal to the reference:

| | old `moe_experts_bf16` | `moe_experts_mma_bf16` before | after |
|---|---:|---:|---:|
| T=40 | 0.01 % (rel_l2 3.9e-5) | 1.01 % (3.5e-4) | 0.19 % (1.6e-4) |
| T=128 | 0.14 % (1.4e-4) | 0.74 % (3.2e-4) | 0.13 % (1.3e-4) |
| T=512 | 0.12 % (1.3e-4) | 0.60 % (2.8e-4) | 0.13 % (1.3e-4) |

(first run of a throw-away diagnostic, random case seed 5; the committed test uses other data, see 8.5.) The kernel-admission worst `rel_l2` of `moe_experts_mma_bf16` fell from 3.377e-4 (7.2) to 1.245e-4 (`final-gate/logs/kernels.log`).

Cause. `moe_mma_kernel` called `ik_mma_bf16_16816(acc[i][j], ...)` with the running fp32 sum as the C operand for all 32 (gate/up) or 8 (down) k steps of 64. The tensor core's accumulate step aligns the operands to the larger exponent and drops low bits (its fp32 accumulation is not an IEEE add), so the error of a long dot product grows with the number of steps; the warp-per-row kernel sums in ordinary fp32 and does not have it. The weights are dequantised exactly and the bf16 rounding points of the epilogue were already the reference ones, so accumulation was the only precision difference left. The mechanism is inferred from the effect of the fix (5x fewer off-by-one outputs); the SASS was not inspected. The signed mean error against the reference is small and of mixed sign (|gain| below 2e-6 before and after), so this was extra noise, not a bias.

Fix (`kernels/cuda/moe_grouped.cu`, mainloop): every k16 `mma` starts from a zero fragment and its result is added to the accumulator with a normal fp32 add (`float t[4] = {0}; mma(t, ...); acc += t`). Cost on the kernel (A/B in one lease, original and fixed kernel alternated twice, `bench_real_shapes`, microseconds): T=16 918 -> 931, T=64 2020 -> 1995, T=128 2275 -> 2309, T=256 2446 -> 2419, T=1024 3019 -> 3112 (+3.1 %), T=4096 6743 -> 7002 (+3.8 %). Prefill tok/s of the whole engine is unchanged (8.6). The dense `matmul_*_gemm` / `matmul_*_mma` kernels use the same in-mma accumulation; they are unchanged against the old build (8.2), so they are not part of this regression and were left alone.

### 8.7 Why the gates still fail, and why that is not a kernel defect

The requirement "at least as close to the vLLM golden as the old build on every prompt" cannot be met by any numerically different but equally correct kernel on this model, and the data shows it:
- Old against new, with the MoE kernel the only difference: mean KL 6.0e-3 (long decode), 3.6e-3 (short prefill). After the fix: 5.6e-3 and 4.2e-3. The kernel got about three times closer to the exact result and the end-to-end distance to the old build did not move.
- Fixed against unfixed new (two kernels that differ only in the accumulation): mean KL 5.56e-3 (long decode), 4.71e-3 (short prefill), 2.44e-3 (short decode), 8 and 20 flipped argmax positions. The same size as old against new.
- Per prompt against the vLLM golden the three builds trade places: of 10 short prefill prompts the fixed build has the lower KL than the old build on 5, the higher on 4 and the same on 1, of 5 long prefill prompts lower on all 5; `chat_system` prefill KL is 25.8 (old), 47.0 (new), 12.4 (fixed) x 1e-3, `chat_multiturn` short decode 16.7, 31.0, 86.6 x 1e-3 (one position with KL 1.33), `long_code_4k` decode top-1 96.9, 92.2, 92.2 %. Aggregate KL against the golden is lower or equal for the new build than for the old one in prefill (short 6.71 -> 6.60 -> 6.27e-3, long 44.9 -> 40.1 -> 42.7e-3) and in long decode (9.90 -> 8.65 -> 9.14e-3); only short decode is higher (9.58 -> 10.24 -> 15.56e-3, 160 positions, dominated by that one prompt).
- The old build under an equivalent attention kernel fails its own baseline gate (8.3), and the SIMT-against-flash difference on the old build (mean KL 3.2e-3 short, 2.9e-2 long, 7.3) is as large as old against new.
What amplifies a difference of one bf16 step in a fraction of the MoE outputs to a KL of several 1e-3 was not measured (top-8 routing flips are the obvious candidate: a flip swaps an expert in one layer for one token). Consequence for the gate: the x1.15 aggregate margins and the per-prompt limits (KL x1.75, top-1 -1 point or one position) do not separate a defect from a re-roll on this model, and only the self-golden budgets, which are derived from the noise floor, are meaningful. Not done here (out of scope): deriving the per-prompt limits from the measured spread of equivalent builds, or gating on aggregates over more prompts and positions.
