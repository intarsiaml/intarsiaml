Facts the script fixes that the old section left open:

* **Which code produced "before" (finding 1).** Both binaries are built with `INTARSIA_BUILD_STAMP` (head, code-tree hash, dirty,
  overlay). The gate refuses a baseline whose head is neither `--pre-change 4963b43` nor an ancestor of the build under test
  (`--revlist`), whose tree is dirty beyond the declared harness files, or whose code tree equals the build under test. A
  baseline recorded with `INTARSIA_CUDA_DISABLE` set is refused; names in that variable that match no kernel are an error.
* **Same-weights gate (finding 2).** `--write-self-golden` / `--self-golden` compares the new build with the logits of the
  pre-change build directly. Budgets and how they were chosen: `docs/accuracy.md`, "Choosing the self-golden budgets".
* **Replays visible (finding 4).** `/metrics` and the bench JSON carry graph replays, captures, eager and profiled decode steps;
  `bench speed --require-graphs` and the verdict stage fail on zero replays. The plan also prints a WARNING when graphs are
  disabled because decode kernels differ between positions.
* **Profiling and variance (findings 5, 6).** `--profile-every 0` on every arm; interleaved rounds, warmup, per-rep spread, a
  decision rule in the script header. `docs/benchmarking.md`.
* **vLLM down, memory guard (finding 7).** See `docs/benchmarking.md`. The build moved out of the exclusive lease. The lease
  `--mem` is 100 GB (`MEM_LEASE_GB`) because nothing else may use the box; peak RSS of the 16k accuracy run has still not been
  measured, so this is a budget, not a measurement.

Gate rule once the numbers exist: PASS only if the verdict stage says `PHASE 1 SPEED GATE: PASS` (all three sizes PASS in every
valid round against vLLM measured in the same lease) and every accuracy stage passed against the recorded baselines.
`NOT DECIDED` is reported as such.

  That is a build-against-build KL. The baseline gate's margin (x1.15 on KL) applies to each build's KL against the vLLM golden, which is a different quantity, so whether the
  margin is tighter than this noise is an inference that was not measured.
- A max position KL of 19.7 (35b-long noise run, teacher-forced prefill) is hard to call reordering noise. The run cannot tell "the 35B amplifies a numerically equivalent

### 8.4 The defect in `moe_experts_mma_bf16` and its fix

What was compared. Real layer shape (H=2048, I=512, 64 experts, top-8), outputs against the CPU reference `ref_moe_experts` (which matches the old kernel to 0.01 to 0.1 % of elements), bf16 elements that are not equal to the reference:

| | old `moe_experts_bf16` | `moe_experts_mma_bf16` before | after |
|---|---:|---:|---:|
| T=40 | 0.01 % (rel_l2 3.9e-5) | 1.01 % (3.5e-4) | 0.19 % (1.6e-4) |
| T=128 | 0.14 % (1.4e-4) | 0.74 % (3.2e-4) | 0.13 % (1.3e-4) |
| T=512 | 0.12 % (1.3e-4) | 0.60 % (2.8e-4) | 0.13 % (1.3e-4) |

(first run of a throw-away diagnostic, random case seed 5; the committed test uses other data, see 8.5.) The kernel-admission worst `rel_l2` of `moe_experts_mma_bf16` fell from 3.377e-4 (7.2) to 1.245e-4 (`final-gate/logs/kernels.log`).

Cause. `moe_mma_kernel` called `ik_mma_bf16_16816(acc[i][j], ...)` with the running fp32 sum as the C operand for all 32 (gate/up) or 8 (down) k steps of 64. The tensor core's accumulate step aligns the operands to the larger exponent and drops low bits (its fp32 accumulation is not an IEEE add), so the error of a long dot product grows with the number of steps; the warp-per-row kernel sums in ordinary fp32 and does not have it. The weights are dequantised exactly and the bf16 rounding points of the epilogue were already the reference ones, so accumulation was the only precision difference left. The mechanism is inferred from the effect of the fix (5x fewer off-by-one outputs); the SASS was not inspected. The signed mean error against the reference is small and of mixed sign (|gain| below 2e-6 before and after), so this was extra noise, not a bias.

Fix (`kernels/cuda/moe_grouped.cu`, mainloop): every k16 `mma` starts from a zero fragment and its result is added to the accumulator with a normal fp32 add (`float t[4] = {0}; mma(t, ...); acc += t`). Cost on the kernel (A/B in one lease, original and fixed kernel alternated twice, `bench_real_shapes`, microseconds): T=16 918 -> 931, T=64 2020 -> 1995, T=128 2275 -> 2309, T=256 2446 -> 2419, T=1024 3019 -> 3112 (+3.1 %), T=4096 6743 -> 7002 (+3.8 %). Prefill tok/s of the whole engine is unchanged (8.6). The dense `matmul_*_gemm` / `matmul_*_mma` kernels use the same in-mma accumulation; they are unchanged against the old build (8.2), so they are not part of this regression and were left alone.

### 8.7 Why the gates still fail, and why that is not a kernel defect

The requirement "at least as close to the vLLM golden as the old build on every prompt" cannot be met by any numerically different but equally correct kernel on this model, and the data shows it:
- Old against new, with the MoE kernel the only difference: mean KL 6.0e-3 (long decode), 3.6e-3 (short prefill). After the fix: 5.6e-3 and 4.2e-3. The kernel got about three times closer to the exact result and the end-to-end distance to the old build did not move.
- Fixed against unfixed new (two kernels that differ only in the accumulation): mean KL 5.56e-3 (long decode), 4.71e-3 (short prefill), 2.44e-3 (short decode), 8 and 20 flipped argmax positions. The same size as old against new.
- Per prompt against the vLLM golden the three builds trade places: of 10 short prefill prompts the fixed build has the lower KL than the old build on 5, the higher on 4 and the same on 1, of 5 long prefill prompts lower on all 5; `chat_system` prefill KL is 25.8 (old), 47.0 (new), 12.4 (fixed) x 1e-3, `chat_multiturn` short decode 16.7, 31.0, 86.6 x 1e-3 (one position with KL 1.33), `long_code_4k` decode top-1 96.9, 92.2, 92.2 %. Aggregate KL against the golden is lower or equal for the new build than for the old one in prefill (short 6.71 -> 6.60 -> 6.27e-3, long 44.9 -> 40.1 -> 42.7e-3) and in long decode (9.90 -> 8.65 -> 9.14e-3); only short decode is higher (9.58 -> 10.24 -> 15.56e-3, 160 positions, dominated by that one prompt).
- The old build under an equivalent attention kernel fails its own baseline gate (8.3), and the SIMT-against-flash difference on the old build (mean KL 3.2e-3 short, 2.9e-2 long, 7.3) is as large as old against new.
What amplifies a difference of one bf16 step in a fraction of the MoE outputs to a KL of several 1e-3 was not measured (top-8 routing flips are the obvious candidate: a flip swaps an expert in one layer for one token). Consequence for the gate: the x1.15 aggregate margins and the per-prompt limits (KL x1.75, top-1 -1 point or one position) do not separate a defect from a re-roll on this model, and only the self-golden budgets, which are derived from the noise floor, are meaningful. Not done here (out of scope): deriving the per-prompt limits from the measured spread of equivalent builds, or gating on aggregates over more prompts and positions.

## 9. Long-context investigation: `chat_reuse_4k` (2026-10-13, spark1, measured)

Question: is there a boundary / tail-tile / chunk defect behind the 35B long-golden outlier `chat_reuse_4k` (4631 tokens, the only long prompt that is not a multiple of 16; prefill top-1 87.7 %, KL21 0.257, max position KL 28.8 against vLLM; flash against SIMT on the same build mean KL21 0.175, max 17.7, where the other prompts agree to 5e-3 to 1.2e-2)?

Answer in six lines:
1. **No defect in our engine was found, and the evidence excludes the hypotheses in the task.** The result does not move with the chunk size (64, 256, 1024, 8192: 8192 is one single chunk, so no later-chunk rope offset, KV append edge, GDN conv/state carry or non-aligned final chunk exists in that run), nor with the truncation length (4608 aligned, 4624, 4631: positions < 4608 are bit-identical), and the last 23 positions are the quietest (mean KL21 0.002 against 0.24 overall).
2. **Both attention kernels are correct on the real tensors.** Dumped q / K cache / V cache / output of all 50 prefill-attention calls of three real 35B prompts (T = 32, 256, 44 at pos0 = 256; head_dim 256) and recomputed in fp64: flash max rel_l2 1.95e-3, SIMT 1.92e-3 (bf16 output rounding), including the second chunk. "Two correct kernels cannot differ by KL 17" is false on this model: they can, because of 3.
3. **The prompt is a noise amplifier, for every kind of change of the last bits.** The same flash kernels at chunk 256 against chunk 64 or 1024 (only GEMM / MoE row tiling differs) give mean KL21 0.13 to 0.14 on `chat_reuse_4k` and 0.005 to 0.010 on `long_code_4k` / `long_docs_4k`: the same size as flash against SIMT. About 100 of 4631 positions have KL21 > 1 in each pair.
4. **Where the amplification sits:** inside the open user turn. 70 % of the KL is on the 43 % of positions where some engine puts more than 10 % on `<|im_end|>` / `<|im_start|>` / `<|endoftext|>` (vLLM has `<|im_end|>` as top-1 with p > 0.5 at 1292 of 4631 positions): "does the turn end here" flips between runs, with p about 1 on either side (the earlier `''` rows were these special tokens, which a decoder hides). By segment (c256 against c64): system 0.012, user document 0.139, question and assistant prompt 0.010, generated continuation 0.0013. The same document as raw tokens, with no ChatML around it, is 4 to 5 times quieter (9.5).
5. **vLLM shares it.** Where vLLM and ours disagree sharply on the true next token, vLLM is right and ours wrong at 6 positions, ours right and vLLM wrong at 5. Ours against vLLM (0.19 to 0.27) is about 1.5 times ours against ours (0.13 to 0.17), as expected for two noisy samples; vLLM also runs an fp8 KV cache (not separated, 9.9).
6. **The ids are the golden's ids, and they are right.** Re-tokenising the five prompts with `tools/goldenlib.py` and the model's tokenizer gives exactly the golden's ids (and `reuse_split` 4521) for all five prompts, so there is nothing to fix in the golden tooling. Fix: none to the engine. The long-context test of this section guards the shapes (9.6); the gate consequence is in 9.9.

## 10. Gate calibration and final verdict (2026-10-13, spark1 and Mac, measured)

### 10.0 This is a post-hoc gate change

Plainly: the per-prompt rule of the baseline gate was changed **after** the 35B gates failed (8.6) and after the failures were traced to noise (9). Before the change the gate said FAIL for `35b-short` and `35b-long`; after it, `35b-long` says PASS on its baseline part and `35b-short` still says FAIL. Nothing here shows the new kernel is right; it shows what the gate can and cannot tell.

The evidence that justifies the change (all measured, not argued):

* The old build fails its own fixed-margin per-prompt gate when only an equally correct thing changes (8.3, 9.2, 9.5). This window repeats it on the old build with the fixed margins: SIMT instead of flash attention fails `35b-short` prefill `code` top-1 (100.0 -> 97.7 %, limit 98.85 %); prefill chunk 1024 instead of 256 fails `35b-long` `chat_reuse_4k` top-1 and `|tail diff|` and `long_code_4k` decode top-1 (`gate-calibration/spark1/logs/*.envelope-*.log`, section "FIXED margins only").
* The same experiment shows the **aggregate** checks are not immune either: with chunk 1024 the old build fails the aggregate tail-bucket KL of `35b-long` prefill (4.49e-2 -> 5.27e-2, limit 5.16e-2) and the aggregate top-5 of decode; with SIMT attention and a chunk-only envelope it fails the decode aggregate top-1 (10.5). The instruction was to keep the aggregates hard, and they are; this is a finding, not a change.

What was fixed in advance (script header of `4ad0eea`, written before any number of this window existed): k = 2; perturbations SIMT attention + chunk 64 for `35b-short`, chunk 1024 for `35b-long`, SIMT on `35b-long` as the held-out check; the aggregates unchanged; and the prediction that `35b-short` decode fails an aggregate on the `0e77696` numbers, so the gate stays FAIL whatever the envelope does to the per-prompt part. The prediction held. k was not tuned after seeing the result.

### 10.1 What was built

`intarsia accuracy --write-noise-envelope E.json --noise-ref B.json --noise-perturb chunk|chunk=N|attn-simt|external:TEXT` runs the same build a second time with a declared perturbation against the baseline `B.json` of the unperturbed run and writes, per mode and prompt, the |difference| of top-1, mean 21-way KL and mean |tail diff| (and of the largest single-position KL, shown only) with a provenance stamp; more perturbations into the same file give the per-prompt maximum. `--baseline B.json --noise-envelope E.json` then uses per prompt `limit = baseline -/+ max(fixed margin, k x delta)`, `--envelope-k` (default 2), prints every prompt's limit with its source (`fixed` / `envelope`), the delta, and the `k` that would be needed, and the number of failing prompts by k. Without an envelope the per-prompt checks are unchanged and a warning is printed on models whose `config.json` shows experts or linear-attention layers. Aggregates untouched. The envelope is refused unless golden, run configuration and build match the baseline's. Code: `crates/intarsia-cli/src/cmd/accuracy/envelope.rs` (new, added to the harness overlay), `baseline.rs`, `accuracy.rs`, `provenance.rs` (`ExecInfo.fault`); description, flags and "Choosing k" in `docs/accuracy.md`, "Noise envelope". Debug hook for the sensitivity check: `INTARSIA_CPU_MUTATE=<op,..>:scale=<f>` in `crates/intarsia-backend-cpu/src/fault.rs` (a deliberate bug; off by default).

### 10.8 Final Phase 1b accuracy verdict

**FAIL, not accepted.** Per case, with the calibrated gate at k = 2:

| case | verdict | reason |
|---|---|---|
| `35b-short` | **FAIL** | decode aggregate mean KL, tail-bucket KL and max KL fail their fixed limits (hard by instruction); `chat_multiturn` decode KL needs k = 16.5. Prefill per-prompt now PASS (the fixed-margin failure on `code` is inside the SIMT envelope). |
| `35b-long` | baseline PASS (per-prompt with the chunk-1024 envelope, aggregates, prefix reuse); absolute 4-bit floor FAIL as for the old build | held-out SIMT decode check FAILED (10.6): the envelope has only one kind of noise |
| `8b-short`, `8b-long` | PASS | fp32 goldens, bf16 floor |

What the calibration changed: it removes the per-prompt failures the noise explains (`35b-short` prefill `code`; nothing else failed per-prompt on the long set after the envelope), and it exposes that the remaining `35b-short` failure is **not** attention or chunk noise. Whether it is a defect is **not settled**: the bisect (7, 8.2) puts the 35B difference in `moe_experts_mma_bf16` alone, the kernel passes the unit test that bounds its error against the CPU reference to a small multiple of the old kernel's (8.5), and the vLLM golden itself moves that prompt between 16.7e-3, 31.0e-3 and 86.6e-3 for three kernel versions (8.7); but no MoE-kernel perturbation is in the envelope (the old build has no second MoE kernel to perturb with), so the gate cannot call it noise either. The accurate statement is: Phase 1b accuracy is **not shown to be acceptable** on `35b-short`, and the gate as run cannot decide it.

### 10.9 Left undone or uncertain

* k = 2 is not a calibrated error rate (10.2); with the one or two perturbations the window could afford, a correct build will often fail one prompt. A hard per-prompt verdict needs at least four perturbations per case or a larger `--envelope-k`; the `k needed` column is the number to read.
* `35b-long` has only the chunk perturbation; SIMT would have caught the decode failure of 10.6 as noise only if recorded. Not done in this window.
* The aggregates are inside the noise as well on `35b-long` (10.0) and are still fixed; calibrating them like the per-prompt checks is the obvious next step and was out of scope.
* A MoE-kernel perturbation (for example `moe_experts_bf16` against `moe_experts_mma_bf16` on the new build, or a second reordering of the old one) would say whether `chat_multiturn` decode is routing-flip noise; not measured.
* `chat_multiturn` decode is 16 positions of one prompt; the decode aggregate of `35b-short` is dominated by it.
* The Mac test model is dense and the hook flips bf16 output bits; its envelopes say nothing about the 35B's noise, only about the mechanics.
* 8B baseline/envelope not recorded; the dense per-prompt fixed margins were not re-validated in this window.
