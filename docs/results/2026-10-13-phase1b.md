  Port 8000 (vLLM) refuses connections. The `spark1` ssh alias routes through Tailscale, which reports the node
  offline, so it times out earlier. This looks like a hung or thrashing host (kernel up, userspace not
  serving), not a network fault. Polling every 30 s for over two hours never got a banner.
- Cause unknown. The harness agent had an 8B HF golden job (4.6k tokens, top-20) running when the host went away
  and cannot say whether it was responsible. spark1 uses unified memory, so memory pressure from that job next
  to the 64 GB `spark1-vllm` reservation is the first suspect, but nothing observed proves it.
- I have no power control on the box. A person needs to power-cycle it.
- spark2 was not substituted: it has no cargo toolchain, no goldens or 35B checkpoint paths set up for this, and
  its vLLM serves a different role (`retro`), so an A/B against the "guidance" checkpoint there would not be the
  required comparison.

## 5. Procedure to finish: `scripts/phase1b-acceptance.sh`

Section 5 used to be a list of shell commands. Review of it (`docs/reviews/2026-10-13-opus-phase1b-review.md`, findings 1, 2,
4 to 7) found that it could not decide the gate: the "before" baseline came from the new tree with kernels switched off, the
accuracy gates could not see a small change, nothing said whether decode replayed graphs, profiled steps and single runs
decided a 76 against 78 tok/s margin, and a 38 GB server ran next to the 64 GB vLLM reservation. It is now one script. Nothing
below has been run on a GPU; the script has been run only in `DRY_RUN=1` on the Mac (stubbed ssh, rsync, fleetq and docker).

```sh
export VLLM_CONTAINER=<name from docker ps on spark1>   # the guidance vLLM; the script restarts it, it does not recreate it
export S1_35B=<Qwen3.6-35B-A3B NVFP4 dir on spark1>
git status --short                                      # must be clean: the tree under test is stamped
scripts/phase1b-acceptance.sh                           # all stages; STAGES=preflight,build to stop before the lease
DRY_RUN=1 scripts/phase1b-acceptance.sh                 # shows every remote command without running any
```

Facts the script fixes that the old section left open:

* **Which code produced "before" (finding 1).** Both binaries are built with `INTARSIA_BUILD_STAMP` (head, code-tree hash, dirty,
  overlay). The gate refuses a baseline whose head is neither `--pre-change 4963b43` nor an ancestor of the build under test
  (`--revlist`), whose tree is dirty beyond the declared harness files, or whose code tree equals the build under test. A
  baseline recorded with `INTARSIA_CUDA_DISABLE` set is refused; names in that variable that match no kernel are an error.
* **Same-weights gate (finding 2).** `--write-self-golden` / `--self-golden` compares the new build with the logits of the
  pre-change build directly. Budgets and how they were chosen: `docs/accuracy.md`, "Choosing the self-golden budgets".
* **Replays visible (finding 4).** `/metrics` and the bench JSON carry graph replays, captures, eager and profiled decode steps;
  `bench speed --require-graphs` and the verdict stage fail on zero replays. The plan also prints a WARNING when graphs are
  disabled because decode kernels differ between positions.
* **Profiling and variance (findings 5, 6).** `--profile-every 0` on every arm; interleaved rounds, warmup, per-rep spread, a
  decision rule in the script header. `docs/benchmarking.md`.
* **vLLM down, memory guard (finding 7).** See `docs/benchmarking.md`. The build moved out of the exclusive lease. The lease
  `--mem` is 100 GB (`MEM_LEASE_GB`) because nothing else may use the box; peak RSS of the 16k accuracy run has still not been
  measured, so this is a budget, not a measurement.

Gate rule once the numbers exist: PASS only if the verdict stage says `PHASE 1 SPEED GATE: PASS` (all three sizes PASS in every
valid round against vLLM measured in the same lease) and every accuracy stage passed against the recorded baselines.
`NOT DECIDED` is reported as such.

## 6. Honest gaps carried forward

- Everything in section 3. The largest risks are build errors in the never-linked CUDA Rust path, a silent
  graph fallback to eager on the real plan, and an accuracy regression from the new MoE and GEMM kernels
  (the grouped MoE kernel differs from the old `moe_experts_bf16` by rel_l2 up to 3.5e-4 in the standalone check, a different
  summation order; the `*_gemm` kernels were checked identical to `*_mma`, rel_l2 0, in 30 shape/format combinations; the new GPU tests that
  assert both have not run).
- vLLM serves an fp8 KV cache and we use bf16, so every 35B KL against it includes reference KV noise. Separating
  the two needs a vLLM started with `--kv-cache-dtype auto`, which was not allowed here.
- Reuse gate (`accuracy --mode reuse`) has run only on an attention-only model, never on GatedDeltaNet. The CPU test of graph replay after a mid-sequence
  GatedDeltaNet restore exists now (`crates/intarsia-models/tests/graphs.rs`); the real-model part is the `graphs` stage of the script.
- The decode profile (`2026-10-13-phase1b-decode-profile.md`) was measured with the replica's 4-launch `ik_moe_experts_bf16`, not the engine's
  `moe_experts_decode_bf16`; its 76 tok/s graph figure is not an engine-kernel-set number (corrected there).
- Claims fixed after review: the M=40 head case in `quant/cases.rs` is admission-only (the model's head is capped at 16 rows and never
  selects `*_gemm`); `tools/golden_vllm.py --cache-salt` exists to keep the golden request off the prefix cache but has not run against a
  live server, and the goldens built so far did not use it.
- The model-level MoE-vs-HF test the review asked for is still not built.
- Fusions (GDN conv+gating+recurrence, rmsnorm+residual) and multi-stream branches inside the engine's graph are
  not written. The replica says they are worth up to about 0.6 ms per token.
- Decode ABI change: `ik_rope_bf16`, `ik_kv_append_bf16`, `ik_attn_decode_bf16` and `ik_attn_decode_bf16_splitkv`
  gained a `pos` argument before `stream`; the HIP worktree (phase2a/hip) must adopt it.
- Residue on spark1 from earlier agents: `~/intarsiaml-harness`, `~/intarsiaml-golden/run8b.sh`, `acc.sh`, and
  the new goldens. No target directory of mine exists there (I never reached spark1).
