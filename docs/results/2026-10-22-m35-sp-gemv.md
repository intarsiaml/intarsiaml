# M35 sp-gemv: split-K M=1 GEMV for fp8 / nvfp4 on Metal (negative result)

Branch `lane-m35/sp-gemv` (base d99cfa73, commits f47b8354 and 3b02bb1f). **Not merged: the kernels are correct but end-to-end decode is flat.**

## Key lesson

The lane started from a profile in which `matmul_fp8_gemv` averaged 97.8 us per launch (8192x2048 at 170-195 GB/s, 39 % of decode GPU time). That profile was taken in a non-exclusive slot while other jobs shared the GPU and memory bandwidth. **Contended profiles overstated the GEMV time by about 2x, so the premise was wrong.** In an exclusive slot the old kernel already runs 8192x2048 in 42.8 us (~395 GB/s in profile mode, which includes a few us of per-command-buffer cost). The big GEMVs sit at the per-launch floor; the remaining decode time is outside these kernels (a `cb`-mode profile would show where).

Take per-kernel timings for A/B only from an exclusive slot, and compare per-shape medians, not per-op step sums: unrelated ops moved 15 % between two runs of the same slot (attn 2669 -> 2206 us, moe_experts 2019 -> 1758 us per step), so sums mostly show run-order drift.

## What changed

- `fp8_gv_*` / `nv_gv_*` replace the `_m1` GEMVs: a threadgroup of SG simdgroups owns R rows and streams them together with 8-byte loads (rows at 8 mod 16 need no head / tail), each thread quantises only its own 8 activations (no staging barrier), fixed-order combine (deterministic). SG follows K, R follows N (>= 32768 threads). M = 2..8 keeps `_m8`.
- W8A8 quantiser computed on the value (fma-corrected reciprocal quotient + bit-pattern rounding); bit-identical to `f32_to_fp8_e4m3` (175M random cases, plus `tests/quant.rs` over every bf16 pattern through the GEMM, the 8-row and the 1-row GEMV).
- Metal profile labels now carry n / k / bytes for fp8 / nvfp4 matmuls (nvfp4: logical K, bytes include block scales).
- Summation order of the M=1 GEMVs changes, so merging would need a re-record of the Metal drift dump.

## Correctness

`kernels test --backend metal --op matmul_fp8` / `matmul_nvfp4`, with and without `--model`: 0 FAIL, ADMITTED (fp8 gemv 34 cases max_abs 2.25e-3 rel_l2 5.9e-5; nvfp4 gemv 21 cases max_abs 1.78e-4 rel_l2 2.9e-6). `cargo test -p intarsia-backend-metal --release`: all green.

Decode is flat within noise. Only fp8 512x2048 (-22 %) and the nvfp4 shared gate / up (-32 %) got faster, worth about 0.2 ms of a 9.6 ms step, below what the e2e runs resolve.

## Caveats

- `examples/quant_bw` times random-bit activations, not real ones; use `QBW_IS=0` for pure weight streaming. Its earlier per-launch profile mode timed cold buffers (first touch) and biased every first-listed variant; it is removed.
- fleetq jobs: 3767, 3779, 3785, 3791, 3834, 3856, 3903, 3904, 3948, 3955 (exclusive e2e + profiles), 3976.
