## Summary

- **The eager half of the idea is already there:** on CUDA the verify rows of eager passes (copy chains, eager MTP fallbacks, batched verify, the head's catch-up rows) already run as one row-table launch per layer, by lane vat's knob that is not HIP-gated (section 1). A CUDA knob for them would do nothing.
- **The real gap is the captured `spec_step` graph** (every normal MTP step): `q = k + 1` per-row launches per full-attention layer (section 2). Graph-replay microbench: a rows launch saves 0.1 to 0.4 ms of a 17.3 ms step (section 3).
- **Change:** opt-in `INTARSIA_CUDA_VERIFY_ATTN_ROWS=1` lets captured passes use the rows kernel (device positions, per-cache-pair K / V tables allocated before the capture). Unset: today's behaviour, plan byte-identical.
- **Result (35B, spark1, ABBA x 4):** the four default cells **1.0134x** (16 of 16 round-cells above 1; chat-short 138.4 -> 140.5 tok/s, code-gen 160.7 -> 162.6), copy cells neutral (1.0000x, 0.9999x). Greedy ids equal to the knob off and `--spec off` (11 of 11 arms), mb8 batched replies identical (7 of 7), CUDA bitwise tests 3 of 3.
- **Recommendation: keep opt-in for now; default-on candidate for CUDA `--spec mtp` at tp 1** (user's call).

## Probe

Branch `cvat` from origin/main `bcf502979` (contains #457). Measurement and a small opt-in change; nothing default-on.

### 1. The eager verify path already runs the row-table launch on CUDA (no port needed)

- The knob that gates it, `INTARSIA_HIP_VERIFY_ATTN_ROWS`, is not backend-gated: `crates/intarsia-core/src/model.rs:1872` (`map_or(true, ...)`, default on).
- The guard in `crates/intarsia-core/src/model/verify_attn.rs:verify_attn_rows` asks only `backend.verify_attn_per_row()` and `backend.supports_row_tables()`. On CUDA the first is true for an
  MTP model (`crates/intarsia-backend-cuda/src/device.rs:374` and `:381`, set by `model.rs:1809` for `--spec mtp`), the second is always true (`device.rs:366`); `device_address` exists (`device.rs:455`).
  The row-table kernel is registered (`kernels/cuda/attention_splitkv.cu:902`, `ik_attn_decode_bf16_splitkv_rows`) and `crates/intarsia-backend-cuda/tests/row_tables.rs` proves it bitwise the one-row launch.
- Evidence it engages: 119 serve logs of lane sideeager/postchain2 say `verify attention rows: engaged (one row-table attention launch per layer)`
  (`grep -rh 'verify attention rows' docs/results/2026-11-18-sideeager/raw docs/results/2026-11-17-*`); copycuda's nsys trace of a max-batch-1 MTP server
  (`spark1:~/intarsiaml-copycuda/out/ns1/b1.sqlite`) holds 22 `splitkv_rows_persist_kernel` launches (the eager 1-draft end steps; nothing else runs a rows kernel at `--max-batch 1`).
- So the eager paths (copy chains `INTARSIA_SPEC_COPY` 8-row passes, eager MTP fallbacks, request-ending 1-draft steps, the MTP head's catch-up rows) are **already one launch per layer**. A CUDA knob for them would change nothing.
- Batched verify (`INTARSIA_BATCHED_VERIFY`) is a batched decode step: its attention is `OpCall::rows` row-table launches by construction (`model/batch.rs:236` `row_tables_wanted`; the `verify_attn_rows: false` at `batch.rs:1152` is the phantom model struct of the plan probe, not a serving path).

### 2. The only per-row remainder: captured `spec_step` graphs (the main CUDA MTP path)

- `verify_attn_rows` returned `Ok(false)` for every captured pass (`self.capture_ops.lock().unwrap().is_some()`), and the caller required `dpos.is_none()` (`model.rs` attention block, `// lane vat` comment).
  A captured MTP step (`spec_graph.rs:capture_spec_step`, replayed by `spec_step`) therefore records, per full-attention layer, `q = k + 1` `attn_decode` calls with one-element device positions (`dpos` entry `r`),
  each a `splitkv_kernel` + `combine_kernel` pair, plus the head's catch-up and chain rows. `spec_step_ok` (`spec_graph.rs:74`) requires `backend.verify_attn_per_row()`, i.e. exactly this per-row form.
- Share of a replay (copycuda's `b1.sqlite`, 2273 graph launches, graph-node kernels only): `splitkv_kernel` 33.7 launches per replay = 716 us, `combine_kernel` 114 us, together **830 us of 23.1 ms (3.6 %)**
  of kernel time per replay (about 30 of the 34 launches are the verify rows of the 10 full-attention layers at k = 2).
  Launch overhead inside a graph is small (sideeager: 68.5 us idle per replay across ~1000 nodes), so a rows launch can only win kernel time (tail / occupancy), not launch gaps.

### 3. What a rows launch saves inside a graph (microbench, `raw/microbench-2.txt`)

`crates/intarsia-backend-cuda/tests/verify_attn_rows.rs::timing_captured_attention_layers` (`INTARSIA_CVAT_TIMING=1`), spark1 GB10, vLLM up beside it, fleetq `--quiet gpu,cpu`: a graph of 10 attention
layers (35B shapes: 16 q / 2 kv heads, head_dim 256; each layer its own cache) replayed 40 times, best of 5, per-row launches (`attn_decode_bf16_splitkv`, device positions: 2 kernels per row) against one
`attn_decode_bf16_splitkv_rows` launch per layer:

| rows t | pos0 200 | 600 | 1500 | 3000 | 6000 |
|---|---|---|---|---|---|
| 2 per-row / rows (us per 10 layers) | 207 / 102 | 221 / 110 | 333 / 261 | 640 / 482 | 1065 / 837 |
| **3** (k = 2, the default) | 309 / 103 | 330 / 182 | 459 / 337 | 888 / 630 | 1466 / 1079 |
| 3 saved | **206 us** (67 %) | 148 (45 %) | 122 (27 %) | 258 (29 %) | 388 (26 %) |
| 4 per-row / rows | 420 / 104 | 444 / 184 | 588 / 413 | 1124 / 777 | 1846 / 1330 |
| 8 per-row / rows | 821 / 176 | 898 / 341 | 1086 / 718 | 2128 / 1384 | 3464 / 2392 |

At k = 2 a step replays in about 17.3 ms (`spec: mtp graph step` mean 17.31 ms in the chat-short ids run), so the saving is **0.7 to 2.2 % of a step** (0.7 % at 1500 tokens, 1.5 % at 3000, 2.2 % at 6000, 1.2 % at 200 tokens);
that is above the stop line (0.5 %), so the captured path is worth the change. Not counted: the MTP head's catch-up rows (1 attention layer) go through the same function.

## Change

Knob `INTARSIA_CUDA_VERIFY_ATTN_ROWS=1` (CUDA, off by default; `model.rs:1812`). With it, `Model::verify_attn_rows` takes a CAPTURED pass too (`verify_attn.rs:verify_attn_rows_captured`):

- positions: the capture's own device position table (`dpos`, `ws.pos` at `POS_VERIFY`) as the call's `pos` (`[t]` i32, row `r` reads entry `r`, as the per-row launches read entry `r` as a one-element tensor); nothing is uploaded in a capture;
- K / V address tables: a recording bakes in the address of its table region, and `VerifyAttnTab`'s regions are per layer SLOT and rewritten when another sequence's caches arrive, which would silently
  re-point an older sequence's graph. So captured passes use `VerifyCapTab`: regions keyed by the (K, V) cache-address pair, allocated once and never rewritten, in a buffer of their own (1024 regions x 256 B), registered
  before the capture starts (`register_verify_cap_tabs`, called by `capture_spec_step`). A cache without a region (table full) keeps the per-row launches (`verify attention rows: captured: ...` note on stderr);
- one rank only (`tp.world == 1`, no peers): `capture_spec_peer` keeps per-row launches;
- the scratch check and kernel selection are the eager path's (`registry.select`, `scratch_bytes <= plan scratch`); eager passes, the plan probe and `INTARSIA_CUDA_VERIFY_ATTN_ROWS` unset are untouched (the new fields are `false` / empty).

## Verdict

**Opt-in, default unchanged.** The knob is a **default-on candidate for CUDA `--spec mtp` at tp = 1** (the 35B: +1.3 % on every default cell, 16 of 16 round-cells above 1, ids and replies bitwise identical, plan byte-identical, neutral where
the copy chains dominate); the flip is the user's call. What is not covered: tp > 1 (falls back to per-row launches), other models and the fp8 KV cache (the rows kernel has an fp8 twin, not run here),
contexts above 8k (microbench only: the saving grows with context, 2.2 % of a step at 6000 tokens), several sequences in a graph cache beyond 1024 K / V cache pairs (then the per-row launches, silently except one stderr note).

Limitation by design: the table regions of a dead sequence's caches are never reused (a region is never rewritten, since a graph may still name it); the cap is 1024 pairs (10 attention layers + the head = 11 per sequence, so ~90 sequences' worth), after which new
caches record per-row launches and say so once on stderr (`captured: all table regions taken`). A `--max-batch 1` server reuses one state; a long-lived server that allocates many fresh states would hit the cap, not a wrong result.

Revert: unset `INTARSIA_CUDA_VERIFY_ATTN_ROWS` (the default). Eager passes: `INTARSIA_HIP_VERIFY_ATTN_ROWS=0` (already default on, not HIP-only).
