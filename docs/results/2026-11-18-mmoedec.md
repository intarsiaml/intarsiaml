# mmoedec: the arithmetic e2m1 decode for 1..=8-row MoE expert calls on Metal (Qwen3.6-35B-A3B NVFP4, endor)

Lane `mmoedec`, branch `mmoedec` from origin/main `eb6a48413` (#450 mmoe16 had merged by then; the work was done on top of `origin/mmoe16` `6a994d869` and cherry-picked, see "Not done / unverified"). Opt-in only: `INTARSIA_METAL_MOE_BITDEC=1`, off by default. Nothing is default-on.
Measured on endor (Apple M5 Max, macOS 27.0), `Qwen3.6-35B-A3B-NVFP4`, tp 1, the default recipe `--spec mtp --spec-k 2`. Every GPU run had its own `fleetq` slot (`--quiet gpu,cpu`); builds used `--load cpu`.
Raw output: `docs/results/2026-11-18-mmoedec/raw/`. Scripts: `scripts/mmoedec/` (adapted from mmoe16's and mcopy's).

## Verdict

- **Exact: yes.** A 1..=8-token MoE expert call with the knob on is bitwise equal to the T one-token calls with it off: 224 cases / 1008 token rows (T = 1..=8, seven routings, bf16 and f32 out, weights at offset 0 and 8, activations incl. bf16 subnormal, near-2^-126 and near-2^100). Greedy ids knob on = off = `--spec off` in 8 of 8 (chat-short, code-gen, reason, copy3k; GDN verify fuse unset and set).
- **Faster per layer: a little.** 1.01 to 1.02x at 1..=3 rows, 1.03 to 1.05x at 8 rows (micro, three runs). That is 0.02 to 0.08 ms per pass at 1..=3 rows, against a 13 to 14 ms pass (about 0.4 %).
- **Faster served: not measurable.** The default-recipe ABBA scatters from 0.85 to 1.07 per round and its sign depends on the arm order in the round. Pooled over 14 rounds the median of the per-round ratios is 0.997 to 1.003x on all four cells. See "Served" for both designs.
- **The path runs in served decode.** A counter build counted 97 % of the MoE expert launches of a 300-token MTP run on the `_a` kernels (T = 3 verify: 4800 of 4800, T = 1: 178 of 178).
- **Default-on stays the user's call.** At best a sub-percent gain, so there is no case for flipping it. It costs nothing when off.

## What changed

1. `crates/intarsia-backend-metal/src/lib.rs`: `moe_bitdec_enabled()` (`INTARSIA_METAL_MOE_BITDEC` equal to `1`, read once) and the test hook `with_moe_bitdec`.
2. `crates/intarsia-backend-metal/src/moe.rs`: `launch_moe_experts` picks `moe_dec_gu_a` / `moe_dec_dn_a` (#450's kernels, unchanged: the same per-pair grid, per-pair work, rounding order) when the knob is on and T is 1..=8, or `INTARSIA_METAL_VERIFY16=1` and T is 9..=16.
   - 2..=8 tokens already ran the per-pair rows path (`moe_experts_bf16_rows`); only the two shaders change.
   - One token (`moe_experts_bf16`, plain decode) used `moe_dec_gu` + `moe_dec_dn` (the second also sums the 8 pairs in k order). With the knob it takes the rows path instead: `_a` gate+up, `_a` down per pair, then `moe_gather` in k order, so 3 dispatches instead of 2. `moe_gather` sums in the same k order and with the same roundings as `moe_dec_dn_impl` (tests/rows_exact.rs pins that for T >= 2; the new unit test pins T = 1 against the knob-off call).
   - No new shader: the kernels of #450 serve 1..=16 rows.
3. `docs/tuning.md`: the `INTARSIA_METAL_MOE_BITDEC` row (2^114 limit, the one-token path change, what `NEGCTL` / `MOE_ROWS_FAT=0` no longer reach).
4. `crates/intarsia-backend-metal/tests/moe_bitdec.rs`: the bitwise test, the negative control and the `--ignored` timing test.

Not a registered op or kernel: the plan is unchanged.
The exactness argument is #450's: (code / 2^14) * (x * 2^14) is the same real number as code * x, so every fma of the 16-term chain rounds to the same float. It needs |x| < 2^114 for every activation entering the routed experts.

## Gates

**(a) Bitwise unit test** (`cargo test --release -p intarsia-backend-metal --test moe_bitdec`, `raw/rebased-checks.txt`, first run `raw/moe_bitdec-first.log`): `MMOEDEC bitwise: 224 cases, 1008 token rows equal`.
- T 1..=8; routings: random, identical, overlap, invalid ids (-1, E, i32::MIN), a token with no valid expert, duplicates, a 72-expert pool; bf16 and f32 out; weights at offset 0 and 8; activations normal, tokens scaled by 1e-6 and 3e4, one token of raw bf16 bit patterns (subnormals, near 2^-126, near +-2^100, signed zeros).
- Each case compares every output byte (guards included) of: the knob-off one-token calls (reference), the knob-on one-token calls, and for T >= 2 the knob-off and knob-on rows calls.
- **Negative control** (`bitdec_negative_control`): one activation of the last token is changed in the reference (T = 1, 2, 3, 8); about 1900 bytes differ, first at the last token's first byte.
- A unit-level "the knob switches kernels" test was tried and dropped: above 2^114 both paths overflow downstream to inf / NaN, so the bytes do not tell them apart. The dispatch proof is the counter below.

**Dispatch proof (counter build)** (`scripts/mmoedec/counter.sh`, `raw/counter.log`, `raw/counter/`, patch `raw/count.patch`, applied only to a temporary build, reverted): `generate --spec mtp --spec-k 2`, chat-short, 300 tokens, GDN verify fuse on. One line per MoE experts launch, counted by (rows path, T, kernel).

| launches | knob off | knob on |
|---|---|---|
| T = 3 verify, rows path (40 layers x 120 steps) | 4800 `_p` | 4800 `_a` |
| T = 2, rows path | 40 `_p` | 40 `_a` |
| T = 1, one-token call | 178 `moe_dec_gu` | 178 `_a` (rows path) |

5018 of 5161 launches (97.2 %) run the `_a` kernels; the rest are prompt-prefill pieces. The 300 ids are identical off and on.

## Speed

### Per layer: routed experts at 1, 2, 3, 8 tokens (micro)

Test: `timing_moe_bitdec` (`raw/timing-run1.log` to `run3.log`; `raw/tables-micro.md`). 35B shapes (E 256, top 8, H 2048, I 512), 24 routings cycled over 4 weight sets (1.7 GB, so expert reads are mostly uncached), 48 calls per block, best of 3, 6 alternating rounds, median per run. T = 1 is the `moe_experts_bf16` call (knob on: rows path with `_a` kernels and the gather), T >= 2 the rows call. Three separate runs; the table shows the median and the three run ratios. "pass" is x 40 layers.

| T | routing (distinct experts) | knob off | knob on | ratio, median of 3 runs [runs] | saved per pass of 40 layers |
|---:|---|---:|---:|---|---|
| 1 | pool72 (8.0) | 40.1 us | 39.5 us | 1.015x [1.015, 1.034, 1.007] | 0.024 ms of 1.60 ms |
| 1 | random (8.0) | 40.4 | 39.8 | 1.017x [1.017, 1.016, 1.018] | 0.024 ms of 1.62 ms |
| 2 | pool72 (15.3) | 63.8 | 62.8 | 1.013x [1.013, 1.011, 1.019] | 0.040 ms of 2.55 ms |
| 2 | random (15.9) | 65.9 | 64.6 | 1.015x [1.011, 1.015, 1.021] | 0.052 ms of 2.64 ms |
| 3 | pool72 (21.6) | 85.2 | 83.1 | 1.021x [1.018, 1.027, 1.021] | 0.084 ms of 3.41 ms |
| 3 | random (23.3) | 89.1 | 88.3 | 1.010x [1.014, 1.009, 1.010] | 0.032 ms of 3.56 ms |
| 8 | pool72 (43.7) | 174.5 | 165.8 | 1.053x [1.050, 1.055, 1.053] | 0.348 ms of 6.98 ms |
| 8 | random (57.4) | 201.2 | 196.3 | 1.028x [1.028, 1.025, 1.032] | 0.196 ms of 8.05 ms |

Reading:
- All 24 run ratios are above 1.0, but at 1..=3 rows the gain is 1 to 2 %, and the ratio grows with expert reuse (T = 8 pool72 1.05x, #450's T = 16 pool72 1.107x). At 1..=3 rows almost every pair is a distinct expert, so a weight read is not shared and the decode saving is small next to the memory traffic (T = 1: 8 experts x about 1.6 MB in 40 us is about 320 GB/s).
- The T = 1 number mixes two changes (solo to rows path, table to bit decode); they were not separated. That the on arm is not slower at T = 1 means the extra `moe_gather` dispatch costs less than the decode saves.

### Served: knob off against on (default recipe, both arms GDN verify fuse on)

Setup: `serve --max-batch 1 --spec mtp --spec-k 2`, one binary (`target-mmoedec/intarsia-new`), the arms differ by env only, a fresh server per arm and round, greedy, thinking off, cells chat-short, code-gen, reason, agent-edit, 3 reps each (`scripts/mmoedec/ab.sh`, `round.sh`, raw `raw/ab`, `raw/ab-run-r*.log`). Decode tok/s. Reply shas are equal in every comparison (168 of 168 round / cell / rep triples have one sha across all arms and servers).

**Design 1: ABBA across rounds, 4 rounds** (the brief's; the arm order reverses on even rounds; `raw/tables-ab.md`). Values are medians over 12 reps [min-max]; the ratio is the median of the per-round ratios, with the per-round ratios.

| cell | koff | kon | on / off |
|---|---|---|---|
| chat-short | 177.9 [145-185] | 174.6 [144-186] | **0.995x** (1.008, 0.988, 0.955, 1.003) |
| code-gen | 206.7 [176-211] | 194.6 [164-211] | **0.949x** (1.010, 0.921, 0.936, 0.962) |
| reason | 212.1 [180-216] | 200.1 [169-214] | **0.944x** (0.997, 0.853, 0.932, 0.956) |
| agent-edit | 201.9 [195-214] | 195.1 [176-207] | **0.958x** (1.009, 0.894, 0.983, 0.934) |

That looked like a loss, with big scatter (a round-2 `kon` server ran at 144 to 179 tok/s, the knob-off server after it at 145 to 207). Six more rounds of the same design (rounds 5 to 10; `raw/tables-ab-10rounds.md`) gave on / off medians of 1.000x, 0.975x, 0.964x, 0.975x (chat-short, code-gen, reason, agent-edit). The odd rounds (knob-off server first) had a median ratio of 1.008 to 1.014 and the even rounds (knob-on first) 0.946 to 0.998, so the result depends on which arm runs first: an order effect, not an arm effect.

**Design 2: A B B A inside each round, 4 rounds** (rounds 11, 13, 15, 17; each arm runs twice per round, on the positions B C in rounds 11 and 15 and A D in rounds 13 and 17; `scripts/mmoedec/round-abba.sh`, `abba-table.py`, `raw/tables-abba.md`). **Pooled, 14 rounds** (10 of design 1, 4 of design 2): median of the per-round on / off ratios 1.003x (chat-short), 1.003x (code-gen), 0.997x (reason), 1.003x (agent-edit); means 1.000, 0.992, 0.988, 0.993.

Reading: the served gain, if there is one, is below what this setup resolves (per-round scatter of several percent, an order or position effect of 2 to 4 %). The micro predicts 0.02 to 0.08 ms per 13 to 14 ms pass, about 0.4 %. Design 1 alone (4 rounds) would have read as a 5 % loss and design 2 alone as a 3 to 4 % gain; neither is an arm effect. The thermal level was 0 for most cells, 1 or 2 for some in each arm (`raw/ab-run-r*.log`, `raw/abba-run-r*.log`).

## Not done / unverified

- **Served speed is unresolved** (above). A bigger sample or a pinned-clock setup would be needed for a sub-percent effect. Not chased: the micro bounds it.
- **Rebased after measurement.** The served runs, the plan gate, the ids gates, the counter and the whole-crate run used the tree on `origin/mmoe16` `6a994d869` plus this change; #450 merged during the work, so the change was cherry-picked onto origin/main `eb6a48413`. On that tree only `moe_bitdec`, `moe_verify16`, `rows_exact` and `docs_env_vars` were rerun (all pass). The diff between the two bases does not touch `crates/intarsia-backend-metal` or `kernels/metal`.
- The T = 1 micro mixes the rows-path switch with the decode change. A solo `_a` variant (same arithmetic, no gather) was not built and the table-kernel rows path at T = 1 was not timed.
- `--max-batch` 4..=8 decode and batched MTP verify were not run served (same kernel, bitwise per the unit test). Greedy only; one machine, one model. The 27B has no NVFP4 routed experts, so the knob does nothing there.
- Exactness depends on |x| < 2^114 (documented in `docs/tuning.md`).
- `cargo fmt` / clippy were not run (CI does not run them).

## Revert

Unset `INTARSIA_METAL_MOE_BITDEC` (the default): the existing kernels run exactly as before (gate (c) and the knob-off arm of every test). Reverting the PR removes the knob, the launcher branch and the test.
