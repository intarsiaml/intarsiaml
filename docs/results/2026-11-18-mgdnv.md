# mgdnv: the fused speculative-verify GatedDeltaNet rows on Metal (Qwen3.6-35B-A3B NVFP4, endor)

Lane `mgdnv`, branch `mgdnv` from origin/main `835796344` (PR #439). Opt-in only: `INTARSIA_METAL_GDN_VERIFY_FUSE=1`, off by default; nothing is default-on.
Measured on endor (Apple M5 Max, macOS 27.0), `Qwen3.6-35B-A3B-NVFP4`, tp 1, every run in a `fleetq` slot (`--quiet gpu,cpu`; builds `--load cpu`).
Raw output: `docs/results/2026-11-18-mgdnv/raw/`; scripts: `scripts/mgdnv/` (mrows16's scripts with the knob arms; cells and table script are mcopy's, `scripts/mcopy/`).

## Verdict

- **Exact: yes.** The Metal unit test is bitwise the row-by-row path (outputs, final states and every per-row save) for 35 shape / row-count cases, rows 2 to 16, and its negative control sees a changed input. Greedy ids, knob on against knob off, are equal in 15 of 15
  cells x recipes (5 cells x default MTP, `INTARSIA_SPEC_COPY=20`, `=20,15`), all equal to `--spec off` too. `plan show --json` is byte-identical to origin/main with the knob unset and with it set. The whole Metal crate tests (37 test binaries) pass.
- **Faster across the board in this run: yes, modestly on ordinary MTP, clearly on copy chains.** Default MTP recipe (4 ABBA rounds x 3 reps): chat-short 1.027x, code-gen 1.029x, reason 1.027x, agent-edit 1.022x, copy3k 1.026x (medians of the per-round ratios; the low single
  cell-rounds are noted below). `INTARSIA_SPEC_COPY=20,15` (16-row chain passes): copy3k **1.096x**, json-xform **1.082x**, every round 1.050 to 1.100. The lowest median ratio over all seven cells is 1.022.
  Individual cell-rounds scatter by several percent (0.928 to 1.062 on the default cells), as the Mac's noise does; no cell has a median below 1.
- **Whether to make it default-on is the user's call.** Not done here. Caveats: the batched (several sequences per pass) verify branch was only checked at `--max-batch 2` (below); one machine, one model; the gains on default MTP are about 2.5 %, close to the noise of a single round.

## What changed

1. `kernels/metal/gdn.metal`: two new kernel families, `gdn_conv_snap_bf16_k2..k8` and `gdn_delta_snap_bf16_dk32/64/128/256` ("Speculative-verify rows" section). Each is the BODY of the one-row kernel (`gdn_conv_t<K, false>`, `gdn_delta_rule_t<DK>`)
   token for token, run over the T rows in one dispatch, plus snapshot stores: the conv state after token `t` is the history registers after their shift (written to save buffer `t`), the delta-rule state after token `t` is the simdgroup's `s[]` registers.
   The existing kernels are untouched. The arithmetic is unchanged (same loops, same `precise::` calls, same simd_sum order), so outputs, final state and saves are what the T one-row launches and slot copies produce.
   Metal has no arrays of buffers, so the (up to 15) save buffers are 15 consecutive bindings (conv kernel: 4..18, delta kernel: 7..21); unused ones alias the state buffer and are never touched (`p.e` / `p.pad` = T - 1 saves). One conv tile only (T <= 16 <= 32), the state update fused at the end, as the one-row kernel does.
2. `crates/intarsia-backend-metal/src/gdn.rs`: `MetalBackend::gdn_verify_rows_impl` (called from `Backend::gdn_verify_rows`, `lib.rs`): checks the knob (`INTARSIA_METAL_GDN_VERIFY_FUSE` equal to `1`, read once) and the arguments (rows 2..=16, K 2..=8, dk 32/64/128/256, bf16 activations, f32 conv / delta state and saves, shapes, bounds) and returns `Ok(false)` with nothing encoded otherwise;
   else two `dispatch`es (conv, delta rule). Both go through the same encoder as every other launch.
3. `crates/intarsia-core/src/model/gdn_block.rs`: the caller's row limit 2..=8 -> 2..=16 (the backend decides). `crates/intarsia-backend-cuda/src/device.rs`: CUDA refuses more than 8 rows itself (`snap_conv.len() > 7` -> `Ok(false)`, the row-by-row path), so CUDA behaves as before. HIP does not implement the call (default `false`) and then takes its own `gdn_verify_fuse_ok` path as before. Doc comment of the trait method updated.
4. `docs/tuning.md`: the `INTARSIA_METAL_GDN_VERIFY_FUSE` row. `INTARSIA_GDN_DEC` (the CUDA skip condition) has no Metal counterpart: Metal's one-row and T-row delta-rule kernels are the same kernel, so nothing is skipped. `INTARSIA_GDN_STATE=bf16` is CUDA only (Metal's state is f32, always).
5. Tests: `crates/intarsia-backend-metal/tests/gdn_verify_snap.rs` (bitwise + negative control, and an `--ignored` timing test), `tests/gdn_verify_snap_off.rs` (knob unset: `Ok(false)`).

Not a registered op, so the served plan is the same with the knob on or off, and the verify pass's row-by-row fallback is untouched: the caller still runs it whenever `gdn_verify_rows` answers `false`.

### Why about 2.5 % on default MTP and 8 to 10 % on chains: the per-layer cost (`raw/micro-timing.txt`, `cargo test ... --test gdn_verify_snap -- --ignored --nocapture`)

One GatedDeltaNet layer of the 35B (hk 16, hv 32, dv = dk = 128, K = 4), 200 back-to-back calls, wall microseconds including the host encode cost the engine also pays, best of two alternating blocks:

| T rows | row by row (T x conv + delta + T-1 slot copies) | `gdn_verify_rows` | ratio | x 30 layers |
|---|---|---|---|---|
| 2 | 19.2 us | 13.2 us | 1.46x | -0.18 ms |
| 3 | 29.8 us | 16.9 us | 1.77x | -0.39 ms |
| 4 | 39.6 us | 20.7 us | 1.91x | -0.58 ms |
| 8 | 85.4 us | 36.0 us | 2.38x | -1.48 ms |
| 16 | 176.8 us | 65.3 us | 2.71x | -3.34 ms |

A 3-row MTP pass is about 13 to 14 ms (2.8 tokens per pass at about 210 tok/s), so -0.39 ms is about 2.8 %: the served +2.2 to 2.9 % on the default cells. A 16-row chain pass saves 3.3 ms: the same direction and order as the served 8 to 10 % (not derived from it; the pass times of the chain arms were not measured).
The saving is the dispatches and slot copies, not the state traffic: the fused kernel reads the state once, writes it once and writes T - 1 snapshots, against T reads, T writes and T - 1 copies.

## Batched verify check (`scripts/mgdnv/batch2.sh`, `raw/batch2`)

The core change also routes the BATCHED verify branch (several sequences per pass, `segs.len() > 1` in `gdn_block.rs`) through the fused call. `serve --max-batch 2 --spec mtp --spec-k 2 --spec-off-at 9` with `INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1` (both off on Metal by default), two concurrent greedy cells (code-gen, reason, 2 reps each, two requests at a time),
knob off then on: **8 of 8 reply shas equal** (`BATCH2 PASS`), and the counter build saw 57000 fused calls (3-row), four times the solo run's count in the same cells. A first attempt without those two variables (`raw/batch2-solo-only`) never batched the verify (the Metal recipe drafts only while one sequence decodes) and also passed 8 of 8. Per-request tok/s with the knob on were 1 to 4 % higher in the batched run, one run, not a measurement.
Not proven: that the multi-sequence branch (and not solo passes) produced these particular calls; the call count says it ran a lot of them.

## Not verified

- The CUDA build of `device.rs` (`ik_cuda` is not set on this Mac: `cargo check -p intarsia-backend-cuda` compiled without the CUDA code), so the 7-save guard there is reviewed, not compiled. `tests/gdn_verify_snap.rs` of CUDA was not run.
- Default-on soak (long contexts, thinking mode, sampled requests with the knob), tp > 1, the 27B (dense, no GatedDeltaNet in the same layout: not run), the 4-bit / fp8 variants of the model, prefix-store restores with the knob. The ids gates are greedy; sampled requests were not compared.
- The batched verify branch was checked at `--max-batch 2` with 8 replies, not at 8 sequences, and the hit of the multi-sequence branch is inferred from the call count.
- The speed table is one machine, 4 rounds; ratios inside about 2 % of 1 on the default cells are not distinguishable from noise on their own, only as the same sign in all seven cells and in the per-layer micro.
- `cargo fmt` / clippy: CI does not run them (`.github/workflows/ci.yml`), and the touched files were not reformatted.
- Commits are signed `Claude Opus 5.5` as `scan/lane-rules.md` asks; the lane ran on Sonnet 5.5.

## Revert

Unset `INTARSIA_METAL_GDN_VERIFY_FUSE` (the default): the row-by-row calls and copies run exactly as before (gates (b), (c) above, `tests/gdn_verify_snap_off.rs`). Reverting the PR removes the two kernel families, the launcher and the core / CUDA 16-row plumbing.
