## 2. Diagnosis

### Decode launch gaps (item 1)

* Decode already runs as one HIP graph per step: every bench and profile run reports `graph replays = steps - 1, captures 1,
  eager decode steps 0`, and there is no host sync inside a step (argmax end to next step start: median 10 us).
* The idle time is inside the replay: each kernel boundary costs ~3 us whatever the kernels are (intra-step gap p10 / p50 / p90
  2.92 / 3.00 / 3.16 us, `prof/decode128-*.txt`), so idle = launches x ~3.2 us (1.834 ms / 578 = 3.17 us mean). That is CLR's per-node
  dispatch on gfx12; the CLR knobs (`HIP_FORCE_DEV_KERNARG`, `ROC_USE_FGS_KERNARG`, `DEBUG_CLR_MAX_BATCH_SIZE`,
  `GPU_STREAMOPS_CP_WAIT`) were tried on graph replay in `2026-10-13-hip-decode.md` without effect.
* So the lever inside the backend is fewer launches. The only multi-op chain the model graph already exposes as one optional
  fused op that HIP did not implement is `QkNormRopeKv` (6 launches per full-attention layer: q norm, q rope, k norm, k rope,
  k append, v append). Other fusions (MoE combine + residual, gate_split + sigmoid_mul, GDN conv + delta rule) need new ops in
  the model graph (shared core code), see section 7.

### GDN delta rule (item 2)

* Bound by latency, not memory or compute. Per token a wave reads one 4 KB qkv row and does 2 x 64 FMAs per lane for the two
  state dot products; at 2.0-2.3 us per token that is far from either limit. Everything in the token loop waits on the previous
  token's state (the recurrence), so the cost is the dependency chain plus the stalls added to it.
* The ISA of `gdn_delta_rows_kernel<128, 2>` showed the stalls: the next-token prefetch sits in `if (t + 1 < T)` and is converted
  inside that branch, so the wave executes `s_wait_loadcnt 0` right after issuing it (the prefetch hides nothing); each
  `__syncthreads` is a workgroup fence on global memory as well (`s_wait_loadcnt 0` + `global_inv`, twice per token); both warp
  sums go through `ds_bpermute` (5 LDS round trips each); beta and decay run per token on the scalar unit (~230 SALU per token).
* Not repeated: splitting state rows over more lanes (dead end). Not built: a chunked / WY form. It changes the summation order
  (no bitwise, own accuracy campaign), CUDA's chunked kernel lost to the lanes kernel (`2026-10-17-cuda-prefill-2.md`), and
  removing the stalls alone gave 2.6x bitwise. After v2 the delta rule is 15.7 % of prefill, so WY is a smaller lever now.

## 4. What was built

1. **`gdn_delta_rule_bf16_v2`** (kernels/hip/gdn.hip, `gdn_delta_rows_v2_kernel<128, 2, PD>`): same block (one wave = 16 value
   rows of one head, 2 lanes per state row), same lane-to-element map, same float operations in the same order as
   `gdn_delta_rows_kernel<128, 2>`. Changes, each against one stall above:
   * the raw bf16 q/k/v of the next PD tokens stay in a register ring (token loop unrolled by PD, each slot its own registers),
     loaded unconditionally (index clamped to the last token) and converted when their token runs; full groups of PD tokens
     run without a branch between slots, so the wait counter only waits for the slot's own load;
   * LDS-only barriers (`__builtin_amdgcn_fence(..., "workgroup", "local")` + `s_barrier`): the block is one wave, the barrier
     only orders the sq / sk staging; no `global_inv`, no wait on the in-flight prefetch;
   * warp sums with `v_permlanex16` (xor 16) and DPP `row_xmask` (xor 8, 4, 2, 1), added in `ik_warp_sum`'s order;
   * beta and decay for 32 tokens at once (one per lane, the same `sigmoidf` / `expf(neg_a * softplus(...))`), read per token
     with `v_readlane`;
   * k read from LDS once per token (the update loop reuses the kv loop's registers);
   * the two dot products and the state update as explicit `__builtin_fmaf` under `#pragma clang fp contract(off)` in the
     contraction the rows kernel compiles to (`fma(x, x', y * y')`, then z, w fused). Left to the compiler, the first cut fused
     the other product of the first pair and moved about one bf16 output in 10^4 (state bitwise, outputs not; found with a
     bisection in W3, logs/w3.log).
   * Registered for every `GdnDeltaRule` call with dk = 128 (decode and prefill; `GDN_V2_MIN_TOKENS = 1`), priority 10 over
     the rows kernel, which stays registered (other key widths, admission, the bitwise reference).
   * Knob `INTARSIA_HIP_GDN_PD` = 1 | 2 | 4 (default 2), registered in `ENV_KNOBS`; every value gives the same bits.
     Timing (`prof/gdn-timing.txt`): PD 2 and 4 equal, PD 1 slower at decode (8.6 vs 6.3 us).
2. **`qk_norm_rope_kv_bf16`** (kernels/hip/elementwise.hip, `qk_norm_rope_kv_kernel<CacheT>`): grid (T, Nkv), block G + 1
   waves (G = N / Nkv <= 8): wave w < G does query head kvh * G + w, wave G does k head kvh and the v copy. Each wave repeats
   the arithmetic of the launches it replaces: the qk_norm vector path (lane i squares values 8i..8i+7, one-wave block sum,
   bf16-rounded normalised row kept in LDS), rope on that bf16 row (angles in double narrowed to float, computed once per block;
   the rotation's contraction spelled out as `fma(a, c, -(b * s))` / `fma(b, c, a * s)`, rope_kernel's ISA), the un-rotated
   tail passed through, and the bf16 or fp8 (`f32_to_e4m3`) cache store. Device position (`pos`) as `rope_bf16`, so it replays
   in the decode graph. Needs head_dim % 8 == 0, <= 256, 16-byte aligned rows (the launcher refuses anything else).
   * `Op::QkNormRopeKv` removed from the HIP `UNIMPLEMENTED` list; the model already tries the fused op first (`run_fused`) and
     falls back to the unfused ops, so no core change. The 8B (32 / 8 heads of 128) takes it too.
3. Tests: `tests/gdn_v2.rs` (19 shapes: the 35B layout at T = 1, 2, 3, 4, 5, 7, 8, 9, 31, 32, 33, 63, 64, 65, 312, 1000 and
   three odd layouts with idle lanes; output rows and final state compared byte for byte; run once per PD 1 / 2 / 4; plus an
   ignored timing test), `tests/qk_rope_kv.rs` (240 cases: 5 head layouts incl. the 35B's partial rotary and zero-centred
   weights, T = 1 / 2 / 5 / 17, positions 0 / 37 / 4090, bf16 and fp8 caches, host and device position; plus 60 random draws
   of the 35B's 17-row shape at positions up to 16k, against the unfused launch chain; q, both whole caches compared byte for
   byte), registry pin `kernels::tests::round4_selection_is_pinned` (the fused prologue for both models at every row count and
   both cache types, none for groups > 8 or odd widths; v2 for dk = 128 at T = 1 .. 4096, the rows kernel for dk = 64).

## 7. Tried and dropped

* **One-launch split-KV decode** (`attn_decode_bf16_splitkv_v2`, W1): the last split block of each (row, kv head), found with
  a ticket counter, ran the combine, one launch instead of two, bitwise. Slower: 174.6 vs 139.6 us per step at 128-token
  context, 953.8 vs 405.7 us per step at 4k (logs/w1.log vs `decode4k-base`); decode at 4k 129.9 vs 135.7 tok/s. The serial
  merge in one block per kv head costs more than the boundary it saves, and the ticket block was extra (small) resident memory.
  Removed.
* **GDN v2, first cut** (W1): q/k/v of the next 4 / 8 / 16 tokens staged in LDS behind one barrier per chunk. 0.9-1.15x the
  rows kernel (2.00-2.38 us per token); the ISA showed the same waits (`__syncthreads` still waited for the in-flight loads).
  Replaced by the register ring + LDS-only barriers.
* **GDN v2 with compiler-chosen contraction** (W2): state bitwise, a few bf16 outputs per 10^4 off by one ulp; ids4k differed
  from base. Fixed by the explicit FMAs (W3 bisection, W4 bitwise).
* Not attempted (out of the HIP backend, or out of time):
  * further decode fusions need new core ops: MoE combine + next residual norm, `gate_split` + `sigmoid_mul`, GDN conv + delta
    rule; the 3 `__amd_rocclr_copyBuffer` nodes per step (7.4 us) are graph copy nodes of the step's inputs;
  * a persistent decode kernel for the tiny ops (a large new design; graphs already remove the host from the loop);
  * item 3: direct fp8-weight-to-register loads in `matmul_fp8_mma_v2` and the 12-byte-per-lane spill of its 128 x 128 tile.
    `dq_gemm<Fp8PolicyQ>` is now the largest prefill kernel (141 ms, 22 %), so it is the next lever.
