# HIP tp2 prefill: the wht6 lossy all-reduce wire (lane wht6-ar), 2026-11-14

## Lane brief (kept here so it survives context compaction)

- Goal: port radiance's `wht6` lossy all-reduce wire (v2.0.0 ddcb9c6, `libr4d/r4d_ar_oneshot_2rank_wht6.{h,hip}`) for tp=2
  PREFILL on the two R9700s (gfx1201), **opt-in only**. Decode stays on the exact all-reduce.
- Why: lane H27P (LOG row 2026-10-27 03:40) attributes ~35 % of the 27B MXFP4 tp2 4k prefill to all-reduce volume; radiance
  prefills at 6133 tok/s against our 2240. Payoff estimate (unmeasured): 10-15 % on the 35B tp2 prefill.
- Build: 2-rank one-shot all-reduce, wht6 wire, selected by `INTARSIA_HIP_AR_WIRE=wht6`, only for messages >= a size threshold
  (radiance: 128 KiB; tune). Decide the f32-partial question and the fused `ar_norm` question. Both ranks bit-identical.
- Gates (all before "done"): (1) kernel test on two devices: error bound against the exact all-reduce, rank-to-rank
  bit-identity, sizes around the threshold, non-multiples of 64; (2) accuracy, 35B NVFP4 tp2 (27B MXFP4 tp2 if it fits): knob on
  vs off, change-vs-base KL rule, vLLM goldens, greedy-id divergence on a short and a 4k prompt; (3) speed: tp2 prefill tok/s at
  1k / 4k / 16k (35B), 4k (27B), on vs off, same build, alternating, >= 3 rounds, and tp2 decode on vs off; (4) `cargo test` for
  touched crates on the Mac, `cargo build --release -p intarsia-cli --features hip` in the tatooine image.
- Fleet rules: tree on tatooine is `~/intarsiaml-wht6-ar/` (never `~/intarsiaml/` or `~/intarsiaml-gdn-chunk/`); every tatooine
  command through fleetq (owner per lane); builds `--load cpu --mem 0`; GPU work `fleetq acquire --host tatooine --takes-down
  radiance --mem 30 --expect <MIN> --label "intarsiaml hip: wht6-ar <what>" --wait`, stop radiance, `FLEETQ_JOB=<id>` on every
  command, ALWAYS start radiance again, check `curl -s http://tatooine:8080/v1/models`, release. Windows < 45 min, batched in
  scripts, nohup + log, poll <= 4 min; no tool call above 4 min. Never `--force` / `--no-queue`. Kill only own PIDs. `< /dev/null`
  on inner docker / dev.sh commands. At the end remove the docker target volume and scratch on tatooine (the tree may stay).
- Deliverable: small commits on branch `wht6-ar` in `/opt/code/intarsiaml/.worktrees/wht6-ar`. No push, no PR, no merge. Do not
  delete the worktree or the radiance clone (`.worktrees/gdn-chunk-radiance`, read-only). Results here, plus a LOG.md row.
- Final report under 600 words: files, selection, each gate with numbers, what is not done, recommendation (lossy: worth an
  opt-in serving profile or not).

## Summary

- Built: `kernels/hip/allreduce_wht6.hip` (`ik_ar2_wht6`), selected by **`INTARSIA_HIP_AR_WIRE=wht6`** (default `exact`), floor
  `INTARSIA_HIP_AR_WIRE_MIN_KB` (default 128). Off by default; with the variable unset nothing changes (the existing comm suites pass
  unchanged).
- Kernel gate: PASS. Both ranks bit-identical at every size and dtype pair; worst rotated error 0.996 of the codec's bound;
  rms error 1.5-2.0 % of the reduced partial; exact below the floor and for non-multiples of 64.
- Speed (35B NVFP4 tp2, same build, alternating, 3 rounds x 3 reps): prefill **+9.9 % at 1k, +15.6 % at 4k, +15.3 % at 16k**;
  decode unchanged (0.996-0.999 x).
- Accuracy (35B NVFP4 tp2): **the change-vs-base KL rule FAILS** at the default floor, on the short golden (KL 4.72e-3, 1.49 x the
  reference noise, two prompts over their own limit) and on the long golden (3.38e-2, 1.52 x). The vLLM-golden gates still pass
  (short 5.2e-3, long 1.49e-2, floor 3e-2). Greedy ids leave the exact wire's at id 15 (24-token prompt) and id 82 (4.4k prompt).
  A higher floor only moves which prompts are lossy: at 1024 KiB the short golden passes (0.87 x), at 8192 KiB it is exact, and
  the long golden fails the same way (1.54 x).
- Not done: every 27B MXFP4 number (the intarsia-format 27B checkpoint is no longer on tatooine), so the bf16 / GEMM-push
  interplay is unmeasured in a model.
- Recommendation: do not offer it as a serving profile as it is. Keep it as an experimental opt-in knob; see section 6.

Design decisions:

- **Where it runs.** On the wide path's scratch, flags and counters (64 blocks, 20 MiB slots) with `ar2_kernel`'s fence handshake,
  so a lossy launch and an exact wide launch advance the same counters and may follow each other. Extra memory: one local pack
  buffer of 20.3 MiB per rank. A 20 MiB slot carries 26.2 M elements, so a 4096-row f32 chunk of hidden 2048 is one launch (the
  exact wire needs two).
- **Which messages.** Wide-path all-reduces (above the 128 KiB LL limit) of at least the floor and a whole number of 64-element
  groups. Everything else is exact: the 1-row decode step (8 KiB at hidden 2048), the LL path, the all-gather, sizes that are not
  multiples of 64 (the whole message stays exact; no model shape produces one, hidden sizes are multiples of 64).
- **f32 partials are encoded from f32 directly.** The 35B's prefill all-reduces f32 partials (33.5 MB per 4096-row chunk). The
  rotation runs in f32 either way, so the f32 partial costs only its wider load and is not rounded to bf16 before the 6-bit
  quantiser. On the wire that is 5.1x fewer bytes than the f32 partial, 2.6x fewer than a bf16 one.
- **The fused `ar_norm` path** takes at most 16 rows (`ar_norm_shape`), so it carries no prefill traffic: no lossy variant, it
  stays exact. A consequence for decode: a batched decode step stays exact up to 16 rows through the fused path, and through the
  plain path as long as its partial is under the floor (16 rows x 2048 x 4 bytes = 128 KiB is not above the LL limit). A server
  with more than 16 decode rows per step and the plain path would send lossy decode all-reduces at the default floor: raise
  `INTARSIA_HIP_AR_WIRE_MIN_KB` there. Not exercised in this lane (the speed arms ran one stream).
- **The GEMM pre-push** (`INTARSIA_HIP_AR_PUSH`, bf16 partials of the W4A8 GEMM) is not armed for a message the lossy wire takes:
  the two are alternatives for the same message. Only the 27B uses the push; not measured here.
- **Not ported:** radiance's push check (`r4d_archk_*`), the host mailbox mirror, the fused gated-residual writes.
- A run with the wire on prints one `hip tp wire: LOSSY ...` line at start.

## 2. Gate 1: kernel tests (both R9700s) - PASS

`cargo test --release -p intarsia-backend-hip --test ar_wht6 -- --test-threads=1` in the tatooine image, final build
(`raw/tatooine/kt3/wht6.{out,err}`): 4 passed, 1 ignored (the rate benchmark).

- `wht6_wire_is_rank_identical_within_its_bound_and_exact_below_the_floor`: ten sizes (f32 elements 32704, 32768, 32832, 32800,
  40000, 100008, 133120, 614464, 10485760, 26278400: below, at and above the 128 KiB floor, not multiples of 64, a last chunk
  that is not full, fewer chunks than blocks, a 2048 x 5120 chunk, two launches), three dtype pairs each (f32 in place, f32 into
  bf16, bf16 in place), data with outlier channels, near-zero rows and all-zero groups:
  - the two ranks' outputs are **bitwise equal** in every case;
  - below the floor, at exactly 128 KiB and for non-multiples of 64 the result is **bitwise the exact sum**;
  - lossy f32 results: every rotated error element is within the codec's bound (half a step of each rank, step = amax of the
    rank's rotated group / 31, 0.4 % slack for the bf16 scale): worst **0.996 of the bound**;
  - the f32 -> bf16 result is bitwise the f32 result rounded once, and a bf16 partial gives bitwise the code of an f32 partial
    holding the same values.

  | f32 elements | worst rotated error / bound | rms error / rms of the exact sum |
  |---:|---:|---:|
  | 32832 | 0.991 | 1.97 % |
  | 40000 | 0.990 | 1.45 % |
  | 133120 | 0.991 | 1.62 % |
  | 614464 | 0.995 | 1.66 % |
  | 10485760 | 0.996 | 1.68 % |
  | 26278400 | 0.996 | 1.66 % |

- `wht6_floor_and_the_exact_default`: wire off = exact; floor above the message = exact; floor at the message = lossy.
- `wht6_wire_survives_a_delayed_rank_between_exact_collectives`: 30 rounds of ten mixed collectives (LL, exact wide, lossy, bf16
  and f32) with one rank delayed at random: every result bitwise the undelayed round's on both ranks, 0 wrong.
- `wht6_wire_without_the_wait_is_caught_by_the_stress_test` (negative control, drain 9): 106 wrong results (82 in the first
  window), so the stress test does see a stale read.
- The existing suites with the wire unset (`--test comm --test ar_push --test ar_norm`, `raw/tatooine/kt3/comm.out`): 13 + 4 + 4
  passed, 0 failed.

wire, not the load, sets it.

## 6. Not done, not verified, and the recommendation

- **27B MXFP4 tp2: nothing measured.** `/data/models/intarsia` on tatooine holds the 35B NVFP4, the 8B and a 27B DSpine
  checkpoint; the amd Quark MXFP4 27B the tp2 scripts used (`models--amd--Qwen3.8-27B-Quark-AWQ-MXFP4`) is gone (only radiance's
  `.rad` files remain). So there is no 27B accuracy, no 27B 4k prefill number, and the interplay with the GEMM pre-push (which the
  lossy wire replaces for bf16 partials) is unmeasured in a model. At kernel level the bf16 2048 x 5120 all-reduce goes from 838
  to 389 us, but the push path already hides part of the exact all-reduce behind the GEMM, so the 27B gain cannot be read off that.
- Batched decode above 16 rows per step with the wire on: not exercised (see section 1).
- The graph-captured and recorded-plan paths were exercised only as far as `serve` and `accuracy` use them; no dedicated test.
- `intarsia kernels test` has no two-device harness, so gate 1 is the dedicated `tests/ar_wht6.rs`.
- Fleet: six short fleetq windows with radiance down, about 14 minutes in total (the longest 5.8 min); radiance answered after
  each. The docker target volume `intarsia-cargo-target-wht6-ar` and the log scratch on tatooine are removed; the tree
  `~/intarsiaml-wht6-ar/` is left.

**Recommendation.** As ported (6 bits) this is not worth a serving profile: it buys 10-16 % of prefill on the 35B and fails the
project's own change-vs-base accuracy rule on both goldens, with greedy output changing within the first 15 to 82 tokens. Keep it
merged only as the experimental opt-in it is (default exact, a LOSSY line in the log), or leave the branch unmerged. If the prefill
gain is wanted, the cheaper next step is a wider symbol in the same kernel rather than a floor: 8-bit symbols pack as four 16-byte
words per lane and chunk (the layout stays coalesced), cut the quantiser error 4x (so the KL roughly 16x, to about 0.1 x the
reference noise by that scaling), and still send 3.9x fewer bytes than the f32 partial; from the rate table that keeps most of the
35B gain. That is an estimate, not a measurement, and it is not radiance's wire. For the 27B the question is open until its
checkpoint is back on tatooine.
