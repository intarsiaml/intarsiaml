# mcdiag: why MTP graph steps get slower after a copy chain (CUDA, Qwen3.6-35B-A3B NVFP4, spark1)

## Lead from the coordinator (mcopym, PR #435, Metal): checked first

On Metal the slowdown after a chain does not happen (fresh server: n20 1.012x, knob-on with no chain firing 0.991x, 3 rounds x 5 reps). On Metal the MTP step is not a
captured graph; on CUDA it is. Lead: state the CUDA graph keeps after a chain rollback (re-capture, invalidation, a changed pointer or shape forcing re-instantiation,
the graph falling back to eager launches after the chain). Not a proven cause.

**Checked with the nsys traces (`raw/nsys1/`, `scripts/mcdiag/recap.py`, `raw/nsys1/recap.txt`): ruled out on CUDA.** `generate`, code-gen, 500 tokens, one forced
chain pass (`INTARSIA_SPEC_COPY=256` + `INTARSIA_SPEC_COPY_PROBE=100`: a bogus 8-row chain at position 168, accepted 0, greedy ids equal the base run's), nsys
`--cuda-graph-trace=node`, two runs:
- Graph launches = replays = traced graph steps (181 / 181 / 180), exactly one eager burst between replays after the warm-up (891 kernels = the chain pass, after replay 35);
  no eager kernels in any later gap, so no fallback to eager launches. `intarsia_graph_*` counters agree: `captures 4` in the base and the probe run, `eager decode steps=0`.
- The `captures` field of the trace (spec-step captures so far) is 3 at the first and at the last traced step: no capture and no invalidation after the chain.
- Three recordings (the head's queued row count n = 1, 2, 3), identical before and after the chain: the same graph node ids with the same grid, block, dynamic shared
  memory and register count for every node; no recording after the chain that was not there before (pre 3, post 3, 0 new).
So the graph is not re-captured, re-instantiated or bypassed; what moves, if anything, is the time the same nodes take (below).
