# mcdiag: why MTP graph steps get slower after a copy chain (CUDA, Qwen3.6-35B-A3B NVFP4, spark1)

Lane `mcdiag`, branch `mcdiag` from origin/main `cc7c8026` (includes mcopy2). Measured on spark1 (DGX Spark GB10) with vLLM up beside it (fleetq,
`--quiet gpu,cpu`). Raw output: `docs/results/2026-11-17-mcdiag/raw/`; scripts: `scripts/mcdiag/`. Opt-in only, nothing default-on.

**Result: not found, no fix.** The slowdown is real and reproducible, but nothing this lane could look at explains it. It is not graph state, not the
queued head rows or position, not the GPU clock, and it is not per request: it outlasts the request that ran the chain. What is left (and was not
measured, see the end) is process or device level state that the chain pass leaves behind. No code change that fixes it is proposed; the PR carries
measurement hooks (all opt-in, listed in `docs/tuning.md`) and the scripts, so the next lane can start from the repro.

## The effect, measured

Greedy ids are equal in every arm below (same sha per request across arms and rounds, `raw/*/` logs; `generate` ids equal over 800 tokens).

1. **Real chains, served** (`raw/real3/`, `scripts/mcdiag/real_an.py`, 4 rounds x 8 reps of code-gen 800 tokens, arms base / n256 / n20 in one server each,
   `INTARSIA_SPEC_TRACE=1`). Every graph step of an n20 request is compared with the same position bin (50 tokens) of the same request in the base server of the
   round (same prompt, greedy: same tokens, same positions):

   | n20 minus base, ms per graph step | mean | sd | bins |
   |---|---|---|---|
   | no chain has run yet in this server process | -0.046 | 0.188 | 81 |
   | a chain pass has run earlier in this process | +0.175 | 0.253 | 367 |
   | n256 (knob on, no chain fires), all bins | -0.035 | 0.125 | 448 |

   Per round (not seen / seen): r1 +0.06 / +0.15, r2 -0.06 / +0.12, r3 -0.11 / +0.25, r4 -0.03 / +0.20. Decode tok/s of the same run, median of 8 reps per
   round: n256 / base = 0.9992, 1.0036, 1.0038, 1.0030 (median 1.0033); n20 / base = 0.9873, 0.9899, 0.9874, 0.9807 (median 0.9873). The n20 chains ran 35 times;
   an 8-row chain pass costs 27.2 ms (mean, max 33.4 ms, trace line `spec: copy pass 8 rows`), accepted 0 to 7 (0:9, 1:10, 2:12, others 4).
2. **No dose response** (`raw/real3-dose.txt`): the difference is +0.31 ms with 1 chain seen so far, +0.19 with 2-3, +0.11 with 4-6, +0.21 with 7+; chains that
   accepted 0-3 tokens so far +0.17, 4+ +0.18. One chain, even a missed one, is enough; more chains do not add.
3. **No decay with position** (`raw/real3-posdep.txt`): n20 minus base after a chain, by 100-token position bin from 100 to 800: +0.20, +0.21, +0.18, +0.17,
   +0.13, +0.16, +0.16, +0.27. Before any chain: -0.07 .. +0.11. The offset does not shrink over the 600+ steps that follow.
4. **One forced chain in `generate`** (`raw/gen1-analysis.txt`, `INTARSIA_SPEC_COPY=256 INTARSIA_SPEC_COPY_PROBE=150`, a bogus 8-row chain at position 220, 800
   tokens): mean step before the chain +0.014 vs the no-chain run at the same positions, in the chain's bin +0.31, after it +0.21, +0.16, +0.18, +0.20, +0.17 (the
   last bin +0.01, 50 steps). Run 2 of the pair: +0.35 over all later steps. The host gap stays 3-4 us (median pre 0.004, post 0.003, max 0.009 ms), graph
   steps 282 of 282, captures 3 before and after. mcopy2's repro stands.

## Hypotheses

**1. Memory placement (eager 8-row pass allocates, touches scratch, uses save rows past k).** Not tested directly (no allocation or L2 counter in this build). The
plan differs only in `scratch_bytes` (mcopy2); what was tested is the trigger. A single eager MTP step
(probe kind `e`, `INTARSIA_SPEC_COPY_PROBE=450,e`: the step runs outside the graph, through the same eager verify code, no chain) carries over -0.011 ms in
`raw/s6-analysis.txt` and +0.076 in `raw/s3-analysis.txt`; a catch-up-only probe (kind `c`) +0.089 (s3). Those are inside the noise (below), so the chain
pass's eager launch is not shown to be the trigger, but not excluded either.

**2. Graph re-capture, re-instantiation, fallback to eager (the Metal lead, mcopym, PR #435): ruled out on CUDA.** nsys with `--cuda-graph-trace=node`
(`raw/nsys1/recap.txt`, `scripts/mcdiag/recap.py`), code-gen, 500 tokens, one forced chain at position 168, two runs:
- graph launches = replays = traced steps (181 / 181 / 180); exactly one eager burst between replays after the warm-up (891 kernels, the chain pass); no eager
  kernel in any later gap, so no step falls back to eager launches;
- the spec-step `captures` field of the trace is 3 at the first and the last step, `intarsia_graph_captures_total` 4 in base and probe runs, `eager decode
  steps=0`: no capture and no invalidation after the chain;
- three recordings (queued head rows n = 1, 2, 3), identical before and after: same graph node ids with the same grid, block, dynamic shared memory and
  register count for every node; no recording after the chain that was not there before (pre 3, post 3, 0 new).

**3. Head state (queue offset or KV position after `mtp_catch_up`): ruled out as the cause.** (a) The trace line now carries the queued rows `n` and the
position `len` (`INTARSIA_SPEC_TRACE`): mean `n` is 2.72 before and 2.84 after the chain in the probe run, 2.82 in the base run; the n mix is not what moves the
time (by-n means, `raw/gen1`, n=3 steps after position 220: base 18.26 / 18.23, probe 18.26 / 18.59, runs r1 / r2: the same n, a different time in r2). (b) The slowdown outlives the request: with `INTARSIA_SPEC_COPY_PROBE_ONCE=1`
the probe fires in one request of the server and the 6 requests after it (fresh KV, fresh head queue) are still slower in `raw/s5-analysis.txt`: bogus-chain
post minus pre +0.12 ms, n20 +0.11, n256 +0.04 (3 rounds of 18 request pairs, per-request sd 0.13-0.20, so each mean is +-0.04). mcopy2's "for the rest of the
request" is too narrow: the state is per process or device.

**4. Clock or power state: no evidence.** `nvidia-smi` sampled every 200 ms beside the four `generate` runs (`raw/gen1/*.smi`): SM clock 2392-2483 MHz in all
runs (modal 2405-2418), no step down after the chain, power 14-15 W average in all four, no difference between probe and base runs. The offset does not
decay with position (item 3 above), so it is not a transient.

## What did not work as a measurement (so nobody repeats it)

- **nsys per-kernel difference-in-differences cannot resolve 0.2 ms here.** Comparing post-chain with pre-chain replays, probe against base (`raw/nsys1/nsys-did.txt`,
  `scripts/mcdiag/nsys.py`): span DiD +404 us and kernel-time-sum DiD +317 us (pair 1), +231 us and -219 us (pair 2). The null, base-r1 against base-r2 (same
  run twice, no chain), gives -486 us span and -659 us kernel sum. Run-to-run variation (with only 17 pre-chain replays of a 500-token run) is larger
  than the signal, so no kernel can be named from these traces. A longer run with the chain early (about 120 pre-chain replays) and more repeats of the same
  arm is needed first.
- **One-event probes are near the noise.** Single bogus chain per process, 3 rounds: chain +0.08, catch-up only +0.09, eager step +0.08 (s3), bogus +0.12, n20 +0.11 (s5),
  bogus +0.05, n20 -0.003, n256 -0.04 (s4, 2 rounds), eager -0.011 (s6). The sd of a request-pair difference is 0.13-0.20 ms, with 18 pairs per arm the standard error
  is 0.03-0.05, so differences between the probe kinds (+-0.1) are not resolved. The real-chain pool (item 1, 367 bins) is the one clean signal.
- **Core placement is as large as the effect and was not separated.** `taskset` to the Cortex-X925 cores 5-9 (`baseP`) vs unpinned, 3 rounds (`raw/s6-analysis.txt`):
  pinned is 0.03 ms faster before and 0.13 ms faster after the event; pinned to the A725 cores 0-4 it is 0.15 ms slower. With the event pinned to the X925 cores the
  carry-over is +0.06 ms, unpinned +0.12 (s5 bogus) / -0.01 (s6 eg). A decode thread that the scheduler moves to a slower core after the chain pass would look exactly like
  this; the data here is not enough to say it does (`scripts/mcdiag/cpusample.py` exists for the per-core trace, it was not run on a probe arm).

## Left undone, and the next measurement

- The `INTARSIA_SPEC_GRAPH=0` pair (mcopy2's second proposed measurement) is half done: `probeg0` (graphs off, one chain) ran, there is no `baseg0` to compare with
  (the eager step has no `mtp graph step` trace line, and `generate`'s decode ms differs by arm: 5.55-5.60 s probeg0 vs 5.16-5.18 s base, which is the graph-on gain, not the chain).
- The chain-length sweep (probe kinds `3`, `5`, `8`: is the trigger the 8-row pass, or any chain or rollback?) was prepared (`intarsia-b` supports it,
  `scripts/mcdiag/serve2.sh`) and not run: spark1 went unreachable (fleetq: all hosts offline at 20:51, ping to the gateway fine) before it could be queued.
  Suggested run: arms `base`, `L3`, `L5`, `L8` with `INTARSIA_SPEC_COPY=256+INTARSIA_SPEC_COPY_PROBE_ONCE=1+INTARSIA_SPEC_COPY_PROBE=450,<L>`, 4 rounds,
  `scripts/mcdiag/serve2.sh`; analysis `scripts/mcdiag/serve2_an.py`. If only L8 is slow the trigger is the verify pass's row count (save rows past k, the
  multi-row kernels: 891 eager kernels vs the 1002-node step); if all lengths are slow it is the chain/rollback path.
- A `taskset` or `cpusample.py` run on a real n20 arm, to see whether the decode thread's core changes after the first chain.

## Fix size

None proposed: without a root cause nothing here is small and safe. The flip bar (code-gen at least 0.995x, agent-edit at least 1.03x with knob n20) is
not reached: code-gen stays at about 0.987x (n20 / base median of rounds above, 800-token code-gen, served, 4 rounds x 8 reps); agent-edit was not re-measured.
The ids gate (7 cells), `plan show --json` and the ABBA speed A/B of the task were not run, since there is no fix to gate.

## What the PR adds

- `INTARSIA_SPEC_COPY_PROBE=<g>[,<what>]` and `INTARSIA_SPEC_COPY_PROBE_ONCE=1`: measurement hooks, opt-in, ignored without `INTARSIA_SPEC_COPY`; docs/tuning.md rows.
- `INTARSIA_SPEC_TRACE` graph-step lines now also print `n`, `len`, `captures` and a wall-clock stamp; a `spec: copy pass <rows> rows <ms>` line for chain passes.
- `scripts/mcdiag/`: build, `gen.sh` (one-chain repro, nsys / smi / taskset options), `serve2.sh` (event inside a request series), `ab.sh`, analyzers.
- Checks run: `cargo check -p intarsia-core --tests`, `cargo test -p intarsia-cli --test docs_env_vars` (env-var drift test), the CUDA release build on spark1, and the
  runs above with greedy ids equal to the no-probe arm. Not run: the repo's full CUDA test suite, the 7-cell ids gate.
