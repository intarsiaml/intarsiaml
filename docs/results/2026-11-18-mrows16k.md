# mrows16k: where the 16-row verify pass of the copy chains spends its time on Metal (Qwen3.6-35B-A3B NVFP4, endor)

Lane `mrows16k`, branch `mrows16k` from origin/main `835796344`. Measurement first; any change is opt-in, nothing is default-on.
Measured on endor (Apple M5 Max, macOS 27.0), `Qwen3.6-35B-A3B-NVFP4`, tp 1, every run in a `fleetq` slot (`--quiet gpu,cpu`). Raw: `docs/results/2026-11-18-mrows16k/raw/`; scripts `scripts/mrows16k/`.

## 1. Profile: the 16-row pass against the 8-row pass

Method (`scripts/mrows16k/prof.sh`, `prof-all.sh`, `passtable.py`): `generate --spec mtp --spec-k 2` with `INTARSIA_SPEC_COPY=20,<len>` on the copy3k prompt (2969 tokens, greedy, 700 new tokens), `len` 7 (8-row verify passes, 85 of them) and `len` 15 (16-row passes, 42), traced with
`INTARSIA_METAL_PROFILE` (the engine's GPU-timestamp trace, `docs/tuning.md`): `kernel:` (every launch its own command buffer, so launches never overlap; each record carries Metal's fixed per-command-buffer cost of a few us) and `cb:` with
`INTARSIA_METAL_COMMIT_EVERY=1` ("ce1": launches stream as in a normal run, one command buffer each; consecutive independent launches overlap, so a launch's time is attributed from the later of its start and the previous launch's end, which makes the classes sum to the pass span).
(A plain `cb:` trace of each run was also taken, not used and not kept.) A pass is the records from `embedding_bf16` to `argmax_f32`; classes are by op name (and, for matmuls, shape). Real (unprofiled) pass times are the engine's own `spec: copy pass N rows X ms` lines of the `none` runs.

Unprofiled pass time, median (`raw/prof/none-copy3k-L*.err`): **8 rows 21.07 ms (85 passes), 16 rows 39.16 ms (42 passes) = 1.86x**, so the extra is 18.1 ms. (A 3-row MTP verify pass is 8.3 ms, a 1-row step about 8 ms.)
The traced runs show the same ratio: ce1 span 23.32 ms and 44.09 ms (1.89x; the trace itself adds about 2 to 5 ms), kernel-mode sum of launch times 23.26 and 43.21 ms (1.86x).

Per op class, ms per pass, and each class's share of the extra (ce1, overlap-free; kernel mode in the next two columns, which agrees within a few points; launches per pass 8 -> 16 rows):

| dense fp8 GEMM (GDN qkv / z / out, attention q / k / v / o) | 4.96 | 9.69 | 4.73 | **22.8 %** | 4.86 -> 9.65 | 130 -> 260 |

Reading it:
- **Nothing is spread thin and nothing is a single fixable cost: almost every class doubles, because the verify rows are row-exact (bitwise the 1-row decode) and the kernels get their exactness by doing each row's math separately.** Dense fp8, lm_head, the GDN loop and the copies are exactly 2.0x; the 16-row dense matmuls are two 8-row launches (`row_chunks`), the GDN block is a row loop of three launches per row (conv, delta rule, snapshot copy) on Metal.
- **MoE (28.8 %)** is the largest class and not a 16-row-specific cost: the routed experts read each distinct expert's weights once per layer and a 16-row pass touches more of them (trace, `moe_experts_bf16_rows` launches of the passes: 39.6 distinct experts per layer on average at 8 rows, 60.8 at 16, 1.5x; gate/up 123 -> 210 us, 1.7x; down 70 -> 131 us, 1.9x, so a little more than the union growth, the rest is per-pair work). Cutting it means a faster per-pair expert kernel at every row count, not a 16-row variant.
- **Dense fp8 (22.8 %)** is the one class where a cheap exact change exists: its shader (`fp8_rows_mmt_*`, simdgroup matrices) is templated on the row tile `R` (R = 1 is the 8-row form that runs today) and the source says "R = 2 (16 rows) is not instantiated". The profile above shows its two 8-row launches at the same per-launch cost as one (55 vs 57 us on 8192 x 2048), and `docs/results/2026-11-17-mchunkx.md` table A shows the 5..8-row form is flat in rows (the cost is the weight pass, not the MMAs).
- GDN loop + snapshot copies (23 % together) is the next candidate: a fused Metal `gdn_verify_rows` like the CUDA one (conv + delta rule in one launch, snapshots written inside) is a new kernel and was not attempted here. lm_head (9.9 %) is near-linear per row (mchunkx table A, `nvfp4_head_35b`: 257 us per row at every M), so one launch of 16 rows would not help. Attention (6.7 %) is two 8-row launches at about 144 us each (a 3-row launch is about 66 us), so a single 16-row launch would also be about 2x: nothing to gain, which also closes mrows16's "fix (2)".

## 2. The one candidate fix, tried: one launch of a 16-row fp8 tile (R = 2) is SLOWER than today's two launches of 8; not kept

Idea (the only class with a cheap exact change in sight, 22.8 % of the extra): `matmul_fp8_gemv_rows` for 9..=16 rows as ONE launch of the R = 2 instantiation of the simdgroup-matrix shader `fp8_rows_mmt_*` (the template already takes `R`; q(x) padded to 16 rows, two 8-row accumulator tiles per threadgroup, each row's per-block chains and fold unchanged), so the weight decode is shared by 16 rows.
Implemented opt-in (`INTARSIA_METAL_FP8_ROWS16=1`, off by default; 2 new entry points, launcher, scratch rounding, `chunk_sizes` returning no split) and tested bitwise: `fp8_rows16_is_bitwise_the_one_row_gemv`, 960 cases, 12000 rows (M 9..=16, the 10 fp8 shapes, both weight layouts incl. NaN codes, f32 and bf16 out, is 0 / 0.37 / 2.0, aligned and unaligned x, unaligned scratch) all equal the 1-row `matmul_fp8_gemv`; both negative controls (two rows of the second tile swapped; q(x) skipped) differ (16336 and 64292 of 106496 bytes). The existing fp8 tests still pass. **Exact, but not faster.**

Micro timing (`timing_fp8_rows16`, one 35B decode step's fp8 launches: 40 x 8192x2048, 30 x 4096x2048, 40 x 2048x4096, 20 x 512x2048, weights cycled through 400 MB of copies, quiet fleetq slot, thermal level 0 before and after; two runs, `raw/timing-fp8-rows16-run1.log`, `-run2.log`, identical to 0.1 %), us per step:

| rows | today (split: halves; 7+2, 8+2, 8+3, 8+4 at 9..12) | one 16-row launch | ratio |
|---:|---:|---:|---:|
| 8 (one launch) | 4571 | n/a | |
| 9 | 7349 | 10339 | 1.41x |
| 12 | 8224 | 10404 | 1.27x |
| 16 | 8965 | 10383 | **1.16x (slower)** |

Per shape at 16 rows: 8192x2048 4226 -> 4937 us, 4096x2048 1805 -> 2128, 2048x4096 2585 -> 3045, 512x2048 350 -> 272 (only the 512-row shape wins). The 16-row launch costs 2.27x one 8-row launch (the kill bar was 1.6x), against 1.96x for two 8-row launches. The kernel is not weight-pass-bound once the row tile doubles: the cost of the 5..=8-row form is flat in rows only because q(x) is padded to 8. Likely cause (inferred from the kernel, not measured): every threadgroup of 8 outputs re-reads all the q(x) rows from device memory (33 MB per 8192x2048 launch at 8 rows against 16 MB of weights), so that traffic and the per-row MMAs grow with the tile; staging q(x) in threadgroup memory would be a redesign, not the small change the brief allows.
**Verdict: not kept.** The engine code is not in this PR (`git apply` the patch to reproduce: `raw/rows16-experiment.patch`, kernel + launcher + tests + the timing test; it is exact and opt-in, just slower).

## 3. Verdict

- **The 16-row verify pass costs 1.86x the 8-row one (39.2 vs 21.1 ms unprofiled) because nearly every class of the pass doubles: the row-exact kernels do each row's math separately.** No single class is a cheap exact win: MoE (29 % of the extra) is per-pair expert work, dense fp8 (23 %) is two 8-row launches that a single 16-row launch does not beat (section 2), the GDN row loop plus its snapshot copies (23 %) is 3 launches per row, lm_head (10 %) and attention (7 %) are per-row or per-launch linear.
- **What this means for the copy chain on Metal:** the +7.7 % (copy3k) / -4.2 % (json-xform) of `len` 15 against `len` 7 in mrows16 is the cost curve of the pass, not a missing 16-row kernel: a 16-row pass emits up to 16 tokens for 39 ms (about 410 tokens/s at full acceptance) and an 8-row pass 8 for 21 ms (380). Closing it needs a cheaper per-row pass, not a bigger one.
- **Next candidates, ranked by share of the extra (none attempted):** (1) the GDN row loop and its rollback snapshot copies, 23 % together: a fused Metal `gdn_verify_rows` (the CUDA backend has one: conv + delta rule in one launch with the snapshots written inside) would remove about 1.4 launches per row; (2) MoE expert kernel throughput (29 %), which pays at every row count; (3) fp8 / lm_head per-row cost (33 % together), which also needs the per-row work to drop, not the launch count.

## Gates

No engine code changed in this PR (docs, scripts and raw data only), so the code gates do not apply: no new `INTARSIA_*` variable (the experiment's `INTARSIA_METAL_FP8_ROWS16` is only in the patch, so no `docs/tuning.md` row), `plan show --json` is trivially the same binary as origin/main, no speed A/B (there is no new arm). The experiment itself passed its own bitwise tests (section 2) before being dropped on speed.

## Not done / unverified

- The profile is of copy3k on one prompt (2969 tokens, acceptance about 99 %); expert counts and attention cost depend on the context length and on what the rows route to (json-xform was not profiled).
- Kernel-mode per-class times carry Metal's fixed per-command-buffer cost (most for the small launches: the GDN loop and the copies); the ce1 attribution is overlap-free but still includes about 0.8 us per launch of profiling cost. The classes agree within a few points between the two, and the real pass totals come from unprofiled runs.
- The cause of R = 2 being slow is an inference from the kernel's loads, not a measurement; a Metal GPU capture was not taken.
- A fused Metal GDN verify kernel, a faster expert kernel and a threadgroup-staged R = 2 fp8 kernel were not tried.
