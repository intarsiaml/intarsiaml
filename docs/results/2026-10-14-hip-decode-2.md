## 2. What was built

Four fused decode ops. They are **new core ops** (`Op::MatmulPair`, `MatmulFp8Pair`, `MatmulNvfp4Glu`,
`GatedRmsnorm`) that only the HIP backend implements; the model asks the registry for the fused kernel and falls back to
the unfused ops when there is none. CUDA is untouched: its table test lists the four ops as optional,
`cargo check --workspace` builds, and `INTARSIA_NO_FUSION=1` turns fusion off on HIP too (also off under tensor
parallelism).

| fused op | replaces | where used | launches saved/step |
|---|---|---|---|
| `matmul_fp8_pair_gemv` | 2 x fp8 GEMV of one x | GDN `in_proj_qkv` + `in_proj_z` (30 layers), attention k + v (10) | 40 |
| `matmul_pair_bf16_gemv` | 2 x bf16 GEMV of one x | GDN b + a (30), MoE router + shared-expert gate (40) | 70 |
| `matmul_nvfp4_glu_gemv` | shared gate GEMV + up GEMV + silu_glu | shared expert (40) | 80 |
| `gated_rmsnorm_bf16` | rmsnorm + silu_glu | GDN output norm (30) | 30 |

`ExecRunner::run_fused` / `Model::try_fused` (model.rs) is the fallback hook: `call.check()` + `Registry::select`
(the lookup `exec` makes, so plan recording and admission see exactly the calls that run), `Ok(false)` when there is no kernel.

Each fused kernel runs the **same arithmetic in the same order** as the kernels it merges (blocks `[0, nb0)` run the
first matrix and the rest the second through the very same `gemv_body` / `fp8_gemv_body` that the unfused kernels use; the
glu kernel keeps one warp per row for gate and up, rounds both to bf16 as the GEMV store would, then applies
`silu_glu`'s expression `ik_silu`; the gated norm is `rmsnorm_kernel` followed by `silu_glu_kernel` with the bf16 rounding of
the normalised value in between). So the outputs are **bitwise** the unfused outputs, which is why the 35B accuracy is unchanged
to the last printed digit (section 4).

Not on the list, deliberately: the GDN a/b gates are not merged with qkv/z (dense bf16 vs fp8 weights, different kernels),
and gate_split + sigmoid_mul are 10 layers only (10 + 10 launches, 0.4% of kernel time).

Files: `kernels/hip/{matmul,fp8,nvfp4,norm}.hip`, `ik_hip.h` (`ik_silu`), `kernels/abi/ik_abi.h`, hip crate
`ffi.rs` / `device.rs` / `quantmoe.rs`, core `ops.rs`, `quant/{ops,cases}.rs`, `model.rs`, `model/gdn_block.rs`, `quant/moe.rs`, cpu
`fused_ref.rs` (the CPU reference is the composition of the unfused ops: `ref_*` is the f64 oracle, `cpu_f32_*` the f32 one).

## 4. Gates

* **Fused kernels vs the launches they replace**: `crates/intarsia-backend-hip/tests/fused_decode.rs` (4 tests, GPU) require
  *bitwise* equality with the unfused GPU kernels and rel_l2 < 1e-3 / 6e-3 against the cpu `ref_*` kernels, at the model's shapes
  (8192x4096x2048, 512x512, 32+32, 256+1, 512x2048 glu, d=128 norm) and at edges (segment shorter than one block, odd N, K=4112 past the
  prefetch window, scalar norm path d=130, W8A8 and W8A16 in one call, different weight and input scales per segment, different
  global scales for gate and up). 4 passed.
* **Mutations** (`scripts/hip-decode/mutate.py`, `remote.sh mutate`; each applied to a copy of the tree, built and run), all six
  FAIL the intended test: `pair-block` (second matrix starts one block late), `fp8-pair-scale` (second segment uses the first's
  scales), `glu-scale` (up scaled with gate's global scale), `glu-round` (gate not rounded to bf16 before silu), `gated-order`
  (silu applied to the wrong operand), `gated-round` (normalised value not rounded). The seven earlier mutations still target
  `decode_v2`; the new ones run `fused_decode` (`mutate.py x --test-of <name>` selects the target).
* **Admission**: the four kernels are registered with the registry (Deterministic, bf16 budget) and swept by
  `intarsia kernels test` / plan-time admission (`quant/cases.rs` builders for the sweep and for exact planned shapes): hip
  `kernels test` on the 35B in `qualify` (model shapes): 38 kernels, 613 cases, ADMITTED; quick 35B sweep: pair 3, fp8 pair 9, glu 3,
  gated norm 2 cases, ADMITTED; full 8B sweep: pair 6, fp8 pair 15, glu 6, gated norm 16 cases, ADMITTED (626 cases, 38 kernels).
* **35B accuracy** (`accuracy --backend hip --mode both`, golden `qwen36-35b-a3b-nvfp4-vllm-top20.safetensors`, `--max-seq 4096`):
  prefill top-1 98.54%, KL(21-way) 6.349e-3; **decode top-1 99.38%, KL(supp) 9.962e-3**, KL(21-way) 1.074e-2: the same numbers
  as before the change, floor verdict PASS, golden gate PASS.
* **8B fp32 goldens**: `qwen3-8b-fp32`: prefill top-1 100.00% KL 2.335e-4, decode 100.00% KL 3.626e-4, PASS;
  `qwen3-8b-long-fp32`: prefill 99.58% KL 3.966e-4, decode 100.00% KL 3.573e-4, PASS.
* **Graph replay == eager**, 35B, 256 greedy tokens: `GRAPH == EAGER: the 256 generated token ids are identical`
  (graph run: 256 replays, 1 capture, 134.99 tok/s; eager `--no-graphs`: 131.11 tok/s). The fused kernels take only
  tensor arguments, so they capture like any other launch.
* CPU side (Mac): `cargo check --workspace` and `cargo check -p intarsia-cli --features hip` pass. `cargo test --workspace` on the Mac
  passes everything except the tests that load a model through the memory planner (`intarsia-models`, `intarsia-cli real_model`):
  they fail with `only 0 MiB free ... cannot hold a 16-token context`, a host-memory reading of this Mac. The same suite
  (`cargo test --release --workspace --exclude intarsia-backend-hip`) in the tatooine dev image: 0 failures.

## 5. Not done / uncertain

* **fp8 GEMV tuning (candidate c) was not attempted.** The earlier sweep stage already covers rows per warp and staging variants for
  the v2 kernel; the pair kernel inherits the default (2 rows/warp). The remaining 50 fp8 launches (19.8 us avg) are
  where a wider-load or 1-row-per-warp variant for N=2048 (o_proj / out_proj: 128 blocks) could pay; not measured.
* Further launch candidates, in order of launches saved per step: moe_combine into the shared-down GEMV epilogue (40),
  topk with the router (40, needs a single-block reduction over 256 logits), conv + delta rule (30), rope + kv_append + qk_norm on
  the 10 attention layers (about 50).
* `intarsia kernels test --backend hip --model <35B> --quick` exits non-zero ("kernel admission failed") because
  `attn_prefill_bf16_flash` runs 0 cases in the quick 35B sweep (its predicate needs m > 16 and the quick sweep draws smaller chunks;
  `all_pass` treats a 0-case kernel as not admitted). Every kernel that runs a case is ADMITTED, including the four new ones. I did not run this exact
  command on the base tree, so I cannot say the exit code is unchanged; `qualify`'s own kernels stage (on the model's shapes)
  passes. Not touched.
* The unstamped binary and the dirty tree mean the baselines written by `qualify` are marked unstamped.
