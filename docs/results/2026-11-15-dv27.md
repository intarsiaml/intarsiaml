## The 27B `--max-batch 2` + batched MTP failure (`no kernel for matmul_mxfp4 ... m=6`), for the coordinator's fix lane

**Command and env** (smoke, fleetq #9393, `raw/smoke/job.log` lines for `V65536.s-b2`; `serve-V65536.s-b2.log`, `serve-V0.s-b2.log`):
`INTARSIA_BATCHED_MTP=2 INTARSIA_BATCHED_VERIFY=1 INTARSIA_VERIFY_TOPK=1 intarsia serve --backend cuda --model ~/models/Qwen3.8-27B-Quark-AWQ-MXFP4 --max-seq 8192 --mem-budget 30 --profile-every 0 --max-batch 2 --spec mtp --spec-k 2 --mtp-draft-vocab N`
(N = 65536 and 0 both fail the same way; all three env variables and `--max-batch 2` were set; the 35B's opt-in set from `docs/results/2026-11-14-mtp2s.md`). The server logs `batched MTP N=2` and `batched MTP: sampled requests ... seed-exact`, starts, and fails at the first request.
Server log: `[watchdog] engine failed (no kernel for matmul_mxfp4 on cuda/sm_121 (m=6 n=10240 k=5120 act=Some(Bf16) w=Some(U8)) [admitted kernels only] [row-exact verify kernels only]); exiting for restart`, then `[supervisor] signal 15`.

**Why m = 6.** `INTARSIA_BATCHED_VERIFY=1` verifies the two drafting sequences in one pass: 2 sequences x (1 + 2 drafts) = 6 rows. The dispatch table has a kernel for m = 6 on this op (`crates/intarsia-backend-cuda/tests/rows_registry.rs:176-178`, the `ROWS_PINS` snapshot:
`matmul_mxfp4 w4a16 k=5120 -> bf16: 1..=1 matmul_mxfp4_gemv_rows; 2..=4 matmul_mxfp4_gemv_mr_rows; 5..=4096 matmul_mxfp4_gemv_rows`; kernels registered at `crates/intarsia-backend-cuda/src/kernels.rs:1203-1204`, the `_mr_rows` multi-row GEMV is documented as M = 2..=4 at `kernels.rs:282`),
but the server loads with admission on plan shapes and **admitted kernels only** (`crates/intarsia-cli/src/common.rs:497`, `registry.rs:391` `[admitted kernels only]`), and the plan probes only verify row counts `2..=verify_rows()` (= 3 for k = 2) and batch row counts `2..=batch_rows()` (= 2) (`crates/intarsia-core/src/plan.rs:272-280`).
So `matmul_mxfp4_gemv_rows` at m = 6 is never admitted (untested) and is skipped by `require_admitted` in the registry lookup (`crates/intarsia-core/src/registry.rs:360-396`). The m-sizes with a row-exact kernel in the table: 1, 2-4 (mr) and 5-4096 (gemv_rows); the m-sizes admitted at runtime on this server: 1 (decode), 2-3 (verify), 2 (batched decode), plus the prefill shapes.
This is a reading of the code and the failing log, not a tested fix: the plan probe not covering `batch_rows x verify_rows` rows would be the thing to check.

**Can the 27B's shipped defaults reach it? No (opt-in only).** `recipes/qwen3_5_vl.toml` has no `batched_mtp` key (the 35B's `qwen3_5_moe.toml` sets `batched_mtp = 1`, which never has two sequences verify together). With no env, a `--max-batch > 1` server does not draft the 27B at all (`crates/intarsia-core/src/engine/batch.rs:967-970`: `--spec mtp` with the batching engine needs `INTARSIA_BATCHED_MTP=N`), and plain batched decode only runs m <= `--max-batch` rows. Reaching m = 6 needs both `INTARSIA_BATCHED_MTP=2` (or higher) and `INTARSIA_BATCHED_VERIFY=1` explicitly. Whether `INTARSIA_BATCHED_MTP=2` alone is enough or `BATCHED_VERIFY` is required is tested by smoke2 (#9460), below.

**Clean request error or crash? An engine failure, then a server exit.** The failing step is an engine step, so the watchdog marks the engine failed and exits for the supervisor to restart (`engine failed ...; exiting for restart`). In-flight requests are ended with an `Ev::Err("engine failed: ...")` event (`crates/intarsia-core/tests/fault_inject.rs:165-172`), then the process exits: it is not a per-request error, the server restarts. In this smoke the speed client saw no successful request (`StatisticsError: no median for empty data` in `speed.py`, i.e. every request failed) and the next arm's server started fresh, so the damage was one server exit per start, not a hang. I did not capture the client's HTTP-level error text (speed.py discards it on failure).

## Results: single stream, the shipped shape (CUDA, spark1, 27B Quark MXFP4, `serve` + `--spec mtp --spec-k 2 --mtp-draft-vocab N`)

Method: eight visits in ABBA order (`V65536 V98304 | V131072 V0 | V0 V131072 | V98304 V65536`, fleetq #9466 #9467 #9468 #9469, `--quiet gpu,cpu`), a fresh `intarsia serve --backend cuda --max-seq 8192 --mem-budget 30` per visit
(binary `itlcreep-ef31cff03e85` = origin/main at #373; vLLM `guidance` up and idle: 0 requests before and after every visit; MemAvailable never below 63.5 GB, memwatch killed nothing), 8 prompts per set, **256 forced tokens each**, one stream, warm-up request once per visit,
`scripts/dv27/speed.py` (the dvocab harness: localeval's streaming client, decode tok/s = (completion_tokens - 1) / decode window). T = 1.0 means top_k 20 / top_p 0.95 with a fixed seed per prompt; "greedy" is T = 0.
Sets: `en` (English chat), `code`, `cjk` with thinking at the server default (the 27B answers a Chinese prompt with a mostly English think block: CJK share 0.28 of the characters), `cjk` thinking off (the forced tokens are the Chinese answer: CJK share 0.43-0.44), `mixed` (en, zh, code, JSON).
Each arm ran twice (the two ABBA visits): the two visits of an arm agree within 0.3 % in every cell (see `raw/sweep-table-s1.md`), so the differences below are not visit noise.

Reading it:
- **The 35B's gap is present on the 27B**: with Chinese answers (thinking off) the default runs at 0.71 (T 1) / 0.66 (greedy) of the 131072 arm's speed, acceptance 0.43 / 0.39 against 0.60 / 0.68. With thinking at the default the Chinese prompts still lose (0.76 of 131072): 28 % of the reply characters are CJK, so it is a mixed English / Chinese cell.
- The full head is not the answer on this model: 7-8 % slower than the default on English and code (the 248320-row head costs more than the acceptance it gains: 0.552 vs 0.519).

## Results: 2 streams (`--max-batch 2`, `INTARSIA_BATCHED_MTP=2` only, no batched verify; fleetq #9575-#9578, T = 1.0, 4 sets, 16 / 16 replies identical in every cell)

This is the mode of the 35B's 2-stream sweep that works on the 27B (smoke2, #9460: the server starts, drafts, replies identical V65536 vs V0, 8 / 8). With `INTARSIA_BATCHED_VERIFY=1` added it fails (previous section), so the 35B's full opt-in set cannot be measured on the 27B.
It is **opt-in only** (the 27B recipe has no `batched_mtp` key; a `--max-batch 2` server does not draft the 27B by default).
Ratio of mean combined decode tok/s to 65536 (two visits per arm, `raw/sweep-table.md`):

| cell (2 streams) | 65536 tok/s | 98304 | 131072 | 0 (full head) |
|---|---:|---:|---:|---:|
| en | 27.94 | 0.997 | 0.989 | 0.992 |
| code | 28.49 | 0.987 | 0.986 | 0.987 |
| Chinese, thinking off | 28.64 | 1.000 | 0.996 | 0.994 |
| mixed | 28.19 | 0.987 | 0.984 | 0.980 |

**Caveat: this mode barely drafts, so these cells hardly exercise the draft vocabulary.** Verify passes x tokens per pass over generated tokens (from the `speed-*-b2n-*.json` `mtp` counters) is only **1-2 % (Chinese thinking off), 2-4 % (code), 6 % (English) and 7-8 % (mixed)** of the tokens (e.g. 18-54 verify passes for ~1000 tokens);
almost every token came from plain batched steps (the combined 28 tok/s is about two plain streams' worth, 2 x ~15 tok/s, `2026-11-07-cuda27-decode.md` section 1; at one stream the same share is 98 %). The acceptance figures here (Chinese 0.333 for 65536, 0.500 / 0.722 / 0.796 for 98304 / 131072 / full) rest on 18-54 passes.
So the result is "no difference measurable at two streams in the mode that works", not "a wider head costs more": the 0 to -2 % below 65536 is small and could be the wider head's per-pass cost on the few drafting passes plus the larger per-visit noise of two concurrent streams. The vocabulary does not matter for the 27B at two streams as measured; a mode that actually drafts there would need the m = 6 failure fixed first.

## Recommendation

**Use `--mtp-draft-vocab 98304` for the 27B CUDA default** (single stream is the shipped shape):
- 1 stream: no cell more than 1 % below the default (English, code, mixed: 0.991-1.007; the visit-to-visit spread is 0.3 %), Chinese thinking off **+23 % (T 1) / +37 % (greedy)**, Chinese thinking default +22 %; replies identical to the default's in 16 / 16 of every cell.
- These are small real losses, not noise: the two visits of an arm agree within 0.3 %, and 98304 is below 1.000 in four of the five English / code / mixed cells (0.991-0.998; the worst is mixed at -0.9 %, acceptance 0.569 to 0.561). It passes only on the +/-1 % threshold below. In the unshipped opt-in 2-stream mode it is 0.987 on code and mixed (every wider arm is 0.98-0.99 there, and the mode barely drafts, see above).
- **131072** is the Chinese-first alternative: +32 / +41 / +52 % on Chinese, but **-1.4 to -2.1 % on every English / code / mixed cell** (0.979-0.986, in both ABBA visits). Use it only if the traffic is known to have a lot of Chinese. This agrees with the 35B result rather than contradicting it: `2026-11-14-dvocab.md` found "no losing cell" for 131072 against main's default, which at one stream was the full head, and recorded that against 65536 it gives up about 2-3 points on English and code, the same cost measured here. The recommendations differ only because the 27B's default is already 65536; the
  c27 breakdown (`2026-11-07-cuda27-decode.md` section 1) puts the 65536-row draft head at 2.77 of 86.6 ms per pass, so doubling the rows costs about 3 % of a pass, in line with the 1.4-2.1 % seen.
- **The full head (0)** loses 7-8 % on English and code: not an option.
- The "no losing cell" test I applied: every 1-stream cell >= 0.99 of the default (a judgement threshold of about 3x the visit spread, not a significance test). 98304 passes it (worst 0.991), 131072 and the full head do not. **Read strictly (no cell below 1.000) no value passes**; PR 2 is opened on the 1 % reading and the user decides.

**PR 2** (`dv27: 27B CUDA mtp_draft_vocab default (USER DECISION, do not merge)`) changes `[tuning.cuda] mtp_draft_vocab` 65536 -> 98304 (`recipes/qwen3_5_vl.toml` line 177) and the one test line that pins it (`crates/intarsia-models/tests/mtp.rs:1541`).
Tests on endor (fleetq #9613): `cargo test -p intarsia-models --test mtp --test recipe_27b_chunk --test recipes_doc` 57 / 4 / 3 passed. The docs rows that quote the 27B CUDA value (`docs/tuning.md:48`, `docs/recipes.md:157`, the LOG defaults rows) are not touched: they follow if the user accepts.

**HIP and Metal are not changed and not measured.** HIP (`[tuning.hip]`, line 117; tatooine, radiance runs there, no downtime approved) and Metal (line 103) keep 65536. The 27B tokenizer has the identical id layout (`docs/results/2026-11-14-dvocab/raw/tokscan-27b.txt`: the first CJK id is 95726), so 65536 holds no Chinese token there either, and the HIP doc already measured the symptom
(Chinese acceptance 65.9 % to 51.4 %, 16 % slower than the full head, `docs/results/2026-10-25-sp-hip-spec.md`). That is an inference, not a measurement: the CUDA cost of the wider head (the 27B's fp8 head and `mix` draft head) differs from HIP's, so the best value on HIP may differ from 98304.

## Limits

- One checkpoint (Quark AWQ MXFP4 W4A16), one host (GB10 spark1), 8 prompts per set, 256 forced tokens, a single seed per prompt: the replies are the same across arms by construction, so this compares arms on identical token streams but samples few of them. Chinese prompts are the 8 of `scripts/dvocab/speed.py` (translations of the English ones plus Rust, arithmetic, an email).
- The binary is itlcreep's build of origin/main at #373 (`itlcreep-ef31cff03e85`), not an own build; no code differs on this path from main at the time (HIP, wht6 and docs changed since).
- ITL p99 is localeval's per-token number over 8 requests per cell and was not decisive.
- The memory watch was missing for the first two smoke visits (not for the sweep); MemAvailable never dropped below 63.5 GB.
- Not measured: tp2 over the two Sparks (MTP at tp2 is refused for a remote rank, `2026-11-07-cuda27-decode.md` section 6), prompts over ~1k tokens, other quantisations, `INTARSIA_BATCHED_VERIFY=1` (fails, above).
