# DeepSeek V4.1 Flash at TP=2: rank caches, runtime, engine (lane dsv41/tp2)

Lane `dsv41/tp2`, 2026-10-31 / 11-01. Mia EXL3 2.9 bpw checkpoint
(`Mia-AiLab/DeepSeek-V4.1-Flash-1017-EXL3-EAQ-v1-2.9-bpw` @ `45ee5d0f`), text only.

## What is in the branch

- **Per-rank weight cache** (`crates/intarsia-models/src/dsv41_cache.rs`, `intarsia dsv41-cache --model CKPT --out DIR --rank R
  --world W [--layers N]`): an already-sharded safetensors checkpoint per rank on the Spark's local NVMe, plus config,
  tokenizer, chat template and the Engram token map. Column-parallel EXL3 linears (`wq_b`, shared `w1`/`w3`, `head`) keep
  `N / W` outputs. Row-parallel ones (`wo_b`, shared `w2`) keep `K / W` inputs. `attn_sink` keeps `H / W` heads. `wo_a`
  keeps the rank's `o_groups / W` slices, renumbered from 0. Routed experts are stored as the built EXL3 `MoeExperts`
  arena (`I / W` wide). Indexer, compressor, router, hc and Engram `wkv` are replicated; `mtp.*` and `bias_vl` are
  dropped. The loader streams it with O_DIRECT (6.9 GB/s measured on spark2, 17.3 GiB few-layer cache), so the page
  cache never holds the weights.
  Caches built: spark1 `~/intarsia-dsv41-tp2/cache/r0of2` and spark2 `~/intarsia-dsv41-tp2/cache/r1of2`, 97 GB each.
  `l3-*` are few-layer (`--layers 3`) caches for parity.
- **TP graph** (`dsv41::graph::build_with(.., GraphTp { world, layers })`): heads, groups and experts per rank. The
  collectives are stage extras, not ops (the op set is frozen):
  - an f32 partial all-reduce after `wo_b` and after the MoE (`Comm::all_reduce_sum_into`, rounded once);
  - an all-reduce of the gathered Engram rows (a rank's foreign rows are exact zeros);
  - an all-gather of the head's logits.

  `layers` truncates the model for few-layer runs.
- **Fused routed + shared experts**: one `MoeExperts` launch per layer. The shared expert is expert 384 of a 385-row
  arena, picked by a 7th slot of weight 1. At decode a fill writes that slot; prefill uses transpose, fill, transpose
  (TensorFold's served-decode layout). `dsv41::runtime::fuse_shared_experts` appends it at load.
- **Runtime** (`intarsia_core::dsv41::runtime`): an eager executor over the graph for one rank and one sequence.
  - Engram: both layers' rows are hashed and issued as soon as a pass's token ids are known. The pass waits for layer
    *l*'s records right before layer *l*, an eager split of the pass at layers 1 and 14.
  - `touch` runs at pass start and before the logits read.
- **Engine** (`crates/intarsia-models/src/dsv41_engine.rs`): the single-sequence `Engine` for `generate` / `serve`, with
  prefix reuse down to the ring margin.
  - A rank cache passed as `--model` is detected by `load_engine_group`.
  - Rank 1 runs `intarsia tp-worker` with its own cache. `tp_remote::serve` is now generic over a `RankModel`
    (`Model` is unchanged). The handshake fingerprint is the source checkpoint plus world, layers, capacity, chunk and
    act.
- **CUDA kernels added by this lane**: `transpose01`, `engram_gather`, `engram_merge` (admitted on GB10), plus
  `logits_f16w` / `matmul_f16w`. The router `ffn.gate` and the indexer `weights_proj` are f16 in the checkpoint;
  rounding them to bf16 would move expert choices.
  `tests/dsv41.rs::every_step_resolves_to_a_cuda_kernel` checks the sm_121 registry against every step (TP=1 decode
  and prefill shapes, and a TP=2 rank's).

### EXL3 split-K for the small-grid decode linears (`58b2286b7`, threshold `2353db633`)

`ik_matmul_exl3_splitk` is a new entry point in `kernels/cuda/exl3.cu`. It cuts K into S splits (S divides K / 128, the
smallest S whose grid N / 128 x S reaches the SM count, at most 16). Each block stores its raw 128-column partial in f32;
a second launch adds the partials in split order, then applies H, svh and the rounding like `linear_kernel`. It is
deterministic, but not bitwise equal to the GEMV.
- Other EXL3 models cannot pick it up. It is registered at priority -10, and the GEMV accepts every shape it does. Only the
  DSv4.1 runtime selects it, by name, for one-row calls with grid N / 128 < `INTARSIA_DSV41_EXL3_SPLITK` (default 16,
  0 = off).
- The SASS of all 34 existing kernels in `exl3.cu` is identical before and after (cuobjdump on spark2,
  `scripts/dsv41-tp2/splitk-gpu.sh`).
- Admission sweep on GB10: 134 cases, 0 failures, max_abs 5.3e-3, rel_l2 1.7e-3 (GEMV: 7.0e-3 / 1.7e-3). The exl3 test
  binary passes (10 tests, including the split-K sweep).

Microbenchmark (M = 1, cold weights, us per call; `bench_splitk`):

| shape (TP=2 rank) | grid | GEMV | split-K |
|---|---|---|---|
| wkv / compressor N=512 K=5120 | 4 | 45.2 | 12.3 |
| wo_a slice N=1024 K=4096 | 8 | 37.9 | 17.9 |
| wq_a N=1280 K=5120 | 10 | 46.7 | 29.1 |
| indexer wq_b N=4096 K=1280 | 32 | 18.7 | 20.8 |
| wo_b N=5120 K=4096 | 40 | 58.9 | 62.1 |

That is 1.6-3.7x faster at grid 4-10 and 5-10 % slower at grid 32-40, so the threshold is 16.

Numerics of the probe binary: window 1's golden came from `2d20b0b4d`, the probe ran on `a904d271f` with split-K off. They
are the same numerics: the golden regenerated in this window matches window 1's token for token on every prompt
(story, chat_short, chat_multiturn, chat_reasoning, count and both long prompts 64/64) up to the first EOS that intarsia
may now emit (science @ 19, code @ 47, chat_system @ 28).

**Every divergence is a near-tie or an EOS protocol artefact, not a numerics bug.** The largest cross-engine gap
(0.137 nats) is smaller than intarsia's own prefill-vs-decode disagreement at chat_short (0.318 nats). TensorFold's token is intarsia's rank
1-3 everywhere, at most 0.137 nats below intarsia's top-1.

- **EOS artefact (fixed in `b4c66e514`).** The goldens use `min_tokens` + `ignore_eos`. The DSv4.1 engine masked EOS

  emitted EOS at code @ 47 and chat_system @ 28; intarsia could not. At chat_system @ 28, intarsia gives EOS a logprob of
  -0.000, so it agrees with TensorFold once allowed.
- **Rank 1 but the recorded token differed** (chat_short, chat_multiturn, chat_system). The probe's logits come from a
  prefill pass (prompt + prefix in one chunk). The recorded tokens came from decode steps, which use different kernels

  0.047, chat_multiturn 0.050, chat_short 0.318. Split-K does not enter this probe: it only runs on one-row calls.

- chat_system now matches TensorFold for 45 tokens, including the post-EOS text "EOS BOS # 为什么天空是蓝色的".
- code matches for 49 tokens.
- The remaining first divergences are the five near-ties above, plus two inside text after an EOS token, where both

## Step 3: CUDA graphs for DSv4.1 decode (what blocks capture; estimate, not started)

Measured base for the gain (window 8, `9eb46e656`, defaults): a decode pass takes 35.4 ms. Host enqueue is 18.1 ms of it
(window 5 nsys: 2036 launches at 8.7 us each; the fused HcSublayer removes about 260 of them), and the last nsys GPU busy time was 30.9 ms per token (window 5, before the fused
HcSublayer). A captured decode replays at about GPU busy time, so expect about 31 ms per token, about 32 tok/s (+15 %).
Inside a graph the gaps between kernels also shrink, so somewhat more is possible.

**Why the decode pass cannot be captured as it is.** The runtime rebuilds the graph for every pass from `(t, pos0)` and
passes `pos0` to the kernels as a host scalar. The runtime never sets `OpCall::pos`, so no device position exists.
Three things depend on the position:

1. **Shapes.** Compressed keys `nk = (pos0 + t) / r` grow every token at the 20 ratio-1 layers and every second token at
   the 18 ratio-2 layers (`compress_ratios`: 5 x 0, 20 x 1, 18 x 2; compression in KV-source layers 2, 8, 14, 20). This
   sets the shapes of the cmp / index-key slot views, of the candidate mask `[t, n_blocks(nk)]`, of the top-k output
   `[t, min(index_topk, nk)]`, and the `Nc` / `Kc` that `attn_sparse` reads from those shapes. One graph per position
   parity is therefore not enough: the counts must come from the device.
2. **Topology.** The compressor branch (rmsnorm, `indexer.wk`, k_norm, rope, act_quant into the slot, then the latent's
   rmsnorm / rope / act_quant) is emitted only `if groups > 0`. At the ratio-2 sources that is every second token.
3. **Write rows.** `act_quant` writes the new index key / latent into slot row `row0 = pos0 / r` (an address baked into
   the call), and `rope` uses position `row0 * r` with stride `r`.

The rest is capturable as it stands:
- MoE: `exl3_moe.cu` groups the experts on the device (`group_kernel`), and its grids depend only on host-known shapes.
- EXL3 GEMV / split-K and the dense kernels: static shapes.
- NCCL: capturable (`Comm::capture_safe`, used by the main engine at TP=2).
- Engram: the host hashes, does tier IO, then an H2D copy. The plan already splits the pass at layers 1 and 14 with a
  host wait between segments, so this becomes three graphs with the Engram copies outside them.

**Estimate, part (a): kernel work** (cuda-attn lane kernels; the coordinator has since released them to this lane).

| kernel | change | estimate |
|---|---|---|
| `compress_pool` | groups and ring row from a device position; always launched, writes nothing when no group completes | 1-2 h |
| `indexer_blocks`, `indexer_topk` | `nk` from a device position; grids sized for the slot capacity with early exit (the ADR-0007 pattern); top-k width fixed at `index_topk`, filled with -1 when `nk` < top-k | 5-7 h (`indexer_topk` is the big one) |
| `attn_sparse` | `Nc` / `Kc` from the device instead of the tensor shapes (its `dpos` path exists) | 1-2 h |
| `act_qdq`, `rope_tail` | slot write row and rope position `floor(pos / r) * r` from the device, with a group-complete predicate (a tiny kernel at pass start can write the derived scalars per ratio) | 2-3 h |
| tests | device- vs host-position bitwise tests (`graph_pos.rs` style) for all of the above, plus the existing but never-run `dpos` paths of `rope_tail`, `window_kv` and `attn_sparse` | 3-4 h |

Total about 12-18 h of kernel work, plus GB10 test runs.

**Estimate, part (b): graph, runtime and tp_remote work (this lane).**
- A capture mode of the graph: capacity-sized shapes and a fixed workspace layout, the compressor branch always emitted
  (predicated), and the position as a device tensor uploaded before each replay.
- Three captured segments split at the Engram layers 1 and 14.
- NCCL landing buffers reserved at load.
- The tp-worker captures and replays the same segments (a replay message in the DSv4.1 protocol).
- Eager fallback for prefill and for capture failures.

About 8-12 h, plus two full-model windows: bitwise eager-vs-graph greedy tokens on TP=2, then speed.

**Overall:** about 2.5-3.5 days for one agent, about 1.5-2 days if (a) and (b) run in parallel.

## Where the 2x decode gap is (TensorFold source and logs, window 11)

**TensorFold decodes speculatively, with the checkpoint's own drafter.** Source: BLACKFOLD's engine, bertholomus/TensorFold
@ `6366d2c` + recipe patches, local copy `.worktrees/blackfold/src/tensorfold`.
- `zig/src/server/engines.zig:23`: `.drafts = !args.no_drafts`, so drafting is on unless `--no-drafts` is passed.
  `.worktrees/blackfold/bf-node.sh` does not pass it.
- `zig/src/families/dsv41/draft.zig:1-11`: the DSpark drafter. Three stages, each a MoE block at top-3 of 128 routed
  experts plus the shared one, fed by taps of target layers 37-39. Then a Markov loop (rank 256) and a confidence head
  that picks how many drafts each round verifies (`draft.zig:663`, `_choose_k`).
- The Mia checkpoint ships these weights: `mtp.0`, `mtp.1`, `mtp.2` with about 1610 tensors each. The config sets
  `num_nextn_predict_layers` 3, `dspark_block_size` 5, `dspark_target_layer_ids` [37, 38, 39], `dspark_markov_rank`
  256, `dspark_n_routed_experts` 128, `dspark_num_experts_per_tok` 3. Our `config.rs:20` parses them, "not executed".
- **Acceptance:** the server logs `rounds=` and `accepted=a/d` per request (`[tensorfold] done ...`). Over 655 requests
  in `.worktrees/blackfold/logs`:
  - long generations (more than 256 tokens): 2.07 tokens a round, 61 % of drafts accepted;
  - 33-256 tokens: 2.34 a round, 62 %;
  - 1-32 tokens: 4.28 a round, 74 %.
  - About 1.9 drafts are verified per round, so a round is about 2.9 rows. Code content accepts more, which matches
    its content-dependent speed (code 102 vs prose 57 tok/s).
- **Calibration on our benchmark** (the server is started at temperature 1, so the 655 requests above mix sampled
  chats, MMLU and thinking). The 12 temperature-0 requests of localeval speed sweeps in the same logs (128 tokens at
  prompts of 133-16332 tokens) give 2.22 tokens a round, 54 % of drafts accepted, and about 3.2 rows a round. The
  BLACKFOLD sweep's 60.5 tok/s at 1K makes a measured round about 36 ms (127 tokens over about 58 rounds).
- **Per-pass cost:** TensorFold's served round-cost table (`draft.zig:658`, the lane core's model for choosing k) is
  30.0 / 35.2 / 39.9 / 44.9 / 48.6 ms for 1-5 rows, plus `draft_ms` 3.5 ms. The measured 36 ms round (3.2 rows +
  drafter) is below what the table predicts (about 45 ms), so the table is conservative.
- So most of the gap is speculation (2.22 tokens a round). There is a second, per-pass gap. TensorFold's 3.2-row round
  with drafting takes 36 ms; our 1-row pass takes 35.4 ms, and our 3.2-row verify would take about 48 ms.
- **The four env toggles:**
  - `TF_DS_GRAPHS`: the round's stretches as CUDA graphs.
  - `TF_DS_HC_SIDE`: the HC mixes' side work (dots, Sinkhorn) on a second stream, joined at the next mix.
  - `TF_DS_L2_PREFETCH`: a paced L2 prefetch of the next kernels' weights, three launches a layer on its own stream
    (`round.zig:357`).
  - `TF_DS_REPLAY_FLOOR`: a correctness mode for short chunks whose window reaches below a floor (`prompt.zig:714`),
    not a speed lever.
  - Also in the launcher: decode gathers over an RDMA ring (`TF_RDMA_DEVICES`) instead of NCCL, and Engram reads by
    Linux AIO.

**Our pass cost by rows** (window 11, `INTARSIA_DSV41_PROFILE`):
- A 4-row pass takes 54.3 ms (10 passes, median), 1.53x our 1-row pass. TensorFold's table scales 1.50x. These passes
  ran at positions 4-12, so they undercount attention and indexer cost at reply depth: read the scaling as a lower
  bound.
- Scaled the same way, our 2 / 3 / 5 rows would be about 41.5 / 47.1 / 57.3 ms.
- The other row counts of the step were not measured: its token-id prompts shared a prefix, and the prefix cache
  absorbed them: each prompt extended the previous one, so every measured pass was 4 new rows at positions 4-12. A
  rerun needs distinct prompts.

**Lever 1, what it needs** (about 3-5 days; most of it is drafter numerics parity):
- **Weights.** `dsv41_cache.rs:16` drops `mtp.*`, so the rank caches need the three stages added. They can go in their
  own rank files, so the 96 GiB of existing parts need no rewrite. That is an estimated 2.5 GiB per rank (128-expert
  stages vs 384), which brings the measured minimum of 10.0 GiB available to about 7.5. The watcher's kill line is 5 GiB.
- **Drafter.** The graph and CPU reference for the three stages (window rings of absorbed taps, sparse attention over
  the 128 newest positions + the block rows, MoE top-3 of 128 + shared), the Markov loop (rank 256, vocabulary split
  over the ranks) and the confidence head. It also needs fixtures from the official reference: `golden/dsv41` has none
  for MTP.
- **Verify.** Head logits for every row of a multi-row pass, the accept/reject loop in `dsv41_engine.rs`, and the
  choice of k (fixed first, confidence-based later).
- **Rollback.** Exists: `truncate` runs on both ranks; ring slots keep a 16-token margin and shared slots truncate by
  length (`dsv41_layers.rs:406` tests it). A 5-token draft block fits.
- **Not bit-identical.** Greedy output with speculation will not match the current goldens bit for bit, because verify
  passes use the multi-row kernels. The checks stay the near-tie probe and MMLU.

the MoE `grouped_rows` kernel is 64 % of the time (window 10 nsys), so that is where a prefill lever would start.
