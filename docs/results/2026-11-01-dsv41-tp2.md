# DeepSeek V4.1 Flash at TP=2: rank caches, runtime, engine (lane dsv41/tp2)

Lane `dsv41/tp2`, 2026-10-31 / 11-01. Mia EXL3 2.9 bpw checkpoint
(`Mia-AiLab/DeepSeek-V4.1-Flash-1017-EXL3-EAQ-v1-2.9-bpw` @ `45ee5d0f`), text only.

## What is in the branch

- **Per-rank weight cache** (`crates/intarsia-models/src/dsv41_cache.rs`, `intarsia dsv41-cache --model CKPT --out DIR --rank R
  --world W [--layers N]`): an already-sharded safetensors checkpoint per rank on the Spark's local NVMe, plus config,
  tokenizer, chat template and the Engram token map. Column-parallel EXL3 linears (`wq_b`, shared `w1`/`w3`, `head`) keep
  `N / W` outputs. Row-parallel ones (`wo_b`, shared `w2`) keep `K / W` inputs. `attn_sink` keeps `H / W` heads. `wo_a`
  keeps the rank's `o_groups / W` slices, renumbered from 0. Routed experts are stored as the built EXL3 `MoeExperts`
  arena (`I / W` wide). Indexer, compressor, router, hc and Engram `wkv` are replicated; `mtp.*` and `bias_vl` are
  dropped. The loader streams it with O_DIRECT (6.9 GB/s measured on spark2, 17.3 GiB few-layer cache), so the page
  cache never holds the weights.
  Caches built: spark1 `~/intarsia-dsv41-tp2/cache/r0of2` and spark2 `~/intarsia-dsv41-tp2/cache/r1of2`, 97 GB each.
  `l3-*` are few-layer (`--layers 3`) caches for parity.
- **TP graph** (`dsv41::graph::build_with(.., GraphTp { world, layers })`): heads, groups and experts per rank. The
  collectives are stage extras, not ops (the op set is frozen):
  - an f32 partial all-reduce after `wo_b` and after the MoE (`Comm::all_reduce_sum_into`, rounded once);
  - an all-reduce of the gathered Engram rows (a rank's foreign rows are exact zeros);
  - an all-gather of the head's logits.

  `layers` truncates the model for few-layer runs.
- **Fused routed + shared experts**: one `MoeExperts` launch per layer. The shared expert is expert 384 of a 385-row
  arena, picked by a 7th slot of weight 1. At decode a fill writes that slot; prefill uses transpose, fill, transpose
  (TensorFold's served-decode layout). `dsv41::runtime::fuse_shared_experts` appends it at load.
- **Runtime** (`intarsia_core::dsv41::runtime`): an eager executor over the graph for one rank and one sequence.
  - Engram: both layers' rows are hashed and issued as soon as a pass's token ids are known. The pass waits for layer
    *l*'s records right before layer *l*, an eager split of the pass at layers 1 and 14.
  - `touch` runs at pass start and before the logits read.
- **Engine** (`crates/intarsia-models/src/dsv41_engine.rs`): the single-sequence `Engine` for `generate` / `serve`, with
  prefix reuse down to the ring margin.
  - A rank cache passed as `--model` is detected by `load_engine_group`.
  - Rank 1 runs `intarsia tp-worker` with its own cache. `tp_remote::serve` is now generic over a `RankModel`
    (`Model` is unchanged). The handshake fingerprint is the source checkpoint plus world, layers, capacity, chunk and
    act.
- **CUDA kernels added by this lane**: `transpose01`, `engram_gather`, `engram_merge` (admitted on GB10), plus
  `logits_f16w` / `matmul_f16w`. The router `ffn.gate` and the indexer `weights_proj` are f16 in the checkpoint;
  rounding them to bf16 would move expert choices.
  `tests/dsv41.rs::every_step_resolves_to_a_cuda_kernel` checks the sm_121 registry against every step (TP=1 decode
  and prefill shapes, and a TP=2 rank's).

## Stage 5a: few-layer parity

`crates/intarsia-models/tests/dsv41_runtime.rs`. The reference is the official code's layer outputs on 16 prefill rows,
then decode at positions 16 and 17, layers 0-2. Only token ids and Engram rows come from the fixture; the rows are
served by a tier keyed by the official hash ids, so a wrong hash errors. Each depth runs layers 0..l in the runtime.
The table shows max |got - ref| / max |ref|, worst over the three steps.

| run | L0 | L1 | L2 |
|---|---|---|---|
| CPU, 1 rank, fp32 | 4.4e-6 | 5.9e-6 | 3.6e-5 |
| CPU, 2 ranks (host comm), fp32 | 4.4e-6 | 5.9e-6 | 3.6e-5 |
| CPU, 1 rank, bf16 | 6.7e-3 | 4.1e-3 | 1.7e-2 |
| CPU, 2 ranks, bf16 | 6.7e-3 | 2.2e-2 (a) | 2.8e-2 |
| CUDA (GB10, spark2), 1 rank, bf16 | 7.1e-3 | 2.2e-2 (a) | 2.4e-2 |

(a) A routing near-tie at layer 1, decode step 1: summation order (two ranks, or CUDA) flips expert 270 to 78 (`INTARSIA_DSV41_ROUTES=1`
prints the sets). In fp32 the two ranks match the one-rank result to rounding.

The CUDA fp32 flow is not run: the backend's shared kernels (embedding, norms) take bf16 activations only.

## Stage 5b: full model, TP=2 across spark1 + spark2

The first window was fleetq #7621, binary `2d20b0b4d`, run with `scripts/dsv41-tp2/run-full.sh`:
- rank 0: spark1, `serve --tp 2 --tp-remote`;
- rank 1: spark2, `tp-worker`;
- NCCL 2.30.7 over ConnectX-7, `NCCL_MAX_NCHANNELS=2`, `NCCL_BUFFSIZE=1 MiB`;
- capacity 32768, chunk 512, Engram hot tier 1 GiB.

**Load:** 23 s per rank from vLLM down to serving (16 s O_DIRECT stream of 96.3 GiB at 6.1-6.4 GB/s, then the shared-expert
fuse). Health was up 29 s after start.

**Per-rank memory** (rank 0; rank 1 matches):

| | GiB |
|---|---|
| weights | 95.43 |
| workspace (chunk 512) | 0.24 |
| sequence state (32K tokens) | 0.10 |
| kernel scratch | 0.004 |
| rest: CUDA context, NCCL, Engram tier incl. 1 GiB hot tier, host | 2.04 |
| **non-weight total** | **2.38** (target <= 6) |
| MemAvailable after warm-up | 13.3 |

**Greedy text** (`golden_tf.py tokens` on tools/prompts/golden*.jsonl, raw completions, 64 tokens each): coherent on all 10
prompts. Examples: counting goes on as "13, 14, 15, ..."; the code prompt completes `is_prime` correctly; the
science prompt explains RuBisCO and photorespiration. In the ChatML prompts, the model sometimes runs on past `<|im_end|>`:
these are raw completions with `ignore_eos`, which is expected. The file is `.scratch/full-w1/tok-intarsia-tp2.st`
(not committed); 10 prompts x 64 tokens took 31 s including prefill.

**Chat requests** failed in this window: the checkpoint's chat template calls `{}.copy()`, which minijinja lacks. Fixed in
`d91129d4c` (`dict.copy()` / `list.copy()` in the template engine).

**Token agreement with TensorFold:** not measured. No TensorFold token golden exists (`golden/dsv41` has none), and this
lane may not run the TensorFold server. `golden_tf.py tokens --tokenizer` against intarsia writes the same
`intarsia-golden-tokens-v1` format, so once a TensorFold golden is recorded on the same prompt set,
`golden_tf.py compare` gives the agreement.

### Second window (fleetq #7623, binary `2ab87ada3`)

Same layout and settings as the first. Load 22.9 s, MemAvailable 110.5 -> 13.0 GiB after warm-up, non-weight 2.05 GiB
on rank 0 (the startup log line: workspace 0.237, scratch 0.004, state 0.103, rest = CUDA context + NCCL + Engram + host).

**Chat** works with the template fix. With the template's default (thinking on), the content is the reasoning, then
`</think>`, then the answer. Example: "...Capital France Paris. Need concise.</think>The capital of France is Paris."
That window's binary had no reasoning parser for DSv4.1. `5fea1a106` adds `think-tags`, so a request with
`enable_thinking: true` gets `reasoning_content` split off at the single `</think>` token. Like every other model, a
request that leaves thinking unset gets it all in `content`. Counting, `fibonacci` code and the lighthouse story are coherent.

**Speed** (localeval, `results/20261101-015410-adhoc-dsv41-intarsia-tp2-speed`; one stream, 128 output tokens, median
of 3, eager runtime without CUDA graphs):

| prompt tokens | TTFT s | prefill tok/s | marginal prefill tok/s | decode tok/s |
|---|---|---|---|---|
| 117 | 0.48 | 241 | - | 24.8 |
| 1028 | 1.92 | 536 | 634 | 24.6 |
| 4094 | 7.21 | 568 | 580 | 24.7 |

For reference, the Mia/TensorFold 2x-Spark server measures 89 / 56 / 59 tok/s decode (memory note, same checkpoint).
Decode is eager: about 1400 launches a token plus 2 all-reduces per layer, with no CUDA graph. The Engram wait is
0 ms (the rows are back before layer 1), and the graph build takes 0.08 ms.

**MMLU** (localeval, `--thinking off`, `--limit 10` per subject): stopped at the window limit after 32 of 57 subjects.
The per-subject accuracies are in the log (`.scratch/full-w2/mmlu10-partial.log`). The comparison uses the same items,
the first 10 of each subject, from the Mia/TensorFold reference run (`results/20261031-195017-adhoc-dsv41-mia-tf-quality`,
`--limit 25`, 0.879 overall):

| | items | accuracy |
|---|---|---|
| intarsia TP=2 | 320 | **0.856** |
| Mia/TensorFold, same 320 items | 320 | 0.875 |
| Mia/TensorFold, 25 per subject, same 32 subjects | 800 | 0.871 |

The gap is 6 of 320 items (274 vs 280). 11 subjects differ, in both directions (abstract_algebra 0.4 vs 0.6,
high_school_physics 1.0 vs 0.9). The standard error at n = 320 is about 0.02, so this neither confirms nor fails the
0.879 +- 0.01 gate.

At this speed the full gate run (`--limit 25`, 1425 items) needs about 3.5 h. Each item averages about 2600 prompt
tokens and 25-70 output tokens, about 9 s each, mostly prefill. Mia answers in 7 tokens on average.
