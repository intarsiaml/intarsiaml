# copycuda: CUDA copy drafts re-measured after the SIDE_EAGER default

## Brief

Lane `copycuda` in /opt/code/intarsiaml (Rust inference engine). Measurement only: no default changes, no engine code changes. Output: a docs-only PR with results.

### Question
Should copy drafts (`INTARSIA_SPEC_COPY=20`, default len 7 on CUDA) become default-on for CUDA serving at `--max-batch 1` with `--spec mtp`? Earlier it failed its bar only on code-gen (n20/base 0.987x), and the cause was found: eager passes put the GPU in a slow mode via side-stream forks (#447). `INTARSIA_SIDE_EAGER` is now default-on on main (PR #453 merged), so re-measure on current origin/main.

Bar (from lane mcopy2, `docs/results/2026-11-17-mcopy2.md`): no cell below 0.995x, and agent cells (agent-edit, agent-batch) >= 1.03x. Report against that bar plainly: pass or fail per cell.

### Method
Reuse the mcopy/mcopy2/sideeager harness under `scripts/` (`scripts/mcopy*`, `scripts/sideeager*`, and the results docs `docs/results/2026-11-17-mcopy.md`, `2026-11-17-mcopy2.md`, `2026-11-18-sideeager.md` for exact commands, model and cells). Served, 4 ABBA rounds, arms: base (copy unset) vs `INTARSIA_SPEC_COPY=20`, all other settings main defaults. All default cells (chat-short, code-gen, reason, agent-edit, agent-batch, copy3k, json-xform). Ids: greedy ids equal copy vs `--spec off` on at least copy3k and code-gen. Also count slow-mode replays if the harness supports it (sideeager did).

## Result

Lane `copycuda`, branch `copycuda` from origin/main `11cb82fe4` (PR #440; contains #447 postchain2 and #453 sideflip). Measurement only: no engine code, no default changed.
spark1 (DGX Spark GB10) with vLLM up beside it and idle (its request counters, polled every second, did not move in any run: `raw/*/vllm-*.log`), every run in a fleetq slot
(`--quiet gpu,cpu` for the timing runs, `--load cpu` for the build and the analysis), build `CARGO_BUILD_JOBS=3 MAX_JOBS=3 FLASHINFER_NVCC_THREADS=1`, free-memory watchdog `scripts/copycuda/wd.sh`
(kill below 15 GB available) on build and serves, never fired; 55-57 GB available at every server start. spark2 not used.

**Verdict: copy drafts do not meet the mcopy2 bar, by one cell: code-gen reads 0.992x (below 0.995x in 4 of 4 rounds). Every other cell passes, both agent cells >= 1.03x. Do not flip as is.**
It is much closer than before (code-gen 0.981x in mcopy2, 0.987x earlier): the slow mode is gone in both arms, and what is left on code-gen is the cost of one missed chain per 800-token request (about 0.25 % by
the logged pass times, 0.8 % measured; the rest is not explained). The knob is not free on a workload that never copies; whether 0.8 % on plain code generation is an acceptable price for +50 to +69 % on copy-heavy text and
+4 to +17 % on agent turns is the user's call.

### Speed: ABBA, served, `serve --max-batch 1 --spec mtp --spec-k 2`, base (knob unset) against `INTARSIA_SPEC_COPY=20` (len 7)

Binary: one build for both arms, origin/main `11cb82fe4` + this lane's scripts (`INTARSIA_BUILD_STAMP=copycuda-11cb82fe4...-dirty`, `crates/` identical to main), built on spark1 in 6 min 27 s (`raw/build-run.out`).
Startup line of the copy arm: "copy drafts on: a chain of up to 7 tokens when the last 20 tokens occurred earlier". `INTARSIA_SIDE_EAGER` unset in both arms (the code takes eager forks only with `=1`, `model.rs`), no
`INTARSIA_SPEC_TRACE` in the timing runs. Cells from `scripts/mcopy/prompts.py`, 3 reps each, in the order chat-short, code-gen, reason, agent-edit, agent-batch, copy3k, json-xform; 2 warm-up requests per server.

Against the bar: "no cell below 0.995x" fails on code-gen only (chat-short and reason pass at 1.002 and 1.000; their lowest rounds are 0.9994 and 0.9975); "agent cells >= 1.03x" passes on both.
Greedy replies (sha of the full reply text) equal across the two arms in all 28 round-cells (7 cells x 4 rounds, 3 reps each, `raw/ab12-an.txt`), including code-gen, where chains fire (below).

- **Noise.** Absolute tok/s moves with the round, in both arms alike (chat-short: base 140.9 / 137.4 and n20 141.3 / 137.3 in rounds 1 / 2, so up to 3 % between rounds; code-gen base 159.7-160.8), which the per-round ratio cancels; sideeager measured a server-to-server step-time spread of 0.1-0.3 ms (0.5-1.7 %), the size of the code-gen gap. The 4 code-gen rounds all fall
  below 0.995 and the two slots agree (0.9932 / 0.9924), but rounds 3-4 repeat rounds 1-2 with the same prompts (same nonce tags, fresh servers), so they are replicates of servers, not new prompts: the evidence is 2 fresh prompt sets x 2 server pairs. The
  code-gen shortfall is small (0.4 to 1.0 %) against the bar's 0.5 % margin: it is a fail by the stated bar, not a large regression.
- **code-gen per rep** (the 12 prompt-reps x 2 slots, n20 / base): 0.995 0.994 0.996 0.991 1.002 0.998 | 0.990 0.989 0.988 0.991 0.997 1.000. Reps 1 and 2 of every round lose 0.5-1.2 %; rep 3 is level. Which requests fire a chain was not
  logged in the timing runs (no trace), so this pattern is not explained.
- **agent-edit is bimodal by prompt, and its round median swaps reps.** Per prompt (nonce tag.rep; both slots agree to 0.003): c1.0 0.998 / 0.995 (a 1200-token runaway reply, no copy), c1.1 0.999 / 1.002 (a 44-token reply), c1.2 **1.180** / 1.179 (298 tokens),
  c2.0 **1.179** (298), c2.1 **1.164** (308), c2.2 **1.162** (308). In c1 rounds (1 and 3) the median rep of base is the 298-token reply (156.8) and of n20 the 1200-token one (159.2), so the round ratio 1.015 compares different replies;
  the same-prompt ratio of that 298-token reply is 1.18. The 4 of 6 prompts that are real edit replies gain 16-18 %; the 2 that are not (runaway, 44 tokens) are level. The bar is met by the median (1.092, as in mcopy2's method), and by
  every reply that is an edit; it is not met in rounds 1 and 3 if the round median alone is read (1.015). mcopy2 saw the same bimodality (0.997, 1.167, 1.007).
- **Base got faster since mcopy2** (copy3k 157.4 against 151.5, code-gen 160.5 against 153.7, chat-short 139.1 against 132.8: SIDE_EAGER default + later main), so the gain cells read less than mcopy2's 1.756x / 1.555x
  as ratios (1.693x / 1.507x) while the n20 arm's absolute speed is higher (copy3k 266 against 266 in mcopy2's 1.756 x 151.5; json-xform 234 against 232).

### Ids gate: PASS

`scripts/copycuda/ids.sh` (`generate --temperature 0 --show-ids --chat --no-think`, 35B NVFP4, CUDA, tp 1; `raw/ids-run.out`, `raw/ids/`): copy3k (2902 ids), code-gen (500) and json-xform (2600) x arms `off`, `mtp`, `copy=20`:
**6 of 6 compared arms identical to `--spec off`** (`mtp` and `copy=20` on each prompt; `ids fails=0`). Chains fired where expected: copy3k 359 chain passes (357 accepted 7 of 7), json-xform 323; **code-gen's 500-token `generate`
fires no chain** (`copy_passes=0`), so that ids check does not exercise the chain path. The chain path on code-gen is covered by the served runs, where each 800-token request fires one chain and the replies are equal to base's
(28 of 28 round-cells above, and 9 of 9 reply shas equal across the 4 nsys servers). Also the 3 `mtp` arms equal `off`.

### Slow mode: none in either arm (nsys, `raw/ns1/`)

`scripts/copycuda/nsys2.sh` (sideeager's, with `EXTRA` cells): 4 servers in the order b1 c1 c2 b2 (base, copy, copy, base), nsys with `--cuda-graph-trace=node` from server start, trace on, 2 chat-short warm-ups, 3 x code-gen 300,
2 x code-gen 800, 1 x agent-edit, 1 x copy3k per server; `scripts/copycuda/nsys_req.py` (sideeager's rule: a graph launch with idle > 200 us is slow). Reply shas equal in all 9 requests of all 4 servers.

Sideeager's base servers had 205-374 of 1191 launches slow; here 0 of 2261 (base) and 0 of 1270 (copy): #453 removed it, and copy passes (eager, on the main stream: "inside [M 893 S 0]" in each 800-token code-gen request) do not bring it back.
The replay span after a chain (requests 5-6 of the copy servers, 17.44-17.60 ms) is the span of the base servers' same requests (17.50-17.65): **mcopy2's "persistent +0.2 to 0.3 ms per graph step after the first chain" does not show**.
Launch counts differ because copy replays fewer steps (copy3k: 1 launch of 969 for base on a 2900-token reply, the chains emit 8 tokens per eager pass).

What the log of the copy servers shows on code-gen (`raw/ns1/serve-c1.log`, trace on): each 800-token request fires one chain, a miss: `pos 828 drafted 7 accepted 2 emits 3` and `pos 665 drafted 7 accepted 1 emits 2`, 28.5 ms per 8-row eager pass, against an MTP graph step of
about 17.6 ms for 2.77 tokens: a missed chain costs about 9 to 16 ms, about 0.25 % of a 5.2 s request. The measured shortfall is about 0.8 %; **the remaining 0.5 % is not explained** (candidates: the lazy head catch-up after a chain, an extra eager head pass,
chains in reps that this one-request-per-server nsys run did not hit; not tested).
