## 1. What was built

* `INTARSIA_LMHEAD_QUANT=fp8|mxfp4` (`off`, `0`, empty or unset: off; the variable wins over the recipe key) and the recipe key `[tuning.<backend>] lm_head_quant` (no shipped recipe sets it). `crates/intarsia-core/src/quant/head.rs`, wired in `Model::load` (`load_head`).
* The head is quantised on the host at load from the checkpoint's float bytes and the **bf16 head is not loaded**: the 27B checkpoint has its own `lm_head.weight` (`tie_word_embeddings: false`), so resident weights drop by 2.54 GB and gain 1.27 GB (fp8) or 0.68 GB (mxfp4). A tied head (the embedding table) is quantised into a separate copy, the embeddings stay bf16.
* **The MTP draft head is not a separate tensor** in this model: `draft_head` is `row_prefix(65536)` of the head, so it is the first 65536 rows of the same quantised tensor, on every backend. Nothing extra to load, nothing extra to gate.
* **Tensor parallelism**: each rank quantises its own vocabulary rows `[r V/2, (r+1) V/2)` from the source bytes; the fp8 scale is the amax of the **whole** tensor, so the split head holds exactly the rows of the replicated quantised head (CPU test `split_quantised_head_is_bitwise_the_replicated_quantised_head`).
* Formats and kernels are the existing ones; no kernel changed. fp8: e4m3 with ONE f32 scale per tensor (`amax/448`), W8A16 (`scales = (ws, 0)`), `Op::MatmulFp8`. mxfp4: e2m1 with one e8m0 scale per 32 columns, W4A16 (`act = 0`, set explicitly: it does not inherit `[tuning.hip] mxfp4_act = "fp8"`), `Op::MatmulMxfp4`.
* **Deviation from the brief, stated plainly: fp8 has a per-tensor scale, not per-row scales.** The fp8 ABI is `scales [2] = (weight_scale, input_scale)` on every backend; per-row scales would need a new scales layout in the Metal, HIP and CUDA kernels (or a logits post-scale through the graph, row-table and rowtab paths). e4m3 is a floating-point format, so a per-tensor scale costs little against a per-row one (relative error is scale independent above the subnormal range); MXFP4 carries per-32 group scales, finer than per-row. Per-row fp8 is built only if both formats fail the rule below.
* CUDA: the variable is ignored with a one-line note (the 35B head is already NVFP4 there; the 27B on CUDA was not gated).
* Plan note (`plan show`, load log) appears only when the option is on; with it unset the plan is byte-identical.

## 2. Pass rule (written before any quality number)

All of these, per format, on the 6 prompts of `scripts/cmtp/ids-prompts` (`4k-0..2`, `16k-0..2`), raw text plus 128 greedy tokens of the bf16 head (so the teacher-forced decode window lies on the model's own distribution). Same binary, `INTARSIA_LMHEAD_QUANT` unset vs set, `intarsia accuracy --write-self-golden` / `--self-golden`, top-64 rows, `--mode both` (prefill = every position of the prompt; decode = the last 128 positions through the single-token kernels):

1. **Mean 21-way KL(bf16 head || quantised head) <= 1e-3 nats** in each of prefill and decode, over the 4k prompts and over the 16k prompts separately (1e-3 is the bf16 gate class's mean-KL floor in `accuracy --max-mean-kl`; for scale, the 27B's own MXFP4 body sits ~3e-2 from the HF reference, the 4bit class floor).
2. **Top-1 flips <= 1.0 % of positions** (top-1 agreement >= 99.0 %) in the decode window and in prefill.
3. **Accuracy**: MMLU (10 per task, n = 570) and GSM8K (n = 100), localeval, thinking off, one server per arm in the same window: the quantised arm within 2 SE of the bf16-head arm (SE of the difference for MMLU about 0.02; GSM8K is coarse, +-0.14, and is reported, not gated more finely).
4. Report-only: max single-position KL, greedy 256-token ids first-divergence on the 6 prompts, tail-mass difference.

**Choosing the format.** fp8 is the default candidate. MXFP4 is recommended instead only if it passes the same rule AND gains at least 3 more points of single-stream decode throughput than fp8 on that backend in the ABAB runs.

**Speed protocol.** Same binary and window, `INTARSIA_LMHEAD_QUANT` unset (A) vs set (B), ABAB (two visits each, a fresh server per visit), localeval `speed` 1k/4k/16k, 128 generated tokens, 3 reps per size, plain (`--spec off`) and with MTP k2. HIP: tp2 and tp1, plus 1/4/8/16 streams at tp2. Metal: endor, `--exclusive`.

**No-op gates.** Variable unset: greedy ids identical to main for the 27B and the 35B on each backend touched; `plan show` and `kernels test` unchanged; `cargo test --workspace --no-fail-fast`.

## 3. Results

### 3.1 Verdict against the pass rule

| criterion | fp8 (per-tensor e4m3) | mxfp4 (per-32 e8m0) |
|---|---|---|
| 1. mean KL <= 1e-3, 4k and 16k, prefill and decode | **pass** (HIP tp2 7.5e-4 / 6.2e-4 prefill, 4.4e-4 / 4.4e-4 decode; Metal: 7.6e-4 / 6.3e-4 prefill, 7.1e-4 / 3.9e-4 decode) | **fail** (1.0e-2 to 1.3e-2 prefill, 5e-3 to 1.2e-2 decode, both backends) |
| 2. top-1 flips <= 1.0 % | **fail in prefill on both backends, and in the Metal decode window** (2.45 % at 4k, 1.95 % at 16k on HIP tp2, whose decode window passes at 0.78 % / 0.26 %; Metal: 2.42 % / 1.98 % prefill and 1.56 % / 1.04 % in the 128-position decode window) | **fail** (6 to 8 % prefill, 3 to 7 % decode) |
| 3. MMLU / GSM8K within 2 SE | **pass**: MMLU 0.8368 vs 0.8316 (n = 570), GSM8K 0.52 vs 0.48 (n = 100) | pass: MMLU 0.8193 (-1.2 pt), GSM8K 0.49 |
| speed beats fp8 by >= 3 points | n/a | HIP tp2 plain: yes (+10.3 % against fp8 +5.0 %, different windows); Metal plain: no (within 1 point); Metal MTP: noisy (+3, +8, -11 points; one visit each) |

**fp8 does not meet the rule as written: the mean KL and the accuracy are fine, but about 2 % of positions change their top-1 token in teacher-forced prefill on both backends (twice the 1.0 % bound; the 768-position decode windows give 0.3 to 0.8 % on HIP and 1.0 to 1.6 % on Metal).** The same positions are 0 % with the bf16 head, so the flips are all quantisation. mxfp4 fails the rule on every logit criterion; its extra speed over fp8 (about 5 points on HIP tp2 plain, none on Metal plain) does not buy back a 5 to 7 % top-1 churn, so it is not the recommended format. The branch ships both behind the opt-in; the call on whether 2 % top-1 churn is acceptable for the speed is the user's (the default stays bf16 either way).

Why not per-row fp8 scales (the brief's first choice)? Measured on the real head (section 3.2) the weight error of per-row and per-tensor e4m3 is the same to three digits, so per-row scales would not move the flip rate; the cost is a new scales layout in every backend's kernels.

## 4. One change outside the new module

`crates/intarsia-backend-metal/src/fp8.rs` `rows_ok`: the row-exact fp8 GEMV (the MTP verify kernel, M = 2 to 8) refused K > 4096 because the staged form keeps 4 rows of activations in threadgroup memory. The `_xd` form (the default, `INTARSIA_METAL_FP8_ROWS_XD`) and the simdgroup-matrix form read q(x) from device memory and have no such limit, so the cap now applies only when `_xd` is switched off. Without this the Metal plan for `fp8 head + MTP` failed with "no kernel for matmul_fp8 (m=2 n=248320 k=5120)" (first Metal quality run, `raw/metal-quality/cmp-fp8.err`). The row-exact test gained N x 5120 shapes (the staged form is skipped there). For models whose fp8 matmuls have K <= 4096 nothing changes, which the Metal gates above confirm for the 35B (K = 4096 at most).

## 5. How to use it

```
INTARSIA_LMHEAD_QUANT=fp8 intarsia serve --backend metal --model ~/models/Qwen3.8-27B-Quark-AWQ-MXFP4 ...
```

or `lm_head_quant = "fp8"` under `[tuning.<backend>]` in a recipe. The load log prints `lm_head quantised to fp8 (...)` and `plan show` carries the same note. Rows `INTARSIA_LMHEAD_QUANT` in `docs/tuning.md` and `[tuning.<backend>] lm_head_quant` in `docs/recipes.md`; decision in `docs/decisions/LOG.md`.

## 6. Not run / uncertain

* CUDA: the variable is ignored there (the 27B on CUDA is not a fleet target; the 35B head is already NVFP4).
* HIP: the 35B greedy-id gate at tp1; KL quality at tp1 (the tp2 run quantises the same rows, so only the kernel shape differs); the 75 min windows were used for 17, 51, 23, 14 and 14 minutes, radiance restored and answering after each.
* Metal: localeval accuracy (MMLU / GSM8K) and 16 streams; mxfp4 speed is one visit per cell.
* TensorFold / Radiance comparison: not run; the table says how much of the gap the head closes, not whether it closes it.
* The KL prompts are 6 documents (raw text, not chat), so the top-1 flip rate is a statement about teacher-forced prefill on that text; the chat-template decode window is 768 positions.
* Per-row fp8 scales were not built (section 3.1).
* Raw `.safetensors` goldens (about 50 MB) are not committed; `scripts/lmhead/mquality.sh` and the `gen` action of `scripts/lmhead/hdrive.sh` regenerate them.
