## What flips

`INTARSIA_PREFIX_HERD` (`crates/intarsia-core/src/engine/batch.rs`, `BatchedOptions::new`): unset = on, `0` = off, anything else (including `1`) = on. Before: only `1` turned it on. The startup line changed with it:
"prefix herd: on (default, INTARSIA_PREFIX_HERD=0 turns it off)" is printed when the batched engine has a prefix store; with no store nothing is printed unless the variable is set (then "set but has no effect without --prefix-store").
`SchedulerConfig::prefix_herd` itself still defaults to off (library default, the scheduler tests set it explicitly); only the env reader in `BatchedOptions::new` changed.

Who sees a difference: only a server that runs the **batched engine (`--max-batch` > 1) with a prefix store** (`--prefix-store on` or `INTARSIA_PREFIX_STORE`). The store default is not touched here (still off: it costs 12-14 % on unrelated 8K bursts and moves greedy ids against store-off,
`2026-11-17-flipev.md` section 6, `2026-11-17-storeids.md`; that is a separate decision). So default-on herd changes nothing for anyone who does not already opt into the store.

Herd is inert without a store **by construction**, not only on the workloads measured: `herd_held` returns false unless a request carries a store (`herd_min()` is `None` otherwise, `scheduler.rs:herd_held`), and with every request unheld
`prefill_pick` returns the first entry of `prefill_ranking()`, which under fifo is the first prefilling sequence in `active` order: the same sequence the old fast path (`pick_prefill`'s `position(Prefilling)`) returned (`active` only ever loses entries through `Vec::remove`, so it keeps admission order).
`plan show` builds no batched engine and takes no `--max-batch`, so the plan cannot depend on the knob (gate below).
