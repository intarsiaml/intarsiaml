## 2. How TensorFold's exchange works, and whether we can use it (step 2)

Source: `zig/src/families/dsv41/rdma.zig`, `zig/kernels/cuda/dsv41/rdma_gather.cu`, `rdma_bench_main.zig`.

- **Registered**: pinned host memory (`mmap` + `mlock` + `cuMemHostRegister(portable | devicemap)`, device pointer by `cuMemHostGetDevicePointer`; on GB10 this takes the coherent path where `cuMemHostAlloc` takes an uncached one): a send ring (slots x max bytes), a receive ring (slots x world x max bytes) and a metadata block (flags per slot and peer, doorbell, sizes, sent, abort word). Both rings are `ibv_reg_mr`-registered (local + remote write). One RC queue pair per peer and rail, 256 zero-length receives posted.
- **Signal**: the stage kernel copies this rank's slice into its send slot, `__threadfence_system`, and the last block stores the doorbell (`st.relaxed.sys`). A **host proxy thread** spins on the doorbell, posts one `RDMA_WRITE_WITH_IMM` per rail (the immediate is the sequence number) into the peer's receive slot, polls the completion queue, and on a receive completion publishes `flags[slot][peer] = seq` in pinned memory. The collect kernel spins on that flag with `ld.acquire.sys`, then reads the slot. The sequence number is device state (`*seq`), not a kernel argument.
- **Under a recorded graph**: both are ordinary kernels (the proxy is outside the graph), so they capture and replay like any other; TF's bench replays 50-gather graphs. No host node, no `cudaLaunchHostFunc`, no stream callback. An optional programmatic-dependent-launch variant (`griddepcontrol`) is TF's default, not needed here.
- **Requirements**: libibverbs (rdma-core, installed), an active RoCE port (CX7 `rocep1s0f1` and `roceP2p1s0f1`, 200 Gb/s each, MTU 4096), a GID index (**3**, RoCE v2 over IPv4, the one NCCL uses here; TF's default 5 does not exist on these HCAs), `RLIMIT_MEMLOCK` unlimited (it is, on both Sparks; a container needs `--ulimit memlock=-1 --cap-add IPC_LOCK --device /dev/infiniband`, as TF's `start.sh` passes), `cuMemHostRegister` (allowed), and one spinning host core a rank (TF naps it when idle). **No kernel module, no driver or system setting, no `nvidia-peermem`, no GPUDirect, no permission change**: nothing to stop and report.
- Ordering: with world 2 the sum `own + peer` equals `peer + own` bit for bit, so the result is bitwise the NCCL all-reduce (checked below).

## 3. Microbench (step 3)

Program `rdma_bench.cu` (one process a rank, TCP side channel for the queue-pair info, NCCL joined in the same process with run-full.sh's exact settings: 2 channels, 1 MiB buffer, both HCAs, GID 3). Per call: `[spin kernel: 100 us of device time, stamps t_start] [exchange] [stamp t_done]`, 64 calls in a captured graph, replayed 30 to 40 times, device `%globaltimer` stamps. Paths: `nccl` = `ncclAllReduce` f32 (out of place) + the f32 -> bf16 round kernel = `Comm::all_reduce_sum_into` as the engine runs it; `rdma` = stage kernel + collect kernel (sum + round); `null` = two empty kernels (the harness floor: 1.4 us); `pp` = ping-pong, rank 0 stages then collects, rank 1 collects then stages, RTT / 2.

How to read the numbers. A symmetric exchange between two ranks that start `d` us apart costs the early rank `d` + the exchange and the late rank the exchange minus `d`; the ranks then alternate roles, so each rank's latency is bimodal (5 and 17 us) and its median is not the exchange. The **mean of the two ranks' latencies for the same call** is independent of the offset, and it equals the ping-pong RTT / 2 (11.7 against 11.8, 13.6 against 13.7, 17.0 against 17.1 us on one rail): that is the one-shot, skew-free latency, and it is what the table gives (median and p99 over 1860 to 2480 calls). NCCL needs no such step (its two ranks end together: min, mean and max agree within 1 us). Bitwise check: 25600 bf16 values of the NCCL path against the RDMA path, 0 differ, on both ranks, rail 1 and rail 2.

fleetq: #8018 (first runs, one rail, tuning knobs), #8038 (decomposition, two rails, ping-pong, memory load), owner `claude-rdma`, `--host spark1,spark2 --quiet gpu,cpu`, vLLM up on both (the prefill lane's own windows ran around mine). Proxy thread pinned to an X925 core (7) unless noted; pinning, PDL, stage blocks (4 / 16 / 32) and collect blocks (4 / 16 / 48) moved nothing outside 0.5 us (`raw/bench1-r0-v-*.log`).

## 4. The engine path (step 4)

Files: `kernels/cuda/ik_rdma.cu` (the bench's kernels and proxy as a C ABI; compiled with `-DIK_HAVE_VERBS` and `-libverbs` only when `infiniband/verbs.h` and `libibverbs.so` exist, otherwise stubs; `build.rs`), `crates/intarsia-backend-cuda/src/rdma.rs` (`RdmaComm`: wraps the NCCL `Comm`, takes over `all_reduce_sum_into` of an f32 partial into bf16 on stream 0 up to 256 KiB, everything else, and every prefill chunk above 256 KiB, stays NCCL), `nccl::create_with_rdma` (the two ranks swap one byte on the control TCP stream: a difference in the setting is an error, not a hang; then the queue-pair info), `crates/intarsia-cli/src/common.rs` (`rdma_wanted`: the three-state setting), `crates/intarsia-backend-cuda/src/rdma_policy.rs` (the setup as a lock-step conversation on the control stream, written against a `RingOps` trait so the fallback rules are unit-tested without CUDA: 11 tests over loopback sockets). Devices and GID come from `NCCL_IB_HCA` and `NCCL_IB_GID_INDEX` (run-full.sh already sets both). The queue pairs take NCCL's own link settings (timeout 20, 7 retries, min RNR timer 12, RNR retry 7: a dead link reports after about 34 s). Every thread of the stage kernel fences its own stores before the barrier. The proxy thread spins; after 20 ms with no traffic it naps 20 us a turn (an idle server pays at most that on the first exchange). Rows in `docs/tuning.md` (`INTARSIA_DSV41_RDMA`, `_DEADLINE_S`, `_FAULT`); unit tests for the setup rules, the handshake and the device parsing.

## 5. Failure behaviour (review round)

What the review asked for, and what changed: the queue pairs use NCCL's link settings (timeout 20, 7 retries, so a dead link reports after about 34 s, where the first version used the verbs defaults); a device wait ends at `INTARSIA_DSV41_RDMA_DEADLINE_S` (default 180 s, read when the ring opens) or at once when the abort word is set; the setting is three-state and the setup runs in lock-step on both ranks (any failure on either rank, or an explicit `0` on one, leaves both on NCCL, with one log line under auto); libibverbs is dlopen'ed; every thread of the stage kernel fences its own stores; and a failed group ends both processes: the pass errors, the engine marks itself failed (`/health` 503, new requests refused), the server exits with code 87 and the worker aborts the communicator and exits with 87, for a restart of both ranks.

Method: `scripts/dsv41-tp2/failtest.sh`, a hook of `run-full.sh`, one fleetq job a window with vLLM taken down and restored. Every case starts both ranks fresh (so it also checks that a restarted pair serves), compares the golden prompts with a clean run (case c0), sends a long request, injects the fault, and records `/health` and both PIDs every ~0.4 s. Faults are signals to our own PIDs and a test hook of the ring (`INTARSIA_DSV41_RDMA_FAULT`); no system, network or driver setting is touched. Deadlines were shortened to 20 s (30 s for b) with `INTARSIA_DSV41_RDMA_DEADLINE_S`; the default is 180 s. Times are after the fault. Raw: `failtests/` (steps.log of each case, timeline, request and response, the tail of both rank logs).

**A real hang was found and fixed.** Killing the worker (rank 1) made the primary hang: the client got nothing for its whole 300 s timeout, `/health` went 503 only at 55 s (the stall watchdog) and the primary never exited, mid-decode (a1) and in prefill (a4), #8142. Cause (no stack could be taken: `ptrace_scope` is 1 and I do not change system settings; inferred from what the two fixes below changed): after a failed or hung pass of its own, the primary waits for the worker's answer (up to its 600 s reply timeout), and the reader thread aborted the communicator, which can block, before it let anything else see that the connection was gone. Two changes: the peer's reader thread now marks the engine failed as soon as the connection drops or the worker reports a failure (before it aborts the communicator, which can block), and a backend error on the primary no longer waits for an answer that will not come (`settle` in `dsv41_engine.rs`). The same wait explained the 25 s of case c2 and the 47 s of b2 on the intermediate heads.

## 6. Paths this branch touches but does not enable: 35B at TP=2 over the Sparks, and HIP
