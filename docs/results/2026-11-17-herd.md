# herd: followers of an in-flight shared prefix wait and restore it (opt-in `INTARSIA_PREFIX_HERD=1`)

Lane `herd`, branch `herd` from origin/main `a2d6be540`. Raw output: `docs/results/2026-11-17-herd/raw/` (`results.jsonl` has every cell with
the per-request TTFT, cached tokens and generated ids; `window.log`, the four serve logs, prefix-store and metrics snapshots).

## Problem

`serve --max-batch N --prefix-store on`: the store is looked up at admission only. When 8 requests with the same new 16k prefix arrive
together, nothing is stored yet at admission (the leader has not prefilled), and no request ever looks again, so each prefills the
prefix itself. (The leader's first chunk capture can already be there for requests admitted an iteration later: 2048 tokens, see the
baseline column below.)

## What was built

- `SchedulerConfig::prefix_herd` (`INTARSIA_PREFIX_HERD=1`, default off; `docs/tuning.md` row). Two `BatchSeq` hooks with no-op
  defaults: `herd_min()` (the store's `min_tokens`, `Some` only for a store request) and `herd_resume(model, slot, pos)`.
- Hold (`Scheduler::herd_held`): a prefilling request is held while an **older** (lower id) store request is still prefilling, shares at
  least `min_tokens` leading tokens with it, and has not prefilled past that shared length, while the held request has not either. A leader is
  always older, so the oldest prefilling request is never held: no cycle is possible. A leader that finishes, is cancelled or fails stops
  prefilling and releases its followers, which then prefill whatever no stored prefix covers.
- Resume (`Scheduler::prefill_pick` -> `herd_resume`): the first time a released follower is picked for a chunk it looks the store up again
  (`SeqStore::restore`: the same `lookup_filtered`, the same schedule-point / `chunk_invariant` filter, the same restore as admission, the
  MTP head restart included) and continues from the longest stored prefix longer than its position. `Seq::pos` / `cached` follow, so `Done`
  reports the restored tokens as cached. Counters: `herd_holds`, `herd_restores`, `herd_tokens` in `BatchMetrics`.
- Scheduler edit is localized: `prefill_pick` replaces the one `position(Prefilling)` line of the non-overlap prefill loop in `step`, plus
  new methods. **Merge point for lane `sjf`**: its ordering belongs inside the candidate selection of `prefill_pick`, and requests for which
  `herd_held(i)` is true must stay excluded from it. (The overlap branch is untouched; overlap is refused with the store.)

### Design choice: hold, then restore once

With the store on, packed prefill and overlap are off and the scheduler gives one chunk per iteration to the oldest prefilling request.
So even with the herd off a follower sits idle until its leader's whole prefill is over; what it loses is only the second look at the store.
"Hold until the leader passes the shared length, restore once" is therefore optimal in compute (the GPU is serial, a follower cannot
use a capture before it exists) and in lookups (one per follower). Re-looking up before every follower chunk would add lookups and
partial restores that each get overwritten, for no gain. The hold itself changes nothing under FIFO and matters as soon as another
policy (`sjf`) can pick a younger request first: without it the follower would prefill the prefix cold.

### Deferred captures are restorable before the settle

The leader's per-chunk captures are inserted device-to-device and moved to host only at its `Done`, but the entry is in the store at once and
`restore` reads a device-tier object like any other (store test `store_deferred_captures_restore_unsettled_then_settle_to_host_and_disk`).
Measured on the Spark: the herd-on visits show **21 more device-tier hits** than the herd-off ones (3 cells x 7 followers), host hits equal
(24 each): the followers restored before the leader's `Done`. Cost: 21 extra restores = +0.29 s of restore time in total over 3 cells
(about 14 ms each, `last_restore_ms` 28 ms for the 2k admission restore and the 16k one alike). No change to the leader's captures was needed.

## Verdict

Ship **opt-in**: gate (a) passes, ids gate passes, no-regression cell ties. For a later default decision by the user: 4x lower TTFT sum / wall for 8
simultaneous requests with one new 16k prefix, no change for unrelated prompts, bitwise replies. Not covered: staggered arrivals on the GPU
(mock-tested only: a late follower restores at admission and again after its hold), prefixes of other sizes, `max-batch 16`, the interaction with
lane `sjf`'s order (see the merge point above), Metal / HIP (CPU tests only for the store-with-batching path there).

## Revert

Unset `INTARSIA_PREFIX_HERD` (default off). Code revert: the three commits of the branch; the hooks default to no-ops.
