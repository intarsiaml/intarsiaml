Status: **shipped default-on** (bitwise, so no numerics decision). `matmul_mxfp4_nax` calls of 129..192 rows run the in-kernel

## 1. Microbench and the limits (task 1)

`examples/naxd_bench.rs` (lane mprefill's microbench; the only change is a `ROUNDS` line per cell with the round's times in round
order), per `matmul_mxfp4_nax` call: the scratch path against each in-kernel form, 7 interleaved rounds (the arm order rotates every
round, so a round's arms ran back to back), a 1 GiB pool of distinct weights, W4A16. M = 128, **129**, 144, 160, 176, 192, **193**,
224, 256 (129 and 193 added: the first row of a third and a fourth 64-row tile, where the form's cost steps; the Ms between sweep
points, for example 130..143, were not measured). Form 0 (64 x 64, BK 64, 4 simdgroups) is the routed form. Output hashes equal across all arms in all 108 cells
(`HASH DIFFERS`: 0 lines).

Two runs, `raw/bench-run1-thermal2.txt` (#9802, thermal pressure 2 before and after: a hot box) and `raw/bench-run2.txt` (#9806,
waited for pressure 0 first, 2 again at the end). `scripts/msm192/limits.py` pools the rounds (14 per cell): ratio = scratch time /
form 0 time within each round; **limit = the largest M of the sweep such that every M' from 128 up to it has its worst round at
least 1.03x**, capped at 192 (the brief). Median ratio over the 14 rounds, worst round in brackets; bold = worst round at least 1.03:

Per-run limits (`raw/limits-run1.txt`, `raw/limits-run2.txt`), in the table's row order: run 1 (hot) 192 / 192 / 192 / 160 / 144 / 129,
run 2 (cooled) 192 / 192 / 192 / 192 / 160 / 128; pooled 192 / 192 / 192 / 160 / 144 / 128. The pooled worst rounds fix the limits, so
the hot-box run 1 is what holds 10240 x 5120 at 160 and 5120 x 6144 at 144 (the cooled run alone would allow 192 and 160).
Measured Ms are the sweep above: a limit of 160 means 161..176 did not pass in every round, and Ms between sweep points were not
measured. The ratio is highest at M = 129 and falls to 144 on most shapes (the form pays for a third 64-row tile from the first
row past 128), then is flat to 192.

* **GDN z projection = 6144 x 5120**: Qwen3.8-27B has 48 linear-attention value heads x 128 = 6144 (`config.json`
  `linear_num_value_heads`, `linear_value_head_dim`), hidden 5120. The 10240 = 2 x (16 x 128) + 6144 qkv in-projection and the
  12288 = 24 x 256 x 2 q + gate projection pin the other labels. No other projection has N = 6144, K = 5120, so the entry-less
  6144 x 5120 is the z projection only. The z projection is the shape msmallm found losing at
  M = 160 (0.94x there; 0.99x worst round here at 160, 1.01x at 129): it stays at 128.
* Above 192 (M = 193..256) the FFN shapes still gain 1.09x to 1.14x median (worst round 1.01x to 1.07x), the others go to 0.97x to
  1.09x. Not taken: the brief caps the limit at 192 (a follow-up could raise the three FFN / attn q + gate shapes).

## 2. Implementation (task 2)

`crates/intarsia-backend-metal/src/mxfp4.rs`:

* `NAXD_SHAPE_MAX_M: &[(N, K, limit)]` (five entries) and `naxd_max_m(n, k)` (the entry, else `NAXD_SMALL_MAX_M` = 128).
* `naxd_pick(knob, m, n, k)` (was `(knob, m)`): `Auto` => `m <= naxd_max_m(n, k)`. The one caller, `launch_mxfp4_nax`, passes the call's
  N and K (`w.shape[0]`, `x.shape[1]`). `Off` and `All(f)` are unchanged.
* Same kernel registration, scratch size, plan, M > 8 boundary to the GEMV and form 0 as lane msmallm; the form is bitwise the scratch
  path (lane mprefill's `naxd_forms_are_bitwise_the_scratch_path`, the extended routing test below). Not touched: the dispatch around
  `launch_mxfp4` (lane mb16's rows dispatch).
* Docs: the `INTARSIA_METAL_MXFP4_NAXD` row of docs/tuning.md and two comments (`kernels.rs`, `launch_mxfp4_nax`) said "M <= 128".
* Outside the three named things, disclosed: the `ROUNDS` print in `examples/naxd_bench.rs` (bench tooling).

`tests/mxfp4_nax.rs::small_m_routing_is_bitwise_the_scratch_path` now: for every `NAXD_SHAPE_MAX_M` entry, `Some` at 9, 128, 129, limit - 1 and
limit and `None` at limit + 1 and 4096 (and the `Off` / `All` arms); unknown shapes keep 128 (`None` at 129); the six 27B shapes have

window edges (128, 129, limit - 1, limit, limit + 1 on 5120 x 6144; 129, limit, limit + 1 on the other four) for W4A16 and W4A4,
bf16 and f32 outputs.

## 4. Speed (task 3)

`scripts/msm192/abba.sh`: per visit a fresh server (default engine: MTP, max-batch 1), a warm-up slice no cell uses, then cells of 8
distinct prompts of an exact token count (`scripts/msm192/prompts.json`, `prompt_tokens` checked at 100 / 140 / 170 / 190), one
stream, 16 tokens, TTFT per request; the null4k cell is 3 requests of about 4.7k tokens. A = main `c60d26caf` binary, B = this branch,
both with the knob unset. Prefill rows are tokens - 1, so 140 / 170 / 190 tokens are 139 / 169 / 189 rows (inside 129..192;
the shapes with a limit under 190 leave the form at the top of it). Thermal pressure 0 at the start of every cell (COOL waits). Round 1 visit order A1 B1 B2 A2 (#9812,
COOL 180), round 2 B3 A3 A4 B4 (#9817, COOL 240).

Round 2 (`raw/abba2-analysis.md`; the cooled round, spread = (max - min) / mean over the arm's two visits):

| cell | tokens | A TTFT p50 ms | B TTFT p50 ms | B / A | spread A / B |
|---|---:|---:|---:|---:|---|
| t100 (null: M <= 128 on both) | 100 | 212.6 | 212.6 | **1.000** | 0.1 % / 0.1 % |
| t140 | 140 | 346.5 | 291.8 | **0.842** | 0.2 % / 0.1 % |
| t170 | 170 | 357.9 | 309.4 | **0.864** | 1.5 % / 0.2 % |
| t190 | 190 | 367.2 | 326.2 | **0.888** | 1.7 % / 2.0 % |
| null4k (remainder only) | 4719 | 5454.9 | 5477.2 | 1.004 | 12.8 % / 2.7 % |

Both rounds pooled (4 visits per arm; `raw/abba-all-analysis.md`): t100 0.981, t140 0.845, t170 0.884, t190 0.902, null4k 1.011.
Round 1 alone (`raw/abba1-analysis.md`): t140 0.848, t170 0.903, t190 0.916, t100 0.963 (its second pair of visits ran 4 to 10 %
slow on both arms at thermal 0: A2 t100 234 ms against 212 ms in every other visit, so the pooled null spread is 10 %: that is
the noisy pair, not an effect of the build; B / A inside the pair is the same as in the rest). The 4k cell's A arm swings 5.1 to 5.8 s
visit to visit in both rounds (a 3-request p50 of a 5 s job), so it does not meet the under-3 % null bar; **the 100-token cell is the
null cell** that does (round 2: 0.1 % spread, B / A 1.000), as the brief allows.

The step at 129 rows on main is visible in the A column: 100 tokens 213 ms, 140 tokens 347 ms (the scratch path's weight decode
over the whole model, once per call, against the in-kernel decode that skips it). The gain shrinks with the length (-16 % at 140,
-11 % at 190); the shapes whose limit is 144 or 160 are back on the scratch path in the upper part of 129..192.
