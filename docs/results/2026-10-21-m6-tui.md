# M6: terminal UI (`intarsia tui`), 2026-10-21

## Headline

`intarsia tui [--url http://host:port]` ships as the new `intarsia-tui` crate behind the default-on `tui` cargo feature of
`intarsia-cli`. It shows the live architecture map (queue, prefill/decode, layer stack from the plan, kernels, KV cache,
sampler, output) with live overlays, a metrics pane with sparklines and TTFT/ITL percentiles, and a streaming chat. It runs
against a real Metal server (Qwen3-8B, `--max-batch 4`) and shows non-zero live metrics. No server change was needed.
Usage, data sources and the snapshot: `docs/tui.md`.

## Live numbers (Qwen3-8B, Metal, `--max-batch 4`, one chat request of 107 generated tokens)

| Frame | What it shows |
| --- | --- |
| mid-stream (t=2.3 s) | running 1, decode 7.1 tok/s and prefill 27.3 tok/s (scheduler counters over the last scrape), ITL p50 42 ms, batch avg 1.0 rows, step 37.5 ms, chat "streaming 16 tok" |
| reply finished (t=6.8 s) | decode 21.1 tok/s, last request TTFT 156 ms / decode 23.1 tok/s / prefill 173 tok/s, KV 133 / 16384 tokens (0.8 %), ITL p50 43 ms p95 82 ms p99 152 ms (n=98), kernel shares (matmul 31.6 %, matmul_pair 28.9 %, rmsnorm_add 14.0 %), chat "107 tok in 4.8 s (22.5 tok/s)" |
| settled (t=9.6 s) | rates back to 0, TTFT p50 175 ms (n=1; interpolated inside its histogram bucket, the real value was 153 ms), tokens prompt 27 / generated 107 |

Findings from the run (they changed the code, see the decisions):

- The engine books token counters, KV tokens and `last_*` values when a request finishes, so mid-stream they read 0. The
  decode/prefill rates therefore come from the scheduler counters in `/metrics` when `--max-batch N` is on.
- The plan lists kernel variants per op (`matmul` three times), so the map merges them per op name.
- Metal serving defaults to `--profile-every 0`, which turns kernel shares into `n/a`; the live run used `--profile-every 16`.
- Port 18099 was taken by something else in the first attempt (fleetq #3103, no result); the script now picks a free port.
