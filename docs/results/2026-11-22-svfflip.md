# svfflip: `INTARSIA_SAMPLED_VERIFY_FAST` default-on for CUDA (2026-11-22)

Lane `svfflip`, branch `svfflip` from origin/main `2474c17b9`. User decision #13 (approved 2026-11-22): make `INTARSIA_SAMPLED_VERIFY_FAST` default-on. Code, tests and docs only; no new measurement (the default-on path is the measured `=1` path).

## What changed

- Recipe key `[tuning.cuda] sampled_verify_fast = true` in `recipes/qwen3_5_moe.toml` (the Qwen3.6-35B-A3B NVFP4, the measured pair), resolved in the loader like the flipprep keys `batched_verify` / `verify_topk` (`Recipe::resolve_sampled_verify_fast`, `engine::resolve_sampled_verify_fast`, `load.rs`). Every other recipe and backend: off.
- `INTARSIA_SAMPLED_VERIFY_FAST` wins both ways. Parse (`engine::sampled_verify_fast_env`): `0` / `false` / `off` / `no` off, `1` / `true` / `on` / `yes` on, unset or empty: the recipe decides, unknown: warning and the recipe decides. (The KV-once variable reads `=off` as on; this one does not.)
- The knob acts as before only with batched MTP and sampled drafting (`BatchedEngine::new`: `opts.sampled_verify_fast && mtp && opts.mtp_sampled`). Startup line names the variable and says `=0` turns it off. Doc comments, `/metrics` help texts and the `docs/tuning.md` row no longer say opt-in.

## Why CUDA / the 35B recipe only

The evidence is CUDA, 35B NVFP4, tp 1, one and two sampled streams ([samphost](2026-11-20-samphost.md), [samp2s](2026-11-20-samp2s.md)): one stream sampled +13 to +18 % at 4k / 32k / 64k, two streams neutral (+0.6 / +4.2 / -2.9 %, all inside 2 SE, the pass cost is unchanged), `top_k` 0 one stream +14.6 %, seeded replies byte-identical on or off (`top_k` 20 one and two streams, 0 and 100 one stream). The fast path is backend-generic code (device-side top-k needs `device_sampling`, on for CUDA and HIP; the captured step exists on every backend that captures graphs) but was never run on Metal or HIP, so those stay off, as the copy-draft default (#474) and the KV-once default (#473) scoped their flips to the backend measured. The 27B on CUDA has no `batched_mtp` in its recipe, so the knob would be inert there either way; it is not opted in.

Not measured, and therefore not flipped: Metal, HIP, tp 2 (a sampled request does not speculate there), the 27B, `--max-batch 1` (single-sequence engine, which does not read the knob), `top_k` 100 timing, `n` > 2 sequences.
