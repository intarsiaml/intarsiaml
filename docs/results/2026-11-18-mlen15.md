# Lane mlen15: Metal copy-chain len 15 and `INTARSIA_METAL_VERIFY16` default-on (decision candidate)

Date 2026-11-18, endor (Apple silicon, Metal), Qwen3.6-35B-A3B NVFP4, `--spec mtp --spec-k 2`. **Decision candidate, not merged.**

## The decision

On Metal only:

1. `INTARSIA_METAL_VERIFY16` unset = on (`0` = off, `1` still works). The 9..=16-row `moe_experts_bf16_rows` calls run the bit-decode kernels, bitwise the one-token call (`crates/intarsia-backend-metal/tests/moe_verify16.rs`).
2. `INTARSIA_SPEC_COPY=<n>` without `,<len>` means chain `len` 15 on Metal (16-row verify passes); CUDA and every other backend keep 7 (the CUDA GatedDeltaNet verify block takes at most 8 rows). Copy drafts stay opt-in. `<n>,<len>` and the adaptive `<n>,<len>,a` (#440) behave exactly as before.

They flip together: len 15 without VERIFY16 lost json-xform 0.958x (`docs/results/2026-11-18-mrows16.md`, #438).

## Evidence (earlier lanes, not re-measured)

`docs/results/2026-11-18-mmoe16.md` (#450), served, 4 ABBA rounds:

| Cell | len 15 + VERIFY16 vs len 7 | len 15, VERIFY16 on vs off |
|---|---|---|
| copy3k | 1.138x | 1.060x |
| json-xform | 1.006x (tie) | 1.031x |

Greedy ids 8/8. #455 (`mmoedec`) found no served gain from extending the bit-decode to 1..=8 rows, so nothing else is waiting on this knob.

## Where the length is resolved

One place knows the backend: `crates/intarsia-core/src/spec.rs`, `set_copy_backend` (line 387) records `copy_len_default_for(backend)` (Metal 15, else 7) in a process-wide atomic, and `copy_from_env` (line 496) resolves an `INTARSIA_SPEC_COPY` value without `,<len>` against it on every call (the env text is cached, the length is not). Both consumers go through `copy_from_env`: the load-time verify-row width (`SpecConfig::save_rows` / `verify_rows`, spec.rs) and the engine's chain (`crates/intarsia-core/src/engine.rs`, `meta.spec_copy.or_else(copy_from_env)`), so they cannot disagree. The loader calls `set_copy_backend` as soon as the backend is known: `load_engine_group` right after `backend_name` (`crates/intarsia-models/src/load.rs`) and the tensor-parallel rank entry `serve_remote_rank`. An explicit `EngineMeta::spec_copy` (tests) wins as before. `CopyCfg::parse` keeps the old default (7); `CopyCfg::parse_with(v, default_len)` takes it.

Decode tok/s from `generate`; one run each, so noise of several percent is expected. The served ABBA rounds above are the evidence for speed.

|---|---|---|---|---|
| copy3k | 120.6 | 441.1 | 407.5 | 370.0 |
| json-xform | 119.3 | 316.9 | 339.7 | 335.1 |
| code-gen | 124.9 | 203.8 | 213.3 | 204.5 |

json-xform's single run has the new default 5 % under base and 7 % under `VERIFY16=0`, against a served tie (1.006x) and a 1.031x gain of the knob in 4 ABBA rounds; this is one `generate` run per arm and was not repeated. code-gen has no copies, so the default does not change it (203.8 against 204.5).

## Notes for the decision

* Default-on VERIFY16 also changes a `--max-batch` decode step of 9..=16 sequences and a 9..=16-token prefill tail (same kernel, bitwise per mmoe16); only the copy-chain path is gated here.
* The loader now reserves 15 per-row recurrent-state buffers (instead of 7) when `INTARSIA_SPEC_COPY=<n>` is set on Metal; the plan is unchanged with the variable unset.
* With VERIFY16 on, `INTARSIA_METAL_NEGCTL=moe_gu` / `moe_dn` and `INTARSIA_METAL_MOE_ROWS_FAT=0` negative controls no longer reach 9..=16-row calls (`=0` restores them).
* Revert, no rebuild: `INTARSIA_METAL_VERIFY16=0` and `INTARSIA_SPEC_COPY=<n>,7`.
