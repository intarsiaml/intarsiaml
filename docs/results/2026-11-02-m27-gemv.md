# M27-GEMV: Qwen3.8-27B MXFP4 decode on Metal (endor, Apple M5 Max): the GEMV was ALU-bound, decode +20 % (4k) / +15 % (16k), bits unchanged

Lane `m27-gemv`, branch `lane-m27/gemv`, 2026-11-02 (EST), base `origin/main` `c33851575` (PR #283, lane m27: MXFP4 prefill GEMM, MTP k2 default). Box endor; every GPU or timing run held a fleetq slot (owner `claude-m27-gemv`, job ids below; `--quiet gpu,cpu` for timing). Raw logs: `2026-11-02-m27-gemv/raw/` (largest file under 1 MB). No slot is held.

## 1. Task 1: where the decode time goes (4k, MTP off)

* **Bytes per decode pass: 15.48 GB**, not the 18.03 GB resident size: 12.94 GB MXFP4 codes and scales (summed `bytes` of the `t = 1` launches of the profile), 2.54 GB bf16 `lm_head`; the 2.5 GB embedding table is a row gather. The KV read at 4k is 0.27 GB (16 full-attention layers, 4 kv heads, 256 x 2 B x 2 x 4096) and the GatedDeltaNet state traffic is not counted. At 21.9 to 23 tok/s that is 340 to 355 GB/s over the whole token.
* **Time split**, per-kernel profile (`INTARSIA_METAL_PROFILE=kernel:`, one command buffer per launch, so each time carries a few us of fixed cost; fleetq #7982, `raw/profile/kernel-mode-base-4k.jsonl.gz`), main-like base, one step: 42.6 ms = MXFP4 GEMV 30.1 ms (**71 %**) + bf16 `lm_head` 5.5 ms (13 %) + decode attention 4.0 ms (9 %, 16 calls of 251 us) + everything else 3.0 ms (7 %). The GEMV is over half, so it was the right target. The GEMV rate in that profile, bytes-weighted: **429 GB/s** (gate/up 462, down 455, GDN qkv 434, z 398, out_proj 395, q_proj 449, k/v 202, the 48-row GDN `a`/`b` projections 14 GB/s). If every GEMV ran at the 574 GB/s of the 8B BF16 GEMV, the step would lose 7.6 ms (18 %).
* **Host and encoding**: `INTARSIA_METAL_PROFILE=cb:` (normal submission, fleetq #8031, #8117; `raw/scripts/cbstats.py`): a step is 948 launches in 9 command buffers; GPU busy 41.93 ms of a 42.16 ms step on main (GPU idle **0.6 %**, the gap is the token feedback), 35.91 of 36.16 ms on this branch. Decode is GPU-bound; encoding and CPU overhead are not a lever. (An earlier cb run, one slot, #8031: lane-m27 base 46.86 / 47.66 ms with 1.7 % idle vs the GEMV-only change 40.45 / 40.74 ms; it is a different slot from the main run, which is why the same kernels read 46.9 and 40.6 to 41.9 ms.)
* **Comparison inside the backend.** `gemv_bf16.metal` (574 GB/s on the 8B): per 16-byte weight load a lane does 8 bf16 products, i.e. 0.5 elements per DRAM byte; `UNROLL` independent 16-byte loads in flight, 2 ALU ops per bf16 pair to widen both operands, then one fma per element. `nvfp4.metal` decodes two codes per mask-shift pair by building a half (`nv_x2`, value x 2^-14) and folds 2^22 into the scale. `mxfp4.metal` decoded one code at a time with a compare-and-select chain on the magnitude bits (about 13 integer operations per weight by counting the source, an estimate), so a DRAM byte (2 weights) cost about 30 ALU operations against about 1.5 for the BF16 kernel's 0.5 element per byte. At 365 to 430 GB/s that is about 5 T operations/s (an estimate; the chip's peak was not looked up). The variant sweep below is the evidence: only the decode change moved the rate, more loads in flight or more rows per simdgroup did not. **The kernel was decode-ALU-bound, not latency-bound.** Its activation loads (64 B per 16 B of weights, from L1) were not the limit either.

**Second change: no activation pre-pass dispatch for W4A16 calls (`INTARSIA_METAL_MXFP4_XFUSE`, default on).** Every GEMV was preceded by a dispatch that copied x (W4A16) or QDQ'd it (W4A4) into scratch. For a W4A16 call (`OpAttrs::mxfp4_w4a16`, which the model sets when the activations are not quantised, so `act` is 0 and the pre-pass is a copy) with 16-byte aligned x, the GEMV reads x itself. A hack that only skipped the dispatch (fleetq #8010) measured 1.3 to 2.2 us per call; in the model, rotated and in one slot, fusion on vs off is **+5.1 % at 4k and +1.8 % at 16k** decode (26.13 vs 24.87 and 21.08 vs 20.71 tok/s, #8113, #8114; the pre-pass dispatch is largely hidden in the isolated pool benchmark, where fused and pre-pass tie, `raw/microbench/xfuse-vs-prepass-w4a16-w4a4.txt`, #8110). MTP k2 with fusion off was not run. `INTARSIA_METAL_MXFP4_XFUSE=0` restores the pre-pass.

**A first version also fused the W4A4 QDQ into the GEMV (each output row's simdgroup QDQ'ing the activation groups it reads). Measured, that is 1.9x (M = 1) to 3.4x (M = 3) slower for W4A4 (`raw/microbench/w4a4-in-lane-qdq-regression-before-the-gate.txt`, fleetq #8100: 164.9 vs 86.0 us at 17408x5120 M = 1, 466.5 vs 138.9 us at M = 3): every row repeats the QDQ of the same group N times in a kernel that is already ALU-bound. It is not shipped: W4A4 calls keep the pre-pass, the in-lane QDQ code was removed, and the final microbench shows W4A4 fused-flag on or off equal (1.00 to 1.01).**

Attribution run (fleetq #8050 and #8062, rotated, base = lane m27's `9bad344e7` build, an earlier build of this branch; 4k / 16k decode tok/s): base 22.08 / 16.8; GEMV decode only 25.53 / 19.4 (+15.6 %, +15.3 %); + fusion 26.07 / 19.7 (+2.1 %, +1.4 %); + head split 3 28.08 / 24.5 (+7.7 %, +24.5 %).

## 3. In-situ result (kernel-mode profile, 4k, fleetq #8117; the base figures of section 1 are from another slot, so only ratios inside one column mean anything)

Branch, one step 37.3 ms in kernel mode (base 42.6, other slot): GEMV 25.1 ms (67 %) at **516 GB/s bytes-weighted** (gate/up 536, down 531, qkv 534, z 506, out 498, q_proj 542, k/v 319, 48-row projection 24 GB/s at 5.5 us each), `lm_head` 5.5 ms (465 GB/s), attention 3.9 ms, rest 2.9 ms.

Target (GEMV at or above 500 GB/s): **met bytes-weighted over the step (516 GB/s) and for every projection of 6144 x 5120 and above (498 to 542 GB/s in the profile, 525 to 570 in isolation), which carry over 99 % of the GEMV bytes.** Not met, with reasons: the 1024 x 5120 k/v projections (5.2 MB: 7 us, latency and dispatch bound, 319 to 406 GB/s) and the 48-row GDN `a`/`b` projections (96 launches of 5.5 us each, 0.5 ms per step = 1.4 % of the step; launch-bound, a fused or pair launch would be the fix). The microbench's cold pool and the profile's per-buffer fixed cost both include a few us per call, so the large shapes' 550 to 570 GB/s in isolation and 531 to 542 in situ are the honest pair.

## 5. The attention head split: +5 % at 4k and +25 % at 16k over the branch default, **not made the default** (gate result below)

The profile shows 16 decode-attention calls of 241 to 251 us per step at 4k, 67 GB/s of KV. The 27B's full attention is 24 query heads over 4 kv heads at head_dim 256: a group of 6, padded to 8 registers per lane, the spill case that `head_split` (`INTARSIA_METAL_ATTN_HS`) was added for the 35B's group of 8 (default 4 there, 1 for everything else). With `INTARSIA_METAL_ATTN_HS=3` (two heads per threadgroup, no padding) on this branch: decode 4k x1.053 over the branch default (27.52 vs 26.13), 16k x1.248 (26.31 vs 21.08), k2 4k x1.088 (32.79 vs 30.15) (fleetq #8113, #8114, #8116; an earlier rotated run, #8029 / #8033, gave HS=2 and HS=3 the same: +8 % at 4k, +25 % at 16k).

It is not bitwise: the split changes GP and the simdgroup count, so the rounding order differs. Gates with the final-tree binary and the env var set (`raw/accuracy-hs-rejected/`, `raw/identity-hs3/`, binary = this branch before the m8 loop change, the attention kernel is the same): floor PASS; all-rows decode KL 7.17e-4 (HS=3) and 7.55e-4 (HS=2) against the baseline's 1.28e-3, top-1 99.38 % unchanged; but the per-prompt baseline comparison (fixed margins x1.75 + 1e-5 on 16 teacher-forced positions per prompt) **FAILS** for 2 of 10 prompts at HS=3 (chat_system 3.0e-4 -> 5.9e-4, limit 5.4e-4; long_prose_300 1.4e-4 -> 6.5e-4, limit 2.6e-4) and 1 of 10 at HS=2 (long_prose_300 -> 1.6e-3); HS=1 (the default) passes with identical numbers. The 4k greedy text differs from main from character 704 on at 256 tokens at HS=3 (the short prompt is identical). MTP k2 == off with HS=3 was checked on the earlier tree (identical, `raw/dev/gates1-hs3-binary.log`), not on the final tree. So the head split is a **numerics change that fails the project's per-prompt gate on tiny absolute KL (1e-3 nats)**, and flipping it is a decision for the coordinator or the user: the one-line change is `head_split` in `crates/intarsia-backend-metal/src/attn.rs` returning `grp / 2` for `d == 256 && grp == 6` (plus the unit test `head_split_divides_the_group...` and the `INTARSIA_METAL_ATTN_HS` row's default), about +5 % at 4k and +25 % at 16k for the 27B. A bitwise variant would need the split count and simdgroup count to stay those of HS=1 (the policy sees the virtual kv head count); not tried.

## 6. Not done, not checked, open

* **Head split default** (section 5): measured, gated, left off.
* **`lm_head`** (bf16 GEMV, 248320 x 5120): 5.4 ms, 471 GB/s against 574 for the 8B shape; 12 % of the step, ~1 ms of headroom. Not tried (its variant choice and K = 5120 blocking are in `kernels.rs` `GEMV_VARIANTS`).
* **48-row GDN `a`/`b` projections** (0.6 ms / step) and the **1024-row k/v projections** (0.3 ms): launch-bound; a pair or fused launch is the lever.
* The M = 8 / MTP-verify multi-row form is ALU-bound on its per-row chain (150 GB/s); a smaller gain there than at M = 1 (x1.10 vs x1.2).
* W4A4 (`--mxfp4-act dynamic`) was pinned bitwise in the test, not run end to end on a model; MMLU, 32k context, batched serving (`--max-batch > 1`), peak memory and the localeval sweep were not re-run (this lane changes decode kernels only; localeval takes its own slot and was not needed for the same-binary A/B above).
* The gap to the TensorFold 4-bit decode (65.6 tok/s at 4k, old record, different quant) is untouched: this branch is at 26.1 tok/s (30.2 with MTP k2) at 4k.
* Development A/Bs on earlier builds (`raw/dev/`, not rotated for ab1) and the variant sweep binaries are in `raw/microbench/`; the m8-form check (v1 vs v3 vs v5, fleetq #8074) chose the loop that keeps the direct bf16 load when no QDQ is needed.
* No slot is held. Worktree scratch (`.scratch/`, `target/`, `target-test/`) is left in `.worktrees/m27-gemv` (ignored by git); the temporary main worktree was removed with `git worktree remove`.
