## Result

**#382 works on CUDA when no MTP head is loaded, and does not reach the CUDA default config (MTP on at tp=1).** In the default config
every `restore` and `aligned` case of acc-4k still reuses nothing (`cached 0`) and the prefix-reuse gate fails. The cause is the MTP
exclusion #382 documents (`SequenceState::inner_snapshot_bufs`, `crates/intarsia-core/src/state.rs:541`, `self.mtp.is_some()` returns no
buffers, so a macro pass snapshots only at its end). That is the HIP doc's open item, now shown on CUDA's default serving path. Not
fixed here: an MTP snapshot needs the head's pending rows at the inner chunk end, which the pass has only at its end (design work).

### 4. Why does `long_code_4k continue` diverge at token 3? Noise of a near-tie prompt, not a reuse bug

The evidence, in the order it settles the question:

1. **Different prompt, no oracle.** The committed `long_code_4k` continue oracles (`golden/oracle/*long_code_4k-s2000|s3072*`) were built from the *long* golden (`"golden": "qwen36-35b-a3b-nvfp4-vllm-long-top20.safetensors"`, prompt-id fingerprint `8a94fca8861bbbb4`). The 4k golden has a `long_code_4k` prompt of the same name with other token ids, so `find_continue_oracle` skips the oracle ("the golden's prompt token ids differ from the ones it was made for", `accuracy.rs:1993`) and `continue` falls to the absolute stream tolerance, which is built to flag any divergence beyond 0.25 nats at a near-tie. The two 4k-golden prompts with an oracle (long_docs_4k, chat_reuse_4k) pass `continue` oracle-relative in every arm.
2. **At the divergent token the model is at a near-tie.** On the 4k golden: cold margin 0.168 to 0.191 nats (top-2 log-prob gap), warm margin 0.355 to 0.632; warm and cold pick different top-2 tokens (warm 23776 / 1901, cold 1528). Shared rows differ by 0.45 to 1.0 nats and KL up to 4e-2 to 1e-1, which exceeds the 0.25-nat built-in scale only at this one row.
3. **Same prompt family against the oracle passes.** One run (main, default config, long golden, chunk 1024, split 2000, so the committed s2000 oracle applies; `raw/p395/main-acc-longgolden-c1024.log`): `long_code_4k continue` agree **32/32**, `mean KL(oracle||cold) 2.13e-3, mean KL(oracle||warm) 2.87e-3, warm/cold 1.35x, limit 1.5x cold + 3e-3 = 6.20e-3: PASS`; `long_docs_4k` 27/32 PASS (0.81x), `chat_reuse_4k` PASS (1.11x), long_code_12k 20/32 ok. The earlier fx5c measurement of `long_code_4k` on CUDA against an f64 CPU oracle says the same (`2026-10-22-fx5c-reuse-vs-oracle.md` section 5b: KL to the oracle cold 2.80e-3, warm 3.09e-3, 1.10x; both top-1 32/32).
4. **Not specific to resuming.** It is identical at chunk 2048 and 1024, with spec off, with macro off and on the pre-#382 tree, so no part of #382 / #395 touches it. A first diagnostic attempt (`--reuse-diag`, same long golden, `raw/p395/main-acc-longgolden-c1024-diag.log`) died after the first prompt with "bad request: empty token list" in the `restore` diagnostic (a tool defect, not investigated) but its `long_docs_4k continue` block already shows the underlying property: on this build cold chunk 1024 vs cold chunk 512 differ at KL 9.5e-3 mean (1 argmax flip), cold 1024 vs 1023 at 1.45e-2, and warm vs cold (same context) at 1.67e-2, i.e. the warm / cold gap is the size of a chunk-shape change; cold 1024 vs 2048 is bitwise (so macro and chunk 2048 are exact). Warm and cold are each deterministic (bitwise on rerun).

Conclusion: warm (resumed at `plen - 1`, one 993-row tail chunk) and cold (chunked) are two samples of the same bf16 noise cloud; on a low-entropy code prompt with a 0.17-nat top-2 margin that is enough to flip token 3. Evidence against a reuse bug: oracle-relative pass on the matching golden and fx5c. Not proven for the 4k golden's own `long_code_4k` (no oracle for its ids). Suggested follow-up (not done): build a `long_code_4k` continue oracle for the 4k golden, or judge it by the legacy "16 leading tokens" rule as HIP does.
