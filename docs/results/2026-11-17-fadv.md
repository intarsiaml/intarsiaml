# fadv: drop the checkpoint's page cache after the weights are on the device (2026-11-17)

Verdict: **ships default-on for the CUDA backend on integrated-memory devices (GB10), `INTARSIA_LOAD_DROP_CACHE=0` takes it back.** Every gate passes. Revert: set `INTARSIA_LOAD_DROP_CACHE=0`, or revert the PR (no other file depends on it).

## What changed
- `WeightSource::release_page_cache` (default no-op), implemented by `SafeTensors`, delegated by the compressed-tensors and MLX wrappers and `SchemedSource`. `SafeTensors` first `madvise(MADV_DONTNEED)`s its read-only mappings (drops this process's page-table entries; `posix_fadvise(DONTNEED)` skips pages that are still mapped), then `posix_fadvise(fd, 0, 0, DONTNEED)` on each shard.
- `load.rs` calls it once after `Model::load` / `load_shard` (both the local, tensor-parallel and remote-rank paths) when `INTARSIA_LOAD_DROP_CACHE=1`, or unset on a backend named `cuda` whose `DeviceInfo.unified` is true. `docs/tuning.md` has the row.
- No `O_DIRECT` reads were added.

## Is anything still referencing the mapping? (the brief's check)
- CUDA does not implement `Backend::wrap_host`; only Metal and the CPU backend do. So on CUDA every tensor is copied (`upload_new`) and no device buffer keeps a mapping. Those two backends are off by default, because there the buffer *is* the page cache (forcing `=1` there would only cost re-reads).
- After `Model::load` the loader reads `weights` only for `scheme()` (not file-backed). The DFlash draft opens its own `SchemedSource` and is not touched. The DSv4.1 loader has its own `dsv41_cache.rs` and is unchanged.

- With the drop on, buff/cache does not grow with the checkpoint: off holds +21.5 GB after a cold load, on +0 GB. A warm cache of the shards is also released (-22.3 GB: the shards plus 0.8 GB of the binary and tokenizer files read by the earlier steps).
- Load wall time (process start to exit, includes one token): cold 69.8 / 61.9 s on vs 69.5 / 64.9 s off; warm 31.4 / 33.8 s on vs 37.4 / 36.8 s off. Not worse; cold is within noise, warm is not slower. The drop happens after the upload, so it cannot slow the read itself; with vLLM live the spread between repeats (3 s) is as large as the difference.
- Not measured: the CUDA `MemFree` figure and KV capacity under `serve` after the load (the effective plan already uses `max(MemFree, MemAvailable)`, `hostmem.rs`, so the 2026-10-23 symptom was already patched at plan time; this lane removes the cache itself). `avail_after_mb` (MemAvailable) was 76.2-76.5 GB in all runs, on or off, as expected since MemAvailable counts clean cache.

(c) `plan show --json`: byte-identical on vs off (15570 bytes). The text form differs in one line, `mtp: drafter head 'mtp' loaded in 0.9 s` vs `1.2 s` (a load timing; unrelated to the drop). That is the answer to the open question in the 2026-10-23 08:40 LOG row: `plan show` plans from `max(MemFree, MemAvailable)` (since the hostmem fix) and clean page cache counts in MemAvailable, so dropping it does not move the plan.

(d) `generate` greedy ids, on vs off, 64 tokens: short prompt (5 tokens) identical; 4k prompt (3806 tokens, `--max-seq 8192`) identical. The first 4k try used a 10083-token prompt that the 8192 context rejected for both arms; rerun with a shorter one (`gate_d4k.sh`).

(e) `cargo test -p intarsia-models --lib` 73 passed (new: `load_drop_cache_default_is_cuda_on_integrated_memory_only`; `safetensors` roundtrip now also calls `release_page_cache` and rereads the mapping), `-p intarsia-core --lib` 211 passed, `-p intarsia-cli --test docs_env_vars` 2 passed. All on the Mac (CPU); the Linux-only `madvise`/`fadvise` path compiled and ran on spark2 in the release build above.
