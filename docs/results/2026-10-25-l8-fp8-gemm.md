# Lane l8: dense fp8 GEMM for prefill (bitwise), scope note

Branch `lane-l8/fp8-gemm` off `origin/main` e5af0a159 (after #152/#153). Plan: `docs/plans/2026-10-25-r9700-push.md` Lane 8 (fp8 GEMM half;
flash attention is not in this lane). Nothing in this section was run on a GPU: it is arithmetic on the committed profiles.

## 0. Scope (written before any code)

### 0.1 The kernel today

`f8_gemm_kernel<WN, WM, TN, TM, OutT>` (`kernels/hip/ik_f8_gemm.h`, called from `matmul_fp8_mma_f8` in `fp8.hip`; row-major weights
by default, the `frag` layout is opt-in `INTARSIA_HIP_FP8_FRAG`). W is the A operand (output features), the pre-quantised e4m3
activations the B operand.

| M, N | tile (weights x tokens) | block | wave tile | LDS (static) | used by (35B, M = 4096) |
|---|---|---|---|---|---|
| M >= 2048, N >= 8192 | 256 x 128 `<4,4,4,2>` | 16 waves (512 threads) | 64 x 32 | 2 x (256 + 128) x 80 B = 61,440 B | qkv / q+gate |
| M >= 2048, N < 8192, >= one block per CU | 128 x 256 `<4,4,2,4>` | 16 waves | 32 x 64 | 61,440 B | z, out_proj, k / v |
| other M >= 65 | 128 x 128 `<4,2,2,4>` | 8 waves | 32 x 64 | 2 x 256 x 80 = 40,960 B | tails |
| M <= 64 | 128 x 16 / 32 / 64 | 4 waves | | small | not prefill |

Pipeline: 64 k bytes per stage, one `__syncthreads` per stage, global -> registers (issued at the start of the stage) -> LDS (at its
end), LDS double buffer, one 16 B `ds_read_b128` feeds two WMMAs. VGPR / occupancy lines are filled in from the compile log in 0.4.

### 0.2 What a bitwise change can and cannot touch

One output element is a chain of `v_wmma_f32_16x16x16_fp8_fp8` on one accumulator, in increasing k, where each WMMA sums the 16 products of the 8 + 8 k bytes the two lane halves hold (per 32-k group, lo WMMA = bytes
0..7 and 16..23, hi WMMA = bytes 8..15 and 24..31), then one multiplication by `weight_scale * input_scale`.

* Cannot change: which k enter which WMMA, the order of the WMMAs on one accumulator, a second accumulator per output (split-k or a
  partial-sum tree), the epilogue arithmetic, the activation quantisation (`f8_actq_kernel`), hipBLASLt itself (its internal order
  is not ours; it is a different set of bits, so it is out).
* Can change: block / wave tile, how many waves, the LDS layout (swizzle instead of padding, stage size), the global-load distance
  and register / LDS staging, the order in which *independent* accumulators are issued, `s_barrier` placement, instruction
  scheduling, the epilogue's store pattern. Tile changes were already shown bitwise by hp (21 tiles x 11 shapes, partial M too).

### 0.3 What is left to win

From `docs/results/2026-10-22-hp-hip-prefill-roofline.md` (hp, rocprofv3, Qwen3.6-35B-A3B on one R9700, chunk 4096; hp's section 7
numbers are the profile of today's main, because the hp tile table is what is in the tree):

| | 4k | 16k |
|---|---:|---:|
| prefill span (profile) | 409.7 ms | 1783.8 ms |
| dense fp8 projections (`f8_gemm_kernel`) | 58.3 ms (14.2 %) | 229.0 ms (12.8 %) |
| rate today | about 180 TFLOP/s (work 10.47 TFLOP at 4k) | about 183 TFLOP/s |
| hipBLASLt fp8 at the same shapes | about 284 TFLOP/s (244-306) | same |
| fp8 WMMA issue peak (measured) | 377 TFLOP/s | |
| 3 % of the span | 12.3 ms | 53.5 ms |

Time saved if the kernel reaches a given rate (work fixed, share of the profile span):

| rate | fp8 ms at 4k | saved at 4k | saved at 16k |
|---|---:|---:|---:|
| 200 TFLOP/s | 52.4 | 5.9 ms = 1.4 % | 19 ms = 1.1 % |
| 228 TFLOP/s (80 % of hipBLASLt) | 46.0 | 12.3 ms = **3.0 %** | 44 ms = 2.5 % |
| 250 TFLOP/s | 41.9 | 16.4 ms = 4.0 % | 61 ms = 3.4 % |
| 284 TFLOP/s (hipBLASLt parity, upper bound) | 36.9 | 21.4 ms = 5.2 % | 81 ms = 4.6 % |

The plan's "about 5 %" was written against the pre-hp 164 TFLOP/s; hp's tile table (already in main) took 8 ms of that, so what
is left is **3 % at 80 % of hipBLASLt, 5.2 % at parity**. The upper bound is above the 3 % stop line, so the lane is not stopped
on paper; the stop test is the microbenchmark: a candidate has to average at least about 228 TFLOP/s over qkv / z / out_proj / kv
at M = 4096 (against 160-190 for the tiles in main) to be worth a served A/B.

27B: the 27B's default prefill path is the MXFP4 W4A4 kernels in `mxfp4.hip`; `f8_gemm_kernel` is not called for it (only the
opt-in `INTARSIA_HIP_MXFP4_FOLD=1` kernel is a structural copy of it, with its own code). A served 27B check will say so with a
measurement of `f8_gemm_kernel` launches rather than assume it.
