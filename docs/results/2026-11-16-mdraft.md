# mdraft (2026-11-16): one batched MTP draft for both sequences of a 2-stream 35B iteration (spark2)

Lane `mdraft`, branch `mdraft`, worktree `.worktrees/mdraft`, from main c8367d5a7 (#409). Follows `docs/results/2026-11-16-mtp2s.md` (lever 2) and `docs/results/2026-11-16-itl2s.md`.

## Verdict

**Ship, default-on for CUDA (`INTARSIA_BATCHED_DRAFT=0` off): bitwise-neutral, 2-stream draft 5.00 -> 3.77 ms, iteration 29.4 -> 28.2 ms (-1.26 ms), 2-stream tok/s 1.040x (1.037-1.043x on all 10 cells), 1 stream unchanged (0.997x, 0.995-0.999x: one sequence is never batched).**
It passes the stop rule (>= 0.7 ms per iteration, >= 1.015x). It is the narrow version: the draft lm_head and its argmax are batched, the head's layer passes are not (below), so it is below mtp2s's 1.3-2.5 ms estimate at its low end.

## What was built

A drafting step is, per sequence: a catch-up pass of the head layer over its n queued rows (n = accepted + 1, 1-3), the lm_head + argmax of the last row (download) = draft 1, then k - 1 chained one-row layer passes each followed by lm_head + argmax + download. Serial, two sequences: 4 layer passes, 4 lm_heads (0.6 ms each, the 131072-row reduced head), 4 host syncs.

`Model::mtp_draft_batch` (`crates/intarsia-core/src/model/mtp.rs`): the layer passes stay exactly the per-sequence ones (same row counts, same kernels, each on its own head cache). Only what follows a pass changes: the sequence's output row goes to a staging row (`MtpHead::stage`) instead of an immediate lm_head, and after all sequences' passes ONE lm_head runs over the staged rows on the row-exact multi-row GEMV (`exact_rows`, bitwise the one-row GEMV per row, `tests/rows_exact.rs`) and ONE argmax + download returns the ids. Per iteration: 2 lm_heads and 2 syncs instead of 4 and 4. The ordinary multi-row kernels were deliberately not used for the layer (a 2-3-row catch-up picks `moe_experts_bf16`, a batched row-exact pass would pick `moe_experts_decode_v2_rows_bf16`: different kernels, drafts could differ).

Plumbing (scheduler): `BatchModel::{batched_draft, draft_batch}` and `BatchSeq::{prepare_hold, prepare_finish}` (defaults: never hold, nothing changes); `decode_phase` plans in two phases only when `batched_draft()` and b > 1 (a drafting sequence stops before its draft, `Prep::Draft`; the drafts of all of them run as one batch; each sequence finishes its step in the original order). Both draft branches are held: greedy deferred-verify (`engine.rs`) and keyed/sampled (`engine/keyed.rs`, the T = 1 cells). `Backend::batched_draft()` defaults false (Metal, HIP, CPU unchanged); CUDA returns true unless `INTARSIA_BATCHED_DRAFT=0`.
Falls back to per-sequence drafts (`Ok(None)`, nothing run): 1 or more than 8 drafting sequences, different draft depths (adaptive k), `--mtp-draft-subset` / full draft head, tensor parallelism, scripted drafts, head dump, plan dry run, no verify buffer. #406's prefix-store state is untouched (the head state afterwards, cache length / queue / sync, is what the serial draft leaves; asserted by the unit test).

Note on the counters gate, how it was made deterministic. Raw server counters differ between runs of the SAME binary by a few proposed tokens (mtp2s noted it): a second base run (`base2`) differs from base by 9 of 1017 lines, all at the first passes of one request whose start position depends on when the neighbour's prefill chunk lands. So "identical counters" is checked as the multiset of per-pass lines (position, drafted, accepted), not totals: base == new (second run, `n1b`) with 0 differences, and the first new run and `=0` run equal base2's variant, i.e. every difference is the arrival-time one, none follows the knob. The unit test is the deterministic bitwise check of the draft ids themselves.

## Not built (follow-ups)

- The head layer passes themselves (4 of them, ~0.5 ms each, launch-bound) are still serial. The chained one-row passes could run as one packed pass (`attn_block_packed`, row-exact kernels), bitwise the serial ones by the same argument as batched decode: about 0.5 ms more. The 2-3-row catch-ups cannot be batched bitwise (different MoE kernel for the batched exact pass), so they would need an opt-in numerics change.
- Sequences with different adaptive depths fall back to serial drafts.
- Only spark2 / 35B NVFP4 measured.
