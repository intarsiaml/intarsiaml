## 1. Native WMMA GEMM on HIP instead of hipBLASLt

**Context.** The dev image `intarsia-hip-dev:rocm7.2.4-rust1.90.0` has no hipBLASLt, rocBLAS or rocWMMA; `hipblaslt-dev` is installable from the ROCm apt repo but needs a derived image. `ARCHITECTURE.md` allows a vendor prefill GEMM (`cublaslt` / `hipblaslt`) registered as `Exactness::Fast` only.

**Decision.** Prefill `matmul_bf16` / `logits_bf16` on HIP are a native WMMA GEMM (bf16 16x16x16, f32 accumulate, fixed K order, class Deterministic), tile 128x128 for M >= 128, with a SIMT fallback for K % 32 != 0 or unaligned operands. Decode (M <= 4) uses a native GEMV. The grid puts token blocks on `x`, so resident blocks share one weight panel; that alone took the M = 1024 gate shape from 44.7 to 73.5 TFLOPS. Commit a7da13b.

**Alternatives considered.** hipBLASLt: not tried. `hip.md` says a library GEMM is worth it only if it beats the native one, and would then be registered `Exactness::Fast`. Other tiles (4 waves of 64x64, 8 waves of 64x32, 128x64, 128x32, 64x32, 256x64) were equal or worse at M >= 256; 128x128 stays.

**Consequences.** No vendor-library dependency and a deterministic fixed-order GEMM. Qwen3-8B prefill is 2.0k to 3.4k tok/s at the default 256-token chunk and 3.7k to 4.4k with `--prefill-chunk 1024`. The GEMM is 25 to 42 % of the spec-sheet bf16 peak (about 190 TFLOPS, not re-measured) and flash attention about 13 %. Listed next steps, not done: double-buffered K loop with direct-to-LDS loads or `ds_read_tr`, 256-row tiles for N = 12288, a K/V-prefetching flash kernel, a hipBLASLt comparison. The gfx12 fp8 x fp8 WMMA was not used; `matmul_fp8_mma` dequantises e4m3 to bf16 tiles in LDS.

**Evidence.** `phase2a-hip.md` section 5, TFLOPS for q/o 4096x4096, gate 12288x4096, down 4096x12288: M = 64: 20.3 / 17.0 / 23.5; M = 256: 48.0 / 63.9 / 63.2; M = 1024: 73.1 / 73.5 / 72.2; M = 2048: 80.4 / 81.2 / 79.2. (`hip.md` "Not done" summarises this as "63-81 TFLOPS at M >= 256"; the table has 48.0 for q/o at M = 256.)

## 2. Separate HIP headers, wave32 only

**Context.** `kernels/common/ik_portable.h` defines `IK_WARP` as 64 for HIP. That is wrong for gfx12: the R9700 (gfx1201, RDNA4) is wave32 by default and the `__builtin_amdgcn_wmma_*_w32_gfx12` builtins require wave32. ROCm 7.2 accepts the `*_sync` shuffles only with a 64-bit mask, and the `hip_bf16.h` bf16 type changed between ROCm 6 and 7.

**Decision.** HIP kernels have their own header set. `kernels/hip/ik_hip.h` holds the wave32 helpers, bf16 on raw 16-bit patterns and launcher validation (`ik_check`, `IK_TRY`); it hard-sets `IK_WARP` to 32 and `#error`s on `-mwavefrontsize64`, and the backend refuses a device whose `warpSize` is not 32. Shuffles are `__shfl_xor(v, o, 32)`. bf16 is a plain `struct { uint16_t }` with software round-to-nearest-even, independent of `hip_bf16.h`. `kernels/hip/ik_runtime.{h,hip}` wrap the HIP runtime so the Rust side never sees `hipDeviceProp_t`. Quantised and MoE kernels share `ik_quant.h`, `ik_dq_gemm.h`, `moe_wmma.h`. The `cuda` and `hip` features of `intarsia-cli` are mutually exclusive, because both kernel libraries export the same `ik_*` and `ik_rt_*` symbols. The admission fingerprint contains the gfx arch, HIP runtime and driver versions, the `hipcc` version and the tuning knobs that are set.

**Alternatives considered.** Reusing `ik_portable.h`: not viable for gfx12, as above. No other alternative is recorded.

**Consequences.** The kernels need gfx12 (`INTARSIA_HIP_ARCH` defaults to `gfx1201`). The elementwise kernels are hipified from the CUDA sources; flash prefill is a rewrite on WMMA. `ik_rt_memcpy_h2d` synchronises the stream after `hipMemcpyAsync`, because pageable-memory copies do not promise the CUDA staging behaviour.

**Evidence.** `docs/backends/hip.md` "Differences from the CUDA sources"; `phase2a-hip.md` section 1 and 10.7 (30 kernels, 471 cases, all ADMITTED); Phase 2a review finding 7, fixed in 10.1 (`hipcc --version` in the fingerprint, base image pinned by digest, per-image cargo target volume).

## 3. HIP MoE tensor-core path, batch-variant, gated by `INTARSIA_HIP_MOE_WMMA`

**Context.** `moe_experts` has three paths: P <= 16 pairs and K <= 8 (decode) uses `moe_gate_up_p1` + `moe_down_reduce_p1`; T < 16 uses counting-sort grouping and grouped GEMV-style kernels with the same accumulation order; T >= 16 uses grouped bf16 WMMA (`moe_wmma.h`) with the tensor-core k order, so rounding differs. The first two are bit-identical to each other. At the Phase 2a branch point the CUDA backend had no tensor-core MoE path. Opus review finding 5: HIP MoE results depend on batch size.

**Decision.** The WMMA path stays on from T >= 16 and is switchable: `INTARSIA_HIP_MOE_WMMA=0` sends every T to the GEMV-style kernels, so a token's result is bit-identical to T = 1 in any batch. The knob is part of the admission fingerprint. Anything that needs batch-invariant MoE (lossless speculation claims, an `exact` mode) must run with it set to 0. `kMwMinTokens = 16` was not re-tuned.

**Alternatives considered.** Finding 5 was closed as "documented and gated, not made invariant by default" (`phase2a-hip.md` 10.1). Making the WMMA path follow GEMV order is not possible; the reverse (GEMV-style kernels accumulating in the WMMA k-permuted order) is the review's longer-term suggestion and was not done.

**Consequences.** The same prompt can give slightly different hidden states for a different `--prefill-chunk` or a remainder chunk under 16 tokens; prefix-cache reuse versus recompute is not bit-equal; a verify of 16 or more rows is not bit-equal to serial decode on MoE layers. The knob covers `moe_experts` only: the dense GEMV/GEMM switch (GEMV up to M = 4) and the attention split policy are batch dependent too. The registry has no per-kernel batch-invariance flag (open).

**Evidence.** Test `moe_experts_batch_invariance` (E = 32, K = 4, H = 512, I = 256, T in 2, 4, 7, 15, 16, 17, 48, 130): default gives 0 differing tokens for T < 16 and 10 of 211 for T >= 16 (last bits, rel_l2 below 1e-2); with the knob at 0, none differ at any T. Cost of the invariant mode, DRAM-cold, us per launch: T = 1 44.0, T = 4 148, T = 16 534 (757 with tensor cores), T = 64 1480 (1220), T = 256 3800 (1349). The GEMV path is faster below about T = 16 and 3x slower at T = 256. Tensor-core path history at T = 256: ungrouped GEMV style 11.9 ms, LDS-staged WMMA 3.3 ms, register-A WMMA 1.3 ms (`phase2a-hip.md` 9.2, 10.4; `hip.md` "MoE and batch size").

## 4. CUDA graph decode with device-side positions, and the ABI change

**Context.** The Phase 1a engine decoded the 35B at 63 to 65 tok/s against vLLM's 76 to 78. nsys on a native replica of the decode step (spark2, random weights, not the engine) showed GPU busy time of 13.5 ms eager and 13.3 ms graph, so about 1.8 ms (12 %) of the 15.3 ms eager step was host launch gaps. Replica step times: eager 15.3 ms (65 tok/s), graph 13.15 ms (76 tok/s), graph plus a side stream 12.58 ms (79.5 tok/s). Those replica figures used the 4-launch `ik_moe_experts_bf16`, not the engine's `moe_experts_decode_bf16`, so they are not engine numbers (corrected in the profile doc after Phase 1b review finding 9).

**Decision.** The decode step is captured once (`graph_capture` / `graph_replay`) and replayed. The position is a device tensor read when the kernels run, so the graph does not bake it in. ABI change in `ik_abi.h`: `ik_rope_bf16`, `ik_kv_append_bf16`, `ik_attn_decode_bf16` and `ik_attn_decode_bf16_splitkv` gained `const ik_tensor* pos` (i32 `[1]`, null = host `pos0`) before `stream`. Split-KV decode with a device position launches its grid at the length-independent maximum (the scratch bound); stage 1 derives the split count (`nsplit_eff`) on the device, surplus blocks exit and the combine kernel merges only the active splits, so the partitioning and every bit equal the host-position launch. Recurrent (GatedDeltaNet) state is restored by in-place copy, so captured buffer addresses stay valid. The plan prints a WARNING when graphs are disabled because decode kernels differ between positions. Graphs are off when the TP world size is above 1 (ADR-0006). The HIP backend adopted the ABI at the merge of `phase2a/hip` (88c5285) with a `device_pos` test; HIP itself has no graph capture (`supports_graphs()` is false). Commit f6ffaae.

**Alternatives considered.** Not done, rather than rejected: a second stream for independent branches (shared expert, GDN z/b/a projections; 79.5 tok/s on the replica) and fusions (GDN conv + gating + recurrence, rmsnorm + residual), which the replica puts at up to about 0.6 ms per token.

**Consequences.** Any backend implementing these four launchers must take the extra argument (HIP did at the merge). `bench speed --require-graphs` and the verdict stage fail on zero replays, and `/metrics` and the bench JSON carry replays, captures, eager and profiled steps. Review found no capture-safety problem (no host transfers, allocations or syncs while capturing). Replay after a mid-sequence GatedDeltaNet restore is covered by a CPU test (`crates/intarsia-models/tests/graphs.rs`, 6 tests); on the real 35B only a plain greedy decode was exercised, not a mid-sequence restore.

**Evidence.** spark1, 35B NVFP4, 256-step greedy, two prompts: token ids identical with `--no-graphs` (256 of 256), 256 replays, 1 capture, 0 eager steps; decode 73.20 / 72.52 tok/s graph against 64.33 / 63.48 eager (`phase1b.md` 7.4). A/B: ours-new has 640 replays and 0 eager or profiled steps at every size in every round; decode 72.32 / 71.81 / 69.62 tok/s at 128 / 1024 / 4096 prompt tokens against 65.45 / 65.07 / 63.08 for the pre-change build, about +10.5 % (7.5). `graph_pos_check.cu` 5717 checks, 0 failed; `cargo test ... graph_pos` 5 passed. HIP `device_pos`: bitwise device-vs-host position for rope, kv_append and both decode kernels at 9 positions up to 4090, split-KV against SIMT at every position (`phase2a-hip.md` 11.1).

## 5. Tensor-core MoE prefill accumulates k16 steps in fp32

**Context.** Phase 1b added grouped tensor-core MoE prefill (`moe_experts_mma_bf16`, `kernels/cuda/moe_grouped.cu`) and dense `*_gemm` kernels; prefill at 1024 tokens went from 874 to 2316 tok/s together. The first acceptance run failed the 35B per-prompt baseline gate. A bisect with `INTARSIA_CUDA_DISABLE` (35b-long decode, 320 positions, new build against old-build logits) gave mean 21-way KL 2.9e-12 (bit-identical, 0 flips) with `moe_experts_mma_bf16` disabled and 5.983e-3 (13 flips) with only the two `*_gemm` kernels disabled. The whole old-vs-new difference on the 35B is that one kernel; device-position rope, kv_append, the split-KV grid, the lm_head loader and graphs are bitwise neutral.

**Defect.** `moe_mma_kernel` passed the running fp32 sum as the C operand of `ik_mma_bf16_16816` for all 32 (gate/up) or 8 (down) k steps of 64. The tensor core's accumulate aligns operands to the larger exponent and drops low bits (it is not an IEEE add), so error grows with the number of steps. The mechanism is inferred from the effect of the fix; the SASS was not inspected.

**Decision.** Every k16 `mma` starts from a zero fragment and its result is added to the accumulator with an ordinary fp32 add (`float t[4] = {0}; mma(t, ...); acc += t`). Commit 0e77696 (bisect d9a60b1, test and comments ff69dd4).

**Alternatives considered.** Disabling `moe_experts_mma_bf16` restores the old logits bit for bit at the cost of the MoE prefill speed-up; not done. Kernel time at T = 256 / 1024 / 4096: `moe_experts_bf16` 5596 / 21043 / 91953 us against 2403 / 2972 / 6686 us. The dense `*_gemm` / `*_mma` kernels have the same in-mma accumulation, are bitwise equal to the old build, and were left alone; a k16 promotion there would be a separate, measurable change.

**Consequences.** The fix did not make the 35B gates pass (decisions 6 and 7). After it the kernel is as close to the exact result as the old kernel, yet old-vs-new KL is unchanged (5.6e-3 against 6.0e-3 on long decode), and two builds differing only in this accumulation differ by the same amount (mean KL 5.56e-3 long decode, 4.71e-3 short prefill). Why a one-step difference in a small fraction of outputs is amplified is not measured; top-8 routing flips are a hypothesis, nothing logged expert ids.

**Evidence.** Share of bf16 outputs differing from the CPU reference at the real layer shape (H = 2048, I = 512, 64 experts, top-8), T = 40 / 128 / 512: old kernel 0.01 / 0.14 / 0.12 %; mma before the fix 1.01 / 0.74 / 0.60 %; after 0.19 / 0.13 / 0.13 %. Worst admission rel_l2 3.377e-4 to 1.245e-4. Test `moe_experts_mma_is_as_accurate_as_old_kernel` (differing fraction at most 3 x max(old fraction, 0.1 %), rel_l2 at most 2.5 x old) is mutation-checked: the old kernel fails it (T = 128: 0.64 %, rel_l2 3.05e-4), the fix passes (0.14 %, 1.41e-4); the bound is tight on the fixed side (T = 512: 0.25 % against 0.33 %). `moe_experts_mma_is_independent_of_tile_height` guards tile edges, not the defect. Kernel cost: T = 1024 3019 to 3112 us (+3.1 %), T = 4096 6743 to 7002 us (+3.8 %); engine prefill unchanged (1276 / 2315 / 2407 against 1260 / 2316 / 2380 tok/s), decode 72.7 / 72.2 / 69.9 against 72.3 / 71.8 / 69.6 (`phase1b.md` 8.2 to 8.8).

## 6. Accuracy gate: 21-way tail-bucket KL, provenance-checked baselines, self-golden

**Context.** The 35B NVFP4 checkpoint runs only in vLLM, so its reference is a vLLM top-20 golden; vLLM serves an fp8 KV cache and we use bf16, so every 35B KL against it contains reference noise that was not separated. Opus Phase 1b review finding 1: the "before" baseline was to come from the new tree with `INTARSIA_CUDA_DISABLE` and `--no-graphs`, but several Phase 1b changes cannot be disabled and sat in both runs, the baseline stored no git revision, and unknown disable names were ignored. Finding 2: the baseline mean KL of about 6.5e-3 is dominated by reference noise, so the x1.15 margin allowed about 1e-3 nats of real regression.

**Decision, 21-way tail-bucket KL.** A top-k golden is compared with `KL(supp)` (renormalised on the reference's top-k support; blind to mass leaving it), `KL(21-way)` and a tail check. `KL(21-way)` is the KL over the partition {the 20 reference ids, everything else}: vLLM reports full-vocabulary log-probs, so the reference "other" bucket is `1 - sum(top-k)` and ours is our softmax mass outside the same ids. By the chain rule it is the 2-way {support, tail} KL plus `P_ref(support)` times `KL(supp)`, a lower bound of the full-vocabulary KL and the tightest available. It is the gated KL for top-k goldens. The floor also gates `|mean(tail us - tail ref)| <= 0.02` and no non-finite rows. Floors by class: bf16 top-1 >= 99.5 % and mean KL <= 1e-3; fp8 KL <= 5e-3; 4-bit (NVFP4) KL <= 3e-2, top-1 reported not gated.

**Decision, baselines with build provenance from the pre-change commit.** The "before" build is `4963b43` (the Phase 1a head) plus only the accuracy-harness files (`accuracy.rs`, `accuracy/baseline.rs`, `provenance.rs`, `selfgolden.rs`, later `envelope.rs`), built with `INTARSIA_BUILD_STAMP` (head, code-tree hash, dirty, overlay; `scripts/tree-stamp.sh`). The gate refuses a baseline whose head is neither `--pre-change 4963b43` nor an ancestor of the build under test (`--revlist`), whose tree is dirty beyond the declared harness files, or whose code tree equals the build under test; a baseline recorded with `INTARSIA_CUDA_DISABLE` set is refused, and disable names that match no kernel are an error. It also refuses mismatched golden, KV dtype, backend, activation dtype, fp8 mode, prefill chunk and decode positions. Margins: top-1 -0.3 pt (at least one position), mean and 21-way KL x1.15 (at least +1e-6), tail +0.002, largest single-position KL x2.5 (at least +1e-3); per prompt, KL x1.75 (at least +1e-5) and top-1 -1 pt (at least one position). Commit 7593cf7.

**Decision, self-golden gate.** `--write-self-golden` / `--self-golden` compare the new build with the pre-change build's own logits on the same weights. The dump keeps the top-64 log-probs (full-vocabulary normalised) of the prefill path and of the teacher-forced decode window. Default budgets: mean 21-way KL 1e-4, largest position KL 5e-3, top-1 flips 0.5 % of positions, mean `|tail difference|` 5e-4, worst prompt's KL 5 x the mean budget, no non-finite rows. On the 35B the acceptance script uses budget = max(default, 3 x noise floor), the noise floor being the pre-change build with SIMT instead of flash attention against its own dump. Basis of the defaults (Mac cpu, Qwen3-Reranker-0.6B): run-to-run noise of one build is zero (about 1e-14); prefill chunk 64 / 1024 and f32 KV are bitwise identical; f16 KV gives 2.7e-4 mean KL and 19 flips; the f64 `--reference` oracle 1.3e-3 and 26 flips.

**Alternatives considered.** Review finding 1 proposed building the pre-change HEAD in a worktree; the script builds `4963b43` plus the harness files instead (the pre-change engine has no baseline or self-golden support). None other recorded.

**Consequences.** The gate says which code produced a baseline and refuses a mismatch. The default self-golden budgets suit same-numerics changes only; TP against tp=1 fails them (section 11, ADR-0006). On the 35B the noise-derived self-golden budgets are loose (they admit a max position KL of 1.2 short and 59 long), so a self-golden PASS there is weak evidence; the x1.15 aggregate margins and the fixed per-prompt limits cannot separate a defect from a re-roll on that model (`phase1b.md` 7.3, 8.7).

**Evidence.** First acceptance build (9427039): 35b-short self-golden PASS, prefill mean KL 3.582e-3 (budget 9.723e-3); 35b-long PASS, 3.426e-2 (budget 8.751e-2). 8B: new against old mean KL 9.6e-11 prefill, 1.9e-12 decode, 0 flips. The same build FAILED the baseline gate on per-prompt limits with all aggregates fine (35b-short: `code` prefill KL 9.03e-4 to 1.775e-3, limit 1.590e-3; 35b-long: `long_code_4k` top-1 96.875 to 92.188 %, limit 95.31 %).

## 7. Accuracy gate: per-prompt limits from a measured noise envelope; fp32 goldens for dense models

**Context.** After the 35B gates failed (8.6) and were traced to noise (section 9 of the results doc), the old build itself failed its fixed-margin per-prompt gate when only an equally correct thing changed: SIMT instead of flash attention fails `35b-short` prefill `code` top-1 (100.0 to 97.7 %, limit 98.85 %); prefill chunk 1024 instead of 256 fails `35b-long` `chat_reuse_4k` top-1 and `|tail diff|` and `long_code_4k` decode top-1. Aggregates are not immune either: with chunk 1024 the old build fails the aggregate tail-bucket KL of `35b-long` prefill (4.49e-2 to 5.27e-2, limit 5.16e-2) and the aggregate decode top-5. The aggregates were kept hard as instructed; that is recorded as a finding.

**Decision, noise envelope.** `intarsia accuracy --write-noise-envelope E.json --noise-ref B.json --noise-perturb chunk|chunk=N|attn-simt|external:TEXT` reruns the same build with a declared perturbation against the unperturbed baseline and writes, per mode and prompt, the absolute difference of top-1, mean 21-way KL and mean `|tail diff|`; more perturbations into the same file keep the per-prompt maximum. `--baseline B.json --noise-envelope E.json` then uses per prompt `limit = baseline -/+ max(fixed margin, k x delta)` with `--envelope-k` defaulting to 2, and prints each limit with its source, the delta and the `k` that would be needed. The envelope is refused unless golden, run configuration and build match the baseline; aggregates keep their fixed margins. Without an envelope the per-prompt checks are unchanged and a warning is printed for models whose `config.json` shows experts or linear-attention layers. Code: `crates/intarsia-cli/src/cmd/accuracy/envelope.rs`; a deliberate-bug hook for sensitivity checks, `INTARSIA_CPU_MUTATE=<op,..>:scale=<f>` in `crates/intarsia-backend-cpu/src/fault.rs`, is off by default. Commits 4ad0eea, 37e5b79, ab688c8.

**This is a post-hoc gate change**, and the results doc says so: it was made after the 35B gates failed. Before it, `35b-short` and `35b-long` said FAIL; after it `35b-long` passes its baseline part and `35b-short` still fails. What was fixed in advance (script header of 4ad0eea): k = 2; perturbations SIMT attention + chunk 64 for `35b-short`, chunk 1024 for `35b-long`, SIMT on `35b-long` as held-out check; aggregates unchanged; and the prediction that `35b-short` decode fails an aggregate whatever the envelope does. The prediction held; k was not tuned afterwards. Nothing here shows the new kernel is right; it shows what the gate can and cannot tell.

**Known limits.**
1. k = 2 is not a calibrated false-positive rate. Monte Carlo of one upper-limit check (normal noise), fraction of correct builds that fail, by number m of real perturbations in the envelope: m = 1 13.6 %, m = 2 5.5 %, m = 3 2.7 %, m = 4 1.5 % at k = 2. A gate has about 2 modes x 10 prompts x 3 checks, so with one or two perturbations k = 2 flags some prompt of a correct build most of the time. Mac measurements (cpu, Qwen3-Reranker-0.6B, one-ulp matmul fault p = 4.7e-3 as the equally correct perturbation): with a 2-perturbation envelope both correct trials failed one prompt; with m = 4 and m = 7, 3 of 4 trials passed and the fourth failed `chat_system` on a single position (KL 0.15). Rule: a per-prompt failure with `k needed` below about 3 is inside the noise, above 5 it is not; a hard verdict needs at least 4 perturbations or a larger `--envelope-k`. The 35B window could afford one or two.
2. Sensitivity: attention output x1.05 and x1.01 fail the gate; x1.002 is indistinguishable from a correct build; the resolution is about a factor of 2 in rel_l2.
3. The envelope lacks perturbations that reach decode attention and MoE. `35b-long` has only the chunk perturbation, which does not reach the decode attention kernel (envelope delta 0). Held-out check: the old build with SIMT attention, judged against the chunk-1024-only envelope, FAILS `35b-long` decode (aggregate top-1 96.875 to 95.625 %, limit 96.56 %; `long_docs_12k` top-1 96.9 to 92.2 %, limit 95.3 %). The requirement "flash-vs-SIMT on the same build must PASS" is therefore NOT met for `35b-long` decode; a SIMT envelope for the long set (about 3 more minutes of GPU time) was not run. No MoE-kernel perturbation is in any envelope, because the old build has no second MoE kernel.
4. The Mac test model is dense and the hook flips bf16 output bits, so its envelopes say nothing about the 35B's noise.

**Decision, fp32 HF goldens as the default for dense models.** Dense models (Qwen3-8B, the 0.6B Mac model) are gated against an HF fp32 golden (`golden.py --dtype float32`: `qwen3-8b-fp32.safetensors`, 8 prompts, and `qwen3-8b-long-fp32.safetensors`, 10 prompts) with `--gate-class bf16`, plus the baseline gate with fixed margins. HF bf16 against HF fp32 has mean KL 5.6e-4 (short) and 6.3e-4 (long) against a floor of 1e-3, so a bf16 golden passes or fails the floor on its own noise. MoE, hybrid and quantised models (the 35B NVFP4) keep the vLLM top-20 golden, the class floor, a pre-change baseline and the envelope. The fp32 goldens were built on spark1 with vLLM down (HF transformers 5.15.1, torch 2.13.0); sha256 prefixes `7b8b0cdccaa46093` and `ab22f2047c566c25`.

**Alternatives considered.** The fixed per-prompt margins, which are what the envelope replaces: they fail equally correct builds on the 35B (above). Deriving the aggregate limits from the envelope too is named as the obvious next step and was out of scope in the window.

**Consequences.** The 8B CUDA engine passes the bf16 floor against both fp32 goldens: short prefill 100.00 % top-1 / KL 2.90e-4, decode 100.00 % / 3.24e-4; long prefill 99.65 % / 4.00e-4, decode 100.00 % / 3.33e-4. Against the bf16 golden the same engine reads short decode KL 1.12e-3 (FAIL), and tp=2 on the long bf16 golden fails at 99.44 % (8 flips of 1434, 7 allowed) while on the fp32 golden tp=2 passes at 99.51 % (tp=1: 99.58 %).

**Evidence and verdict.** Final Phase 1b accuracy verdict (`phase1b.md` 10.8): **FAIL, not accepted.** `35b-short` FAIL: decode aggregate mean KL 9.07e-3 to 1.506e-2 (limit 1.043e-2), tail-bucket KL 9.58e-3 to 1.556e-2 (limit 1.102e-2), max KL 0.241 to 1.329 (limit 0.602); `chat_multiturn` decode KL 1.67e-2 to 8.66e-2 needs k = 16.5. `35b-long`: baseline part PASS (per-prompt with the chunk-1024 envelope, aggregates), the absolute 4-bit floor FAILS as it does for the old build (prefill KL 4.273e-2 against 3.0e-2; old build 4.49e-2), held-out SIMT decode check FAILED. Prefix reuse is reported as PASS in 10.5 and 10.8 although 7.3 recorded the same gate failing on both builds; the results doc does not explain the difference. `8b-short` and `8b-long` PASS. The doc's own conclusion: Phase 1b accuracy is not shown to be acceptable on `35b-short`, and the gate as run cannot decide it.

## 8. `chat_reuse_4k` is a noise amplifier, not a defect

**Context.** On the 35B long golden, `chat_reuse_4k` (4631 tokens, the only long prompt that is not a multiple of 16) has prefill top-1 87.7 %, mean 21-way KL 0.257 and max position KL 28.8 against vLLM; flash against SIMT attention on the same build gives mean KL 0.175 and max 17.7, where the other prompts agree to 5e-3 to 1.2e-2. The question was whether a boundary, tail-tile or chunk defect sits behind it.

**Decision.** No engine defect was found and no engine fix was made. The prompt is treated as a noise amplifier and is not used to gate a kernel change at 1e-2 KL.

**Alternatives considered.** Options recorded for the owner, none taken: replace the prompt with one that ends its user turn with a question; keep it but gate only the question / continuation segments (about 0.003); take its budget from the measured same-weights spread.

**Consequences.** `chat_reuse_4k` cannot gate a kernel change, because even the chunk size moves its mean KL by 0.13. A test was added: the randomised shape sweep of `crates/intarsia-backend-cuda/tests/attention.rs` gained (rows, pos0) = (23, 4608), (7, 4624), (1, 4630); it passes on spark1 and a mutation (flash causal mask changed to `key > lim`) makes the sweep fail, but that the added cases are what catch it was not shown. Not done: identifying the mechanism, an fp32 reference of the 35B, separating vLLM's fp8 KV from our bf16 KV.

**Evidence** (`phase1b.md` section 9, commit faebb39).
- The result does not move with chunk size 64, 256, 1024 or 8192 (8192 is one chunk, so no later-chunk rope offset, KV append edge, GDN conv/state carry or non-aligned final chunk is involved), nor with truncation at 4608, 4624, 4631 (positions below 4608 are bit-identical); the last 23 positions are the quietest (mean KL 0.002 against 0.24 overall).
- Both attention kernels are correct on the real tensors: q / K / V / output of all 50 prefill-attention calls of three real 35B prompts, recomputed in fp64: flash max rel_l2 1.95e-3, SIMT 1.92e-3.
- Any change of the last bits is amplified: the same flash kernels at chunk 256 against chunk 64 or 1024 (only GEMM / MoE row tiling differs) give mean KL 0.13 to 0.14 on this prompt and 0.005 to 0.010 on `long_code_4k` / `long_docs_4k`, the size of flash against SIMT; about 100 of 4631 positions have KL > 1 in each pair.
- The amplification sits inside the open user turn: 70 % of the KL is on the 43 % of positions where some engine puts more than 10 % on `<|im_end|>`, `<|im_start|>` or `<|endoftext|>`. By segment (c256 against c64): system 0.012, user document 0.139, question and assistant prompt 0.010, generated continuation 0.0013. The same document as raw tokens without ChatML is 4 to 5 times quieter (0.0282 against 0.1330 with the system prompt and open user turn).
- vLLM shares it: where they disagree sharply on the true next token, vLLM is right and ours wrong at 6 positions, ours right and vLLM wrong at 5; ours against vLLM (0.19 to 0.27) is about 1.5 times ours against ours (0.13 to 0.17).
- Re-tokenising the five prompts with `tools/goldenlib.py` gives exactly the golden's ids (`reuse_split` 4521), so the golden tooling is not at fault.

## 9. Spark ops rules

**Context.** spark1 (GB10, 128 GB unified memory) became unreachable at about 01:50 on 2026-10-13: ICMP answered, TCP 22 accepted then timed out in banner exchange, vLLM refused connections. An 8B HF golden job (4.6k tokens, top-20) was running next to the 64 GB `spark1-vllm` reservation (`guidance`, `gpu_memory_utilization 0.5`). The results doc names memory pressure as the first suspect and states that nothing observed proves it (`phase1b.md` section 1). A unanimis capture (record 59325a1b, project intarsiaml, an unverified capture) records more: the hang lasted until about 06:57; the OOM killer took `nvidia-persistenced`, without which docker cannot start GPU containers; restarting it needs the operator's sudo password, since the NOPASSWD rule covers only `drop_caches`. That last part is not in the results docs and rests on the capture alone; the results doc only notes `nvidia-persistenced` active after the later runs. Opus review finding 7 flagged the original acceptance procedure for repeating the co-tenancy: one `--mem 40` lease covering a cargo build, 16k-context 35B accuracy runs and a 38 GB server beside the 64 GB vLLM.

**Decision.**
1. Never co-tenant heavy GPU jobs (golden builds, accuracy runs, benchmark servers) with the 64 GB vLLM on spark1. GPU work takes ONE exclusive fleetq slot with `--takes-down guidance` (`--mem` 100 GB, `MEM_LEASE_GB`: nothing else may use the box; the peak RSS of the 16k accuracy run was never measured, so this is a budget, not a measurement), and the vLLM container is stopped inside the lease. Builds run outside it, in a small shared slot (16 GB, `BUILD_JOBS` 8) with vLLM up.
2. The exclusive takedown is always undone by a trap (`scripts/phase1b-acceptance.sh`, EXIT INT TERM): stop our server (wait, then `kill -9`), kill any remaining `intarsia-acc/(new|old)/target/acc/release` process so an interrupted ssh cannot leave a 38 to 70 GB job next to the reloading vLLM, restart the vLLM container and wait until `/v1/models` answers, then release the slots. The orphan-kill path was exercised only in `DRY_RUN`. A memory pre-check requires each stage's need plus 20 GB headroom.
3. The spark1 vLLM container binds only the tailnet IP `100.120.88.104:8000` (host network, `--host 100.120.88.104`), not `127.0.0.1` or `192.168.1.95`. Scripts use `VLLM_HOST=100.120.88.104` for the health check, bench URL, `/metrics` poller and info capture.
4. Non-interactive ssh has neither `cargo` nor `nvcc` on `PATH`; the ssh wrappers export `~/.cargo/bin` and `/usr/local/cuda/bin`.
5. Leave the box clean. Scratch trees (`~/intarsia-acc`, `~/intarsia-dbg`, `~/intarsiaml-harness`) were deleted through fleetq slots after the runs; `~/intarsiaml` (the documented benchmark checkout) and `~/intarsiaml-golden` were kept. After a run check: container up, `/v1/models` answers (served name `guidance`), `fleetq status` shows `spark1-vllm up` and no slot held, `nvidia-persistenced` active.

**Alternatives considered.** Substituting spark2 for the A/B was rejected in the results doc: no cargo toolchain, no goldens or 35B paths, and its vLLM serves another role (`retro`). Otherwise none recorded.

**Consequences.** `guidance` is down for every GPU window: about 59 min in the acceptance run (08:17:55 to 08:50:11 and 08:51:12 to 09:20:10 minus three windows in which it served as the A/B arm), about 51 min for the bisect and final-gate windows (09:35:37 to 09:59:10, 09:59:33 to 10:26:46), and 23 min 16 s for the gate-calibration window (12:06:01 to 12:29:17). The trap restored it each time. In the A/B, vLLM is stopped while ours runs and is measured in the same lease. The repo docs do not establish the cause of the hang, only that the co-tenancy is the suspect.

**Evidence.** `phase1b.md` sections 1, 5, 7.1, 7.6, 8.1, 10.3; review finding 7; the script header and trap; unanimis record 59325a1b-ef4a-4a6d-9c3f-8127fa622eb8.

## 10. Radiance downtime rules on tatooine

**Context.** tatooine's two R9700 cards are held by the `radiance` service (`radiance-rank0`, `radiance-rank1`, 31 GB each in fleetq), which answers at `http://tatooine:8080/v1/models`. Any GPU burst for the HIP backend takes it down. The first Phase 2a downtime log listed five takedowns and about 16 minutes; `fleetq log` showed 13 takedowns and 29 min 02 s (five dense-model bursts 17 min 16 s, eight 35B bursts 11 min 46 s), with the longest wait after a release 43 s. In one case the lease was released before radiance answered: CPU-only job #1412 started on the same slots at 02:03:43, four seconds before radiance-rank0 was back (02:03:47). The cause was the burst script releasing the lease (or waiting a fixed 15 s) instead of waiting for `/v1/models`.

**Decision.**
1. Every GPU burst on tatooine runs under a fleetq lease with `--takes-down radiance`; tp=2 work is one job across both cards (`fleetq run --host tatooine-r9700,tatooine-r9700-2 --takes-down radiance --mem 30`). Single-card work sets `HIP_VISIBLE_DEVICES=0`.
2. Order: acquire the lease, `systemctl --user stop radiance`, run the work, `systemctl --user start radiance`, poll `/v1/models` until it answers, and only then release. If it has not answered after about 3 minutes, do not release.
3. Builds and CPU-only work run in `--mem 0` slots and do not touch radiance.
4. Batch stages into one burst (`scripts/phase2b-burst.sh` takes a stage list) and record the downtime from `fleetq log` in the results doc.

**Alternatives considered.** None recorded.

**Consequences.** Every rerun of a GPU check costs radiance downtime. fleetq's own "is back" marker lags the real answer by up to a few seconds.

**Evidence.** After the fix: the Phase 2a fix pass had 7 takedowns, 17 min 34 s in total, the longest 4 min; Phase 2b had 4 bursts, 7 min 03 s against a 90 min budget, plus 2 re-gate bursts, 1 min 19 s against 25 min; radiance answered within 15 s after every restart in Phase 2b, before the lease was released. The Phase 2a merge gates took about 3 minutes (`phase2a-hip.md` 8, 10.8, 11.2; `phase2b-tp.md`).

## 11. Open items

Recorded as they stand; none is resolved by this ADR.

1. **The Phase 1b speed gate FAILS.** Decode on the 35B (spark1, vLLM measured in the same lease, 3 of 3 rounds valid): ours 72.32 / 71.81 / 69.62 tok/s against vLLM 76.10 / 77.58 / 76.38 at 128 / 1024 / 4096 prompt tokens; the per-round gap is -3.6 to -7.1 tok/s against about 1 tok/s of noise (5.3 / 7.4 / 8.9 % behind, growing with context). After the k16 fix: 72.7 / 72.2 / 69.9 (3 reps, not paired with vLLM). Prefill is 1.8x to 2.7x faster than before but still 1.3x behind at 128 tokens, 2.4x at 1024 (2316 against 5652 tok/s) and 2.8x at 4096 (2380 against 6649). The cause of the remaining decode gap was not measured, and the as-shipped `--profile-every 16` round was not run. The vLLM arm uses fp8 KV, ours bf16.
2. **`35b-short` decode `chat_multiturn` is unresolved.** KL 1.67e-2 to 8.66e-2 over 16 positions of one prompt (needs k = 16.5), which alone moves the decode aggregates past their fixed limits. Whether it is routing-flip noise is untested: a MoE-kernel perturbation for the envelope (for example `moe_experts_bf16` against `moe_experts_mma_bf16` on the new build) does not exist, and nothing logged expert ids.
3. **The TP self-golden against tp=1 fails the default 1e-4 budget** (ADR-0006): mean 21-way KL 5.896e-4 prefill and 5.071e-4 decode (about 6e-4), max position KL 5.0e-2 and 1.5e-2, worst prompt 9.8e-4 and 2.0e-3; flips, tail mass and finiteness are within budget. tp=2 passes the absolute floor on both fp32 goldens. A TP-specific budget needs its own measured noise floor (a tp=2 envelope) and a separate decision; the default budgets were not loosened.
4. **HIP has no graphs** (`supports_graphs()` false). Decode runs eagerly at 844 launches per 35B step. The claim that about 4 of the 10.4 ms step is small-launch overhead is not established; per-kernel timestamps need `rocprofv3`, not tried.
5. **TP does not support the 35B hybrid / MoE / quantised formats.** GatedDeltaNet and MoE sharding and FP8 / NVFP4 shard loading refuse with `Unsupported`; step 6 of Phase 2b was not attempted. Also open there: vocab-parallel lm_head (rank 1 idles about 2 ms per token), graphs for tp > 1, persistent rank threads, the P2P all-reduce is two-rank only, fused all-reduce + RMSNorm.
6. Gates and calibration: the noise envelope has no decode-attention or MoE perturbation (so flash-vs-SIMT on `35b-long` decode does not pass); k = 2 is not a calibrated false-fail rate; the aggregates are inside the noise on `35b-long` too and are still fixed; `35b-long` prefill misses the absolute 4-bit floor for the old build as well; the prefix-reuse discrepancy of decision 7; the `chat_reuse_4k` options of decision 8; `8b-4k` has no golden (skipped); no baseline or envelope was recorded for the dense models; the model-level MoE-vs-HF test asked for in review is not built.
7. Kernel and tolerance debt: CUDA `quantmoe.rs` still has the single shared tolerance (1.5e-2 / 6e-3) while HIP's is 1.5e-2 / 1e-3; admission has no per-output-dtype tolerance; the registry has no batch-invariance flag; the dense `*_gemm` / `*_mma` kernels keep in-mma accumulation; the server and bench JSON do not record engine version, SHA or backend fingerprint.
8. HIP performance, not like-for-like with other engines: Qwen3.6-35B-A3B NVFP4 decodes at 94 to 97 tok/s on one card (about 2.2 GB per token estimated, 34 % of the 285 tok/s byte floor), against llama.cpp Vulkan Q4_K_XL 112 and vLLM-radiance MXFP4 141 tok/s (different formats and a different model generation). Prefill is 1.1k to 3.1k tok/s (1.1k at 128 tokens) and the fp8 projection GEMV reaches 47 to 75 % of 627 GB/s DRAM-cold.
