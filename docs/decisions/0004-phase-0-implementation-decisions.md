# ADR-0004: Phase 0 implementation decisions

_Drafted by fleet model `guidance` from the raw note; checked against the note by Claude 2026-10-12_

## Status
Accepted

## Context
Implementation decisions made by the Phase 0 build agents (workflow wf_f554d5ea-a45, 2026-10-12), accepted by Claude as the Phase 0 baseline. Each line: agent area - title: note.

## Decision
- **Resolver 3 and rust-version 1.90 workspace-wide**: Building on the Mac (rustc 1.99) must not select crates that spark1's cargo 1.90 cannot build. Resolver 3 is MSRV-aware, so Cargo.lock is resolved to 1.90-compatible versions; verified by cargo check --workspace --all-targets on spark1. Cargo.lock is no longer gitignored because the workspace ships a binary.
- **Core owns traits and the generic decoder; models owns loading; tokenizer behind a TextCodec trait**: intarsia-core has no tokenizer or TOML dependency. Recipe types live in core so the decoder can walk them; TOML parsing, safetensors, tokenizers and minijinja live in intarsia-models and plug in through RecipeLoader-free types, WeightSource and TextCodec. LocalEngine therefore sits in core and is shared by all backends.
- **Op set beyond the list in the plan**: Add, Logits, KvAppend, Sample: Residual add (last block), a Logits matmul with f32 output (lets GPUs specialise the lm_head GEMV), KvAppend (the cache write is its own op so attention kernels stay pure readers), and a Sample op with a deterministic uniform-draw input so device and host sampling agree. The engine currently samples on the host via core::sampler (same code as the Sample reference); Sample is registered and admission-tested but not required of GPU backends.
- **Out-of-place ops with a preallocated activation workspace**: No op aliases its input except KvAppend's in-place cache, which keeps kernel ABIs and reference semantics simple; the workspace (sized by prefill_chunk) is allocated once at load and is included in the memory plan. rmsnorm_add fuses residual add + next norm and returns both the sum and the normed value; the norm is applied to the sum as stored in the activation dtype, like a bf16 residual stream.
- **Two kernel sets on cpu-ref**: naive f64 oracle and rayon f32: ref_<op> (f64 accumulate, is_reference) is the oracle every other implementation is graded against; cpu_f32_<op> (rayon, f32 accumulate, deterministic by construction since parallelism is over independent outputs) is what the engine runs. Weights stay mmap'd bf16 (zero-copy via Backend::wrap_host) and are converted per row inside matmul. Argmax tie-break (lowest index) is part of the op contract.
- **Explicit kernel registration list, admission result in Registry**: Backend::kernels() returns Vec<KernelImpl> (no inventory/linkme, which break with nvcc static libs); register_kernel! macro mirrors the plan's syntax. AdmissionReport::apply marks Admitted/Rejected in a Registry; rejected kernels are unselectable. Pass criterion: rel_l2 <= tol.rel_l2 and max_abs <= tol.max_abs * max(1, max|reference|); Exact class and integer outputs require bit equality.
- **kv_dtype default is bf16, not the fp8_e4m3 shown in ARCHITECTURE 3.5**: Phase 0 GPU kernels target bf16 KV. fp8_e4m3 KV is already supported by cpu-ref (software conversion, admission-tested) and the recipe can set it, but no GPU kernel accepts it yet.
- **Single-sequence KV prefix reuse makes cached_tokens real**: The contiguous cache of the previous request is reused for the common prefix (always recomputing at least the last prompt token; disabled when a Recurrent slot exists). No radix tree or paging, as deferred by the plan. EOS counts toward completion_tokens (like vLLM) but is not emitted as a Token event.
- **Chat template precedence follows transformers**: chat_template.jinja first, then tokenizer_config.json chat_template; overrides: ChatTemplateSource::{TokenizerConfig, File} (CLI --chat-template-from-config / --chat-template-file). Verified against transformers on the Mac model, whose chat_template.jinja is a reranker template. minijinja is configured with trim/lstrip blocks, pycompat string methods, raise_exception, strftime_now and a Python-style tojson (', ' and ': ' separators, preserve_order).
- **Telemetry design**: one serde struct, sampled op timing: TelemetrySnapshot (schema_version 1, documented in docs/telemetry.md) with steps_total (monotonic watchdog counter), request lifecycle counters, token totals, KV fill, live device free memory (probe calls Backend::info), and per-op calls plus sampled time (timed_calls/time_ms) because GPU timing needs a sync (profile_every, 1 on cpu, 16 default on GPUs).
- **Bridge thread per request between the sync Engine and async axum**: Engine::submit returns a blocking std mpsc Receiver. A small named thread forwards GenEvents into a tokio unbounded channel and records TTFT and ITL on Done. When the HTTP response is dropped, the forward fails, the thread drops the engine receiver, and the engine cancels at its next token. A queued request keeps its bridge thread parked until the engine reaches it.
- **Histograms and Prometheus text are hand-written**: No prometheus crate. Gauges and counters come straight from TelemetrySnapshot (no duplicated counters). TTFT and ITL are not in telemetry, so the server keeps its own histograms. TTFT = Done.prefill_ms. ITL = decode_ms/(completion_tokens-1), observed with weight n-1, so it is a per-request mean, not true per-token jitter. Extra metrics added: intarsia_requests_finished_total{reason}, intarsia_op_calls_total{op}, tokens_used and tokens_capacity gauges, intarsia_info, and last-request tok/s gauges.
- **Content flattening and error flavors**: OpenAI content-part arrays and Anthropic blocks are flattened to plain strings before apply_chat_template, because the Qwen3 template calls string methods on content. Only text parts are accepted; image and tool blocks return 400. Errors use the OpenAI {error:{...}} shape or the Anthropic {type:error,error:{...}} shape depending on the endpoint.
- **Request defaults follow the API specs**: temperature defaults to 1.0 (OpenAI and Anthropic default), so deterministic output needs temperature 0. max_tokens defaults to the remaining context for OpenAI; the engine clamps it. It is required for Anthropic. n must be 1, and completions accept one prompt (string or token ids). A prompt at or over context_len is rejected up front with a 400. The model field is ignored and the served name is always reported.
- **Blocking engine calls run on spawn_blocking**: Tokenize, apply_chat_template, telemetry and info go through spawn_blocking. This keeps the 2 HTTP worker threads free, and /metrics and /events keep responding while a long prefill is running.
- **Dependencies added to [workspace.dependencies]**: axum 0.8 (http1, json, query, tokio; default features off), tokio, tokio-stream, futures-util, plus tower and http-body-util for tests. tokio-stream is declared in the server's Cargo.toml but not used in code yet.
- **Golden file lives outside the repo copy on spark1**: Another agent's `rsync --delete` of the repo to ~/intarsiaml/ wiped the first qwen3-8b golden and replaced it with the Mac file. I regenerated it into ~/intarsiaml-golden/, which repo syncs do not touch.

- golden.py has a --dtype float32 option: It lets us separate engine error from the noise in the HF bf16 reference. The noise result is recorded in docs/accuracy.md.
- ppl.txt is embedded in the binary with include_str!: `--ppl-file` overrides it. The default perplexity gate is 40; cpu-ref scores 28.8 on the Mac model.
- Default golden path is golden/<hf-repo-name lowercased>.safetensors: It is searched in ./golden, then in the repo's golden dir. `--golden` overrides it.
- Dashboard and bench logic live in crates/intarsia-bench; the CLI files are thin: Keeps the ratatui, ureq and SSE dependencies out of the other crates. The CLI only adds intarsia-bench and sysinfo, below the agent-owned marker. ureq is built with default-features=false, so it supports plain http only; this is documented, and https needs a tunnel.
- Prompt sizes are calibrated from server usage.prompt_tokens: A 0-sentence and a 200-sentence call give tokens per filler sentence, as localeval does. This works with any tokenizer and any server, and the actual prompt token count is reported per row.
- Optional request parameters are dropped on HTTP 400/422 and retried once: ignore_eos, min_tokens and stream_options are non-standard. Servers that reject them still get benchmarked, and a warning says which were dropped. A row with gen below --gen also warns.
- intarsia top derives live values from snapshot deltas: The snapshot has no live rates. Steps/s comes from steps_total deltas. Per-op share uses each op's sampled time_ms scaled by calls/timed_calls, smoothed with an EMA. The decode and prefill sparklines are last_*_tok_s and change only when a request finishes. Architecture-strip loads are defined in docs/observability.md: API from queue depth, scheduler from running/waiting, engine from steps/s against its recent peak, kernels from estimated busy fraction, device from KV fill.
- Wedge indicator in the Grafana dashboard: requests running+waiting > 0 while rate(intarsia_engine_steps_total[1m]) == 0, so a hung kernel with a live /metrics shows up. The doc includes the matching alert rule.
- doctor emits one JSON fingerprint that bench can embed: `doctor --json --out f.json` then `bench speed --fingerprint-file f.json` stores it under fingerprint.host. The default backend is auto (cuda if compiled in, else cpu). The bandwidth test uses the Backend trait's alloc/upload/copy/download, so it works unchanged once the CUDA backend exists.
- localeval target conventions: spark-intarsia targets spark-4e77:8090 with bandwidth_gbs=221 and gb_per_token=16.4, and uses structured=prompt because Phase 0 has no json_schema.
- Own cudart FFI through small C wrappers, no cudarc: All runtime calls (malloc, memcpy, streams, device properties, mem info, bandwidth probe) go through kernels/cuda/ik_runtime.cu. The Rust side never depends on cudaDeviceProp layout or CUDA-version-specific symbols, and the link is just libcudart, libcublas and libstdc++, which the system loader finds through ldconfig.
- build.rs degrades to a stub without nvcc: cuda is a default workspace member, so `cargo check --workspace` on the Mac must not need CUDA. Without nvcc (or with INTARSIA_NO_CUDA=1) the crate compiles to a stub and `create()` returns Unsupported. The target arch is configurable through INTARSIA_CUDA_ARCH (default sm_121). It is baked into the kernel registrations, and `create()` refuses a device of a different arch.
- cuBLAS GemmEx for the Fast matmul, native GEMV for decode: matmul_bf16 and logits_bf16 call cublasGemmEx (bf16 in, f32 accumulate, reduced-precision split-K reduction disallowed). They use a per-device handle and 32 MB workspace created in ik_rt_init_device, so no launcher allocates. matmul_bf16_gemv and logits_bf16_gemv are warp-per-row kernels for M<=4: 16-byte streaming weight loads, fixed shuffle-reduction order, registered Deterministic with priority 10 over cuBLAS. Alignment is checked per launch, with a scalar fallback.
- Attention is one block per (query, head) with online softmax: Simple and correct first, as the task allowed. Head dim up to 256; the predicate rejects larger. K and V are bf16 only. Scores use 128-key tiles with fixed-order reductions, so results are repeatable.
- kv_append also accepts an fp8_e4m3 cache: The core admission sweep runs a bf16-new/fp8-cache case that the shape predicate cannot exclude, so the launcher converts with saturating round-to-nearest-even, which is bit-identical to core's f32_to_fp8_e4m3. Attention does not support fp8 KV.
- Every backend entry point binds the device: The runtime keeps a per-thread current device, and the engine calls the backend from several threads, so each method calls cudaSetDevice first. A test exercises upload and download from other threads. Streams are created on demand and indexed by StreamId; stream 0 is non-blocking.
- Edited kernels/abi/ik_abi.h outside my listed area: The foundation report said the cuda agent adds the remaining launcher prototypes. Only the prototype block changed; the IK_DTYPE_* enum is untouched.
- Sample op not implemented on the device: The engine samples on the host from downloaded f32 logits and uses Argmax on the device only for greedy decoding.
- info() reports bandwidth measured at create: A device-to-device copy probe, about 244 GB/s on this box, counting read plus write traffic. It is not a pure read-stream figure.
- Gate the Mac 0.6B model against an fp32 HF golden at the default thresholds: The bf16 golden gives mean KL 1.247e-3 against the 1e-3 gate. HF bf16 is itself 8.7e-4 away from HF fp32 on this prompt set, while cpu-ref is 5.5e-4 from fp32. I generated an fp32 golden with golden.py --dtype float32 and gated against it, which passes at the defaults. The bf16 golden also passes with --max-mean-kl 2e-3. The default is unchanged and the choice is documented as an open decision: keep 1e-3, make it size-aware, or use fp32 goldens for small models.
- Serve with --max-seq 8192 for the benchmarks: The default context is 4096, so a 4096-token prompt plus 128 generated tokens would not fit. 8192 tokens of KV costs about 1.2 GB on the 8B.
- Report the floor two ways: The headline % of floor uses the task's 221 GB/s / 16.38 GB = 13.5 tok/s. Decode reads one row of the embedding table, so about 15.1 GB per token is read and the real floor is about 14.6 tok/s. The doc states both.
- Keep the server on 127.0.0.1 and reach it through an ssh tunnel: Port 8090 was never exposed on the LAN. The built-in bench ran on spark1 itself, and localeval went through ssh -L 18090:127.0.0.1:8090.
- No source changes made during integration: The pieces already worked together (workspace builds, lockfile is consistent on Rust 1.90, the CUDA path runs), so I only added docs, the bench JSON and the fp32 golden.
