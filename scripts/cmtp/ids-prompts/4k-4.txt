# Tuning

What you can change without touching code, how to measure the effect, and which changes alter the numbers the model
produces. Read [benchmarking.md](benchmarking.md) for the measurement rules (clocks, warmup, fleet slots) and
[accuracy.md](accuracy.md) for the accuracy gates; this page is the index of knobs.

**Rule of thumb.** A knob marked **numerics: yes** can change the output logits, so a speed number taken with it is
only worth quoting next to an `intarsia accuracy` run on the same settings. A knob marked **no** changes scheduling,
memory or logging only. Defaults are the recipe's and the code's; nothing below is on by default unless the table says
"on".

Everything here is measured the same way:

```sh
# 1. start the server with the setting (inside a fleetq slot on a fleet box)
intarsia serve --model /models/Qwen3-8B --backend hip --prefill-chunk 1024 --port 8090
# 2. speed: prefill/decode tok/s and % of the bandwidth floor, 3 reps, median
intarsia bench speed --url http://localhost:8090 --model Qwen3-8B --sizes 128,1024,4096 --gen 128 --reps 3 \
    --prefill-chunk 1024 --label chunk1024          # --prefill-chunk here only records the value in the JSON
# 3. numerics: top-1 / KL against a golden (only for knobs marked yes)
intarsia accuracy --model /models/Qwen3-8B --backend hip --golden golden/qwen3-8b.safetensors --prefill-chunk 1024
```

For logged comparisons against other engines, or an interleaved A/B, use `localeval speed` (see
[benchmarking.md](benchmarking.md#localeval) and the `local-model-bench` skill) instead of hand-written loops.
`intarsia plan show --model <dir> --backend <b> [--json]` prints the values the loader resolved and where each one came
from (flag, recipe, default), so you can confirm a setting took effect before you measure.

## Flags (`serve`, `generate`, `accuracy`, `plan show`)

All of these are in the shared model-argument group of `crates/intarsia-cli/src/common.rs` unless noted.

An explicit flag wins, `--mtp-draft-vocab 0` turns the default off | **yes**, output unchanged, only acceptance moves | N=65536 on HIP: 27B +8 to +12%, 35B +2 to +5% on English and code; Chinese loses (acceptance 65.9% to 51.4%, 16% slower than the full head). CUDA and Metal are unmeasured for the 27B. Measure on your traffic; `--mtp-draft-vocab 0` for CJK-heavy 27B traffic |
| FP8 activations | `--fp8-act static\|none` | recipe `[defaults] fp8_act` | **yes** (W8A8 vs W8A16) | `accuracy` against a golden; decode tok/s |
| MXFP4 activations | `--mxfp4-act dynamic\|none` | what the checkpoint declares | **yes** | as above |
| Context and KV memory | `--max-seq N`, `--kv-fraction F`, `--mem-budget GiB` | 4096, 0.5, measured free memory | no | `plan show` prints the planned context; `bench speed --sizes` up to it |
| Step profiling | `--profile-every N` | every step on cpu, every 16th on GPUs, never for `serve` on metal; 0 = never | no, but profiled steps are slower and bias throughput | **Use `--profile-every 0` for every number you will quote**; use 1 only to read the per-op table (`generate --op-table`) |
| Reference kernels | `--reference` | off | **yes** (f64 oracle kernels; fails at load on backends without reference kernels, e.g. cuda) | accuracy oracle, not speed |
| Admission | `--admit`, `--no-admission-cache` | `serve` always admits | no | `intarsia kernels test --model` |

Two of these have recipe defaults you can change permanently instead of passing a flag each run: `[tuning]` /
`[tuning.<backend>]` `prefill_chunk` (and `prefill_peel`) and `[defaults]` `kv_dtype`, `max_batch`, `fp8_act`. See [recipes.md](recipes.md).
Only commit a recipe tuning value together with the measurement behind it (a comment citing `docs/results/...`), as
`recipes/qwen3_5_moe.toml` does.

## Environment variables

Every `IA_*` name that appears in `crates/`, `kernels/`, `scripts/`, `tools/` or `.github/` has a row. A test
(`crates/intarsia-cli/tests/docs_env_vars.rs`) fails when a name exists in the code and is missing here, or a row names a
variable the code no longer mentions or cites a file that does not contain it, so this table cannot drift silently. Add
a row when you add a variable. `file:line` is where the variable is read, as of the last edit of this table; the file
is checked, the line number is not.

Columns: **Default** is the behaviour when the variable is unset. **Numerics** says whether moving it away from the
default can change the computed values: `yes`, `no`, `n/a` (test, bench or build harness, not a runtime feature) or
`unverified`, meaning the code makes no bit-identity claim, so treat it as `yes` until an `accuracy` run says otherwise.
A `yes` on a variable that is on by default describes the default path itself; it is not a change. Opt-ins that change
numerics (`IA_CUDA_FAST_PREFILL`, `IA_CUDA_MOE_NVFP4`, `IA_TP_FUSION`, ...) stay off until measured.
